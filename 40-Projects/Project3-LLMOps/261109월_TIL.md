## 💡 오늘의 작업 총평

오늘 제일 크게 배운 건 두 가지다.

**1. 점수가 낮은 것과 답이 틀린 것은 다르다.** 리허설 결과에서 한 답안(S-FINAL-13)은 Faithfulness가 0.5였는데, Judge 4칸은 모두 1이었고 원문 대조 결과 답도 맞았다. RAGAS에 다시 물어보니 답변을 주장 4개로 쪼갠 뒤 2개를 "문맥에 없다"고 봤는데, 그 두 개가 **질문에서 온 값**("10월 31일", "열 상자")이었다. 발제 규칙대로 문맥(`retrieved_contexts`)에만 근거를 찾으니, 질문의 사실에 문서의 규칙을 적용한 정확한 답도 낮게 나온다. **지표는 정의대로 계산됐고, 정의가 우리가 보고 싶은 것의 일부만 본다.** 그래서 점수 하나가 아니라 4칸을 같이 쓰는 이유를 직접 확인했다.

**2. 방식 간 차이를 해석하기 전에 채점기가 일관적인지 먼저 재야 한다.** 방식별 평균은 hybrid_rerank가 근거·조건·Faithfulness는 가장 높은데(1.00, 1.00, 0.96) 판단만 가장 낮았다(0.80 대 0.93). 그런데 원문을 읽어 보니 판단 0점 3건은 모두 **다른 방식이 같거나 더 못한 행동을 하고도 1점을 받은 경우**였다. 거의 같은 답변에 한쪽은 1, 한쪽은 0이었다. 시험 답안 10장×3회에서는 흔들림이 0이었지만 **실제 답안에서는 아직 안 재 봤다.** "hybrid_rerank는 판단이 낮다"를 그대로 비교표에 쓰면 채점기의 흔들림을 검색 방식의 성질로 오해할 수 있다. 내일 이 흔들림을 먼저 잰다.

| 확인 | 결과 |
| :--- | :--- |
| 리허설 45건 채점 (질문 15 × 3방식, 서비스 오류 0건) | 평가 불가 0칸, 해당 없음 0칸, `--workers 4`로 약 7분 |
| Faithfulness 3회 채점 135번 중 실패 | 0번. 45건 중 14건은 회차마다 점수가 달랐음 (한 번만 쟀다면 그만큼 흔들렸을 것) |
| 방식별 Faithfulness 평균 | naive 0.86 / hybrid 0.86 / hybrid_rerank 0.96 |
| 방식별 판단 평균 | naive 0.93 / hybrid 0.93 / hybrid_rerank 0.80 (**해석 보류**, 위 2번) |

## 🎯 작업별 핵심

### 1. 점수가 팀 Langfuse에 안 붙는 원인 (이슈 확인)

실제 전체 실행에서 점수 기록이 실패했다. 원인은 코드가 아니라 **서버와 SDK의 버전 불일치**였다. SDK 5.1.0은 점수를 배열로 보내는데 팀 서버 3.227.0은 객체만 받아서 400으로 거절했다. platform 담당이 서버를 v4(4.76.0)로 올려 점수 저장이 복구됐고, 내가 점수 5개가 한 트레이스에 붙은 것을 화면에서 확인해 캡처를 이슈에 첨부했다. 새 서버는 점수를 API로 조회할 수 없어서(404) **화면에서만 확인할 수 있다**는 것도 알게 됐다.

### 2. Faithfulness 흔들림은 3회 평균으로 (PR 99, 머지)

gpt-6-luna는 temperature를 못 고정해서 같은 답안도 점수가 달라진다. 주장이 하나뿐인 짧은 답은 0과 1 사이를 오간다. 내가 "그냥 3회 평균이 더 안정적이지 않나"라고 물었고, **방식 간 차이가 이 흔들림보다 작으면 방식 때문인지 우연인지 알 수 없다**는 이유로 정했다. 회차별 점수를 따로 남겨 달라는 것도 내 요청이었다(나중에 흔들림을 분석할 자료). 실제 AI 12건에서 실패 0, 회차가 달랐던 답안 2건, 시간은 104초였다.

### 3. 코드 정리: 파일 13개 → 9개 (PR 115, 머지)

내가 "**없어도 되고 + 있어도 해가 없는** 파일은 합쳐라"는 두 조건을 줬고, Claude가 파일마다 판정했다. 일회성 확인 도구 2개 삭제, 흔들림 측정 도구는 `calibrate --repeat`으로 합침, `platform_adapter`는 해체, 정답 읽기는 metrics 로더 하나로 통일했다. **의존이 생기는 정답 읽기만은 조건에 안 맞아 처음엔 뺐다가**, 내가 "문제가 생기면 그때 요청하자"며 오늘 하자고 해서 진행했다. 대신 로더가 바뀌면 알려 주는 테스트를 같이 넣었다. 규모는 18개 파일, +144/−369줄이다.

### 4. 리허설 결과 첫 채점과 원문 대조 (Claude가 발견한 것 중심)

metrics가 넘긴 45건을 팀 값으로 채점했고, 사례 12건을 원문과 대조해 읽었다. 발견한 것은 다섯 가지다.

| 발견 | 내용 |
| :--- | :--- |
| 상태 불일치 (judge 밖) | 기대가 보류·되묻기인 18건 중 상태가 기대와 맞은 것은 5건. 행동은 보류인데 상태는 `answered` |
| 되묻기 누락 (answer 쪽) | 되묻기 문항에서 세 방식 모두 관련 접수일을 묻지 않았고, hybrid는 오늘 날짜(11/9)를 기준으로 경로를 안내함 |
| 엄격도의 일관성 | 필수 사실의 일부를 빠뜨렸을 때, 절차("화주에게")는 1점으로, 구체 값(주소·정의)은 0점으로 채점. 기준이 섞임 |
| 판단 칸 불일치 | 거의 같은 행동에 1점과 0점. hybrid_rerank의 판단 0점 3건 모두 해당 |
| Faithfulness의 한계 | 질문에서 온 값은 문맥에 없다고 보아 낮게 나옴 (총평 1) |

## ⚠️ 오늘의 함정 모음

**1. 결과 폴더가 레포에서 제외되지 않았다** (Claude가 발견)
metrics가 "답변·문맥이 든 파일이라 저장소에 올리지 말고 비공개로만"이라고 했는데, `results/`는 `.gitignore`에 없어서 `git add .` 한 번이면 올라갈 뻔했다. 레포 파일은 안 건드리고 내 PC에서만 제외했다. **규칙이 문서에만 있고 도구에는 없는 곳**이라 팀에도 알릴 만하다.

**2. 설명이 길면 안 읽힌다** (내 피드백)
코드 설명이 길고 어렵다고 여러 번 말했고, 이후 한 줄 요약 → 비유 → 표 순서로 바꿨다. 팀원에게 내 작업을 발표로 설명하려면 같은 훈련이 필요하다.

**3. 쉘 문법을 잘못 줬다**
내 터미널은 Windows PowerShell 5.1이라 `&&`를 못 쓰고, 꺾쇠 자리표시(`<run_id>`)를 그대로 치면 오류가 난다. 한 줄에 명령 하나, 자리표시는 실제 값으로 쓰기로 했다.

**4. `.env.example`을 실수로 고쳐 둠**
별명을 예시 파일에 적었다가 `git restore`로 되돌렸다. 실제 값은 `.env`에만 둔다.

**5. 아직 못 푼 것** — 팀 값으로 실행했을 때 스팬 내보내기 시간 초과 경고가 한 번 나왔다. 원인은 아직 모른다.
