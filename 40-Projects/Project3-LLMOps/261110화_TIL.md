# TIL — "채점기를 먼저 재고, 확인한 사실만 팀에 넘기고, '있으면 좋은' 코드는 지운다"

> 11/10 하루 한 작업이다. 3차 프로젝트(해운 Basic, PDF 15개 기반 RAG 질의응답 서비스, 5명 팀)에서 나는 **judge(LLM 평가)** 담당이다. 오늘은 네 가지를 했다. 오전에 **채점기 흔들림과 사람 판정을 사전 등록한 기준으로 측정**했고, 오후에 그 결과를 **metrics와 팀에 넘길 자료**로 만들어 슬랙으로 보냈고, **질문 1번당 토큰 사용량**을 정리했고, judge 코드를 **반드시 필요한 것만 남기도록 정리**하는 PR을 올려 머지했다.
>
> **역할 분담** — 코드, 테스트, 문서, PR 본문 초안은 Claude가 작성했다. 나는 방향 결정, 사람 판정, 승인, 팀 전달(슬랙), 머지를 맡았다. 특히 "**발표는 platform이 하고 나는 자료 지원**", "**사실에 근거한 내용만 쓰고, 그래서 뭘 해야 하는지까지**", "**조건·근거도 해석 보류로 표시**", "**채점 원본 데이터도 같이 보내되 분리해서 쓰라고 명시**", "**'있으면 좋다'는 코드는 필요 없는 코드일 수 있다. 반드시 있어야 하나?**"는 내 판단이다. 아래에서 "Claude가 발견한 것"과 "내가 정한 것"을 구분해서 적는다.
>
> **강의 연결** — [LLMOps 11/02][ops1102]의 **회귀 판정**(바꾼 뒤에도 결과가 같은지)은 코드 정리 PR을 다른 PR과 합쳐 시험하는 데에, [LLMOps 11/03][ops1103]의 **운영 지표와 토큰**(평가 호출을 서비스 사용량과 분리)은 토큰 사용량 문서에 쓰였다.

## 💡 오늘의 작업 총평

오늘 제일 크게 배운 건 두 가지다.

**1. 채점기 점수는 "맞나"와 "매번 같나"를 따로 재야 한다.** 사람이 원문을 보고 채점한 것과 비교하면 60칸 중 58칸이 같았다(97%). 그런데 같은 답안을 3번 다시 채점시키면 판단 칸은 84%만 같았고, 조건·근거·판단은 **3번 채점할 때마다 세 방식의 순위가 바뀌었다.** 점수가 사람과 맞아도, 다시 채점하면 순위가 바뀌는 칸으로는 "어느 방식이 더 좋다"고 말할 수 없다. 측정 전에 정해 둔 규칙("순위가 한 번이라도 바뀌면 그 칸의 방식 비교는 해석 보류")대로 세 칸을 해석 보류로 정했다.

**2. 팀에 넘기는 문서에는 확인한 사실만 쓴다.** 처음 만든 전달 문서에 "판단 칸은 애매한 질문일수록 흔들린다"는 문장이 들어갔다. "추정"이라고 표시했지만 원인을 확인한 적은 없었다. 내가 "왜 사실에 근거한 주장만 해야 하는데 추측이 있냐"고 지적했고, 문서를 **확인한 것 / 기준 / 결과 / 확인하지 못한 것 / 그래서 할 일**로 다시 썼다. 다시 쓰면서 규칙을 다시 읽으니, Claude가 앞에서 한 말("사실·조건·근거는 그대로 써도 된다")도 일관률 기준만 본 **틀린 설명**이었다.

| 확인 (리허설 45건 기준) | 결과 |
| :--- | :--- |
| 흔들림: 45답안 × 3회 = 135번 채점 | 호출 실패 0. 3번 모두 같은 점수: 사실 100% / 조건 91% / 근거 93% / **판단 84%** |
| 방식 순위 | 조건·근거·판단은 3번 채점마다 바뀜 → **해석 보류** |
| 사람 대조 (독립 표본 15답안, 60칸, 방식 이름 가림) | 독립 판정 58/60 = **97%** (기준 85%), 재확인 후 60/60 |
| 코드 정리 PR (머지) | `src/judge/` 파일 9개 → 7개, 11개 파일 +75 / −396줄, 전체 테스트 222개 통과 |

## 🎯 작업별 핵심

### 1. 채점기 흔들림과 사람 판정 (오전)

**흔들림**: 같은 답안의 Judge 4칸을 3번 더 채점했다(135번, 실패 0). 사실·조건·근거는 일관률 90%를 넘었지만 판단은 84%였다. **판단 칸이 왜 흔들리는지는 아직 확인하지 못했다.**

**사람 판정**: 이미 점수를 본 사례를 빼고 15답안을 방식 이름을 가린 채 판정했다. 58/60(97%)이 같았다. 다른 2칸은 같은 답안의 근거·판단이었고, 둘 다 "사람 0, 채점관 1"이었다. 내가 "판정에 실수가 있었을 수 있다"며 다시 봤고, 인용 조각에 근거 문장이 있어 두 칸 모두 1로 고쳤다. 다만 **채점관 점수를 본 뒤의 재확인**이라 독립 판정이 아니다. 그래서 97%와 100%를 둘 다 보고한다.

판정하다가 내가 "원문이 어떻게 처리됐는지 보여 줘야 판정할 수 있다"고 요청해서 참고 부록을 붙였다. 채점관은 못 본 정보라 "사람이 보는 것 = 채점관이 받는 것" 원칙에서 벗어난 점을 기록했다.

### 2. 팀에 넘길 자료 (오후)

발표는 platform이 하고, 나는 ④ 품질 평가 자료를 지원한다(내가 정함). 슬라이드 초안 5장과 발표자용 질의응답 표를 만들었다.

metrics 전달 문서는 내 요청으로 **왜 했나 / 무엇을 / 어떤 기준 / 결과 / 그래서 할 일** 구조로 바꾸고, Judge 4칸이 무엇인지 설명을 추가했다. 그 과정에서 정한 것:

| 결정 | 내용 |
| :--- | :--- |
| 해석 보류 범위 (내가 선택) | 판단만이 아니라 **조건·근거·판단 세 칸 모두**. 규칙은 칸별로 정한 것이라 일부만 적용하면 반만 지키는 셈 |
| 숫자 처리 | 점수는 지우지 않고 그대로 두고, "이 차이로 우열을 말하지 않는다"는 표시만 붙임 |
| 원자료 전달 (내 제안) | 설명서만으로는 상대 AI가 형식을 모르니 채점 원자료도 함께. 대신 연습용 별도 폴더, 최종 결과와 섞지 말 것, 정답·원문은 검색·생성에 쓰지 말 것을 명시 |

### 3. 질문 1번당 토큰 사용량

리허설 run에서 집계했다. 서비스 호출은 질문 1번당 **입력 2,601~2,707 / 출력 303~372 토큰**, 답안 1개 채점은 **입력 약 13,000 / 출력 약 3,199 토큰**이다. 채점이 입력은 약 5배, 출력은 약 10배다(Faithfulness 3회 + Judge 4칸). 저장소 어디에도 단가가 없어서 금액은 계산하지 않았고, 두 숫자는 더하지 말라고 적었다(평가 호출은 서비스 지표와 분리).

### 4. 코드를 반드시 필요한 것만 남기기 (PR 122, 머지)

내가 "**'있으면 좋다'라고 느껴지는 코드는 사실 필요 없는 코드일 수 있다. 반드시 있어야 하나?**"라는 기준을 줬다. 기준은 ① 발제 필수 항목에 필요한가 ② 팀 규칙(데이터 손실 방지, 계약)에 걸리나 ③ 최종 채점에서 실행되나.

| 변경 | 이유 |
| :--- | :--- |
| 내 PC 전용 우회 스위치 삭제 (내가 먼저 의문 제기) | 만든 이유(platform의 temperature 문제)가 해결됨. 켜 둔 채 채점하면 측정·Langfuse 기록이 빠짐 |
| 시험지 도구 2개와 테스트 삭제 (내가 의문 제기) | 11/5 결과는 spec에 남음. 프롬프트가 11/5 이후 한 줄도 안 바뀌었고 고칠 계획도 없음 |
| Faithfulness 반복 평균을 `score.py` → `ragas_eval.py` 이동 (SoC) | Faithfulness 로직은 한 파일에, `score.py`는 조립만 |
| 같은 값을 두 번 지정하던 호출, 시험용 실행 옵션, 쓰이지 않는 예외 처리 삭제 | 아무도 쓰지 않음 |

남긴 것도 기준으로 설명할 수 있다. **이어하기(중간 저장)**는 데이터 손실 방지라 필수, **동시 채점(`--workers`)**은 필수는 아니지만 최종 채점 핵심 반복문이라 최종 채점 뒤에 다시 본다. `__init__.py`와 `README.md`는 다른 영역 5곳과 같은 팀 구조라 남기고 용도 설명을 적었다. RAGAS를 함수 안에서 늦게 불러오는 구조도, 불러오기에 약 4.4초가 걸린다는 측정값을 근거로 남겼다.

## ⚠️ 오늘의 함정 모음

**1. 추측이 팀 문서에 들어갔다** (내가 발견)
"추정" 표시가 있어도 읽는 사람은 원인을 아는 것처럼 받아들인다. 지우고 "확인하지 못함"으로 바꿨다. 앞으로 팀에 넘기는 문서는 **사실 / 기준 / 확인하지 못한 것 / 할 일**로만 쓴다.

**2. 규칙을 일부만 적용할 뻔했다** (Claude의 실수, 다시 쓰다 발견)
처음에는 "판단 칸에만 주석"이라고 넘겼다. 사전 규칙의 "순위가 바뀌면 해석 보류"는 칸별 규칙이라 조건·근거에도 걸린다. 이미 보낸 메시지가 있으면 정정본을 다시 보내야 했다.

**3. "있으면 좋다" 쪽으로 치우친 설명** (내 피드백)
시험지 도구를 두자는 Claude의 설명에 납득이 안 됐다. "나쁜 답을 잡는 유일한 근거"라고 했지만, 그 근거는 이미 11/5 결과로 기록돼 있었고 코드는 **다시 시험할 때만** 필요했다. 기준을 "반드시"로 바꾸니 결론이 분명해졌다.

**4. 이전 세션 작업을 "모른다"고 답했다** (내 피드백)
채점 명령을 물었을 때 Claude가 확인하지 못했다고만 했다. 이전 세션 기록을 검색하니 실행 명령이 남아 있었다. 모르면 **찾아볼 방법부터** 말해야 한다.

**5. 용어가 어려웠다** (내 피드백)
"해석 보류", "판단만 주석"을 그냥 썼다가 무슨 말인지 모르겠다고 했다. 예시 표(가짜 숫자로 표 모양 보여 주기)를 붙이고 나서야 통했다. 발표 자료도 같은 수준으로 써야 한다.

**6. 기억해 둔 메모가 낡았다** (Claude가 발견)
"다음 PR에 지울 함수"로 적어 둔 것이 이미 지워져 있었다. 메모를 믿기 전에 코드를 다시 확인하고, 틀린 메모는 지웠다.
