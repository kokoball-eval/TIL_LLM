# TIL — "빠르게 만드는 것보다 '결과가 같다'를 증명하는 것이 먼저고, 공유 환경에서는 PR 하나에 목적 하나"

> **역할 분담** — 코드, 테스트, 문서, PR 본문 초안은 Claude가 작성했다. 나는 방향 결정, 승인, 로컬 실행 확인, 푸시·머지, 팀 전달(슬랙·Notion)을 맡았다. 특히 "**기존 작동 방식과 흐름에는 영향이 없어야 한다**", "**실제로 로컬에서 돌려 보고 기대한 결과와 맞는지 확인하자**", "null 점수를 건너뛰는 게 **발제·팀 규칙·전체 구조 세 면에서 맞는지 먼저 검토**하자", "PR은 **목적별로 나누자**"는 내 판단이다. 아래에서 "Claude가 발견한 것"과 "내가 정한 것"을 구분해서 적는다.

## 💡 오늘의 작업 총평

이번에 제일 크게 배운 건 **최적화는 "빨라졌다"가 아니라 "결과가 같다"를 먼저 증명해야 끝난다**는 것이다.

채점이 오래 걸리고, 중간에 한 건이 실패하면 처음부터 다시 해야 했다. 그래서 동시 채점, 실패 격리, 이어하기를 넣었다. 하지만 속도를 얻는 대신 **결과 순서가 섞이거나, 점수가 달라지거나, 실패가 조용히 묻히면** 채점기를 믿을 수 없다. 그래서 변경 전 코드와 변경 후 코드를 **같은 340건**에 돌려서 결과 파일을 한 줄씩 비교했다.

| 확인 | 결과 |
| :--- | :--- |
| 가짜 AI 340건, 변경 전 vs 후 (1개씩·4개 동시, 오류 주입 포함) | 결과 파일과 점수 기록이 **완전히 같음** |
| 속도 (가짜 AI, 호출당 지연 포함) | 299초 → **78초** |
| 중간에 강제로 끊고 이어하기 | 한 번에 끝낸 결과와 **동일**, 저장된 건은 AI를 다시 안 부름 |
| 실제 AI 18건, 1개씩 vs 4개 동시 | 173초 → **51초**, 평가 불가 건수 같음(3건), Judge 4항목 72칸 중 **70칸 일치** |

두 번째로 남은 건 **공유 환경에서는 PR 하나에 목적 하나**라는 것이다. 한 브랜치에 속도 개선과 검증 도구가 섞여 있어서, main에서 새 브랜치를 따서 PR을 나눴다. 그리고 나눈다고 말해 놓고 PR을 하나만 올려서 헷갈리게 한 일이 있었다. 말한 것과 한 것을 맞추는 것도 작업의 일부다.

## 🎯 작업별 핵심

### 1. 임시 부품을 걷어내고 팀 코드에 연결해 머지 (첫 PR)

어제 구조 파악용으로 만든 채점 코드는 팀 공용 타입을 복사한 임시 파일(`_stubs.py`)에 기대고 있었다. 팀 `contracts.py`와 `platform`이 main에 들어온 뒤, 임시 부품을 지우고 `platform_adapter.py`를 **platform을 부르는 유일한 창구**로 만들었다. 채점 AI 호출은 `platform.llm.call(kind="eval")`, 점수 기록은 `tracing.record_score`다. 이 PR(15개 파일, +1,022줄)이 오늘 오전에 머지됐다.

### 2. 팀 호출을 연결하다 찾은 것 — temperature 문제

연결 후 실제 채점을 돌리니 **전부 실패**했다. 원인을 따라가 보니 팀 설정 `config.py`의 `GENERATION_TEMPERATURE = 0.0`이 `llm.py`에서 그대로 모델에 전달되는데, **gpt-6-luna는 0.0을 거부하고 기본값(1)만 받는다.** 더 어려웠던 점은 `llm.py`가 어떤 오류든 `model_error` 한 단어로 바꿔 던져서 **원인 문장이 코드에서는 안 보인다**는 것이다. 모델을 직접 불러 봐야 "does not support 0.0 with this model"이 보였다.

**정한 것**: 값이 비어 있으면 temperature를 아예 보내지 않도록 platform에 요청했다. 11/9 설정 동결 전에 필요하다. 내 PC에서만 쓰는 우회 스위치(`JUDGE_LLM=local`, 커밋 안 됨)로 실제 채점 시험은 계속했다. 오늘 main 최신에서도 아직 `0.0` 그대로라 답을 기다리는 중이다. **어제 "다음 날 확인"으로 남긴 의문이 풀렸고, 풀린 방향은 팀 코드에도 같은 문제가 있다는 것이었다.**

### 3. 속도·안정성 개선 4가지 (PR 76)

| 변경 | 쉬운 설명 | 왜 |
| :--- | :--- | :--- |
| `--workers N` | 답안 N건을 동시에 채점, 결과는 항상 원래 순서로 모음 | 시간 대부분이 AI 응답 대기라서 동시에 기다리면 줄어듦 |
| 실패 격리 | 한 건이 터져도 그 건만 "평가 불가: 사유", 나머지는 계속 | 하나 때문에 전체가 멈추면 안 됨 |
| `--resume` | 한 건씩 `.partial` 파일에 저장, 끊기면 이어서 | 이미 쓴 호출 비용과 시간을 버리지 않음 |
| 토큰 합산 규칙 통합 | `add_optional` / `sum_usage` 한 곳 | 규칙이 세 곳에 있으면 한 곳만 어긋날 수 있음 |

기본값은 `--workers 1`이라 옵션을 안 쓰면 **예전과 똑같이** 동작한다. 기존 동작을 바꾸지 않는다는 조건을 코드 구조로 지킨 것이다.

### 4. null 점수는 Langfuse로 보내지 않는다 — 세 면에서 검토 (PR 76에 포함)

실제 AI 테스트에서 Langfuse가 **값이 null인 점수를 거절**하는 걸 발견했다(원래 있던 동작이고 platform이 실패를 삼켜서 경고 로그만 쌓임). 곧바로 고치지 않고, 건너뛰는 게 맞는지 **세 면**에서 먼저 검토했다.

| 면 | 확인 결과 |
| :--- | :--- |
| 발제 요건 | null과 이유는 `eval.jsonl`에 이미 남음. 건수도 거기서 셈. Langfuse 필수 범위는 "질문·검색 문서·모델 입출력을 같은 요청 ID로"이고 점수 첨부는 필수가 아님 |
| 팀 규칙 | "측정 못 한 값은 None, 0으로 바꾸지 않는다"와 일치. platform 코드는 고치지 않고 judge 쪽에서 처리 |
| 구조 | judge가 platform을 쓰는 유일한 창구(`platform_adapter`)에서 걸러 한 곳에서 번역 |

그 결과 Langfuse 화면의 평균도 "null은 평균에서 뺀다"는 규칙과 자연스럽게 일치하게 됐다. 부작용도 하나 있다. Langfuse에서 점수가 비어 있으면 "해당 없음 / 평가 불가 / 아직 채점 안 됨" 중 무엇인지 화면만으로는 구분이 안 된다. 그래서 이유의 기준이 `eval.jsonl`이라고 spec과 README에 적었다.

### 5. 대표 사례 원문 대조 도구 (PR 78)

발제는 대표 사례를 사람이 PDF 원문과 대조하라고 요구한다. 실제 답안은 수백 건이라 손으로 고르면 시간이 모자라서, **사례를 고르고 인용한 쪽의 PDF 원문과 정답지 근거 쪽을 한 장으로 모으는** `review_sheet`를 만들었다. 고르는 기준은 다섯 가지다: 기대 동작과 판단 점수의 어긋남, Faithfulness와 4칸의 어긋남, 방식 간 결과 갈림, 해당 없음·평가 불가. 판정은 사람이 한다(자동 채점이 사람 확인을 대신하지 않음). 시험지·정확도·흔들림 측정 도구들도 함께 올렸다.

### 6. PR 분리와 충돌 해결

한 브랜치에 "속도 개선"과 "검증 도구"가 섞여 있었다. 팀 규칙이 **PR 하나에 목적 하나**라서 main에서 새 브랜치를 따 변경만 옮겼다. 먼저 올린 PR이 Squash로 머지되면서 두 번째 PR의 같은 문서(spec 11·12번 줄)와 충돌했다. 충돌 내용을 열어 보니 서로 다른 줄이라 **둘 다 살리는 쪽**으로 풀었다. 11번은 main 쪽(null 규칙), 12번은 내 쪽(원문 대조 시트 사용법)이다. 푸시 후 CI가 도는 동안 `BLOCKED`로 보이는 것도 직접 확인했다.

### 7. 문서·아티팩트 정리와 팀 정보 정리

머지 후 낡은 공부 자료(PR 현황 문서, 설계 노트, 채점 구조 가이드 아티팩트)를 현재 상태로 갱신했다. 팀 Notion에는 팀원별 직무명·역할·담당 Task·산출물 표를 스펙과 폴더 구조에 맞춰 검증해서 정리했다.

## ⚠️ 오늘의 함정 모음

**1. 이어하기가 엉뚱한 결과를 냈다** (Claude가 점검 중 발견)
이어하기를 (질문 ID, 검색 방식)을 열쇠로 저장했더니, 시험 데이터에는 같은 질문·방식이 여러 번 나와 **서로 덮어썼다.** 고유한 키 6개에 저장 28건이 들어가 결과가 틀리고 새 AI 호출이 0번이었다. 한 번에 끝낸 결과와 **비교해 보지 않았으면** 못 찾았을 결함이다. 지금은 "앞에서부터 순서대로 일치하는 구간만 재사용"하고 테스트로 고정했다.

**2. 실제 AI 테스트 점수가 내 Langfuse 클라우드로 전송됐다** (Claude가 미리 예상 못 함)
`.env`에 키가 있어서 실제 AI로 채점한 두 번의 점수가 그대로 올라갔다. 내 로컬 테스트용 키라 문제는 없다고 확인했지만, **"시험"이 외부로 흔적을 남길 수 있다**는 걸 기억해 둔다. 앞으로는 시험 때 키를 빼는 쪽이 안전하다.

**3. 같은 답안인데 Faithfulness가 1.0과 0.67**
실제 AI 비교에서 한 건이 이랬다. 속도 변경 때문이 아니라 RAGAS가 매번 주장을 다르게 뽑는 알려진 변동이다. **속도 최적화와 점수 변동은 따로 봐야 한다.**

**4. "PR 분리했다"고 해 놓고 하나만 올라갔다** (Claude의 소통 실수)
코드를 두 갈래로 나눴을 뿐 PR은 하나만 올렸는데, 그 사실을 분명히 말하지 않아서 혼란이 있었다. 이어서 "둘 다 진행하겠다는 거냐"는 질문에도 선택지와 제안을 한 문단에 섞어 써서 헷갈리게 했다. 이후로는 **무엇을 이미 했고, 무엇을 제안하고, 무엇이 내 결정을 기다리는지**를 나눠서 말하기로 했다.

**5. "PR 79"는 없었다** (내가 번호를 잘못 말함)
머지되지 않는다고 본 PR은 실제로는 78이었다. 충돌(CONFLICTING)이 원인이었다. 번호가 헷갈리면 목록부터 확인하는 게 빠르다.

**6. 새 규칙이 중간에 생겼다**
작업 중에 main에 "요청되지 않은 옵션이나 반환값은 넣지 않는다"는 규칙(ponytail)이 들어왔다. 내가 만든 `record_score`의 "보냈는지 여부 반환값"이 테스트에서만 쓰여서 군더더기였고, 그 규칙에 맞춰 지웠다. **병합 전에 최신 main의 규칙부터 읽는 것**이 중요하다.

**7. 직접 `git pull`이 막혔다**
내 수정 파일 8개와 main에서 들어온 변경이 겹치고, 커밋된 상태에서도 문서 두 곳이 충돌했다. 작업 중이던 변경을 stash로 치우고 병합한 뒤 되돌려서 해결했다. **작업 중인 변경이 있으면 pull 전에 어떤 파일이 겹치는지부터 본다.**
