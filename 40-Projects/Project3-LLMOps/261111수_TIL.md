# TIL — "점수는 AI가 매기고, 코드는 부탁하고 확인하고 모르는 값은 모른다고 남긴다"

> 11/11 하루 한 작업이다. 3차 프로젝트(해운 Basic, PDF 15개 기반 RAG 질의응답 서비스, 5명 팀)에서 나는 **judge(LLM 평가)** 담당이다. 제출(11/13)을 앞두고 오늘은 **내가 맡은 코드를 내 말로 설명할 수 있게** 공부하는 데 하루를 썼다. `rules.py`와 `judge.py`를 한 줄씩 읽었고, 그 사이에 **응답 상태값과 채점 기준**, **해운 문서의 업무 창구**를 정리했다. 작업으로는 **코드 지도 문서를 최신 코드에 맞추고**, **main에 빠져 있던 spec 수정 1건을 PR로 올려 머지**했고, **머지가 끝난 로컬 브랜치와 작업 폴더를 정리**했다.
>
> **역할 분담** — 설명, 문서 수정, PR 본문은 Claude가 작성했다. 나는 질문, 이해 확인, 머지, 정리 승인을 맡았다. "**비전공자도 이해할 수 있게 직관적으로**", "**말을 어렵게 하지 마라**", "**필요 없는 브랜치와 폴더는 지우자**"는 내 요청이다.
>
> **강의 연결** — [LLMOps 11/03][ops1103]의 **운영 지표와 토큰**(평가 호출을 서비스 사용량과 분리)이 오늘 읽은 토큰 합산 함수의 목적과 같았다.

## 💡 오늘의 작업 총평

오늘 제일 크게 배운 건 두 가지다.

**1. judge 코드의 철학은 "모르는 값을 0으로 바꾸지 않는다" 하나로 꿰어진다.** `rules.py`의 함수들이 전부 이 규칙을 지키려고 있다. 토큰을 더할 때 하나라도 모르면 합계도 "모름", 평균을 낼 때 빈칸은 빼고 0점은 넣음, 서비스 오류 답안은 판단만 0점이고 나머지는 "평가 불가". 빈칸을 0으로 바꾸면 `[1, 1, 0, 빈칸]`의 평균이 0.667에서 0.500으로 떨어진다. **채점할 수 없었던 것을 "틀렸다"로 처리하는 거짓 숫자**가 된다.

**2. 점수를 매기는 건 AI뿐이고, 코드는 부탁하고 확인하는 일만 한다.** `judge.py`를 읽다가 "검수하는 함수가 채점하는 건가, 진행 함수가 또 채점하는 건가" 헷갈렸다. 정리하면 **편지(채점 부탁) 쓰기 → AI가 채점 → 답에서 점수 부분 고르기 → 모양 확인 → 틀리면 한 번만 다시 부탁**이다. 코드는 점수를 새로 매기거나 고치지 않는다.

| :--- | :--- |
| 코드 공부 | `rules.py` 전체(함수 5개), `judge.py` 전체(함수 7개) |
| spec 수정 PR | main에 빠져 있던 "Langfuse 점수 연결 확인" 1줄 → PR 129 머지 |

| 자동 알림을 승인으로 착각하지 않나 | 삭제 도중 "명령이 끝났다"는 자동 알림이 왔지만 승인으로 보지 않고, 내가 직접 한 "모두 삭제" 요청을 기준으로 진행 |

## 🎯 작업별 핵심

### 1. 응답 상태값과 판단 채점 기준

상태는 4개다. 셋은 AI가 고르고, `error`는 API 코드가 붙인다.

| 상태 | 뜻 |
| :--- | :--- |
| `answered` | 근거가 충분해서 답함 |
| `needs_clarification` | **사용자 쪽 정보**가 빠져서 되물음 (예: 장비가 20GP인지 40GP인지) |
| `abstained` | **자료 쪽 정보**가 없거나 문서끼리 충돌해서 보류 |
| `error` | 시스템 오류로 답을 못 만듦 → 판단 0, 나머지 평가 불가 |

판단 칸은 기대 동작과 다르면 원칙적으로 0이고, **상태 이름이 아니라 실제 내용**을 본다. 판단은 되묻기·보류여도 항상 0 또는 1이다. 가장 애매한 건 "일부만 답하고 보류"인데, 판단 칸이 흔들리는 원인과 관련 있는지는 아직 확인하지 않았다.

### 2. 해운 문서의 업무 창구

창구 안내 문서(SB14)를 기준으로 선사 창구 5개(예약, 서류, VGM, 반입, 운항)의 역할을 정리했다. 채점에서 자주 걸리는 건 **창구끼리 대신하지 않는다**(반입 기록으로 적재를 확정하지 않음)와 **창구를 안내한 것 ≠ 요청이 끝난 것**이다.

### 3. `rules.py` 한 줄씩

| 부분 | 쉬운 말 |
| :--- | :--- |
| `LLMCall` | "부탁 편지를 주면 답장을 주는 곳"에 붙인 이름. 진짜 AI든 테스트용 가짜든 이 모양이면 끼울 수 있음 |
| `JUDGE_ITEMS` | 채점 칸 4개(사실·조건·근거·판단)의 고정 명단 |
| `add_optional`, `sum_usage` | **채점에 쓴 토큰**을 입력끼리, 출력끼리 더함. 모르는 쪽만 "모름" |
| `tag` | 빈칸 이유 앞에 칸 이름을 붙임. metrics가 칸별 건수를 셀 때 이 이름을 봄 |
| `precheck` | 서비스 오류 답안은 AI를 부르지 않고 판단 0, 나머지 평가 불가로 바로 처리 |
| `mean_ignoring_none` | 빈칸은 빼고 0점은 넣어서 평균 |

### 4. `judge.py` 한 줄씩

| 함수 | 쉬운 말 |
| :--- | :--- |
| `_load_prompt` | 채점 규칙 글을 처음 한 번만 읽고 기억 (세 방식이 같은 규칙을 쓰게) |
| `_format_context`, `_format_citations` | 서비스가 본 자료와 단 출처를 글로 정리 |
| `build_messages` | 위 글과 질문·답변(서비스 결과에서 그대로), 정답 기준을 모아 **채점 부탁 편지** 완성. "서비스가 본 자료"와 "서비스가 못 본 정답"을 구역 이름부터 나눔 |
| `_extract_json` | AI의 답에서 **점수가 적힌 부분만** 골라냄 (앞뒤 인사말은 버림) |
| `parse_judge_output` | 4칸이 다 있나, 점수가 0·1·빈칸인가, 이유가 있나, 판단이 빈칸이 아닌가 확인 |
| `judge_one` | 전체 진행. 모양이 틀리면 한 번만 다시 부탁, 그래도 안 되면 "채점 못 함" (0점으로 바꾸지 않음) |

### 5. main에 빠져 있던 spec 수정 (PR 129, 머지)

어제 코드 정리 PR을 머지한 **뒤에** 같은 브랜치에 spec 수정 1건을 커밋해서 main에 들어가지 못하고 있었다. 최신 main에서 새 브랜치를 만들어 그 커밋만 옮겼다. 내용은 "리허설 45건 모두 점수가 같은 요청의 트레이스에 붙고 값이 `eval.jsonl`과 일치"를 spec에 기록한 것이다.

### 6. 코드 지도 문서 최신화

오늘 main에 **새 검색 방식**(하위 질문으로 나눠 검색)이 추가됐다. judge 코드는 방식 이름을 공용 양식 파일 한 곳에서 읽어 와서 **한 줄도 고치지 않고** 새 방식까지 채점할 수 있다. metrics도 같은 방식으로 바꿨고, 비교표에 내가 요청한 **해석 보류 표시**를 넣었다. 문서에 이 두 가지와 "세 방식 → 모든 방식" 표현을 반영했다.

## ⚠️ 오늘의 함정 모음

**1. 설명이 너무 어려웠다** (내 피드백)
같은 개념을 "틀", "출입구", "어댑터", "이름표"로 계속 바꿔 부르고, 한 번에 여러 개념을 섞었다. 내가 "말을 왜 이렇게 어렵게 하냐"고 했고, 그 뒤로 **한 번에 한 가지, 쉬운 비유 하나로 통일, 용어는 꼭 필요할 때만**으로 바꾸니 통했다. 발표에서 내가 팀원에게 설명할 때도 같은 규칙이 필요하다.

**2. 작은 예시를 직접 실행하는 게 가장 잘 통했다**
"함수를 넘긴다", "자료 카드를 글로 옮긴다"는 말로는 안 와닿았는데, 진짜 AI·가짜 AI를 바꿔 끼우는 예시와 실제 함수 실행 결과를 보여 주니 바로 이해됐다.

**3. 머지한 브랜치에 계속 커밋하면 main에 안 들어간다** (Claude가 발견)
squash 머지 후 같은 브랜치에 커밋한 1건이 하루 동안 빠져 있었다. **머지 후에는 브랜치를 정리하고 새 브랜치에서 시작**해야 한다.

**4. 자주 헷갈린 것**
- 토큰 합산은 서비스 토큰이 아니라 **채점 토큰**
- 받는 쪽(서비스 결과 `RunRecord`)은 **읽기만**, 만드는 쪽(채점 결과)은 **채워서 내보냄**
- 편지(AI에게 보내는 것)와 답장(AI가 돌려준 점수)은 **다른 것**
