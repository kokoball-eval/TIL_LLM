## 💡 오늘의 작업 총평

오늘 제일 크게 배운 건 **7B 모델에게 규칙을 "문장으로" 가르치는 데는 한계가 있다**는 것이다.

프롬프트에 규칙을 한 줄 넣으면 고치려던 문항은 좋아지는데, 응답 64개 중 29개가 같이 바뀌었다. "트랙 A 결함은 개발 배정하지 않는다"고 쓰자, 모델은 처리를 바꾸는 대신 **분류를 "개선 제안"으로 바꿔서** 개발 배정을 유지했다. 규칙을 피해 간 거다.

그래서 방향을 바꿨다.

| 누가 | 무엇을 |
| :--- | :--- |
| 모델 | 판단 — 분류, 우선순위, 재현 정보 |
| 코드 | 형식 — 허용 값 밖이면 그 칸만 JSON 스키마로 다시 받기 |
| 코드 | 절차 — Critical은 무조건 리드 QA 사인 요청, 결함 제보는 폐기 전에 한 번 더 확인 |

최종 측정 결과가 이 설계를 그대로 증명했다. **코드로 강제한 항목(허용 값 위반, 언어 위반, 결함 폐기)은 처음 보는 리포트에서도 0건**이었고, **모델 판단 항목(Critical 놓침, 우선순위)은 개발용보다 크게 떨어졌다.** 개발용 문항을 보면서 고친 판단 규칙은 개발용 문항에만 통했다.

결과가 나빠진 건 아쉽지만, 측정 전에 "결과 보고 아무것도 안 고친다"고 정해 둔 덕분에 **진짜 실력이 어디까지인지** 알게 됐다. 이게 평가용 세트를 따로 두는 이유였다.

돌아보면 이번 버전은 강의 내용을 가장 많이 쓴 버전이다. 평가셋 분리와 최종 측정은 머신러닝의 봉인 Test 원칙, 형식 재요청은 프롬프트 엔지니어링의 JSON Schema·출력 복구와 LangChain의 1회 복구, 안전장치와 기록 방식은 fail loud와 Argument Validation에서 왔다. 그 위에 처리 규칙과 정답 라벨은 실무 경험으로 채웠다.

## 🎯 작업별 핵심

### 1. 평가셋 63건과 판정 체계 v2

**평가셋의 원재료는 내 경험이다.** 가상 게임 "Aether Raid"(모바일+PC 크로스플랫폼 RPG)를 설정하고, 채팅 인터뷰 4번으로 실무에서 어떤 제보가 들어오고 어떻게 처리했는지 답했다. Claude는 그 답을 판정 기준서와 문항으로 정리했다. 로드맵에 있던 "AI로 말투·오타 변형" 단계는 하지 않았다. 63건 모두 사람이 검토한 원문만 쓴다.

평가셋은 현업 인입을 닮아야 한다. 커뮤니티 원문(트랙 A)과 QA가 쓴 이슈(트랙 B)는 재현 정보의 질이 달라서 처리 경로도 다르다. 실무에서 실제로 그렇게 처리했기 때문에 이걸 판정 기준서 규칙(H-2, H-2b)으로 나눴다. 판정 칸도 실무 방식으로 바꿨다. `[심각도]` 대신 실무에서 쓰던 `[우선순위]` 4단계를 쓰고, **모델이 알 수 없는 건 묻지 않기로** 했다. 모델은 재현에 성공했는지 알 수 없으니 `[재현 여부]`를 버리고, 리포트에 적힌 정보가 충분한지(`[재현 정보]`)와 적힌 빈도(`[발생 빈도]`)만 옮기게 했다.

**자동화가 Critical을 직접 개발에 보내지 않는다.** `긴급 사인 요청`은 리드 QA가 확인하고 사인한 뒤 개발에 전달한다는 뜻이다. 1차 트리아지 자동화의 목표는 판단을 대신하는 게 아니라 **사람이 봐야 할 건을 빠짐없이 골라 넘기는 것**이다. [PE 09/11][pe0911] 8-1강의 "모델은 실행 요청만 작성하고 실행은 프로그램이 담당한다"는 실행 경계와 같은 생각이다. 여기서는 그 경계에 사람이 한 명 더 선다.

평가 지표는 [ML 08/14][ml0814]의 "목적별 평가지표 선택"을 따랐다. Critical 놓침(X-1)은 재현율 관점, 과잉 상신은 정밀도(오탐) 관점으로 따로 센다. 정답률 하나로 묶으면 드문 Critical 누락이 정확도 착시에 묻힌다. 실무에서도 Critical을 놓치면 라이브 장애 대응이 늦어지고, 괜히 올리면 리드 QA 시간이 든다. 비용이 달라서 X-1을 가장 무거운 실수로 뒀다.

평가셋은 개발용 32건과 평가용 31건으로 나눴다. [ML 08/11][ml0811]의 Train/Valid/Test 분리와 [ML 08/14][ml0814]·[ML 08/18][ml0818]의 **봉인 Test 원칙**이다. 나눌 때 위험 건(X-1~X-3) 문항을 먼저 번갈아 배정했다. 한쪽에만 Critical이 몰리면 비교가 안 된다. 평가용은 `--final`을 줘야만 실행된다. 정답 라벨의 원본은 생성 스크립트이고, 저장소의 JSON이 스크립트 결과와 같은지 테스트로 확인한다. 판정 기준서, 문항 설계, 검토 기록(배치 검토 5회 + 전체 검토 5회)도 남겨서, 라벨을 왜 그렇게 붙였는지 나중에 물어도 답할 수 있다.

### 2. 게이트 FAIL 5회 → 최종 구성 (ISSUE-007)

진행 순서는 이랬다. v2.1(원인 분석 반영) ❌ → v2.2(규칙 문장 추가) ❌ → v2.3 + 안전장치 ❌ → H-0 + 재요청 ✅ → v2.4 ❌(seed 3쌍으로 기각) → enum 재요청 ❌(A10 드러남) → 폐기 확인 질문 ✅ → 언어 재요청 ✅ → pattern 제한 ✅.

프롬프트는 [PE 09/11][pe0911] 6-1강의 Baseline 비교 방식으로 한 번에 하나씩 바꿨고, 매번 게이트가 같은 조건(평가셋·옵션·seed·모델 digest)인지 먼저 확인한 뒤 판정했다. [ML 08/18][ml0818]의 공정한 비교 계약을 게이트에 넣은 셈이다. 그런데 7B 모델은 한 줄만 바꿔도 전체가 흔들려서, **seed 하나로는 효과와 우연을 구분할 수 없었다.** v2.4를 기각한 근거는 seed 1의 FAIL이 아니라 seed 3쌍(1·11·21)에서 일관되게 나빠진 결과였다.

**`무관 중`을 처음 알아챈 건 나였다.** 결과를 보다 "분류가 무관 중인 건 뭐야?"라고 물었고, Claude가 원인을 찾았다. 프롬프트 표기 `…, 무관 중 택1`에서 "중"이 값에 붙어 버린 것이었다. 허용 값에 없는 값이 나오면 그 자체가 결함이라 "`무관 중`이라는 건 없어야 한다"고 정했고, 그래서 허용 값 위반 0건(R6)을 게이트 **절대 기준**으로 올렸다. [PE 10/02][pe1002]의 "'결제입니다.'는 의미상 맞더라도 형식 실패"와 같은 판단이다. 출력 계약을 어기면 다음 프로그램이 깨진다.

처음엔 텍스트로 "다시 써 줘"라고 재요청했는데, 모델은 `무관 중`을 그대로 되풀이했다. 그래서 **위반한 칸만 JSON 스키마로 다시 받는** 방식으로 바꿨다. 선택지 칸은 허용 값 목록(`enum`), 자유 서술 칸은 허용 문자 패턴(`pattern`)으로 생성 단계에서 제한한다. [PE 09/11][pe0911] 7-1강의 JSON Schema 구조화 출력과 8-2강의 "모델이 만든 인자는 신뢰할 수 없는 외부 입력, `pattern`으로 검증"을 그대로 쓴 부분이다. 재요청은 1번만 하고, 받은 값도 처음과 같은 형식 계약으로 다시 검증하고, 또 틀리면 첫 응답을 그대로 둔다. [LC 09/30][lc0930] 5-3강의 "검증 실패 → 1회 복구 → 같은 Parser로 재검증"과 [PE 09/11][pe0911] 7-3강의 "최대 1회 제한적 재요청"이다. 상한이 없으면 비용과 종료 시점을 예측할 수 없다. [LC 09/29][lc0929]에서 숨은 재시도를 `max_retries=0`으로 끄던 것처럼, 재시도는 한 곳에서 명시적으로만 한다.

**Claude가 발견한 것: `무관 중`을 고치자 A10의 X-2(결함 폐기)가 드러났다.** H-0이 우연히 폐기를 막고 있었던 거다. **형식 오류가 판단 오류를 가리고 있었다.** 결함 하나를 고치면 그 뒤에 숨어 있던 결함이 보인다. 폐기 직전 "이상 현상 제보 / 무관"을 한 번 더 묻는 질문을 넣어서 해결했다. A10은 보류로 바뀌고, 광고 글(A17)은 그대로 폐기됐다. 실무에서도 결함일 가능성이 있는 제보는 폐기하지 않는다(판정 기준서 H-9).

**"`熱`만이 아니라 다른 언어가 섞여도 다 잡히냐"고 내가 물었다.** 그 질문 덕분에 R7을 "금지 문자 목록"에서 "허용 문자 목록(한글·ASCII·일부 기호)" 방식으로 바꿨다. 금지 목록은 빠뜨린 언어를 못 잡지만, 허용 목록은 목록 밖이면 다 잡는다. [PE 09/11][pe0911] 8-2강의 Allowlist Router와 같은 발상이다. 한계도 있다. 악센트 없는 라틴 문자 외국어(예: 스페인어 일부)는 ASCII라 못 잡는다. 코드 주석에 남겼다.

후처리 안전장치(g2)는 **`[처리]` 줄만 바꾸고 정답 라벨은 보지 않는다.** 실제 BTS에 붙는 코드는 정답을 모르기 때문이다. 라벨을 엉뚱하게 바꿔도 결과가 같은지 테스트로 확인한다. [PE 10/02][pe1002]의 "정답은 Python 비교에만 쓰고 모델에 보내지 않는다"와 같은 원칙이다. 그리고 허용 값 밖 값은 비슷한 값으로 고치지 않고 위반으로 남긴다. [LC 09/29][lc0929]·[LC 10/01][lc1001]의 fail loud다. **코드가 판단까지 고치면 측정이 거짓말을 한다.** 실무로 보면 검수 단계가 결함을 대신 고쳐 버려서 결함 발생률이 실제보다 낮게 집계되는 것과 같다.

실행 기록에는 모델 원본 응답(`raw_response_text`), 재요청 시도(`attempts`), 적용된 안전장치 규칙(`guardrail`)을 함께 남긴다. [LC 10/01][lc1001]의 Tracing·관측처럼, "모델이 맞힌 것"과 "BTS에 들어간 결과"를 나중에 따로 볼 수 있게 하기 위해서다. 재요청·폐기 확인·안전장치 흐름은 모두 가짜 모델 클라이언트로 모델 없이 테스트한다([LC 09/29][lc0929]의 테스트 더블).

### 3. 저장소 구조 정리

`src/`를 `common/`(공용 도구), `bench_v1/`(동결된 v1.0), `pipeline/`(현역)으로 나눴다. 파일 이름에서 버전 표기를 빼고, 버전은 코드 안 상수로 실행 기록에 남긴다. 저장소 루트 경로를 9개 파일이 각자 계산하던 것도 `common/paths.py` 한 곳으로 모았다. [LC 09/30][lc0930]의 "이름 하나를 바꾸면 그 이름을 읽는 모든 곳이 영향을 받는다. 이름 변경은 인터페이스 변경으로 다뤄야 한다"를 실제로 겪은 작업이다.

**구조를 바꿔도 측정 결과는 하나도 바뀌면 안 된다**는 게 내 조건이었다. "통합으로 코드가 고장 나서 측정이 꼬이는 일은 없었으면 한다." Claude가 확인한 것은 테스트 173개, 저장된 실행 기록 22건 재채점 결과 일치, 게이트 판정 일치, 기록된 응답 재생 64/64 일치, v1.0 산출물 일치다. 리팩토링의 **동작 동일성 검증**이다. 순서를 바꿔도 문법 오류가 안 나는 곳이 가장 위험하다는 [LC 09/30][lc0930] 7절 이야기처럼, 겉으로 멀쩡한 변경일수록 결과를 직접 대조해야 한다.

### 4. 평가용 세트 최종 측정

측정 전에 규칙부터 정했다. "결과가 어떻게 나오든 그대로 기록하고, 프롬프트·안전장치·채점기를 고치지 않는다." [ML 08/18][ml0818]의 "탐색 결과를 확인하기 전에 선정 규칙을 먼저 고정"과 [PE 10/02][pe1002]의 "결과 미선별 — 개선이 없어도 그대로 기록"이다. `--final` 플래그는 [PE 10/02][pe1002] 실습의 `RUN_FINAL`과 같은 역할이다. 측정 전에는 `--strict-env`로 GPU 점유와 전원 연결을 점검하고, Ollama에 남은 이전 상태를 비우는 `ollama stop`을 절차에 넣었다(OBS-002, [LC 09/29][lc0929] 환경 재현성).

결과는 이랬다 (Qwen2.5-7B, 개발용 → 평가용).

| 지표 | 개발용 | 평가용 |
| :--- | :---: | :---: |
| 허용 값 위반 / 언어 위반 / 결함 폐기 | 0 / 0 / 0 | **0 / 0 / 0** |
| 형식 STRICT | 100% | **100%** |
| X-1 Critical 놓침 | 2 / 22 | **6 / 18** |
| 우선순위 정답률 | 62.5% | **43.5%** |
| 6칸 모두 정답 | 28.1% | **8.1%** |

형식·절차 지표와 판단 지표를 한 점수로 섞지 않고 나눠 봤다. [LC 09/30][lc0930]의 "형식 준수는 평가를 시작할 수 있는 전제 조건이지 품질 지표가 아니다"와 [PE 10/02][pe1002]의 "판정 기준(Oracle) — 형식, 정답, 근거를 분리한다"를 따른 것이다. 그래서 "형식은 100%인데 판단은 무너졌다"가 한눈에 보였다.

**1차 결과와 복구 후 결과도 따로 셌다.** 복구 로직이 있으면 최종 형식 준수율은 좋게 나오지만, 그게 모델 실력인지 복구 덕분인지 모른다. [LC 09/30][lc0930] 5-3강에서 "1차 형식 준수율과 복구 후 형식 준수율을 분리해서 집계해야 진짜 성능이 보인다"고 적어 둔 그대로, 같은 응답을 모델 원본(허용 값 위반 9건)과 최종 출력(0건)으로 각각 채점했다.

놓친 Critical 5문항(S04, B20, B15, S11, S16)은 **규칙이 프롬프트에 이미 있었다.** 표현이 바뀌자 적용을 못 했다. 오답 노트를 외워서 연습 문제는 맞혔는데 시험 문제는 못 푼 꼴이다. 봉인 Test를 따로 둬야 하는 이유가 그대로 드러났다. 평가용이 없었다면 개발용 점수만 보고 "판단도 충분하다"고 잘못 결론 냈을 거다. 테스트에서 말하는 **살충제 역설**과도 통한다. 같은 문항만 반복하면 새 유형의 실패는 안 보인다. 판단이 갈리는 건을 바로 종결한 X-3 4건까지 보고 나니, [PE 09/11][pe0911] 7-3강의 "사람 검토 큐로 격리"가 왜 필요한지 확실해졌다. 이건 v1.5 과제로 넣었다.

**날조 2건은 탐지기 오판이었다(Claude가 분석).** 리포트에는 "100번", "100연"이 있고 모델은 "100회"라고 썼다. 같은 수량인데 단위 글자가 달라서 날조로 잡혔다. v1.2에서 "5초"와 "15초"를 구분하려고 넣은 "수치는 붙여 쓴 형태 그대로" 규칙의 부작용이다. 규칙대로 지금 안 고치고 측정값 그대로 기록하고, v1.4에서 회귀 테스트와 함께 고친다(ISSUE-008). 실무에서도 측정 도구의 오판은 도구 결함으로 따로 등록하고, 끝난 회차 결과를 고쳐 쓰지 않는다.

평가용 세트는 이번에 한 번 썼다. 31건은 작은 표본이라 이 수치를 모델 전체 성능의 증거로 보지 않고([PE 10/02][pe1002]의 표본 한계 인정), v1.4 최종 측정에 같은 세트를 다시 쓸지는 따로 정한다.

### 5. 보고서에 강의 내용을 녹이기

처음에는 "부트캠프에서 배운 걸 썼다"를 따로 문서로 만들려 했는데, 내가 **평가 보고서 본문에 녹이는 게 낫다**고 방향을 바꿨다. 각 절에 "무엇을 했다" 바로 뒤에 "어떤 강의 원칙을 따랐는지(TIL 링크)"와 "QA 실무로 보면 무엇과 같은지"를 붙였다. 처리 규칙, 평가 문항과 정답 라벨, "날조가 소극적 응답보다 위험하다"는 선정 기준은 강의가 아니라 **QA 실무 기준**으로 정했다고 따로 밝혔다. 강의와 실무 판단을 합쳤다는 게 오히려 드러난다.

**Claude가 짚어준 확인 포인트**도 두 가지 있었다. 하나는 인용은 TIL에 **실제로 적힌 표현**으로만 한다는 것이다. 처음 초안에서 08/18 TIL을 "검증 데이터 과적합"으로 인용하려 했는데, 다시 확인해 보니 그 TIL에 있는 건 "Test 세트 봉인 원칙"과 "사전 선정 규칙"이었다. 출처와 다르게 인용하면 면접에서 바로 걸린다. 다른 하나는 학습 순서와 구현 순서가 항상 같지는 않다는 것이다. 형식 채점(R1~R7)은 10/02 강의의 "판정 기준 분리"보다 먼저 만들어져 있었다. 그래서 "배운 뒤 적용했다"가 아니라 "이 원칙을 따랐다"로 쓴다.

## ⚠️ 오늘의 함정 모음

**1. 프롬프트 선택지 표기 하나가 허용 값 위반을 만들었다**
`…, 무관 중 택1`의 "중"이 값에 붙어 `무관 중`이 나왔다. 사람에게는 자연스러운 문장이 모델에게는 값의 일부가 된다. 표기를 ` | `로 바꾼 v2.4는 오히려 다른 판단이 무너져 기각했고, 표기 문제는 재요청 단계에서 해결했다.

**2. "다시 써 줘"는 같은 실수를 되풀이한다**
텍스트 재요청에 모델은 `무관 중`을 seed 3쌍 모두에서, `과熱`도 그대로 다시 썼다. 말로 부탁하지 말고 생성 단계에서 값을 **제한**(`enum`, `pattern`)해야 했다.

**3. 측정 도중 전원 어댑터가 빠져 있었다**
평균 지연이 +27% 늘었다. 그 실행은 무효로 하고 기록을 지운 뒤 다시 쟀다. v1.1 때 "게임 끄고 전원 연결"이라고 적어 놓고도 또 걸렸다. 이제 최종 측정은 `--strict-env`로 돌려서 환경 경고가 있으면 아예 멈춘다.

**4. 같은 seed인데 결과가 달랐다 (OBS-002)**
Ollama가 다른 프롬프트를 처리한 뒤에는 같은 seed로도 응답이 재현되지 않았다. 측정 전에 `ollama stop`으로 상태를 비우는 걸 절차에 넣었다. seed 고정은 "같은 조건이면 같은 결과"이지 "언제나 같은 결과"가 아니다.

**5. 재요청 "채택" 건수를 부풀려 셌다** (Claude 코드의 결함)
재요청한 칸이 원래 멀쩡했는데도 "채택"으로 셌다. 원래 위반이던 칸이 고쳐졌을 때만 채택으로 세도록 고쳤다. 지표 정의가 틀리면 숫자가 좋아 보여도 의미가 없다.

**6. 구조 정리 중 Claude 쪽에서 난 사고 2건**
도움말을 보려고 `capture_env`를 실행했다가 환경 기록 파일을 덮어썼고(되돌림), 허용 문자 패턴 문자열이 변환 과정에서 깨졌다(다시 작성). 둘 다 동작 동일성 검증에서 잡혔다. **검증 단계가 있어야 리팩토링 사고가 커밋 전에 걸린다.**

**7. `.github/workflows/tests.yml`은 이번에도 내가 고쳤다**
보호 위치라 원격 도구로 못 쓴다. PowerShell `[IO.File]` 명령으로 직접 바꿨다.

**8. 최종 보고서 초안이 바로 이해가 안 됐다** (내가 지적)
용어와 수치만 나열돼 있어서 내가 읽어도 애매했다. 요약 3줄, 시험 비유, 용어 표, "쉽게 말하면" 칸을 넣어 다시 썼다. **보고서는 쓴 사람이 아니라 읽는 사람 기준으로 써야 한다.**

**9. 태그를 CI 확인 전에 push했다** (내 실수)
커밋 push와 태그 push를 한 번에 실행했다. 다행히 CI는 초록색이었다. 태그는 "이 시점이 완성본"이라는 표시라서, **CI 초록색 확인 → 태그** 순서가 맞다.

**10. `LF will be replaced by CRLF` 경고**
Claude가 쓴 파일은 LF, Windows는 CRLF라서 나오는 안내다. `.gitattributes`가 저장 방식을 맞춰 주므로 커밋 내용은 달라지지 않는다. 경고가 나와도 놀라지 말 것.
