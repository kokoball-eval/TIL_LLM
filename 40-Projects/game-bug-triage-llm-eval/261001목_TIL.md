> v1.1 첫 회귀 판정에서 게이트가 못 잡은 결함이 2건 나왔다(KL-001). Llama의 날조는 형식이 멀쩡해서 통과했고, Qwen의 판정 저하는 "노이즈인지 진짜 변화인지" 몰라서 참고용으로만 봤다. v1.2의 질문은 "**가장 위험한 결함(날조)을 사람 없이 잡을 수 있는가?**"였다. 오전에 로드맵을 다시 짜고, 날조 탐지기, seed 고정 모드, 측정 환경 점검을 만들어 `v1.2` 태그까지 달았다.
>
> **역할 분담** — 코드와 테스트는 Claude가 작성했다. 나는 로드맵의 최종 목표 결정, 변경안 검토와 승인, 로컬 실행(seed 고정 2회 실행, 깨끗한 환경 재측정, pytest, git), 결과 확인을 맡았다. 아래에서 "Claude가 발견한 것"과 "내가 한 것"을 구분해서 적는다.

> **강의 연결** — 설계 판단마다 어떤 강의 내용을 썼는지 옆에 적었다. [ML]은 머신러닝, [PE]는 프롬프트 엔지니어링, [LC]는 LangChain 과정 TIL이다.

## 💡 오늘의 작업 총평

v1.1까지의 게이트는 **형식만 보는 게이트**였다. 서두 사족, 빈 줄, 허용 값 밖 값은 잡지만, Llama가 "GTX 1660 Ti", "WASD 키 반복 입력"을 지어내도 형식이 멀쩡하면 PASS였다. 버그 트래커를 가장 크게 오염시키는 결함인데 게이트가 못 본 거다. 형식 검사를 통과했다고 내용이 맞는 건 아니고, 형식 게이트가 내용 게이트를 대신할 수도 없다.

오늘은 게이트에 **내용을 보는 눈**을 두 개 달았다.

| 무엇을 | 어떻게 |
| :--- | :--- |
| 날조 | 응답에 나온 기기·OS·버전·수치·조작 조건이 입력 리포트에 있는지 규칙으로 확인 → `hallucination_max = 0` (절대 기준) |
| 판정 저하 | seed를 고정해 같은 조건이면 같은 응답이 나오게 만들고 → 같은 seed끼리 비교할 때만 판정 변화 0건을 요구 |

그리고 9/30에 Llama 속도가 −32.5% 떨어진 게 모델 문제가 아니라 **측정 환경 문제**였다는 걸 확인했다. 깨끗한 환경에서 다시 재니 64.3 t/s로 돌아왔다. 환경을 통제하지 않으면 게이트가 모델 대신 환경을 판정한다. 그래서 환경도 측정 전에 점검해서 기록하도록 만들었다.

돌아보면 오늘 설계의 뼈대는 거의 다 강의에서 왔다. 탐지기를 어떻게 검증할지는 머신러닝의 정밀도·재현율에서, 판정을 무엇으로 할지는 LangChain의 판정 기준(Oracle)에서, seed와 환경 점검은 LangChain의 환경 재현성과 머신러닝의 공정한 비교 계약에서 가져왔다.

## 🎯 작업별 핵심

### 1. 로드맵 재설계 — 최종 목표부터 정하기

최종 목표를 "**사람이 보지 않아도 1차 트리아지가 돌아가는 파이프라인**"으로 정했다(내가 결정). 시니어 QA로서 "실무적 사고"만으로는 차별점이 안 된다고 봤고, 현업에서 나올 만한 데이터로 실제로 돌아가는 결과를 보여 주고 싶었다.

최종 지표는 4종이다. **자동 처리율, 자동 처리분 정확도, 날조 0건, 위험 건 누락 0건.** 여기에 [ML 08/14][ml0814]의 "정확도의 착시"를 그대로 썼다. 사기 거래가 2%뿐이면 전부 "정상"이라고 해도 정확도 98%가 나온다. 트리아지도 같다. 자동 처리율만 보면 아무거나 자동 처리하면 되고, 정확도만 보면 쉬운 것만 자동 처리하면 된다. 그래서 둘을 같이 보고, 비용이 큰 실수 두 가지(날조, 위험 건 누락)는 0건 기준으로 따로 묶었다. 같은 강의의 "오탐 비용과 미탐 비용은 다르다"는 이야기가, 실무에서 Critical을 놓치는 것과 괜히 올리는 것의 무게가 다른 것과 정확히 겹쳤다.

v1.5에는 **확신도 기반 라우팅**(자동 등록 / QA 검토 큐)을 새로 넣었다. [PE 09/11][pe0911] 7-3강의 "억지로 복구하지 말고 사람 검토 큐로 격리한다"는 원칙이다. 전부 자동화가 아니라 "사람이 봐야 할 것을 골라 넘기는 것"까지가 목표다. 버전마다 "무슨 질문에 답하는가"를 먼저 정한 v1.1 때 방식도 이어 갔다. 목표 지표가 정해져 있어야 각 버전이 그중 무엇을 올리는지 설명할 수 있다.

### 2. 날조 탐지기 (`detect_hallucination.py`)

**LLM이 아니라 규칙으로 판정한다.** 채점기가 매번 같은 판정을 내야 게이트 기준으로 쓸 수 있다. 다른 LLM에게 "날조야?"라고 물으면 채점기도 흔들린다. [LC 09/29][lc0929]의 "결정적 영역과 비결정적 영역을 나눈다"를 채점기에 적용한 셈이다. 모델 응답은 비결정적이어도, 그걸 판정하는 도구는 결정적이어야 한다. LLM 채점은 v1.4에서 사람 채점과 얼마나 맞는지 잰 뒤에 쓴다.

**"구체 사실"만 본다.** 기기·OS·하드웨어·버전·수치·조작 입력이다. 요약 문장 의미의 날조는 보지 않는다. [LC 09/29][lc0929]에서 배운 "판정은 글자 단위 일치로 하지 않는다"를 생각하면, 의미 비교는 정상적인 바꿔 말하기("크래시남" → "앱 강제 종료")까지 날조로 잡기 쉽다. 대신 트래커를 가장 크게 오염시키는 **기기·환경·조건 날조를 오탐 없이** 잡는 데 집중했다. 실무에서도 리포트에 없는 기기 사양이 붙어 있으면 개발자가 엉뚱한 환경에서 재현을 시도하게 되니, 이게 가장 비싼 날조다.

근거 확인은 항목마다 엄격함이 다르다. 기기명은 "갤럭시 기종(S21)"과 "갤럭시 S21"처럼 구성 토큰이 모두 입력에 있으면 근거로 본다. 반면 **수치는 붙여 쓴 형태가 그대로 있어야 한다.** "5초"와 "15초"를 구분해야 하기 때문이다. 무엇을 느슨하게 보고 무엇을 정확히 볼지 정하는 게 판정 기준(Oracle) 설계였다.

**정보 요청은 날조가 아니다.** "Windows 10/11 중 택1 확인 필요"처럼 묻는 건 트리아지 응답의 정상 동작이다. 실무에서 리포터에게 재현 환경을 되묻는 것과 같다. 그래서 따로 기록만 하고 세지 않는다.

**탐지기도 검증해야 쓸 수 있다.** 실제 로그 85건으로 확인했다. Llama Q08 날조 4건을 **전부** 잡았고(재현율), Qwen 40건·Cloud 5건에서 **오탐 0건**이었다(정밀도). [ML 08/14][ml0814]에서 배운 대로 둘을 같이 봐야 한다. 하나만 보면 "전부 날조로 판정"하는 탐지기도 탐지율 100%가 나온다.

Llama Q08 날조는 seed가 다른 3번의 실행(v1.0, 9/30, 10/1), 6회차 **전부에서** 재현됐다. 우연이 아니라 재현되는 결함이다. 오늘 실행에서는 "3회 연속 패턴", "10분 정도 플레이 후"처럼 **처음 보는 형태**로 날조했는데, 탐지기가 그것도 잡았다. 특정 문장을 외운 게 아니라 규칙으로 잡는다는 증거다. 남은 한계도 있다. "전투 모드에서 캐릭터가 무한히 이동"처럼 구체 사실 없이 요약 내용 자체를 지어내면 못 잡는다. 이건 v1.4의 숙제로 넘겼다.

### 3. seed 고정 모드 (`--seed N`)

1회차는 seed N, 2회차는 seed N+1이다. **두 회차를 같은 seed로 돌리면 "2회 반복해서 출력 안정성을 본다"는 설계 의미가 사라진다.** 회차마다 다르지만 고정된 seed를 쓰면, 회차 간 변동은 보면서 실행 간 재현성도 얻는다.

판정 변화 기준(`verdict_change_max = 0`)은 **두 실행의 seed가 같을 때만** 적용하고, 다르면 SKIP한다. [ML 08/18][ml0818]의 "공정한 비교 계약"이다. 강의에서는 같은 개발 데이터, 같은 CV, 같은 지표를 고정해야 후보끼리 비교할 수 있다고 했다. 여기서는 seed까지 같아야 "판정이 바뀌었다 = 진짜 변화"라고 말할 수 있다.

순서도 중요했다. 노이즈와 진짜 변화를 구분할 수 있어야 비교 기준을 세울 수 있다. 그래서 먼저 seed=1로 두 번 돌려서 **응답 원문 40/40건 일치**를 확인했고(내가 로컬에서 실행), 그다음에 기준을 0건으로 확정했다. 이 결과는 테스트로도 고정했다. 첫 실행을 새 기본 기준선으로 고정했지만 **v1.0 기준선은 지우지 않았다.** README 수치의 출처이기 때문이다. "최신 기준"과 "문서 수치의 출처"는 역할이 다르다는 v1.1 때 교훈이다.

### 4. 측정 환경 점검 (`preflight.py`)

모델을 부르기 전에 두 가지를 점검한다. **Ollama 외 GPU 점유**(1,024 MiB 이상이면 경고)와 **전원 연결**(배터리면 GPU 클럭이 낮아질 수 있음)이다. 결과는 `run_config.environment`에 남긴다. [LC 09/29][lc0929] 7절 "환경 재현성 — 같은 코드인데 결과가 다른 이유"에서는 라이브러리 버전, 인터프리터, 숨은 재시도를 통제 변수로 들었다. 로컬 LLM 벤치마크에서는 GPU를 함께 쓰는 프로그램과 전원 상태가 그 자리에 들어간다.

점검 실패는 기본적으로 기록만 하고 막지 않는다. 막고 싶으면 `--strict-env`를 준다. 그리고 **"측정할 수 없음"과 "문제 있음"을 구분한다.** `nvidia-smi`가 없으면 경고가 아니라 측정 불가로 기록한다. 둘을 섞으면 GPU 없는 CI에서 매번 경고가 난다. 같은 날 LangChain 강의 TIL([LC 10/01][lc1001])에도 "모르는 값은 0이 아니라 None / not_available로"라는 같은 원칙이 있다.

외부 명령(`nvidia-smi`, Windows 전원 API) 호출과 판정 로직은 분리했다. 판정 로직이 순수 함수라서 GPU 없는 CI(리눅스)에서도 테스트할 수 있다. [LC 09/29][lc0929]의 "비결정적인 한 칸만 빼고 나머지는 결정적 테스트로 덮는다"와 같은 구조다.

결과적으로 다른 프로그램이 VRAM을 거의 안 쓰고(362~485 MiB) 전원이 연결된 상태에서 다시 재니 Llama가 **64.3 t/s**였다(v1.0 66.56 t/s, 9/30 44.9 t/s). 모델 digest는 그대로였으니 9/30의 급락은 환경 탓이었고, OBS-001을 종료했다. v1.1 TIL에 "게임 끄고 전원 연결, v1.2에서 체크리스트로 만들 예정"이라고 적었던 걸 오늘 코드로 만들었다. **사람이 기억하는 체크리스트보다 코드가 확인하는 체크리스트가 낫다.**

## ⚠️ 오늘의 함정 모음

**1. 탐지기 오탐 2건 (ISSUE-006)** (Claude가 단위 테스트 작성 중, 커밋 전에 발견)
- 입력에 "v2.3.1"이 있고 응답이 "v2.3.1 회귀 테스트 권장"이면, 버전 번호 일부와 "회귀"의 "회"가 합쳐져 **"3.1 회"라는 횟수**로 뽑혀 날조로 판정됐다.
- 입력이 "15초 후에 멈춤"이면 응답의 **"5초"가 근거 있음**으로 판정됐다. "15초" 안에 "5초"가 들어 있으니까.
- 둘 다 숫자 앞뒤 문맥을 안 봐서 생긴 문제다. 실제 로그 85건에는 없던 형태라 수치에는 영향이 없었지만, "v2.3.1 회귀 테스트 권장"은 트리아지 응답에서 흔한 표현이다. 그대로 뒀으면 평가셋을 늘리는 v1.3에서 정상 응답을 FAIL로 만들었을 거다. [LC 09/29][lc0929]의 가짜 `AIMessage`처럼 **이상한 입력을 원하는 만큼 만들어 넣는 테스트**가 실제 데이터에 아직 없는 결함을 먼저 잡았다.

**2. 탐지율만 보면 탐지기가 좋아 보인다**
"전부 날조"라고 판정해도 탐지율은 100%다. [ML 08/14][ml0814]의 정확도 착시와 같은 함정이다. 그래서 Qwen·Cloud 로그로 **오탐 0건**을 같이 확인했다. 정보 요청 문맥("중 택1", "여부 확인")을 날조로 안 세는 것도 오탐을 막는 장치다.

**3. 같은 seed로 두 회차를 돌리면 반복 측정이 아니다**
seed 고정이라고 1·2회차를 같은 seed로 두면 두 번 잰 게 아니라 한 번 잰 걸 복사한 거다. 그래서 1회차 N, 2회차 N+1.

**4. 오늘 정한 것들의 대가는 다음 날 나왔다** (v1.3에서 알게 된 것)
- "5초"와 "15초"를 구분하려고 **수치는 붙여 쓴 형태 그대로** 비교하게 했는데, v1.3 최종 측정에서 "100번"을 "100회"로 옮긴 응답을 날조로 잡았다(ISSUE-008). 오탐 하나를 막은 규칙이 다른 오탐을 만들었다. 정밀도와 재현율처럼, 규칙 기반 탐지기도 한쪽을 조이면 다른 쪽이 새는 트레이드오프가 있다.
- "같은 seed면 같은 응답"(40/40)은 **Ollama가 직전에 다른 프롬프트를 처리하지 않은 상태**에서만 성립했다(OBS-002). 프롬프트를 바꿔 가며 잴 때는 `ollama stop`으로 모델을 내리고 잰다. 오늘 확인한 전제에도 숨은 조건이 있었다.
