## 💡 오늘의 작업 총평

이번에 제일 크게 배운 건 **"좋아 보이는 결과"와 "채택할 수 있는 결과"는 다르다**는 것이다.

v1.3에서 모델은 Critical 규칙을 프롬프트에서 읽고도 처음 보는 리포트에는 적용하지 못했다. 그래서 신입 트리아지 담당자를 교육하는 두 방식을 비교했다.

| 방법 | 신입 교육으로 비유하면 | 결과 (개발용, seed 3개 합계) |
| :---: | :--- | :--- |
| M1 | 모범 답안 4개 보여 주기 | Critical 누락 25 → **9**. 그런데 과잉 상신 26 → 56, 예시 모듈을 21번 복사 → **탈락** |
| M2 | Critical 체크리스트 쥐여 주기 | Critical 누락 25 → 17, 올린 8건 모두 진짜 Critical, 다른 지표 그대로 → **채택** |

모델 비교도 같았다. gemma4:12b + M2는 개발용에서 **Critical을 하나도 놓치지 않았고** 6칸 모두 정답도 19.8% → 45.8%였다. 그런데 잘 처리하던 이슈를 다른 곳으로 보내는 문항 단위 회귀가 seed 3개 모두에서 기준(4)을 크게 넘었다(16~18). 숫자만 보면 바꾸고 싶었지만, **측정 전에 커밋한 기준을 결과를 보고 바꾸지 않았다.** QA 실무에서도 전체 통과율이 올랐다고 회귀 결함을 넘기지 않는다.

최종 측정은 이 판단을 겸손하게 만들었다. 처음 보는 25건에서 날조·결함 폐기·사람 확인 누락·형식 위반은 모두 0건이었지만, **체크리스트가 판정을 바꾼 건은 0건**이었다. 즉 M2의 효과는 최종 세트에서 확인되지 않았다. 계획서에 미리 적어 둔 "개발용 개선 폭은 실제보다 크게 나올 수 있다"가 그대로 나왔고, 그것도 그대로 기록했다.

결론은 v1.5 방향으로 이어졌다. 모델 하나에 "놓치지도, 과하게 올리지도 않는" 판단을 기대하기보다, **놓치지 않는 쪽으로 기운 판단을 사람 검토 큐가 받아내는 구조**가 현실적이다. 신입 판정을 리드가 확인하는 QA 조직 구조와 같다.

## 🎯 작업별 핵심

### 1. 모델 재선정 — 판단력이 좋은 모델 ≠ 절차에 맞는 모델

"최신 모델 몇 개"가 아니라 **트리아지 업무가 모델에 요구하는 것**에서 후보 조건을 정했다. 한국어 리포트를 읽고, 8칸 고정 형식으로 BTS에 넣고, 사내 PC 1대(VRAM 8GB)에서 돌고, 상업적으로 쓸 수 있어야 한다. 이 조건으로 8개 중 2개를 빼고(비상업 라이선스, VRAM 초과), 6개를 사전 점검했다.

**사전 점검 도구 자체에 결함이 있었다(ISSUE-009).** 1차 점검 결과를 검토하다 gemma4 계열이 GPU 적재 PASS를 받은 근거가 이상하다는 게 드러났다. 점검 코드가 `ollama ps`가 보고한 크기를 그대로 믿었는데, gemma4 계열은 Ollama가 크기를 실제보다 작게 보고한다(OBS-003). Claude가 판정을 "보고 크기가 모델 파일 크기의 90% 미만이면 HOLD(판정 불가)"로 바꾸고, nvidia-smi VRAM과 생성 속도를 같이 남기게 했다. **측정 도구가 틀린 값으로 PASS를 내는 게 측정을 못 하는 것보다 위험하다.** [LC 09/29][lc0929]의 fail loud와 같은 판단이다.

비교 결과 gemma4:12b가 판단 지표(Critical 누락 8 → 3, 우선순위 정답 119 → 158)에서 크게 앞섰지만, 처리 단계 회귀와 경계 건 확정 처리(X-3)가 모든 seed의 같은 문항에서 반복돼 기준을 넘지 못했다. 교체 규칙은 측정 전에 정해 둔 대로였다. [ML 08/18][ml0818]의 "결과를 보기 전에 선정 규칙을 고정"이다.

같은 기간에 **v1.3에서 미뤄 둔 날조 탐지기 오판(ISSUE-008)도 고쳤다.** "100번" → "100회"처럼 같은 수량을 다른 횟수 단위로 옮긴 응답을 날조로 보던 문제다. 고친 뒤 저장된 응답 2,545건을 다시 판정해 바뀐 8건이 모두 이 오판 사례인지 확인했다. v1.3 때는 "측정 후 채점기 수정 금지" 규칙 때문에 기록만 했던 걸, 다음 버전의 첫 작업으로 회귀 테스트와 함께 고친 거다.

### 2. 새 최종 평가용 세트 25건 — 시험지를 다시 만들다

v1.3 평가용 31건은 이미 결과를 봤으니 더 이상 "처음 보는 시험지"가 아니다. 63건을 모두 개발용으로 돌리고, 새 시나리오 25건(F01~F25)을 봉인했다. [ML 08/14][ml0814]·[ML 08/18][ml0818]의 봉인 Test 원칙이다.

**시나리오는 내가 제시했다.** 탈퇴 유예 중 계정 잠김, 길드장 위임 후 권한이 남는 문제, 환불 후 재화 미회수처럼 라이브 서비스에서 실제로 문제 되던 유형이다. Claude가 리포트 원문과 라벨 초안을 썼고, 나는 2회 검토로 라벨을 확정했다.

검토하면서 **라벨이 판정 기준서와 부딪히는 문항**이 나왔다. 이때 "라벨을 규칙에 맞출지, 규칙을 고칠지"를 내가 정했다.

- **F03 (드문 조건의 무료 보상 손실)** — 기준서 F-2대로면 Critical인데 실무 감각으로는 Major였다. 기준서에 "드문 조건에서만 생기고 우회 가능한 무료 보상 손실은 Major까지 가능, 유료 재화는 Critical 유지" 단서를 넣었다. "유료 재화였다면 Critical로 볼 수도 있으니 Critical도 허용"한다고 정해서, 정답은 Major, Critical도 허용 답으로 뒀다.
- **F15** — 무료 재화 1골드 차이는 손실이 작아서 Minor.
- **F22** — v1.3 검증 규칙(트랙 A는 개발 배정 금지)에 걸렸다. v1.4 생성기에서만 "허용 분류에 개선 제안이 있으면 허용"으로 완화했다. v1.3 도구는 그대로 둔다.
- **F25** — CS 응대가 먼저라 권장 조치 삭제.

기존 63건 라벨이 하나도 안 바뀌었는지, 새 25건이 기존 원문을 재사용하지 않았는지는 테스트로 고정했다.

### 3. 방법 비교 설계 — 측정 전에 다 정하고 커밋

계획서(`method_comparison_v14_plan.md`)와 기준 파일을 측정 전에 커밋했다. 처음 Claude가 쓴 5단계 설계 초안은 내가 읽어도 무슨 소린지 몰라서 "좀 더 직관적으로" 설명해 달라고 했고, 신입 교육 비유로 다시 들었다. 그리고 **"추천대로가 정말 최선이냐, 좀 더 깊게 생각해 봐"**라고 되물었더니 Claude가 보완점 2가지를 더 찾았다. 추천을 그대로 받지 않고 한 번 더 찔러 보는 게 효과가 있었다.

**M1·M2 설계는 실무 교육 방식이다.** 신입에게 심각도 기준표만 외우게 하면 처음 보는 이슈에 대입을 못 한다. 그래서 과거 판정 사례를 보여 주거나(M1), 확인 항목 체크리스트를 준다(M2). [PE 09/11][pe0911] 6-1·6-2강의 경계 사례 few-shot과 [PE 10/02][pe1002] 실습 4의 체크리스트 중심 출력을 그대로 가져왔다.

**M2는 "올리기만" 한다.** Critical을 놓치면 장애고, 잘못 올리면 리드 QA가 한 번 더 보면 된다. 손해가 비대칭이니 체크리스트는 내리는 쪽으로 안 쓴다. 이미 Critical인 첫 응답은 답만 기록하고 건드리지 않는다.

여기서 내가 하나 물었다. 체크리스트 질문에 **"확실하지 않으면 아니오"** 문장을 넣는 안이었는데, "Critical이 많아지는 것보다 실제 Critical을 놓치는 게 더 최악인데도 넣는 게 맞냐"고. Claude는 넣는 쪽을 추천했다. 체크리스트는 올리기만 하니까 답이 "예"로 기울면 과잉 상신이 쌓이고, 사전 기준(과잉 상신 증가 +4 이하)에 걸려 **방법 자체가 탈락해 체크리스트를 아예 못 쓰게 된다**는 이유였다. 납득하고 승인했다. 실제 결과에서도 "예"가 섞인 답이 122건 나왔는데, 그중 114건이 이미 Critical인 건이라 설계대로 기록만 됐다. 이 두 규칙이 없었으면 판정이 흔들렸을 거다.

**Minor/Trivial 완화는 내 의견이다.** 결함이냐 아니냐가 가장 큰 기준이고, Minor와 Trivial은 실무에서 처리 차이가 작다. 이 차이로 방법 비교가 갈리면 의미 없는 차이에 휘둘린다. 그래서 두 등급을 서로 허용 답으로 두되, 첫 정답은 그대로 두고 `label_relaxed`로 표시했다.

채택 기준은 세 겹이다. 절대 기준(날조·허용 값 위반·언어 위반 0, 평균 10초 이하), 기준선 대비(X-2·X-3이 같은 seed의 M0보다 안 늘 것), 회귀 기준(맞히던 문항이 틀리게 바뀐 수 등). 그리고 **seed 3개 모두 통과 + Critical 누락 감소**여야 채택한다. 나빠지지 않은 것만으로는 바꾸지 않는다. QA로 보면 릴리스 판정 기준(Exit Criteria)을 테스트 전에 합의해 두는 것이다.

### 4. 구현 — "통합 때문에 측정이 꼬이면 안 된다"

내 조건은 v1.3 때와 같았다. **M0(기존 방식)는 한 글자도 바뀌면 안 된다.** Claude는 프롬프트 조립 함수에 예시 블록 인자를 붙이되 기본값을 빈 문자열로 둬서 M0 프롬프트가 그대로인지 테스트로 확인했다. 실제 실험에서도 M2의 1차 판정이 M0와 378/378 같았다. 그래서 **M2의 변화는 순수하게 체크리스트 효과**라고 말할 수 있다.

**Claude가 미리 막은 것 두 가지.**

- 예시 원문은 코드에 따로 적지 않고, 내가 승인한 문서(`m1_examples.md`)를 실행할 때 읽는다. 코드와 문서 중 한쪽만 고쳐지는 걸 막기 위해서다. 그런데 Windows에서 git이 CRLF로 체크아웃하면 같은 문서라도 프롬프트 문자열과 지문이 달라진다. 그래서 읽을 때 줄바꿈을 LF로 맞추고, CRLF 파일로 읽어도 같은지 테스트를 붙였다.
- 예시가 평가셋 88건의 표현을 옮겨 쓰지 않았는지(6글자 조각 겹침 15% 미만) 테스트로 확인했다. [PE 10/02][pe1002]의 예시 오염 방지다.

비교 도구(`triage-compare`)는 판정 전에 **조건이 같은지부터** 본다. 개발용인지, v1.4 평가셋인지, seed 구성이 맞는지, 비교 대상 외 조건이 같은지. 하나라도 어긋나면 판정하지 않고 종료 코드 2로 멈춘다. [ML 08/18][ml0818]의 공정한 비교 계약을 코드로 박은 거다.

### 5. 실험 A·B — 기준이 나 대신 결정했다

실험 A는 위 총평대로 M2 채택. M1이 탈락한 장면이 인상적이었다. 예시 E4(계정당 1회 보상 반복 수령 악용)를 본 뒤로, 모델이 **악용 정황만 있어도 Critical로 올렸다.** 다른 유저 제재 요청은 원래 CS로 넘길 일인데 리드 QA 사인 큐로 갔다. 예시 모듈 "결제·재화 / 보안·어뷰징"을 상관없는 문항에 21번 복사했다. 신입이 선배의 모범 티켓을 상황 상관없이 베껴 쓰는 것과 똑같다. 7B 모델에게 예시는 "기준"이 아니라 "따라 할 답"이었다.

**Claude가 분석한 M2의 남은 누락 17건**은 두 갈래였다. 10건은 처음부터 "결함이 아니다"로 분류해서 체크리스트를 아예 안 물었고(B20을 "개선 제안"으로, S11을 "버그 아님"으로), 7건은 체크리스트에 전부 "아니오"라고 답했다. 실무에서도 "버그 아님"으로 닫힌 이슈는 심각도 기준표를 거칠 기회가 없다. **체크리스트는 분류가 맞을 때만 작동한다.**

실험 B(gemma4:12b)는 총평대로 탈락. 판정 결과를 보고 아쉬웠지만 기준은 그대로 적용했다. [PE 10/02][pe1002]의 "차이가 없으면 없다고 기록"과 같은 원칙으로, 원하는 결과가 아니어도 그대로 남겼다. 대신 gemma를 "놓치지 않는 대신 자주 올리는 담당자"로 보고, 사람 검토 큐와 짝을 이루는 v1.5의 출발 자료로 남겼다.

### 6. 최종 측정 — 두 번째 시험지

| 지표 | 결과 |
| :--- | :---: |
| 날조 · 결함 폐기 · 사람 확인 누락 · 형식 위반 | **0건** |
| 형식 STRICT | 100% |
| Critical 누락 | 2 / 10 (F01 한 문항을 2회 모두 놓침) |
| 처리 정답률 | 72% |
| 평균 응답 시간 | 2.3초 |

**코드로 강제한 형식·절차는 두 번째 시험지에서도 지켜졌다.** v1.3의 "모델은 판단하고, 형식과 절차는 코드가 강제한다"가 한 번 더 확인됐다.

놓친 F01(탈퇴 철회 후 로그인 불가)은 체크리스트 1번 질문("로그인을 할 수 없고 우회 방법이 없는가")이 딱 맞는 상황인데도 모델이 "아니오"라고 답했다. 질문을 줘도 적용을 못 하는 경우가 있다.

**Claude가 짚어준 확인 포인트: 개발용 안에서도 "연습 문제만 잘 푸는" 효과가 남아 있었다.** 개발용 63건을 v1.3 분할로 다시 나눠 보니, 같은 M2인데 프롬프트를 맞춘 옛 개발용 문항은 Critical 누락 1/66, 나머지 옛 평가용 문항은 16/54였다. 방법 비교에서 나온 개선 폭도 주로 옛 평가용 문항에서 생겼다. 평가셋을 한 덩어리로만 봤으면 못 봤을 차이다. 테스트의 살충제 역설과 같다.

### 7. 보고서 — 모르는 사람이 읽어도 이해되게

v1.3 때 "보고서는 읽는 사람 기준"이라고 배웠는데, 이번엔 처음부터 요구했다. **QA 실무 경험과 KANT 부트캠프 LLM 트랙에서 배운 내용을 썼다는 걸 반드시 밝히고, 내용을 모르는 사람이 읽어도 직관적으로 이해되게.** Claude가 최종 보고서를 다시 썼다.

- 용어 표에 "QA 실무로 비유하면" 칸 (X-1 누락 = 장애 보고 누락, 문항 단위 회귀 = 이전 빌드에서 통과하던 케이스가 새 빌드에서 실패)
- 방법 설명을 신입 교육 비유로
- 결과 표마다 "쉽게 말하면" 칸
- 마지막 절에 "실무에서 가져온 것"(장애 등급, 신입 교육 방식, Exit Criteria, 회귀 판정 등)과 "부트캠프에서 배운 것"(출처 TIL 링크 포함)을 표 두 개로 분리

강의 출처는 v1.3 때처럼 TIL에 실제로 적힌 원칙으로만 인용했다.

## ⚠️ 오늘의 함정 모음

**1. 7B 모델은 예시를 "기준"이 아니라 "답"으로 읽는다** (M1)
Critical 누락은 가장 많이 줄었는데, 과잉 상신이 2배가 되고 예시 모듈을 21번 복사했다. 계획서에 위험으로 적어 둔 "예시 내용 복사"가 그대로 나왔다. 한 지표만 봤으면 M1을 채택했을 거다.

**2. 가짜 모델이 체크리스트에 무조건 "예"라고 답했다** (Claude 테스트의 결함)
처음 만든 가짜 모델은 모든 체크리스트 질문에 "예"라고 답해서, "예" 편향 때문에 방법이 탈락하는 경우를 테스트가 볼 수 없었다. 문항별로 다른 답을 주게 바꾸고, "예"로 기운 체크리스트가 과잉 상신 기준에 걸려 탈락하는 테스트를 추가했다. **늘 통과하는 테스트 더블은 검증을 안 하는 것과 같다.**

**3. 사전 점검이 외부 도구의 보고값을 그대로 믿었다** (ISSUE-009)
Ollama가 gemma4 크기를 작게 보고해서 GPU 적재 PASS가 잘못 났다. 외부 도구 값은 독립된 값(파일 크기)과 대조한 뒤에만 판정에 쓴다.

**4. 실험 B 중간에 측정 환경 점검이 실행을 거부했다** (ISSUE-011)
seed 1을 돌린 뒤 seed 11·21이 `--strict-env`에 막혔다. 나는 "음 뭐지!" 하고 Claude에 물었고, Claude가 원인을 찾았다. 마지막에 돌린 gemma가 메모리에 남아 "다른 프로그램이 VRAM을 쓴다"로 잡힌 것이다. `ollama stop` 후 다시 돌렸다. 코드 수정은 **실험 도중에 조건이 바뀌지 않게** v1.5로 미뤘다. 측정은 오염되지 않았다. 점검이 조용히 넘어가지 않고 멈춰 준 덕분이다.

**5. 같은 seed인데 기준선이 일부만 재현됐다** (OBS-004)
M0를 다시 돌렸더니 옛 개발용 응답이 64개 중 48·48·45개만 일치했다. 바로 앞에 처리한 문항이 다르면 같은 seed라도 답이 달라진다. 게임 QA로 치면 "직전 화면 상태"가 재현 조건에 들어가는 버그다. 실험 안에서는 문항 순서가 같아서 비교에는 영향이 없었다.

**6. 라벨이 판정 기준서와 부딪혔다** (F03, F22)
현업 감각으로 붙인 라벨이 기준서 규칙과 맞지 않았다. 라벨을 규칙에 억지로 맞추지 않고, 기준서에 단서를 추가하거나 v1.4 검증 규칙만 완화했다. 어느 쪽을 고칠지는 측정 전에 내가 정했다. **측정 뒤에 정했다면 결과 맞추기가 됐을 거다.**

**7. README 로드맵이 실제 진행과 어긋나 있었다** (Claude 발견)
실험 A를 돌리는 동안 README를 봐 달라고 했더니, Claude가 v1.4 로드맵 줄이 실제 진행(모델 재선정, 방법 비교)과 다르다는 걸 찾았다. 코드만 커밋하고 소개 문서는 놓치기 쉽다. 버전 작업 중간중간 README도 같이 볼 것.

**8. 개발용 개선 폭을 믿으면 안 된다**
개발용에서 M2는 Critical 누락 25 → 17이었지만, 최종 세트에서 체크리스트가 바꾼 판정은 0건이었다. [ML 08/18][ml0818]·[PE 10/02][pe1002]에서 배운 "개발 데이터로 고른 결과는 과대평가된다"를 숫자로 직접 봤다.
