# TIL — 로컬 LLM 후보 조사와 스모크 테스트 (프로젝트 1일차)

> 게임 버그 리포트 트리아지에 쓸 로컬 LLM을 고르는 프로젝트 첫날.
> Use Case를 정의하고, 후보 2종의 Model Card를 읽고, 실제로 돌아가는지 단일 호출로 확인했다.

## 오늘 한 일

## 1. "서로 다른 모델 2개"의 기준

처음엔 같은 모델의 4bit / 8bit 양자화 버전을 비교하면 되는 줄 알았는데 그게 아니었다.
**서로 다른 아키텍처·패밀리**여야 의미 있는 비교가 된다. 양자화 차이는 같은 모델의 정밀도 차이일 뿐이라
"어느 모델을 쓸 것인가"라는 질문에 답하지 못한다.

그래서 계열이 다른 두 개를 골랐다.

| 항목 | Qwen2.5-7B-Instruct | Llama-3.1-8B-Instruct |
|---|---|---|
| 라이선스 | Apache 2.0 | Llama 3.1 Community License |
| 최대 Context | 네이티브 32,768 (YaRN 적용 시 131,072) | 네이티브 128,000 |
| 공식 지원 언어 | 다국어 | 영·독·불·이·포·힌디·태국·스페인 8개 (**한국어 미포함**) |

## 2. Model Card는 "숫자"보다 "조건"을 봐야 한다

가장 헷갈렸던 게 Context Length였다. Qwen2.5도 128K를 지원한다고 알고 있었는데,
Model Card를 직접 열어보니 **네이티브는 32,768**이고 131,072는 YaRN이라는 rope scaling을
`config.json`에 설정해야 도달하는 값이었다.

> To handle extensive inputs exceeding 32,768 tokens, we utilize YaRN...

Llama-3.1은 네이티브 128K라 조건이 없다. 둘 다 "128K"라고만 적으면 완전히 다른 얘기가 된다.
**숫자만 옮겨 적으면 안 되고, 그 숫자가 성립하는 조건까지 확인해야 한다.**

라이선스도 마찬가지였다. Llama 3.1 Community License는 월간 활성 사용자 7억 명을 넘으면
별도 계약이 필요하다는 조건이 붙는다. 학생 프로젝트 범위에선 무관하지만,
"상업적 사용 가능 여부"를 판단 기준에 넣었다면 이 조건을 기록해둬야 한다.

한국어 지원도 그렇다. Llama-3.1의 공식 지원 언어 8개에 한국어는 없다.
"안 된다"가 아니라 **"공식적으로 보증하지 않는다"**는 뜻이고, 실제 성능은 직접 재봐야 한다.

## 3. 모델은 태그와 digest로 식별한다

`ollama list`로 확인한 실제 실행 식별값을 기록했다.

| 모델 | 태그 | digest |
|---|---|---|
| Qwen2.5-7B | `qwen2.5:7b` | `845dbda0ea48` |
| Llama-3.1-8B | `llama3.1:8b` | `46e0c10c039e` |

"Qwen 7B를 썼다"만 적으면 나중에 같은 실험을 재현할 수 없다.
같은 이름이라도 태그와 양자화 레벨(`Q4_K_M`)이 다르면 다른 모델이다.

## 4. CLI와 Python은 각각 확인해야 한다

`ollama run <모델>`로 대화가 되는 것과, Python 코드에서 호출이 되는 건 별개다.
CLI가 되는데 Python에서 안 되면 원인은 모델이 아니라 클라이언트나 환경 쪽이다.
**경로를 나눠서 확인해두면 문제가 생겼을 때 범위를 좁힐 수 있다.**

```python
import ollama
client = ollama.Client()
response = client.generate(model="qwen2.5:7b", prompt=TEST_PROMPT, options={...})
```

## 5. 첫 호출은 느리다 — 로딩 시간이 섞여 있다

단일 호출 측정값을 보고 "생각보다 느린데?" 했는데, 응답 메타데이터를 뜯어보니
**전체 시간의 절반 이상이 모델을 GPU에 올리는 시간**이었다.

| 항목 | Qwen2.5-7B | Llama-3.1-8B |
|---|---:|---:|
| 전체 소요 시간 | 3.807초 | 5.060초 |
| └ 그중 모델 로딩 | 2.124초 | 3.198초 |
| 생성 토큰 수 | 100 tokens | 115 tokens |
| 초당 생성 속도 | 64.56 tokens/s | **66.51 tokens/s** |
| VRAM 점유 | **4,528.1 MiB** | 5,027.5 MiB |

전체 시간만 보면 Qwen이 빠르지만, 로딩을 빼고 순수 생성 속도만 보면 Llama가 근소하게 앞선다.
**같은 "빠르다"는 말도 무엇을 재느냐에 따라 결론이 뒤집힌다.**

여기서 본 실험 설계에 반영할 걸 하나 얻었다 — 반복 측정을 할 거라면
**첫 호출(워밍업)은 통계에서 분리해야 한다.** 안 그러면 콜드 스타트 지연이 평균을 왜곡한다.

## 6. 스모크 테스트에서 본 정성적 차이

같은 버그 리포트를 두 모델에 넣고 출력 성향을 비교했다. 숫자보다 이쪽이 더 흥미로웠다.

**Llama-3.1이 나았던 점**

- 인게임 지명 `스피릿 아일랜드`를 원문 그대로 보존 (Qwen은 `스플릿 아일랜드`로 오독)
- 지정한 카테고리 라벨 `Crash/Freeze`를 그대로 유지 (Qwen은 `Crash`로 임의 축약)

**Qwen2.5가 나았던 점**

- 규격대로 즉시 출력 시작 (Llama는 `"다음은 분석된 버그 리포트 요약입니다."` 같은 서두를 붙임)
- 출력이 간결

고유명사 오독은 실무에서 꽤 위험하다. 맵 이름이 틀리면 버그 티켓이 엉뚱한 부서로 배정된다.
반대로 서두 사족은 정규식 파서를 깨뜨린다. **둘 다 "품질"이 아니라 "연동 가능성"의 문제였다.**

## 7. 오늘 세운 가설

> Llama가 고유명사 보존·스키마 준수·순수 생성 속도에서 앞선다.
> 유일한 약점인 서두 사족은 프롬프트 네거티브 지시로 통제 가능할 것이다.
> **따라서 가드레일을 넣으면 Llama가 최종 채택 모델이 될 것이다.**

2일차 본 실험은 이 가설을 검증하는 방향으로 설계하기로 했다.

## 오늘의 실수: 같은 파일명으로 덮어쓰기

스모크 테스트 결과를 저장하는 코드를 이렇게 짰다.

```python
safe_model_name = MODEL_TAG.replace(":", "_")
output_path = output_dir / f"{safe_model_name}_verify.json"   # 실행할 때마다 덮어씀
```

프롬프트를 바꿔가며 여러 번 돌렸는데, **파일명이 같으니 마지막 실행만 남았다.**
중간 관측치를 메모해뒀다가 나중에 원본과 대조하려니 어느 실행의 값인지 추적이 안 됐다.

타임스탬프를 파일명에 넣거나, 한 파일에 append 하는 식으로 짰어야 했다.

```python
# 이렇게 했어야 했다
output_path = output_dir / f"{safe_model_name}_verify_{datetime.now():%Y%m%d_%H%M%S}.json"
```

> 실험 기록은 **덮어쓰지 말고 쌓아야 한다.**
> 나중에 "이 숫자 어디서 나왔지?"를 답할 수 없으면 그건 근거가 아니다.
