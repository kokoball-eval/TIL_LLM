## 💡 오늘의 작업 총평

v1.0은 "지금 어떤 모델이 이 업무에 맞는가"를 **한 번 재고 끝나는 사진 한 장**이었다. 오늘은 그걸 "**바꿀 때마다 나빠졌는지 자동으로 판정하는 게이트**"로 바꿨다.

작업 전에 먼저 정리한 게 있다. "이 프로젝트는 왜 계속하나?"라는 질문에 답할 수 없어서, 로드맵의 각 버전을 "**무슨 질문에 답하는가**"로 바꿔 봤다.

| 버전 | 답하려는 질문 |
| :---: | :--- |
| v1.0 | 어떤 모델이 이 업무에 맞는가? |
| v1.1 | 무언가 바꿨을 때 나빠졌는가? |
| v1.1.1 | 평가 도구 자체는 믿을 수 있는가? |
| v1.2 | 가장 위험한 결함(날조)을 사람 없이 잡을 수 있는가? |
| v1.3 | 평가셋이 실제 업무를 대표하는가? 다른 도메인에도 쓸 수 있는가? |
| v1.4 | 품질 채점까지 자동화해도 사람 판단과 맞는가? |
| v2.0 | 검색이 끼어도 새로운 실패 유형을 측정하고 막을 수 있는가? |

이으면 "**LLM에게 트리아지를 맡겨도 되는지 계속 증명하는 평가 체계**"가 된다. 주인공은 트리아지 도구가 아니라 **평가 체계**이고, 게임은 평가 대상 사례다. SW QA를 기본 축으로, 게임 QA 복귀와 LLM Eval 확장을 모두 열어 두는 내 직무 목표와도 맞는 방향이라 이렇게 가기로 했다.

## 🧭 종합 QA 체크포인트

- **게이트는 "좋다는 증거가 있을 때만" 통과시켜야 한다.** 측정값이 없으면 통과가 아니라 실패. 기준 파일 오타로 검사가 빠지면 판정 불가.
- **비교하기 전에 "비교해도 되는가"부터 본다.** 테스트 환경이 다르면 결과를 비교하지 않는 것과 같은 원칙이다.
- **측정 도구도 테스트 대상이다.** 채점기가 틀리면 모든 판정이 틀린다.
- **결함을 고치면 재발 방지까지 한다.** 되돌리기(조치)만 하지 않고 같은 일이 다시 안 생기게 구조를 바꿨다.
- **게이트가 PASS라고 품질이 보장되는 건 아니다.** 오늘 첫 판정에서 게이트가 못 잡는 결함 2건이 나왔다.

## 🎯 작업별 핵심

### 1. v1.1 — 회귀 게이트

**핵심 개념**

- **절대 기준 + 회귀 기준을 둘 다 둔다.**
  - 절대 기준만 있으면: 1.4초 → 1.99초로 서서히 느려져도 "2.0초 이하"라 통과
  - 회귀 기준만 있으면: 기준선이 원래 나쁘면 "똑같이 나쁨 = 통과"
  - 실제로 Llama 로그끼리 비교하면 회귀 기준은 전부 통과(변화 0%)인데, 절대 기준(STRICT 5% < 95%)에서 FAIL이 났다.
- **STRICT 95%는 1건까지 허용하지만, 서두 사족(R1)은 따로 0건을 요구한다.** 실패에도 무게가 다르다. 빈 줄은 파서가 견디지만 서두 사족은 Jira 등록을 깨뜨린다.
- **종료 코드로 결과를 낸다.** 0 PASS / 1 FAIL / 2 판정 불가. 1은 원인 분석, 2는 조건 맞추기로 대응이 다르다.
- **채점 규칙은 기존 `score_format.py`를 가져다 쓴다.** 규칙이 두 군데 있으면 한쪽만 고쳤을 때 보고서와 게이트가 어긋난다.

**QA 체크포인트** — 첫 회귀 판정(v1.0 기준선 → 오늘 재실행)

- Qwen: **PASS.** 지연 +9.1%(허용 20%), 판정 변화 3건
- **Llama의 Q08 날조가 재현됐다.** v1.0의 "GTX 1660 Ti"에 이어 이번엔 "WASD 키 반복 입력", "NVIDIA GPU, 10분 이내". 한 번 우연히 나온 게 아니라는 근거가 생겼다. 그런데 **형식은 멀쩡해서 게이트는 못 잡았다.**
- **Qwen Q07이 `불명확` → `발생(100%)`으로 나빠졌다.** 모호한 불만인데 확정 재현으로 판정한 것. 판정 변화는 아직 참고용이라 PASS였다.
- 둘 다 **v1.2를 해야 하는 이유**가 실제 데이터로 나온 셈이다.

### 2. v1.1.1 — 평가 도구 테스트 + CI

**핵심 개념**

- **모델은 CI에서 돌리지 않는다.** GPU가 없고, 출력이 매번 달라 테스트가 가끔 실패한다(flaky). 대신 커밋된 실제 로그로 "도구가 같은 입력에 같은 판정을 내는지"를 본다.
- **규칙 하나만 어기는 응답으로 테스트한다.** 여러 규칙을 동시에 어기면, 한 규칙 검사가 고장 나도 다른 규칙이 대신 실패해 줘서 테스트가 통과해 버린다.
- **README 수치를 재현하는 테스트(골든 테스트).** 채점 규칙을 고쳤는데 문서 수치가 안 나오면 바로 실패한다.
- **뮤테이션 확인.** 테스트가 통과하는 것만으로는 쓸모를 알 수 없어서, 코드를 일부러 망가뜨렸을 때 실패하는지 봤다(Claude가 수행). R4 검사를 끄면 4개, 기준 파일에 오타를 넣으면 5개가 실패했다.

**QA 체크포인트** — 테스트가 결함 2건을 잡았다 (둘 다 Claude가 테스트 작성 중 발견)

- **경계값 결함.** 허용폭과 정확히 같은 +20%인데 FAIL. `(1.668 − 1.39) / 1.39 × 100 = 20.000000000000004`. 화면에는 "+20.0% (허용 20.0%)"로 보이는데 FAIL이 뜨는 모순. → 변화율을 반올림한 뒤 비교하도록 수정.
  - ISTQB의 **경계값 분석**(BVA)이 경계에서 결함을 찾은 교과서적 사례다. 면접에서는 "Claude와 경계값 테스트를 설계하다 발견했다"로 정확히 말할 것.
- **기준 파일 오타를 조용히 무시.** `strict_rate_mn`처럼 쓰면 그 기준이 빠진 채 PASS. **"잘못 판정하는 것"보다 "검사 안 하고 통과시키는 것"이 더 위험하다.** 문제가 있다는 신호조차 없기 때문이다.

### 3. 기록 — CHANGELOG와 이슈 로그

**핵심 개념**

- `CHANGELOG.md`: 버전별로 추가·변경·수정을 나눠 적고, 각 버전이 답하려는 질문을 함께 쓴다.
- `docs/issue_log.md`: 오늘 나온 문제를 **현상 → 원인 → 조치 → 재발 방지** 형식으로 정리. 결함 5건, 알려진 한계 1건, 관찰 사항 1건. 심각도 기준도 문서 첫머리에 정의했다.
- 이슈 기록은 QA가 매일 쓰던 결함 보고서와 형식이 같다. **8년 동안 해 온 일이 그대로 포트폴리오가 되는 지점**이라 제일 공들일 가치가 있다.

**QA 체크포인트**

- 기록에 "누가 했는가"를 정확히 남긴다. 문서 첫머리에 작업 방식(AI와 협업, 역할 분담)을 밝혔다. 면접에서 코드를 물으면 이 기록이 기준이 된다.

## ⚠️ 오늘의 함정 모음

**1. 재실행 한 번에 README 수치의 출처가 사라진다** (Claude가 재실행 결과 검토 중 발견)
`run_eval.py`가 `local_eval_results.json`을 덮어써서 `summarize_eval.py` 결과가 README와 달라졌다. v1.0 내용으로 되돌리고, 이후로는 `history/`에만 저장하게 바꿨다. **"최신 결과"와 "문서 기준 결과"는 역할이 다르다.**

**2. 게이트를 벤치마크보다 먼저 돌렸다** (내 실수)
`compare_runs.py`를 `run_eval.py`보다 먼저 실행해서, v1.0끼리 비교한 결과(변화 전부 0%)를 보고 "잘 됐다"고 생각할 뻔했다. **명령 순서가 결과의 의미를 바꾼다.** 이제는 출력 첫 줄에 `후보 실행: …` 경로가 찍히므로, **어떤 실행과 비교한 결과인지부터 확인**한다.

**3. 게임을 켜 두고 벤치마크를 돌리면 측정이 오염된다**
재실행에서 Llama가 지연 +45.6%, 속도 −32.5%로 FAIL. 그런데 모델 digest는 v1.0과 같았다. 모델이 아니라 **환경**(같은 GPU를 쓰는 다른 프로그램, 전원 모드 등)의 차이였을 가능성이 높다. 벤치마크를 돌릴 때는 게임을 끄고 전원을 연결한다. v1.2에서 체크리스트로 만들 예정.

**4. 마크다운 굵은 글씨는 한국어 조사 앞에서 깨진다** (내가 GitHub 화면에서 발견)
`**"평가 체계"**로` → 닫는 `**` 앞이 문장부호(`"`)이고 뒤가 글자(`로`)면 굵은 글씨로 인식되지 않는다(CommonMark 규칙). → `"**평가 체계**"로`처럼 따옴표를 밖으로. 좁은 표 칸에서 `완료`가 `완/료`로 쪼개지는 것도 한국어 줄바꿈 특성이었다.

**5. `git add` 없이 `git commit`** (내 실수)
`no changes added to commit`이 나와서 당황했다. git은 **담기(add) → 기록(commit)** 두 단계다.

**6. 첫 CI가 6초 만에 실패했다**
`Unable to resolve action astral-sh/setup-uv@v9`. Claude가 참고한 릴리스 정보가 최신이 아니어서 없는 버전을 적었고, 공식 README 예시(`v10.1.0`)로 고쳐서 성공(13초, 47 passed). 워크플로 파일은 로컬에서 돌려 볼 수 없으니 **push 직후 Actions 탭 확인까지가 작업 완료**다.

**7. PowerShell에서 한글 파일 내용이 깨져 보였다**
`Get-Content`로 CI 파일을 확인하니 한글이 `?됯? ?꾧뎄`처럼 나왔다. 파일은 정상 UTF-8이었고, Windows PowerShell 5.1이 UTF-8(BOM 없음) 파일을 한국어 기본 인코딩(CP949)으로 **표시만** 잘못한 것이었다. 파일이 깨진 건지, 보이는 게 깨진 건지 구분해야 한다.

**8. `.github` 폴더는 원격 도구로 쓸 수 없다**
보안상 보호 위치라 Claude가 직접 넣지 못했고, PowerShell 명령으로 내가 직접 만들었다.
