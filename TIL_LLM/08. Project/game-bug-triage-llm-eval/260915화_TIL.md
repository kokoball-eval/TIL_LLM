## 1. Ollama 응답 메타데이터는 나노초 단위다

`client.generate()`의 응답에는 성능 측정에 쓸 수 있는 필드가 같이 온다.
처음에 `load_duration`을 그대로 찍어보고 "로딩에 2,145,000,000초?" 하고 당황했는데 **단위가 나노초**였다.

```python
response = client.generate(model=model, prompt=prompt, options=OPTIONS)

# 나노초 → 초
load_duration_sec = round(response.get("load_duration", 0) / 1_000_000_000, 3)

eval_count = response.get("eval_count", 0)        # 생성된 토큰 수
eval_duration_ns = response.get("eval_duration", 0)  # 생성에 걸린 시간(ns)
```

- `load_duration` : 모델을 메모리에 올리는 데 걸린 시간
- `eval_count` / `eval_duration` : 생성 토큰 수와 생성 시간
- 전체 응답 시간(`elapsed`)은 직접 `time.perf_counter()`로 잰다

**중요**: `elapsed`와 `eval_duration`은 다르다. `elapsed`는 요청부터 응답 완료까지 전부,
`eval_duration`은 순수 토큰 생성 구간만이다. 이 둘을 섞으면 속도 지표가 엉킨다.

## 2. VRAM은 `ps()`로 재고, "측정 시점 값"이다

```python
ps = client.ps()
for m in ps.get("models", []):
    name = m.get("name", "")
    if name == model or name.startswith(model.split(":")[0]):
        vram_mib = round(m.get("size_vram", 0) / (1024 * 1024), 2)
```

`size_vram`은 바이트 단위라 MiB로 변환해야 한다.
그리고 이건 **그 순간의 점유량**이지 최대 사용량이 아니다.
보고서에 "최대 VRAM"이라고 쓰면 측정하지 않은 값을 주장하는 게 되므로, "VRAM 점유량"으로만 표기했다.

## 3. 워밍업은 결과 배열에서 아예 분리한다

첫 호출은 모델을 디스크에서 GPU로 올리느라 느리다. 실측으로 Qwen 2.145초, Llama 3.429초가 걸렸다.
이 값이 평균에 섞이면 지연 시간 통계가 통째로 왜곡된다.

그래서 **그냥 빼지 않고 별도 키에 저장**했다. 빼기만 하면 나중에 "왜 뺐는지"를 확인할 수 없기 때문이다.

output_payload = {

## 4. 측정 실패를 0으로 채우면 안 된다

이번에 가장 크게 배운 습관. `eval_duration`이 0이면 나눗셈이 터지니까 예외 처리를 해야 하는데,
이때 **0으로 채우고 싶은 유혹**이 생긴다. 하지만 "측정에 실패했다"와 "실제로 0이다"는 완전히 다른 의미다.
0으로 채우면 평균이 조용히 왜곡되고, 나중에 원인을 추적할 수도 없다.

```python
tokens_per_sec = (
    round(eval_count / (eval_duration_ns / 1_000_000_000), 2)
    if eval_duration_ns > 0
    else None          # 0이 아니라 None(결측)으로 남기고 사유를 기록
)
```

## 5. 비교 실험에서는 `generate()`로 입력을 통제했다

`chat()`은 system/user 역할을 나눠 넣을 수 있어 편하지만, **모델마다 chat template이 다르게 적용된다**.
같은 문장을 넣어도 실제로 모델에 들어가는 최종 입력이 미묘하게 달라진다는 뜻이다.

두 모델을 비교하는 게 목적이라면 그 차이 자체가 통제되지 않은 변인이 되므로,
시스템 프롬프트를 문자열로 직접 이어붙여 `generate()`에 통째로 넣었다.

```python
prompt = f"{SYSTEM_PROMPT}\n\n[버그 리포트]\n{report_text}"
response = client.generate(model=model, prompt=prompt, options=OPTIONS)
```

Cloud 비교 스크립트도 같은 방식으로 조립해서, 로컬과 클라우드가 받은 입력을 동일하게 맞췄다.

## 6. TPS가 빠른데 체감은 느릴 수 있다 (Latency Paradox)

| 지표 | Qwen2.5-7B | Llama-3.1-8B |
|---|---:|---:|
| 초당 생성 속도 | 58.74 tokens/s | **66.52 tokens/s** |
| 평균 생성 토큰 수 | **76.5 tokens** | 117.6 tokens |
| 평균 응답 시간 | **1.390초** | 1.809초 |

Llama가 초당 13% 빠른데 최종 응답은 Qwen이 23% 빨랐다.
**Llama가 말을 1.5배 길게 했기 때문**이다.

여기서 배운 것 — `tokens/s`는 하드웨어 디코딩 처리량이지 사용자 체감 속도가 아니다.
체감 속도는 `초당 속도 × 생성 토큰 수`로 결정되므로, 출력이 간결한 모델이 실무에선 더 빠를 수 있다.

## 7. 오늘의 진짜 배움: 정보가 없을 때 모델이 하는 행동

`"크래시남"` 한 단어짜리 리포트를 넣었더니 두 모델의 반응이 갈렸다.

**Llama-3.1** — 원문에 없는 내용을 지어냈다.
- 1회차: `[요약]: 게임 내 전투 모드에서 플레이어 캐릭터가 무한히 이동하는 결함 현상 발생`
- 2회차: `[누락 정보]: ... Windows 10, Intel Core i5, NVIDIA GeForce GTX 1660 Ti`

입력 어디에도 없는 증상과 하드웨어 사양을 **확정적인 문장으로** 적었다.

**Qwen2.5** — 지어내진 않았지만 `누락 정보: 없음`으로 소극적으로 처리했다.

둘 다 결함이지만 성격이 다르다.
Qwen의 소극성은 "이럴 땐 되물어라"는 규칙이나 예시 한 건으로 교정할 수 있다.
반면 없는 사실을 만들어내는 건 프롬프트로 통제하기 어렵고, QA 파이프라인에 들어가면
**존재하지 않는 버그 티켓이 자동 발행된다**.

> 모델을 고르는 기준이 "누가 더 잘하냐"가 아니라
> **"어떤 실패를 감당할 수 있느냐"**라는 걸 오늘 처음 체감했다.

1일차에 세웠던 "Llama가 승자" 가설을 여기서 뒤집었다.

## 8. 2회 반복은 그 자체로 정보다

문항당 2회를 돌리라는 요건이 처음엔 형식적으로 보였는데, 돌려보니 아니었다.
같은 입력·같은 설정인데도 Llama는 **10문항 전부** 응답이 달랐고 (Qwen은 10문항 중 5개),
그중 3건은 판정 자체가 바뀌었다.

- Llama Q08: 심각도 `Critical` → `Blocker`, 모듈 `전투` → `시스템`
- Llama Q09: 심각도 `Critical` → `Major`
- Qwen Q08: 모듈 `시스템` → `네트워크`

같은 버그를 두 번 넣었는데 심각도가 달라진다면 트리아지 자동화에 그대로 쓸 수 없다.
**반복 실행은 낭비가 아니라 안정성 측정**이었다.
