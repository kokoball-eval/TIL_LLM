## 💡 오늘의 학습 총평

- **핵심 통찰: 5장에서 방향이 뒤집힌다**
  - 1~4장은 **남의 API에서 데이터를 받아오는 쪽**(클라이언트)이었고, 5장부터는 **내가 API를 만들어 내주는 쪽**(서버)이다.
  - 2장에서 배운 `GET`/상태 코드/`header·query·body`가 **반대편에서 다시 나온다.** 받는 쪽에서 익힌 개념을 주는 쪽에서 재사용하는 구조라 5장이 유난히 익숙했다.
  - 그래서 2장을 대충 넘겼으면 5장에서 두 번 고생할 설계다. 교안이 왜 수집을 먼저 가르치는지 이제 이해됐다.

- **두 번째 통찰: 1장부터 6장까지 관통하는 단어는 '계약(contract)'이다**
  - 1-2강 이용 조건 기록 → 2-1강 요청 구조 분석표 → 4-2강 "작은 문서 계약" → 5-1강 "API 계약" → 6-1강 "스키마는 데이터 계약".
  - 매 장마다 같은 단어가 나오는데 우연이 아니다. **경계선을 먼저 글로 정하고 구현을 맞추는 순서**를 계속 훈련시키는 것.
  - 7장에서 배운 `Prompt Contract`, `JSON Schema`도 같은 뿌리였다. 대상만 LLM에서 API로 바뀐 것.

- **세 번째 통찰: Pydantic을 두 번째로 만났다**
  - 260911 TIL에 적었던 `strict=True`, `extra="forbid"`, `@model_validator` — 그건 **LLM 출력을 검증**하는 용도였다.
  - 6-1강은 같은 도구를 **API 입력을 검증**하는 데 쓴다. 둘 다 "신뢰할 수 없는 외부 입력에 경계선을 긋는" 같은 일이다.
  - 이제 Pydantic이 특정 기능이 아니라 **경계 방어 도구**로 보인다.

- **향후 계획 및 다짐**
  - `/openapi.json`이 오늘 가장 크게 남았다. **기계가 읽을 수 있는 API 계약서**가 자동으로 생긴다는 건, 계약 테스트·breaking change 감지·테스트 자동 생성의 입구가 열린다는 뜻이다.
  - LLM Eval 파이프라인을 짤 때 이걸 어떻게 쓸지 따로 정리해두자. SDET 포지션에서 실제로 쓰이는 기술이다.

## 4장. 수집 데이터 정제와 RAG용 문서 데이터셋 구성

### 4-1강 : 데이터 품질 점검과 정제
- **핵심 개념**:
  - **"파일을 읽을 수 있는가?" 다음에 "같은 기준으로 사용할 수 있는가?"** 를 확인해야 한다. JSON 문법이 완벽해도 값의 품질은 별개.
  - 다루는 문제는 다섯 가지로 한정: `결측` · `중복` · `HTML` · `공백` · `날짜`.
  - 3장에서 저장한 원천 파일은 **덮어쓰지 않고** 정제 결과를 별도 파일로 만든다.
- **결측의 네 가지 얼굴**:
  - 키 자체가 없음 / 값이 `None` / 빈 문자열 `""` / **공백만 `"   "`**
  - 네 번째가 함정. 눈으로 보면 뭔가 있는 것 같지만 쓸 수 있는 값이 아니다.
  - 판정은 `not record.get("title", "").strip()` — 키 없음과 공백을 한 번에 처리.
- **중복은 기준이 먼저다**:
  - **제목이 같다고 같은 문서가 아니다.** 원천이 준 `source_id`를 기준으로 삼고 `set`으로 기시감을 검사.
  - 이번 fixture는 "첫 레코드 유지"지만 이것이 모든 데이터의 정답은 아니다. 최신 수정본을 유지해야 하면 갱신 시각을 비교해야 한다.
- **HTML·공백 정리 순서**:
  - `html.unescape()` (entity → 문자) → `re.sub(r"<[^>]+>", " ", ...)` (태그 제거) → `" ".join(text.split())` (공백 통일)
  - **Why?** → `&nbsp;`를 먼저 공백으로 바꿔야 마지막 단계에서 다른 공백과 함께 정리된다. 순서를 뒤집으면 entity가 문자 그대로 남는다.
  - 교안이 정규식의 범위를 명시: **통제된 학습용 HTML에만 적합.** 스크립트·스타일·잘못 닫힌 태그가 있는 실제 웹 문서는 HTML parser를 써야 한다.
- **날짜는 추측하지 않는다**:
  - 허용 형식을 `DATE_FORMATS`로 고정하고 순서대로 `strptime` 시도, 전부 실패하면 `None` 반환.
  - **읽지 못한 날짜를 오늘 날짜로 바꾸지 않는다.** 이유 두 가지 — ① 실행일마다 결과가 달라져 재현성이 깨진다 ② 원천에 없던 사실을 만든다.
- **QA 체크포인트**:
  - **건수 등식 `입력 = 정상 + 중복 + 제외`** 가 이 강의의 유일하고 확실한 검증 장치. 테스트 리포트의 `Total = Pass + Fail + Blocked + Skipped`와 같은 구조로, 안 맞으면 어느 분기에서 카운터를 빠뜨린 것.
  - "억지로 채우지 않는다"는 **결함 은폐 금지**와 같다. 결측을 빈 값으로 채우는 건 재현 안 되는 버그를 "재현 불가"로 닫는 것과 동일 — 문제가 사라진 게 아니라 보이지 않게 된 것.
  - 날짜 추측은 **비결정성(non-determinism) 주입**. 어제 통과한 게 오늘 실패하고 원인은 코드가 아니라 시계인 상황 = flaky test의 메커니즘 그대로.
  - **검사 순서가 결과를 바꾼다.** 이번 코드는 `중복 → 필수값` 순서인데, 뒤집으면 살아남는 레코드가 달라진다. 교안이 "fixture에 맞춘 순서"라고 명시한 것은 테스트 전제조건을 밝힌 좋은 태도.
  - "파일이 생성되면 성공"은 스모크 테스트만 하고 통과 처리하는 것. 건수 합계·필수 필드·태그 잔존·날짜 형식·**두 번 실행 동일성**까지 확인해야 한다.

### 4-2강 : 본문/메타데이터 분리와 RAG 문서셋 구성
- **핵심 개념**:
  - 정제 레코드의 모든 필드가 유용하지만 **역할은 같지 않다.** 검색할 것과 설명할 것을 나눈다.
  - 문서 한 건을 세 부분으로: `document_id`(다시 찾는 이름) · `content`(검색 대상) · `metadata`(표시·필터·출처)
  - 도서관 비유 — 책 본문(content), 도서카드(metadata), 청구기호(document_id).
- **왜 한 문자열로 합치지 않는가**:
  - 모든 값을 `join`하면 URL의 기호와 날짜 숫자가 **의미 검색에 끼어든다.**
  - 반대로 제목·URL을 다 빼면 검색 결과 화면에 **보여줄 게 없다.**
  - 그래서 역할별로 나눠서 둘 다 갖는다. `metadata`를 `content`에 중복 삽입하지도 않는다 — 기준값이 어느 쪽인지 모호해진다.
- **필드 배치 판단 4문**:
  - 의미 검색에 직접 쓰나? → `content` / 필터·정렬 값인가? → `metadata` / 원문 확인용인가? → `metadata` / 같은 문서를 다시 찾는 값인가? → ID 재료
- **document_id는 제목이 아니라 원천 ID로**:
  - 제목은 **수정될 수 있고 겹칠 수 있다.** `source_id`에 `doc-` 접두사를 붙여 `doc-news-001` 형태로 만든다.
  - 영문·숫자·하이픈 외 문자는 하이픈으로 치환 (`"guide 010"` → `doc-guide-010`).
  - 시각이나 난수를 쓰지 않으므로 **같은 입력이면 항상 같은 ID**가 나온다.
- **ID와 내용 버전은 다른 개념**:
  - 본문이 수정돼도 같은 원천 문서라면 `document_id`는 유지. "내용이 바뀌었나?"는 SHA-256 같은 해시로 별도 판단 (심화).
- **저장 전 검증 3종**:
  - `document_id`가 비어있지 않은 문자열인가 / 같은 ID가 두 번 있지 않은가 / `content`와 `metadata.source_url`이 있는가
  - `enumerate()`로 위치를 함께 추적해 오류 메시지에 몇 번째 문서인지 넣는다.
- **QA 체크포인트**:
  - 교안의 **"값의 출처 추적표"** 는 요구사항 추적 매트릭스(RTM)와 구조가 같다. 검색 결과가 이상할 때 "이 값이 어느 단계에서 왔지?"를 즉시 역추적할 수 있게 하는 장치 — 파이프라인 단계가 늘어날수록 **결함 격리(fault isolation)** 의 유일한 근거가 된다.
  - `document_id`의 **멱등성(idempotency)**: 같은 입력이 항상 같은 ID를 만들면 파이프라인을 몇 번 재실행해도 문서가 중복 생성되지 않는다. 8-3강 "부작용 Tool 4대 방어선"의 멱등성과 같은 개념.
  - 반대로 ID에 타임스탬프나 UUID를 쓰면 **돌릴 때마다 새 문서가 생겨 벡터DB에 같은 내용이 쌓인다.**
  - "작은 문서 계약"이라는 표현에 주목. `4장 dict 구조 → 6장 Pydantic 스키마 → 7장 Query API` 로 이어지는 **계약 우선 설계**의 첫 단계.
  - 검증을 **파일을 쓰기 전에** 하는 것이 릴리스 게이트. 쓰고 나서 확인하면 이미 오염된 산출물이 존재한다.
  - "JSON 저장하면 바로 RAG 된다"는 오해 = **완료 정의(DoD) 착각.** 지금 만든 건 문서의 '모양'이고, 청킹·임베딩·인덱싱이 남았다. 교안이 강의마다 "여기까지가 범위"를 긋는 것이 학습자의 진척도 오판을 막는 장치.
  - `metadata`도 검색에 쓰인다 — `content`는 **검색 문장**, `metadata`는 **검색 조건**. "작년에 나온 문서 중 환불 규정"이면 전자는 content, 후자는 metadata 필터.

## 5장. FastAPI 서버와 REST API 기본 구조

### 5-1강 : 클라이언트-서버 / REST / FastAPI 프로젝트 구조
- **핵심 개념**:
  - 클라이언트는 브라우저만이 아니다. **3장에서 만든 그 수집 코드도 클라이언트였다.** 모바일 앱, Python 프로그램, 모니터링 도구 전부 해당.
  - 클라이언트는 서버의 Python 함수를 직접 실행하지 않는다. **서버가 공개한 URL로 HTTP 요청을 보낸다.**
  - **API 계약** = 클라이언트가 알아야 할 네 가지: method / path / 필요한 입력 / 응답 모양. 서버가 DB를 쓰는지 파일을 쓰는지는 숨겨진다.
- **REST — URL은 명사, method는 동사**:
  - `/getDocumentsNow` ❌ → `GET /documents` ⭕. URL은 **다룰 대상**, method가 **동작**을 표현.
  - `GET /documents`와 `POST /documents`는 path가 같아도 다른 요청. **method와 path는 항상 한 쌍으로 읽는다.**
- **FastAPI vs Uvicorn (가장 헷갈리는 지점)**:
  - `app = FastAPI()`를 실행해도 **서버는 열리지 않는다.**
  - `FastAPI` = 어떤 요청을 어떤 함수가 처리할지 **정의** (메뉴판과 요리사)
  - `Uvicorn` = 지정한 주소·포트에서 요청을 **대기** (가게 문을 열고 전화를 받는 역할)
  - `uvicorn.run("app.main:app", ...)` 의 `"app.main:app"`은 `app/main.py`의 `app` 객체를 뜻한다.
- **데코레이터 한 줄의 구조**:
  - `@app.get("/")` → `app`(등록할 객체) + `get`(허용 method) + `"/"`(받을 path) + 아래 함수(처리 로직)
  - Python 사전·리스트를 그냥 `return`하면 FastAPI가 JSON으로 변환한다.
  - **함수 이름은 API 주소가 아니다.** 클라이언트는 `read_root()`를 요청하지 않고 `GET /`을 요청한다.
- **자동 문서 2종**:
  - `/docs` — **사람이 보는** Swagger UI (직접 눌러서 테스트 가능)
  - `/openapi.json` — **기계가 읽는** API 계약서
  - 함수 아래 docstring이 문서 설명으로 자동 반영된다.
- **TestClient**:
  - `TestClient(app)`은 app을 직접 감싸므로 **실제 네트워크 포트가 필요 없다.**
  - 검증은 상태 코드와 JSON을 **함께** — 상태만 200이고 본문이 비어있을 수 있다.
- **QA 체크포인트**:
  - **"클라이언트는 내부 구현을 몰라도 된다"는 문장은 블랙박스 테스팅의 정의 그 자체.** 테스트 기준은 "코드가 이렇게 생겼으니"가 아니라 "계약이 이렇다고 했으니"여야 한다. 구현을 보고 테스트를 쓰면 구현이 바뀔 때마다 깨지고 정작 계약 위반은 못 잡는다.
  - **`/openapi.json`이 오늘의 최대 수확.** 기계가 읽는 계약서가 자동으로 존재하면 ① 계약 테스트 ② 배포 전후 스키마 diff로 breaking change 자동 감지 ③ 테스트 스켈레톤 자동 생성 ④ endpoint 커버리지 측정이 가능해진다. SDET 실무의 입구.
  - "자동 문서가 있으면 검증 끝"은 오해. **`/docs`는 선언된 계약, TestClient는 실제 동작.** 이 둘의 불일치가 실제 버그의 큰 원천이며, 문서에 200이라 써 있는데 500이 나는 상황을 문서만으로는 절대 못 잡는다.
  - TestClient의 위치 = **테스트 피라미드 중간층.** 라우팅·직렬화·검증을 다 거치면서 네트워크 불안정성이 없어 flaky하지 않고 CI에 적합. 3장의 MockTransport(외부 API를 가짜로)와 대칭 구조.
  - 테스트는 **함수 이름이 아니라 HTTP 계약**을 잡아야 한다. 함수 직접 호출 테스트는 리팩토링에 깨지고, 클라이언트가 실제로 겪는 것을 검증하지 못한다.

### 5-2강 : Routing / parameter / request / response와 /health
- **핵심 개념**:
  - 라우팅은 **method + path 조합**으로 함수를 찾는다. `GET /health`는 연결되지만 `POST /health`(method 다름), `GET /health/detail`(path 다름)은 연결되지 않는다.
- **입력 3종 구분**:
  | 종류 | 위치 | 역할 | 필수 |
  |---|---|---|---|
  | path parameter | URL 경로 안 `{}` | **어떤** 자원인지 선택 | 필수 |
  | query parameter | `?` 뒤 | **어떻게** 볼지 조절 | 보통 선택 |
  | request body | 본문 JSON | 구조화된 데이터 전달 | — |
  - **구분 기준**: `document_id`가 바뀌면 다른 자원을 보고, `limit`이 바뀌면 같은 자원을 다르게 본다.
- **FastAPI의 입력 위치 판정**:
  - route path에 `{이름}`이 있고 같은 이름의 매개변수 → path / `BaseModel` 타입 → body / 나머지 단순 매개변수 → query
  - 자동 형변환도 해준다. URL의 `limit=12`는 글자로 오지만 `limit: int` 선언이 있으면 정수로 변환, `limit=hello`는 422.
- **Query 제약과 검사 시점**:
  - `Query(default=30, ge=5, le=100)` — `ge`=greater or equal(최소), `le`=less or equal(최대)
  - **`limit=2`는 내 함수 코드가 한 줄도 실행되기 전에** FastAPI가 422를 만든다. 방어 코드를 함수 안에 쓰지 않아도 된다.
- **상태 코드 3종 — 404와 422의 차이**:
  - `200` 정상 처리
  - `404` ID 형식은 맞는데 **그 문서가 없음** (찾아보고 없다고 답한 것) → `HTTPException(404, detail=...)`
  - `422` 입력이 **선언한 타입·범위에 안 맞음** (찾아보기도 전에 거절한 것)
  - 우편 비유 — 404는 주소 형식은 맞는데 그 집이 없음, 422는 우편번호 칸에 한글을 쓴 것.
  - **422는 서버 고장이 아니다.** 4xx는 클라이언트 문제이고, 오류 body에 어느 입력이 틀렸는지 위치 정보가 들어있다.
- **`/health`**:
  - `{"status": "ok"}` 하나만 반환하는 아주 작은 endpoint. 모니터링 프로그램이 주기적으로 호출.
  - **"health가 200이면 다 정상"은 오해.** 이건 API 프로세스가 요청을 처리할 수 있다는 최소 신호이며, DB 연결이 끊겼어도 200이 나올 수 있다.
- **5개 검증 시나리오**:
  - `GET /health` → 200 / `GET /documents/{id}?limit=12` → 200 / `GET /documents/doc-news-999` → 404 / `POST /preview` + body → 200 / `?limit=2` → 422
- **QA 체크포인트**:
  - **위 5개가 그대로 최소 테스트 스위트 설계다.** 헬스체크(사전 조건) + happy path + not found + 다른 입력 위치 + invalid input. 정상 1개에 비정상 2개 — 초보 설계에서 가장 많이 빠뜨리는 게 404/422 케이스다.
  - **경계값 분석이 필수.** `ge=5, le=100`이면 `4 / 5 / 100 / 101 / 생략 / hello`를 시험해야 한다. `>=`를 `>`로 잘못 쓴 off-by-one은 **경계값 그 자체(5, 100)를 넣지 않으면 절대 안 잡힌다** — 4와 101만 테스트하면 통과해버린다.
  - **검증이 어디서 일어나는지가 결함 격리를 결정한다.** `422`=FastAPI 검증 계층(내 함수 실행 전) / `404`=내 함수 로직 / `500`=내 코드 버그. 3단이 분리돼 있으면 상태 코드 분포만 보고 원인을 좁힐 수 있다 — 422 급증은 클라이언트 계약 위반, 404 급증은 데이터 부재, 500 급증은 내 코드. 2-2강 "실패 계층 5단"이 서버 쪽에서 재현된 것.
  - **`/health`의 범위 설계는 QA/SRE 경계에서 실제로 사고가 나는 지점.** 얕으면 장애를 놓치고(200인데 서비스는 죽음), 깊으면 남의 장애로 내 서버가 재시작된다. 실무에서는 `liveness`(프로세스 응답 가능 → 재시작 판단)와 `readiness`(의존성 포함 → 트래픽 투입 판단)로 나눈다. 교안은 얕은 것만 만들지만 **"무엇을 보장하고 무엇을 보장하지 않는가"를 명시한 것**이 알람 설계의 전제가 된다.

## 6장. Pydantic 스키마와 문서 관리 API 구현

### 6-1강 : BaseModel 요청/응답 스키마 설계
- **핵심 개념**:
  - 4-1강의 문제가 재등장한다. **JSON 문법이 맞아도 업무 규칙은 틀릴 수 있다.** JSON parser는 중괄호와 쉼표만 확인한다.
  - 손으로 검사하면 필드 4개 × 검사 4종(존재/타입/길이/기본값) = 16분기가 **endpoint마다 복붙**된다.
  - Pydantic은 이 조건을 **모델 한 곳에 표로 선언**하게 해준다. "이 JSON에 어떤 필드가 있어야 하고 각 값은 어떤 조건을 만족해야 하는가"를 코드로 적은 표.
- **BaseModel**:
  - 상속하면 **객체를 만드는 순간 검증이 실행된다.** 통과하면 `dict`가 아니라 객체가 되므로 `request["title"]`이 아니라 `request.title`로 읽는다.
  - **기본값이 없는 필드는 자동으로 필수.** 빠지면 오류.
  - `model_dump()`로 검증된 모델을 일반 사전으로 되돌릴 수 있다.
  - 입국 심사대 비유 — 창구에서 서류를 다 확인하고, 통과한 이후엔 유효하다고 믿고 일할 수 있다.
- **Field로 조건 붙이기**:
  - `min_length` / `max_length` / `description` / `default`
  - **`description`이 OpenAPI 문서에 자동으로 나간다.** 검증 규칙과 문서 설명이 같은 한 줄에서 나온다.
  - 교안 주의: 제약조건 숫자는 "좋아 보이는 값"이 아니라 **서비스 요구와 저장 한계**를 기준으로 정해야 한다.
- **`default_factory=list` — 조용한 버그 방어**:
  - 리스트는 변경 가능한 객체이므로 `default=[]`로 두면 **모든 요청이 같은 리스트를 공유**한다.
  - `default_factory=list`는 모델을 만들 때마다 새 빈 리스트를 만든다. `assert first.tags is not second.tags`로 독립성 확인.
  - **`tags`의 `max_length=5`는 리스트 원소가 최대 5개**라는 뜻. 태그 하나의 글자 수가 아니다.
- **요청 모델 ≠ 응답 모델**:
  - 요청 = 클라이언트가 아는 값 (`title`, `content`, `source_url`, `tags`)
  - 응답 = 거기에 **서버가 만든 값**이 더해짐 (`document_id`, `created_at`)
  - `@app.post("/documents", response_model=DocumentResponse)` 로 응답 모양까지 선언하면 자동 문서가 명확해진다.
- **검증 오류는 `loc`로 읽는다**:
  - `error.errors()`가 필드별 오류 정보를 사전 목록으로 반환. `item["loc"]`=위치, `item["type"]`=오류 종류.
  - 교안 조언: **오류 메시지를 통째로 외우지 말고 위치와 제약조건을 연결해서 읽어라.**
- **validator 하나, 순서가 핵심**:
  - 공백만 든 `"   "`은 길이 3이라 `min_length=2`를 **통과해버린다.**
  - `@field_validator("title", "content", "source_url", mode="before")` — **`mode="before"`가 Field 길이 검증 *전에* 실행**되므로 공백 제거 후 길이를 검사할 수 있다.
  - `isinstance(value, str)` 체크는 문자열이 아닌 값에 `.strip()`을 부르지 않고 **Pydantic의 타입 검사에 넘기기 위한 것.**
- **QA 체크포인트**:
  - **검증 규칙과 문서가 같은 출처에서 나온다 — 오늘 가장 큰 수확.** "문서엔 100자인데 실제론 50자에서 잘림" 같은 고질병은 문서와 코드가 다른 곳에 있어서 생긴다. Pydantic은 그 불일치를 **구조적으로 불가능하게** 만든다. 테스트로 잡는 게 아니라 설계로 없애는 것이고, 문서를 신뢰할 수 있게 되면 **문서에서 테스트를 생성**할 수 있다.
  - **`loc`/`type`으로 assert 하고 메시지 문구로 assert 하지 마라.** 메시지는 라이브러리 버전에 따라 바뀌어 코드는 정상인데 테스트가 깨지는 false failure를 만든다. UI 자동화에서 화면 텍스트 대신 요소 ID로 잡는 것과 같은 원칙.
  - **`default_factory` 누락은 잡기 가장 어려운 침묵형 버그.** 첫 요청은 정상이고 두 번째 요청에서 앞의 태그가 남는다 → **단일 요청 테스트로는 절대 안 잡힌다.** 같은 프로세스에서 요청을 두 번 이상 보내고 두 번째의 상태가 깨끗한지 확인하는 **상태 오염(state pollution) 테스트**가 필요하다.
  - **한글 경계값 주의.** `title="문서"`는 한글 2자로 `min_length=2`를 만족하지만, 한글은 문자 수와 바이트 수가 다르다. `min_length`는 문자 기준인데 DB 컬럼은 바이트 기준일 수 있어 저장 단계에서 잘린다. **한글·이모지 경계값 테스트는 국내 서비스 QA의 기본.**
  - **요청/응답 모델 분리는 보안 방어이기도 하다.** 모델이 하나였다면 클라이언트가 `{"document_id": "doc-admin-001"}`을 보내 남의 문서를 덮어쓸 수 있다 — **mass assignment 취약점.** API 보안 체크리스트 항목: "서버 소유 필드를 요청에 넣어보면 어떻게 되나?"
  - "validator는 많을수록 안전"은 오해. **검증 로직의 복잡도가 곧 테스트 조합의 크기.** Field로 표현 가능한 조건은 Field로(선언적, 문서에 반영, 순서 명확) 쓰고 꼭 필요한 변환만 validator로. 교안이 validator 하나를 세 필드에 공유시킨 것은 좋은 절제.
  - **순서 의존성은 4-1강과 같은 패턴.** `중복→필수값`(4-1), `공백제거→길이검사`(6-1). 코드 리뷰 질문이 생긴다 — *"이 검사들의 순서가 바뀌면 결과가 달라지나? 달라진다면 의도된 것이고 문서화돼 있나?"* 순서 의존성이 문서에 없으면 리팩토링 후 **테스트는 통과하는데 동작은 달라지는** 사고가 난다.
