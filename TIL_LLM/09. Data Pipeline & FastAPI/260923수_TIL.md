## 💡 오늘의 학습 총평

- **핵심 통찰: 8장 2강에서 3장 1강으로 되돌아왔다**
  - 3-1강에서 **429는 대기 후 같은 page 재시도**라고 배웠는데, 8-2강에서는 **429를 즉시 실패로 확정**한다. 정반대다.
  - 처음엔 모순인 줄 알았는데 맥락이 달랐다. 3-1강은 **페이지네이션 GET**(멱등, 부작용 없음)이고 8-2강은 **생성 POST**(중복 처리·중복 과금 위험)다.
  - **같은 상태 코드라도 요청의 성격에 따라 대응이 달라진다.** "429를 만나면 어떻게 한다"를 외운 게 아니라 "무엇을 기준으로 판단하는가"를 배워야 했던 것.
  - 교안이 8-2강에서 *"POST 재시도 주의: 첫 요청을 처리하고도 응답만 늦었을 수 있다"* 고 명시한 게 이 대비의 핵심이다.

- **두 번째 통찰: 오늘 배운 건 전부 '계약을 유지하는 법'이었다**
  - 7-2강에서 `mock` / `external` / `ollama` 세 경로가 **모두 같은 `QueryResponse(answer, sources, provider)`** 를 반환한다.
  - 외부 서비스의 JSON 키가 `answer`든 `message.content`든, 클라이언트는 그 차이를 모른다. **경계에서 변환해 내부 계약을 지키는 것.**
  - 그래서 공급자를 갈아끼워도 클라이언트 코드는 그대로다. 4장 "작은 문서 계약" → 6장 Pydantic 스키마 → 7장 Query 계약으로 이어지는 설계가 여기서 결실을 맺었다.

- **세 번째 통찰: 1~8장이 한 바퀴 돌아 닫혔다**
  - `수집(1~3장) → 정제·문서화(4장) → 서빙(5~6장) → LLM 연동(7장) → 안정화(8장)`
  - 각 장에서 미뤄뒀던 것들이 정확히 약속한 자리에서 회수됐다. 2-1강의 429 예고 → 3-1강, 3-1강의 "지수 백오프는 8장에서" → 8-2강, 5-2강의 "201은 6-2강에서" → 6-2강.
  - **커리큘럼 자체가 의존성 그래프로 설계돼 있다.** 진도를 건너뛰면 왜 막히는지 이제 이해된다.

- **향후 계획 및 다짐**
  - 이 과정 전체를 관통한 도구는 결국 **MockTransport와 고정 fixture**였다. 1장부터 8장까지 단 한 번도 실제 네트워크에 의존하지 않고 모든 시나리오를 재현했다.
  - LLM Eval 파이프라인에 그대로 옮길 수 있는 자산이다. 별도 문서로 정리하자.

## 6장. Pydantic 스키마와 문서 관리 API 구현

### 6-2강 : 문서 등록/조회 API 구현
- **핵심 개념**:
  - 세 endpoint로 최소 CRUD의 C와 R만 완성. `POST /documents`(201) · `GET /documents`(200) · `GET /documents/{document_id}`(200)
  - 저장소는 **Python 사전 두 개**. `DOCUMENTS`(ID → 문서)와 `SOURCE_INDEX`(URL → ID). 두 번째는 URL 중복을 빠르게 찾기 위한 색인.
  - 등록 처리 순서: 요청 → Pydantic 검증 → ID 생성 → 사전 저장 → 201 + JSON 반환
- **상태 코드 5종이 각각 다른 계층의 실패**:
  | 코드 | 상황 | 클라이언트의 대응 |
  |---|---|---|
  | 200 | 조회 성공 | 응답 사용 |
  | 201 | 새 문서 등록 성공 | 새 자원이 생김 |
  | 404 | ID에 해당하는 문서 없음 | 다른 ID 확인 |
  | 409 | 같은 원문 URL이 이미 등록됨 | 기존 문서 사용 |
  | 422 | 필드/길이 오류 | JSON body 수정 |
  - **409는 요청 형식 오류가 아니다.** Pydantic 검증은 통과했고 타입·길이도 올바르다. **현재 저장소 상태와 충돌**하는 것.
- **모델 상속과 언패킹**:
  - `class DocumentResponse(DocumentCreate)` — 요청 필드를 상속받고 `document_id`만 추가.
  - `DocumentResponse(document_id=..., **request.model_dump())` — `**`가 사전의 key-value를 이름 있는 인자로 펼친다.
  - `model_config = ConfigDict(str_strip_whitespace=True)` — 6-1강의 `@field_validator` 대신 모델 설정 한 줄로 모든 문자열의 공백을 제거.
- **빈 목록은 404가 아니다**:
  - 저장소가 비어도 `GET /documents`는 **빈 리스트 `[]`와 200**을 반환. **목록 자원은 존재하고 항목이 0개**라는 뜻.
  - 한 건 조회(`/documents/{id}`)는 없으면 404. 컬렉션과 개별 자원의 의미가 다르다.
- **메모리 저장소의 한계 (교안이 명시)**:
  - 장점: 코드가 짧고 흐름이 보임 / 파일 권한 문제 없음 / 테스트 초기화 쉬움
  - 한계: **서버를 끄면 사라짐** / 여러 프로세스가 공유 불가 / 많은 데이터 검색 어려움
  - 심화의 JSON 내보내기도 "동시 쓰기·중간 실패·서버 간 공유를 해결하지 않는다"고 범위를 못 박음.
- **QA 체크포인트**:
  - **`clear_store()`가 두 사전을 *함께* 비우는 이유가 핵심.** 한쪽만 비우면 **"문서는 없는데 URL은 중복으로 판단"되는 상태 불일치**가 생긴다. 이건 테스트 격리 실패의 전형이며, 증상이 "두 번째 테스트만 이상하게 실패"로 나타나 원인 추적이 어렵다.
  - **테스트에서 ID를 하드코딩하지 않는다.** 교안이 `created.json()["document_id"]`를 꺼내 조회에 쓴다 — **ID 생성 규칙에 의존하지 않는 테스트**. 규칙이 `doc-news-001`에서 UUID로 바뀌어도 테스트는 안 깨진다.
  - **순번 ID `f"doc-news-{len(DOCUMENTS)+1:03d}"`의 위험을 교안이 직접 밝힘** — 삭제 후 재등록 시 ID 충돌, 여러 서버 동시 처리 시 race condition. 단일 프로세스 실습 전용임을 명시한 것이 좋은 태도.
  - **`response_model`은 입력이 아니라 출력 계약 검증.** endpoint가 실수로 다른 필드를 반환하면 여기서 걸린다. 6-1강의 요청 검증과 **방향이 반대인 방어선**.
  - **409는 "상태 의존 실패"라 단일 요청 테스트로 못 잡는다.** 같은 payload를 **두 번 연속** 보내야 재현된다. `default_factory` 버그와 같은 종류 — 순서·상태가 있는 테스트가 필요하다.
  - 중복 정책은 서비스마다 다르다(거절 / 기존 반환 / 본문 갱신). **중요한 건 정책을 상태 코드와 응답으로 일관되게 표현하는 것** — 테스트는 정책의 일관성을 검증해야 한다.

## 7장. LLM 연동 Query API 구현

### 7-1강 : Query 요청/응답 구조와 context 설계
- **핵심 개념**:
  - **이번 강의는 LLM을 호출하지 않는다.** 먼저 "무엇을 질문하고 어떤 자료를 근거로 쓸지" 계약만 완성.
  - 튜터의 이유가 명확하다 — *"모델 연결까지 한꺼번에 넣으면 오류가 요청 때문인지, 문서 조회 때문인지, 외부 서비스 때문인지 구분하기 어렵다."*
  - 흐름 4단계: 요청 검증 → 근거 결정 → 프롬프트 조합 → 응답 모양 정리
- **세 필드의 역할 분리**:
  - `question` — **무엇을 알고 싶은가** (항상 필수)
  - `context` — 요청에 직접 넣는 근거 (짧은 본문 1회성에 적합)
  - `document_id` — 저장 문서를 가리키는 표지 (같은 문서를 반복 질문할 때 편리)
  - `answer`와 `sources`는 **서버가 만드는 값**이므로 요청에 넣지 않는다.
- **정확히 하나(XOR) 규칙**:
  | document_id | context | 결과 |
  |---|---|---|
  | 있음 | 없음 | 허용 |
  | 없음 | 있음 | 허용 |
  | 있음 | 있음 | **거부** |
  | 없음 | 없음 | **거부** |
  - 둘 다 보내면 **어느 근거를 우선할지 모호**하고, 둘 다 없으면 **답변 근거가 없다.**
  - `@model_validator(mode="after")`로 구현. `has_document == has_context`이면 둘 다 True거나 둘 다 False.
- **`extra="forbid"`**:
  - `question`을 `quesiton`으로 쓴 오타를 **모델 검증 단계에서 즉시 거부**한다. 없으면 코드 깊은 곳에서야 발견된다.
- **없는 문서는 빈 문자열로 바꾸지 않는다**:
  - `resolve_context()`가 `KeyError`를 내고 **LLM 호출 전에 멈춘다.** endpoint에 붙일 때 404로 변환.
  - 4-1강 "읽지 못한 날짜를 추측하지 않는다"와 **같은 원칙**.
- **프롬프트는 구역을 나눈다**:
  - `지시문` → `[근거]` → `[질문]` → `[답변]` 순서. 복잡한 템플릿 클래스 없이 문자열 조합만.
  - 인증 키·비밀번호처럼 답변과 무관한 값은 프롬프트에 넣지 않는다.
- **QA 체크포인트**:
  - **"LLM 없이 계약부터"는 결함 격리 설계 선언이다.** 변수를 한 번에 하나씩만 늘리는 것 — 요청 검증이 틀렸는지, 문서 조회가 틀렸는지, 외부 서비스가 죽었는지를 **분리해서 확인 가능한 상태**로 만든 뒤에 다음 단계로 간다. 테스트 전략의 기본이 커리큘럼 구조 자체에 들어가 있다.
  - **필드 단위 검증과 필드 간 관계 검증은 다른 계층.** 각 필드는 `None`을 허용하지만 모델 전체 규칙은 "정확히 하나" — `Field`로는 표현할 수 없고 `model_validator`가 필요하다. 테스트 케이스도 4가지 조합(있음/있음, 있음/없음, 없음/있음, 없음/없음)을 **전부** 채워야 XOR 로직을 검증할 수 있다.
  - **`extra="forbid"`는 침묵형 버그 방어.** 없으면 오타 키가 **조용히 무시되고** 기본값으로 동작한다 — 클라이언트는 값을 보냈다고 믿는데 서버는 못 받은 상태. 상태 코드도 200이라 모니터링에도 안 잡힌다.
  - **`sources`는 장식이 아니라 추적성(traceability) 계약.** 교안이 *"사용하지 않은 문서 제목을 넣거나 빈 목록으로 고정하면 답변을 추적하기 어렵다"* 고 경고한다. RAG 평가에서 **답변이 실제로 그 근거에서 나왔는지**를 검증하려면 `sources`가 정확해야 한다 — 내 프로젝트의 환각 판정에 직결되는 지점.
  - **검증 오류와 `context`를 로그에 무조건 출력하지 말 것.** `context`에 개인정보나 내부 문서가 들어올 수 있다. 1-2강 개인정보 논의가 서버 로그에서 재등장.

### 7-2강 : 로컬/외부 LLM API 연동
- **핵심 개념**:
  - 세 호출 경로 — `mock`(고정 답변) / `external`(`{"answer": "..."}` JSON API) / `ollama`(로컬 모델, `message.content`)
  - **세 경로가 전부 같은 `QueryResponse(answer, sources, provider)`를 반환한다.** 클라이언트는 공급자별 원본 JSON을 해석하지 않는다.
  - 모델 호출 함수의 책임 3가지: 프롬프트를 서비스가 요구하는 JSON에 넣기 / HTTP 성공 확인 / JSON에서 답변 문자열 꺼내기
- **mock-first 실행 순서**:
  - `LLM_MODE=mock`으로 성공 확인 → 프롬프트 검사 → 그다음 `external` 전환
  - **Why?** → mock에서 실패하면 API Key나 인터넷을 볼 필요가 없다. **우리 서버 코드부터** 보면 된다.
  - mock이 제거하는 변수: 모델 버전 변화 / 생성 설정에 따른 문장 차이 / 인터넷·API Key / 사용량 비용
- **환경변수 3종**:
  - `LLM_MODE`(항상, 기본값 `mock`) / `LLM_API_URL`(external) / `LLM_API_KEY`(external)
  - `os.getenv("LLM_MODE", "mock").strip().lower()` — `" Mock "`도 `mock`으로 해석.
  - **외부 모드에서만 비밀값을 요구**하고, 없으면 호출 전에 `RuntimeError`.
- **오타 모드는 조용히 넘기지 않는다**:
  - 허용값은 `mock`/`external`/`ollama` 셋뿐. `exernal` 같은 오타를 **기본값으로 바꾸지 않고 503**으로 알린다.
  - **Why?** → 조용히 mock으로 돌면 **"실제 모델을 썼다"고 착각**하게 된다.
- **Ollama 변환**:
  - 요청 `{"model", "messages":[{"role","content"}], "stream": False}` → 응답 `data["message"]["content"]`
  - 외부 JSON 예제의 `prompt`/`answer`와 키 이름이 다르므로 **요청과 응답을 각각 변환**한다.
  - 답변 문장은 매 실행 달라진다. 성공 판정은 고정 문장 일치가 아니라 **실제 호출 여부 / 비어있지 않은 answer / sources / provider**로 한다.
- **오류 3종**:
  - `422` 요청 JSON 검증 실패 / `404` document_id 없음 / `502` 외부 LLM 호출 실패
  - `502`는 "우리 서버가 외부 서비스에서 정상 응답을 못 받았다"는 경계 표현.
- **QA 체크포인트**:
  - **공급자 3종이 같은 응답 계약을 반환한다 = 테스트 가능성 그 자체.** 같은 테스트 스위트를 mock으로 CI에서 돌리고, 실제 모델로 스모크 테스트할 수 있다. 계약이 같지 않으면 **모델을 바꿀 때마다 테스트를 새로 써야** 한다.
  - **`run_all.py`가 `os.environ["LLM_MODE"] = "mock"`을 명시적으로 고정하는 게 중요.** 수강생 컴퓨터에 이전 값이 남아 있어도 결과가 바뀌지 않게 하는 것 — **테스트 환경 독립성**. "내 PC에선 되는데" 문제의 정확한 예방책이고, CI와 로컬의 결과가 갈리는 원인 1순위가 이거다.
  - **MockTransport fixture가 `Authorization` 헤더를 `assert`한다.** 단순 가짜 응답이 아니라 **"내 호출 코드가 키를 헤더로 제대로 보내는가"를 검증하는 계약 테스트.** 실제 키 없이 인증 흐름을 검증하는 방법이다.
  - **"HTTP 200이면 answer가 있다"는 오해가 세 번째 등장** (2-1강, 3-2강, 여기). `isinstance(data, dict)` → `answer` 존재 → 자료형 → 공백 여부를 **네 단계로 검사**한다. HTTP 성공과 애플리케이션 데이터 성공은 다른 계층.
  - **오타 모드를 503으로 알리는 것 = fail loud 원칙.** 조용한 기본값 대체는 **"테스트가 통과했는데 실제로는 아무것도 검증 안 된"** 최악의 상황을 만든다. 모델 평가 파이프라인에서 이런 게 나면 결과 전체가 무효다.
  - **API Key의 3중 차단**: 소스 코드에 안 씀(환경변수) / 프롬프트에 안 넣음 / 우리 API 응답과 오류 문장에 안 섞음. 2-2강의 키 관리가 서버 쪽에서 확장된 형태.

## 8장. 비동기 처리와 안정적인 API 서비스 통합

### 8-1강 : 비동기 처리와 httpx.AsyncClient
- **핵심 개념**:
  - **비동기는 CPU를 빠르게 만드는 게 아니라 대기 시간을 겹치는 것.** 교안 표현: *"동시에 여러 CPU 명령을 계산한다"보다 "여러 대기 시간을 겹친다"로 이해하는 편이 정확합니다.*
  - 1초씩 걸리는 독립 요청 3건 → 동기는 약 3초, 비동기는 대기가 겹쳐 약 1초.
  - 잘 맞는 작업: 외부 REST API 여러 건 / LLM 응답 대기 / 비동기 DB 드라이버 / 파일·소켓 입출력
  - 안 맞는 작업: 이미지 변환, 수치 계산 등 **CPU를 오래 쓰는 작업**은 별도 전략 필요.
- **네 가지 도구만**:
  - `async def` — 코루틴 함수를 만든다. 호출만 하면 결과가 아니라 **코루틴 객체**가 나온다.
  - `await` — 결과가 올 때까지 기다리되 **이벤트 루프는 다른 코루틴을 진행**한다. 프로그램 전체가 멈추는 게 아니다.
  - `asyncio.gather()` — 여러 awaitable을 함께 실행
  - **한 개의 `AsyncClient`** — 연결 풀 재사용
- **gather 결과는 입력 순서**:
  - 3번이 가장 먼저 끝나도 입력이 `[1, 2, 3]`이면 결과도 같은 위치 순서.
  - 덕분에 **요청 ID와 결과 위치를 쉽게 연결**할 수 있다.
- **묶기 전에 의존 관계를 본다**:
  - `fetch_user()` → `fetch_orders(user["user_id"])` 처럼 **앞 결과가 뒤 요청에 필요하면 gather 불가.**
  - 무조건 묶지 말고 데이터 의존 관계를 먼저 확인.
- **Client 수명 관리 3문**:
  - Client를 어디서 만들었나 / 여러 요청이 같은 Client를 쓰나 / 사용 후 닫히나
  - 반복문 안에서 `async with httpx.AsyncClient()`를 매번 열면 **연결 풀 재사용 이점을 잃는다.**
- **QA 체크포인트**:
  - **`expected_output`이 `"AsyncClient 생성 횟수: 1"`을 검증한다.** 결과값뿐 아니라 **리소스 사용 패턴을 테스트로 고정**한 것 — 누가 리팩토링하면서 반복문 안으로 Client를 옮기면 기능은 멀쩡한데 이 테스트가 깨진다. **성능 회귀를 기능 테스트로 잡는** 좋은 예.
  - **fixture가 3번 요청을 가장 빨리 끝나게 설계한 것이 의도적.** `await asyncio.sleep((4 - item_id) * 0.01)` — 완료 순서와 결과 순서를 **일부러 어긋나게** 만들어 놓고 입력 순서 유지를 검증한다. 순서 보장을 테스트하려면 **순서가 뒤집힐 조건을 만들어야** 한다는 것.
  - **`gather` 하나가 실패하면 전체가 실패한다.** 부분 성공을 저장할지 전체를 실패시킬지는 **서비스 요구사항**이고, 테스트 케이스도 그 정책에 맞춰야 한다. "3건 중 1건 실패" 케이스를 안 만들면 이 동작은 프로덕션에서 처음 발견된다.
  - **무제한 동시 요청 금지.** 3건과 10만 건은 다르다 — 호출 제한 초과, 연결 수 증가, 메모리 증가. 부하 테스트 설계 시 **동시성 상한**이 있는지부터 확인해야 한다.
  - `response.json()`은 **일반 메서드라 `await`하지 않는다.** 모든 것에 `await`를 붙이는 게 아니라 코루틴인지 확인해야 한다.

### 8-2강 : Timeout / retry / rate limit / middleware 통합
- **핵심 개념**:
  - **네 가지만 구현한다** — 각 대기 단계 timeout 2초 / timeout·5xx에 최대 1회 재시도 / 외부 실패를 502로 / 방법·경로·상태만 한 줄 로그
  - 교안이 범위를 못 박은 이유: *"안정성 기능을 한꺼번에 많이 넣으면 오히려 실패 원인을 찾기 어려워집니다."*
  - 제외 항목 명시: 사용자별 rate limiter, 멱등성 키, HTTP 날짜 해석, 복잡한 로깅 설정.
- **timeout**:
  - `httpx.AsyncClient(timeout=2.0)` — 숫자 하나가 **연결/읽기/쓰기/연결 풀 각 단계**에 적용된다.
  - **"요청 전체가 2초 안에 끝난다"는 뜻이 아니다.** 각 대기 단계의 한도다.
  - `500`과 `timeout`은 다르다 — 전자는 **HTTP 응답을 받았고** 상태가 서버 오류, 후자는 **응답을 못 받고** 대기 한도를 넘음.
  - 너무 짧으면 정상 요청도 실패(정상 1.5초에 timeout 0.2초), 너무 길면 사용자가 오래 기다린다.
- **재시도 대상 선별**:
  | 상황 | 재시도? | 이유 |
  |---|---|---|
  | `TimeoutException` | ⭕ 1회 | 일시적일 수 있음 |
  | 5xx | ⭕ 1회 | 서버 측 일시 장애 |
  | 400 | ❌ | 요청 모양 문제 |
  | 401, 403 | ❌ | 같은 키를 다시 보내도 해결 안 됨 |
  | 404 | ❌ | 주소·자원 문제 |
  | **429** | ❌ | **호출량 제한 정책에 따른 거부** |
  - `range(2)` = 최초 시도 + 재시도, **총 2회 호출**. "재시도 1회"가 "총 1회 호출"이 아니다.
- **POST 재시도의 위험 (교안 경고)**:
  - 실제 생성 API는 **첫 요청을 처리하고도 응답만 늦었을 수** 있다 → 다시 보내면 **중복 처리나 중복 과금**.
  - 공급자의 재시도 정책과 **멱등성 지원 여부**를 먼저 확인해야 한다.
- **exponential backoff는 개념만**:
  - `base_delay * (2 ** attempt)` → 0.5초, 1초, 2초. 재시도가 한 번뿐이므로 이번엔 구현하지 않고 **"실패 직후 무한 반복하지 않는다"** 원칙만 적용.
- **예외 하나로 수렴**:
  - `class ExternalServiceError(RuntimeError)` — timeout, 반복된 5xx, 4xx, 잘못된 JSON, DNS·연결 실패를 **전부 이 하나로** 바꾼다.
  - endpoint에서 한 번에 `502`로 변환. `TimeoutException` 검사를 먼저 두는 이유는 **timeout도 HTTPX의 `RequestError` 계열**이기 때문.
- **최소 로그 middleware**:
  - 기록: `method` / `path` / `status_code` 세 개뿐
  - **기록하지 않음: 전체 question, 전체 context, Authorization 헤더, API Key**
  - `@app.middleware("http")` + `await call_next(request)` 구조.
- **QA 체크포인트**:
  - **오늘 가장 큰 배움 — 3-1강의 429와 8-2강의 429가 정반대 결론이다.**

    | | 3-1강 | 8-2강 |
    |---|---|---|
    | 요청 | 페이지네이션 **GET** | 생성 **POST** |
    | 부작용 | 없음 (멱등) | 있을 수 있음 (중복 처리·과금) |
    | 429 대응 | 대기 후 **같은 page 재시도** | **즉시 실패** |

    상태 코드만 보고 대응을 정하면 안 되고 **요청의 멱등성**을 함께 봐야 한다. 테스트 설계도 마찬가지 — "429 케이스"를 하나로 뭉치면 안 된다.
  - **fixture가 `[503, 200]` 순서로 응답하고 호출 횟수 2를 검증한다.** 결과만 보면 "성공"인데, **재시도가 실제로 일어났는지**는 호출 횟수를 세야만 알 수 있다. 재시도 로직을 통째로 지워도 두 번째 호출이 200이면 결과는 같다 — **동작을 검증하려면 부수 효과를 관찰해야 한다.**
  - **"재시도 1회 = 총 호출 2회"는 전형적인 off-by-one 오해.** 외부 API 요금제나 호출 한도 계산에서 2배 차이가 나므로, 문서와 코드가 같은 정의를 쓰는지 확인해야 한다.
  - **로그 필드 최소화는 보안 테스트 항목이다.** 로그는 디버깅에 필요하지만 **민감 정보 노출 경로**가 된다. "오류 메시지에 내부 URL이나 비밀값이 섞이지 않는가"를 점검 항목으로 넣어야 한다 — 특히 `str(error)`를 그대로 `detail`에 넣는 코드는 위험할 수 있다.
  - **`ExternalServiceError` 하나로 수렴시킨 설계**가 테스트를 단순하게 만든다. 외부 실패 케이스마다 다른 예외를 잡을 필요 없이 **경계에서 한 번만** 처리한다. 2-2강 "실패 계층 5단"에서 배운 분리와 반대 방향처럼 보이지만, **진단은 세분화하고 처리는 수렴시키는 것**이 요점.
  - **timeout 값은 측정 후 결정.** "생략하지 않는다 / 수업 고정값과 운영값을 구분한다 / 정상 지연을 측정한 뒤 조정한다" — 성능 기준선(baseline) 없이 임계값을 정하지 말라는 얘기고, 이건 QA가 제공해야 할 데이터다.
