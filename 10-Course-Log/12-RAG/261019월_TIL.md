## 💡 오늘의 학습 총평

- **오늘 나온 약어 정리 (처음 보는 게 많아서 먼저 풀어 둠)**

  | 약어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | RAG | Retrieval-Augmented Generation (검색 증강 생성) | 질문마다 관련 문서를 검색해 근거로 넣고 답하게 하는 방식 |
  | BM25 | Best Matching 25 | 질문 단어가 청크에 몇 번, 얼마나 드문 단어로 나오는지로 점수를 매기는 검색 방식 |
  | TF / IDF | Term Frequency / Inverse Document Frequency | 한 문서 안 등장 횟수 / 전체에서 드문 단어일수록 큰 가중치 |
  | CAG | Cache-Augmented Generation (캐시 증강 생성) | 공통 자료의 계산 상태를 저장해 두고 반복 질문에 재사용하는 접근 |
  | KV cache | Key-Value cache | 모델이 앞부분을 계산한 중간 결과를 저장한 것 |
  | Top-k | — | 점수 상위 k개 결과 |
  | OCR | Optical Character Recognition (광학 문자 인식) | 이미지 속 글자를 읽어 내는 기술 |
  | NFC | Normalization Form C (유니코드 정규화 형식 C) | 같은 한글이 다른 코드로 저장된 걸 하나로 맞추는 규칙 |
  | JSONL | JSON Lines | 한 줄에 JSON 객체 하나씩 저장하는 파일 형식 |
  | sha256 | Secure Hash Algorithm 256-bit | 내용이 1글자만 바뀌어도 완전히 다른 값이 나오는 지문(해시) 계산 방식 |

- **핵심 통찰: RAG는 "모델을 바꾸는 게" 아니라 "입력을 바꾸는 것"이다**
  - LLM만으로는 우리 회사 규정에 답하기 어렵다. 학습 시점 이후를 모르고(Knowledge Cutoff), 사내 데이터를 본 적 없고(Private Data), 모르면 지어낼 수 있다(Hallucination).
  - RAG는 질문할 때마다 최신·사내 문서를 **검색해 근거로 넣고**, 근거가 없으면 "확인 불가"로 보류한다. **모델을 다시 학습시키지 않는다** — 문서만 갱신하면 바로 반영되고 출처도 보여 줄 수 있다.
  - LangChain 6-3강과 2차 프로젝트 Review에서 사람이 필요한 문서를 골라 프롬프트에 붙였던 일을, 이제 **검색기(Retriever)가 대신 맡는다.**

- **두 번째 통찰: 검색 품질은 검색 알고리즘보다 "앞에서" 정해진다**
  - 오전은 깔끔한 `documents.json`을 받아 Query 쪽(검색 → Context → 답변)을 한 바퀴 돌렸고, 오후는 그 `documents.json`을 원본 파일(TXT · HTML · PDF)에서 직접 만드는 Indexing 앞단을 다뤘다.

    | 오전 (Query 쪽) | 오후 (Indexing 앞단) |
    |---|---|
    | 1-1 현행 문서만 고르기, 검색 실패 vs 근거 부족 | 2-1 형식이 달라도 같은 본문으로 읽기 |
    | 1-2 역색인, OR 검색, 색인 갱신 | 2-2 버전·상태·출처·본문 해시 |
    | 1-3 80/20 청킹, BM25 Top-3, Context 예산, 출처 라벨 | 2-3 공백·틀 문구·중복·빈 본문 정제 |
    | 1-4 토큰 예산, 캐시 키, 비교 후보 고르기 | 2-4 JSONL 저장, 줄 번호 검수 |

  - 오후 오리엔테이션의 문장 — 본문이 깨지거나 구버전이 섞이면 BM25도 임베딩도 그대로 틀린다. **입력 데이터 품질이 시스템 품질의 상한선**이라는 건 QA에서 테스트 데이터 품질이 테스트 결과의 신뢰도를 정하는 것과 같다.

- **세 번째 통찰: "검색 성공"과 "답변 가능"은 다른 문제다**

  | 검색어 | 검색 | 근거 | 의미 |
  |---|---|---|---|
  | 숙박 비용 | ✓ | ✓ | travel에 같은 표현과 정산 규정 |
  | 호텔비 | ✗ | 있음 | 답은 travel에 있는데 **글자가 달라서** 못 찾음 → 검색 표현 문제 |
  | 개인 취미 | ✓ | ✗ | education은 찾지만 **지원 여부가 규정에 없음** → 근거 부족 |

  - 같은 "답을 못 함"이라도 원인이 다르면 고칠 곳이 다르다. 검색 실패는 검색기를, 근거 부족은 문서나 보류 정책을 봐야 한다. 결함 리포트에서 증상이 같아도 원인 분류를 먼저 하는 것과 같다.

- **네 번째 통찰: 지난 과목의 원칙이 RAG에서 또 나왔다**

  | 지난 과목 | 오늘 (RAG) |
  |---|---|
  | LangChain 6-2강 — Retriever 계약 `str → list[Document]`, 0건도 유효 | 1-1 `find_policy` → 빈 목록 `[]`도 정상 결과 |
  | LangChain 6-3강 — `[근거: doc-003]`이 실제 검색 결과에 있는지 대조 | 1-3 `validate_answer` — S99 같은 가짜 출처 차단 |
  | LangChain 6-1강 — `Document(page_content, metadata)`, metadata 키 일관성 | 2-1 로더가 달라도 같은 `Document` 모양 |
  | 2차 Review 02 — 정규화는 표기 차이만 줄인다 | 2-3 NFC·공백 정규화, 뜻은 바꾸지 않음 |
  | 2차 Review 08 — 실패 행 삭제 금지 | 2-3 제외한 것은 항상 기록 (`excluded` · `rejected` · `removed`) |
  | 10/2 Python 실습 — 출고 3일 ≠ 도착 3일 | 1-1 "12만원"만으로는 부족, 단위(1박당)·조건(영수증·사전 승인)까지 |

- **향후 계획 및 다짐**

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. "답을 못 함"의 원인 분류 — 증상이 같아도 원인이 다르다

| 원인 | 예 | 고칠 곳 | 근거 교안 |
|---|---|---|---|
| 검색 표현 문제 | "호텔비" → 0건 (본문은 "숙박 비용") | 검색기 (동의어, 형태소 분석, 의미 검색) | 1-1 |
| 토큰화 문제 | "영수증" → 0건 (색인에는 "영수증을") | 토큰화 규칙 (조사 분리) | 1-2 |
| 근거 부족 | "개인 취미" → education은 찾지만 지원 여부 없음 | 보류 정책 ("확인 불가") | 1-1 |
| 예산 초과로 Context 누락 | 예산 110자 → 식비 근거 빠짐 | Context 예산, 청크 크기 | 1-3 |
| 청크 경계 문제 | "서면 / 승인"이 두 청크로 갈라짐 | 청킹 전략 (3장) | 1-3 |
| 색인 미갱신 | 문서를 추가했는데 "재택근무는" → 0건 | Indexing 다시 실행 | 1-2 |
| 원본 로딩 문제 | PDF 줄바꿈·꼬리말 섞임, 스캔 PDF는 본문 없음 | 로더·정제 규칙 | 2-1, 2-3 |

→ RAG 결과가 틀렸을 때 **생성 모델부터 의심하지 않는다.** 로딩 → 정제 → 청킹 → 색인 → 검색 → Context 순서로 어느 단계에서 근거가 사라졌는지 먼저 찾는다. 2차 Review의 "생성 문장보다 분류 결과부터 확인"과 같은 디버깅 순서다.

### 2. 버전 관리 — 최신 문서를 고르는 건 모델이 아니라 우리다

- 같은 규정의 구버전(travel-old, 1박당 8만원)과 현행(travel, 12만원)을 **둘 다 모델에 넘기면 어느 쪽을 따를지 헷갈린다.** 모델에 넘기기 전에 적용할 버전을 먼저 정한다 (1-1).
- 판단 기준은 **`status`** 다. 발행일(`published_at`) 하나만 보고 최신이라고 판단하지 않는다 (2-2).
- 구버전은 지우지 않고 `status=retired`로 검색에서만 뺀다. 감사·비교용으로 원본은 남긴다 (2-3).
- `retrieve` 안에서 `status == "current"`로 **먼저 거른 뒤** 점수를 매긴다 (1-3).

### 3. 출처 추적 — 답변에서 원문까지 끊기지 않게

```
답변 → [S1] → chunk_id → document_id(travel) → title(v2) → source_url
```

| 장치 | 막는 것 | 근거 교안 |
|---|---|---|
| Context에 실제로 넣은 근거만 S1, S2 라벨 부여 | 검색은 됐지만 Context에서 빠진 문서를 출처로 연결 | 1-3 |
| `validate_answer` — citations가 실제 출처 목록의 부분집합인지 | S99 같은 가짜 출처 | 1-3 |
| answered는 출처 1개 이상, insufficient는 빈 출처 | 근거 없는 답변을 확인한 답변처럼 표시 | 1-3 |
| `source_url`은 본문이 아니라 metadata에 | URL이 검색 점수를 흐림 | 2-2 |
| `chunk_id = 문서ID:본문해시:80:20:시작위치` | 원문·설정이 바뀌었는데 같은 ID로 착각 | 1-3 |

→ 다만 **검사를 통과해도 답변 문장이 원문 뜻을 정확히 옮겼는지는 사람이 원문과 대조**해야 한다. 2차 Review의 "형식 통과 ≠ 내용 통과"와 같다.

### 4. 예산 — 문자 수와 토큰 수는 다르다

| 단계 | 기준 | 주의 | 근거 교안 |
|---|---|---|---|
| 청킹 80/20 | 문자 수 | 임베딩 모델 토큰 한도와 별개 | 1-3 |
| Context 예산 260 | 문자 수 (제목·라벨·구분 줄바꿈 2자 포함) | 실제 서비스는 토큰으로 센다 | 1-3 |
| 문서 토큰 예산 | 토큰 수 = 한도 − 지시문 − 이력 − 출력 예약 − 여유 | 1,434문자 ≠ 1,434토큰. 생성 모델 Tokenizer로 센다 | 1-4 |

- 8192 − 500 − 500 − 1000 − 192 = **6000**. 출력 예약을 3000으로 늘리면 문서 예산은 **4000**으로 줄어든다. 답변을 길게 받으려 할수록 근거 공간이 줄어드는 trade-off.
- **Top-k ≠ 실제 근거 수.** k=3은 청크 3개이고 문서는 2개일 수 있다. k=2로 요청해도 점수가 있는 후보가 1개면 출처는 1개다. 예산이 작으면 검색된 근거도 Context에서 빠진다.

### 5. 정제 원칙 — 덜어내기만 하고, 고쳐 쓰지 않고, 기록한다

| 하는 것 | 하지 않는 것 |
|---|---|
| 연속 공백·탭을 한 칸으로, NFC 정규화 | 부정어·금액·조건 수정 ("정산되지 않습니다" → "정산됩니다"면 규정이 반대) |
| 메뉴·제목 줄·꼬리말 같은 틀 문구(Boilerplate) 제외 | 문장을 임의로 요약 |
| 버전·범주·본문 해시가 **모두** 같은 문서만 중복 제거 | 버전이 다른 문서 삭제 |
| strip 후 빈 본문 제외 | 제외한 것을 기록 없이 버리기 |

- 쓸모 있는 틀 정보는 metadata로 옮긴다 (제목 → `title`, 날짜 → `published_at`). 본문에서 빼도 정보는 잃지 않는다.
- **제외 기록**(`excluded`, `rejected`, `removed`)이 있어야 필요한 규정을 실수로 지우지 않았는지 사람이 다시 확인할 수 있다. 정제 단계 자체가 검증 가능해야 한다.

### 6. 실패를 조용히 넘기지 않는다 (fail loud)

| 지점 | 동작 | 근거 교안 |
|---|---|---|
| 빈 검색어 | `ValueError("검색어를 입력하세요.")` — 빈 문자열은 모든 본문에 포함돼 전체가 나오기 때문 | 1-1 |
| 빈 ID·중복 ID·빈 본문·출처 필드 누락 | `read_documents`가 색인 전에 `ValueError` | 1-3 |
| 근거 없음 | 모델을 **부르지 않고** 바로 보류 (`insufficient`) | 1-3 |
| JSONL 깨진 줄 | 조용히 건너뛰지 않고 **"3행: …"** 줄 번호와 함께 멈춤 | 2-4 |
| `overlap >= size` | `ValueError` — 청킹이 끝나지 않는 설정 차단 | 1-3 |

→ 빈 검색어 사례가 특히 좋다. 오류가 안 나고 **전체 문서가 나오는 게 더 위험한** 경우다. 조용히 틀리는 동작을 입력 검증으로 막는다.

### 7. 결정성 — 같은 입력이면 같은 결과

- BM25 결과는 **점수 큰 순서, 동점은 chunk_id 순서**로 고정된다. 결과 비교·회귀 테스트가 가능하다.
- `chunk_id`에 본문 해시와 청킹 설정을 포함 → 원문이나 설정이 바뀌면 ID도 바뀐다. "같은 ID인데 내용이 다른" 상태를 막는다.
- 캐시 키(sha256 앞 12자리)는 model · scope · text가 같으면 같고, **모델이나 접근 범위가 다르면 달라진다** → 다른 권한의 캐시를 섞지 않는다.
- Ollama 생성은 `temperature=0`, JSON 스키마 지정. 그래도 응답을 `validate_answer`로 **다시 검사**한다. 모델의 형식 준수만 믿지 않는다.

### 8. 방식 선택은 측정으로 — 규칙은 비교 순서일 뿐

```
문서가 예산을 넘나? ── 예 → RAG 또는 문서 범위 축소
        │ 아니요
반복 요청 + 캐시 지원? ── 예 → 전체 입력 + prefix cache 비교
        │ 아니요
전체 입력부터 비교
```

- 예산 초과를 **가장 먼저** 본다. 캐시를 지원해도 입력이 안 들어가면 소용없다.
- 이 규칙은 **어떤 후보부터 비교할지**를 정하는 연습이다. 실제 채택은 같은 질문으로 **정확도와 처리 시간을 측정**해서 정한다.
- 캐시 키를 만든 것 ≠ 실제 캐시. 이 코드는 KV 텐서를 저장하지 않고, scope도 권한 검사가 아니며, 키가 같다고 캐시 적중·속도 향상이 검증된 것도 아니다.

### 9. Claude가 짚어준 확인 포인트

**① 1-3 코드는 metadata를 얕게 복사하는데, 2-2는 깊은 복사가 필요하다고 가르친다**
- Claude가 `rag_ch01_03/rag_core.py`의 `chunk_documents`를 읽어 보니 청크마다 `"metadata": dict(doc["metadata"])` — **얕은 복사**를 쓴다. 코드 주석도 "중첩 객체가 있다면 그 객체까지 분리되는 복사는 아니에요"라고 적어 두었다.
- 오후 2-2강은 정확히 이 지점에서 "`dict(meta)`는 바깥만 새로 만들어서 한 청크의 수정이 원문으로 번진다 → `deepcopy`"를 가르친다.
- 지금 `documents.json`의 metadata는 중첩 없이 평평해서 문제가 없지만, 3장에서 청크마다 `section` 같은 **중첩 값을 붙이기 시작하면 잠재 결함**이 된다. 오전 코드를 그대로 가져다 쓰면 터질 수 있는 부분이라, 3장 코드에서 어떤 복사 방식을 쓰는지 확인할 것.

**② 본문 해시만으로 재색인을 판단하면 "폐기" 상태 변경을 놓친다**
- 2-2강: 해시는 **본문만으로** 계산하므로 `status`만 바뀌면 해시는 그대로다.
- 그런데 같은 강의에서 해시를 "다시 색인할 대상 찾기"에 쓴다고 설명한다. 규정이 `current → retired`로 바뀌었는데 본문은 그대로라면, **해시 비교로는 "변경 없음"으로 판단돼 재색인되지 않을 수 있다.**
- 오전 `retrieve`는 검색할 때마다 `status`를 다시 읽어 거르므로 이 실습에서는 괜찮다. 하지만 실무에서 색인에 status를 함께 저장해 두는 구조라면, 폐기된 규정이 **현행처럼 계속 검색되는** 결함이 생긴다. 재색인 판단 기준에 **본문 해시 + metadata 변경**을 함께 봐야 한다.

**③ 검색 결과 Top-3 안에 질문과 덜 관련된 식비 청크가 2개 들어왔다**
- "출장 숙박 비용 한도는?" → travel 10.456점, meal 2.578점, meal 2.136점. 식비 규정은 "출장", "한도는" 같은 공통 단어 때문에 점수를 받았다.
- 예산 260이면 식비 근거도 S2로 Context에 들어간다. 이번 답변은 S1만 인용했지만, **관련 없는 근거가 Context에 섞이면 모델이 엉뚱한 금액을 가져올 위험**이 생긴다. Top-k를 크게 잡는 게 항상 좋은 게 아니다. 3장 이후 검색 평가에서 "관련 없는 근거 비율"도 볼 지표로 메모.

## 1장. RAG 이해와 아키텍처 (오전)

### 1-1 : RAG가 필요한 이유와 적용 조건
- **핵심 개념**:
  - LLM만으로 부족한 세 가지:
    | 한계 | 뜻 | 예 |
    |---|---|---|
    | Knowledge Cutoff (지식 기준 시점) | 학습 시점 이후를 모름 | 지난달 바뀐 규정도 예전 기준으로 답함 |
    | Private Data (비공개 데이터) | 사내 데이터를 본 적 없음 | 공개되지 않은 규정은 알 수 없음 |
    | Hallucination (환각) | 모르면 지어냄 | 근거 없는 금액을 사실처럼 말함 |
  - RAG 흐름: 질문 → **검색**(현행 규정에서) → **Context 구성**(근거 + 문서 ID) → **답변 생성**(근거로만). 검색하고 문서를 넣어도 **모델 가중치는 바뀌지 않는다.**
  - **모든 질문에 RAG가 정답은 아니다.** 먼저 "이 질문에 답하려면 어떤 자료가 필요한가?"부터 묻는다.
    | 요청 | 필요한 자료 | 시작할 방식 |
    |---|---|---|
    | 회사 출장 숙박 한도는? | 현행 출장 규정 | 규정 검색 후 답변 생성 (RAG) |
    | 지금 내 교육비 잔액은? | 개인별 승인·사용 내역 | **인증된 업무 API 조회** |
    | 첨부한 한 페이지 요약해 줘 | 이미 전달된 문서 | 문서를 직접 입력 |
  - **최신 버전 고르기**: 12개 문서 중 `status == "current"` 10개만 검색 후보. travel(12만원)과 travel-old(8만원)를 모델이 고르게 하지 않는다.
  - `term in d["content"]` — 글자가 **그대로** 들어 있는지만 본다. 뜻이 같아도 글자가 다르면 못 찾는다.
  - 찾은 문서와 질문을 **하나의 입력(Prompt)** 으로 묶는다. 자료형이 `list[dict]`(문서 목록) → `str`(모델이 읽는 한 문자열)로 바뀐다.
  - **좋은 답변에는 금액과 조건이 함께**: 1박당 12만원(기본 한도·단위) + 숙박 영수증(증빙) + 예약 전 서면 승인(한도 초과 조건). "12만원"만 전달하면 실제로 정산을 못 받는다.
- **퀴즈 1-1 `find_policy`** (교안 정답): 빈 검색어면 `ValueError` → `current_only`에 따라 `current` 또는 `documents` → `term in content`인 문서 목록. "숙박 비용" 현행만 `['travel']`, 구버전 포함 `['travel', 'travel-old']`, "호텔비" `[]`, "개인 취미" `['education']`.
- **QA 체크포인트**:
  - **빈 검색어 검사가 핵심 경계값이다.** 빈 문자열은 모든 본문에 포함돼서 검사 없이 돌리면 **전체 문서가 나온다.** 오류보다 무서운 "조용히 전부 통과"를 입력 검증으로 막는다.
  - **"호텔비 0건"과 "개인 취미 1건"을 같은 실패로 보면 안 된다.** 하나는 검색 표현 문제, 하나는 근거 부족. 원인별로 고칠 곳이 다르다.
  - **답변 검증 기준이 "금액 하나"가 아니라 "금액 + 단위 + 조건"** 이다. 10/2 실습의 "출고 3일 ≠ 도착 3일"처럼, 핵심 숫자만 맞고 조건이 빠지면 사용자에게는 틀린 답이다.
  - **RAG가 아닌 방식이 맞는 질문**(개인 잔액 → 인증된 API)을 구분하는 것도 요구사항 분석이다. 개인 데이터를 문서 검색으로 해결하려 하면 권한 문제가 생긴다.

### 1-2 : Indexing과 Query 파이프라인
- **핵심 개념**:
  - 1-1 방식은 질문마다 문서 10개 전부를 훑는다. 질문이 늘수록 같은 일을 반복한다.
  - **Indexing**(문서를 읽을 때 한 번) → **역색인**(단어 → 문서 ID) → **Query**(색인에서 바로 찾기)
  - `build_index` — `re.findall(r"[가-힣a-zA-Z0-9]+", content)`로 단어를 나누고, 단어마다 문서 ID를 `set`에 모은다. 같은 문서에 여러 번 나와도 ID는 한 번만.
    | 단어 | 문서 ID |
    |---|---|
    | 숙박 | {travel} |
    | 영수증을 | {education, travel} |
    | 재택근무는 | {remote} |
  - **"영수증"으로 찾으면 0건** — 조사가 붙은 "영수증을"이 다른 단어로 저장됐다.
  - **OR 검색** — 단어별 ID의 **합집합**. 한 단어만 맞아도 후보라서, 점수·순위가 없어 education도 함께 나온다 → 1-3에서 BM25로 순위를 매긴다.
  - `by_id = {d["document_id"]: d for d in current}` — 색인은 ID만 주므로 ID로 원문(제목·본문)을 다시 찾는다.
  - **문서를 추가해도 색인은 저절로 바뀌지 않는다.** remote를 빼고 만든 색인에서 "재택근무는" → `[]`, 다시 만들면 `['remote']`. 원문이 바뀌면 Indexing을 다시 실행한다.
- **퀴즈 1-2 `search_all_words`** (교안 정답, AND 검색): 단어가 없으면 `[]` → 첫 단어의 문서 집합을 **복사**해서 시작 → 나머지 단어마다 `intersection_update`(교집합). "숙박 교육비는" OR `['education', 'travel']` / AND `[]`, "숙박 영수증을" OR `['education', 'travel']` / AND `['travel']`.
- **QA 체크포인트**:
  - **첫 집합을 복사하지 않으면 색인 원본이 바뀐다.** `index.get(...)`이 돌려주는 set을 그대로 `intersection_update`하면 저장된 색인 자체가 줄어든다. 검색 한 번이 다음 검색 결과를 망가뜨리는 **상태 오염 결함**. 퀴즈가 "검색 후에도 index는 그대로여야" 를 통과 조건으로 둔 이유.
  - **조사 문제("영수증" vs "영수증을")** — 한국어 RAG에서 형태소 분석 없이 공백·기호로만 나누면 생기는 대표 결함. 테스트 케이스에 **조사를 바꾼 질문**을 넣어야 한다.
  - **색인 갱신 누락은 에러 없이 "검색 결과 없음"으로만 나타난다.** 문서를 추가·수정한 뒤에는 그 문서가 실제로 검색되는지 확인하는 단계가 필요하다.
  - OR(합집합) vs AND(교집합) — OR은 놓치는 건 적지만 엉뚱한 후보가 늘고, AND는 정확하지만 놓치기 쉽다. 테스트 설계의 재현율·정밀도 trade-off와 같은 구조.

### 1-3 : 2-Step RAG 기준선과 실습 환경
- **핵심 개념**:
  - **2-Step = 검색 한 번, 생성 한 번.** `rag_core.py`의 다섯 함수:
    | 함수 | 하는 일 |
    |---|---|
    | `read_documents` | ID·본문·출처 필드를 검사하며 읽기 (12개) |
    | `chunk_documents` | 80자 청크, 20자 겹침 (28개) |
    | `retrieve` | 현행 청크만 BM25 Top-3 |
    | `build_context` | 문자 예산 260 안에서 S1·S2 라벨 |
    | `generate_ollama` | (선택) 답변 생성 + 출처 검사 |
  - **80/20 청킹**: travel 본문 148자 → 시작 위치가 80 − 20 = 60자씩 이동 → `[0:80]`, `[60:140]`, `[120:148]`. 첫 청크가 "서면"에서 끝나 **"서면 승인" 조건이 두 청크로 나뉜다** → 그래서 겹침을 둔다. 다만 고정 길이는 문장 경계를 보지 않는다(3장에서 비교).
  - `chunk_id = 문서ID:본문해시:80:20:시작위치` — 원문이나 설정이 바뀌면 ID도 바뀐다.
  - **BM25** — 질문 단어가 청크에 몇 번 나오는지(TF), 얼마나 드문 단어인지(IDF), 청크 길이 보정. 식에서 k1=1.5, b=0.75. 0점 후보는 제외.
  - **Top-3 = 청크 3개이지 문서 3개가 아니다.** "출장 숙박 비용 한도는?" → travel 10.456, meal 2.578, meal 2.136 → 문서는 travel·meal 2개.
  - **Context 예산** — 들어가는 근거만 라벨을 받는다. 제목·라벨·구분 줄바꿈 2자도 예산에 포함. 예산 110이면 S1 travel만, 260이면 S1 travel + S2 meal.
  - **선택 실습 (Ollama)**: 근거가 없으면 모델 호출 없이 바로 보류. 있으면 JSON 스키마(`status` · `answer` · `citations`)로 요청 → `validate_answer`로 가짜 출처(S99) 차단, answered는 출처 필수. 결과 예: "국내 출장 숙박 비용 한도는 1박당 12만원입니다. (S1)", citations `['S1']`.
    ```powershell
    $env:OLLAMA_MODEL = "gemma3:4b-it-q4_K_M"
    cd ch01\rag_ch01_03
    uv run generate_answer.py
    ```
- **퀴즈 1-3 `prepare_input`** (교안 정답): `retrieve(question, chunks, method="bm25", k=k)` → `build_context(rows, max_chars=260)` → `{"question", "context", "sources"}`. "재택근무는 주 몇 회인가요?" → 출처 `[('S1', 'remote')]` (k=2지만 점수가 있는 후보는 1개), Context에 "주 2회"와 "사전 일정 협의"가 함께 들어감.
- **QA 체크포인트**:
  - **k와 max_chars를 구분한다.** k는 검색 후보 수, max_chars는 그 후보를 Context에 넣는 예산. 검색된 후보가 전부 모델 입력에 들어간다고 가정하지 않는다.
  - **출처는 Context에 실제로 넣은 근거만** — 검색은 됐지만 예산 때문에 빠진 문서를 출처로 표시하면, 사용자는 모델이 보지도 않은 문서를 근거로 믿게 된다.
  - **청크 경계에서 조건이 잘리는 결함** — "서면 / 승인", 퀴즈 1-3에서 "협업 시간 문장이 끊긴 점"도 같은 유형. 조건문이 경계에 걸리는 문서를 테스트 케이스로 모아 둘 것.
  - **근거가 없으면 모델을 부르지 않는다** — 비용 절감이자 환각 방지. LangChain 10-2강의 "검색 0건이면 모델 호출 0회"와 같은 원칙.
  - **`validate_answer`는 형식과 출처 ID만 검사한다** — 답변 문장이 원문 뜻을 정확히 옮겼는지는 사람이 원문과 대조. 코드 주석에도 명시돼 있다.
  - **`read_documents`가 색인 전에 데이터 검사** — 빈 ID·중복 ID·빈 본문·출처 필드 누락을 막는다. 잘못된 데이터가 색인에 들어가면 이후 모든 검색이 오염된다.

### 1-4 : RAG와 Long Context, CAG 선택 기준
- **핵심 개념**:
  - **규정이 10개뿐이면 그냥 다 넣으면?** 전체 입력 1,434문자 vs 검색 입력 157문자.
    | | 문서 전체 입력 | 검색 후 입력 |
    |---|---|---|
    | 장점 | 검색 단계에서 자료를 놓치지 않음 | 질문과 관련된 자료로 입력을 줄임 |
    | 확인할 점 | 많은 자료에서 필요한 조건을 찾는지 | 검색이 필요한 문서를 빠뜨리지 않는지 |
  - **문서 토큰 예산** = 한도 − 지시문 − 이력 − 출력 예약 − 여유. 8192 − 500 − 500 − 1000 − 192 = 6000. 출력 예약 3000이면 4000. **1,434문자를 1,434토큰으로 계산하면 안 된다** — 생성 모델의 Tokenizer로 센다.
  - **세 용어는 같은 기준으로 나눈 선택지가 아니다.**
    | 용어 | 무엇인가 | 예 |
    |---|---|---|
    | RAG | 근거를 **가져오는 방식** | 숙박 규정을 검색해 답변에 넣음 |
    | Long Context | 긴 입력을 **처리하는 능력** | 규정 전체나 더 많은 검색 결과를 넣음 |
    | CAG | 공통 자료의 계산 상태를 **재사용하는 접근** | 같은 규정으로 반복 질문 시 공통 앞부분 계산 재사용 |
    RAG + Long Context는 함께 쓸 수 있다. 전체를 넣을 수 있다고 검색이 항상 불필요해지는 건 아니다.
  - **캐시 키** — model · scope · text를 sha256으로 해시해 앞 12자리. 같은 입력이면 같은 키, 범위·모델이 바뀌면 다른 키 → 다른 권한의 캐시를 섞지 않는다.
- **퀴즈 1-4 `choose_input`** (교안 정답): `document_tokens > available`이면 "RAG 또는 문서 범위 축소" → `repeated and cache_supported`면 "전체 입력 + prefix cache 비교" → 나머지는 "전체 입력부터 비교". (3000, 6000, O, O) → prefix cache 비교 / (900000, 6000, O, O) → RAG 또는 축소 / (3000, 6000, X, X) → 전체 입력부터.
- **QA 체크포인트**:
  - **조건 검사 순서가 결과를 바꾼다** — 예산 초과를 먼저 봐야 한다. 캐시를 지원해도 입력이 안 들어가면 캐시 비교 자체가 무의미하다. 2차 Review의 "길이 검사가 공백 제거보다 먼저"처럼, 명세에 검사 순서가 있어야 기대 결과를 정할 수 있다.
  - **"키 생성 ≠ 캐시 적중 ≠ 속도 향상"** — 세 단계를 각각 따로 검증해야 한다. LangChain 8-2강의 "객체 생성 ≠ 인증 ≠ 조회 가능"과 같은 구조.
  - **scope는 권한 검사가 아니다** — 키를 나누는 값일 뿐. 보안 기능으로 오해하면 안 된다 (LangChain 6-2의 "source filter는 권한 검사가 아니다"와 같음).
  - **방식 선택 규칙은 비교 후보를 고르는 것까지** — 실제 채택은 같은 질문으로 정확도와 처리 시간을 측정해서 정한다. 러브코드에서 모델·방식을 비교할 때도 같은 원칙.

## 2장. 문서 로딩과 데이터 품질 (오후)

### 2-1 : 문서 로딩과 Document 구조
- **핵심 개념**:
  - 같은 규정이 세 가지 파일 형식으로 온다.
    | 파일 | 읽는 방법 | 결과 |
    |---|---|---|
    | travel.txt | `read_text()` | 본문만 있어 그대로 → 기준과 **같음** |
    | travel.html | `HTMLParser`로 `<p>` 안의 글만 | 메뉴(`<nav>`)·제목(`<h1>`)·꼬리말(`<footer>`) 제외 → 기준과 **같음** |
    | travel.pdf | `pypdf`로 텍스트 계층 추출 | 줄바꿈·제목·꼬리말이 섞여 나옴 |
  - `documents.json`의 travel은 **비교 기준**, `raw/` 폴더 파일이 **실제 로더 입력**.
  - **PDF: 줄 끝 ≠ 문장 끝** — "정산할 수 / 있습니다"처럼 문장 중간에서 끊긴다. 줄 0 = 제목, 줄 1~3 = 본문, 줄 4 = 꼬리말("교육용 가상 규정 · 2026-08-01 · 1").
  - **OCR이 아니다** — 스캔 이미지 PDF는 같은 방법으로 본문이 안 나온다.
  - `lines[1:-1]`로 제목·꼬리말을 떼고 공백으로 이어 붙이면 기준 본문과 같다(`True`). 단, **이 PDF 구조를 확인한 뒤 쓰는 규칙**이다. 제목이 두 줄인 PDF에 그대로 쓰면 제목 일부가 본문에 섞인다.
  - `<p>`만 고르는 규칙도 이 예제용. 실제 웹 문서는 본문 영역을 찾는 규칙을 파일 구조를 보고 따로 정한다.
  - **`Document(page_content, metadata)`** — 로더가 달라도 같은 모양으로. `page_content`는 검색할 본문, `metadata`는 title · category · status · version · published_at · source_url + document_id + format.
- **퀴즈 2-1** (교안 정답): `body_lines = lines[1:-1]` → `pdf_body = " ".join(body_lines)` → 첫 문장 `split(". ")[0]`, 마지막 문장 `[-1]`. "원문과 같은 본문: True".
- **QA 체크포인트**:
  - **같은 내용, 다른 형식 = 동등성 테스트.** TXT·HTML·PDF 결과를 기준 본문과 글자 단위로 비교하는 건, 같은 기능을 여러 플랫폼에서 돌려 결과가 같은지 보는 **크로스 플랫폼 검증**과 같은 구조다.
  - **`False`가 나오면 확인 순서**: 첫 문장 → 마지막 문장 → 공백 → 줄 순서. 차이가 어디서 나는지 좁혀 가는 디버깅 절차가 교안에 들어 있다.
  - **`lines[1:-1]` 같은 "이 파일에만 맞는 규칙"을 일반 규칙으로 쓰면 안 된다.** 다른 배치의 PDF가 들어오면 조용히 본문이 잘리거나 제목이 섞인다. 로더 규칙은 **어떤 입력에 대해 확인한 규칙인지**를 기록해 둬야 한다.
  - **스캔 PDF는 빈 본문** — 에러 없이 빈 문자열이 나온다. 2-3의 빈 본문 검사로 이어지는 이유.

### 2-2 : 출처 추적을 위한 Metadata 설계
- **핵심 개념**:
  - 같은 제목, 다른 버전을 구분하는 필드:
    | document_id | version | published_at | status | source_url |
    |---|---|---|---|---|
    | travel | v2 | 2026-08-01 | current | …/rag40/travel |
    | travel-old | v1 | 2025-01-01 | retired | …/rag40/travel-old |
  - Metadata의 세 가지 쓰임:
    | 쓰임 | 필드 | 연결 |
    |---|---|---|
    | 필터 | status · category | 검색 후보 고르기 (1-1 현행 필터) |
    | 출처 | title · version · source_url | 원문 찾아가기 (답변의 인용) |
    | 갱신 | 본문 해시 | 바뀐 문서 찾기 (다시 색인할 대상) |
  - **출처 표기** — `"출장 숙박 정산 (v2) | https://example.invalid/rag40/travel"`. URL은 검색 점수를 높이려고 넣는 값이 아니라서 **본문에 섞지 않고 metadata에** 둔다. 1-3의 S1 → travel → 원문 URL로 연결된다.
  - **청크마다 metadata를 깊게 복사(`deepcopy`)** — `dict(meta)`는 바깥만 새로 만들고 안쪽 list·dict는 원문과 같이 써서, 한 청크의 수정이 원문으로 번진다. 원본을 공유하면 마지막에 붙인 `section`이 모든 청크에 덮어써진다.
  - **본문 해시** — content → UTF-8 바이트 → sha256 → 앞 12자리(수업용 축약). travel `46fb3976b5b2`, travel-old `5d10631a88a2`. 같으면 다시 색인할 필요 없고, 달라지면 그 문서만 다시 청킹·색인. **status만 바뀌면 해시는 그대로**. 12자리 축약값은 문서 ID를 대신하지 않는다.
  - `choose_current(docs, category)` — category와 status를 **모두** 확인.
- **퀴즈 2-2** (교안 정답): `d["metadata"]["category"] == category and d["metadata"]["status"] == "current"`. "출장" → travel, meal (travel-old는 retired라 제외) / "교육" → education. 새 dict가 아니라 **원래 문서 객체**를 반환.
- **QA 체크포인트**:
  - **발행일만으로 최신을 판단하지 않는다** — 날짜가 최신이어도 아직 적용 전이거나 철회된 문서일 수 있다. status를 함께 보는 건 "날짜 기준 정렬 = 최신"이라는 가정을 의심하는 것.
  - **얕은 복사 공유 결함** — 한 청크를 고쳤는데 다른 청크와 원문이 같이 바뀐다. 에러 없이 데이터가 오염되는 유형이라 찾기 어렵다. 테스트로는 "청크 하나를 수정한 뒤 원문 metadata가 그대로인지" 확인한다 (원문 section: None).
  - **해시로 변경 감지 = 회귀 범위 축소** — 바뀐 문서만 다시 처리한다. 게임 QA에서 변경된 빌드 영역만 집중 재검증하는 것과 같은 발상. 다만 해시가 무엇을 기준으로 계산되는지(본문만) 알아야 놓치는 변경이 없다 (🧭 9-②).
  - **원래 객체를 반환** — 필터 결과로 새 dict를 만들면 이후 수정이 원본에 반영되지 않거나, 반대로 의도치 않게 반영된다. 반환값이 "같은 객체인지, 사본인지"는 계약의 일부다.

### 2-3 : 중복 · 빈 본문 · Boilerplate 정제
- **핵심 개념**:
  - **정제는 덜어내는 일이지, 고쳐 쓰는 일이 아니다.**
    | 대상 | 하는 일 |
    |---|---|
    | 공백·탭 | 연속 공백을 한 칸으로, NFC로 한글 표현 통일 |
    | Boilerplate (틀 문구) | 메뉴·제목 줄·꼬리말 같은 반복 문구 제외 |
    | 중복 | 버전·범주·본문 해시가 **모두** 같은 문서만 제외 |
    | 빈 본문 | strip 후 빈 문자열이면 제외하고 원인 기록 |
  - **하지 않는 것**: 부정어·금액·조건 수정. "정산되지 않습니다" → "정산됩니다"면 규정이 반대가 된다.
  - **공백 정규화**: `re.sub(r"[ \t]+", " ", unicodedata.normalize("NFC", noisy)).strip()` — 공백과 탭만 한 칸으로, 줄바꿈은 그대로. `repr()`로 탭·양끝 공백처럼 안 보이는 글자를 확인.
  - **Boilerplate를 빼는 이유**: 모든 문서에 똑같이 들어 있어 검색 점수를 흐리고, 청크와 토큰 예산을 차지한다. 쓸모 있는 값은 metadata로(제목 → title, 날짜 → published_at).
  - **중복 제거**: `key = (version, category, sha256(content))`. 13개 입력(12개 + travel 복사본) → 12개 유지, travel 복사본 1개 `excluded`. travel-old(v1)는 버전이 달라 **다른 키 → 유지**.
  - **빈 본문**: 스캔 PDF(텍스트 계층 없음), 본문 영역을 못 찾은 HTML에서 생긴다. 그냥 두면 청크도 비고, 검색 결과에 빈 근거가 올라와 **답변에 출처만 있고 내용이 없다.** `rejected`에 `('blank-demo', '빈 본문')` 기록.
- **퀴즈 2-3 `clean_lines`** (교안 정답): 줄마다 `re.sub(r"[ \t]+", " ", line).strip()` → 빈 줄이거나 footer와 같으면 `removed`, 아니면 `kept` → `("\n".join(kept), removed)`. 제외한 줄: `['교육용 가상 규정 · 2026-08-01 · 1']`, 12만원 · 예약 전에 · 정산되지 않습니다 문장 보존.
- **QA 체크포인트**:
  - **정제 전후 의미 보존 테스트** — "12만원", "예약 전에", "정산되지 않습니다" 같은 **금액·조건·부정어가 남아 있는지** 확인하는 게 정제 단계의 통과 기준이다. 정제가 의미를 바꾸면 그 뒤 모든 단계가 틀린 근거로 동작한다.
  - **제외 기록 = 감사 추적(audit trail)** — 무엇을 왜 뺐는지 남겨야 "필요한 규정을 실수로 지웠는가"를 나중에 검토할 수 있다. 2차 Review의 "실패 행 삭제 금지"와 같은 원칙.
  - **중복 판단 키에 버전을 넣는 이유** — 본문이 비슷해도 버전이 다르면 다른 문서다. 키를 너무 느슨하게 잡으면 구버전·신버전 중 하나가 사라진다.
  - **`repr()`로 안 보이는 문자 확인** — 탭, 양끝 공백, 다른 코드의 한글처럼 화면에서 같아 보이는 차이가 검색 실패의 원인이 된다. 게임 로컬라이징 QA에서 보이지 않는 특수문자를 잡던 것과 같다.

### 2-4 : 표준 JSONL 저장과 데이터 검수
- **핵심 개념**:
  - **JSON 배열 vs JSONL**: `documents.json`은 배열 하나, `documents.jsonl`은 12줄(한 줄 = 문서 하나).
    | JSONL 장점 | 뜻 |
    |---|---|
    | 이어 쓰기 | 새 문서를 마지막 줄에 추가 |
    | 나눠 읽기 | 큰 파일도 한 줄씩 처리 |
    | 오류 위치 | 몇 번째 줄이 깨졌는지 바로 |
  - **직렬화**: `json.dumps(row, ensure_ascii=False)` — 기본값(True)이면 "숙박"이 `"숙박"`로 바뀐다. 파일은 `encoding="utf-8", newline="\n"`으로 연다.
  - **본문에 줄바꿈이 있어도 레코드는 한 줄** — 실제 줄바꿈은 JSON 문자열 안에서 `\n` 두 글자로 이스케이프된다. `json.loads`로 읽으면 다시 복원된다.
  - **검수 3단계 + 줄 번호**:
    | 단계 | 검사 | 오류 예 |
    |---|---|---|
    | ① 문법 | `json.loads` 성공? | `3행: Expecting value: line 1 column 1 (char 0)` |
    | ② 객체 | dict인가? | 각 행은 JSON 객체여야 합니다 |
    | ③ 본문 | content가 str인가? | `2행: content는 문자열이어야 합니다` |
    `raise ValueError(f"{number}행: {error}") from error` — 원래 오류를 연결해 둔다.
- **퀴즈 2-4 `load_jsonl`** (교안 정답): `Path(path).open(encoding="utf-8")` → `enumerate(stream, 1)` → `inspect_line(line, number)` 결과를 모아 반환. 마지막 문서 retention 교육 자료 보관(12개), 3행 content를 숫자로 바꾼 복사본 → `3행: content는 문자열이어야 합니다`.
- **QA 체크포인트**:
  - **줄 번호가 있는 오류 메시지 = 재현 가능한 결함 리포트.** "어딘가 깨졌다"가 아니라 "3행의 content가 숫자다"로 바로 위치를 짚는다. 좋은 버그 리포트의 재현 정보와 같다.
  - **깨진 줄을 조용히 건너뛰지 않는다** — 건너뛰면 12개 중 11개만 색인되고 아무도 모른다. 데이터 누락은 검색 실패로만 드러나서 원인 추적이 어렵다.
  - **저장 후 다시 읽어 개수 확인** — 저장한 것과 읽은 것이 같은지 왕복(round-trip) 검증. 2차 Review의 "기록 수가 계획과 맞는지 먼저 확인"과 같은 습관.
  - **`enumerate(stream, 1)`로 1부터 센다** — 사람이 보는 에디터 줄 번호와 맞추기 위해. 0부터 세면 오류 메시지의 줄 번호가 실제와 하나씩 어긋난다.
  - **`ensure_ascii=False`** — 한글이 이스케이프되면 파일을 열어 사람이 검수할 수 없다. 사람이 읽을 수 있는 데이터인지도 품질 기준이다.
