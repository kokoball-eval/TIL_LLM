## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | Golden Dataset | — | 질문 + 원문과 대조한 **참고 답변** + **근거 문서 ID**를 미리 정해 둔 평가 기준 파일 (모델 출력을 복사한 게 아님) |
  | JSONL | JSON Lines | 한 줄에 JSON 하나씩. 통째로 `json.loads`하면 Extra data 오류 → 줄마다 읽는다 |
  | dev / test | development / test split | 설정을 고치고 비교하는 용 / 고른 설정을 **마지막에 한 번** 확인하는 용 |
  | Hit@k | — | 상위 k개 안에 필요한 문서가 **하나라도** 있으면 1 |
  | Recall@k | — | 필요한 문서 중 **찾은 비율** (분모 = 필요한 문서 수) |
  | BM25 | Best Matching 25 | 단어(토큰) 일치 기반 검색 (7장) |
  | Dense | Dense Retrieval | 임베딩 벡터 유사도 기반 검색 (E5) |
  | Hybrid / RRF | — / Reciprocal Rank Fusion | BM25와 Dense 순위를 합치는 검색 / 순위의 역수로 점수를 합치는 방식 |
  | RAGAS | Retrieval Augmented Generation Assessment | RAG 답변·Context를 LLM으로 채점하는 평가 라이브러리 |
  | Faithfulness | — | 답변의 주장이 **Context로 뒷받침**되는가 |
  | Answer Relevancy | — | 답변이 **질문에 관련**된 답인가 (숫자 정확성은 판정 안 함) |
  | Context Precision / Recall | — | 유용한 근거가 **앞 순위**에 있나 / 참고 답변의 사실이 **Context 안에** 있나 |
  | Parent-Child | — | 작은 Child 청크로 **찾고**, 그 청크가 속한 큰 Parent로 **읽는** 구조 |
  | Context Compression | — | Context에서 질문에 필요한 문장만 남겨 줄이는 것 |
  | Agentic RAG | — | 결과를 보고 **다음 질의·도구·종료**를 정하는 RAG |
  | CRAG | Corrective RAG | 검색 품질을 평가한 뒤 보정(필요하면 외부 검색)하는 연구 구조 |
  | Self-RAG | Self-Reflective RAG | 검색 필요성·생성 내용을 **비평 토큰을 학습한 모델**이 스스로 판단하는 연구 구조 |
  | GraphRAG | — | 문서에서 개체·관계를 뽑아 **그래프**로 만들고 따라가며 답하는 방식 (Microsoft) |
  | Local / Global / DRIFT | — / — / Dynamic Reasoning and Inference with Flexible Traversal | 개체 주변 관계 탐색 / 커뮤니티 보고서 종합 / 보고서에서 시작해 후속 질문으로 Local까지 내려가는 탐색 |
  | 노드 / 간선 | Node / Edge | 그래프의 항목(규정·영수증·팀장) / 항목 사이의 관계(제출·승인자) |
  | NetworkX | — | 파이썬 그래프 라이브러리 (`DiGraph` = 방향 그래프) |
  | Multimodal RAG | — | 표·이미지·페이지 그림까지 검색 근거로 쓰는 RAG |
  | ColPali | ColBERT(Contextualized Late Interaction over BERT) + PaliGemma | 페이지를 **이미지로** 읽고 여러 벡터로 표현하는 문서 검색 모델 |
  | MaxSim | Maximum Similarity | 질문 벡터마다 **가장 잘 맞는 페이지 조각**의 점수를 골라 합하는 방식 |
  | OCR | Optical Character Recognition (광학 문자 인식) | 이미지 속 글자를 텍스트로 읽는 기술 (오늘 PNG는 OCR 결과가 아님) |

- **핵심 통찰: 오전은 "같은 기준으로 재기", 오후는 "잰 결과로 찾은 빈틈을 메우기"**
  - 어제 7장은 검색을 바꾸고 결과를 **눈으로** 읽었다. 오늘 오전은 같은 질문 20개·같은 정답 파일로 **숫자**를 매겼고, 오후는 그 숫자 아래에서 찾은 빈틈 네 종류를 하나씩 메웠다.

    | 단계 | 오늘 배운 것 | 확인할 질문 |
    |---|---|---|
    | 8-1 Golden Dataset | 질문 · 참고 답변 · 근거 문서 ID, dev/test 분리 | 무엇이 정답인가? |
    | 8-2 Hit · Recall | 청크 k개 → 문서 ID 비교, 질문별로 구한 뒤 평균 | 근거를 찾았나? |
    | 8-3 RAGAS | 주장 단위 라벨, 네 지표의 입력 | 답이 근거에 맞나 / 질문에 답했나? |
    | 8-4 전후 비교 | 하나만 바꾸고 dev로 고르고 test로 확인 | 바꿔서 좋아졌나? |
    | 9-1 Parent-Child | 작게 찾고 넓게 읽기, 예산 안에 조건 남기기 | 문맥이 잘렸나? |
    | 9-2 Agentic RAG | 다시 검색하고, 언제 멈출지 정하기 | 표현 때문에 못 찾았나? |
    | 9-3 GraphRAG | 규정 사이 관계를 간선으로 따라가기 | 여러 문서를 이어야 하나? |
    | 9-4 Multimodal | 값 + 단위 + 출처, MaxSim, 페이지 이미지 | 표·그림 속 숫자인가? |

- **두 번째 통찰: 평균 0.9의 정체는 "q10 하나"였다 — 평균은 결론이 아니라 출발점**
  - BM25 k=3 평균 Hit · Recall = **0.9** → "근거의 90%를 찾았다"가 아니라 **9개는 1.0, q10 하나가 0**이었다.
  - Hybrid로 바꾸면 0.9 → 1.0. 이 **0.1 상승도 q10 한 질문**이다. 그리고 q10은 문서 Recall이 1.0이 되어도 정답 문장(수료증과 영수증)은 education@60에 있는데 education@0만 들어올 수 있다.
  - q10 하나를 RAG 과목 전체에 걸쳐 따라가면 이렇게 된다:

    | 단계 | q10 "교육비 정산 증빙은?"에 일어난 일 |
    |---|---|
    | 7-1 BM25 | 토큰 불일치로 **빈 목록** (자료가 없는 게 아님) |
    | 8-2 평가 | 평균 0.9 아래에 숨은 **유일한 실패** |
    | 8-4 Hybrid | 문서 Recall 1.0 — 하지만 증빙 청크 포함은 따로 확인 |
    | 9-2 재검색 | "수강 완료 후 제출" 표현으로 education@60 확보 |
    | 9-1 Parent | 원문 전체로 수료증과 영수증 문장까지 Context에 |

  - 2차 Review에서 "정확도 하나보다 오류 사례를 직접 읽는다"고 배운 게, RAG에서는 **질문 하나를 단계별로 끝까지 따라가기**로 이어졌다.

- **세 번째 통찰: 근거에 맞다(Faithfulness) ≠ 질문에 답했다(Relevancy) — 그리고 둘 다 "정확하다"는 아니다**

  | 답변 | 내용 | 근거 일치 | 질문 적합 | 실제 판정 |
  |---|---|---|---|---|
  | A | 1박당 12만원 + 숙박 영수증 | 1.0 | ✓ | 정답 |
  | B | 1박당 **30만원** + 숙박 영수증 | 0.5 | ✓ (Relevancy가 A와 **같음**) | 금액 오류 |
  | C | 식비 1일 3만원 | **1.0** | ✗ | 숙박 질문에 답하지 않음 |
  | D (퀴즈) | 1**일**당 12만원 + 숙박 영수증 | 0.5 | ✓ | 단위 오류 (B와 같은 0.5, 다른 이유) |

  - C는 원문에 있는 사실이라 근거 일치 1.0인데 질문에 답하지 않았고, A와 B는 Relevancy가 같다. **지표 하나에 정확성 판정을 맡기면 안 되는 이유**가 표 한 장에 다 들어 있다.
  - RAG 3일차 Citation의 "출처가 있다 ≠ 출처가 문장을 뒷받침한다"가, 오늘은 "**근거가 있다 ≠ 질문에 답했다**"로 한 축 더 늘었다.

- **네 번째 통찰: 확장 기법은 "빈틈의 종류"에 맞춰 고른다 — 그리고 확장마다 새 위험이 생긴다**

  | 관찰한 빈틈 | 확장 | 새로 생기는 위험 |
  |---|---|---|
  | 문장 중간에 조건이 끊김 | Parent · 인접 구간 (9-1) | Context 길이 증가 |
  | 질문 표현 때문에 못 찾음 | 재검색 · 질의 변형 (9-2) | 반복 호출 비용, 무한 반복 |
  | 여러 규정의 관계를 따라가야 함 | 그래프 (9-3) | 자동 추출 오류, 색인 비용 |
  | 표·이미지가 답에 중요 | 구조 추출 · 시각 검색 (9-4) | 모델 메모리, 행·열 혼동 |

  - "확장을 더하기 전에 **어느 단계에서 정보가 처음 사라졌나**부터 찾는다." 1일차부터 계속 나온 "원인 단계부터 분리"가 RAG 과목의 마지막 정리 문장이었다.

- **향후 계획 및 다짐**
  - RAG 과목이 오늘로 끝났다. 1일차 문서 수집부터 오늘 평가까지 **원문 → 청크 → 검색 → Context → 답변 → 평가 기록** 한 바퀴를 다 봤다.
  - 러브코드(2차 프로젝트)나 이후 평가 작업에서 바로 가져갈 것:
    - 평가셋에 **질문 · 참고 답변 · 근거 문서 ID · 답 가능 여부 · split**를 처음부터 같이 적기
    - 평균만 보지 않고 **질문별 개선·악화 목록**을 같이 남기기
    - dev/test를 나눌 때 **어려운 유형(여러 문서·표현 불일치·답 없음)이 양쪽에 다 들어가게** 하기 (🧭 9-③)
    - 답이 없는 질문에도 **"규정하지 않는다"고 적힌 문장**이 있는지 같이 표시하기 (🧭 9-④)
  - 교안 마지막 과제 — **질문 하나를 골라 원문 → 평가까지 실제 데이터로 한 장 정리** — 는 포트폴리오 설명 방식으로도 그대로 쓸 수 있을 것 같다.

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 평가 기준(Golden Dataset)이 먼저다 — 기대 결과 없는 테스트는 없다

| 필드 | 쓰는 곳 | 주의 | 근거 교안 |
|---|---|---|---|
| `question` | 시스템 입력 (**이것만** 보냄) | — | 8-1 |
| `reference` · `relevant_document_ids` | **평가에만** 사용 | 검색 입력에 붙이면 정답을 넣는 셈 | 8-1 |
| `answerable` | 답 가능 여부 | 답 없는 질문은 검색 Recall 분모에서 빼고 **단정 여부**를 따로 평가 | 8-1 |
| `split` | dev(개발) / test(최종 확인) | 근거 문서가 겹치지 않게 (교집합 `[]`) | 8-1 |

- 테스트 케이스의 **기대 결과(Expected Result)** 와 같다. "출장비는 얼마?"처럼 숙박/식비/합산 여부에 따라 답이 갈리는 질문은 **기대 결과를 먼저 고정**해야 "출장 문서를 찾았으니 성공" 같은 판정을 막는다.
- 문서 ID는 **검색 비교용**, 정확한 문장·조건은 **답변 검토용** — 서로 대신하지 않는다. 청크 크기를 바꾸면 chunk_id는 바뀌지만 document_id는 유지되니까 근거는 문서 ID로 적는다.

### 2. 지표의 정의(단위·분모·순서)를 결과 표에 같이 적는다

| 확인할 것 | 다르게 하면 | 근거 교안 |
|---|---|---|
| 청크 단위인가, 문서 단위인가 | 같은 "Recall"이라도 다른 평가 | 8-2 |
| 분모가 무엇인가 | 답 없는 q11·q12는 분모에서 제외 → 분모 **10** (12 아님) | 8-2 |
| `ranked[:k]` 먼저, 그다음 집합 | 문서를 먼저 중복 제거하면 q06 Top-2 Recall 0.5 → 1.0 | 8-2 |
| 질문별로 구한 뒤 평균 | 근거가 2개인 q06도 질문 가중치는 같음 | 8-2 |
| 8-2 문서 ID Recall vs 8-3 Context Recall | 비교 대상이 다름 (문서 ID 집합 vs 참고 답변 사실) | 8-3 |

→ A·B 두 방식 모두 틀린 게 아니라 **다른 단위의 평가**다. 숫자만 옮겨 적으면 다른 정의의 숫자끼리 비교하는 실수가 생긴다.

### 3. 평균 아래를 읽는다 — 질문별 개선·악화 목록

- k=3 평균 0.9 = **q10 하나가 0.** Hybrid 0.9 → 1.0 = **q10 하나의 개선.** 악화(losses)는 `[]`.
- k를 3 → 5로 늘려도 q10은 해결 안 된다 — BM25 **양수 점수 후보가 0개**라서. 원인이 k가 아니라 **토큰 불일치**다.
- k=5에서 무관한 meeting·vpn이 들어와도 **Recall은 안 내려간다** → Recall만으로는 **잡음을 모른다.** k를 늘릴 땐 Context 길이·처리 시간·최종 답변 정확성을 같이 본다.
- 2차 Review에서 "평균 정확도보다 틀린 사례를 직접 본다"던 원칙과 같다. 회귀 테스트에서도 **통과율보다 새로 실패한 케이스 목록**이 먼저다.

### 4. 하나만 바꾸고, dev로 고르고, test는 기록만

| 고정 (통제 조건) | 바꾼 것 하나 |
|---|---|
| 질문 dev 12 · test 8, 80/20 청크, 현행 필터, golden.jsonl, k = 3 | 검색 방법 (BM25 → Dense → Hybrid) |

- 한 번에 여러 개를 바꾸면 **무엇이 효과를 냈는지** 알 수 없다. 다음 변경 후보(질의 재작성 / Parent 확장 / 재정렬)도 **하나씩** 넣고 같은 dev로 다시 잰다.
- test를 보며 설정을 고치면 최종 확인이 개발에 섞인다. test 결과는 이렇게만 쓴다:

  | 표현 | 판정 |
  |---|---|
  | dev의 개선이 test에서도 확인됐다 | ✗ (test는 세 방법 모두 1.0 → 개선 자체가 없음) |
  | 이 시스템의 검색 성공률은 100%다 | ✗ (질문 6개, 서비스 전체가 아님) |
  | test 6개 질문의 근거 문서는 Top-3에 있었다 | ✓ |

- 게임 QA의 "빌드 비교" 원칙과 같다 — 비교할 때 **바뀐 변수 하나만** 있어야 결과를 그 변수 탓으로 돌릴 수 있다.

### 5. 자동 평가 점수는 "판정"이 아니라 "검토할 곳의 표시"

| 사실 | 의미 | 근거 교안 |
|---|---|---|
| A·B·C는 사람이 쓴 연습 답변, 기본 실행 비율은 **수동 라벨** | RAGAS 점수와 구분 | 8-3 |
| 평가 LLM은 주장을 **다르게 나눌 수 있음** | 수동 라벨과 같은 숫자가 나온다는 보장 없음 | 8-3 |
| 검수 기록도 **매번 같지 않음** | 1회 점수로 결론 내지 않기 | 8-3 |
| 평가에는 **실제로 모델에 보낸 Context**를 씀 | 원문 전체를 주면 검색 실패를 놓침 | 8-3 |
| 네 점수를 무조건 평균 내지 않음 | 낮아진 지표의 **입력과 실제 답변**을 함께 읽기 | 8-3 |
| API 오류는 **미완료**로 기록, 0점으로 기록하지 않음 (README) | RAG 3일차의 `system_error ≠ insufficient`와 같은 원칙 | 8-3 |

### 6. 잘라도, 줄여도, 조건은 남아야 한다

- 80자 Child는 "담당 임원의 **서면**"에서 끊긴다 → 1일차부터 따라온 그 절단이 오늘 **Parent 확장**으로 해결됐다.
- 압축의 기준은 **짧아졌나**가 아니라 **답을 바꾸는 조건(금액·부정·기간·승인 전후)이 남았나**다.

  | 예산 | 남은 문장 | "13만원 숙박도 정산?"에 대한 gemma3 응답 (1회 기록) |
  |---|---|---|
  | 70자 | 1박당 12만원 · 숙박 영수증 (54자) | "아니요, … 정산할 수 **없습니다**" (단정) |
  | Parent 전체 | + 예약 전 서면 승인 · 승인 없는 초과 불가 | "… 예약 전에 담당 임원의 **서면 승인이 필요**합니다" |

- 두 응답 모두 출처는 **S1** — 같은 ID라도 가리키는 본문 범위가 다르다. 그래서 확장한 본문은 `travel:parent:v2` 같은 **별도 ID**로, 실제 검색된 Child는 `retrieved_child_ids`에 남긴다.

### 7. 반복에는 종료 조건이 있어야 한다 — 성공 경로만 테스트하지 않는다

| 종료 상태 | 조건 | 뜻 | 근거 교안 |
|---|---|---|---|
| `candidates_ready` | 제목 검사를 통과한 후보가 생김 | **검토할 후보가 생겼다** (정답 확정 아님) | 9-2 |
| `repeated_query` | 같은 질의 반복 | 무한 반복 방지 | 9-2 |
| `search_limit` | `max_searches` 도달 | 시도 횟수 제한 | 9-2 |

- 성공 경로뿐 아니라 **반복·제한 경로도 실제로 실행**해 본다 — 예외 흐름 테스트.
- education@0은 제목 검사('교육비')를 통과하지만 증빙 문장이 없다 → **통과 조건이 약하면 잘못된 통과**가 생긴다. 제목 일치 = 주제 확인일 뿐.
- 모델이 action을 고르게 하면 검사가 더 필요하다. gemma3는 **빈 검색 결과인데 `answer`를 골랐고**, 인용 검사(`q in context`)가 막았다. 문자열 포함 검사는 **최소한의 확인**이다.

### 8. 관계·숫자는 "원문 근거 + 조건"과 같이 저장한다 — 없는 것을 있다고 확대하지 않는다

- 그래프 간선에 **조건과 원문 출처**를 같이 저장한다. 같은 승인자(팀장)라도 education은 **수강 전**, leave는 **휴가 시작 3영업일 전** → 하나로 합치지 않는다.
- meal의 "승인자 규정 없음" = 이 문서와 그래프에 **명시 안 됨.** "승인 불필요"로 확대 금지 (RAG 3일차 "규정 안 함 ≠ 지원 안 함"과 같은 원칙).
- 숫자는 **값 + 단위 + 원문 ID + 출처**를 같이 저장한다. 12만원 × 2박 = 24만원은 **산술 결과**일 뿐 영수증·사전 승인까지 판정한 값이 아니고, 교육비 30만원을 더한 54만원은 **더할 근거가 없다.**
- 확장 기법의 비용도 같이 본다. 교안 검수 기록 기준으로 Claude가 확인한 숫자:

  | 항목 | 기록 | 비고 |
  |---|---|---|
  | RAGAS 실제 평가 (질문 1개 × 답변 3개) | 생성 요청 **18회**, 약 **1.6만 토큰** | 최대 20회 제한 안에서 |
  | GraphRAG 색인 (문서 10개) | 엔티티 69 · 관계 62 · 커뮤니티 보고서 17 | 실행마다 달라짐 |
  | GraphRAG 질의 시간 | Local **10.2초** · Global **12.5초** · DRIFT **47.4초** | DRIFT ≈ Local의 4.7배 |

### 9. Claude가 짚어준 확인 포인트

**① 9-1 문자 예산을 늘렸는데 승인 문장이 오히려 빠지는 구간이 있다**
- 9-1의 `main.py`는 문장을 앞에서부터 보면서 **예산에 안 들어가면 건너뛰고 다음 문장을 계속 본다** (`break`가 아니라 `if`만 있음). 문장 길이는 28 · 24 · 38 · 30자(+공백 1).
- 예산을 50~130자로 바꿔 가며 남는 문장을 시뮬레이션해 보면:

  | 예산 | 남는 문장 | 승인 관련 내용 |
  |---|---|---|
  | 54 ~ 84 | ① 한도 ② 영수증 | 없음 |
  | **85 ~ 92** | ① ② **④ 승인 없는 초과는 자동 정산 안 됨** | "승인"이 있다는 것만, 누가·언제는 없음 |
  | **93 ~ 123** | ① ② **③ 예약 전 담당 임원 서면 승인** | ④가 **다시 빠짐** |
  | 124 ~ | ① ② ③ ④ | 모두 |

- 예산을 92 → 93으로 1자 늘렸는데 ④가 빠지고 ③이 들어온다. **예산과 남는 조건이 단조롭게(늘수록 더 많이) 움직이지 않는다.** 교안의 70·140 두 값만 보면 안 보이는 구간이다.
- 교안의 "생각해 보기"(첫 문장 + 승인 두 문장을 넣으려면 예산이 얼마?)도, 세 문장만 고르면 29+39+31 = **99자**지만 이 코드 방식(앞에서부터, 영수증 문장 포함)으로는 **124자**가 있어야 ③④가 같이 남는다.
- QA로 보면 전형적인 **경계값 테스트** 대상이다. 예산 같은 설정값은 대표값 두 개가 아니라 **문장 길이 합이 바뀌는 지점마다** 확인해야 하고, 압축 결과에 **필수 조건 문장이 남았는지**를 검사 항목으로 따로 둬야 한다.

**② Answer Relevancy 점수는 A(정답)와 C(엉뚱한 답)의 차이가 0.0135뿐이다**
- 검수 기록: A **0.8705**, B **0.8705**, C **0.8570**. B는 금액이 틀렸는데 A와 **소수점까지 같고**, 질문에 답하지 않은 C도 A보다 **0.0135** 낮을 뿐이다.
- Relevancy는 "답변에서 다시 만든 질문 ↔ 원질문"의 **임베딩 유사도**라서, 2일차에 Claude가 짚었던 **E5 점수가 0.78~0.92의 좁은 띠에 몰리는 현상**이 여기서도 나타난 것으로 보인다. 숙박 답변이든 식비 답변이든 "출장 비용 이야기"라 비슷하게 나온다.
- 그래서 "Relevancy 0.86 이상이면 통과" 같은 **절대 기준선**을 두기 어렵다. 0.0135 차이는 실행마다 바뀌는 흔들림에 묻힐 수도 있다. 같은 질문 안에서 **상대 비교**로 보고, 낮게 나온 답변은 결국 사람이 질문 요구 항목(숙박 한도 ✓ / 증빙 ✓)을 체크리스트로 확인해야 한다.

**③ test 질문 6개는 모두 "단일 문서 질문"이라 검색 방법 차이를 구분할 수 없다**
- `golden.jsonl`을 보면 dev에는 **여러 문서가 필요한 q06(meal + travel)** 과 **토큰 불일치 q10**이 있지만, test의 답 있는 질문 q13~q18은 **모두 근거 문서가 하나**이고 BM25로도 이미 1.0이다.
- 그래서 test가 "모두 1.0"인 건 세 방법이 다 좋아서라기보다 **test에 어려운 유형이 없어서**일 가능성이 크다. dev에서 Hybrid가 해결한 유형(토큰 불일치)이 test에 하나도 없으니, test는 그 개선을 **확인할 기회 자체가 없다.**
- 교안이 "dev의 개선이 test에서도 확인됐다 ✗"라고 쓴 이유를 데이터로 보면 이렇다. 평가셋을 나눌 때 **근거 문서가 겹치지 않게**(교안 기준)에 더해, **질문 유형(단일 문서 / 여러 문서 / 표현 불일치 / 답 없음)이 양쪽에 고르게** 들어가도록 나눠야 test가 의미를 갖는다. 게임 QA에서 회귀 테스트 세트에 **이전에 터졌던 유형의 케이스**를 꼭 넣던 것과 같다.

**④ 답이 없는 질문에도 "규정하지 않는다"는 근거 문장이 있다 — 그런데 평가셋엔 `[]`로 적혀 있다**
- q12 "개인 취미 강좌도 지원하나요?" → education 원문 마지막 문장: "개인 취미 강좌의 지원 여부는 이 문서에 **규정되어 있지 않습니다.**"
- q20 "해외 출장 항공 좌석 등급은?" → travel 원문: "**국내** 출장 숙박…", "이 규정은 **교통비와 식비를 정하지 않습니다.**"
- 두 질문 모두 `relevant_document_ids: []`라서 검색 평가 분모에서 빠진다. 그런데 모델이 **올바르게 보류하려면** 바로 이 "미규정" 문장이 Context에 들어와야 한다. 이 문장이 없으면 모델은 "규정이 없다"가 아니라 그냥 근거가 부족한 상태에서 추측할 수 있다 — RAG 3일차 gemma3가 개인 취미 강좌 질문에서 `invalid_output`을 냈던 그 질문이다.
- 그래서 답 없는 질문에도 `relevant_document_ids`와 별도로 **"보류 근거 문서"** 칸을 두면, "보류해야 할 질문에서 보류 근거를 찾았는가"까지 검색 단계에서 잴 수 있다. q11(매출 목표)처럼 **관련 문서 자체가 없는** 질문과 q12처럼 **문서는 있는데 정하지 않은** 질문은 보류 이유가 다르니 구분해 두는 게 좋다 (교안 8-1 노트도 q12를 "관련 문서는 찾았는데 답이 없음"으로 따로 설명한다).

## 8장. RAG 평가 (오전)

### 8-1 : 소규모 Golden Dataset 설계
- **핵심 개념**:
  - **Golden Dataset = 질문 + 원문과 대조한 참고 답변 + 근거 문서 ID.** 모델 출력을 정답으로 복사한 파일이 아니다.
  - 자료: 문서 **12개**(현행 10 · 구버전 2), 청크 28개(현행 24), `golden.jsonl` 질문 **20개** → split `{'dev': 12, 'test': 8}`, answerable `{True: 16, False: 4}`.
  - JSONL은 **줄마다** `json.loads` (`splitlines`). 전체를 한 번에 넣으면 Extra data 오류.
  - **q06 정답을 원문까지 따라가기**:
    | 답에 필요한 내용 | 근거 | 검토할 조건 |
    |---|---|---|
    | 숙박비 1박당 12만원 | travel | 국내 출장, 1박 기준 |
    | 식비 1일 3만원 | meal | 국내 출장, 1일 기준 |
    | 남은 숙박비 한도를 식비에 합산하지 않음 | meal | 두 한도 분리 |
    - ✗ "출장비는 15만원이에요" — 12 + 3 단순 합산. 금액이 다 나와도 **단위와 합산 금지가 사라져 오답.**
  - **답이 없는 질문**: q11 올해 매출 목표(규정 어디에도 없음), q12 개인 취미 강좌(교육비 문서가 **정하지 않음**). ✓ "현재 자료에서 확인할 수 없어요" / ✗ 임의의 매출액, ✗ "지원하지 않아요". 검색 Recall 분모에서 빼고 **단정 여부**를 따로 평가한다.
  - **dev/test 분리**: dev 근거 6개 문서(education, incident, leave, meal, travel, vpn) / test 근거 4개 문서(equipment, meeting, remote, retention) → **교집합 `[]`.** 같은 원문의 의역 질문은 `group_id`로 묶어 함께 나눈다.
- **퀴즈 8-1** (교안 정답): `next(g for g in golden if g["question_id"] == target_id)`, `by_id[did]` → q09 근거 = **education, 분기 1회 · 1인당 30만원.** 금액만 맞고 "월 1회"로 바뀌면 오답 → **금액과 횟수를 함께.**
- **QA 체크포인트**:
  - **"정보 없음"을 "아니다"로 바꾸지 않는다** — 미규정을 부정으로 단정하는 건 별도 오류 유형. 평가셋에 답 없는 질문을 **의도적으로 섞어야** 과잉 응답을 잴 수 있다.
  - **dev/test 누수(leakage)** — 2차 Review의 `group_id` 기준 분할과 같은 원칙. 같은 원문에서 나온 질문이 양쪽에 있으면 dev에서 맞춘 표현이 test에서도 그대로 통한다.
  - 질문 20개는 작은 평가셋이다. 여기서 얻은 숫자를 **서비스 전체 성공률로 확대하지 않는다.**

### 8-2 : 검색 평가 Hit@k · Recall@k
- **핵심 개념**:
  - **Hit@k = 1(|R ∩ S| > 0)**, **Recall@k = |R ∩ S| / |R|** (R: 필요한 문서 집합, S: 상위 k개 청크의 문서 ID 집합).
  - 검색은 **청크 단위**, 정답 비교는 **문서 ID 단위** — 이 정의를 먼저 고정한다.
  - **q06 BM25 실제 순위**: meal@60 · travel@0 · meal@0 · meeting@60 · vpn@60
    | k | 찾은 문서 | Hit@k | Recall@k |
    |---|---|---|---|
    | 1 | meal | 1 | **0.5** |
    | 3 | meal, travel | 1 | 1.0 |
    | 5 | meal, meeting, travel, vpn | 1 | 1.0 |
    - k=1은 Hit 1이지만 숙박비 근거(travel)가 없다 → **Hit만 보면 놓친다.**
    - meal@60(합산 금지)과 meal@0(식비 3만원)은 문서 집계에선 meal 하나, 답변엔 **서로 다른 사실.**
    - k=5에 무관한 meeting·vpn이 들어와도 Recall은 그대로 → **Recall만으로는 잡음을 모른다.**
  - **답 있는 dev 10개 평균**: k=1 Hit 0.9 · Recall 0.85 / k=3 · k=5 Hit 0.9 · Recall 0.9. q11·q12는 근거 집합이 비어 **분모에서 제외**(평가 안 한다는 뜻 아님).
  - 0.9의 정체 = q01~q09 모두 1.0, **q10 하나가 0.** q10은 BM25 **양수 점수 후보 0개** → k를 늘려도 해결 안 됨.
  - **청크 k개 먼저 vs 문서 먼저 중복 제거**: RRF처럼 meal@60 · meal@0 · travel@0 순서면 A(청크 2개 먼저) = {meal} → 0.5, B(문서 먼저) = {meal, travel} → 1.0. 이번 수업의 정의는 **A.**
- **퀴즈 8-2** (교안 정답): `found = {r["document_id"] for r in ordered[:2]}` → `{'meal'}` · Recall **0.5.** 문서를 먼저 중복 제거하면 1.0 — 평가 단위를 결과 표에 함께 적는다.
- **QA 체크포인트**:
  - **지표 정의 문서화** — 같은 이름의 지표라도 단위·분모·순서가 다르면 다른 숫자가 나온다. 결과 표에 정의를 같이 남기지 않으면 비교가 무의미해진다 (🧭 2).
  - **"k를 늘리면 해결"의 함정** — 후보 자체가 0개면 k는 소용없다. 원인이 순위인지, 후보 생성인지부터 나눈다.

### 8-3 : 답변 평가 RAGAS 기본 지표
- **핵심 개념**:
  - q05 "출장 숙박 비용 한도와 필요한 증빙은?"에 대한 **사람이 쓴 연습 답변** A(정답) · B(30만원, 금액 오류) · C(식비 3만원, 주제가 다름).
  - **평가에는 실제로 전달한 Context를 쓴다** — k=3을 요청했지만 양수 BM25 후보가 2개 → [S1] travel@0, [S2] meal@0. C의 식비 내용도 이 Context로 뒷받침된다. 압축·길이 제한을 했다면 **최종적으로 모델에 보낸 문장**으로 평가.
  - `main.py`가 질문·참고 답변·실제 Context·답변 A~C를 `answer_review_08.json`에 저장 → 선택 실습 RAGAS도 이 파일을 그대로 읽는다 → **수동 검토와 자동 평가가 같은 입력.**
  - **주장 단위 수동 라벨**: A = [금액 ✓, 증빙 ✓] **1.0**, B = [금액 ✗, 증빙 ✓] **0.5**, C = [식비 ✓] **1.0** — RAGAS 점수가 아니라 **직접 라벨한 비율.**
  - **RAGAS 네 지표**:
    | 지표 | 살펴보는 관계 | 입력 | 이 실습에서 볼 점 |
    |---|---|---|---|
    | Faithfulness | 답변 주장 ↔ Context | 답변 · Context | B의 30만원을 근거가 뒷받침하나 |
    | Answer Relevancy | 답변 ↔ 질문 | 질문 · 답변 · 임베딩 | C가 숙박 질문에 관련된 답인가 |
    | Context Precision | 검색 순서 ↔ 유용한 Context | Context · 참고 답변 | 숙박 근거가 앞에 있나 |
    | Context Recall | 참고 답변 사실 ↔ Context | Context · 참고 답변 | 필요한 사실이 Context에 있나 |
  - **선택 실습**: 임베딩 = **로컬 E5 small**(질문 유사도), 평가 = **LLM API**(주장 판단) → 임베딩 API 키 불필요. 준비 모드: shape [2, 384] · generation_requests 0 · completed false.
  - **검수 기록 (gpt-6-luna)**: A 1.0 / 0.8705, B **0.5** / 0.8705, C 1.0 / 0.8570, Context Recall 1.0 · Precision ≈ 1.0 — **매번 같지 않다.**
- **퀴즈 8-3** (교안 정답): D "숙박비는 **1일당** 12만원…" → `d_labels = [False, True]` → **0.5.** 원문은 1박당. B(30만원)와 같은 0.5지만 **틀린 이유가 다르다.**
- **QA 체크포인트**:
  - **같은 점수, 다른 결함** — B와 D는 둘 다 0.5지만 금액 오류 vs 단위 오류. 점수만 집계하면 결함 유형이 사라진다. 2차 Review처럼 **오류 유형 라벨**을 따로 남긴다.
  - **두 축은 합치기 전에 따로 읽는다** — C는 근거 1.0인데 질문에 답 안 함. "근거에 맞다"와 "질문에 답한다"는 다른 테스트 항목이다.
  - **평가 입력 = 실제 시스템 입력** — 시스템이 못 본 원문 전체를 평가에 주면, 테스트 환경이 운영 환경과 달라 검색 실패를 놓친다.

### 8-4 : 오류 분류와 개선 전후 비교
- **핵심 개념**:
  - 실험 질문: "현행 문서의 **같은 80/20 청크**에서 **검색 방법만** 바꾸면 문서 Recall@3이 달라지는가?" 답변 생성 모델은 부르지 않는다(Dense는 E5).
  - `lambda q, cat=None, m=method: …` — `m=method`로 **이번 반복의 방법을 고정.** 같은 평가 함수에 검색기만 갈아 끼운다.
  - **dev 결과 (Hit@3 / 문서 Recall@3)**: BM25 0.9 / 0.9, Dense **1.0 / 1.0**, Hybrid **1.0 / 1.0.** wins `['q10']`, losses `[]`. q10: BM25 `[]` → Hybrid `['education', 'meal', 'travel']`.
  - 하지만 education@0엔 증빙이 없고 **수료증·영수증은 education@60** → 문서 ID가 맞아도 위치가 빠질 수 있다.
  - **다음 변경 후보는 이유와 함께 하나씩**:
    | 관찰 | 다음에 시험할 변경 | 함께 볼 결과 |
    |---|---|---|
    | BM25 q10 후보 없음 | 질의 재작성 · 토큰 처리 (7-4) | education@60 회수와 무관한 후보 |
    | 올바른 문서의 앞 청크만 검색 | Parent 확장 · 인접 청크 (9-1) | 증빙 포함 여부와 Context 길이 |
    | 후보는 있지만 순위가 낮음 | 재정렬 (7-3) | 정답 청크 순위와 추가 처리 시간 |
  - Dense와 Hybrid가 같은 점수 → 최종 선택엔 **지연 · 자원 · 실제 답변 비교**가 더 필요.
  - **test (답 있는 6개)**: 세 방법 모두 1.0 / 1.0, wins `[]` losses `[]`. ✓ "test 6개 질문의 근거 문서는 Top-3에 있었다"까지만.
- **퀴즈 8-4** (교안 정답): `saved["dev"]["hybrid"]["rows"]` → Hybrid q10 `['education', 'meal', 'travel']` · Recall 1.0 (BM25는 `[]` · 0.0). **문서 Recall 1.0 ≠ 증빙 문장 확보.**
- **QA 체크포인트**:
  - **통제 변수** — 질문·청크·정답·k·필터를 고정하고 검색 방법 하나만 바꾼다. 실험 설계의 기본이자, 버그 재현에서 "변수 하나씩 바꾸기"와 같다.
  - **wins/losses를 같이 본다** — 평균이 올라도 특정 질문이 근거를 잃을 수 있다. 오늘은 losses `[]`였지만 **항상 확인**하는 칸이 있어야 한다.
  - **동점일 때의 선택 기준** — 정확도가 같으면 지연·자원·운영 비용이 결정한다. 지표 하나로 끝내지 않는다.

## 9장. 고급 RAG — 빈틈 메우기 (오후)

### 9-1 : Parent-Child와 Context Compression
- **핵심 개념**:
  - **Child** = 검색용 작은 청크(80자) / **Parent** = 답변에 넘길 넓은 문맥(이번엔 원문 전체 148자). Parent를 새로 임베딩하지 않고 **document_id로 원문을 조회**한다.
  - travel@0(0~80)은 "…담당 임원의 **서면**"에서 끊긴다. "출장 숙박 한도는?"엔 충분하지만, "**13만원짜리 숙박도 정산할 수 있나요?**"엔 뒤쪽 **예약 전 승인 조건**까지 필요하다.
  - **작게 잘라야 잘 찾고, 넓게 읽어야 조건을 안 놓친다** → 둘을 분리.
  - **같은 Parent는 한 번만**: 검색 청크 3개 → Parent **2개.** 확장 본문 ID = `travel:parent:v2`(별도 ID), 실제 검색된 Child = `retrieved_child_ids`. 원래 Child ID로만 표시하면 **인용 범위가 혼동**된다. LangChain `ParentDocumentRetriever`도 같은 구조.
  - **Context 압축**: 정규식 `[^.]+\.`로 문장 분리 → **한도·초과·승인·영수증**이 든 문장만 → 네 문장 (0~28, 28~53, 53~92, 92~123). 마지막 "교통비와 식비를 정하지 않음"은 빠진다. 단어 기반 **추출**이라 원문 표현이 유지된다(생성 요약은 더 짧지만 조건이 바뀔 수 있음).
  - **예산 70 vs 140**: 70자 → 2문장 54자(승인 조건 누락), 140자 → 4문장 124자(13만원 질문에 필요한 조건 포함).
  - gemma3 1회 기록: 짧은 추출문 → "정산할 수 **없습니다**" 단정 / Parent 전체 → "예약 전 서면 승인이 **필요**합니다". 둘 다 출처는 S1.
- **퀴즈 9-1** (교안 정답): `if "승인" in text` → (53, 92) "한도 초과 숙박은 예약 전에 담당 임원의 서면 승인…", (92, 123) "승인 없이 초과 지출한 금액은 자동 정산되지 않습니다." 70자 예산이면 두 문장 모두 빠진다.
  - 생각해 보기 (Claude가 계산해 확인): 첫 문장 + 승인 두 문장만 고르면 29 + 39 + 31 = **99자.** 하지만 `main.py` 방식(앞에서부터, 영수증 문장 포함)으로는 **124자**가 있어야 ③④가 함께 남는다 (🧭 9-①).
- **QA 체크포인트**:
  - **1일차부터 따라온 "서면 / 승인" 절단이 오늘 해결됐다** — 1일차 청킹 경계 → 2일차 Recall 통과 → 3일차 모델이 잘린 문장을 이어 씀 → 5일차 Parent 확장. 결함 하나를 **발견 → 영향 → 해결**까지 추적한 셈.
  - **압축의 합격 기준 = 필수 조건 문장 포함 여부** — 길이가 아니라 "금액·부정·기간·승인 전후"가 남았는지 검사 항목으로 둔다.
  - **위치는 시작 포함 · 끝 제외** — 인용할 땐 저장한 start/end로 원문을 다시 읽는다. 경계값 처리(off-by-one)가 인용 정확도에 직결된다.

### 9-2 : Corrective / Agentic RAG
- **핵심 개념**:
  - 한 번 검색하고 끝내지 않고, **결과를 보고 다음 동작**을 정한다. 반복 구조만 만든다고 해결되지 않는다 — **언제 다시 찾고 언제 멈추는지**가 핵심.
  - 비슷한 이름, 다른 범위:
    | 접근 | 추가하는 판단 | 이 수업의 범위 |
    |---|---|---|
    | 기본 RAG | 정해진 검색 후 생성 | 6장의 한 번 검색 흐름 |
    | Agentic RAG | 다음 질의 · 도구 · 종료 선택 | 최대 두 번의 사내 자료 검색 |
    | CRAG | 검색 결과 품질 평가 후 보정 | 근거 검토 후 재검색하는 발상 (논문은 외부 검색으로 보완) |
    | Self-RAG | 검색 필요성 · 생성 내용을 모델이 비평 | 학습된 비평 토큰 — 일반 LLM에 "검토해"라고 시키는 것과 다름 |
  - **실제 두 번 검색**: 1차 원질문 "교육비 정산 증빙은 무엇인가요?" → `[]` / 2차 "교육비 지원 수강 완료 후 제출합니다"(수업용 변형) → education@60 · education@0 · retention@120. education@60에 **수료증과 영수증.** retention도 들어왔으니 **결과가 있다고 전부 쓰지 않는다.**
  - 7-4는 여러 표현을 **한꺼번에** 검색했고, 9-2는 **결과를 보고** 다음 검색을 할지 정한다.
  - **`search_loop` 세 종료 이유**: `candidates_ready`(검토할 후보가 생김, 정답 확정 아님) / `repeated_query`(`seen`으로 같은 질의 반복 방지) / `search_limit`(`max_searches` 도달).
  - education@0은 제목 검사('교육비')를 통과하지만 증빙 문장이 없다 → **잘못된 통과 조건의 예.**
  - **선택 (agent.py)**: 모델이 `action`(answer / rewrite / abstain) · `reason` · `next_query` · `evidence_quotes` JSON 반환. answer여도 **인용이 실제 Context에 없으면 차단.** gemma3 1회 기록: 빈 검색 결과인데 **answer, 인용 `[]`** → 인용 검사에서 중단 → "현재 자료에서 답을 확인하지 못했습니다."
- **퀴즈 9-2** (교안 정답): `max_searches=2` → same `('repeated_query', 1, [])`, changed `('candidates_ready', 2, [60, 0])`.
  - 생각해 보기 (Claude가 교안 코드로 확인): `max_searches=1`이면 `queries[:1]`로 원질문만 검색 → 빈 결과 → 루프 종료 → **`search_limit`.** 변형까지 못 간다.
- **QA 체크포인트**:
  - **종료 조건 테스트** — 반복 로직은 성공 경로보다 **멈추는 경로**(반복 질의, 횟수 초과)를 먼저 확인한다. 무한 루프·과금 폭주를 막는 안전장치.
  - **상태 이름이 과장하지 않게** — `candidates_ready`는 "정답"이 아니라 "검토 후보 있음". 상태 이름을 정확히 붙여야 다음 단계가 잘못 믿지 않는다.
  - **모델 판단 뒤에는 코드 검사** — 모델이 answer를 골라도 인용 검사로 막는다. RAG 3일차 `validate_answer`·`bind_claim`과 같은 이중 안전장치.

### 9-3 : GraphRAG Local · Global · DRIFT
- **핵심 개념**:
  - 질문: "영수증을 내는 규정과 각 규정의 승인자는?" → education·meal·travel의 증빙을 모으고 **각각의 승인 조건**을 따로 읽어야 한다.
  - 기본 실행의 관계 8개는 **사람이 원문을 읽고 만든 주석**(자동 추출 아님) → NetworkX `DiGraph` **노드 10 · 간선 8.** 간선에 `relation`·`condition`·`source_document_id`·`source_url`을 같이 저장.
    | 규정 | 대상 | 관계 | 조건 |
    |---|---|---|---|
    | travel | 영수증 | 제출 | 숙박 정산 |
    | education | 영수증 · 수료증 | 제출 | 수강 완료 후 |
    | meal | 영수증 | 제출 | 출장 식비 정산 |
    | travel | 담당 임원 | 승인자 | 한도 초과 숙박 예약 전 서면 승인 |
    | education | 팀장 | 승인자 | 수강 전 |
    | leave | 팀장 | 승인자 | 휴가 시작 3영업일 전 |
    | vpn | 관리자 | 승인자 | VPN 계정 발급 |
    - 영수증과 수료증은 **다른 노드**, 팀장은 education과 leave가 **공유하는 노드.**
  - **간선 따라가기**: 방향 = 규정 → 제출물·승인자. 영수증으로 **들어오는** 노드 = `predecessors` → `['education', 'meal', 'travel']`. education → 팀장(수강 전), travel → 담당 임원(한도 초과 숙박 예약 전 서면 승인), meal → **승인자 규정 없음**(= 명시 안 됨, "승인 불필요"로 확대 금지).
  - **Microsoft GraphRAG**: 개체·관계를 **자동 추출**하고, 밀접한 묶음(커뮤니티)마다 **요약 보고서**를 만든다.
    | 방식 | 시작점과 사용하는 자료 | 질문 예 |
    |---|---|---|
    | Local | 질문 관련 개체, 주변 관계와 원문 | 교육비 신청과 증빙에는 어떤 절차가 연결되나 |
    | Global | 여러 커뮤니티 보고서를 종합 | 전체 규정에서 반복되는 비용 정산 원칙은 |
    | DRIFT | 관련 보고서로 시작 → 후속 질문 → Local 탐색 | 전체 흐름을 본 뒤 구체 절차를 더 확인 |
    - Local은 "모든 이웃 조회", DRIFT는 "단순 BFS(너비 우선 탐색)"가 **아니다.** 문서 10개라 원문 검색으로도 개요가 보인다 — 오늘은 방법을 익히는 것이지 **기본 검색보다 낫다는 비교가 아니다.**
  - **선택 실습**: 임베딩 = 로컬 E5, 관계 추출·보고서·답변 = LLM API. `check_setup.py`(API 없음): 문서 [10, 384] · 색인 false. 검수 기록: 엔티티 **69** · 관계 **62** · 보고서 **17** — 실행마다 달라진다. 답변의 금액·승인 조건은 **원문과 대조**하고, "한도 초과면 승인 필요"를 "한도 안이면 승인 불필요"로 **뒤집지 않는지** 본다.
- **퀴즈 9-3** (교안 정답): `sorted(graph.predecessors("팀장"))` → education **수강 전** / leave **휴가 시작 3영업일 전.** 같은 승인자라도 시점이 다르다 → 하나로 합치지 않는다. `successors('팀장')`은 `[]`(간선 방향: 규정 → 팀장).
  - 생각해 보기: 원문 근거 없이 `("meal", "팀장", "승인자", …)`를 추가하면, 그래프가 "식비도 팀장 승인이 필요하다"는 **원문에 없는 규정**을 사실처럼 답에 넣게 된다. 그래프는 원문보다 정확할 수 없다.
- **QA 체크포인트**:
  - **방향 있는 데이터의 조회 방향** — `predecessors`/`successors`를 바꾸면 빈 결과가 나온다. 빈 결과 ≠ 관계 없음 (RAG 3일차 "빈 필터 결과 ≠ 규정 없음"과 같은 함정).
  - **자동 추출 결과는 실행마다 다르다** — 엔티티 69개가 매번 같다는 보장이 없다. 색인 결과도 **테스트 대상 데이터**로 보고 원문과 대조한다.
  - **"명시 안 됨"과 "불필요"를 구분** — 검수 기록의 Local 답변은 식비에 대해 "별도의 사전 승인 조건이 **확인되지 않습니다**"라고 썼다. 이 표현이 "승인 불필요"로 바뀌지 않는지가 확인 포인트.

### 9-4 : Multimodal RAG와 ColPali
- **핵심 개념**:
  - PDF·이미지 규정은 **표의 행·열·각주**까지 읽어야 한다. 새 금액이나 규정은 추가하지 않고 travel·education 원문 그대로 사용.
  - **같은 "12만원"도 어느 행의 값인지**: travel 12만원 · 국내 출장 1박당 · 숙박 영수증 / education 30만원 · 분기 1회 1인당 · 수료증과 영수증. 숫자 목록만 뽑으면 어떤 규정의 값인지 모른다 → **원문 ID · 단위 · 출처**를 같이 저장. 정규식은 각 문서의 첫 "숫자+만원"만 읽는 예제(일반 표 파서 아님). 실제 표라면 행 제목·열 제목·통화 단위·페이지 위치·병합 셀·각주까지.
  - **계산은 계산, 승인 판단은 따로**: 120000 × 2박 = **240,000원**(산술 결과). ✗ 240000 + 300000 = 540,000원(다른 규정 예산을 합칠 근거 없음). 계산 전에 **적용 대상**부터 정한다.
  - **ColPali의 MaxSim**: score(Q, D) = Σᵢ maxⱼ qᵢᵀdⱼ. 페이지를 이미지로 읽고 **여러 벡터**로 표현(문서 하나를 벡터 하나로 만드는 E5와 다름). 2차원 수치 모형: A [1,0],[0,1] → 1 + 1 = **2.0**, B [0.71,0.71] → 0.7071 + 0.7071 = **1.4142.** 실제 ColPali 출력이 아니고, 2.0은 확률이 아니다.
  - `main.py`가 같은 원문으로 **PNG 두 장**(education.png, travel.png)을 생성 — OCR 결과나 외부 스크린샷이 아니라 모델 입력. ColPali(vidore/colpali-v1.3)는 **검색 모델**이고 답변 생성은 별도. 교안도 모델 추론은 **미검증.**
- **퀴즈 9-4** (교안 정답): `r["document_id"] == "travel"` → `120000 travel https://example.invalid/rag40/travel`. education(300000)을 고르면 다른 규정의 금액. 답에는 1박당 · 숙박 영수증까지 함께.
- **QA 체크포인트**:
  - **숫자에는 단위와 출처가 붙어 다녀야 한다** — 값만 있는 숫자는 다른 행과 섞인다. 데이터 검증에서 "값 + 단위 + 출처"를 한 세트로 확인.
  - **산술 결과 ≠ 판정 결과** — 24만원은 한도 계산일 뿐, 영수증·사전 승인 조건까지 만족했는지는 별도 판정. 게임 QA에서 "수치 계산이 맞다"와 "보상 지급 조건이 맞다"를 따로 검증하던 것과 같다.
  - **입력 이미지 자체를 확인** — PNG에 12만원·1박당·숙박 영수증·한도 초과 승인 문장이 **잘리지 않았는지** 직접 본다. 모델 입력이 깨지면 뒤 단계는 모두 의미가 없다.

## 정리 — RAG 과목 마무리: 질문 하나를 끝까지 따라가기

- 수집·정리 → **출처 남긴 청크·임베딩** → 검색 → **Context** → 답변 → **평가 기록**
- 실습을 설명할 땐 **질문 하나**를 골라 단계마다 **실제 데이터**를 보여 준다. 그러면 잘못된 답이 **어느 단계에서 생겼는지** 찾을 수 있다.
- 어느 확장이든 **같은 평가 질문(8장)** 으로 전후를 비교한다.
- 수업 후 해 볼 것: `ch09/rag_ch09_01`에서 `uv run compare_contexts.py`(Ollama로 짧은 추출문 vs Parent 전체 답 비교), 질문 하나를 골라 원문 → 평가까지 한 장 정리.
