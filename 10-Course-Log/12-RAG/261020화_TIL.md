## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | Chunk / 청킹 | — | 검색·임베딩에 쓸 문서의 작은 조각 / 문서를 조각내는 일 |
  | Overlap | — | 앞 조각 끝과 다음 조각 시작에 반복되는 범위 |
  | Truncation | — | 입력 한도를 넘는 부분을 **조용히 잘라 내는** 동작 |
  | E5 | EmbEddings from bidirEctional Encoder rEpresentations | 이번에 쓴 임베딩 모델 계열 (`intfloat/multilingual-e5-small`, 384차원) |
  | Embedding | — | 문장을 숫자 벡터로 바꾼 것. 비슷한 뜻이면 가까운 방향 |
  | Pooling | — | 토큰마다 나온 벡터 여러 개를 문장 벡터 하나로 모으는 일 |
  | Dense Retrieval | — | 임베딩 벡터의 유사도로 찾는 검색 (어제 BM25는 단어 일치 기반 Sparse 검색) |
  | Cosine Similarity | 코사인 유사도 | 두 벡터의 **방향**이 얼마나 같은지 (1 같음, 0 직각, −1 반대) |
  | Top-k | — | 점수 상위 **최대** k개 |
  | Threshold | — | 결과에 남길 점수의 **하한** |
  | Golden set / dev | Golden dataset / development set | 정답을 미리 정해 둔 평가 질문 묶음 / 그중 개발·조정용 |
  | Hit@k | — | 상위 k개에 정답 문서가 **하나라도** 있으면 1 |
  | Recall@k | — | 필요한 정답 문서 중 상위 k개에서 **찾은 비율** |
  | Qdrant | (제품 이름) | 벡터와 metadata를 함께 저장·검색하는 Vector Store — 5장 예고 |

- **핵심 통찰: 청킹이 검색의 "상한선"을 정한다**
  - 어제 80/20 고정 길이에서 "서면 / 승인"이 두 청크로 갈라진 문제를 오전 내내 따라갔다.

    | 설정 | travel 청크 | 저장 문자 | ① 한도 | ② 영수증 | ③ 승인 |
    |---|---|---|---|---|---|
    | 80 / 0 | 2 | 148 | ✓ | ✓ | ✗ |
    | 80 / 20 | 3 | 188 | ✓ | ✓ | ✗ |
    | 100 / 20 | 2 | 168 | ✓ | ✓ | ✓ |

  - 겹침 20자를 줘도 승인 문장([54:92])을 통째로 담은 청크는 **하나도 없었다.** 근거 문장이 어느 청크에도 온전히 없으면, 뒤에서 아무리 좋은 임베딩 모델을 써도 그 조건은 한 청크로 찾아지지 않는다.
  - 그래도 수업은 **80/20을 공통 기준선**으로 저장했다 — 최적이라서가 아니라 4~8장에서 임베딩·검색·평가를 **같은 청크로 비교**하기 위해서. 끊긴 승인 문장은 9장(Parent-Child)에서 다시 쓸 **평가 사례로 남겨 둔다.**

- **두 번째 통찰: "점수가 높다 ≠ 답이 있다"**
  - "회사의 올해 매출 목표는?"처럼 **답이 없는 질문에도** 결과는 나온다 (연차 규정 0.7986). 검색은 상대적으로 가장 가까운 후보를 돌려줄 뿐, 답이 있는지는 판정하지 않는다.
  - **0.7986 ≠ 정답 확률 79.86%** — 2차 Review의 "confidence ≠ 정답 확률"이 임베딩 점수에서 또 나왔다.
  - q05(숙박 한도와 증빙)에서 2위 meal:0(0.8750)은 점수가 높지만 **식비 1일 3만원** — 숙박 질문의 답이 아니다. 금액과 적용 단위(1박당 / 1일)는 **본문을 읽어야** 구별된다.

- **세 번째 통찰: 비교 실험은 "하나만 바꾸고 나머지는 고정"**
  - 3-2: 어디서 자를지(경계) / 무엇으로 셀지(문자 vs 토큰)를 **하나씩** 바꿨다.
  - 3-4: 알고리즘·원문·근거 문장은 고정, **size와 overlap만** 바꿨다.
  - 4-3: 청킹은 고정, **k와 threshold만** 바꿨다.
  - 4-4: 코퍼스·청크·필터·입력 형식·k·질문은 고정, **모델만** 바꿨다.
  - 07 과정 6-1강 통제 실험, 10/2 Python 실습 A/B 비교, 2차 Review 08 비교가 오늘 네 번 반복됐다. **무엇 때문에 결과가 달라졌는지 말할 수 있는 실험**만 의미가 있다.

- **네 번째 통찰: 평균 1.0 뒤에 숨은 질문별 차이를 읽어야 한다**
  - E5 small과 base 모두 dev 12개에서 **Hit@3 = 1.0, Recall@3 = 1.0**. 평균으로는 차이가 없다.
  - 그런데 퀴즈 4-4에서 질문별로 맞대 보니 **q04, q09, q10, q11, q12 — 5개 질문의 검색 문서가 달랐다.** 이 부분은 🧭 9번에 Claude가 짚어준 확인 포인트로 정리했다.

- **향후 계획 및 다짐**
  - 러브코드에서 본인 역할이 **모델 평가·비교 실험**이라, 오늘 4-4의 기준선 저장 방식(모델 ID·차원·k·입력 형식·질문별 결과·Hit·Recall·처리 시간)을 그대로 비교 실험 기록 양식으로 가져갈 수 있다.
  - 비교할 때마다 **고정한 조건 표**를 먼저 쓰고, 평균 지표와 함께 **질문별 결과가 달라진 사례**를 원문으로 대조하는 습관.
  - 내일은 5장 — `vectors.npy`를 통째로 읽던 방식을 Vector Store(Qdrant)로 옮긴다.

## 📊 어제보다 나아진 점

- 어제는 RAG 흐름과 문서 준비(로딩·Metadata·정제·JSONL)였고, 오늘은 그 문서를 **청크로 나누고 → 벡터로 바꾸고 → 점수로 찾고 → 기준선으로 남기는** Indexing·Query의 중간을 채웠다.
- 슬라이드 78장 중 오후 4장은 벡터·내적·코사인처럼 수학이 섞여 있어서, Claude에게 **2차원 손계산 예시(q=[3,4], d₁=[6,8] …)를 한 줄씩 풀어 설명**해 달라고 했다. "정규화하면 내적 = 코사인"이 왜 그런지 숫자로 따라가니 이해가 됐다.
- 어제처럼 약어·용어를 먼저 표로 정리하고 들어갔다. 특히 **Hit@k와 Recall@k의 차이**(하나라도 vs 비율)를 미리 구분해 두니 4-4가 덜 헷갈렸다. ★
- 아직 코드를 직접 짜지는 못하지만, 오늘은 **"설정값과 실제 결과가 같은가"** 를 확인하는 시선을 연습했다 — overlap=20인데 실제 겹침 0, chunk_size=50인데 최종 51토큰 같은 사례들.

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 설정값 ≠ 실제 동작 — 결과를 읽어서 확인한다

| 설정 | 기대 | 실제 | 근거 교안 |
|---|---|---|---|
| Recursive `chunk_overlap=20` | 청크끼리 20자 겹침 | **겹침 0** (넘길 조각이 20자 이하가 아니라서) | 3-2 |
| Token `chunk_size=50` | 최대 50토큰 | 최종 입력 **51토큰** (분할 때는 `passage:` 접두사·특수 토큰이 빠짐) | 3-2 |
| `threshold=None` | 아무것도 안 거름 | 점수 하한만 생략. **현행 필터와 k는 그대로** | 4-3 |
| `k=5` | 5개 반환 | 하한 통과 후보가 2개면 **2개** | 4-3 |
| 벡터 생성 성공 | 입력 전체 반영 | 512토큰 넘으면 **조용히 잘림** | 3-2, 4-1 |

→ 교안 문장 그대로 — **설정값만 믿지 말고 결과를 읽어 확인한다.** overlap은 목표값이고, 실행 성공은 입력 전체 처리를 뜻하지 않는다.

### 2. 조용히 일어나는 결함 — 에러 없이 품질만 떨어진다

| 결함 | 왜 조용한가 | 잡는 방법 | 근거 교안 |
|---|---|---|---|
| Truncation | 한도를 넘으면 오류 없이 잘림 (79토큰 → 30토큰, "서면 승인" 조건 사라짐) | 최종 입력 조립 방식 그대로 Tokenizer로 **미리 재기** | 3-2 |
| 청크 순서 ↔ 벡터 행 불일치 | `vectors[7]`이 다른 원문을 가리켜도 계산은 됨 | `chunk_fingerprint` 비교 → 다르면 "다시 임베딩하세요" | 4-1 |
| 접두사 중복 | 원문 text에 `passage:`를 저장하면 다시 임베딩할 때 두 번 붙음 | 접두사는 **모델에 넣을 때만** | 4-1 |
| 패딩까지 평균 | [99, 99]에 끌려가 [34.33, 33.67] | mask로 패딩 제외, 분모도 `mask.sum()` | 4-1 |
| 다른 모델 벡터 섞기 | small 384차원 문서 + base 768차원 질문 | 모델이 바뀌면 문서도 다시 임베딩 | 4-4 |
| metadata 제목 미반영 | 저장만 하고 임베딩 입력에 안 넣으면 제목은 검색에 안 쓰임 | `embedding_text = 제목 + \n + 본문`을 따로 | 3-3 |

### 3. 청크 품질은 "길이"가 아니라 "근거 보존"으로 본다

- 3-2: 고정 분할은 최대 45토큰으로 **더 작지만** "서면 승인" 조건을 끊었다. Token 분할은 51토큰이지만 금액·영수증·초과 승인 3문장을 한 조각에 담았다. **작은 청크 = 좋은 청크가 아니다.**
- 3-4의 근거 보존 검사: `any(phrase in c["text"] for c in selected)` — 근거 문장이 **한 청크 안에 통째로** 있는지.

  | 관찰값 | 확인하는 것 | 확인하지 못하는 것 |
  |---|---|---|
  | 청크 수 | 검색 단위 개수 | 질문과의 관련성 |
  | 본문 문자 합계 | 중복 포함 텍스트 양 | 벡터·인덱스 전체 저장 용량 |
  | 문장 전체 포함 (True) | 한 청크의 조건 보존 | **실제 검색·생성 성공** |

- False여도 인접 청크를 함께 가져오면 이어 읽을 수 있고, True여도 그 청크가 검색되지 않으면 답에 못 쓴다. **각 지표가 무엇을 보장하고 무엇을 보장하지 않는지** 표로 정리해 두는 습관.

### 4. 구조를 지키는 청킹 — 서로 다른 규정이 섞이지 않게

- 글자 수로만 자르면 **교육비 마지막 조건 + 재택근무 첫 조건**이 한 청크에 섞일 수 있다.
- `MarkdownHeaderTextSplitter`로 `##` 제목 단위로 먼저 나누고 → 절 안에서만 Recursive → **overlap도 절 안에서만** 적용.
- splitter는 제목만 `section`으로 준다. **원문 ID·status·source_url은 우리가 다시 연결**해야 한다 (`by_title`로 원문을 찾아 `metadata.update`).
- 표는 **값만 떼면** "30만원"이 무슨 항목인지 모른다 → 행마다 열 이름을 붙인다. 목록의 "위 항목은 제외" 같은 예외는 **가리키는 대상과 같은 청크**에 두거나 검색 후 범위를 넓힌다.
- "개인 취미 강좌는 규정되어 있지 않다" 같은 **예외·미규정 문장도 청크 본문에 남긴다** — 보류 판단의 근거가 되기 때문.

### 5. 점수 해석 — 순위일 뿐 답의 존재가 아니다

| 상황 | 점수 | 실제 |
|---|---|---|
| q05 1위 travel:0 | 0.8945 | 숙박 12만원 + 영수증 → 답 |
| q05 2위 meal:0 | 0.8750 | 식비 1일 3만원 → **숙박 질문의 답 아님** |
| 매출 목표 질문 1위 leave:0 | 0.7986 | 연차 규정 → **답 없음** |

- 정규화된 벡터끼리는 **내적 = 코사인**. 방향만 비교하고 길이 영향은 사라진다 ([3,0]은 [1,0]보다 3배 길어도 코사인 1.0으로 1위).
- 유사도(클수록 가까움)와 거리 = 1 − 유사도(작을수록 가까움)는 **정렬 방향이 반대**. 라이브러리가 어느 쪽을 돌려주는지 확인한다.
- 동점은 `chunk_id` 순서로 고정 → 여러 번 실행해도 같은 결과(결정성).

### 6. k와 Threshold — 줄이면 깔끔해지지만 근거가 빠진다

| 조정 | q06 결과 | 교훈 |
|---|---|---|
| k=1 → 2 | 문서 Recall 둘 다 0.5인데 **읽을 수 있는 정보는 다름** (k=2에 식비 금액 추가) | 문서 단위 지표가 청크 단위 정보 차이를 숨긴다 |
| k=3 | 식비·숙박비·합산 여부 **세 항목 완성**, 215자 | — |
| k=5 | 새 금액 없이 사전 승인 조건만 추가, 323자 | k를 늘리면 입력만 길어질 수 있다 |
| threshold 0.88 | travel:0(0.8768) 탈락 → **숙박비 금액 누락** | 결과가 줄었다고 검색이 좋아진 게 아니다 |

- 순서: **현행 필터 → 점수순 정렬 → 하한 → 앞에서 k개.**
- 0.80·0.84·0.88은 **이 모델·이 자료의 비교값**일 뿐 다른 모델에 그대로 쓰면 안 된다.
- k를 늘릴 땐 "추가된 청크가 **질문의 어떤 항목**을 해결하는가"를 본다.

### 7. 평가 지표 — 무엇을 재고 무엇을 안 재는지

| 지표 | 계산 | 재지 않는 것 |
|---|---|---|
| Hit@k | 정답 문서가 하나라도 있으면 1 | 정답 문서가 여러 개일 때 몇 개를 찾았는지 |
| Recall@k (문서) | 찾은 정답 문서 / 필요한 정답 문서 | 그 문서의 **모든 조건(청크)** 이 들어왔는지, 관련 없는 후보 비율 |
| 둘 다 | 검색만 평가 | 생성 답변의 정확도, 보류 판단 |

- 같은 문서의 청크 여러 개는 **문서 하나**로 센다.
- 정답이 빈 질문(q11 매출 목표, q12 취미 강좌)은 Recall 분모가 0 → **평균에서 분리**한다.
- `reference`(정답 문장)는 **채점용**이고 생성 모델에 넘기지 않는다 (2차 Review 08의 "평가 기준은 프롬프트에 넣지 않는다"와 같음).
- dev 12개로 조정하고 **test 8개는 보관** — 2차 Review의 validation/test 분리, 10/2 실습의 개발/최종 분리와 같은 원칙.

### 8. 재현성 기록 — 같은 조건으로 다시 돌릴 수 있게

| 기록 | 왜 | 근거 교안 |
|---|---|---|
| `chunk_id = 문서ID:본문해시12:size:overlap:start` | 원문·설정이 바뀌면 ID도 바뀜 | 3-4 |
| `embedding_config.json` (model_id, dimension, normalized, input_format, chunk_fingerprint) | 벡터가 어떤 조건으로 만들어졌는지 | 4-1 |
| `dense_baseline.json` (모델·차원·k·입력 형식·질문별 문서 ID·Hit·Recall·처리 시간) | 다음 모델·설정과 같은 조건으로 비교 | 4-4 |
| 대안 설정은 `chunks_candidate.json`에 따로 | 수업 공통 `chunks.json`과 섞지 않기 | 3-4 |

→ 청크가 바뀌면 **그 뒤의 벡터와 색인도 모두 다시** 만들어야 한다. 앞 단계 산출물이 바뀌었는데 뒤 단계를 그대로 쓰면 행 번호가 엉뚱한 원문을 가리킨다.

### 9. Claude가 짚어준 확인 포인트

**① 평균 1.0이 세 번째로 나왔다 — 이번엔 5개 질문의 결과가 달랐는데도**
- 2차 Review에서 기준 모델과 BERT가 validation 1.0, test 0.9722로 **완전히 같았던** 천장 효과(평가셋이 너무 쉬워 차이를 못 가리는 현상)가 오늘 E5 small vs base에서도 반복됐다 — 둘 다 Hit@3·Recall@3 = 1.0.
- 그런데 이번엔 다르다. 퀴즈 4-4 결과로 보면 **dev 12개 중 5개(q04, q09, q10, q11, q12)에서 검색된 문서 목록이 달랐다.** 그중 q11·q12는 답이 없는 질문이라 Recall 평균에서 빠지고, 나머지도 정답 문서만 포함되면 1.0이 된다.
- 즉 지금 지표는 **"정답 문서가 들어왔는가"만** 재고, "관련 없는 문서가 얼마나 섞였는가", "답 없는 질문에서 무엇을 끌어오는가"는 재지 않는다. 러브코드 모델 비교에서도 평균 지표가 같으면 **질문별로 결과가 달라진 사례부터** 원문 대조하는 게 실제 차이를 찾는 방법이다.

**② 문서 Recall 1.0인데 정작 승인 조건은 어느 청크에도 온전히 없을 수 있다 — 오전과 오후가 이어지는 지점**
- 오전 3-4: 80/20에서 승인 문장("한도 초과 숙박은 예약 전에 담당 임원의 서면 승인을 받아야 합니다")은 **어느 청크에도 통째로 없다.**
- 오후 4-4: 기준선은 바로 그 80/20 청크로 만들었고, travel 문서가 검색되면 문서 Recall은 1.0이다.
- 그래서 "초과 숙박은 어떻게 승인받나요?" 같은 질문은 **문서 Recall 1.0이 나와도 근거 문장이 반으로 잘린 청크만** 모델에 들어갈 수 있다. 4-4 지표는 검색만 평가하고 "모든 조건이 Context에 들어갔는지"는 따로 확인하라고 교안도 적어 두었다 — 오전의 근거 보존 검사(문장 단위)와 오후의 Recall(문서 단위)을 **함께 봐야** 이 구멍이 보인다.

**③ E5 점수는 좁은 구간에 몰려 있어서, 하한값이 아주 예민하다**
- 오늘 나온 코사인 점수가 거의 다 **0.78 ~ 0.92 사이**다 — 답 있는 q06 상위 5개가 0.86 ~ 0.91, 답 없는 매출 목표 질문 상위 3개가 0.78 ~ 0.80.
- 그래서 하한을 0.84 → 0.88로 **0.04만 올려도** 숙박비 근거(0.8768)가 사라졌다. 0과 1 사이를 넓게 쓰는 점수가 아니라서, "0.8이면 꽤 높다" 같은 감으로 하한을 정하면 위험하다.
- 교안도 두 질문만으로 0.80에서 갈리는 건 **우연일 수 있다**고 했다. 하한은 반드시 dev 질문 여러 개(답 있음·답 없음 섞어서)로 놓치는 근거와 걸러지는 오답을 함께 세어 정해야 한다.

## 3장. 청킹 전략과 비교 실험 (오전)

### 3-1 : Chunk Size와 Overlap
- **핵심 개념**:
  - 문서를 통째로 검색 단위로 쓰면 질문과 **관련 없는 문장까지** 모델 입력에 들어간다 → 작은 조각(청크)으로 나눈다 = **청킹**. 그러면 **조각의 경계**가 중요해진다.
  - travel 148자를 80자씩 자르면 `[0:80]`이 **"서면"에서 끝나고** `[80:148]`이 "승인을 받아야 합니다"로 시작한다. 앞 조각만 검색되면 무엇을 받아야 하는지, 뒤 조각만 검색되면 무엇에 대한 승인인지 모른다.
  - **겹침(Overlap)** — 다음 조각의 시작을 앞으로 당겨 경계 근처를 두 조각에 함께 넣는다.
    | 값 | 의미 | 이번 설정 |
    |---|---|---|
    | size | 한 조각의 최대 문자 수 | 80 |
    | overlap | 인접 조각이 공유할 문자 수 | 20 |
    | size − overlap | 시작 위치 이동 간격 | 60 |
    → 시작 위치 0, 60, 120 → `[0:80]`, `[60:140]`, `[120:148]`. `[60:80]` 20자가 두 청크에 함께.
  - `windows(text, size, overlap)` — `range(0, len(text), size - overlap)`, `end = min(start + size, len(text))`, 끝에 닿으면 `break`. 결과에 **`(start, end, piece)`** 를 함께 담아야 나중에 원문 위치를 찾는다.
  - 문자 수만 보고 자르니 **단어 중간**에서도 끊긴다("정" / "니다."). 20자를 겹쳐도 두 번째 조각은 "숙박은"부터라 **"한도 초과"가 빠진다** — 겹침이 만능은 아니다.
  - **저장량**: 80/0 → 148자, 80/20 → 188자(+40), 100/20 → 168자(+20). 겹친 구간이 두 번 저장되기 때문. 문자 합계일 뿐 벡터·인덱스 크기는 아니다.
- **퀴즈 3-1** (교안 정답): `if not 0 <= overlap < size: raise ValueError(...)` → `return windows(text, size, overlap)`. 100/20 → `[0:100]`, `[80:148]` (승인 문장 전체가 첫 청크에), 80/80·80/−1 → ValueError.
- **QA 체크포인트**:
  - **`overlap >= size`면 이동 간격이 0 이하 → 무한 반복.** 실행 전에 막는 입력 검증이 경계값 테스트의 교과서 사례다 (80/80, 80/−1).
  - **검증과 분할의 역할 분리** — `checked_windows`는 검사만, 자르기는 `windows` 재사용. 테스트도 둘을 따로 할 수 있다.
  - **위치(start, end)를 함께 반환** — 나중에 "이 청크가 원문 어디였나"를 추적할 수 있어야 결함 위치를 찾는다. 1일차 `chunk_id`에 start를 넣은 이유와 같다.
  - **`len(text)`는 문자 수, 모델 한도는 토큰 수** — 3-2로 이어지는 단위 함정.

### 3-2 : Fixed / Recursive / Token 청킹
- **핵심 개념**:
  - 두 손잡이를 **하나씩** 바꾼다: **어디서 자를지**(문자 위치 vs 문장 경계) · **무엇으로 셀지**(문자 vs 토큰).
  - **Fixed 80/20** — 글자 수 위치에서 기계적으로 → "서면" / "정" / "니다."에서 끊김.
  - **Recursive 80/20** — `RecursiveCharacterTextSplitter(chunk_size=80, chunk_overlap=20, separators=[". ", " ", ""], keep_separator="end", strip_whitespace=False)`
    - 큰 구분자부터: `". "`(문장) → `" "`(단어) → `""`(문자). 앞 구분자로 나눠도 80자를 넘는 부분만 다음 구분자로.
    - 결과 3조각: ① 금액·영수증 ② 초과 승인·미승인 지출 ③ 범위 — **조각 하나만 읽어도 뜻이 통한다.**
    - 단, `". "` 기준은 이 샘플에서만 통하는 가정(소수점·약어·목록 주의).
    - **`chunk_overlap=20`인데 실제 겹침은 0.** 나눈 문장을 다시 합쳐 청크를 만들고, 겹침으로 넘길 조각이 20자 이하여야 하는데 이 샘플엔 없다. **overlap은 목표값이다.**
  - **모델 한도는 토큰** — E5 Tokenizer로 `"passage: " + text`를 세면 54자 → 32토큰, 70자 → 40토큰, 24자 → 17토큰. 문자÷토큰 비율이 1.69·1.75·1.41로 **청크마다 달라서** "한글 몇 글자 = 몇 토큰" 고정 환산식은 쓰기 어렵다.
  - **Token 청킹** — `from_huggingface_tokenizer(tokenizer, chunk_size=50, chunk_overlap=10, …)`: 분할 방식은 그대로, **길이 함수만 Tokenizer로.** 결과 2조각 51토큰 / 33토큰.
    - 설정 50인데 51 → 분할할 때는 `passage:` 접두사·특수 토큰이 빠져 있었다. **최종 입력 조립 방식 그대로 다시 재야** 한다.
    - "토큰 50이 문자 80보다 작으니 더 잘게"가 아니다. 단위가 달라서 크기를 비교하면 안 된다 — 토큰 50 조각이 문자 80 조각보다 **더 많은 문장**을 담았다.
  - **Truncation** — 실습용 30토큰 제한: 전체 79토큰 중 49토큰이 **오류 없이 잘려** 모델에 전달 안 됨. 디코딩해 보면 "예약 전 서면 승인" 조건이 사라짐.
    - 두 방식 구분: 최종 입력 길이를 먼저 재서 **미리 나누기** vs 그대로 넣고 **초과분 잘라내기**.
    - E5와 생성 모델은 Tokenizer·한도가 달라 모델마다 따로 계산.
- **퀴즈 3-2** (교안 정답): `{"text": text, "chars": len(text), "input_tokens": len(tokenizer("passage: " + text)["input_ids"])}`. recursive (54자, 32토큰)·(70, 40)·(24, 17), fixed 최대 45토큰, token 분할 최대 51토큰.
- **QA 체크포인트**:
  - **"한 번에 하나만 바꾼다"** — 경계와 길이 단위를 동시에 바꾸면 결과가 달라진 원인을 모른다. 통제 실험의 기본.
  - **Truncation은 가장 위험한 조용한 결함** — 실행은 성공하고 벡터도 나오는데 입력 일부가 반영 안 됐다. "실행 성공 ≠ 입력 전체 처리". 테스트로는 한도 근처·초과 입력을 넣고 **디코딩해서 무엇이 남았는지** 확인한다.
  - **측정은 실제 사용 조건 그대로** — 접두사·특수 토큰까지 붙인 최종 입력으로 재야 한다. 분할기가 잰 길이와 모델이 받는 길이가 다르다.
  - **길이 지표만으로 청크 품질을 판단하지 않는다** — 고정 분할은 토큰이 더 작았지만 조건을 끊었다. 품질 기준은 "근거가 온전한가".
  - **`". "` 같은 구분자 가정은 샘플 의존** — 소수점("1.5")·약어가 들어간 문서에서 깨질 수 있다. 다른 형식의 문서로 회귀 확인이 필요하다.

### 3-3 : 한국어 / 문서 구조 기반 청킹
- **핵심 개념**:
  - education(교육비) + remote(재택근무)를 `##` 제목을 붙여 한 문자열로 — 실무의 "여러 규정이 한 파일". 글자 수로 아무 데서나 자르면 **교육비 마지막 조건 + 재택근무 첫 조건**이 한 청크에 섞인다.
  - **`MarkdownHeaderTextSplitter(headers_to_split_on=[("##", "section")])`** — `##` 제목 → `metadata["section"]`, 본문에서는 제목 줄 제거(`strip_headers` 기본).
  - splitter는 **제목만** 알려 준다 → `by_title`로 원문을 찾아 `sec.metadata.update(orig["metadata"])` + `document_id` 복사. 이 샘플은 제목이 달라서 가능하고, **제목이 반복되면** 파일 ID·제목 경로가 필요하다.
  - **제목으로 나눈 뒤 긴 절만 다시** — 제목 분할만으로는 길이를 제한 못 해서 절마다 Recursive를 한 번 더(`split_documents` → metadata를 각 청크에 전달). 결과: education 3조각, remote 2조각, 모든 청크에 원문 ID. **overlap도 절 안에서만.**
  - **metadata의 제목은 임베딩에 자동으로 들어가지 않는다.** 임베딩 모델은 넘겨준 문자열만 벡터로 바꾼다.
    | 정보 | 저장 위치 | 효과 |
    |---|---|---|
    | 원문 제목 | metadata.title | 화면 표시와 원문 구분 |
    | 검색용 제목 + 본문 | 별도 `embedding_text` | 임베딩이 제목 표현도 처리 |
    | 원문 ID, URL | metadata | 청크에서 원문으로 연결 |
    | 예외·미규정 문장 | 청크 본문 | 답변 범위와 조건 판단 |
  - **표와 목록** (교안 5절, 설명만): 표는 값만 떼면 "30만원 | 분기 1회 | 수료증"이 무슨 항목인지 모름 → "항목: 교육비 · 한도: 30만원 · 주기: 분기 1회 · 증빙: 수료증"처럼 행마다 열 이름을 붙인다. 번호 목록의 "위 항목은 제외" 같은 예외는 가리키는 대상과 같은 청크에. 표·이미지 직접 처리는 9장 4강(Multimodal RAG).
  - Semantic Chunking(유사도 계산으로 나누기)과 달리 **이미 있는 제목 구조**를 쓴다.
- **퀴즈 3-3** (교안 정답): `f"[{piece.metadata['document_id']}] {piece.metadata['title']}\n{piece.page_content}"`. 첫 줄 `[remote] 재택근무 운영`, 원래 `metadata`와 `page_content`는 수정하지 않음.
- **QA 체크포인트**:
  - **경계를 넘는 섞임 = 데이터 오염** — 서로 다른 규정이 한 청크에 섞이면 검색은 되는데 답변이 두 규정을 뒤섞는다. 구조 경계를 먼저 지키는 게 예방.
  - **도구가 주는 것과 우리가 채워야 하는 것을 구분** — splitter는 section만, 원문 ID·status·URL은 직접 연결. 빠뜨리면 청크에서 원문으로 못 돌아가고, status 필터도 동작하지 않는다.
  - **제목 매칭(`by_title`)은 제목이 고유할 때만 안전** — 같은 제목이 두 문서에 있으면 엉뚱한 원문 metadata가 붙는다. 경계 조건 테스트 대상.
  - **"저장했다 ≠ 검색에 쓰인다"** — metadata에 제목이 있어도 임베딩 입력에 없으면 검색에 영향 없다. 데이터가 어느 단계에서 실제로 쓰이는지 추적해야 한다.
  - **미규정 문장 보존** — "규정되어 있지 않다"는 문장이 정제·청킹에서 빠지면, 모델이 근거 없이 "지원한다"고 답할 위험이 커진다.

### 3-4 : 청킹 전략 비교와 선택
- **핵심 개념**:
  - **비교 기준을 먼저 고정** — travel 첫 세 문장(숙박 한도 28자 · 영수증 24자 · 초과 승인 38자). 승인 문장이 **가장 길고 가장 뒤**라 경계에 걸리기 쉽다.
    | 고정한 입력 | 바꾼 설정 | 관찰 | 저장 |
    |---|---|---|---|
    | 문서 12개 · 근거 문장 3개 | 80/0 · 80/20 · 100/20 | 근거 보존 True/False | 80/20 chunks.json |
  - 결과: 전체 청크 24 → 28 → 22, travel 저장 문자 148 → 188 → 168. 근거 보존은 80/0·80/20 `[✓, ✓, ✗]`, **100/20만 `[✓, ✓, ✓]`**.
  - 80/20에서 승인 문장 `[54:92]`은 청크 1(`0:80`, "서면"에서 잘림)과 청크 2(`60:140`, "숙박은"부터 → "한도 초과" 빠짐) 어디에도 통째로 없다.
  - 개선 후보: **크기 100**, **문장 경계 우선**, **검색 후 인접 청크 함께 가져오기**. 100/20이 이 세 문장엔 좋았지만 다른 규정·질문에서도 그런지는 추가 비교 필요.
  - **공통 기준 80/20으로 `chunks.json`(28개) 저장 — 최적값이 아니다.** 4~8장에서 같은 청크로 비교하려고 고정한 기준선이고, 끊긴 승인 문장은 9장(Parent-Child)에서 평가 사례로 쓴다.
  - `chunk_id` 예: `leave:5a1ba9d2dd70:80:20:0` (문서ID : 본문해시12 : size : overlap : start).
  - 대안 설정은 **`chunks_candidate.json`에 따로** 저장해 공통 `chunks.json`과 섞지 않는다.
  - `documents.jsonl`은 한 줄에 문서, `chunks.json`은 청크 목록 **하나의 JSON 배열**.
- **퀴즈 3-4** (교안 정답): `result.setdefault(c["document_id"], []).append((c["start"], c["end"]))`. travel → (0,80), (60,140), (120,148), 문서 12개 모두(구버전 travel-old 포함), 문서마다 마지막 end = 원문 길이.
- **QA 체크포인트**:
  - **기준선(baseline)을 "최적"과 구분해서 기록** — 80/20은 비교의 출발점일 뿐이라는 걸 명시해 두지 않으면, 나중에 누군가 "80/20이 검증된 최적값"으로 오해한다.
  - **알려진 결함을 지우지 않고 평가 사례로 남긴다** — 끊긴 승인 문장을 숨기지 않고 뒤 장에서 개선 효과를 재는 기준으로 쓴다. 게임 QA에서 알려진 이슈(Known Issue) 목록을 유지하는 것과 같다.
  - **공통 기준과 실험 후보 파일을 분리** — 실험 결과가 공통 기준을 덮어쓰면 그 뒤 모든 비교가 무너진다. 2차 Review의 "같은 실험 폴더면 덮어쓰지 않고 중단"과 같은 원칙.
  - **원본 범위 보관 ≠ 검색 필터** — `coverage_by_document`는 구버전까지 모든 문서의 구간을 모은다. status 필터는 **검색할 때** 따로 적용한다. 저장 단계에서 거르면 감사·비교용 원본이 사라진다.
  - **마지막 end = 원문 길이** 확인 — 원문 뒷부분이 청크에서 누락되지 않았는지 보는 커버리지 검사.

## 4장. 임베딩과 Dense Retrieval (오후)

### 4-1 : 텍스트 임베딩과 벡터 표현
- **핵심 개념**:
  - 문서 12개 → 80/20 청크 **28개** → 검색 단위가 청크라서 **벡터도 28개**(각 384차원).
  - 검색용 임베딩 모델은 관련 있는 문장 쌍은 가깝게, 관련 없는 문장은 멀게 학습돼 있다. 하지만 완벽하지 않아서 "비용"·"영수증"이 겹치는 식비 문서도 숙박 질문 가까이 올 수 있다 → **결과는 원문으로 확인.**
  - 벡터는 후보를 찾는 도구이고, 모델에 근거로 넘기는 건 **원래 본문**이다 → ID·위치를 유지.
  - **Pooling** — Transformer는 토큰마다 벡터(10토큰이면 (10, 384))를 내서 문장끼리 비교하려면 하나로 모아야 한다. 계산용 예: 토큰 [1,2], [3,0], 패딩 [99,99], mask [1,1,0] → 패딩 제외 평균 **[2, 1]**. 패딩까지 평균내면 [34.33, 33.67]로 99에 끌려가고, 분모도 3이 아니라 `mask.sum()` = 2여야 한다. 실제로는 SentenceTransformer가 모델에 설정된 pooling을 자동 적용.
  - **정규화** — 방향은 그대로, 길이만 1로. [2, 1]의 길이 √5 ≈ 2.236 → [0.8944, 0.4472]. **성분의 합이 1이 아니라 제곱의 합이 1**(0.8944 + 0.4472 = 1.34).
  - **E5 입력 접두사** — 문서는 `passage:`, 질문은 `query:`. E5가 역할 접두사를 붙이도록 학습됐다. 접두사는 **모델에 넣을 때만** 붙이고 원래 text에 저장하지 않는다(다시 임베딩하면 두 번 붙음).
  - 모델: `intfloat/multilingual-e5-small` — 384차원, 입력 한도 512토큰, CPU, API 키 불필요.
  - `encode(passages, normalize_embeddings=True)` → **(28, 384)**, 행마다 길이 [1.0, 1.0, 1.0]. **`vectors[i]`와 `chunks[i]`가 같은 청크** — 행 번호가 곧 청크 번호. 성분 하나를 "숙박"처럼 해석하지 않는다.
  - **384 ≠ 512** — 384는 출력 벡터 차원, 512는 입력 토큰 한도(접두사·특수 토큰 포함). 이번 28개 입력 최대 49토큰 → 한도 안. 청크를 30번 반복하면 1234토큰 → 잘릴 수 있음 → 다시 청킹.
  - **`vectors.npy` + `embedding_config.json`** (model_id · dimension · normalized · input_format · chunk_fingerprint). 다음 강의의 `load_vectors`가 지문을 비교해 다르면 "다시 임베딩하세요".
- **퀴즈 4-1** (교안 정답): `model.encode("query: " + question, normalize_embeddings=True)` → shape `(384,)`, 길이 1.0. 질문에 `passage:`를 붙여도 실행은 되지만, E5는 역할별 접두사로 학습됐으므로 질문은 `query:`.
- **QA 체크포인트**:
  - **행 번호 계약** — 청크 순서만 바꾸고 `vectors.npy`를 그대로 두면 계산은 되지만 **다른 원문**을 가리킨다. 조용히 틀리는 결함을 지문(fingerprint) 비교로 막는다. 2차 Review의 "라벨 순서가 뒤집혀도 예외 없이 지나간다"와 같은 유형.
  - **"실행됨 ≠ 올바름"** — `passage:`를 질문에 붙여도, 패딩까지 평균내도 에러 없이 숫자가 나온다. 결과가 그럴듯한지 손계산 예시로 대조할 수 있어야 한다.
  - **생성 조건을 결과와 함께 저장** — 벡터만 있고 어떤 모델·입력 형식으로 만들었는지 모르면, 다음 실험과 같은 조건인지 확인할 방법이 없다. 테스트 결과에 환경 정보를 붙이는 것과 같다.
  - **정규화 확인 = 사전 조건 검증** — 다음 강의의 "내적 = 코사인"은 정규화가 전제다. 길이가 1인지 먼저 확인하는 건 sanity check.

### 4-2 : 코사인 유사도와 Top-k 검색
- **핵심 개념**:
  - **2차원 손계산** — q = [3, 4]
    | 후보 | 벡터 | 내적 q·d | 길이 | 코사인 |
    |---|---|---|---|---|
    | d₁ (같은 방향) | [6, 8] | 50 | 10 | 50/(5×10) = **1** |
    | d₂ (직각) | [4, −3] | 0 | 5 | **0** |
    | d₃ (반대) | [−3, −4] | −25 | 5 | −25/(5×5) = **−1** |
    d₁은 두 배 길어서 내적 50이 컸지만 방향이 같으니 코사인은 1 — **길이 영향 제거.**
  - **정규화하면 내적 = 코사인** (분모 = 1×1) → `vectors @ query` 행렬 곱 한 번으로 28개 점수. (28, 384) @ (384,) → (28,). 안쪽 차원이 같아야 곱할 수 있다.
  - 실제 검색: 질문만 `query:`로 임베딩 → `scores = vectors @ query` → **`status == "current"` 행만** → **행 번호를** `(-score, chunk_id)`로 정렬. 점수 배열만 정렬하면 원문 연결이 끊긴다.
  - **q05 Top-4**: travel:0 0.8945(1박당 12만원 + 숙박 영수증 → 답) / meal:0 0.8750(1일 3만원 = 식비 → 숙박 답 아님) / meal:60 0.8444 / travel:60 0.8399.
  - **답이 없는 질문에도 결과가 나온다** — "회사의 올해 매출 목표는?" → leave:0 0.7986, leave:60 0.7982. **0.7986 ≠ 정답 확률 79.86%.** Threshold로 거를 수 있지만 그것만으론 부족 → 4-3, 6장 보류 처리.
  - **유사도 vs 거리** — 유사도는 클수록 가깝고(d₁ 1 → 1등), 거리(1 − 유사도)는 작을수록 가깝다(d₁ 0 → 1등). 정렬 방향이 반대.
- **퀴즈 4-2** (교안 정답): `lengths = np.linalg.norm(candidates, axis=1)`, `order = np.argsort(-scores)`. scores `[0.7071, 1.0, -1.0]`, order `[1, 0, 2]` — [3, 0]은 q보다 3배 길지만 같은 방향이라 1위.
- **QA 체크포인트**:
  - **점수는 순위이지 답의 존재가 아니다** — 답 없는 질문도 상위 결과가 나온다. 보류 판단은 별도 단계(6장)가 필요하다. 2차 Review의 "confidence ≠ 정답 확률"과 같은 함정.
  - **비슷한 점수, 다른 답** — q05에서 0.8945와 0.8750은 큰 차이가 아닌데 하나는 답, 하나는 오답. 금액·단위(1박당 / 1일) 같은 핵심 조건은 점수가 아니라 원문으로 판정한다.
  - **행 번호로 정렬** — 점수만 정렬하면 어떤 청크의 점수인지 잃는다. 인덱스와 값을 함께 다루는 건 데이터 처리의 기본 계약.
  - **동점은 chunk_id로 고정** — 여러 번 실행해도 같은 결과 = 회귀 테스트 가능.
  - **`axis=1`과 `-scores`** — 축 하나, 부호 하나 틀려도 에러 없이 엉뚱한 순위가 나온다. 손계산 예시로 대조하는 이유.

### 4-3 : Dense Retriever의 Top-k / Threshold
- **핵심 개념**:
  - **q06**: "출장 식비와 숙박비의 한도는 각각 얼마이고 두 한도를 합쳐 쓸 수 있나요?" → 필요한 청크 3개: 식비 금액(meal:0, 1일 3만원) · 숙박비 금액(travel:0, 1박당 12만원) · 합산 여부(meal:60, 남은 숙박비 한도를 식비에 합산하지 않음). "정답 문서를 찾았나"만 보면 **같은 문서 안에서 빠진 청크**를 못 알아챈다.
  - 검색 함수 순서: **현행 필터 → 점수순 정렬 → 하한(score ≥ threshold) → 앞에서 최대 k개.** `threshold=None`은 하한만 생략, k는 **최대** 개수.
  - **k를 늘리면** (q06 순위: meal:60 0.9134 → meal:0 0.8858 → travel:0 0.8768 → travel:120 0.8601 → travel:60 0.8557)
    | k | 찾은 문서 | Recall | 문자 |
    |---|---|---|---|
    | 1 | meal | 0.5 | 55 |
    | 2 | meal | 0.5 | 135 |
    | 3 | meal, travel | 1.0 | 215 |
    | 5 | meal, travel | 1.0 | 323 |
    k=1과 k=2는 **문서 Recall이 같아도 읽을 수 있는 정보가 다르다**(식비 금액 유무). k=5는 새 금액 없이 입력만 길어짐.
  - **하한을 높이면** (k=5 고정): None·0.80·0.84 → 5개 그대로 / **0.88 → 2개(meal만)**, travel:0(0.8768) 탈락 → 숙박비 금액 누락. **결과가 줄었다고 검색이 좋아진 게 아니다.**
  - **하한 하나로 "답 없음"을 가를 수 있나?** q06 상위 0.91·0.89·0.88 vs 매출 목표 0.80·0.80·0.78 — 이 두 질문만 보면 0.80으로 갈리지만 **항상 그렇다는 근거는 없다.** 용어가 겹치는 질문·일부만 답이 있는 질문은 답이 없어도 점수가 높을 수 있다.
  - 기록할 항목: 질문과 설정, 선택된 청크, 정답 근거 포함 여부, 길이, 빠진 사례.
- **퀴즈 4-3** (교안 정답): `exact_rows(q, chunks, vectors, model, k=k, threshold=threshold)`. "출장 숙박 비용 한도와 필요한 증빙은?" → (1, None) `[travel:0]`, (3, 0.88) `[travel:0]`, (3, 0.90) `[]` (모든 후보가 0.90 미만). travel:0에 한도와 영수증이 함께.
- **QA 체크포인트**:
  - **질문을 필요한 항목으로 쪼개서 평가** — q06을 식비·숙박비·합산 여부 3항목으로 나누니 "어느 항목이 빠졌는지"가 보인다. 테스트 케이스의 기대 결과를 **체크리스트로 쪼개는** 것과 같다.
  - **줄이는 설정의 부작용** — k를 줄이거나 하한을 높이면 노이즈는 줄지만 근거도 빠진다. 정밀도·재현율 trade-off를 **실제로 빠진 사례**로 확인한다.
  - **하한 0.90 → 결과 0개** — 모든 후보가 걸러지면 검색은 "아무것도 못 찾음"이 된다. 이것도 정상 동작이고, 이후 단계가 빈 결과를 보류로 처리하는지가 확인 대상.
  - **이 값들은 이 모델·이 자료 전용** — 다른 모델·데이터에 하한값을 그대로 옮기면 안 된다. 환경 의존 설정값은 함께 기록.
  - **두 질문으로 일반화하지 않는다** — 4-4에서 dev 12개로 넓히는 이유.

### 4-4 : 임베딩 모델 비교와 Dense 기준선
- **핵심 개념**:
  - **공정한 비교 — 모델만 바꾸고 나머지는 고정**
    | 고정할 항목 | 이번 실험의 값 |
    |---|---|
    | 코퍼스 | documents.json 12문서 |
    | 청크 | chunks.json 28개 (80/20) |
    | 검색 범위 | status = current |
    | 입력 | `passage:` + text / `query:` + question |
    | 검색 방식 | 정규화 벡터 코사인, k = 3 |
    | 평가 질문 | dev 12개 (test 8개는 보관) |
    바꾸는 것: E5 small(384차원, 기본) ↔ E5 base(768차원, 선택 비교). 모델마다 접두사·정규화 규칙이 다르면 공식 규칙을 따르고 차이를 기록.
  - **Golden dev 12개** = 답 있음 10 + 답 없음 2(q11 매출 목표, q12 취미 강좌).
  - **Hit@k vs 문서 Recall@k** — q06 정답 {meal, travel}에서 meal만 찾으면 Hit = 1(하나라도), Recall = 0.5(절반). 같은 문서의 청크 여러 개는 문서 하나로. 정답이 빈 질문은 Recall 분모 0 → **평균에서 분리**. `reference`(정답 문장)는 채점용이고 생성 모델에 넘기지 않는다.
  - **small 기준선 (k=3)**: 답 있는 10개 Hit 1.0 · Recall 1.0.
    - **q10**: 정답 education + 식비·숙박 문서도 함께 → Recall 1.0 ≠ 후보가 모두 관련.
    - **q12**: "취미 강좌는 규정 안 함" 문장 때문에 education이 상위 → 검색됐다고 **"지원한다"고 답하면 안 된다.** 확인 순서: 정답 문서 포함 → 어떤 조건 → 답변 생성 가능?
  - **`dense_baseline.json`**: 모델 ID·차원·k·입력 형식·질문별 문서 ID·Hit·Recall·질문 처리 시간.
  - **모델이 바뀌면 문서도 다시 임베딩** — small 384차원 벡터에 base 768차원 질문을 섞을 수 없다(차원도 의미 공간도 다름).
  - 교안 기록: small·base **모두 Hit 1.0 · Recall 1.0** → 이 질문 세트로는 차이를 못 가린다. **작은 모델로 만점이면 큰 모델의 비용을 정당화할 근거가 없다.** 최종은 test 질문으로.
  - `--compare-base`(선택, E5 base 추가 다운로드), `compare_api.py`(선택, `--execute` 없이는 호출하지 않고 계획만 보여 줌).
- **퀴즈 4-4** (교안 정답): small·base `rows`를 `question_id`로 묶고 `retrieved_document_ids`가 다른 질문만 `changed`에. 결과: **q04, q09, q10, q11, q12**. 두 모델 모두 Hit@3 = 1.0이라 평균으로는 구분 안 되고, 달라진 질문은 원문을 직접 대조.
- **QA 체크포인트**:
  - **통제 변수 표를 먼저 쓴다** — 무엇을 고정했는지 명시해야 결과 차이를 모델 탓이라고 말할 수 있다. 러브코드 비교 실험 문서의 첫 표로 그대로 쓸 수 있는 형식.
  - **평균에 가려진 차이를 질문별로 본다** — 퀴즈 4-4가 정확히 이걸 보여 준다 (🧭 9-①).
  - **"검색됨 ≠ 답할 수 있음"** — q12처럼 "규정 안 함" 문장이 검색되는 건 오히려 **보류 근거**다. 검색 지표 1.0이 생성 품질을 보장하지 않는다.
  - **비용 대비 근거** — 지표가 같으면 더 작고 빠른 모델이 합리적 선택. 2차 Review에서 BERT와 TF-IDF 점수가 같았을 때와 같은 판단.
  - **외부 API 비교는 `--execute` 없이는 계획만** — 비용이 드는 동작에 명시적 실행 스위치를 두는 설계. 10/2 실습의 `RUN_LIVE`와 같은 안전장치.
  - **test는 보관** — dev로 조정하고 test는 최종 확인용. 평가 데이터 누수 방지.
