## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 데이터 누수(leakage) — 평가를 무효로 만드는 세 가지 경로

오늘 하루에만 **누수를 막는 장치가 세 번** 나왔다.

| 누수 경로 | 어떻게 생기나 | 막는 방법 | 근거 교안 |
|---|---|---|---|
| 같은 상황이 train·validation에 나뉨 | 문장 단위로 무작위 분할 | `group_id`(상황) 단위로 분할, 교집합 0 검사 | 02 |
| validation까지 넣어 `fit` | TF-IDF 어휘·IDF에 평가 문장 통계가 들어감 | `fit`은 train만, validation은 `predict`만 | 03 |
| test를 미리 열어 봄 | 최종 평가용 데이터로 모델을 고름 | 오늘은 test를 **열지 않음**. 모델 선택은 validation으로 | 02, 04 |

→ 지난주 Python 프롬프트 실습(개발 6건 → 프롬프트 고정 → 최종 4건)과 같은 구조다. **고르는 데 쓴 데이터로 최종 점수를 매기지 않는다.**

### 2. 데이터 검사의 한계 — 통과 = 구조가 맞다는 뜻일 뿐

`check_splits`의 다섯 관문:

| 관문 | 확인 내용 |
|---|---|
| 필수 열 | 5개 키가 있고 비어 있지 않은가 |
| 라벨 표기 | `labels.json`과 같은가 |
| id 중복 | 분할 안에서 반복이 없는가 |
| 상황별 라벨 | 한 `group_id`에 정답이 하나인가 |
| 분할 간 중복 | 앞 분할과 겹치지 않는가 |

| 통과가 보장하는 것 | 통과해도 모르는 것 |
|---|---|
| 필수 값, 라벨 표기, 중복과 분할 조건 | **라벨의 의미가 옳은지**, 실제 서비스 품질 |
| 공백·표기만 다른 같은 문장 (NFKC 정규화) | **뜻만 비슷한 다른 문장** (정규화로 못 잡음) |

→ 환불 문의에 `shipping` 라벨이 붙어 있어도 검사는 통과한다. **자동 검사는 구조, 의미는 사람 검토**. 07 과정 7-1강 "JSON 문법 ≠ Schema 구조 ≠ 비즈니스 사실"이 학습 데이터에도 그대로 적용된다.

### 3. 결정적으로 확인할 수 있는 값 — 손으로 예상하고 실행해서 대조

교안은 모든 실습에서 **"실행 전에 출력을 먼저 적게"** 한다. 아래 값들은 매번 같아서 기대값으로 고정할 수 있다.

| 값 | 기대값 | 근거 교안 |
|---|---|---|
| train 행 수 / 상황 수 | 180 / 90 | 01, 02 |
| validation 행 수 / 상황 수 / 라벨별 | 36 / 18 / 12씩 | 02 |
| 누적 상황 수 (train 뒤 → validation 뒤) | 90 → 108 | 02 |
| TF-IDF 특징 수 | 17,329 | 03 |
| 기준 모델 가중치 수 | 51,990 (3 × 17,329 + 3) | 04 |
| 배치 크기 (앞 2문장) | `input_ids` [2, 32], `labels` [2] | 04 |
| 학습 전 loss | 약 1.34 | 04 |
| 갱신 횟수 | 45배치 → epoch당 12번 → 3 epoch 36번 | 04 |

→ 반대로 **BERT의 epoch별 F1은 장치에 따라 다르다** (RTX 5060 기준 lr2e5 1 epoch 0.7827, Mac MPS 0.8222). 이건 범위로 봐야 하는 값이다.

### 4. 라벨 순서 = 번호 계약

- 모델은 번호(0, 1, 2), 사람은 이름(shipping, refund, account)을 쓴다. 그 대응을 정하는 게 `labels.json`의 **순서**다.
- `read_labels`는 빈 목록이나 중복 이름이면 `ValueError`로 멈춘다 — 잘못된 번호 대응을 **읽는 시점에** 막는다.
- 학습할 때와 서비스할 때 라벨 순서가 다르면, 모델이 0을 내도 다른 이름으로 해석된다(퀴즈 1-2 ③). 그래서 `id2label` / `label2id`를 checkpoint `config.json`에 함께 저장한다.
- `confusion_matrix(..., labels=ids)`로 행·열 순서를 고정하고, `confusion_matrix_axes`(행 = 실제, 열 = 예측)까지 결과 파일에 저장한다. **축을 헷갈리면 precision과 recall이 뒤바뀐다.**

### 5. 지표 읽기 — accuracy와 macro F1을 같이 본다

| 지표 | 계산 | 읽는 위치 (혼동행렬) |
|---|---|---|
| accuracy | 대각선 합 ÷ 전체 | 대각선 |
| precision (refund) | TP ÷ **열** 합 | refund라고 예측한 것 중 맞은 비율 |
| recall (refund) | TP ÷ **행** 합 | 실제 refund 중 찾아낸 비율 |
| macro F1 | 라벨별 F1의 평균 | 라벨마다 따로 계산 후 평균 |

- 오류가 라벨마다 다르게 퍼지면 두 값이 달라진다 (6건 예시: accuracy 0.8333, macro F1 0.8222).
- `zero_division=0` — 어떤 라벨을 한 번도 예측하지 않으면 분모가 0. 오류 대신 0점 처리.
- `save_errors` — 틀린 문장만 CSV로 저장. 모두 맞히면 머리글만 남는다. **점수만이 아니라 틀린 사례를 남기는 것**은 지난주 `raw` 보관 원칙과 같다.

### 6. 모델 저장 규칙 — 언제 저장하고, 무엇을 남기나

- 저장 조건: validation macro F1이 **이전 최고점보다 높을 때(`>`)만**. train loss 감소만으로 마지막 모델을 고르지 않는다.
- 같은 최고점이 다시 나오면 덮어쓰지 않는다 → lr5e5는 2·3 epoch 둘 다 1.0이지만 **2 epoch 모델이 남는다**. `>=`로 바꾸면 3 epoch가 남는다(퀴즈 3-2).
- `epochs.jsonl`은 저장 여부와 관계없이 **매 epoch 기록**. 저장된 모델과 학습 기록을 분리해서 남긴다.
- 같은 실험 폴더(예: `lr2e5`)가 이미 있으면 **덮어쓰지 않고 중단**한다. 새 실험은 `RUN_NAME`을 바꾼다. 실험 기록 보호 장치다.
- 가중치는 ZIP에 없다. 예측·서버 실행에는 **직접 학습한 checkpoint**가 필요하다.

### 7. 환경과 자원 — 같은 GPU를 두 모델이 동시에 쓰지 않는다

| 시점 | GPU | CPU |
|---|---|---|
| 분류기 학습 (04) | BERT 학습 | — |
| 서비스 (06 이후) | Ollama 생성 모델 | 학습한 분류기 추론 |

- BERT 학습 전에 `ollama stop 모델이름`으로 생성 모델을 GPU에서 내린다. 안 하면 GPU 메모리 부족.
- 생성 모델(Ollama, OpenAI)은 **학습하지 않고 호출만** 한다. 학습하는 건 분류기(BERT)뿐이다.
- `DATASET`, `LEARNER` 설정값은 한 흐름 동안 **고정**해야 이후 단계(모델 선택, API)가 자기 결과를 찾는다.
- OpenAI 키는 `.env`에만. 코드와 결과 파일에 쓰지 않는다.

### 9. Claude가 짚어준 확인 포인트

**① 기준 모델이 이미 1.0이면, BERT와의 비교로 알 수 있는 게 거의 없다**
- validation 36건에서 기준 모델 macro F1 1.0, BERT도 1.0(lr2e5 3 epoch, lr5e5 2 epoch). 둘 다 만점이면 "BERT가 나아졌다"는 판단이 불가능하다 — **천장 효과(ceiling effect)**.
- 교안도 "정돈된 합성 자료 36건의 결과이고 실제 고객 문의에서도 모두 맞힌다는 뜻은 아니다"라고 적어 두었다.
- QA 관점에서는 **변별력 없는 테스트셋**이다. 너무 쉬운 테스트로는 두 모델의 차이를 못 잡는다. kit의 `data/inquiries`에는 `challenge.jsonl`도 들어 있는데, 오늘 범위에서는 쓰지 않았다. 더 어려운 사례로 비교하는 단계가 뒤에 있는지 내일 확인할 것.

**② 학습 전 loss 1.34는 "정상 출발"을 확인하는 신호다**
- 라벨 3개를 완전히 고르게 맞히면 loss는 ln 3 ≈ 1.10이다. 학습 전 BERT의 loss 1.34는 이 근처라서 **분류층이 막 초기화된 상태가 맞다**는 확인이 된다.
- 만약 학습 전 loss가 0에 가깝다면 정답이 입력에 섞였을 가능성(누수)을, 아주 크다면 라벨 번호 대응 오류를 의심할 수 있다. 학습을 돌리기 전에 하는 **sanity check**다.

**③ 같은 seed여도 장치가 다르면 결과가 다르다**
- `SEED = 42`로 고정했지만 lr2e5 1 epoch F1이 RTX 5060에서 0.7827, Mac MPS에서 0.8222로 다르다.
- 팀 프로젝트에서 팀원마다 장치가 다르면 같은 코드로도 점수가 조금씩 다를 수 있다. 결과를 공유할 때 **장치 정보를 같이 기록**해야 한다.

**④ 교안 03의 TF-IDF 값 확인은 "학습에 쓴 문장"으로 한 것이다**
- `first_text`는 train 문장이라서 맞히는 게 당연하다. 교안도 "새 문의의 성능으로 해석하지 않는다"고 적었다. 학습 데이터에서 잘 맞는 걸 성능으로 보고하지 않는 것 — 테스트 결과를 보고할 때 **어떤 데이터로 확인했는지**를 같이 적어야 하는 이유다.

### 교안 01 : 문의 한 건을 파이썬으로 읽기
- **핵심 개념**:

    | 열 | 예시 | 역할 |
    |---|---|---|
    | `id` | `…family-01-v1` | 행 구분 |

  - 새 고객은 `text`만 보낸다. `label`은 학습할 때만 있는 정답이고, 서비스에서는 **예측해야 하는 값**이다.
  - `read_rows(path)` — `csv.DictReader`로 첫 줄을 키로 쓰고, 모든 셀은 **문자열**로 읽는다. `utf-8-sig`는 엑셀이 붙이는 BOM까지 처리. 본문에 쉼표가 있으면 `split(',')`은 틀어지므로 `csv` 모듈을 쓴다.
  - `read_labels(data_dir)` — `labels.json`에서 라벨 순서를 읽고, 빈 목록이나 중복이면 `ValueError`. 0=shipping, 1=refund, 2=account.
  - `if __name__ == "__main__":` — 직접 실행할 때만 `main()` 호출. 다른 파일이 `import`할 때는 실행되지 않는다(그래서 step04가 재사용 가능).
  - **`return`과 `print`의 차이** — `return`은 다음 코드가 쓸 값을 돌려주고, `print`만 한 함수의 반환값은 `None`이다. "보인다 ≠ 값이 있다".
- **퀴즈 풀이 (Claude가 계산해 확인)**:

  - 1-2: `{'shipping': 2, 'refund': 1}` / `None` / `refund` → `print(counts)`를 `return counts`로 바꿔야 `result`를 쓸 수 있다.
- **QA 체크포인트**:
  - **`print`만 하는 함수는 테스트할 수 없다.** 반환값이 `None`이라 `assert`할 대상이 없다. 다음 단계에서 재사용하거나 검증하려면 `return`이 필요하다.
  - **모든 셀이 문자열로 읽힌다** — 숫자처럼 보이는 값도 `str`이다. 자료형 가정이 틀리면 비교·계산에서 조용히 오류가 난다.
  - **라벨 목록 검증을 읽는 시점에** — 빈 목록·중복 이름은 잘못된 라벨 번호를 만든다. 문제를 가장 앞에서 막는 fail fast.
  - **`PREVIEW_ROWS`를 1로 바꿔도 행 수 180은 그대로** — 화면에 보이는 것과 실제 데이터를 구분하는 연습.

### 교안 02 : 라벨과 학습 데이터를 정리하기
- **핵심 개념**:

    | 라벨 | 해결하려는 일 | 이 앱이 모르는 것 |

    | `shipping` | 출고, 배송 상태, 운송장 확인 | 실제 위치·도착 날짜 |

    | `train.csv` | 모델과 전처리 학습 | 180 / 90 |

- **QA 체크포인트**:
  - **`id`가 달라도 같은 상황일 수 있다.** id만 비교하는 중복 검사는 "다른 표현의 같은 상황"을 못 잡는다. 검사 키를 여러 개 두는 이유.
  - **정규화는 표기 차이만 줄인다.** 공백·전각/반각 차이는 잡지만, 뜻만 비슷한 문장은 못 찾는다. 자동 검사의 **탐지 범위를 알고 쓰는 것**이 중요하다.

### 교안 03 : 비교할 기준 모델 만들기
- **핵심 개념**:
  - **기준 모델부터 만드는 이유** — 같은 train으로 학습, 같은 validation으로 평가해야 "BERT가 나아졌다 / 차이가 없다"를 판단할 수 있다.
  - **문자 TF-IDF** — 문장을 2~5글자 조각으로 잘라 숫자로 바꾼다. 공백도 문자에 포함.
    - TF: 한 문장에 그 조각이 몇 번 나오는가
    - IDF: train 전체에서 흔한 조각일수록 비중을 줄임
    - 학습한 특징 17,329개, 대부분 0이라 희소 행렬로 저장. 값이 크다고 정답 확률이 높은 건 아니다.
  - **Pipeline** — `make_pipeline(TfidfVectorizer(analyzer="char", ngram_range=(2, 5)), LogisticRegression(max_iter=1000, class_weight="balanced"))` → `baseline.joblib`. 변환기와 분류기를 **묶어 저장해야** 같은 문장이 같은 숫자로 변환된다.
    - 여기의 Pipeline은 scikit-learn 기능이고 LangChain과 무관하다.
    - `max_iter=1000`은 최적화 반복 상한이지 데이터 1,000개가 아니다.
  - **`fit`은 train에서만, validation에는 `predict`만.** validation까지 `fit`하면 평가할 문장의 통계를 미리 쓰는 데이터 누수.
  - 지표 계산: `labels=ids`로 행·열 순서 고정, `zero_division=0`, `confusion_matrix_axes`까지 저장. 틀린 행은 `validation_errors.csv`.
  - 실제 결과: **validation 36건 모두 정답, accuracy·macro F1 1.0**.
    | 저장 파일 | 내용 |
    |---|---|
    | `baseline.joblib` | 변환기 + 분류기 |
    | `validation_metrics.json` | 지표와 혼동행렬 |
    | `validation_errors.csv` | 틀린 문장 (지금은 머리글만) |
    | `config.json` | 라벨 순서, 문자 길이 설정 |
- **퀴즈 풀이 (Claude가 계산해 확인)**:
  - 3-1: 혼동행렬 `[[2,0,0],[0,1,1],[0,0,2]]`, accuracy 0.8333, refund precision 1.0 / recall 0.5 (macro F1 0.8222)
  - 3-2: 특징 8개(`배송`, `송␣`, `␣조`, `조회`, `환불`, `불␣`, `␣요`, `요청`) / `new` shape (1, 8), nnz 4 / "계정"은 train에 없던 조각이라 `transform`이 무시 / refit 특징 11개 — 평가 문장으로 어휘가 바뀌는 누수
- **QA 체크포인트**:
  - **기준선(baseline) 없는 점수는 해석할 수 없다.** 게임 QA에서 "이번 빌드 프레임이 60"만으로는 좋아졌는지 모르고 **이전 빌드와 같은 조건에서 비교**해야 하는 것과 같다.
  - **`transform`은 새 조각을 무시한다** — 학습 때 없던 단어(신조어, 오타)는 모델에 보이지 않는다. 실제 서비스에서 새 표현이 들어오면 성능이 떨어질 수 있는 지점.
  - **accuracy만 보면 라벨 불균형을 놓친다.** macro F1은 라벨마다 따로 계산해 평균하므로, 한 라벨만 계속 틀리는 문제를 드러낸다.
  - **혼동행렬의 축을 결과 파일에 같이 저장한다** — 나중에 행·열을 헷갈려 precision과 recall을 뒤바꿔 보고하는 실수를 막는 장치.
  - **6건 예시의 0.8333 / 0.8222는 "계산용 예시이며 실제 모델 결과가 아님"** — 교안이 예시와 실제 결과를 계속 구분해 적는다.

## 1일차 오후 — BERT가 문의를 배우는 과정 (교안 04)

### 04-1 : 문장을 토큰과 배치로 변환
- **핵심 개념**:
  - 기준 모델과 BERT의 차이:
    | | 기준 모델 (03) | BERT (04) |
    |---|---|---|
    | 문장 처리 | 문자 2~5글자 조각 출현 | 토큰 번호 → 문맥 표현 768차원 |
    | 학습 가중치 수 | 51,990개 | 110,619,651개 |
    | 장치 | CPU, 몇 초 | GPU (RTX 5060 기준 약 10초) |
    | 단어 순서·문맥 | 보지 않음 | 반영 |
  - 학습 설정:
    | 설정 | 값 | 뜻 |
    |---|---|---|
    | `LEARNING_RATE` | 2e-5 | 한 번 갱신할 때 움직이는 보폭 (0.00002) |
    | `EPOCHS` | 3 | train 전체를 3번 반복 |
    | `BATCH_SIZE` | 4 | 한 번에 4문장 계산 |
    | `ACCUMULATION_STEPS` | 4 | 4배치(16문장)의 gradient를 모아 한 번 갱신 |
    | `MAX_LENGTH` | 192 | **토큰** 수 기준으로 자름 (글자 수 아님) |
    | `DEVICE` | `cuda` | GPU 없으면 `cpu` |
  - 토큰화: `[CLS] 주문 ##한 지 사흘 ##이 … [SEP]` → `[2, 4867, 2470, 1583, 9229, 2052, …, 3]`
    - `##`은 앞 토큰에 이어지는 조각, `[CLS]`는 문장 맨 앞 특별 토큰(분류할 때 이 위치의 표현 사용).
    - **4867은 '주문'의 어휘 번호이지 정답 번호와 무관하다.** 정답은 토큰에 섞지 않고 `labels`로 따로 전달.
  - `TextDataset` — 토큰(`input_ids`, `token_type_ids`, `attention_mask`)과 정답 번호(`labels`)를 **같은 행 순서**로 묶는다. 이 단계에서는 아직 padding하지 않는다.
  - `DataCollatorWithPadding(pad_to_multiple_of=8)` — 배치마다 가장 긴 문장에 맞춰 뒤를 채운다. 30토큰 → 32칸.
    - `attention_mask`: 1 = 실제 토큰, 0 = 채운 자리. padding을 문장 내용으로 읽지 않게 하는 장치.
    - truncation은 192토큰보다 긴 문장만 자른다.
  - 앞 2문장 배치: `input_ids` [2, 32], `labels` [2], 실제 토큰 수 [30, 21].
- **실습·퀴즈 풀이 (Claude가 계산해 확인)**:
  - 실습 1 (`PREVIEW_ROWS = 1`): `input_ids` [1, 32], `labels` [1], 정답 [0], 실제 토큰 [30]. 첫 차원만 바뀌고 둘째 차원은 그대로 32.
  - 1-1: `32` / `[30, 21, 9]` / `36` → `input_ids` [3, 32], 가장 긴 문장이 33토큰이면 `batch_len` 40.
  - 1-2: `{'input_ids': [2, 31, 32, 33, 3], 'labels': 2}` / `3 1` / `[0, 1, 2]` → 라벨 순서를 뒤집으면 `[2, 1, 0]`. 학습과 서비스의 순서가 다르면 모델이 낸 번호를 **다른 라벨 이름으로 해석**하게 된다.
- **QA 체크포인트**:
  - **어휘 번호와 정답 번호를 혼동하지 않는다.** 둘 다 정수라서 섞여도 코드 오류가 안 난다. 조용히 틀리는 유형.
  - **`MAX_LENGTH`는 토큰 수** — 긴 문의의 뒷부분이 잘리면 핵심 정보를 놓칠 수 있다. 경계값 테스트 대상: 192토큰 근처 문장.
  - **attention mask가 없으면 padding까지 내용으로 읽는다** — 배치 안에서 짧은 문장의 결과가 옆 문장 길이에 따라 달라지는 결함이 된다.
  - **`features`와 `targets`의 행 순서가 같아야 한다** — 순서가 어긋나면 문장마다 엉뚱한 정답으로 학습한다. 학습은 돌아가는데 결과만 이상한, 찾기 어려운 결함.

### 04-2 : BERT의 점수 계산과 가중치 변경 시점
- **핵심 개념**:
  - **본체는 문맥 표현, 분류층은 라벨 점수.**
    | 부분 | 구조 | 파라미터 수 | 시작 상태 |
    |---|---|---|---|
    | BERT 본체 | 12층 Transformer, 토큰마다 768차원 | 110,617,344 | 사전학습 가중치 |
    | 분류층 | Linear 768 → 3 | 2,307 (3 × 768 + 3) | **새로 초기화** |
  - `AutoTokenizer`와 `AutoModelForSequenceClassification`을 **같은 이름**(`klue/bert-base`)에서 불러온다. `num_labels=3`, `id2label`/`label2id`를 설정에 저장.
  - `requires_grad_(True)` — 본체를 고정하지 않고 **본체 + 분류층 모두** 학습한다.
  - 첫 실행 시 `classifier.weight, classifier.bias newly initialized` 안내가 뜨는 건 **정상**(아직 분류를 안 배운 출발 모델).
  - `model(**batch)` — dict 키를 인자 이름으로 펼친다. `labels`가 있으면 loss도 함께 계산.
  - **logits → softmax(합이 1인 확률) → −log p(정답) → 평균 = loss.** 학습 전 정답 확률 0.25, 0.27 → loss 약 1.34.
  - **`backward()`는 gradient 계산, `step()`은 가중치 변경.**
    | 순서 | 호출 | 가중치 변경 |
    |---|---|---|
    | 1 | `zero_grad()` | 그대로 (gradient 비우기) |
    | 2 | `model(x)` → loss | 그대로 |
    | 3 | `loss.backward()` | **그대로** (gradient만 계산) |
    | 4 | `optimizer.step()` | **변경** |
  - `step()`이 하는 일: `w = w - lr * grad`. 예: L(w) = (w−2)², w=0에서 gradient −4, lr 0.1 → 새 w = 0.4.
- **실습·퀴즈 풀이 (Claude가 계산해 확인)**:
  - 실습 2 (lr = 0.0): backward 직후 False, step 직후 **False**. gradient는 계산되지만 보폭이 0이라 움직이지 않는다.
  - 2-1: `0 -4.0 0.4` / `1 -3.2 0.72` / `2 -2.56 0.976` → lr 1.0이면 w가 4.0 ↔ 0.0을 **오가며 수렴하지 않는다**. lr 0.1로 계속 반복하면 2에 수렴.
  - 2-2: `0 3.0` / `1 6.0` / `zero 뒤: 3.0` → gradient는 backward마다 **누적**된다. zero_grad를 빼먹으면 이전 배치의 gradient가 섞여 갱신이 엉뚱한 방향·크기가 된다.
- **QA 체크포인트**:
  - **"함수를 호출했다"와 "값이 실제로 바뀌었다"를 구분한다.** 교안이 `before` 가중치를 복사해 두고 `torch.equal`로 변경 여부를 직접 확인하는 방식은, **동작했다는 로그 대신 상태 변화로 검증**하는 테스트 방식이다.
  - **lr 0 실습 = 경계값 테스트.** 보폭이 0이면 학습이 일어나지 않는다는 걸 직접 확인한다. 반대로 lr이 너무 크면(1.0) 발산·진동한다.
  - **zero_grad 누락은 에러 없이 학습 결과만 이상해지는 결함이다.** 코드가 돌아간다고 맞는 게 아니다. 다만 이 누적 성질을 **일부러** 쓰는 게 `ACCUMULATION_STEPS`다.
  - **"newly initialized" 경고는 정상** — 경고 메시지가 결함인지 정상 동작인지 구분하는 기준을 교안이 미리 알려 준 것. 경고마다 결함 리포트를 쓰지 않으려면 이런 판단 기준이 필요하다.

### 04-3 : 학습 루프와 저장
- **핵심 개념**:
  - **180문장 → 45배치 → epoch당 12번 갱신 → 3 epoch 36번.**
    - 45배치를 4개씩 묶으면 마지막 묶음은 1배치뿐이라, 그 묶음은 loss를 1로 나눈다.
    - 1 epoch = train 전체를 한 번 읽는 범위이지 갱신 1회가 아니다.
  - `DataLoader` — train만 `shuffle=True`(seed 고정), validation은 순서 유지. `num_workers=0`은 Windows에서도 안전.
  - `AdamW(model.parameters(), lr=…, weight_decay=0.01)` — 본체 + 분류층 전체 갱신.
  - 배치 반복문:
    - ① `model(**batch)` — logits와 loss (`loss / window_size`로 평균 맞추기)
    - ② `backward()` — gradient 누적
    - ③ 4배치가 모였거나 마지막이면 `clip_grad_norm_`(gradient 크기 제한, 1.0) → `step()` → `scheduler.step()`
    - ④ `zero_grad()` — 다음 묶음 준비
  - 세부 설정: warmup(36번 중 처음 3번은 학습률을 천천히 올리고 이후 0까지 감소), autocast·scaler(GPU 낮은 정밀도로 메모리 절약), gradient checkpointing(중간 계산을 다시 계산해 메모리 절약). **backward와 step의 역할은 그대로.**
  - `validate_model` — `eval()` + `inference_mode()`, backward·step 없음. `argmax(-1)`로 문장마다 가장 큰 점수의 위치 선택. 지표 함수는 03과 동일.
    | | 학습 | 검증 |
    |---|---|---|
    | 모드 | `train()` | `eval()` |
    | gradient | 기록 | 끔 |
    | backward / step | 있음 | 없음 |
    | 데이터 | train | validation |
  - **점수가 올랐을 때만 저장** — `metrics["macro_f1"] > best_score`면 `save_pretrained`로 가중치·토크나이저 저장.
  - 실제 기록 (kit 공식, RTX 5060):
    | 실험 | epoch 1 F1 | epoch 2 F1 | epoch 3 F1 | 저장한 epoch |
    |---|---|---|---|---|
    | lr2e5 (2e-5) | 0.7827 | 0.9722 | 1.0000 | 3 |
    | lr5e5 (5e-5) | 0.9441 | 1.0000 | 1.0000 | 2 (3은 같은 점수라 저장 안 함) |
  - 실험 폴더 `artifacts/step_by_step/inquiries/learner01/lr2e5/`: `config.json`, `epochs.jsonl`, `training_summary.json`, `validation_metrics.json`, `validation_errors.csv`, `baseline.joblib`(비교용 사본), `checkpoint/`(`model.safetensors`, `config.json`(id2label 포함), 토크나이저).
- **실습·퀴즈 풀이 (Claude가 계산해 확인)**:
  - 실습 3: `RUN_NAME = "lr2e5"`, `LEARNING_RATE = 2e-5`로 학습 → `"lr5e5"`, `5e-5`로 한 번 더. 공식 기록 기준 lr2e5는 3 epoch, lr5e5는 2 epoch 저장. 같은 최고점이 두 번 나오면 **먼저 나온 모델이 남는다**.
  - 3-1: `45 12 36` → BATCH_SIZE 8이면 `23 6 18`. 갱신 횟수가 절반으로 줄어 같은 epoch 수로는 덜 학습될 수 있다.
  - 3-2: `lr5e5 2 1.0` / `lr2e5 3 1.0` → `>=`면 lr5e5는 3 epoch 저장. 같은 점수라면 **덜 학습한(앞선) epoch**가 과적합 위험이 적다는 근거로 `>`를 쓸 수 있다.
- **QA 체크포인트**:
  - **train loss가 아니라 validation 점수로 저장한다.** train loss는 계속 내려가도 새 문장 성능은 떨어질 수 있다(과적합). 선택 기준이 평가 데이터에 있어야 한다.
  - **동점 처리 규칙(`>` vs `>=`)을 명시한다.** 같은 점수에서 어느 모델을 남길지는 코드 한 글자로 바뀐다. 기준이 문서화되지 않으면 실행마다 다른 모델이 남은 이유를 설명할 수 없다.
  - **`epochs.jsonl`은 저장 여부와 무관하게 매 epoch 기록** — 최종 결과만이 아니라 과정 전체를 남겨야 나중에 "왜 이 epoch가 선택됐는가"를 추적할 수 있다. 테스트 실행 로그를 통과·실패와 무관하게 다 남기는 것과 같다.
  - **같은 실험 폴더면 덮어쓰지 않고 중단** — 이전 실험 기록이 실수로 사라지는 걸 막는다. 실험 이름(`RUN_NAME`)을 바꾸는 것이 새 실험의 조건.
  - **"파일에 쓰기 ≠ 학습"** — 학습은 메모리에서 일어나고, 저장은 조건을 만족할 때만이다. 파일이 없다고 학습이 안 된 게 아니고, 파일이 있다고 최신 epoch인 것도 아니다.
  - **`training_summary.json`과 `epochs.jsonl`을 대조** — 실습 3처럼 기록만 보고 저장된 epoch를 예상한 뒤 요약 파일과 비교하는 건, **기대 결과를 먼저 적고 실제와 대조하는** 테스트 절차 그대로다.
