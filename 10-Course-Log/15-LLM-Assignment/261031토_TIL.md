## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | JSON Schema | — | JSON의 **모양**(칸 이름·타입·허용값)을 정해 두는 규격. 내용이 맞는지는 모른다 |
  | `enum` | enumeration | "이 값들 중 하나만" 허용 (예: category 4개) |
  | `additionalProperties: False` | — | 정해진 칸 외에 **다른 칸이 끼어들지 못하게** 막음 |
  | Repair | — | 모델이 답은 했는데 내용이 틀렸을 때, **무엇이 틀렸는지 힌트를 붙여** 1번 다시 요청 |
  | Fallback | — | 고쳐도 안 되면 정해진 안전한 답 + `needs_human=true`로 끝냄 |
  | Function Calling (도구 호출) | — | 모델은 "이 도구 써 줘"라고 **요청만**, 실제 실행은 우리 코드가 함 |
  | `call_id` | — | 도구 요청서와 결과 답장을 짝짓는 **번호표** |
  | `copy.deepcopy` | — | 원본을 통째로 복사. 받은 쪽이 고쳐도 원본이 안 바뀜 (읽기 전용 조회) |
  | Retry | — | 답이 **아예 안 왔을 때**(timeout, 429, 5xx) 같은 요청을 잠깐 기다렸다 다시 보냄 |
  | 408 / 409 / 429 / 5xx | HTTP 상태 코드 | 시간 초과 / 충돌 / 너무 자주 보냄 / 서버 쪽 일시 고장 → 재시도 대상 |
  | 401 / 400 | HTTP 상태 코드 | 인증 실패 / 잘못된 요청 → 몇 번 보내도 같음, **즉시 종료** |
  | Prompt Caching | — | 매번 똑같은 앞부분(정책+문서)을 재사용해 입력 단가를 낮춤 (gpt-5.6-luna: 0.2 → 0.02 USD/1M) |
  | hit / miss / unavailable | — | 캐시 읽기 토큰이 양수 / 0 / 기록 없음 |

- **핵심 통찰: "답이 틀렸다"와 "답이 안 왔다"는 처리가 다르다**
  - **출력 수정(Repair)**: 통화는 됐는데 상대가 엉뚱하게 말함 → "이게 틀렸으니 이렇게 다시" **힌트를 붙여** 요청. 같은 요청을 그대로 보내면 같은 실수를 반복할 수 있다.
  - **전송 재시도(Retry)**: 통화가 아예 안 됨 → 내용엔 문제가 없으니 **같은 요청을** 잠깐 기다렸다 다시. 단, 없는 번호(401)는 백 번 걸어도 소용없으니 바로 끝낸다.
  - 두 가지를 섞으면 안 된다. 그래서 코드에서도 `finish_answer`와 `call_with_retry`가 따로 있다.

- **두 번째 통찰: 모델은 손님, 코드는 주방**
  - 모델은 `data/tickets.json`을 직접 열 수 없다. "IT-1043 찾아 줘"라고 **주문(function_call)**만 하고, `execute_tool`이 실제로 찾는다.
  - 결과를 돌려줄 때 요청서와 **같은 `call_id`**를 붙여야 모델이 어느 결과가 어느 요청 것인지 안다.
  - 도구는 **읽기 전용**: 허용 안 된 이름·이상한 인자는 거절하고, 찾은 티켓은 사본으로 준다.

- **세 번째 통찰: 검사 통과 뒤에도 live 결과를 읽어야 한다 (compare 개선)**
  - `check all` 45/45 통과 후 `compare --live`(26회)를 돌려 기대값과 대조 → `needs_human`·`category`는 **26개 모두 일치**, `source_ids`만 **10개 어긋남**.
  - 원인: 모델이 "API 키는 지우고 공유하세요" 같은 **덧붙인 주의사항**의 문서(`policy-secret` 등)까지 출처로 달았다.

## 🧭 종합 QA 체크포인트

### 1. 스키마 검사 ≠ 내용 검사

| 단계 | 막는 것 | 못 막는 것 |
|---|---|---|
| JSON Schema (strict) | 칸 누락, 타입 틀림, 허용값 밖, 다른 칸 추가 | 빈 답, 없는 출처, 중복 출처, 근거 없이 담당자 불필요 |
| `validate_answer` 규칙 | 위 "못 막는 것" 4가지 | 답이 사실과 맞는지 (사람이 문서와 대조) |

### 2. 경계값 테스트가 버그를 잡는다

- `retry_now = retryable and attempt < 4`로 썼을 때 11개 중 **10개 통과**. 1~2번째 시도에서 끝나는 사례는 모두 통과했고, **세 번 다 실패하는 503 사례**만 "마지막 시도 뒤에도 대기"를 드러냈다.
- 게임 QA의 경계값 테스트와 같다. 정상 경로만 보면 안 보이고, **끝까지 가는 사례**가 있어야 off-by-one이 잡힌다.

### 3. 조용한 실패: `.get`과 오타

- `details.get("cashed_tokens")` (cache → cash 오타) → 오류 없이 `None` → 비용 계산 블록을 **통째로 건너뜀**.
- 증상은 "다음 빈칸 메시지가 엉뚱한 곳을 가리킴"이었다. 오류가 안 났다고 맞은 게 아니다.

### 4. 비용·지연 차이를 캐시 효과로 단정하지 않기

| | 1번 요청 (Python 버전) | 2번 요청 (uv 설치) |
|---|---|---|
| 캐시 읽기 | 0 (miss) | 1,608 (hit) |
| 출력 | 94 | 117 |
| 비용 | 0.00052달러 | 0.00018달러 |
| 시간 | 3.58초 | 2.09초 |

- 비용은 줄었지만 질문·답 길이가 달라서 **전부 캐시 덕분이라고 할 수 없다.** 시간은 서버 상태에도 흔들린다.
- 캐시 읽기는 전체 입력 **안에**, 추론 토큰은 전체 출력 **안에** 이미 들어 있다 → 또 더하면 비용이 부풀려진다 (할인 사과 두 번 계산).

### 5. Claude가 짚어준 확인 포인트

- **힌트·프롬프트는 모델이 읽는다**: "policy 양식에 맞춰" 대신 "4칸 양식에 맞춰". 모델은 코드 변수 이름을 모른다 (10/29와 같은 교훈).
- **빈칸 바로 아래 줄을 보면 어느 빈칸인지 안다**: `return {... "unknown_tool"}` 위는 이름 검사, `raise ValueError("unexpected arguments")` 위는 인자 검사.
- **policy 문장에는 "언제"가 있어야 한다**: "원인을 단정하지 마"만 쓰면 모호 → "오류 화면이나 이미지에서는 …".
- **`--fresh`**: 코드나 자료를 바꾼 뒤 비교는 이전 결과를 재사용하지 않도록 `compare --live --fresh`. 주석만 고쳤으면 재실행 불필요.

## 1. 필수 2 — 답변 형식 검사와 1회 수정

- `answer_format`: 4칸 타입(`answer` string, `source_ids` string 배열, `needs_human` boolean, `category` enum 4개) + 전부 `required` + `additionalProperties: False`.
- `validate_answer` 규칙 4개:
  - 빈 답: `answer["answer"].strip() == ""`
  - 없는 출처: `set(source_ids) - set(known_ids)`가 비어 있지 않음
  - 중복 출처: 목록 개수 ≠ 묶음(`set`) 개수 (중복을 합쳤더니 개수가 줄었다)
  - 근거 없는 확답: 출처 0개인데 `needs_human == False`
- `finish_answer`: 검증 실패 → 오류 종류별 `hints[error_kind]` 힌트를 붙여 **1번만** 다시 요청 → 또 실패면 fallback.
- 결과: `check answer` 18/18, live Python 문의는 수리 없이 첫 시도 통과.

## 2. 필수 3 — 티켓 조회 (`tool_schema`, `execute_tool`, `tool_roundtrip`)

- 스키마: `ticket_id` string, `pattern: "^IT-[0-9]{4}$"`, `required`, `additionalProperties: False`.
- `execute_tool` 3단 거르기: 이름이 `lookup_ticket`이 아니면 `unknown_tool` → 인자가 사전이 아니거나 칸이 `{"ticket_id"}`가 아니면 `invalid_arguments` → 없는 티켓이면 `not_found` → 있으면 `copy.deepcopy(tickets[ticket_id])`.
- `tool_roundtrip`: 모델 output 전체 사본을 기록에 붙이고 → 요청마다 `execute_tool` 실행 → 같은 `call_id`로 `function_call_output` 답장. 최대 4바퀴.
- live (티켓 현재 상태, Q08): 모델이 `IT-1043` 조회 요청 → 코드가 조회 → `resolved` 답변, 출처 `policy-incident`, 티켓 번호는 출처에 안 넣음.

## 3. 필수 3 — 오류 화면 입력 (`image_content`)

- 글 항목 옆에 `{"type": "input_image", "image_url": support.image_url(image_path), "detail": "high"}` 추가.
- policy에 관찰·추측 구분 문장 추가: 오류 화면이나 이미지에서는 원인을 단정하지 말고, 보이는 것만 설명하고 담당자 확인으로 연결.
- live (오류 화면 확인, Q10): 화면의 `401 Unauthorized`, `internal-demo-package`까지 읽고 "화면만으로 계정 폐기나 원인은 확정할 수 없다", `needs_human=true`.

## 4. 필수 3 — 호출 재시도 (`call_with_retry`)

```python
retryable = error.kind in ("timeout", "connection") or status in (408, 409, 429) or 500 <= status <= 599
retry_now = retryable and attempt < 3
```

- `attempt`는 1, 2, 3. 3번째(마지막)에서 실패하면 기다리지 않고 `None`.
- `check retry` 11/11. 재시도는 고정 장애 주입이라 `--live` 없이 실행.

## 5. 필수 3 — 사용량과 비용 (`cache_settings`, `usage_record`)

- `cache_settings`: 캐시 열쇠를 **정책 지시문만으로** 만든다 (`build_instructions(documents, variant)`). 질문·시각을 섞으면 매번 열쇠가 달라져 캐시가 안 맞는다.
- 일반 입력 = 전체 입력 − 캐시 읽기 − 캐시 쓰기 (예: 1,500 − 500 − 200 = 800)
- 비용 = (일반×input + 캐시 읽기×cached + 캐시 쓰기×cache_write + 출력×output) ÷ 1,000,000
- 관측: `None` → unavailable, 양수 → hit, 0 → miss.
- `check usage` 6/6.

## 6. 필수 3 — 전체 연결 (`run_pipeline`)

- 빈칸 6개 모두 **이미 만든 함수를 순서대로 부르기**: `cache_settings` → `answer_format()` → `[tool_schema()]` → `image_content(question, image_path)` → `tool_roundtrip(reliable_send, …)` → `finish_answer(…, {document["doc_id"] for document in documents}, events)`.
