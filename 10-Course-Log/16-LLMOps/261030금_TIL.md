## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | LLMOps | Large Language Model Operations | 실제 요청을 **관측**하고 → 실패를 **평가 데이터**로 남기고 → 변경 전후를 **같은 기준으로 비교**하는 운영 과정 |
  | Langfuse | — | LLM 앱의 실행 기록(Trace) · 데이터셋 · 점수를 보관하고 보여 주는 관측 도구 (오늘은 Langfuse Cloud) |
  | Trace / Trace ID | — | **한 요청의 실행 전체** / 그 실행을 묶는 식별자 |
  | observation | — | Trace 안의 **단계 하나** (span · GENERATION · tool 등) |
  | span | — | 작업 구간 (오늘: policy-qa, retrieve 등) |
  | GENERATION | — | **모델 호출**에 특화된 구간 (오늘: ChatOpenAI) |
  | CallbackHandler | — | LangChain 실행을 Langfuse에 기록하는 연결 객체 — `invoke`의 `callbacks`에 넘겨야 작동 |
  | flush | — | SDK가 **남은 기록 전송**을 처리하는 호출 (서버 반영 확인과는 다름) |
  | Score | — | Trace에 붙이는 평가값 (BOOLEAN · CATEGORICAL 등) |
  | UTC | Coordinated Universal Time (협정 세계시) | 기록 시각의 공통 기준 (`+00:00`) |
  | tzinfo | time zone info | 시각에 붙은 시간대 정보 — 없으면 PC마다 다른 기준으로 읽힘 |
  | HTTP 401 / 403 / 429 | Unauthorized / Forbidden / Too Many Requests | 인증 실패(키 쌍·지역) / 권한 없음(모델 사용 권한) / 호출 한도 초과 |
  | Public / Secret Key | — | 같은 Langfuse **프로젝트의 한 쌍** — 섞어 쓰면 401 |
  | Hobby 요금제 · unit | — | Langfuse 무료 요금제 (월 50,000 units · 30일 보관) / 사용량 단위 (**unit ≠ 모델 호출 1회**) |
  | uv / uv.lock | — | 파이썬 환경 관리 도구 / 패키지 버전을 고정한 잠금 파일 (`uv run --locked`) |

- **핵심 통찰: LangChain · RAG · CE가 "답을 만드는 법"이었다면, LLMOps는 "답이 나온 다음"을 다룬다**
  - 1장은 **한 요청의 증거**를 남기고 읽는 장이다 — 검색 결과 · 모델 입력 · 출력 · 완료 여부. 흐름은 **기록하고 → 다시 찾고 → 나누고 → 분류한다.**

    | 단계 | 오늘 배운 것 | 확인할 질문 |
    |---|---|---|
    | 준비 | 키 네 개 구분, `.env`, 00_start.py, Trace 화면 읽기 | 내 실행이 내 Langfuse에 남았나? |
    | 1-1 요청 단위 관측 | Trace · observation, 수동 span, completed ≠ 정답 | 근거가 처음 사라진 단계는? |
    | 1-2 Trace 재조회 | flush ≠ 서버 조회, Trace ID로 찾기, GENERATION + end_time | 서버에 실행 기록이 있나? |
    | 1-3 도구 추적 | 규정(travel) vs 업무 결과(approval), 부모 시간에 자식 포함 | 어느 출처의 사실인가? 병목은? |
    | 1-4 실패 분류 | 판정 순서, 시각 파싱, 모의 실패 → failure_category | 무엇을 "완료"로 인정하나? |

  - 같은 "수료증 누락"이라도 고칠 곳이 다르다:

    | 관측한 증거 | 실패가 처음 드러난 위치 | 다음에 바꿀 대상 |
    |---|---|---|
    | 검색 문서 목록이 비어 있음 | 검색 | 질문 표현 · 키워드 · 검색 조건 |
    | training은 찾았지만 모델 입력에 증빙 문장이 없음 | 입력 조립 | context 구성 코드 |
    | 입력에 두 증빙이 있지만 답에는 하나만 | 생성 이후 | 응답 지시 · 필수 사실 검사 |

    **최종 답변만 모아 두면 이 세 상황을 구분할 수 없다.** 모델을 바꾸기 전에 근거가 처음 사라진 단계부터 찾는다 — RAG 1일차부터 반복된 "원인 단계부터 분리"가 이번엔 **운영 도구(Trace)** 로 구현됐다.

- **두 번째 통찰: "끝났다"와 "맞았다"를 계속 나눈다 — 오늘 하루에만 세 번 나왔다**

  | 확인 | 알 수 있는 것 | 알 수 없는 것 |
  |---|---|---|
  | `status == "completed"` + 빈 답변 아님 | 모델이 응답을 **끝냈다** | 금액·증빙·출처가 맞는지 |
  | `response_completed = 1` 점수 | 같은 Trace에 완료 판정을 **보관**했다 | 답변 내용의 정답 여부 |
  | GENERATION + `end_time` 재조회 | 서버에 모델 실행 구간이 **끝난 기록**이 있다 | 답변 내용의 정답 여부 |

  - "완료 검사 = 평가할 답이 있는가 / 내용 평가 = 업무 조건을 지켰는가." 내용 평가는 2장(Golden Dataset · Python 평가)으로 넘어간다. RAG 5일차 "Faithfulness ≠ Relevancy ≠ 정확성"처럼, 확인 단계마다 **보장하는 범위**가 다르다.

- **세 번째 통찰: 모르는 상태를 성공으로 채우지 않는다**
  - 1-4 상황: 성공률이 **예상보다 높다** → 상태가 없는 행까지 정상으로 셌기 때문일 수 있다. 버리면 품질이 실제보다 좋아 보인다.
  - status 없음 → `incomplete`, 시각 못 읽음·시간대 없음·종료가 시작보다 빠름 → `invalid_time`, 조회 0개 → "저장 실패"가 아니라 **"아직 확인 못 함"**, usage가 비면 → **비용을 모른다 ≠ 비용 0.**
  - CE 4-1의 "None ≠ 0", RAG 3일차의 `insufficient ≠ system_error`, 네트워크 스터디의 "연결 실패 원인 구분"과 같은 원칙이 이번엔 **운영 지표의 분모** 문제로 나타났다.

- **네 번째 통찰: 다시 확인할 땐 "다시 부르지" 말고 "다시 조회"한다**
  - 터미널엔 답이 나왔는데 Langfuse 목록에 안 보이면 → 모델을 다시 부르면 **기록이 하나 더 생기고 비용도 추가.** `02_read_trace.py`만 잠시 뒤 다시 실행하면 생성 토큰이 들지 않는다.
  - 찾을 때는 **질문 문장이 아니라 Trace ID**로 — 같은 질문을 반복한 실행들이 섞이지 않게. 시각은 UTC ± 1분, 화면의 현지 시각과 다르게 보일 수 있다.

- **향후 계획 및 다짐**
  - 러브코드(2차 프로젝트)와 오픈소스 프로젝트(LLM 트리아지 평가)에 바로 가져갈 것:
    - 요청 하나를 **Trace 하나**로 묶고, 일반 함수(검색·조회)에는 **수동 span**으로 경계 표시
    - 결과 기록에 **app_version · document_ids · trace_id · started_at(UTC) · usage · latency** 남기기
    - 실패 분류를 **판정 순서가 있는 함수**로 만들고, 모의 사례로 분류 규칙부터 검증하기 (🧭 6-②)
  - 2장 예고: "프롬프트를 고쳤더니 좋아진 것 같다 — 정말 좋아졌는지, 다른 질문이 나빠지지 않았는지?" → Golden Dataset · 프롬프트 버전 고정 · Python 평가 · 변경 전후 회귀 판정. RAG 5일차 8장과 이어진다.

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 확인 단계마다 보장 범위가 다르다 — "어디까지 알았나"를 표로 남긴다

| 보이는 현상 | 알 수 있는 사실 | 아직 모르는 사실 | 근거 교안 |
|---|---|---|---|
| 터미널에 답변 | 로컬 코드가 응답을 받음 | Langfuse 저장 여부 | 1-2 |
| `flush()` 완료 | 남은 기록 전송을 처리함 | 서버 검색 반영 여부 | 1-2 |
| Trace 주소 출력 | 연결할 Trace ID가 있음 | 서버 검색 반영 여부 | 1-2 |
| GENERATION 재조회 + end_time | 서버에 모델 실행 기록이 끝남 | 응답 내용의 정답 여부 | 1-2 |
| `response_completed = 1` | 응답이 끝났다는 판정을 보관 | 금액·증빙·출처 | 준비 |
| `failure_category = completed` | 기록 형식·상태·문서가 유효 | 답변 품질 | 1-4 |

- 버그 리포트에서 "재현됨 / 원인 확인됨 / 수정 확인됨"을 구분하듯, **확인 단계의 이름을 정확히** 붙여야 다음 사람이 이미 확인된 것과 아닌 것을 헷갈리지 않는다.

### 2. 실패를 숨기지 않는다 — 종료 코드 1, 대체 데이터 금지, 자동 전환 금지

| 원칙 | 코드에서 | 근거 교안 |
|---|---|---|
| 실패는 **종료 코드 1** | `run()`이 예외를 받아 `SystemExit(1)` | 준비, 1-1 |
| 실패하면 다음 명령으로 넘어가지 않기 | README "실행 실패가 표시되면 다음 명령으로 넘어가지 마세요" | 준비 |
| 예제 답변을 대신 출력하지 않음 | `MODEL_RESPONSE_INCOMPLETE`로 중단 | 1-1 |
| 자동 재시도·다른 모델 전환을 하지 않음 | `max_retries=0`, fallback 모델 없음 | 1-1 |
| 도구 실패 시 정상 승인 데이터를 만들어 계속 진행하지 않음 | — | 1-3 |
| 이전에 성공한 `result_*.json`이 있다고 이번 실행이 성공한 건 아님 | 실패한 실행은 이전 결과를 지우지 않음 | 준비 |

- 마지막 줄이 특히 QA 관점에서 중요하다 — **산출물 파일이 존재한다 ≠ 이번 실행이 성공했다.** 게임 QA에서 빌드 산출물이 남아 있어도 이번 빌드가 실패했을 수 있으니 **빌드 로그와 시각**을 확인하던 것과 같다.
- LangChain에서 Retry/Fallback을 배울 때는 "자동 재시도·대체"가 장점이었는데, 오늘은 **관측 수업이라 일부러 끈다.** 실패가 숨으면 관측할 대상이 사라지기 때문이다.

### 3. 오류 메시지에도 보안이 있다 — 키는 어디에도 남기지 않는다

| 위치 | 남기는 것 | 남기지 않는 것 | 근거 교안 |
|---|---|---|---|
| 터미널 오류 | 오류 종류 + HTTP 상태 + 안전한 안내 | API 오류 원문 (인증 정보가 섞일 수 있음) | 준비 |
| `result_*.json` | 질문 · 답변 · Trace ID · 시각 · 사용량 | 키 | 준비, 1-1 |
| Git | 코드 | `.env` · `.venv` · `result_*.json` (`.gitignore`) | 준비 |
| 교안 댓글 · 채팅 · 화면 공유 | — | 키 값 | 준비 |

- 키 네 개는 **발급처와 용도가 다르다** — `OPENAI_API_KEY`(OpenAI, ChatGPT 비밀번호 아님) / `LANGFUSE_PUBLIC_KEY` · `LANGFUSE_SECRET_KEY`(같은 프로젝트의 한 쌍) / `LANGFUSE_BASE_URL`(지역 기본 주소까지만). 증상별 확인 위치도 다르다: 401 → 키 쌍·지역, 403 → 모델 권한, 429 → 반복 호출 멈추기.
- 터미널에 직접 설정한 환경 변수가 **`.env`보다 우선**할 수 있다 → 값이 이상하면 새 터미널. "설정 파일을 고쳤는데 안 바뀐다"류 결함의 흔한 원인.

### 4. 출처마다 책임지는 사실이 다르다 — 규정 vs 업무 결과

| 출처 | 예시 | 답변에서의 뜻 | 근거 교안 |
|---|---|---|---|
| travel (규정 문서) | 1박 10만원, 영수증 필요 | **누구에게나** 적용되는 일반 한도 | 1-3 |
| approval (업무 조회) | REQ-DEMO-01, 승인, 8만원 | **이 요청 한 건**의 현재 상태 | 1-3 |

- **8만원 승인 ≠ 숙박 한도 8만원.** 모델이 두 금액을 혼동했을 때 **원래 조회 결과(lookup-approval의 Output)** 가 남아 있어야 입력 문제인지 생성 문제인지 구분한다. 승인 금액을 확인할 땐 **모델 답변이 아니라 도구 출력**을 기준으로 삼는다.
- CE 1-1의 "규정만으로는 답이 안 나온다 — 이 예약이 승인됐는지는 도구 결과에 있다"가 오늘은 **Trace 위에서 분리돼 보이는** 형태로 이어졌다. 조회 오류를 승인/미승인으로 바꾸지 않는 원칙도 같다.

### 5. 지연은 "바깥 구간"으로 재고, "안쪽 구간"으로 병목을 찾는다

- 자식 시간은 부모 시간에 **이미 포함**돼 있다. 1.5 + 0.1 + 1.3 = 2.9초로 더하면 중복 계산 — 사용자가 기다린 시간은 **바깥 구간 1.5초.** 퀴즈 1-3의 모든 구간 합 4,185ms ≠ 사용자가 기다린 시간 1,500ms.
- 병목은 **안으로 내려가며** 찾는다: qa-with-business-lookup → **policy-qa**(1,300ms) → **generate-answer**(1,280ms). 도구 구간이 짧고 모델 구간이 길면 업무 DB보다 **생성 길이 · 모델 설정**을 먼저 본다. 단, **한 번의 실행으로 단정하지 않는다.**
- 병렬 처리가 들어가면 자식 합과 사용자가 기다린 시간이 더 크게 달라진다 (퀴즈 1-3 생각해 보기: 두 자식을 동시에 실행하면 부모는 **긴 쪽 + 오버헤드** 정도로 줄어 자식 합보다 짧아질 수 있다).

### 6. Claude가 짚어준 확인 포인트

**① 내 PC의 첫 실행 기록(`result_start.json`)을 교안 기준으로 대조해 보면**
- 실제로 남은 값:

  | 항목 | 내 실행 값 | 교안 기준 / 대조 결과 |

**② 1-4 분류 함수는 "대표 원인 하나"만 남긴다 — 원인이 겹치면 집계에서 사라진다**
- 교안의 여섯 사례는 base에서 **필드 하나씩만** 바꿨다. Claude가 교안 사례 밖의 조합을 같은 `classify`로 돌려 보니:

  | 입력 조합 | 판정 | 사라진 정보 |
  |---|---|---|
  | status=failed + 시간 역전 | `invalid_time` | **모델 실패** |
  | status=failed + 문서 없음 | `model_error` | 검색 없음 |
  | status=None + 문서 없음 | `incomplete` | 검색 없음 |
  | status="COMPLETED"(대문자) | `incomplete` | 실제로는 완료였을 수 있음 |
  | 종료 시각에 시간대 없음 | `invalid_time` | — (의도대로) |
  | 종료 시각이 `...Z` 표기 | `completed` | — (Python 3.11+는 Z를 UTC로 읽음) |

- 첫 줄이 핵심이다. 시각 기록이 깨진 실패 실행은 `model_error`가 아니라 `invalid_time`으로만 세져서, **모델 오류율이 실제보다 낮게** 집계될 수 있다. 교안도 "먼저 검사한 조건이 대표 분류를 정한다 — 모든 원인을 한꺼번에 모으는 분류기는 아니다", "invalid_time이 나왔다고 모델 호출이 정상이라는 뜻은 아니다"라고 적어 두었다.
- 대소문자도 볼 만하다. 1-2의 `judge`는 `x.type.upper() == "GENERATION"`으로 **정규화**하는데, 1-4의 `classify`는 status를 **그대로** 비교한다. 엄격하게 거르는 쪽이 안전하긴 하지만, 같은 과정 안에서 값 정규화 기준이 다르다는 건 기록해 둘 만하다.
- QA로 보면 **단일 결함 주입만으로는 분류기의 우선순위 문제가 안 보인다.** 테스트 케이스에 **결함 두 개를 동시에 넣은 조합**을 추가해야 하고, 집계용으로는 대표 분류와 별도로 **원인 플래그(status_ok · time_ok · has_docs …)를 모두 남기는** 방식이 원인별 비율을 왜곡하지 않는다. 게임 QA에서 버그를 "대표 원인 하나"로만 분류하면 같은 빌드의 다른 결함 통계가 빠지던 것과 같다.

**③ 자식 구간의 합이 부모보다 짧은 "빈 시간"도 관측 대상이다**
- 퀴즈 1-3 숫자로 보면:

  | 부모 | 부모 시간 | 자식 합 | 빈 시간 |
  |---|---|---|---|
  | qa-with-business-lookup | 1,500ms | 100 + 1,300 = 1,400ms | **100ms** |
  | policy-qa | 1,300ms | 5 + 1,280 = 1,285ms | **15ms** |

- 교안은 "자식 시간을 부모에 더하면 중복 계산"을 강조했는데, 반대 방향도 있다 — **어떤 자식 구간에도 속하지 않는 시간**이다. 이 시간은 span으로 감싸지 않은 코드(context 문자열 조립, 결과 딕셔너리 생성, SDK 처리 등)에서 쓰였다고 볼 수 있다.
- 지금은 설명용 숫자라 작지만, 운영에서 이 빈 시간이 커지면 **span을 안 쳐 둔 곳**이 느려졌다는 신호다. 1-1에서 "일반 Python 함수는 자동 추적되지 않아 수동 span을 친다"고 배운 이유가 여기서도 이어진다 — 병목을 찾으려면 **계측되지 않은 구간이 얼마인지**부터 알아야 한다.

## 1-1 : LLMOps의 목적과 요청 단위 관측
- **핵심 개념**:
  - 상황: 교육비를 물었는데 **수료증이 빠졌다.** 프롬프트부터 고치면 될까? → 검색(training을 찾았나?) / 입력 조립(수료증 문장이 들어갔나?) / 생성(답에서 빠뜨렸나?) 순서로 증거를 본다.
  - 문서는 meal · travel · training **세 건**뿐 — 검색 성능이 아니라 **실패 위치 읽기**에 집중하려고. 검색은 키워드 포함 여부(`any(word in question ...)`).
  - **Trace는 요청 전체, observation은 그 안의 단계.** span = 작업 구간, GENERATION = 모델 호출 구간 → 느린 이유를 검색/생성으로 나눠 본다.
  - `lf.start_as_current_observation(name="policy-qa", as_type="span", input=..., metadata={"app_version": version, "synthetic": True})` 안에 `retrieve` 수동 span. **일반 Python 함수는 자동 추적되지 않는다.**
  - **`CallbackHandler()`를 만드는 것만으로는 기록되지 않는다** — `invoke(..., config={"callbacks": [handler], "run_name": "generate-answer"})`로 넘겨야 바깥 span 아래에 붙는다.
  - **트리 항목 수 ≠ 모델 호출 횟수** — ChatPromptTemplate은 메시지 구성, ChatOpenAI만 실제 모델 호출.
  - context = `[id] 본문` 형태로 문서 ID와 본문을 함께. 지시는 **system**, 근거와 질문은 **human.**
  - 남기는 값: `app_version`(어느 버전의 실행인가) · `document_ids`(실제 전달한 출처 범위) · `synthetic`(수업용 가상 자료). app_version은 **코드가 붙인 표지**라 값만 바꾼다고 실행이 바뀌진 않는다 — 실제 변경과 함께 바꾼다. 실무에선 색인·모델·프롬프트 버전도 남겨야 **재현**된다.
  - **호출 성공 ≠ 품질 성공**: `status != "completed"` 또는 빈 답변이면 `MODEL_RESPONSE_INCOMPLETE` — 길이 제한으로 **잘린 답도 실패.** 실패하면 종료 코드 1, 예제 답변 대체·자동 모델 전환 없음.
  - 반환 딕셔너리가 다음 강의로 이어진다: `trace_id` → 1-2 재조회, `answer` → 2장 평가, `usage` · `latency_ms` → 3장 측정·집계.
  - 실행(`01_trace.py`, 모델 1회): 검색한 문서 `['training']`, completed, "교육비는 연간 20만 원까지 지원하며, 영수증과 수료증이 필요합니다. [training]"
- **퀴즈 1-1** (교안 정답): `not retrieve(question)` → "검색", `all(term in context ...)` 실패 → "입력 조립", `all(term in answer ...)` 실패 → "생성", 모두 통과 → "정상". A 검색 · B 입력 조립 · C 생성 · D 정상. 앞 단계가 실패하면 뒤는 보지 않는다.
  - 생각해 보기: A("자기계발 지원을 받으려면 뭘 내나요?")는 검색이 비었고 "확인할 수 없습니다"라고 답했다. 이게 실패인지는 **기대 행동**에 달렸다 — 규정 밖 질문이면 올바른 보류, "자기계발 = 교육비"인데 키워드 차이로 못 찾은 거면 검색 결함. 구분하려면 질문마다 **기대 근거 문서**를 미리 정해 둬야 한다(→ 1-4 마지막 표, 2장 Golden Dataset).
- **QA 체크포인트**:
  - **단계별 증거를 남겨야 원인 분리가 된다** — 최종 답변 로그만으로는 세 실패를 구분할 수 없다. 테스트 로그 설계의 핵심.
  - **버전 표지는 재현성의 조건** — 어느 빌드(app_version · 색인 · 모델 · 프롬프트)의 결과인지 없으면 버그 재현이 안 된다. 게임 QA 버그 리포트의 "빌드 번호" 칸과 같다.
  - **잘린 답 = 실패** — 길이 제한으로 끊긴 출력을 성공으로 세지 않는 것은 경계 조건 처리.

## 1-2 : Trace 재조회와 실행 증거 확인
- **핵심 개념**:
  - 상황: 터미널엔 답이 나왔는데 Langfuse 목록에 안 보인다 → **조회만** 다시.
  - 세 단계로 나눠 확인: **터미널 답변**(로컬 코드가 응답을 받음) → **flush() 완료**(남은 기록 전송 처리) → **서버 재조회**(GENERATION이 서버에 있음). 서버가 검색 가능한 상태로 반영하는 시점은 flush와 다를 수 있다.
  - `lf.api.observations.get_many(trace_id=..., limit=30, fields="core,basic,usage,model,io", from_start_time=started_at − 1분, to_start_time=now + 1분)` — **질문 문장이 아니라 Trace ID**로, 시간 범위는 UTC ± 1분, 필요한 필드만.
  - 반환 목록은 **트리 순서가 아니다** — name · type · 부모 관계 · 시각으로 구조를 읽는다. 구형 trace 조회·구형 score API와 섞지 않는다(이번 SDK는 observations · scores_v3).
  - **GENERATION이 있고, 끝났는지**: `type.upper() == "GENERATION"`만 골라 `end_time`이 모두 있어야 통과, 아니면 `GENERATION_NOT_CONFIRMED`. 서버 재조회 완료: **5개 observation**(ChatOpenAI GENERATION · ChatPromptTemplate CHAIN · generate-answer CHAIN · policy-qa SPAN · retrieve SPAN).
    | 조회한 상태 | 판단 | 확인할 근거 |
    |---|---|---|
    | 관측 0개 | 저장 여부를 **아직 확인하지 못함** | 지역 · 프로젝트 · 조회 기간 · 반영 지연 |
    | 검색 span만 있음 | 모델 실행 완료를 확인하지 못함 | GENERATION 존재 여부 |
    | GENERATION에 종료 시각 있음 | 서버 기록의 실행 구간 종료 | 1-1의 completed와 실제 출력 |
    | 완료됐지만 증빙 누락 | 실행 완료 + 품질 실패 | 모델 입력과 최종 답변 |
  - usage가 비면 **알 수 없음** — 비용을 모른다 ≠ 비용이 0. 조회에도 공통 설정이 네 변수를 확인하지만 실제 조회 인증은 **Langfuse 키.**
- **퀴즈 1-2** (교안 정답): `x.type.upper() == "GENERATION"`, `x.end_time is None` → 0개 "조회 결과 없음"(저장 실패로 단정 X), span만 있거나 end_time 없음 → `GENERATION_NOT_CONFIRMED`, 통과 → "서버 기록 확인".
  - 생각해 보기: "서버 기록 확인"은 **실행 기록이 있다**는 뜻일 뿐 정답이 아니다. 정답 여부는 ChatOpenAI의 입력(근거)과 출력(답변)을 원문과 대조하고, 2장의 평가 기준으로 따로 판정해야 한다.
- **QA 체크포인트**:
  - **"없음"의 해석을 구분한다** — 조회 0개는 "실패"가 아니라 "미확인". 테스트 결과의 Fail과 Blocked(확인 불가)를 구분하는 것과 같다.
  - **확인 행위가 상태를 바꾸지 않게** — 재조회는 모델을 부르지 않는다. 읽기 전용 검증과 쓰기 동작을 분리.
  - **식별자로 찾기** — 같은 질문을 여러 번 실행하면 문장 검색은 섞인다. 테스트 실행마다 고유 ID를 붙이는 이유.
  - **시간대 혼동** — 결과 파일은 UTC, 브라우저는 현지 시각. 시각이 아니라 ID로 대응.

## 1-3 : 검색과 업무 도구의 실행 흐름 추적
- **핵심 개념**:
  - 상황: 숙박 **한도는 규정 문서**에, 이번 출장의 **승인 여부는 업무 시스템**에 있다. 승인 상태가 틀렸는데 문서 검색만 다시 하면 해결되지 않는다 → **두 데이터를 나눠서 관측.**
  - 바깥 `qa-with-business-lookup`(span, `lookup_source: "local-fixture"`) 안에 `lookup-approval`(**as_type="tool"**, input `{"request_id": "REQ-DEMO-01"}`, output `{"status": "승인", "amount": "8만원"}`) → 그다음 `answer(..., extra_context="\n[approval] 요청 REQ-DEMO-01: 승인, 8만원")`. 업무 조회와 QA가 **같은 Trace.**
  - `as_type="tool"`은 **관측 기록의 유형 표시**일 뿐 실제 외부 도구를 호출했다는 뜻이 아니다. 업무 조회는 Python 사전으로 만든 **모의 DB**(외부 API·결재·송금 연결 없음), 답변 생성만 실제 API.
  - 이 예제는 모델이 도구를 고르는 **에이전트가 아니다** — 고정된 승인 내역만 사용.
  - 실행(`03_steps.py`, 모델 1회): "출장 숙박비 한도는 1박 10만원이며, 영수증이 필요합니다. REQ-DEMO-01은 8만원으로 승인되었습니다. [travel] [approval]" → 1박 10만원·영수증은 **travel 문서**, REQ-DEMO-01·승인·8만원은 **lookup-approval 출력**으로 되짚는다.
  - **부모 시간에 자식 시간이 포함된다**(설명용): 전체 1.5초 / 업무 조회 0.1초 / QA 1.3초 → 사용자가 기다린 시간은 **1.5초**, 병목은 policy-qa 안에서.
  - 실무: 요청자의 **권한 확인 뒤** 업무 데이터 조회(4장), 조회 오류를 승인/미승인으로 바꾸지 않기.
- **퀴즈 1-3** (교안 정답): `s["parent"] == name`, `root["ms"]`, `s["ms"]` → 모든 구간 합 **4,185ms** ≠ 사용자가 기다린 시간 **1,500ms**, 병목 **policy-qa → generate-answer.** 업무 DB보다 생성 길이·모델 설정을 먼저 검토.
  - 생각해 보기: lookup-approval과 policy-qa를 동시에 실행하면 total_ms는 **둘 중 긴 쪽(1,300ms) + 오버헤드** 근처로 줄 수 있다. 병렬이면 자식들의 시간이 겹치므로 **자식 합보다 부모가 짧아진다.** (단, 이 예제는 QA가 승인 결과를 context로 쓰므로 실제로는 조회가 먼저 끝나야 한다 — 순서 의존이 있으면 병렬화 자체가 안 된다.)
- **QA 체크포인트**:
  - **출처별 사실을 따로 검증** — 답변의 금액을 확인할 때 "어느 출처의 금액인가"부터. 게임 QA에서 **클라이언트 표시값과 서버 DB 값**을 따로 확인하던 것과 같다.
  - **모의(mock) 데이터 표시** — `synthetic` · `lookup_source: "local-fixture"`처럼 테스트 데이터임을 기록에 남겨 운영 데이터와 섞이지 않게.
  - **도구 실패 시 가짜 정상값으로 진행 금지** — 실패 경로 테스트에서 "조회 실패 → 답변 보류"가 지켜지는지 확인.

## 1-4 : 실패 판정과 원인 분류
- **핵심 개념**:
  - 상황: 성공률이 **예상보다 높다** → 실패 분석 전에 **무엇을 완료된 실행으로 인정할지**부터 정한다.
  - **판정 순서**: ① status가 `completed`/`failed`가 아님 → `incomplete` ② 시각을 못 읽음 · 시간대 없음 · 종료 < 시작 → `invalid_time` ③ `failed` → `model_error` ④ 완료인데 문서 없음 → `retrieval_empty` ⑤ 모두 통과 → `completed`. **먼저 검사한 조건이 대표 분류를 정한다.**
    | 모의 사례 (base에서 필드 하나만 변경) | 판정 | 의미 |
    |---|---|---|
    | 정상 | completed | 상태 · 시간 · 문서 정보가 유효 |
    | 상태 누락 (status=None) | incomplete | 정상 여부를 판단할 정보 부족 |
    | 날짜 오류 · 시간 역전 | invalid_time | 시각 데이터 검토 필요 |
    | 모델 실패 (status=failed) | model_error | 명시적으로 실패한 실행 |
    | 검색 없음 (document_ids=[]) | retrieval_empty | 질문에 따라 **올바른 보류일 수도** 있음 |
  - **시각은 문자열 모양이 아니라 파싱해서**: `datetime.fromisoformat` + `tzinfo` 확인. `+00:00` 같은 시간대가 있어야 서로 다른 PC의 기록을 같은 기준으로 비교. `try/except`는 **파싱 경계만** 감싼다.
  - **모의 실패는 Trace 점수로, 운영 오류율과는 분리**: 모의 입력 1개 = Trace 1개(`simulated-failure-case`, `metadata={"simulation": True}`), 그 Trace ID에 `failure_category`(CATEGORICAL) 점수 → **입력과 판정을 함께** 조회. completed가 아니면 level=WARNING이지만 **Warning은 주의 신호**일 뿐 원인 설명의 근거는 입력과 분류 결과.
  - **검색 없음은 실패일까? 기대 행동을 붙여야 안다**:
    | 검색 결과가 없는 질문 | 기대 행동 | 다음 평가에 넣을 기준 |
    |---|---|---|
    | 재택근무 지원금은 얼마인가요? | 가상 규정 밖이므로 보류 | 출처 없이 확인할 수 없다고 답함 |
    | 교육비 증빙을 물었지만 표현 차이로 검색 실패 | training을 찾아 답함 | 영수증과 수료증, training 출처 |
    - 둘 다 문서 목록은 비어 있지만 **같은 결함으로 묶으면 안 된다.** Trace = 사건의 **증거**, 실패 분류 = 어디서 처음 드러났나, 기대 행동 = 원래 무엇을 했어야 하나, Golden Dataset = 다음 변경에도 같은 기준으로(2장).
- **퀴즈 1-4** (교안 정답): `{"completed", "failed", "cancelled"}`, `end < start`, `"cancelled"` → 취소 → `cancelled`(문서가 없어도 retrieval_empty보다 먼저), 취소 + 시간 역전 → `invalid_time`(형식 검사가 먼저), 모르는 상태 timeout → `incomplete`, 시간대 없는 시각 → `invalid_time`.
  - 생각해 보기: 취소된 요청을 오류율 분모에 넣으면 **사용자가 멈춘 것**이 시스템 실패처럼 보인다. 3장 운영 지표에서는 오류율 분모에서 빼되 **취소 건수·비율을 별도 지표**로 보고하는 게 맞다 — 취소가 갑자기 늘면 "응답이 너무 느려서 사용자가 떠난" 신호일 수 있으니 버리면 안 된다.
- **QA 체크포인트**:
  - **판정 기준(Pass/Fail criteria)을 먼저 정의** — "성공률"은 분자보다 **분모 정의**가 먼저다. 모르는 상태를 성공으로 세면 품질이 부풀려진다.
  - **결함 주입(fault injection) 테스트** — base에서 필드 하나씩 바꾸는 방식은 경계값 테스트의 기본형. 여기에 **결함 조합**을 더해야 분류 우선순위 문제가 드러난다 (🧭 6-②).
  - **테스트 데이터와 운영 데이터 분리** — `simulation=True`로 모의 사례가 운영 오류율 분모에 섞이지 않게.
  - **retrieval_empty ≠ 사용자 응답 실패** — RAG 5일차 "답 없는 질문(q11·q12)은 검색 Recall 분모에서 빼고 단정 여부를 따로 평가"와 같은 원칙.

## 정리 — 1장 결과물: 한 요청의 증거를 남기고 읽는 법

- 1-1 **Trace ID로 한 요청을 묶고**, 일반 함수는 수동 span, **completed ≠ 정답**
- 1-2 **flush ≠ 서버 조회**, 질문 말고 Trace ID, **GENERATION + end_time**
- 1-3 **규정 vs 업무 결과** 출처 분리, **부모 시간에 자식 포함**
- 1-4 **모르는 상태를 성공으로 채우지 않기**, simulation 분리 → 2장: 실패를 **평가 질문**으로
- 2장 전에 직접 해 볼 것: `01_trace.py` 질문을 "출장 숙박비 증빙"으로 바꿔 retrieve의 document_ids와 ChatOpenAI 입력 대조 / Tracing에서 `simulated-failure-case`를 열어 failure_category와 입력을 사례별로 대응.
