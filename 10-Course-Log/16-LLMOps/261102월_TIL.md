## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 평가 기준은 "정답 문장"이 아니라 "기대 행동" — 그리고 기준은 모델에 맞춰 바꾸지 않는다

| 원칙 | 이유 | 근거 교안 |
|---|---|---|
| 문장 완전 일치 대신 **terms · citations · abstain** | 생성 모델은 표현이 달라져 올바른 답도 실패 | 2-1 |
| 보류 질문은 **abstain=True**로 행동을 따로 요구 | 빈 배열만 있으면 아무 말이나 통과 | 2-1 |
| 등록 전 **형식 검사**(ID 중복 · 없는 출처 · 보류인데 terms 있음) | 기준 자체의 결함을 먼저 막음 | 2-1 |
| expected는 **expected_output**에만, 모델엔 question만 | input에 정답을 넣으면 모델이 정답을 보고 답함 | 2-1, 2-3 |
| **실패를 봤다고 기대값을 모델 출력에 맞춰 바꾸지 않기** | 평가 기준이 무너짐 | 2-1 |

- 테스트 케이스의 **기대 결과(Expected Result)** 를 실제 결과에 맞춰 고치는 건 QA에서 가장 위험한 습관이다. "버그가 아니라 스펙이에요"로 기대값을 바꾸려면 **근거(스펙 변경)** 가 있어야 하듯, Golden도 **규정이 바뀌었을 때만** 바꾼다(퀴즈 2-1: 경조사비 규정이 새로 생겨서 d05 · t03 추가).

### 2. 비교는 "하나만 바꾸고, 나머지는 기록으로 고정"

| 항목 | 이번 비교의 처리 | 바뀌면 생기는 문제 | 근거 교안 |
|---|---|---|---|
| 프롬프트 | 기준선 v1 · 후보 v2 | 비교할 변경 대상 | 2-2 |
| 질문과 규정 | 동일 (데이터 해시) | 난이도 · 근거 차이 혼입 | 2-2 |
| 모델과 패키지 | 같은 설정 · uv.lock | 생성 특성 변화 | 2-2 |
| 평가기 | rules-v2 (해시 기록) | 같은 답변도 다른 점수 | 2-2 |
| 3장 문맥 길이 | before/after만 다름 | 무엇을 줄였는지 모름 | 3-2 |

- **`label="latest"`로 비교하면 안 된다** — 퀴즈 2-2처럼 비교 도중 팀원이 새 버전을 등록하면 latest가 v3을 가리킨다. 게임 QA에서 "최신 빌드"가 아니라 **빌드 번호**로 테스트 대상을 지정하던 것과 같은 이유.
- 평가기를 바꾸면 **기준선과 후보를 둘 다** 다시 채점한다. 한쪽만 다시 계산하면 공정한 비교가 아니다.
- 실패해서 되돌릴 때도 프롬프트 하나가 아니라 **검증된 조합(코드 · 프롬프트 · 모델 · 문서 · 검색 설정)** 으로 돌아간다 (2-4, 3-4).

### 3. 오류 ≠ 0점 — "평가할 답이 없음"과 "평가 결과가 0"을 구분한다

| 상황 | 처리 | 근거 교안 |
|---|---|---|
| 완료됐지만 출처가 틀림 | **0점 = 정상 평가 결과**, 지우지 말고 비교에 포함 | 2-3 |
| API 실패 · 응답 미완료 | 평가할 답이 없음 — 0점으로 채우지 않음 | 2-3 |
| 평가기 실패 | 행은 남고 `INCOMPLETE_EVALUATION` → 03이 `EXPERIMENT_HAS_ERRORS` | 2-3 |
| Task 실패 | SDK가 **행을 결과에서 뺌** → 03은 정상 종료될 수 있고 04의 ID 검사가 막음 | 2-3 |
| 비교할 ID 누락 · 중복 | `ValueError` — 누락 항목을 0으로 채우지 않음 | 2-4 |

- 마지막 두 줄이 특히 중요하다. **실패한 행이 조용히 사라지면** 남은 행만으로 평균이 계산돼 결과가 좋아 보인다. 교안도 "SDK 4.17에서 직접 확인, 교안 문장과 달라요"라고 적어 둘 만큼 실제 동작을 확인한 부분이다. 테스트 리포트에서 **실행 수(분모)가 계획과 같은지**부터 확인하는 것과 같다 — 퀴즈 2-3의 `expected_ids − got_ids`.

### 4. 분모와 표본 수를 숫자 옆에 같이 적는다

| 지표 | 분모 | 함께 적을 것 | 근거 교안 |
|---|---|---|---|
| 오류율 | **전체 요청** | 미확인 비율 | 3-1 |
| 완료 지연 p50/p95 | 완료 요청 중 지연값이 있는 것 | `latency_count` | 3-1 |
| 알려진 비용 | 비용값이 있는 요청 (실패 요청 포함) | `cost_coverage` | 3-1 |
| 피드백 응답률 | 전체 요청 (N) | — | 3-3 |
| 응답자 긍정 비율 | 피드백이 있는 요청 (R) | 응답률 | 3-3 |

- **표본 3건이면 p95 = 최댓값**, 2건이면 p50 = 두 값의 평균·p95 = 큰 값. p95가 최댓값이 아니게 되려면 **완료 20건**부터 (Claude가 nearest-rank 식으로 확인: n=19 → 위치 18 = 최댓값, n=20 → 위치 18 = 뒤에서 두 번째).
- 피드백 미응답을 긍정으로 넣으면 3/4처럼 보이지만 실제로 받은 긍정은 1건. 피드백이 전혀 없으면 만족도를 0%나 100%로 채우지 말고 **미확인.**
- 게임 QA의 "통과율 95%"도 **몇 건 중 몇 건인지, 미실행(Blocked) 건은 어떻게 셌는지** 없이는 의미가 없었던 것과 같다.

### 5. 같은 이름의 숫자라도 "어느 구간"을 쟀는지 밝힌다

| 값 | 범위 | 근거 교안 |
|---|---|---|
| `latency_ms` | `answer()` 안의 perf_counter — 검색 + 입력 구성 + 네트워크 + 모델 대기 (flush 제외) | 3-2 |
| ChatOpenAI 시간 | 모델 호출 구간 (Langfuse 서버 표시) | 3-2 |
| 요청 비용 | **GENERATION의 total_cost**만 합산 (부모 span과 더하면 중복) | 3-4 |
| 화면의 `$0.00` | 표시 자릿수 반올림 — **무료가 아님** | 3-4 |

- 어느 시간을 쟀는지 밝히지 않으면 **서로 다른 값으로 개선률을 계산**하게 된다. 1장의 "부모 시간에 자식 시간 포함"과 같은 원칙이 비용에도 적용된다.

### 6. 판정은 "다음 행동"으로 이어져야 한다

| 판정·경보 | 다음 행동 | 근거 교안 |
|---|---|---|
| BLOCK | 해당 질문 Trace와 기대값 검토 | 2-4 |
| CHECK_HOLDOUT | 후보만 별도 질문으로 확인 (holdout 2건 호출) | 2-4 |
| REVIEW | 답변 · 더 넓은 표본 · 운영 조건 검토 — **자동 배포 아님** | 2-4, 3-4 |
| 경보 | 요청 수·미확인 비율 → 최근 변경·실패 Trace 대조 → 완화·복원 → **같은 사례로 재검증** | 3-4 |

- 경보에는 **지표 · 기간 · 임계값 · 최소 표본**이 같이 있어야 한다. 최소 표본이 없으면 "한 건이 느린 것"과 "계속 느린 것"을 구분하지 못한다.
- **배포 명령 성공 ≠ 사고 해결.** 복원 후에도 오류율과 사용자 기능을 다시 확인하고, 원인과 **새 평가 사례**를 남긴다. 게임 라이브 이슈 대응에서 핫픽스 후 **재현 케이스로 재검증**하고 회귀 목록에 추가하던 흐름과 같다.

### 7. Claude가 짚어준 확인 포인트

**① 내 2장 실행에서 rule_pass 25% → 100%의 정체는 "출처 표기" 하나였고, 그 대가로 토큰이 67% 늘었다**
- `result_03.json`의 실제 답변과 점수를 나란히 놓으면:

  | 질문 | 기준선 답변 | 기준선 점수 (terms / citation / behavior → pass) | 후보 답변 | 후보 pass |
  |---|---|---|---|---|
  | d01 | 식비는 하루 2만 원까지 지원되며, 영수증이 필요합니다. | 1 / **0** / 1 → 0 | …필요합니다. **[meal]** | 1 |
  | d02 | 출장 숙박비 한도는 1박당 10만 원입니다. 영수증이 필요합니다. | 1 / **0** / 1 → 0 | …1박 10만원입니다. **[travel]** | 1 |
  | d03 | 영수증과 수료증이 필요합니다. 교육비는 연간 20만 원까지 지원됩니다. | 1 / **0** / 1 → 0 | 영수증과 수료증이 필요합니다. **[training]** | 1 |
  | d04 | 제공된 근거만으로는 재택근무 지원금 금액을 확인할 수 없습니다. | 1 / 1 / 1 → 1 | 확인할 수 없습니다 | 1 |

- 기준선도 **필수 내용(required_terms)은 네 질문 모두 맞혔다.** 떨어진 건 citation_match 하나다. 그런데 기준선 프롬프트("사내 규정 질문에 짧게 답하세요. 주어진 근거를 참고하세요.")는 **출처를 붙이라는 지시 자체가 없었다.** 즉 이번 개선은 "답이 더 정확해졌다"가 아니라 **"출처 표기 형식을 지키게 됐다"** 이다. 교안도 "점수 차이는 '좋아졌다'가 아니라 어떤 출력 조건이 바뀌었는지로 설명한다"고 했는데, 내 실행이 정확히 그 사례다.
- 그리고 비용이 따라왔다 (Claude가 `usage`를 합산):

  | | 입력 토큰 합 | 출력 토큰 합 | 합계 |
  |---|---|---|---|
  | 기준선 (4건) | 263 | 106 | 369 |
  | 후보 (4건) | 539 | 76 | **615 (+67%)** |

  지시문이 길어져 **입력이 2배 이상**(평균 65.75 → 134.75) 늘었고, 답이 짧아져 출력은 줄었다. 3장이 던진 질문 "점수는 같은데 더 비싸고 느려졌다면?"의 반대 버전 — **점수는 올랐는데 더 비싸졌다.** 이 트레이드오프를 받아들일지는 rule_pass만으로 정할 수 없고, 3장 방식으로 비용·지연을 같이 놓고 판단해야 한다. 2-4의 REVIEW가 "사람 검토"인 이유이기도 하다.

**② 같은 식비 질문의 토큰은 세 번 모두 같았고, 지연은 세 번 모두 달랐다**
- 같은 질문("식비 한도와 필요한 서류는 무엇인가요?") + 같은 후보 지시문(POLICY) + 같은 근거가 들어간 실행이 세 번 있었다:

  | 실행 | 입력 토큰 | 출력 토큰 | latency_ms |
  |---|---|---|---|
  | 1장 `00_start.py` (10/30, 내 PC) | 138 | 26 | 2,502.8 |
  | 2장 후보 d01 (11/02, 내 PC) | 138 | 27 | 1,276.7 |
  | 3장 교안 실행 예시 q1 after | 138 | 26 | 1,175.2 |

- **입력 토큰은 입력이 같으면 항상 같다**(토크나이저는 결정적). 그래서 "문맥을 줄이면 입력 토큰이 줄어든다"는 3-2의 주장은 **한 번의 실행으로도** 검증된다 — 858 → 138의 −720토큰이 q1·q2 모두 정확히 같았던 것도 같은 이유다.
- 반면 **지연은 같은 입력에서도 2.1배까지 차이**가 났다(1,175 ~ 2,503ms). 그래서 3-2가 "① 입력 토큰은 바로 판단, ③ 지연은 더 많은 표본으로"라고 순서를 나눈 것이다. 측정값마다 **재현성이 다르다**는 걸 알고 있어야, 한 번 빨라진 결과로 원인을 단정하는 실수를 피한다. 게임 성능 테스트에서 프레임·로딩 시간은 여러 번 재서 분포로 보고, 데이터 크기·메모리 사용량은 한 번 재면 되던 것과 같은 구분이다.

**③ holdout 2건은 "쉬운 유형"만 있어서, REVIEW의 의미를 작게 읽어야 한다**
- `golden.json`을 보면 dev에는 **경계 사례 d03(증빙 두 가지 모두)** 이 있지만, holdout은 t01(정상, 금액 하나) · t02(규정 밖, 보류) 두 건뿐이다. 내 실행에서 후보가 출처를 제대로 붙이는지는 holdout t01("연간 20만원까지입니다. [training]")에서도 확인됐지만, **"두 가지를 모두 답해야 하는" 경계 유형은 holdout에 없다.**
- RAG 5일차에서 Claude가 짚었던 "test 질문이 모두 단일 문서라 검색 방법 차이를 구분할 수 없다"와 **같은 패턴**이다. dev에서 잡은 실패 유형이 holdout에 없으면, holdout 통과는 그 유형에 대해 아무것도 말해 주지 않는다.
- 그래서 holdout을 만들 때도 **dev에 있는 유형(정상 · 경계 · 보류)이 최소 하나씩** 들어가게 나누는 게 좋다. 교안이 "여섯 질문은 판정 논리를 익히는 크기"라고 선을 그은 이유도 이것이고, 실제 운영에선 **빈도 높은 질문 · 손실 큰 질문 · 과거 실패 · 보안 사례**를 추가한다.

## 2장. 평가 데이터와 변경 전후 검증

### 2-1 : Golden Dataset 설계와 등록
- **핵심 개념**:
  - 상황: 식비 질문 하나가 잘된다고 **규정 상담이 잘된다고 말할 수 없다.** 평가 데이터는 잘되는 질문을 모은 시연 목록과 다르다.
  - **정답 문장보다 기대 행동**: `terms`(필수 표현) · `citations`(출처 ID 집합) · `abstain`(보류 여부). 보류 질문의 빈 배열은 누락이 아니라 "요구하지 않음"이고, 그래서 **abstain=True로 보류 행동을 따로 요구.**
  - 질문 6개:
    | id | split | kind | 질문 | terms | citations | abstain |
    |---|---|---|---|---|---|---|
    | d01 | dev | normal | 식비 한도와 필요한 서류는? | 2만원 · 영수증 | meal | false |
    | d02 | dev | normal | 출장 숙박비 한도는 얼마? | 10만원 | travel | false |
    | d03 | dev | **boundary** | 교육비를 받으려면 어떤 서류가? | 영수증 · 수료증 | training | false |
    | d04 | dev | unanswerable | 재택근무 지원금은 얼마? | — | — | true |
    | t01 | holdout | normal | 교육비 지원 한도는 얼마? | 20만원 | training | false |
    | t02 | holdout | unanswerable | 반려동물 의료비도 지원되나요? | — | — | true |
    - d03(경계) = **1장의 "수료증 누락"이 평가 질문이 된 것.**
  - **dev = 결과를 보고 프롬프트를 고치는 용, holdout = 후보를 고른 뒤 확인용.** holdout을 볼 때마다 지시문을 고치면 그 질문도 사실상 dev가 된다.
  - Langfuse 저장 위치: `id · question` → **input**(Task가 사용) / `expected` → **expected_output**(Evaluator만, 모델은 못 봄) / `split · kind` → **metadata**(사람용).
  - 등록 전 `validate`: ID 중복 금지(두 실험을 연결하는 키), citations는 **실제 문서 ID 안에서만**, 보류 질문에 terms · citations가 있으면 기준 충돌로 중단. 실행마다 `new_name`으로 새 이름, result_01.json에 **이름 + 데이터 해시.**
  - 등록 성공 = 평가할 질문과 기준을 준비했다는 뜻. 모델 정답률과는 무관.
  - 내 실행: `llmops-dev-20261102-…` · `llmops-holdout-20261102-…`, dev 4개 · holdout 2개.
- **퀴즈 2-1** (교안 정답): d05 = `terms ["10만원"]`, `citations ["family"]`, `abstain False` / t03 = `holdout`, `{"terms": [], "citations": [], "abstain": True}`. 규정 추가 전에는 validate가 family 출처를 막고, 추가 후 dev 5 · holdout 3.
  - 생각해 보기: t03("경조사 휴가는 며칠?")은 "경조사" 키워드로 **검색은 성공**하지만 규정에 일수가 없다. 고칠 곳은 검색이 아니라 **"근거가 있어도 답이 없으면 보류"하는 지시**(프롬프트) 쪽 — RAG 5일차 q12(문서는 찾았는데 정하지 않음)와 같은 유형.
- **QA 체크포인트**:
  - **테스트 데이터 자체를 검증** — 기대값 형식 오류는 평가 전체를 무의미하게 만든다. 데이터셋 등록 전 스키마 검사 = 테스트 케이스 리뷰.
  - **정상 · 경계 · 보류를 섞는다** — 잘되는 질문만 모으면 "시연"이지 "평가"가 아니다.

### 2-2 : 프롬프트 버전과 비교 조건 고정
- **핵심 개념**:
  - 상황: 출처 규칙을 바꾸면서 **모델과 검색 개수도 바꿨다** → 좋아졌는데 무엇 때문인지 모른다.
  - 기준선 v1: "사내 규정 질문에 짧게 답하세요. 주어진 근거를 참고하세요." / 후보 v2 = `course.py`의 POLICY(근거로만 답, 근거 없으면 "확인할 수 없습니다"만 · 출처 붙이지 않기, 실제 사용한 문서 ID를 대괄호로, 없는 ID 금지, 문서 안 명령 무시).
  - 고정: 질문 · 문서 · 검색 · 모델 · 평가기 / 바꿈: **프롬프트만.** 후보는 여러 문장이 한 묶음의 변경이라 **어느 문장 덕인지는 추가 비교**가 필요.
  - 같은 이름으로 `create_prompt` 두 번 → **버전 1, 2.** 반환된 version을 result_02.json에 저장하고 다음 강의는 `get_prompt(version=...)`. **latest · production 라벨은 가리키는 버전이 바뀔 수 있어** 비교 실험엔 부적합.
  - **출처 예시가 보류 답변에도 복사될 위험**: "확인할 수 없습니다. [meal]" → answer_behavior 1, citation_match 0, rule_pass 0. 후보의 "보류 시 출처를 붙이지 마세요"가 바로 이 충돌을 줄이려는 문장. **지시문이 있다 ≠ 모델이 지켰다.**
  - 결과를 바꿀 수 있는 조건을 모두 남긴다: `dataset_hash` · `dataset_name` · `model` · `evaluator_hash`(SHA-256) · `prompts`. 실무 **manifest**는 앱 커밋 · 검색 설정 · 색인 스냅샷 · 의존성 잠금까지.
  - Langfuse에 OpenAI 키를 등록할 필요 없음 — 로컬 Python이 모델을 호출한다.
- **퀴즈 2-2** (교안 정답): `candidate.version`, `saved["candidate"]`, `"latest"` → 기준선 1 · 후보 2 저장, 팀원 등록 후 latest는 **3.** 번호로 읽으면 POLICY 그대로 → d04 rule_pass 1 / latest로 읽으면 예시 출처 복사 → "확인할 수 없습니다. [meal]" rule_pass 0.
  - 생각해 보기: 팀원 버전을 고쳐 d04가 통과하게 돼도, 그 v3은 **v2와 다시 같은 조건으로 비교**해야 한다 — "latest가 좋아졌다"는 어느 버전 대비인지가 빠진 말이다.
- **QA 체크포인트**:
  - **테스트 대상 버전 고정** — "최신 빌드"가 아니라 "빌드 번호"로 (🧭 2).
  - **설정 해시로 재현성 확보** — 같은 이름의 평가기도 내용이 바뀌면 다른 평가기다.

### 2-3 : Python 평가와 Langfuse 실험 실행
- **핵심 개념**:
  - 상황: 답변이 자연스러운데 **출처가 없다.** 점수 하나로는 무엇이 부족한지 모른다 → 필수 내용 · 출처 · 보류 행동을 **나눠** 계산.
  - **Task** = 데이터셋 항목의 question → 기존 `answer()` 실행(expected_output은 모델에 넘기지 않음) / **Evaluator** = Task 출력 + expected_output을 받는 **Python 함수**(계산은 내 PC, Langfuse는 저장). 평가용 LLM 호출 없음. `max_concurrency=1`, 자동 재시도 없음. metadata에 `prompt_name · prompt_version · evaluator=rules-v2`.
  - 네 점수: **required_terms**(필수 표현 모두) · **citation_match**(출처 ID **집합이 같은지** — [meal][travel]처럼 엉뚱한 출처를 더해도 실패, [fake_1] · [SECRET]도 검사) · **answer_behavior**(보류 여부 일치) · **rule_pass**(셋 다).
  - 정규화: **공백 제거**(2만 원 → 2만원), **쉼표 제거**(20,000 → 20000). 보류는 **"확인할수없" 고정 표현**만 검사.
  - **문자열 규칙의 한계**: "2만원이 아닙니다"에도 2만원이 포함 / "20,000원"처럼 표기가 다르면 실패 가능 → **빠른 회귀 검사**일 뿐, 통과한 답변도 표본으로 읽기. rule_pass comment: "의미 정확성 전체를 보장하지 않음."
  - **오류 ≠ 0점**: 🧭 3 표 참고. LLM judge는 비용 · 편향 · 일관성 문제 → 결정적 검사와 사람 검토부터(5장).
  - 내 실행: 기준선 d01~d03이 citation 0 → rule_pass 0, d04만 1 / 후보 4건 모두 rule_pass 1 (🧭 7-①).
- **퀴즈 2-3** (교안 정답): `dataset.items`, `report["rows"]`, `expected_ids - got_ids` → API 오류 · 응답 잘림은 **행이 사라져** missing으로 찾고, 평가기 실패는 행은 남고 error 표시. 실제 03_evaluate.py는 error만 검사해서 앞의 두 경우를 '완료'로 끝낼 수 있다.
  - 생각해 보기: 두 건이 실패하면 03은 2건만 남은 결과로 정상 종료될 수 있고, 04의 "양쪽 4개 · ID 집합 동일" 검사에서 멈춘다. 03에 넣는다면 `experiment()` 결과를 받은 **직후, 저장 전**에 넣는 게 맞다 — 잘못된 결과 파일이 다음 단계로 넘어가기 전에 막기 위해.
- **QA 체크포인트**:
  - **평가 축 분리** — 하나의 Pass/Fail보다 실패 원인별 체크 항목이 디버깅에 유리 (게임 QA 체크리스트를 항목별로 나누던 것과 같다).
  - **분모 검증** — 실행 계획 수와 결과 행 수가 같은지 먼저 (🧭 3).
  - **자동 판정의 범위를 문서화** — 무엇을 보장하지 않는지를 점수 comment에 남긴다.

### 2-4 : 변경 전후 비교와 회귀 판정
- **핵심 개념**:
  - 상황: 후보의 **평균 점수가 올랐는데** 규정 밖 질문 하나에 **잘못된 출처**가 붙었다 → 평균 + 개별 질문 + 중요 사례 + 실행 오류를 같이 본다.
  - **목록 순서가 아니라 같은 질문 ID끼리**: Langfuse가 돌려주는 순서는 입력 파일 순서와 다를 수 있다. zip으로 위치끼리 묶으면 d01 기준선 ↔ d04 후보를 비교하게 된다. 비교 전 **양쪽 4개 · 중복 없음 · ID 집합 동일** 확인, 누락을 0으로 채우지 않음.
  - `delta = 후보 rule_pass − 기준선 rule_pass`, `accepted = (후보 통과 4건) and (min(delta) ≥ 0)` → `CHECK_HOLDOUT` 아니면 `BLOCK`. 오류나 점수 누락이 있어도 BLOCK.
  - **CHECK_HOLDOUT일 때만** 후보 버전으로 holdout 2건 호출 → 모두 통과면 **REVIEW**, 아니면 BLOCK. **REVIEW ≠ 자동 배포.** 네 질문의 작은 차이에 통계적 우월성을 붙이지 않는다(표본이 크면 paired 비교 · 사례 종류별 · 신뢰구간).
  - 실제 실행(교안·내 PC 동일): 기준선 d01~d03 = 0, 후보 4건 통과 → delta {d01: +1, d02: +1, d03: +1, d04: 0} → CHECK_HOLDOUT → holdout t01 "연간 20만원까지입니다. [training]", t02 "확인할 수 없습니다" 모두 통과 → **최종 REVIEW.** Compare 화면: rule_pass 25% → 100%(+75%p), 녹색 3 = 개선 3건, 빨강 0 = 악화 없음.
  - holdout은 **별도 데이터셋** — dev 집계에 합치지 않는다. 이번 코드는 비교와 판정까지만, 배포 · CI · production 라벨 변경은 하지 않는다.
- **퀴즈 2-4** (교안 정답): `critical`, `len(after)`, `min_rate` → 평가셋 6건, 일반 질문 1건 악화는 83%로 통과, 2건 악화는 67%로 BLOCK, 중요 질문은 1건만 악화돼도 통과율과 상관없이 BLOCK.
  - 생각해 보기: 기준을 결과를 본 뒤에 정하면 **원하는 결론에 맞춰 기준을 고르게** 된다(예: 0.8을 0.67로 낮춰 통과시키기). 그래서 중요 사례 목록과 최소 통과율은 실행 전에 합의한다.
- **QA 체크포인트**:
  - **회귀 = 이전에 되던 것이 깨짐** — 개선 건수보다 악화 건수가 판정을 막는다. 빌드 회귀 테스트와 같은 원리.
  - **중요도 가중치(critical)** — 모든 실패가 같은 무게가 아니다. 게임 QA의 버그 심각도(Critical/Major/Minor)에 따라 출시 차단 여부가 달랐던 것과 같다.
  - **사전 합의된 출시 기준(Exit Criteria)** — 결과를 보고 기준을 바꾸지 않는다.

## 3장. 운영 지표 분석과 개선

### 3-1 : 운영 지표의 정의와 누락값 처리
- **핵심 개념**:
  - 한 지표로 운영 상태를 설명할 수 없다: **품질**(답이 맞나) · **지연**(얼마나 기다렸나) · **오류율**(얼마나 처리 못 했나) · **토큰·비용**(자원을 얼마나 썼나).
  - **SLI** = 실제로 측정하는 지표, **SLO** = 일정 기간 지키기로 한 목표 → 요청 범위 · 측정 구간 · 기간을 함께 정의. 모델 호출 두 번이 포함된 요청 하나를 두 건으로 세면 다른 지표가 된다.
  - 모의 요청 5건:
    | 요청 | 상태 | 지연 ms | 비용 $ |
    |---|---|---|---|
    | A | completed | 100 | 0.001 |
    | B | completed | 200 | 0.002 |
    | C | completed | 900 | None |
    | D | failed | 300 | 0.001 |
    | E | unknown | None | None |
    - 오류율 → A~E 5건 / 완료 지연 → A·B·C / 알려진 비용 → A·B·D. **실패한 D에도 비용**, 완료한 C는 비용을 모름.
  - 완료 3/5 · 명시적 실패 1/5 · 미확인 1/5. unknown 후보: 수집 지연 · 중단 · 취소 · 기록 누락. 미확인 한 건을 빼고 1/4로 계산하면 **질문 자체가 달라진다.** 실제 요청과 모의 요청의 지표도 섞지 않는다.
  - **p50 / p95**: 완료 3건 정렬 100 · 200 · 900 → p50 = 200, p95 위치 = 올림(0.95 × 3) − 1 = 2 → **900(최댓값).** 표본 3건의 p95를 SLA로 해석하지 않는다. 같은 p95라도 집계 방식이 다를 수 있으니 대시보드와 코드의 산식을 맞춘다.
  - **모르는 비용을 0원으로 채우지 않는다**: known_cost_usd = 0.004(A+B+D), cost_coverage = 0.6, total_cost_usd = **None.** 숫자 0 = 확인된 무료, None = 모름. 알려진 비용을 평균으로 확대하는 것도 누락이 무작위라는 근거가 없으면 편향.
  - 실행 결과(`01_metrics.py`, 외부 호출 없음): requests 5 · completed 3 · errors 1 · unknown 1 · error_rate 0.2 · p50 200 · p95 900 · latency_count 3 · known_cost 0.004 · coverage 0.6 · total None. Langfuse에 Trace가 생기지 않는다.
- **퀴즈 3-1** (교안 정답): `limit_ms`, `"timeout"`, `before["completed"] / before["requests"]` → 장애인데 p95가 **900 → 200**으로 좋아져 보이고, timeout은 failed가 아니라 오류율 0 · 미확인 2건. 완료율 18/20을 함께 봐야 장애를 구분한다.
  - 생각해 보기: 전부 시간 초과면 p95가 None → `None < 숫자` 비교에서 오류가 나므로 **p95가 None인지 먼저 검사**해야 한다. timeout을 failed로 세면 오류율이 올라가 장애가 바로 드러나지만, "느려서 끊김"과 "명시적 실패"가 섞인다 — 별도 상태로 세면서 **오류율 + 미확인률을 같이** 보는 게 낫다.
- **QA 체크포인트**:
  - **생존자 편향(survivorship bias)** — 성공한 것만 측정하면 좋아 보인다. 테스트 리포트에서 Blocked · 미실행을 Pass로 세지 않는 것과 같다.
  - **표본 크기와 백분위수** — 작은 표본의 p95는 최댓값일 뿐 (🧭 4).

### 3-2 : 토큰과 지연을 실제 요청에서 측정
- **핵심 개념**:
  - 상황: 규정 한 문장으로 답할 질문인데 **무관한 설명이 길게** 들어간다 → CE의 입력 절약을 **운영 관점으로 검증.**
  - 같은 질문 2개(식비 · 출장 숙박비)에 **문맥 길이만** 바꾼다: before = 규정 뒤 "참고: 회사 정원에는 나무가 있습니다." **60회**, after = 그 문장만 제거. 질문마다 before/after를 **번갈아** 실행(시간 순서 효과 감소). `cost_usd = None`(임의 단가 적용 안 함).
  - 교안 실행 예시:
    | 질문 | 버전 | 입력 토큰 | 출력 토큰 | 지연 ms |
    |---|---|---|---|---|
    | q1 | before | 858 | 26 | 1733.0 |
    | q1 | after | 138 | 26 | 1175.2 |
    | q2 | before | 860 | 23 | 1302.8 |
    | q2 | after | 140 | 22 | 1162.8 |
    - 입력 −720토큰(두 질문 모두 같은 양), 출력은 거의 같음 → **줄어든 것은 입력.** 지연은 비례하지 않음(q1 −557.8ms, q2 −140.0ms).
  - `usage_metadata`의 실제 토큰을 읽는다(글자 수 × 비율 추정 X). 사용량이 없으면 None 유지.
  - **측정 구간**: `latency_ms` = `answer()`의 perf_counter(검색 + 입력 구성 + 네트워크 + 모델 대기, flush 제외) / ChatOpenAI 시간 = 모델 구간(서버 표시).
  - **적은 표본은 원인을 탐색하는 증거**: 버전당 두 건, 네트워크·부하 통제 X → 통계적 성능 향상이라고 말하지 않는다. 순서: ① 입력 토큰이 줄었나 ② 사실과 출처가 유지됐나 ③ 지연은 더 많은 표본으로. after가 더 느리게 나와도 숨기거나 빠르게 나올 때까지 반복해서 고르지 않는다.
  - Usage breakdown: before 858 + 26 = **884**, after 138 + 26 = **164.** ChatOpenAI Preview에서 식비 한도 · 영수증 · [meal] 유지 확인.
- **퀴즈 3-2** (교안 정답): `ALL_DOCS`, `padding`, `"answer"` → all_docs면 두 질문 모두 입력 토큰 증가, q1은 출처가 meal 하나에서 세 문서로, q2는 **검색은 비었는데 답변에 출처가 붙음** → document_ids만 보면 놓친다.
  - 생각해 보기: 비용이 늘어난 만큼 **정답률이나 보류 정확도**가 좋아져야 받아들일 수 있다. 그런데 q2처럼 규정 밖 질문에도 출처가 붙으면 오히려 2장의 citation_match · answer_behavior가 **악화**된다 — 비용과 품질이 둘 다 나빠지는 제안.
- **QA 체크포인트**:
  - **하나만 바꾸는 통제 실험** — 압축 알고리즘 평가가 아니라 "불필요한 입력"의 영향만 본다. 중요한 승인 조건을 지워 토큰이 줄었다면 개선이 아니다.
  - **결정적 지표와 확률적 지표 구분** — 토큰은 한 번으로, 지연은 분포로 (🧭 7-②).
  - **불리한 결과를 숨기지 않기** — "빠를 때까지 다시 재기"는 결과 조작이다.

### 3-3 : 오류율과 사용자 피드백 해석
- **핵심 개념**:
  - 상황: API 호출은 **모두 성공**했는데 사용자는 **만족하지 않는다.** 기술적 오류율(실행이 끝났나) ≠ 사용자 피드백(업무에 도움이 됐나) — 둘을 하나의 성공률로 합치면 원인이 흐려진다.
    | 상황 (설명용) | 오류율 | 사용자 신호 |
    |---|---|---|
    | 네 건 모두 완료, 한 답변이 너무 길어요 | 0% | 불만이 생길 수 있음 |
    | 서버 오류 한 번, 나머지는 정상 답변 | 25% | 나머지 답변은 도움이 됐을 수 있음 |
  - **피드백도 요청 ID에**: 2강의 네 Trace 중 두 개에 `demo_feedback`(BOOLEAN) 연결 — 모델 재호출 없음, comment에 "수업용 모의 피드백". **질문 문장이 아니라 trace_id**에 붙인다(새로 생성한 Trace에 붙이면 사용자가 본 답변과 다른 실행을 평가). 다시 실행하면 같은 이름의 점수가 추가될 수 있다.
  - **응답률과 만족도는 분모가 다르다**: N=4, R=2, P=1 → 응답률 R/N = 50%, 응답자 긍정 비율 P/R = 50%(우연히 같을 뿐 다른 지표). 피드백을 남기는 사람은 만족하거나 불만이 큰 쪽으로 치우칠 수 있어 전체 만족도로 확대하지 않는다.
  - **낮은 점수에서 평가 데이터로**: 낮은 점수 → Trace 열기 → 원인 분류(내용·출처·지연) → **익명화** → dev에 추가 → 2장 회귀 검사. 원문 피드백을 그대로 복사하지 않는다(개인정보, 4장). "너무 길어요"에 글자 수만 줄이면 조건이 빠진 짧은 오답을 고를 수 있다. 부정 의견만 모으지 말고 **정상 사례도 유지.**
  - Trace 전체에 연결된 점수라 **Trace 상단**에서 본다(2장 평가 점수는 task observation에 있었음). 트리의 ChatOpenAI · ChatPromptTemplate 표시 순서는 실행 순서가 아니다 — 시각으로 확인.
- **퀴즈 3-3** (교안 정답): `known`, `f'{c["trace_id"]}-{c["user"]}'`, `len(rows)`, `len(scores)` → 더블 클릭은 한 표로, 마음을 바꾸면 마지막 값으로, 한 답변에 두 사람은 두 표, 응답률은 Trace 기준 **0.25**, 지난주 Trace는 제외, 클릭이 없으면 긍정 비율 None.
  - 생각해 보기: score_id를 trace_id만으로 만들면 **같은 답변에 두 사람이 누른 표가 하나로 덮어써진다**(다른 사용자의 의견이 사라짐). 03_feedback.py를 두 번 실행할 때 점수가 추가되는 것도 score_id를 지정하지 않아서 매번 새 점수로 쌓이기 때문.
- **QA 체크포인트**:
  - **멱등성(idempotency) 설계** — 같은 클릭이 여러 번 들어와도 결과가 같아야 한다. score_id 설계 = 중복 판단 기준 설계 (RAG 3일차 uuid5와 같은 원리).
  - **피드백 → 회귀 케이스 순환** — 게임 라이브 서비스에서 유저 CS 문의를 재현 케이스로 만들어 회귀 목록에 넣던 흐름과 같다. 단, **익명화가 먼저.**

### 3-4 : 지표 기반 개선 판단과 운영 대응
- **핵심 개념**:
  - 상황: 입력 토큰은 줄었지만 **사용자 불만이 늘었다** → 필요한 예외 조건까지 지운 압축이면 비용 절감만으로 유지 불가.
  - **집계에서 개별 실행으로**: ① 요청 수가 같은가 ② 같은 case_id의 토큰 · 지연 · 답변 ③ 차이가 큰 Trace의 근거와 생성 구간. 같은 환경 · 기간 · app_version을 먼저 맞춘다.
    | 지표 (교안 실행 예시) | before | after |
    |---|---|---|
    | requests | 2 | 2 |
    | p50_ms | 1517.9 | 1169.0 |
    | p95_ms | 1733.0 | 1175.2 |
    | total_cost_usd | 0.0004024 | 0.0001132 |
    | cost_coverage | 1.0 | 1.0 |
    - 버전당 2건이라 p50은 두 값의 평균, p95는 큰 값 (Claude가 계산해 확인: median(1733.0, 1302.8) = 1517.9).
  - **확인된 비용만 합산**: Trace를 서버에서 재조회해 **GENERATION의 total_cost**만 모은다(부모 span과 더하면 중복). **하나라도 None이면 요청 비용 전체를 None.** 화면의 `$0.00`은 반올림 표시. `sleep(2.1)`은 무료 계정 조회 제한 간격(재호출 코드 아님). 서버 비용은 청구서와 완전히 같은 회계 자료로 보장되지 않는다.
  - **변경 판단에 품질 조건을 같이**:
    | 관측한 변화 | 바로 결론 내리면 안 되는 이유 | 다음 판단 |
    |---|---|---|
    | 토큰 감소, 필수 증빙 누락 | 비용을 줄이며 품질을 잃음 | 후보 보류, 근거 복원 |
    | 토큰 감소, 두 번의 지연 증가 | 네트워크와 출력 길이 영향 가능 | 대표 질문으로 추가 측정 |
    | 알려진 비용만 감소, 파악률 하락 | 미확인 비용이 많아진 결과일 수 있음 | 수집과 가격 인식부터 확인 |
    | 사실과 출처 유지, 토큰 감소 | 두 질문의 확인에 한정됨 | 더 넓은 평가와 운영 조건 검토 |
    - 판정 **REVIEW**(버전당 2건) — decision은 코드에 고정된 값이고, 코드가 사실 정확성을 입증한 게 아니다.
  - **경보는 행동으로**: 지표 · 기간 · 임계값 · 최소 표본 → 요청 수·미확인 비율 → 영향 범위(기능·환경·버전) → 최근 변경·실패 Trace 대조 → 완화·복원(검증된 조합) → 같은 사례로 재검증. error budget(99% 목표면 1%가 허용 실패량) · burn rate도 함께 볼 수 있다.
  - **복원할 때 무엇을 되돌릴까**: 코드 · 프롬프트 버전 · 모델 설정 · 문서·색인 · 검색 설정 — **검증된 조합을 통째로.** 프롬프트만 되돌려도 색인·모델이 바뀌었다면 이전 동작이 돌아오지 않는다. 규정이 정당하게 개정됐는데 옛 답변을 되살리면 올바른 복원이 아니다.
  - ChatOpenAI 행 비교: before 약 1.72초 · $0.000203, after 약 1.17초 · $0.000059.
- **퀴즈 3-4** (교안 정답): `o.type.upper() == "GENERATION"`, `min_samples`, `1.0` → 버전당 2건이면 "REVIEW: 표본 부족", 가격을 모르는 후보는 비용 None → "싸졌다"가 아니라 "REVIEW: 비용 미확인", 부모 span 비용(0.0009)을 더하면 요청 비용이 부풀어요.
  - 생각해 보기: 가격 미확인 모델을 0원으로 치면 total_cost가 줄어 **"유지 후보"로 잘못 통과**한다. 품질 조건(필수 사실 검사)은 비용 판단 **앞**, 표본 수 검사 바로 다음에 넣어야 한다 — 품질이 깨졌으면 비용을 볼 필요도 없이 막아야 하므로.
- **QA 체크포인트**:
  - **판정 순서 = 우선순위** — 1장 1-4 실패 분류처럼, 먼저 검사한 조건이 결과를 정한다. 표본 부족 → 품질 → 비용 미확인 → 비용 증가 순서는 "무엇이 더 치명적인가"의 합의다.
  - **롤백 범위 정의** — 게임 패치 롤백에서 클라이언트만 되돌리고 서버 데이터는 그대로면 문제가 남던 것과 같다. 되돌릴 단위는 "검증된 조합."
  - **재검증까지가 대응** — 경보 → 조치 → 같은 케이스로 확인 → 회귀 목록 추가.

## 정리 — 2장 · 3장 결과물

- 2-1 **기대 행동**(terms · citations · abstain), 정상 · 경계 · 보류, **dev ≠ holdout**
- 2-2 **버전 번호로 고정**, 프롬프트만 바꾸고 나머지는 해시로 기록
- 2-3 **Task ≠ Evaluator**, 네 점수로 원인 보기, **오류 ≠ 0점**, 문자열 규칙의 한계
- 2-4 **ID로 짝짓기**, 평균이 올라도 악화가 있으면 **BLOCK**, 통과해도 **REVIEW**
- 3-1 **단위 · 분모 · 기간**, unknown과 None을 채우지 않기, 작은 표본의 p95를 과장하지 않기
- 3-2 **실제 사용량**, 어느 구간의 지연인지 명시, 입력 절약과 품질 유지를 함께
- 3-3 **API 성공 ≠ 만족**, 피드백은 원래 Trace에, 응답률과 긍정 비율의 분모
- 3-4 **확인된 비용만**, 경보 → 완화 · 복원 → 재검증
- 4장 예고: 기록에 개인정보가 남는다면? 모델이 형식을 어기거나 권한 밖 문서를 읽는다면? → 신뢰 경계와 권한 통제 · 마스킹 · 출력 검증 · 지시 주입 평가
- 직접 해 볼 것: `llmops_ch02/result_03.json`에서 d04 답변 두 개 비교(기준선 "제공된 근거만으로는 … 확인할 수 없습니다" vs 후보 "확인할 수 없습니다") / `llmops_ch03` 01~04 실행 후 `result_04.json`에서 같은 case_id의 토큰 · 지연 · 비용 나란히 읽기.
