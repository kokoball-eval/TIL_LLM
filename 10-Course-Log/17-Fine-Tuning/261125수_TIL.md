## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | 형식 검사 | format check | JSON으로 읽히나(①) · 키와 타입과 상태 규칙(②) · 인용 ID가 준 문서 안인가(③)를 **차례로** 보는 자동 검사 |
  | 업무 의미 | business meaning | 금액 비교 · 승인 시점 · 근거 적용이 맞는지. **사람이 원문을 읽어서** 판단 |
  | 참조 일치 | reference exact match | 모범답안 객체와 **완전히 같은가**. 가장 좁은 기준이라 표현만 다른 맞는 답도 불일치가 됨 (교안 코드에는 없음) |
  | JSON | JavaScript Object Notation (자바스크립트 객체 표기법) | 응답 계약의 형식. 코드 펜스를 벗겨서 통과시키지 않음 |
  | 스키마 | schema | 필드 이름 · 타입 · 값 규칙의 약속 (`schema_ok`) |
  | API | Application Programming Interface (응용 프로그램 인터페이스) | 프로그램끼리 정해진 입력과 출력을 주고받는 접점. 여기서는 `/answer` 경로 |
  | HTTP | HyperText Transfer Protocol (하이퍼텍스트 전송 규약) | 웹 요청 · 응답 규약. 상태 코드로 결과를 알림 |
  | 200 / 422 / 502 | OK / Unprocessable Entity / Bad Gateway (정상 / 처리할 수 없는 요청 / 잘못된 게이트웨이 응답) | 이 수업에서: 형식 통과 / 입력 거절 / 생성 결과 형식 실패 |
  | FastAPI | FastAPI (파이썬 웹 API 프레임워크) | `/answer` 경로를 만드는 도구 |
  | Pydantic | Pydantic (데이터 검증 라이브러리) | 요청 모델(`AnswerRequest`)의 타입 · 길이 · 여분 필드를 검사 |
  | TestClient | TestClient (테스트용 클라이언트) | 외부 서버를 열지 않고 같은 프로세스에서 API에 시험 요청 |
  | RAG | Retrieval-Augmented Generation (검색 증강 생성) | 검색한 근거를 넣어 생성. 이번 검색은 벡터 검색이 아니라 **낱말 겹침** |
  | 후보 인수인계서 | candidate manifest | 다음 장에 넘기는 후보 · 지문 · 설정 · 알려진 실패 기록 (`candidate_manifest.json`) |
  | dev / test | development / test set (개발 / 시험 자료) | dev는 이미 여러 번 본 자료, test는 8장 최종 평가까지 열지 않음 |
  | SHA-256 | Secure Hash Algorithm 256-bit (보안 해시) | 6장과 7장에 **같은 파일**을 넣었는지 확인하는 지문 |

- **핵심 통찰: 7장은 학습하지 않고, 채점하고 연결한다 — 한 답을 세 가지 질문으로 따로 채점한다**
  - 생성 원문(고치지 않고 보관) → **형식 검사**(자동) → **업무 의미**(사람이 원문 읽기) → **참조 일치**(교안 코드에는 없음). 점수를 말할 때는 **검사 이름과 분모**를 같이 말한다(예: “형식 통과 12/12”, “원문 검토로 초과 2문항 오답”).
  - 셀 6의 반례: `{"status": "answered", "answer": "70,000원은 65,000원 이하이므로 사전 승인이 필요하지 않습니다.", "citations": ["policy01-v1"]}`는 세 관문이 모두 True지만 **업무 의미는 틀렸다**(70,000 > 65,000이므로 예약 전 서면 승인). 형식 검사는 숫자의 대소 관계 · 승인 시점 · 근거가 부족한 이유를 보지 못한다.

- **두 번째 통찰: 다섯 방법을 같은 시험지로 다시 채점하되, 종합 순위로 합치지 않는다**

- **세 번째 통찰: API의 "200"은 업무 정답이 아니다 — 입구는 엄격하게, 출구는 정직하게**
  - `/answer`는 ① 입력 검사(`AnswerRequest`, 위반 시 422) → ② 검색(없으면 빈 목록) → ③ 생성(3장 SFT, 학습된 유일한 칸) → ④ 출력 검사(형식 통과 200 / 실패 · 잘림 502) 순서다. 응답 본문에는 항상 `review_required: True`를 붙인다.
  - 실제 호출에서 “숙박 80,000원” 요청은 `policy01-v2`를 찾아 **형식 통과 · 200**이었지만, “1박 80,000원은 한도 이하”라고 답해 **업무 판단은 틀렸다**(80,000 > 75,000). HTTP 코드만 보고 답이 맞다고 결론내리지 않는다.

- **네 번째 통찰: 실패 칸을 나누고 후보를 고정한다 — 후보 지정은 배포 승인이 아니다**
  - 실패를 **형식 · 검색 · 업무 판단 · 운영** 칸으로 나눈다. 후보는 코드에 `full_sft`로 고정되고, 알려진 실패를 그대로 남기며 `deployment_ready: False`, `test_used: False`다. dev는 이미 여러 번 본 자료라서 이 성과를 새로운 데이터에서의 성능이라고 말하지 않는다.

- **향후 계획 및 다짐**
  - `evaluation_and_connection.ipynb`는 **셀 출력이 비어 있는(실행 전) 상태**다. 그래서 7-3 API 호출 결과 같은 숫자는 **슬라이드의 실행 결과**(RTX 5060 Laptop · BF16 · seed 42 · dev 12 · 1회, T4 · L4는 미실측)다. 다만 7-1 · 7-2의 보고서 비교는 CPU로 되는 부분이라 **Claude가 올려 둔 내 보고서 4개로 그대로 재현**했다(🧭 4-① · ②).

  - 8장 전에 할 것(슬라이드 마지막 장): `evaluation_report.json` · `candidate_manifest.json` + SFT 입력 3개(`training_data.zip` · `sft_model.zip` · `sft_report.json`) 보관 → 8장은 이 다섯 파일에서 시작 → 원문 하나를 골라 실패 칸(형식 · 검색 · 업무 판단) 적어 보기.

### 2. 숫자 하나가 보는 범위를 적는다

| 지표 | 무엇을 보나 | 못 보는 것 | 근거 교안 |
|---|---|---|---|

### 3. 세 가지 채점 = QA의 세 가지 판정

| 채점 | QA로 바꾸면 | 이 장에서 |
|---|---|---|
| 형식 검사 | 스모크 테스트 (실행은 된다) | 자동, 셀 7 · 10 |
| 업무 의미 | 기능 검증 (기획 의도대로 동작하나) | 사람이 원문 읽기, 셀 11 |
| 참조 일치 | 골든 데이터와 완전 비교 | 교안 코드에는 없음 |

- 어느 하나도 다른 것을 대신하지 않는다. 형식이 완벽한 오답이 있고, 참조와 달라도 맞는 답이 있다.

| dpo | 4 · 4 · 2 | JSON 8 · 인용 2 | 0 · 0 · 0 | JSON 12 | 0/12 |

- 내 환경에서도 **원본 설정에서 형식을 통과한 건 full_sft뿐**이라는 결론은 같다. 참조 일치는 교안 코드에 없어서 Claude가 따로 셌고, full_sft의 10/12에서 빠진 두 개는 초과 금액 문항이다. 형식 통과 12/12와 업무 판단이 다르다는 7장의 메시지가 내 데이터에서도 그대로 보인다.
- 내 full_sft의 `policy01-over_limit` 원문은 노트북 셀 19의 `known_bad`와 **글자까지 같다.** 그래서 내 환경에서 돌리면 `review_status`가 “reviewed_same_text”가 될 것으로 읽힌다(직접 실행은 안 함).

**③ 내 DPO는 교안보다 더 무너졌다 — 6장 교훈이 내 데이터에서 다시 확인된다 (Claude가 `dpo_report.json` 확인)**
- 내 L4 DPO(beta 0.1 · lr 2e-5 · 24갱신): 마지막 갱신 loss ≈ 0 · margin 11.47 · 학습한 48쌍 모두 margin 양수. 그런데 chosen reward −10.52(교안 −5.73), 첫 쌍 chosen logp **−126.16**(교안 −66.53), dev 형식 통과 **0/12**(교안 2/12)다.
- 원문은 `{"status": "answered', "answer": "12000", ...}`처럼 **따옴표가 섞여 JSON 자체가 깨졌다.** 6장의 “loss는 성공, 좋은 답은 추락”과 “같은 설정으로 다시 배워도 결과가 같다는 보장은 없다(학습 재현)”가 내 실행에서도 그대로 나타났다. 저장 재로딩은 logits 차이 0.0 · 원문 일치로 정확했다.

**④ 내 5장 QLoRA(L4)는 LoRA와 같은 런타임이라 직접 비율을 낼 수 있다 (Claude가 `qlora_report.json` 확인)**

| | 내 L4 LoRA | 내 L4 QLoRA | 교안 QLoRA |
|---|---|---|---|
| dev loss | 0.9233 → 0.8697 | 1.0464 → 0.9766 | 1.0459 → 0.9745 |
| 학습 최대 메모리 | 1.613 GiB | 1.635 GiB | 1.637 GiB |
| 학습 시간 | 23.7초 | 37.5초 | 25.3초 |
| 형식 통과 | 0/12 | 0/12 | 0/12 |

- `same_runtime_as_lora`가 True라서 5장 노트북 규칙대로 직접 비교할 수 있다. 메모리는 **약 +1.4%**, 시간은 **약 1.58배**로, “0.5B에서는 QLoRA 이득이 안 보인다”가 내 환경에서도 같다. 메모리 구성(로드 직후 451.3MB · 학습 준비 뒤 725.9MB)은 교안과 바이트 수까지 같고, 학습 후 인용 ID도 교안처럼 `政策01-v1`로 나왔다.

**⑤ 검색 함수는 “설명용 축소판”이고, 한계가 슬라이드에 정리돼 있다**
- 검색은 팀 필터 + “숙박 · 예약 · 방” 낱말 겹침이다. 튜터 확인(검색 함수만 호출, 모델 없음)에서 “80,000원 숙소는 승인 필요?” · “호텔은 얼마까지?”는 빈 목록, “통신비 예약은 어떻게?”는 숙박 문서, team=가온으로 “마루팀 숙박 한도는?”을 물으면 가온 문서가 나왔다. 동의어 · 다른 주제 · 팀 지정 오류를 못 걸러서 **검색 품질 평가가 따로 필요**하다.
- `team`은 요청자가 직접 넣는 값이고, 노트북 문구대로 입력 계약은 **요청자의 실제 소속을 인증하지 않는다.**

**⑥ 기존 판정은 “같은 원문”일 때만 재사용한다 — QA의 회귀 판정 규칙과 같다**
- 셀 19는 사람이 읽고 남긴 판정(`known_bad`)을 원문이 **글자까지 같을 때만** 재사용하고(`reviewed_same_text`), 다르면 `new_text_needs_review`로 표시한다. 원문 해시(`raw_sha256`)도 같이 남긴다. 게임 QA에서 **같은 빌드 · 같은 재현 결과일 때만 이전 판정을 그대로 쓰고, 결과가 바뀌면 다시 확인하는 것**과 같다.

## 7장. 모델 성능 평가와 서비스 연결

### 7-1 : 형식과 업무 의미 — 형식 검사와 업무 의미 평가하기
- **핵심 개념**:
  - 흐름: 같은 실행에서 나온 파일인지 확인 → JSON · 계약 · 인용 ID 세 단계 검사 → 형식은 맞고 뜻은 틀린 답 확인.
  - **채점 전에 파일 지문부터 맞춘다**: sft · lora · qlora는 데이터 ZIP 지문을, dpo는 데이터 · 모델 · SFT 보고서 지문을 대조한다. 교안 출력: 비교할 dev 12개, 그룹 policy01 · policy05, test 내용은 읽지 않음.
  - **형식 검사의 관문 세 개**:

    | 관문 | 묻는 것 | 이런 답이 떨어짐 |
    |---|---|---|
    | ① `json_object` | JSON 객체로 읽히나 | 코드 펜스로 감싼 JSON |
    | ② `schema_ok` | 키 3개 · 타입 · 상태와 인용 규칙 | 보류인데 answer가 빈칸 |
    | ③ `citation_ids_ok` | 준 문서 ID 안인가 | 인용만 `政策01-v1`로 다름 |

    - 코드 펜스를 벗겨서 통과시키지 않는다. 모델이 약속을 지켰는지를 재는 검사라서다. `check_format_examples`가 이 함수를 시험한다(형식 맞는 오답은 통과, 펜스 · 잘못된 타입 · 빈 answer · 없는 인용 ID는 거절).
  - **형식이 완벽한 오답도 통과한다**(위 총평의 셀 6 반례).
  - **업무 의미는 문항 유형마다 묻는다** (가온팀 policy01 예):

    | 유형 | 예 | 읽을 때 묻는 것 | 맞는 방향 |
    |---|---|---|---|
    | below | 60,000원 · 한도 65,000 | 한도 이하를 확인했나 | 승인 불필요 |
    | boundary | 65,000원 · 한도 65,000 | 같은 금액을 초과로 바꾸지 않았나 | 승인 불필요 |
    | over_limit | 70,000원 · 한도 65,000 | 초과와 서면 승인을 연결했나 | 승인 필요 |
    | updated | 70,000원 · 개정 한도 75,000 | 개정 한도로 다시 판단했나 | 승인 불필요 |
    | missing | 통신비 · 문서 없음 | 모른다고 하고 담당자를 안내했나 | 보류 |
    | irrelevant | 통신비 · 숙박 규정만 있음 | 숙박 근거를 끌어다 쓰지 않았나 | 보류 |

    - 마루팀(policy05)도 같은 여섯 유형이다(한도 105,000원 → 개정 115,000원). 키워드 유무로 의미 정답률을 만들지 않는다. 같은 금액과 부정 표현도 문맥에 따라 다르다(노트북 문구).
- **QA 체크포인트**:
  - **검사 함수도 반례로 시험**한다 — 2장의 결함 주입과 같은 원칙이다.
  - **점수 = 검사 이름 + 분모** — “12/12”만 말하지 않고 “형식 통과 12/12”라고 말한다.

### 7-2 : 같은 입력 비교 — 같은 입력으로 응답 변화 비교하기
- **핵심 개념**:
  - 흐름: 보고서에 저장된 답을 문항 ID로 정렬 → 질문 · 근거 · 생성 설정 대조 → 단계별 통과 수 → 원문 읽기.
  - **답안지 60장을 문항 ID로 맞춘다**: `comparison`에 base(`sft.dev_before`) · full_sft(`sft.dev_after`) · lora · qlora(`qlora.comparison.qlora`) · dpo의 답을 모은다. 모델 다섯 개를 동시에 불러오거나 학습을 반복하지 않는다. 교안 출력: 같은 dev 입력을 확인한 응답 60개.
  - **원본 설정에서는 SFT만 12/12 통과**(🧭 4-②의 교안 열). 형식 통과 수는 업무 정답 수가 아니다.
  - **원문 읽기: 70,000원은 초과인가요?**

    | 방법 | 원문의 핵심 | 형식 | 뜻 |
    |---|---|---|---|
    | 모범답안 | 70,000원은 한도를 초과하므로 예약 전 서면 승인 | - | - |
    | full_sft | 70,000원은 한도 이하이므로 사전 승인이 필요하지 않습니다 | O | X |
    | base · lora | ```json … 한도 이하의 예약에는 … 초과하는 예약은 … (규정 복사) | X | X |
    | qlora | `{"answer": …, "citations": ["政策01-v1"]}` | X | X |
    | dpo | … 예약 전 서면 승인을 받아 보실 수 없습니다.supports#query} | X | X |

    - 셀 11은 policy01의 다섯 유형만 찍는다. below와 마루팀 답은 `evaluation_report.json`의 `responses`에서 읽는다.
- **QA 체크포인트**:
  - **실패는 첫 실패 단계 하나만 센다** — 뒤 관문을 생략한 False를 세 번 실패로 부풀리지 않는다(합계 = 12를 `assert`).
  - **같게 맞춘 것과 안 맞춘 것을 같이 적는다** — 입력과 생성 설정은 같지만 학습 목적 · 양자화 · 자원은 달라서 “어느 방법이 낫다”는 종합 순위를 만들지 않는다.

### 7-3 : 검색과 API — 검색과 API에 학습 모델 연결하기
- **핵심 개념**:
  - 흐름: 작은 규정 목록에서 검색 → 3장 SFT 복원 → FastAPI `/answer`에서 검색 · 생성 · 형식 검사 → TestClient로 시험 요청. **RAG의 축소판**이고, LoRA · QLoRA · DPO 모델은 이 경로에 올라가지 않는다.
  - **검색: 팀을 고르고 낱말을 센다**: 검색 목록은 dev의 updated 문서(개정판) 두 개(`policy01-v2` · `policy05-v2`)이고 모범답안은 넣지 않는다. 팀이 같은 문서 중 “숙박 · 예약 · 방”이 질문과 문서 양쪽에 들어간 개수가 가장 많은 문서 하나를 돌려주고, 0개면 빈 목록이다. 교안 출력: 통신비 질문 → `[]`. 한계는 🧭 4-⑤.
  - **새 학습 없이 3장 SFT를 되살린다**: GPU · BF16 지원, `candidate_sft` 폴더 없음, ZIP 안 6개 파일(config · generation_config · model.safetensors · tokenizer · tokenizer_config · chat_template, 모두 `sft_model/` 아래) · 경로 · 빈 파일, 토크나이저 어휘 · 템플릿을 확인한다. 확인한 여섯 경로만 일반 파일로 쓰고 ZIP 안의 임의 실행 코드를 불러오지 않는다. dev 한 문항의 원문 일치는 **False여도 멈추지 않고 기록**한다(교안 출력: True).
  - **입구는 엄격하게, 출구는 정직하게**:

    | 설정 · 경로 | 의미 |
    |---|---|
    | `strict=True` | 잘못된 자료형을 임의 변환하지 않음 (`question: 123` → 422) |
    | `extra="forbid"` | 정의하지 않은 필드 거절 (요청자가 `documents`를 끼워 넣으면 422) |
    | `str_strip_whitespace=True` + 길이 1~500 | 공백 한 칸 질문 → 422 |
    | 입력 512토큰 초과 | 422 (코드에만 있고 시험하지 않음) |
    | 답 형식 실패 · 잘림 | 502 (코드에만 있고 시험하지 않음) |
    | 답 형식 통과 | 200, 그래도 `review_required: True` |

  - **실제 호출: 200인데 판단은 틀린다**:

    | 요청 | 검색 | status | 형식 · HTTP | 업무 판단 |
    |---|---|---|---|---|
    | 숙박 80,000원 | `policy01-v2` | answered | 통과 · 200 | **틀림** (80,000 > 75,000인데 “한도 이하”) |
    | 통신비 | 없음 | abstained | 통과 · 200 | 맞음 (보류) |

  - **무엇을 검증했고, 무엇은 안 했나** (슬라이드 20장): 검색은 예제 3개만(동의어 · 다른 주제 · 문서가 많을 때는 미검증), 모델 복원은 파일 · 어휘 · 템플릿과 원문 1건(나머지 11문항 · 다른 GPU는 미검증), 입력 계약은 잘못된 요청 3개(인증 · 권한 · 악의적 질문은 미검증), 출력은 형식 · 인용 ID · 길이 잘림(금액 비교 · 승인 판단은 미검증), API는 프로세스 안 호출 2개(외부 공개 · 동시 요청 · 지연 시간은 미검증), 연결한 모델은 3장 full SFT 하나.
- **QA 체크포인트**:
  - **상태 코드와 업무 판단을 분리** — 200은 “형식을 지켰다”까지다.
  - **검증 범위를 표로 남긴다** — “API를 연결했다”가 아니라 “무엇을 확인했고 무엇을 안 했다”로 적는다. 테스트 리포트의 **테스트 범위 / 범위 밖** 항목과 같다.
  - **입력 계약 ≠ 보안** — 타입 · 길이 · 여분 필드 검사는 인증이나 권한 검사가 아니다.

### 7-4 : 실패와 수정 방향 — 실패 원인을 읽고 수정 방향 정하기
- **핵심 개념**:
  - 흐름: 형식 · 검색 · 업무 판단 실패를 구분 → 알려진 실패를 그대로 남김 → full_sft를 8장 평가 후보로 고정 → test는 아직.
  - **어느 칸에서 실패했는지 나눈다**:

    | 실패 | 알아보는 법 | 이 장의 예 | 다음에 시험할 방향 |
    |---|---|---|---|
    | 형식 | 첫 실패 단계 | 원본 LoRA: 12개 모두 JSON 실패 | 학습 설정 · 데이터 형식 |
    | 검색 | `retrieved_documents` | ‘숙소’ 질문 → 빈 목록 | 동의어 · 검색 방법 · 검색 평가 |
    | 업무 판단 | 문서는 맞고 answer가 틀림 | 80,000원을 75,000원 이하라고 | 비교 사례 · 규칙 코드 · 사람 검토 |
    | 운영 | 이 노트북으로는 모름 | 인증 · 동시 요청 · 외부 공개 | 목적에 맞는 별도 시험 |

    - 금액 비교처럼 답이 하나로 정해지는 규칙은 **모델 대신 코드로 계산**하는 선택지도 있다.
  - **후보는 `full_sft`로 코드에 고정된다**: `selection`에 후보 · 이유(“같은 dev12에서 SFT의 형식 통과는 12/12”) · 알려진 실패 두 개 · `deployment_ready: False`를 남긴다. 알려진 실패: 70,000원은 65,000원을 초과하지만 승인 불필요라고 답함 / 검색은 두 팀의 현재 숙박 문서만 다루며 API의 형식 정상 응답도 업무 의미 검토가 필요함.
  - **8장에 넘기는 것**: `candidate_manifest.json`(후보 · 지문 · 설정 · 정밀도 · 알려진 실패 · `test_used: False`), `evaluation_report.json`(60개 원문 · 검사 · 검토 기준 · API 예 · 검색 목록), 데이터 · SFT 세 파일 그대로. 같은 이름으로 다시 실행하면 보고서가 바뀌므로 이전 결과는 먼저 보관한다.
- **QA 체크포인트**:
  - **릴리스 후보 지정 ≠ 출시 승인** — 후보로 고정해도 `deployment_ready`는 False다.
  - **알려진 이슈를 숨기지 않고 함께 넘긴다** — 다음 단계가 같은 실패를 다시 찾느라 시간을 쓰지 않게 한다. 게임 QA의 **알려진 이슈 목록(known issues)을 빌드와 함께 넘기는 것**과 같다.
  - **dev 성과를 일반화 성능으로 말하지 않는다** — dev는 이미 여러 번 봤다. 일반화는 8장의 test로 따로 본다.

## 정리 — 7장 결과물

| 강 | 한 줄 | 남긴 것 |
|---|---|---|
| 7-1 | 형식 통과와 업무 의미를 따로 채점한다 | 세 관문 True인 오답 |
| 7-2 | 같은 문항 · 근거 · 설정으로 비교한다 | 60개 응답 · 원본 SFT 12/12 |
| 7-3 | 검색 · 생성 · 검사를 API로 잇는다 | 200 두 건 중 판단 오류 한 건 |
| 7-4 | 실패 칸을 나누고 후보를 고정한다 | full_sft · 배포 승인 False |

- **8장이 읽는 것**: `evaluation_report.json`(60개 원문 · 검사), `candidate_manifest.json`(후보 인수인계서), 데이터 · SFT 세 파일. 8장은 test로 최종 평가한다.
- 8장 전에 할 것: 보고서 2개 + SFT 입력 3개 보관 → 8장은 이 다섯 파일에서 시작 → 원문 하나 골라 실패 칸(형식 · 검색 · 업무 판단) 적기.
- 직접 해 본 것: 슬라이드와 노트북을 Claude와 같이 읽고, 올려 둔 내 보고서 4개로 7-1 · 7-2 비교를 Claude가 재현했다. 7-3(모델 복원 · API)은 실행하지 않았다(향후 계획).
