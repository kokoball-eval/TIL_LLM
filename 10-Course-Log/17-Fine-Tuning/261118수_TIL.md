## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 질문 + 모범답안 쌍으로 **답변 토큰의 손실**을 줄이며 가중치를 바꾸는 학습. 3장은 전체 가중치, 4~5장은 LoRA의 A·B를 같은 목표로 학습 |
  | LoRA | Low-Rank Adaptation (저랭크 적응) | 기반 가중치는 고정하고 작은 추가 행렬 A·B만 학습 (4장) |
  | DPO | Direct Preference Optimization (직접 선호 최적화) | chosen vs rejected 상대 선호로 학습. 3장 SFT 모델이 출발점 (6장) |
  | 교사 강요 | teacher forcing | 학습 때 모델이 만든 앞 토큰이 아니라 **모범답안의 앞 토큰**을 문맥으로 주고 다음 토큰을 맞히게 하는 방식 |
  | EOS | End Of Sequence (시퀀스 종료) | 응답이 끝났다는 토큰. 답변과 함께 **정답으로 학습**해야 끝낼 줄 아는 모델이 된다 |
  | labels = −100 | ignore index (손실 제외 표시) | 그 위치는 **직접 손실에서 뺀다**는 뜻. 입력 문맥에서 지우는 값이 아님 |
  | attention_mask | attention mask (주목 마스크) | 1 = 읽는 토큰, 0 = **아예 안 보는** 패딩. labels의 −100과 역할이 다르다 |
  | 패딩 | padding | 길이가 다른 문항을 한 배치로 묶으려고 덧붙이는 빈칸 |
  | 시프트 | shift (한 칸 밀기) | `logits[t]`는 `labels[t+1]`을 맞힌다. 모델 내부에서 처리 (6장 DPO는 직접) |
  | 갱신 | optimizer update / step | 기울기로 가중치를 한 번 바꾸는 일. `max_steps`는 **이 횟수** 기준 |
  | 기울기 누적 | gradient accumulation | 문항 여러 개의 기울기를 모은 뒤 한 번 갱신 (여기선 4문항 = 유효 배치 4) |
  | optimizer / scheduler | optimizer (최적화기) / learning-rate scheduler (학습률 계획) | 기울기로 가중치를 바꾸는 규칙 / 갱신 단계에 따라 학습률을 정하는 계획 |
  | AdamW | Adam with decoupled Weight decay | 기울기의 이동 평균을 쓰는 optimizer. 파라미터마다 상태 2개를 따로 저장 |
  | warmup | warmup (예열) | 시작 몇 갱신 동안 학습률을 서서히 올리는 구간 (이번엔 2갱신) |
  | grad_norm | gradient norm (기울기 노름) | 기울기의 크기. NaN·폭증만 없으면 되고, **1보다 크다고 실패는 아님** (클리핑 전 값일 수 있음) |
  | BF16 / FP16 / FP32 | Brain Floating Point 16-bit / 16-bit / 32-bit Floating Point | 가중치를 저장·계산하는 숫자 형식. 비트가 적을수록 메모리는 줄고 **작은 변화는 반올림으로 사라질 수 있다** |
  | gradient checkpointing | gradient checkpointing (활성값 재계산) | 중간 계산값을 저장하는 대신 역전파 때 **다시 계산**해 메모리를 아끼는 기능. 파일로 저장하는 체크포인트와 **다른 것** |
  | 체크포인트 | checkpoint | 특정 시점의 학습 상태 저장본 (가중치 + optimizer + scheduler + 난수 상태 + 진행 단계) |
  | safetensors | safetensors (안전한 텐서 저장 형식) | 모델 가중치를 담는 파일 형식 (`model.safetensors`) |
  | KV 캐시 | Key-Value cache | 생성 중 이전 토큰의 계산 결과를 저장하는 메모리. 학습에서는 `use_cache=False` |
  | SDPA | Scaled Dot-Product Attention | 어텐션 계산 구현의 한 종류 (`attn_implementation="sdpa"`) |
  | GiB | gibibyte (기비바이트) | 바이트 수를 2³⁰으로 나눈 단위 (GB와 약간 다름) |
  | NaN / Inf | Not a Number / Infinity (숫자 아님 / 무한대) | 손실·기울기에 나오면 학습이 깨졌다는 신호 |
  | SHA-256 | Secure Hash Algorithm 256-bit (보안 해시) | 파일 내용의 지문 |
  | ZIP_STORED | ZIP stored (무압축 저장) | 압축 계산 없이 원래 바이트를 ZIP에 담는 방식 |

- **핵심 통찰: 3장은 "학습이 된다"를 보여 주는 장이 아니라 "학습이 됐다는 숫자가 무엇은 못 보는지"를 보여 주는 장이다**
  - 학습 결과는 dev loss **0.921 → 0.0049**, JSON만 출력 **0/12 → 12/12**로 아주 좋아 보인다. 그런데 같은 dev 12문항의 **업무 판단은 10/12**다. 틀린 두 개는 모두 over_limit(한도 초과)이고, 70,000원 > 65,000원인데 "한도 이하이므로 사전 승인이 필요하지 않습니다"라고 답했다. 슬라이드 제목 그대로 "dev loss 0.0049인데 초과 금액은 틀려요".
  - 손실은 답변 토큰 71개의 **평균**이라 "이하/초과" 판단이 틀려도 평균은 거의 0이다. → 1장에서 배운 "형식 통과 ≠ 업무 의미"를 이번엔 **학습 뒤의 같은 dev**에서 숫자로 다시 확인했다(형식 12/12, 판단 10/12).

    | 교안 | 오늘 한 것 | 남는 산출물 |

    | 3-1 | 프롬프트는 −100, **답변 + EOS만 손실**. 길이가 다른 문항을 패딩해 배치로 묶고, 한 칸 밀린(shift) 손실을 작은 텐서로 확인 | 370 = 299 + 71 · 배치 (2, 379) · 균등 손실 1.79 |

- **두 번째 통찰: "멈췄다"와 "끝났다"를 구분한다 — 전체 계획은 24갱신으로 고정하고 12에서 일부러 멈춘다**
  - `max_steps=24`는 **처음부터 세는 전체 목표**다. 12에서 멈췄다고 12가 목표가 아니고, 재개할 때 24번을 더 하는 것도 아니다(남은 12번만). 학습률 계획(warmup 2 → 24까지 선형 감소)도 이어서 가야 해서, 중단 지점은 `StopAtTwelve` 콜백으로 따로 두고 전체 계획은 건드리지 않는다.
  - 재개는 **모델 파일만 읽고 새로 `train()`** 하는 것과 다르다. `resume_from_checkpoint`는 optimizer · scheduler · 난수 상태 · 진행 단계까지 읽어서 이어간다.

- **세 번째 통찰: 입력과 환경을 먼저 검사하고, 틀리면 GPU 계산 전에 멈춘다**
  - 코드가 학습 전에 **버전 확인 → ZIP 파일 구성 → 그룹 분리 → 대화 역할 · 문자열 검사 → 길이 상한 → GPU 확인 → 이전 결과 폴더 보호**를 순서대로 하고, 하나라도 어긋나면 예외로 멈춘다. 잘못된 자료로 GPU 시간을 쓰지 않으려는 설계다(🧭 1).

- **향후 계획 및 다짐**

| 학습 설정 | 24갱신 · 유효 배치 4 · lr 2e-5 · linear · warmup 2 · AdamW 0.01 · clip 1.0 | 비교 조건이 바뀜 | 3-2 |
| 정밀도 · 장치 | BF16 (지원 GPU) / FP32 (T4 등) | 같은 설정도 수치가 달라짐 | 3-2 |
| 난수 | `seed` · `data_seed` 42 | 순서 · 초기 상태 달라짐 (장치 차이까지는 못 없앰) | 3-2 |

- 게임 QA로 바꾸면: **테스트 리포트에 빌드 번호 · 환경 · 테스트 데이터 버전 · 로그 원문을 같이 첨부하는 것**과 같다. 나중에 결과가 달라졌을 때 "무엇이 바뀌었나"부터 확인할 수 있다.

### 4. Claude가 짚어준 확인 포인트

**① 슬라이드의 학습률 여섯 개는 "warmup 2 + 선형 감소" 공식과 모두 맞는다 (Claude의 계산)**
- 공식: `lr = 2e-5 × (24 − (N−1)) / 22` (N = 로그가 찍힌 갱신). N=4 → 1.909e-05, 8 → 1.545e-05, 12 → 1.182e-05, 16 → 8.18e-06, 20 → 4.55e-06, 24 → **9.09e-07**. 슬라이드 값(1.91e-05 · 1.55e-05 · 1.18e-05 · 8.18e-06 · 4.55e-06 · 9.09e-07)과 전부 일치.
- 마지막이 0이 아니라 9.09e-07인 이유: 로그의 학습률은 **그 갱신에 실제 쓴 값**(스케줄러를 N−1번 진행한 값)이라서 N=24에서도 0에 닿지 않는다. 재개 뒤(13~24) 값도 같은 공식 위에 있으므로 **"같은 24갱신 계획이 이어졌다"는 증거**로 읽을 수 있다(슬라이드 17장 빨간 점선).

**② 메모리 어림(파라미터 × 바이트 × 4)이 체크포인트 파일 크기와 맞아떨어진다 (Claude의 계산)**
- 494,032,768 × 2바이트 = 0.988 GB(0.92 GiB) = `model.safetensors` 988 MB와 같다. 슬라이드 어림의 ×4는 **가중치 1 + 기울기 1 + AdamW 상태 2**로 읽히고, 4배면 약 3.68 GiB. 실측 최고 4.66 GiB와의 차이 약 1 GiB는 활성값 등이다.
- 체크포인트의 `optimizer.pt` 1.98 GB ≈ 모델의 **2배**라서 "AdamW 상태 2개"와 일치하고, 체크포인트 전체가 **모델 크기의 약 3배**인 것도 같은 이유다. (어림 공식의 항목 분해는 Claude의 해석이고 슬라이드에는 합계 식만 있음.)
- 1장의 fp32는 파라미터당 16바이트였고(4 × 4), 이번 BF16은 8바이트(2 × 4)다. 정밀도가 반이면 메모리도 반이 된다는 슬라이드 문장("BF16의 약 2배")과 연결된다.

**③ 2장의 `answer_ids` 77개와 3장의 학습 토큰 71개는 "개행을 세느냐"가 다르다**
- 2장 도식의 `full_ids`는 `<|im_end|>` 뒤에 **개행(`\n`)** 까지 있었고 `answer_ids`(77개)는 그 개행을 포함했다. 3장 `encode_example`은 `end = len(prompt_ids) + answer_ids.index(EOS) + 1`로 **EOS까지만** 자르고 그 뒤 개행은 버린다(첫 학습 문항 71개 · 도식에서도 `\n`은 "버림").
- 두 숫자는 **다른 사례**(2장은 policy03-over_limit, 3장은 policy03-below)라서 77과 71을 그대로 빼면 안 된다. 다만 2장 `dataset_info`의 최대 길이 380(개행 포함)과 3장 train·dev 최대 379가 **정확히 1 차이**인 것은 개행 한 토큰을 빼는 규칙과 맞아 보인다(같은 사례인지는 확인 못 함 → 직접 실행해서 확인 필요). 2장 TIL의 "answer_ids 77개(답변 + 종료 토큰)" 표현은 개행까지 포함한 수라는 점에서 조금 부정확했다.

**④ dev loss 0.0049인데 over_limit 두 개가 틀렸다 — 이건 "손실이 못 보는 것"의 실물 사례**
- 슬라이드의 오답 예: `policy01-over_limit`, 질문 70,000원 > 한도 65,000원인데 "한도 이하이므로 사전 승인이 필요하지 않습니다"로 답했다. 인용(`policy01-v1`)과 JSON 형식은 맞다.
- 학습 전 응답(코드 펜스에 규정 문장을 베끼고 금액 비교 없음)에서 형식은 고쳐졌지만 **금액 비교 판단은 24갱신으로는 아직 안 고쳐졌다**고 읽는 것이 슬라이드와 맞다. 왜 틀렸는지(모델이 숫자 비교를 못 배운 것인지, 문장 틀만 익힌 것인지)는 이 자료만으로 단정할 수 없다. 12문항 원문(`dev_after`)을 직접 읽어 확인해야 한다.
- 1장의 "형식 통과 ≠ 업무 의미 ≠ 참조 일치"가 학습 **뒤**에도 그대로 유효하다는 증거다. 점수를 자동 지표 하나로 확정하지 않고, **사람이 읽는 판단을 따로** 남기는 이유.

**⑤ train loss와 dev loss는 높이를 직접 비교하지 않는다 — 그리고 20갱신에서 작은 반등이 있다**
- train은 **그 로그 구간의 평균**(4갱신 × 4문항), dev는 **그 시점 한 번 잰 값**이다. 4갱신 시점에서 train 0.7016 > dev 0.1599인 것은 train 평균에 학습 **초반의 높은 손실**이 섞여 있기 때문이다(슬라이드: "높낮이 직접 비교 X").
- 20갱신 줄을 보면 train loss가 0.0115 → 0.0159로, grad_norm이 2.50 → 5.84로 올랐고 dev loss는 0.0092 → 0.0070으로 계속 내려갔다. 슬라이드는 "NaN · 폭증만 없으면 OK"라고만 적었다. 구간 평균이 문항 몇 개에 흔들린 정도로 보이지만 이유는 확인 못 함(Claude의 해석). 원인을 단정하지 않고 **그런 줄이 있었다는 사실을 기록**해 둔다.

**⑥ 가중치 표본 변경 24/256과 `changed_count > 0` 검사의 한계**
- 고정한 256개 위치 중 24개만 값이 바뀌었고 최대 변화량은 8.77e-05다. 슬라이드 설명대로 BF16에서는 **작은 변화가 반올림으로 사라질 수 있어서**, 표본 변화 · 손실 · 실제 응답을 **함께** 본다. BF16은 유효숫자가 적다는 것은 알고 있어서(Claude의 설명, 이 모델의 값으로 직접 확인하지 못함) 갱신량이 작으면 같은 값으로 반올림되는 위치가 많은 것으로 읽힌다.
- 코드의 `assert changed_count > 0`은 **"무언가 바뀌었다"** 만 보는 스모크 검사다. 좋은 방향으로 바뀌었는지는 손실과 응답으로 따로 봐야 한다. 이 표본은 노트북 문구대로 "전체 변경 비율이 아니다".

**⑦ 업로드한 `training_data.zip`을 Claude가 확인했다 — 해시와 그룹이 모두 일치**
- ZIP의 SHA-256 = `018a6120f1bb…`로 슬라이드 2장 표의 "SHA-256 018a6120…"과 같다. ZIP 안의 `train/dev/test.jsonl` 해시도 `dataset_info.json`의 `file_sha256`(`d9154d79…` · `e48906f0…` · `2bca42ac…`)과 일치하고, 그룹 구성도 train(03 04 06 07 08 09 10 12) · dev(01 05) · test(02 11)로 2장 슬라이드와 같다. ZIP 안 파일의 수정 시각은 2026-11-13이었다.
- 3장 코드의 `data_sha256`은 **ZIP 파일 자체의 해시**이고 2장 `dataset_info`는 **jsonl 세 개의 해시**다. 2장 TIL에 적어 둔 "ZIP은 다시 만들면 해시가 달라질 수 있다(확인 필요)"가 그대로 이어지는 부분이라, 비교 기록에는 **ZIP 해시와 jsonl별 해시를 같이** 남기는 편이 안전해 보인다.
- 2장 TIL의 우려("1장 baseline 4문항은 train 그룹")와도 이어진다. 3장은 **공통 dev 문항 `policy01-over_limit`** 으로 학습 전후를 비교하고, 실제로 dev 12문항 전체의 학습 전 응답(`dev_before`)을 보관한다.

## 3장. 전체 가중치 SFT와 학습 재개

### 3-1 : 손실 마스크 — 답변 토큰에만 손실 계산하기
- **핵심 개념**:
  - 흐름: SFT의 학습 신호 → `encode_example`(두 번 토큰화해 경계 찾기) → 프롬프트 labels −100 → `collate`로 패딩 → 한 칸 밀린(shift) 손실을 작은 텐서로 확인.
  - **SFT는 모범답안을 학습 신호로 쓴다**. 정답 문장을 검색 저장소에 넣는 것(RAG)과 달리 **손실을 역전파해 가중치를 바꾼다**.

    | 학습에 전달하는 것 | 손실에서 하는 일 | 이번 코드의 위치 |
    |---|---|---|
    | 질문과 규정 | 답변을 계산하는 **문맥으로 읽기만** | `input_ids`의 프롬프트 구간 |
    | 모범답안의 이전 토큰 | 다음 정답 토큰을 예측하는 문맥 (teacher forcing) | `input_ids`의 답변 구간 |
    | 모범답안의 다음 토큰과 EOS | **실제 예측 목표** | `labels`에서 −100이 아닌 위치 |

  - **`encode_example(row)` 순서**: ① `prompt_ids`(system + user, `add_generation_prompt=True`)와 `full_ids`(전체 대화, `False`) 만들기 → ② `full_ids[:len(prompt_ids)] == prompt_ids` 아니면 `ValueError` → ③ 답변 구간에 **EOS가 정확히 하나**인지 확인 → ④ `end = len(prompt_ids) + answer_ids.index(eos_id) + 1`, `input_ids = full_ids[:end]`(**끝의 개행은 버림**) → ⑤ 512 초과면 `ValueError`(자르지 않음) → ⑥ `labels = [-100] * len(prompt_ids) + input_ids[len(prompt_ids):]` → ⑦ `labels[-1] == EOS`와 손실 대상 존재를 `assert`.
  - **첫 학습 문항 `policy03-below`**: 입력 길이 **370**, 답변 시작 **299**, 학습 토큰 **71**(370 = 299 + 71). 프롬프트 299개는 labels가 전부 −100, 답변 + EOS 71개가 손실 대상. 최대 길이는 train 379 · dev 379.
  - `attention_mask`는 모두 1이다. **−100(손실 제외)과 attention 0(아예 안 봄)은 다른 표시**다.
  - **`collate`: 길이가 다른 문항을 한 배치로 묶는다** (가장 짧은 문항 + 가장 긴 문항 379 → `(2, 379)`).

    | 텐서 | 실제 토큰 자리 | 패딩 자리 |
    |---|---|---|
    | `input_ids` | 토큰 ID | `pad_token_id` |
    | `attention_mask` | 1 | 0 (보지 않음) |
    | `labels` | −100 또는 정답 ID | **−100** (손실 제외) |

    - `pad_sequence(..., batch_first=True, padding_value=...)`. 코드 주석: 패딩 ID와 종료 ID가 우연히 같아도 **위치를 기준으로** labels를 패딩한다. 검사: 세 텐서의 모양이 같은지, 패딩 위치 labels가 전부 −100인지, 패딩 뒤에도 실제 마지막 위치 labels가 EOS인지, 학습 토큰 수가 그대로인지(`check_padded_batch`).
    - 실무 메모(슬라이드): 배치는 **가장 긴 문항에 맞춰** 패딩된다. 길이가 비슷한 것끼리 묶으면 계산 낭비가 줄어든다.
  - **한 칸 밀어 맞힌다: `logits[:, :-1]` ↔ `labels[:, 1:]`** (마지막 예측은 짝이 없음). 작은 텐서 예: `toy_logits = zeros(1, 4, 6)`, `toy_labels = [[-100, -100, 2, 5]]`, `ignore_index=-100` → shift 뒤 학습 대상 수 **2**, 균등 분포 손실 **1.791759 = log 6**(6지선다 찍기). 학습은 정답 토큰의 확률을 올려 이 값을 0 쪽으로 내리는 일이다.

    | 어디서 | shift는 누가 |
    |---|---|
    | 3~5장 SFT · LoRA | **모델 내부** (labels만 전달) |
    | 6장 DPO 손실 함수 | **직접** (한 곳에서만) |

  - 슬라이드 4장 메모: 모범답안 문장은 2장 규칙 함수가 만든 **하나의 틀**이라서, 학습 뒤 모델은 이 문장 틀을 거의 그대로 따라 쓴다.
- **QA 체크포인트**:
  - **labels 마스크는 위치로 검증** — 첫 항목(프롬프트)은 −100, 마지막은 EOS, 패딩은 −100인지를 `assert`로 확인한다. 눈으로 확인하지 않는다.
  - **−100과 attention 0을 섞지 않는다** — 프롬프트는 읽어야 하므로 attention은 1이고 손실에서만 뺀다.
  - **정답 마스크가 없으면 질문까지 외우려 한다** — 프롬프트 구간에도 손실을 주면 "질문을 흉내 내는 학습"이 섞인다. 다만 모든 SFT가 프롬프트를 같은 방식으로 마스킹하는 것은 아니다(노트북 문구).
  - **shift를 한 곳에서만** — 모델 내부와 직접 계산에서 둘 다 밀면 정답이 한 칸 어긋난다(2장 함정과 같은 이야기).

### 3-2 : 전체 SFT — 전체 가중치를 업데이트하며 SFT 시작하기
- **핵심 개념**:
  - 흐름: BF16 확인 → 모델 불러오기(전체 = 학습 대상) → **학습 전 dev 12문항 응답 보관** → `TrainingArguments` 설정표 → `Trainer` · `StopAtTwelve` → 12갱신 뒤 `checkpoint-12`.
  - **전체 가중치 4.94억 개를 모두 학습**한다(슬라이드 실측: GPU RTX 5060 Laptop 8GB, `bf16_supported` True → `torch.bfloat16`, 전체 파라미터 494,032,768 = 학습 대상 100%, 최고 메모리 할당 4.66 GiB). 코드는 `total_parameters == trainable_parameters`를 `assert`한다. T4처럼 BF16 미지원이면 FP32(메모리 약 2배). 실무 어림: **전체 SFT 메모리 ≈ 파라미터 수 × 바이트 × 4 + 활성값**.
  - **학습 전 응답(dev 12문항)과 가중치 표본을 먼저 보관**한다 — 학습 뒤 같은 입력 · 같은 위치로 비교하려고. 학습 전 `policy01-over_limit` 응답은 ` ```json ` 코드 펜스 안에 규정 문장을 그대로 옮기고 **금액 비교는 없다**.

    | dev 12문항 학습 전 | 개수 |
    |---|---|
    | JSON만 출력 | **0 / 12** |
    | ` ```json ` 펜스 | 9 / 12 |
    | 다른 형식 | 3 / 12 (글로 쓴 `status: answered` 1개 + missing 두 문항에서 `answered` 한 단어만 쓴 2개) |
    | missing → 'answered' | 2 / 2 |

    - 1장 baseline(코드 펜스 · `answered` 한 단어)과 **같은 실패 양상**이 dev에서도 나온 것이다.
  - **`TrainingArguments`는 학습 실행의 설정표**다(모델이나 알고리즘 자체가 아님). 이번 값은 짧은 비교와 재개를 위한 값이지 모든 모델에 맞는 권장값이 아니다(노트북 문구).

    | 묶음 | 파라미터 = 값 | 의미 |
    |---|---|---|
    | 학습량 | `max_steps` = 24 | optimizer 갱신의 **전체 목표** (epoch보다 우선) |
    | | `per_device_train_batch_size` = 1 | 한 번에 처리할 문항 수 (늘리면 활성값 메모리 증가) |
    | | `gradient_accumulation_steps` = 4 | 네 문항의 기울기를 모아 한 번 갱신 → **유효 배치 4** (1 × 1 × 4) |
    | 학습률 | `learning_rate` = 2e-5 · `lr_scheduler_type` = linear · `warmup_steps` = 2 | 2갱신 동안 올리고 24까지 선형 감소 |
    | | `optim` = adamw_torch · `weight_decay` = 0.01 · `max_grad_norm` = 1.0 | PyTorch AdamW · 감쇠 · 갱신 전 기울기 노름 제한 (가중치 값을 1 이하로 자르는 설정이 아님) |
    | 정밀도 · 메모리 | `bf16` = 지원 시 True · `fp16` = False | BF16 혼합 정밀도 사용 |
    | | `gradient_checkpointing` = True (`use_reentrant=False`) · `use_cache` = False | 활성값 **재계산**으로 메모리 절약 · 학습 중 KV 캐시 안 씀 |
    | 평가 · 로그 | `eval_steps` = 4 · `prediction_loss_only` = True | 4갱신마다 dev **손실**만 평가 (생성 평가는 별도 코드) |
    | | `logging_steps` = 4 · `logging_nan_inf_filter` = False | 4갱신마다 로그 · NaN/Inf를 **숨기지 않음** |
    | 저장 | `save_steps` = 12 · `save_total_limit` = 2 · `save_only_model` = False | 12갱신마다 재개용 상태 저장 · 체크포인트 2개만 보관 · optimizer 등도 함께 저장 |
    | 재현 | `seed` = `data_seed` = 42 · `dataloader_num_workers` = 0 · `report_to` = none | 난수 기준 · 로더 단순화 · 외부 추적 안 씀 |

  - **48문항 한 바퀴 = 12갱신**(48 ÷ 유효 배치 4), 전체 24갱신 = **두 바퀴**. `PAUSE_STEP = 12`는 **중간에 멈출 시점**일 뿐 전체 목표를 12로 바꾸지 않는다. `eval_steps=4`는 문항 4개마다가 아니라 **4갱신(= 16문항) 뒤** 평가한다.
  - **`StopAtTwelve`**: `on_step_end`에서 `global_step == 12`면 `control.should_training_stop = True`. 학습률 계획(24갱신)은 그대로.
  - **`Trainer`에 연결하는 것**: `train_dataset` = train 48 · `eval_dataset` = dev 12(**test는 전달하지 않음**) · `data_collator` = `collate` · `callbacks` = `StopAtTwelve`. **`processing_class=tokenizer`만으로는 답변 전용 labels가 생기지 않는다.** 그 일은 `encode_example`과 `collate`가 한다(자료가 이미 토큰화돼 있음).
  - **첫 구간 결과**: `eval_before = trainer.evaluate()` → 학습 전 dev loss **0.9207**, `trainer.train()` 뒤 `global_step == 12`, 저장 단계 12 · 계획된 전체 단계 24, 첫 구간 **12.572초**.

    | `checkpoint-12` 파일 | 크기 · 역할 |
    |---|---|
    | `model.safetensors` | 988 MB · 가중치 |
    | `optimizer.pt` | 1.98 GB · AdamW 상태 |
    | `scheduler.pt` | 학습률 계획 위치 |
    | `rng_state.pth` | 난수 상태 |
    | `trainer_state.json` | `global_step` 12 · 로그 |
    | config · tokenizer 등 | 불러오기용 |

    - 체크포인트는 모델 크기의 **약 3배**(optimizer 상태가 가중치의 2배). 12.6초 = 12갱신 + dev 평가 3번(각 약 0.4초) + `checkpoint-12` 저장(약 3GB).
- **QA 체크포인트**:
  - **학습 전 응답을 먼저 보관** — "학습 후 좋아졌다"를 말하려면 같은 입력의 학습 전 원문이 있어야 한다(1장 baseline의 연장).
  - **설정표를 읽을 때 "단위"를 확인** — `eval_steps=4`는 4문항이 아니라 4갱신, `max_steps=24`는 추가 24번이 아니라 전체 24번, `warmup_steps=2`는 문항이 아니라 갱신 수.
  - **test는 아예 전달하지 않는다** — 학습 · 설정 선택에 한 번도 안 쓴 시험 자료로 남겨 두려는 장치(2장의 "보고 고치면 dev가 된다").
  - **gradient checkpointing ≠ 체크포인트 파일** — 이름이 비슷하지만 하나는 **메모리 절약용 재계산**, 하나는 **재개용 저장본**이다.

### 3-3 : 곡선 읽기 — 손실 곡선과 학습 설정 읽기
- **핵심 개념**:
  - 흐름: `log_history`에서 `loss` · `eval_loss` · `learning_rate` 꺼내기 → 첫 12갱신 곡선 → train loss와 dev loss의 차이 → `grad_norm` · 시간 · 메모리 읽는 법 → 손실과 업무 정답은 다르다.
  - **손실 곡선: 12번 갱신 만에 크게 내려간다** (y축 = 정답 토큰의 cross entropy, x축 = optimizer 갱신 횟수. `sft_loss_first12.png`는 노트북이 저장한 그림).

    | 0 (전) | - | 0.921 |
    | 4 | 0.702 | 0.160 |
    | 8 | 0.093 | 0.046 |
    | 12 | 0.034 | 0.020 |

  - **로그 한 줄씩** (슬라이드 17장, 재개 뒤 16~24 포함):

    | 갱신 | epoch | train loss | dev loss | learning_rate | grad_norm |

    | dev loss | 0.921 | 0.0049 |
    | JSON만 출력 | 0 / 12 | **12 / 12** |

    - **손실 = 토큰 평균**: 71개 중 '이하' 몇 토큰만 틀려도 평균은 거의 0. **판단 = 사람이 읽는 답**: 금액 하나가 틀리면 업무상 오답.
  - 노트북 문구: dev 12개의 원문과 손실은 **작은 합성 규정에서의 관찰**이며 일반 성능을 판단하지 않는다. BF16 반올림 · 장치 차이 · 새 규정과 다른 질문에서의 동작은 별도로 확인할 범위.
- **QA 체크포인트**:

  - **train과 dev는 집계 방식이 달라 높이를 직접 비교하지 않는다** — 구간 평균 vs 한 시점.
  - **결함 유형별로 센다** — 판단 10/12에서 틀린 2개가 **모두 over_limit**이다. "전체 몇 개 틀림"보다 "어떤 유형이 틀리나"가 다음 조치(데이터 보강? 검사 추가?)를 정한다. 게임 QA의 **결함을 유형별 분류해 원인을 좁히는 것**과 같다.
  - **12문항 · 그룹 2개 · 합성 규정** — 분모를 같이 적고 일반 성능으로 확대하지 않는다.

### 3-4 : 재개 · 저장 — 체크포인트로 학습 재개하고 모델 저장하기
- **핵심 개념**:
  - 흐름: 체크포인트 vs 추론용 모델 → `resume_from_checkpoint`로 12 → 24 → 가중치 표본 확인 → `save_pretrained` · 다시 읽어 같은 응답 → `ARCHIVE_FOLDER`로 ZIP.
  - **체크포인트와 추론용 모델은 용도가 다르다**.

    | | 학습 체크포인트 | 추론용 모델 |
    |---|---|---|
    | 위치 | `sft_run/checkpoint-12 · -24` | `sft_model/` |
    | 담긴 것 | `model.safetensors` · `optimizer.pt` · `scheduler.pt` · `rng_state.pth` · `trainer_state.json` | `model.safetensors` · `config.json` · `generation_config.json` · `tokenizer.json` · chat_template (**optimizer 없음**) |
    | 쓰는 곳 | 학습 재개 (`train(resume_from_checkpoint=…)`) | 응답 생성 · 7장 평가 · 6장 DPO 출발점 |

    - `save_pretrained(폴더)`는 추론용 가중치와 설정만 저장하고 **토크나이저는 별도로 `tokenizer.save_pretrained`** 를 부른다. 이 추론용 모델만으로는 같은 학습 상태를 복원하지 못한다.
  - **재개: 새 Trainer가 12에서 24까지 이어간다**. 순서: `del trainer, model` → `gc.collect()` → `torch.cuda.empty_cache()`(**GPU에 모델 두 개가 동시에 남지 않게**) → `checkpoint`에서 모델 다시 불러오기 → **같은 args · callback 없음**으로 새 `Trainer` → `trainer.train(resume_from_checkpoint=str(checkpoint))` → `global_step == 24` `assert`. 결과(슬라이드): 재개 전 / 최종 단계 **12 / 24**, 재개 구간 **14.721초**, 최종 dev loss **0.004919776692986488**.
  - **`max_steps=24`는 추가 24번이 아니다.** "전체 24 중 남은 12만" 한다. **모델 파일만 읽고 새로 `train()`하면 재개가 아니라 새 학습**이다(새 optimizer · 학습률 계획).
  - **가중치 변화 확인** (`model.layers.0.self_attn.q_proj.weight`의 고정된 256개 위치): `sample_count` 256, `changed_count` **24**, `max_abs_change` **8.77e-05**. BF16에서는 작은 변화가 반올림으로 사라질 수 있어서 **표본 변화 + 손실 + 실제 응답을 함께** 본다(노트북: 전체 변경 비율은 아님).
  - **저장 · 재로딩 검증**: 학습용 혼합 정밀도 래퍼를 제거(`unwrap_model(..., keep_fp32_wrapper=False)`)해 학습 전후와 재로딩의 추론 조건을 저장 dtype으로 맞춘다 → dev 12문항 학습 후 응답 생성 → `save_pretrained` + 토크나이저 저장 → 모델을 지우고 저장본을 다시 읽어 `policy01-over_limit`을 다시 생성 → **저장 전후 같은 응답: True**(`assert`).
  - **`sft_report.json`** = 설정 · 환경 · 데이터 해시 · 손실 기록 · 학습 전후 응답 원문(`dev_before` · `dev_after`) · 재개 기록 → **뒤 장 비교의 근거**.
  - **`sft_model.zip`은 폴더 항목 없이 묶는다**:

    | 만드는 법 | 첫 항목 | 7장 |
    |---|---|---|
    | `ARCHIVE_FOLDER` 셀 (`ZIP_STORED`, 파일만 `rglob`) | `sft_model/chat_template.jinja` | 통과 |
    | 탐색기 · 다른 압축 도구 | `sft_model/` (**폴더 항목**) | 이름 목록이 달라 **거부** |

    - 코드: `source_folder.rglob("*")` 중 `path.is_file()`인 것만 `arcname=path.relative_to(source_folder.parent)`로 넣는다. `ARCHIVE_FOLDER` 기본값은 `None`(아무 파일도 안 만듦). 같은 이름의 ZIP이 있으면 `FileExistsError`.
  - **새 세션에서 `checkpoint-12.zip`만 이어 학습하는 별도 경로**(`RUN_SAVED_CHECKPOINT`, 기본 False): 같은 데이터 · 학습 설정을 유지해야 하고 하드웨어 · 정밀도가 달라지면 수치가 달라질 수 있다. 복원 폴더가 **비어 있어야** 하고(이전 결과를 덮어쓰지 않음), ZIP의 각 항목이 **복원 폴더 밖을 가리키지 않는지** 경로를 검사한 뒤 푼다(`is_relative_to`).
  - 실무(슬라이드): 긴 학습은 중간에 끊긴다(세션 종료 · 선점형 GPU). **재개 가능한 체크포인트를 주기적으로 남긴다.** 학습을 이어가려면 `sft_run/checkpoint-24/` **전체**를 별도 보관해야 한다.
- **QA 체크포인트**:
  - **재개가 정말 "이어진" 것인지는 숫자로 확인** — 단계 12 → 24, 학습률이 같은 계획 위에 있는지, `global_step`이 24인지(🧭 4-①). "에러 없이 끝났다"가 곧 "제대로 재개됐다"는 아니다.
  - **저장하고 다시 읽어서 같은 응답이 나오는지** 확인 — 파일을 썼다는 것과 읽었을 때 같은 모델이라는 것은 다른 주장이다(2장의 "ZIP을 다시 읽어 확인"과 같은 습관).
  - **받는 쪽의 검사가 엄격하다** — 7장은 ZIP의 이름 목록이 정해진 모양이어야 통과시킨다. 같은 내용이어도 **만드는 도구에 따라 이름 목록이 달라진다**. 산출물 형식 계약을 코드로 두고 입력 쪽이 검사하는 구조(게임 QA의 **빌드 패키지 구성 검증**과 같다).
  - **체크포인트 ≠ 배포용 모델** — 용도별로 폴더를 나눠 보관하고, 학습 재개용에는 optimizer가 있어 크기가 3배라는 점을 보관 계획에 반영.
  - **재개 전에 이전 모델을 GPU에서 지운다** — 지우지 않으면 메모리가 모자라 재개 자체가 실패할 수 있다.
  - **ZIP을 풀기 전에 경로를 검사** — 외부에서 받은 압축 파일의 항목이 폴더 밖에 쓰는 것을 막는 방어다(보안 관점의 입력 검증).

|---|---|---|

## ⚠️ 오늘의 함정 모음 (재발 방지용)

| # | 함정 | 왜 틀렸나 | 올바른 방법 | 근거 |
|---|---|---|---|---|
| 1 | `processing_class=tokenizer`만 넣으면 답변 전용 labels가 생긴다고 믿는다 | 이미 토큰화된 자료이고 labels는 `encode_example` · `collate`가 만듦 | labels를 직접 만들고 위치로 검증 | 3-2 |
| 2 | −100과 attention 0을 같은 표시로 이해 | 하나는 **손실 제외**, 하나는 **아예 안 봄** | 프롬프트는 attention 1 + labels −100, 패딩은 attention 0 + labels −100 | 3-1 |
| 3 | 패딩 labels를 pad ID로 채운다 | 패딩 위치에 손실이 생김 | `pad_sequence(..., padding_value=-100)` | 3-1 |
| 4 | EOS를 정답에서 빼거나 개행까지 정답에 넣는다 | 끝낼 줄 모르는 모델 / 필요 없는 토큰 학습 | EOS까지만 `labels`, 뒤 개행은 버림 | 3-1 |
| 5 | 길이 초과 문항을 조용히 자른다 | 오른쪽은 EOS, 왼쪽은 근거 문서 소실 | 512 초과면 `ValueError`로 멈추고 원인 확인 | 3-1 |
| 6 | shift를 모델 내부와 직접 계산에서 둘 다 한다 | 정답이 한 칸 더 어긋남 | 3~5장은 내부 처리, 6장 DPO는 직접(한 곳에서만) | 3-1 |
| 7 | 12에서 멈췄으니 전체 목표가 12라고 생각 | 목표는 `max_steps=24`, 멈춤은 콜백 | 전체 계획 24 유지 + `StopAtTwelve`로 중단만 | 3-2 |
| 8 | `eval_steps=4`를 "4문항마다"로 읽는다 | 단위는 **갱신**(4갱신 = 16문항) | 설정표에서 단위를 같이 확인 | 3-2 |
| 9 | gradient checkpointing을 파일 체크포인트와 혼동 | 하나는 활성값 **재계산**, 하나는 **재개용 저장본** | 두 이름을 따로 외움 | 3-2 |
| 10 | T4에서 BF16이 안 되니 `fp16=True`로 바꾼다 | FP16 스케일링 경로를 쓰게 됨 | FP32로 읽고 학습 (메모리 약 2배) | 3-2 |
| 11 | test를 Trainer 평가에 같이 전달 | 설정 선택에 test가 섞여 dev가 됨 | train · dev만 전달, test는 최종 평가용으로 남김 | 3-2 |
| 12 | `grad_norm`이 1보다 크니 설정 실패라고 판단 | 로그가 클리핑 **전** 값을 담을 수 있음 | NaN · 폭증이 없는지만 본다 | 3-3 |
| 13 | train loss와 dev loss의 높이를 직접 비교 | 구간 평균 vs 한 시점 값 | 추이(내려가는지)만 본다 | 3-3 / 🧭 4-⑤ |
| 14 | dev loss가 낮으니 업무 답도 맞다고 믿는다 | 토큰 평균이라 판단 오류가 묻힘 (10/12) | 사람이 읽는 판단을 따로 기록 | 3-3 / 🧭 4-④ |
| 15 | JSON 출력 12/12를 업무 성능으로 읽는다 | 문장 틀을 익힌 것과 금액 판단은 다름 | 형식과 판단을 따로 센다 | 3-3 |
| 16 | `changed_count > 0`이면 학습이 잘 됐다고 해석 | 무언가 바뀌었다는 스모크 검사일 뿐 | 표본 변화 + 손실 + 응답을 함께 | 3-4 / 🧭 4-⑥ |
| 17 | 모델 파일만 읽고 `train()`을 다시 호출 | 재개가 아니라 **새 학습** (새 optimizer · 학습률 계획) | `train(resume_from_checkpoint=경로)` | 3-4 |

| 19 | `save_pretrained`만 하고 토크나이저를 저장하지 않는다 | 다시 읽을 때 토크나이저가 없음 | `tokenizer.save_pretrained`를 같이 호출 | 3-4 |
| 20 | 체크포인트를 추론용 모델로 쓰거나 그 반대로 쓴다 | 체크포인트는 optimizer 포함 약 3배, 추론용엔 optimizer 없음 | 용도별 폴더 보관 (`checkpoint-24` 전체 vs `sft_model`) | 3-4 |
