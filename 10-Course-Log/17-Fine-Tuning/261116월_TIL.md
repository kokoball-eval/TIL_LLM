## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | 파인튜닝 | Fine-tuning | 준비한 예제로 손실을 계산해 모델의 **학습 가능한 가중치**를 조정하는 작업 |
  | RAG | Retrieval-Augmented Generation (검색 증강 생성) | 검색한 문서를 **응답의 근거로 입력에 넣는** 구성. 가중치는 안 바뀐다 |
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 질문 하나에 모범답안 하나를 보여 주고 **그 답변 토큰의 손실**을 줄이는 학습 (3장) |
  | LoRA | Low-Rank Adaptation (저랭크 적응) | 기반 가중치 W는 고정하고 **작은 추가 행렬 B·A만** 학습 (4장, 540,672개 = 약 0.1%) |
  | QLoRA | Quantized LoRA (양자화 LoRA) | 고정한 W를 4비트(NF4)로 줄여 저장한 채 LoRA 학습. 학습 목표는 SFT 그대로 (5장) |
  | DPO | Direct Preference Optimization (직접 선호 최적화) | 같은 질문의 chosen(선호) vs rejected(비선호) 두 답의 **상대 선호**로 학습 (6장) |
  | NF4 | 4-bit NormalFloat | QLoRA가 쓰는 4비트 저장 형식 |
  | 토큰 / 토큰 ID | token / token ID | 토크나이저가 문장을 나눈 단위 / 그 단위의 번호. 모델은 글자가 아니라 **ID**를 읽는다 |
  | 로짓 | logit | 다음 토큰 후보별 **점수**. softmax를 거치면 확률 |
  | 교차 엔트로피 | cross-entropy | 정답 토큰에 준 확률이 낮을수록 커지는 손실 (−log p) |
  | 기울기 | gradient | 값을 바꾸면 손실이 어떻게 변하는지. 교차 엔트로피 + softmax에서는 **p − y** |
  | SGD / AdamW | Stochastic Gradient Descent / Adam with decoupled Weight decay | 기울기로 값을 갱신하는 방법. 1장은 SGD, 3장부터 AdamW |
  | greedy | greedy decoding | 매번 점수가 가장 높은 후보를 고르는 생성. **같은 입력 → 같은 출력**이라 비교에 쓴다 |
  | EOS | End Of Sequence | 모델이 "여기서 끝"이라고 내는 종료 토큰 (Qwen: 151645, 151643) |
  | revision | — | 모델 저장소의 **특정 버전**(커밋 해시). 같은 이름이어도 가중치·템플릿이 바뀔 수 있어 고정한다 |
  | dtype | data type | 가중치 저장 자료형 (fp32 · bf16 · NF4). 정밀도와 메모리가 갈린다 |
  | baseline | — | **학습 전** 모델의 응답 기록. 정답 예시가 아니라 "비교의 출발점" |
  | 정답 누수 | label leakage | 정답(검토 기준)을 모델 입력에 넣어서 평가가 무의미해지는 것 |
  | KV 캐시 | Key-Value cache | 생성 중 이전 토큰의 계산 결과를 저장해 두는 메모리 (실제 사용량이 모델 파일보다 커지는 이유 중 하나) |

- **핵심 통찰: 파인튜닝 1장은 "학습"이 아니라 "학습하기 전에 무엇이 틀리는지 남기는 장"이다**
  - 학습은 2장(예제 72개)부터고, 1장은 **CPU로 모델을 돌려 학습 전 응답을 얻고, 어디가 틀렸는지 나눠 읽고, `baseline.json`에 저장**하는 것까지다. 슬라이드 문장 그대로 "학습 뒤 좋아졌는지 말하려면, 학습 전 같은 입력 · 같은 설정에서 무엇이 틀렸는지 먼저 남겨야 한다."

    | 교안 | 오늘 한 것 | 남는 산출물 |
    |---|---|---|
    | 1-1 | 프롬프트 · RAG · 파인튜닝이 **바꾸는 곳**을 나누고, 입력(cases)과 사람용 기준(review_criteria)을 분리 | `cases` · `review_criteria` · `build_messages` |
    | 1-2 | 토큰 → 로짓 → 손실 → 기울기 → 한 번 갱신 (세 점수 예제) | 손실 1.099 → 0.909 |
    | 1-3 | 공개 모델(Qwen2.5-0.5B)을 greedy로 돌려 응답 8개 | 응답 8개, 잘림 1개 |
    | 1-4 | 응답을 **형식 · 의미 · 참조 일치**로 나눠 읽고 저장 | 형식 통과 0/4 · 0/4, `baseline.json` |

- **두 번째 통찰: 형식 통과 ≠ 업무 의미 ≠ 참조 일치 — 8개 모두 첫 단계(JSON 읽기)에서 떨어졌다**
  - 지시를 짧게(simple) 줘도, 자세히(explicit) 줘도 **8개 전부 JSON으로 읽히지 않았다.** simple은 앞말(`답변: …`), explicit은 코드 펜스(```` ```json ````), missing 문항은 `answered` 한 단어였다.
  - 그런데 JSON으로 읽히는 응답이 나와도 끝이 아니다. 슬라이드의 3칸 표처럼 **형식은 통과해도 금액 비교가 틀릴 수 있고**, 의미가 맞아도 모범답안과 글자가 다르면 참조 일치는 불일치다. → LLMOps 4-3에서 배운 "`output_valid: True`는 정확성 점수가 아니다"([LLMOps 11/04 TIL](../16-LLMOps/261104수_TIL.md))와 **같은 구조**가 파인튜닝 쪽에서 한 번 더 나왔다.

- **세 번째 통찰: 비교하려면 "무엇이 바뀌었나"를 말할 수 있어야 한다**
  - `baseline.json`에 모델 id · revision, 실행 환경, 가중치 dtype, 생성 설정, 입력, 원문 응답을 **같이** 남기는 이유는 나중에 "좋아졌다 / 나빠졌다" 앞에서 **네 가지(모델 버전 · 데이터 · 설정 · 원문) 중 무엇이 바뀌었는지부터** 확인하려는 것이다. [LLMOps 11/02 TIL](../16-LLMOps/261102월_TIL.md)의 "결과를 재현하는 데 필요한 조합 고정"과 같은 생각이다.

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 비교 기준(baseline)을 만들 때 고정할 것

| 고정할 것 | 1장의 값 | 바뀌면 생기는 일 | 근거 교안 |
|---|---|---|---|
| 모델 버전 | `Qwen/Qwen2.5-0.5B-Instruct` + revision 해시 | 같은 이름이어도 가중치 · 대화 템플릿이 달라질 수 있음 | 1-3 |
| 입력 | 질문 4개 + 문서, system 지시 2종 | 문항이 달라지면 점수 비교가 무의미 | 1-1 |
| 대화 템플릿 | `apply_chat_template` (역할 경계 · 답변 시작 위치) | 모델 계열이 바뀌면 템플릿부터 바뀜 (Qwen `<\|im_start\|>`, Llama `<\|start_header_id\|>`) | 1-2 |
| 생성 설정 | greedy, `repetition_penalty=1.1`, `max_new_tokens=192`, EOS 2개 | 샘플링을 켜면 같은 입력도 답이 달라짐. 상한이 작으면 잘림 | 1-3 |
| 정밀도 · 장치 | fp32, CPU | 정밀도가 달라지면 같은 가중치도 출력이 달라질 수 있음 | 1-3 |
| 원문 | `raw_response` 그대로 | 코드 펜스를 지워서 성공으로 바꾸면 **형식 오류가 사라진다** | 1-4 |

- **system 문자열은 학습(2~3장)과 추론에서 글자 하나까지 같게** 써야 한다. 2장의 `SYSTEM_PROMPT` = 1장의 explicit 지시.
- 게임 QA로 바꾸면: **회귀 테스트의 기준 빌드(baseline build)와 같은 개념**이다. 기준 빌드의 버전 · 설정 · 테스트 케이스가 기록돼 있어야 "새 빌드에서 뭐가 달라졌나"를 말할 수 있다.

### 2. 검사 하나가 보는 범위를 적는다

| 판정 층 | 무엇을 보나 | 못 보는 것 | 근거 교안 |
|---|---|---|---|
| 형식 통과 (`inspect_response`) | JSON 파싱 → 필드 3개 · status 계약 → 인용 ID가 제공 문서 안인지 | **금액 비교 · 승인 시점이 맞는지** | 1-4 |
| 업무 의미 | 85,000원과 같은 금액인데 승인을 요구하나, 90,000원 질문에서 서면 승인을 빠뜨리나, 95,000원 규정을 줬는데 옛 한도를 쓰나, 근거 없는 질문을 지원 불가로 단정하나 | 사람이 읽어야 함 (자동화 안 됨) | 1-4 |
| 참조 완전 일치 | 모범답안 딕셔너리와 **전체가 같은지** | 표현만 다른 올바른 답도 "불일치" | 1-4 |

- 세 기준은 서로를 대신하지 못한다. 슬라이드의 3행 예시: ① 형식 통과 + 의미 오답 + 불일치 / ② 형식 통과 + 의미 정답 + 불일치 / ③ **코드 펜스로 감싼 정답** → 형식 실패 + 의미 정답 + 참조 실패.
- 점수를 읽을 때는 **검사 이름과 분모를 같이** 본다. `0/4`의 분모 4는 **관찰용 4문항**이지 업무 정답률이 아니다. 일반 성능을 추정할 평가셋이 아니다.

### 3. 테스트 케이스는 "틀리기 쉬운 경우"를 일부러 설계한다

| id | 문서 | 확인하려는 것 | 정답 행동 |
|---|---|---|---|
| boundary | TRAVEL-01 (한도 85,000) | **경계값**(=) — 같은 금액 | answered, 승인 불필요 |
| over_limit | TRAVEL-01 | 조금 넘음 | answered, 예약 전 서면 승인 |
| updated | TRAVEL-02 (한도 95,000) | **규정 개정** — 질문은 over_limit과 **똑같고 문서만 다름** | answered, 승인 불필요 |
| missing | 없음 | **근거 없음** | abstained, 확인 불가 + 담당자 확인 |

- over_limit과 updated는 질문 문장이 같은데 정답이 반대다 → **문서를 읽어야만 맞힐 수 있는 쌍**이다. 모델이 질문만 보고 외운 답을 내는지 잡는 장치.
- 게임 QA의 **경계값 분석 · 동등 분할**과 같다. 한도 바로 위 · 아래 · 같은 값 + 패치로 규칙이 바뀐 경우 + 데이터가 없는 경우까지 한 세트로 만든다.
- **정답 누수 방지**: `review_criteria`는 사람이 출력과 비교하는 기준이고 **모델 입력에 넣지 않는다.** (`build_messages`는 `question`과 `documents`만 JSON으로 직렬화.)

### 4. Claude가 짚어준 확인 포인트

**① `fp32 · 4B` = "4바이트"이지 "40억 개"가 아니다**
- 슬라이드 17장 표: fp32 · 4B → **1.98 GB**, bf16 · 2B → 0.99 GB, NF4 · 0.5B → 0.25 GB. 모델은 **파라미터 약 4.9억 개**(0.5B 모델)이고, 여기서 `4B`는 "파라미터 하나가 4바이트"라는 뜻이다. 약 4.9억 × 4바이트 ≈ 1.98 GB가 맞아떨어진다.
- 전체 학습 fp32 · 16B → 7.90 GB는 파라미터당 **16바이트**(가중치 4 + 기울기 4 + AdamW 상태 2개 8)다. 슬라이드 14장의 "AdamW: 파라미터당 추가 메모리 2개"와 이어진다. (분해 내역은 Claude의 계산이며 슬라이드에 적힌 건 총합이다.)
- 실제 사용량은 활성값 · KV 캐시가 더해져 더 커진다(3장 BF16 전체 학습 최고 4.66 GiB는 슬라이드 값).

**② 지시를 자세히 바꿔도 0/4였지만, 이것을 "파인튜닝이 필요하다"의 증거로 단정하지 않는다**
- 노트북 문구: 두 조건은 **같은 모델에 지시만 바꾼 비교**이고, 결과 차이를 파인튜닝 효과라고 부를 수 없다. 네 문항은 동작을 읽기 위한 작은 예제다. 결과가 같거나 명확한 지시 쪽이 나빠져도 원문 그대로 해석한다.
- 오늘의 결론은 "**이 0.5B 모델은 이 지시로는 JSON 형식을 안 지킨다**" 정도까지다. 3장에서 같은 12문항(dev)으로 학습 전후를 비교할 때 비로소 효과를 말할 수 있다.

**③ explicit / missing 응답은 `answered` 한 단어 — 출력 2토큰**
- 근거가 없는 통신비 질문(missing)에서 자세한 지시를 줬는데 모델은 `answered`만 내고 끝냈다(EOS 도달, 출력 2토큰). 이건 JSON 형식 문제이면서 동시에 **"보류 + 담당자 안내"라는 행동을 못 한 것**이다. simple 쪽은 "출장 중 통신비는 최대 50만원까지 지원됩니다"처럼 **없는 금액을 지어냈다(환각)**.
- 같은 문항에서 **실패 양상이 서로 다르다**: 지어내기(simple) vs 단어 하나(explicit). 평가 기록에는 "실패"만 아니라 **어떻게 실패했는지 원문**이 남아야 하는 이유.

**④ simple / updated는 잘렸다 — 192토큰 상한 + EOS 없음**
- 슬라이드 19장 표에서 simple / updated만 출력 192, EOS **X**, 판정 "잘림(상한 도달)". 이 응답은 **끝까지 쓴 답이 아니라 중간에 끊긴 답**이라서, 의미를 판정하기 전에 "잘렸는지"부터 나눠야 한다. 노트북이 `length_limited`를 따로 기록하는 이유.
- 반대로 `max_new_tokens`를 무작정 늘리면 시간 · 메모리가 늘고, 예상 답 길이의 1.5~2배가 기준(슬라이드).

**⑤ 어휘 크기 두 숫자: 151,665 vs 151,936**
- 슬라이드 11장은 토크나이저 어휘를 **151,665개**, 13장은 실제 모델의 로짓 한 줄을 **151,936**으로 적는다. 숫자가 다르다. 슬라이드는 이유를 적지 않았다. Qwen2.5 설정에서 출력 크기(`vocab_size`)가 토크나이저 어휘보다 크게 잡혀 있는 것으로 알고 있지만(Claude 설명, 이 차이의 이유는 내가 직접 확인하지 못함), 3장 전에 `model.config.vocab_size`와 `len(tokenizer)`를 출력해서 **확인 필요**.

## 1장. 학습할 행동과 기준 응답 정의

### 1-1 : 입력 분리 — 프롬프트 · RAG · 파인튜닝의 역할 나누기
- **핵심 개념**:
  - 흐름: 세 방법의 역할 → 네 문항 → 모델 입력과 사람용 기준 분리 → SFT · LoRA · QLoRA · DPO 지도 → `build_messages`.
  - **세 방법은 바꾸는 곳이 다르다**:

    | 방법 | 무엇을 바꾸나 | 비용 | 언제 |
    |---|---|---|---|
    | 프롬프트 | 지시와 문맥 텍스트 | 즉시 · 거의 없음 | 형식 · 지시를 **먼저** 시도 |
    | RAG | 검색한 근거 문서 | 검색 저장소 운영 | **자주 바뀌는 지식** |
    | 파인튜닝 | 학습 가능한 가중치 | 데이터 + GPU 학습 | **지시해도 반복되는 행동 실패** |

    - 규정이 95,000원으로 바뀌면 **문서만 바꾸면** 된다. 금액을 가중치에 외우게 하면 규정이 바뀔 때마다 다시 학습해야 한다. → **지식은 RAG, 행동(형식 · 보류 · 인용)은 파인튜닝.**
  - **SFT · LoRA · QLoRA · DPO는 같은 줄에서 고르는 선택지가 아니다** — 학습 **목표**(무엇을 정답으로 보나)와 학습 **대상**(무엇을 바꾸나)이 다른 축이다.

    | 이름 | 축 | 한 줄 | 장 |
    |---|---|---|---|
    | SFT | 학습 목표 | 모범답안 토큰에 손실 | 3장 |
    | LoRA | 학습 대상 | W 고정 + B·A만 학습 (540,672개 · 0.1%) | 4장 |
    | QLoRA | 학습 대상 | 고정 W를 NF4(4비트)로. 목표는 SFT 그대로 | 5장 |
    | DPO | 학습 목표 | chosen vs rejected 상대 선호. 3장 SFT 결과에서 시작해 **전체 가중치**로 수행(4~5장 어댑터를 이어 붙이지 않음) | 6장 |

  - **`cases`는 모델로, `review_criteria`는 사람에게.** `build_messages(case, explicit)`는 `question` + `documents`를 JSON 문자열로 만들어 **user** 메시지에, 지시 문자열을 **system** 메시지에 둔다.

    | | simple | explicit |
    |---|---|---|
    | 필드 | JSON 3필드(status · answer · citations) | + 3필드만, 코드 펜스 금지 |
    | 보류 규칙 | 없음 | 근거 없으면 abstained |
    | 인용 규칙 | 없음 | answered ↔ 문서 ID |
    | system 토큰 수 | 32 | 165 |

  - 기준 응답은 **정답 예시가 아니라 비교의 출발점**이다. 모든 문서는 수업용 가상 규정이다. 이 실습은 검색 시스템을 구현하지 않고 **관련 문서를 직접 넣어** 생성 단계의 행동만 본다(RAG를 구현한 것이 아님).
- **QA 체크포인트**:
  - **"틀리기 쉬운 경우"를 데이터 모으기 전에 설계** — 경계값(=), 조금 넘음, 개정, 근거 없음 (🧭 3).
  - **같은 질문 + 다른 문서 쌍**으로 "문서를 읽는가"를 따로 확인.
  - **정답 누수 점검** — 모델 입력 JSON에 `review_criteria` 내용이 들어갔는지 먼저 본다.

### 1-2 : 토큰 · 원리 — 토큰 확률과 가중치 갱신으로 학습 이해하기
- **핵심 개념**:
  - 흐름: 토큰과 토크나이저 → `apply_chat_template` → 세 점수 예제(softmax · 교차 엔트로피 · 기울기 · step) → 왜 `p − y`인가.
  - **모델은 글자가 아니라 토큰 ID를 읽는다.** 같은 뜻의 문장이 한글 20토큰 · 영어 15토큰, "1박 85,000원"은 10토큰, "70,000원은 한도를 초과"는 11토큰 → **단어 수 = 토큰 수가 아니다.** 특수 토큰: `<|im_start|>` 151644, `<|im_end|>` 151645, `<|endoftext|>` 151643.
  - **`apply_chat_template`** — 역할 경계(`<|im_start|>system … <|im_end|>`)와 **"여기서부터 답하라"**(`<|im_start|>assistant`)를 붙인다.

    | 인자 | 하는 일 | 실무에서 볼 점 |
    |---|---|---|
    | `add_generation_prompt=True` | 끝에 assistant 시작 표시 추가 | **추론 입력은 True · 정답이 들어간 학습 대화는 False**(2~3장) |
    | `return_dict` · `return_tensors` | `input_ids` + `attention_mask`를 텐서로 | `model.generate(**inputs)`로 바로 |
    | (모델 계열) | Qwen `<\|im_start\|>`, Llama `<\|start_header_id\|>` | 모델을 바꾸면 템플릿부터 바뀜 |

  - **세 점수 한 번 갱신** (`scores=[0,0,0]`, 정답=3번째, SGD 학습률 0.3). 이 계산은 **언어 모델 파인튜닝이 아니라**, 한 위치에서 후보 세 개의 점수만 직접 학습하는 수치 예제다.

    | 단계 | 값 |
    |---|---|
    | 점수 s | [0, 0, 0] |
    | softmax p | [0.333, 0.333, 0.333] |
    | 손실 −log p₂ | 1.099 |
    | 기울기 p − y | [0.333, 0.333, **−0.667**] |
    | s − 0.3 × 기울기 | [−0.1, −0.1, 0.2] |
    | 다시 p / 손실 | [0.299, 0.299, **0.403**] / **0.909** |

    - 정답 점수는 올라가고 나머지는 내려갔다. **`loss.backward()`는 기울기만 계산하고, 값이 실제로 바뀌는 시점은 `optimizer.step()`**.
    - `F.cross_entropy`는 **로짓을 직접** 받는다(앞에 softmax를 따로 넣지 않는다).
    - 실제 모델은 위치마다 로짓이 [어휘 151,936] 한 줄씩. 정답 토큰 확률을 올리는 이 계산을 **답변 토큰 수만큼 평균**한 것이 SFT 손실(3장).
  - **왜 기울기가 `p − y`인가**: 교차 엔트로피 `L = −s_y + log Σ e^(s_j)`를 `s_i`로 미분하면 `−[i=y] + p_i = p_i − y_i`. 연쇄법칙의 작은 예(x=3, w=0.5, 목표 2 → ∂L/∂w = (y−t)·x = −1.5). 검산은 수치 미분 `(L(s₂+0.001) − L(s₂−0.001)) / 0.002 = −0.6667` = autograd의 −0.667.

    | | SGD (1장) | AdamW (3장) |
    |---|---|---|
    | 갱신 | θ − lr·g | θ − lr·m/√v (보정) |
    | 첫 걸음 | 기울기에 비례 | 가중치마다 약 lr |
    | 추가 메모리 | 0 | 파라미터당 2개 |
    | 흔한 lr | — | 전체 1e-5대 · LoRA 1e-4대 |

- **QA 체크포인트**:
  - **토큰 수로 비용 · 길이를 본다** — 같은 한글 문장이 영어보다 토큰이 더 든다. 입력 길이 상한 · 비용 · 잘림 판단은 글자 수가 아니라 토큰 수로.
  - **수치 예제의 "검산 습관"** — 손으로 푼 미분(−0.667)을 수치 미분과 autograd 두 가지로 확인하는 방식은 테스트에서 **기대값을 독립적인 방법으로 검증**하는 것과 같다.
  - 템플릿 안의 **`add_generation_prompt`가 학습 때와 추론 때 다르게** 들어가야 한다는 점을 2~3장에서 반드시 확인.

### 1-3 : 실제 응답 — Colab에서 학습 전 기준 응답 만들기
- **핵심 개념**:
  - 흐름: `from_pretrained`(revision · dtype · 장치) → `eval()`과 `inference_mode()` → `GenerationConfig`(greedy · 192토큰) → `generate` 결과에서 **새 토큰만** → 응답 8개(지시 2 × 문항 4).
  - **불러오기는 학습이 아니다.** `AutoModelForCausalLM.from_pretrained(MODEL_ID, revision=REVISION, dtype=torch.float32).to(DEVICE)` — 호출 자체는 가중치를 바꾸지 않는다. 메모리는 🧭 4-① 참고.

    | | 추론 (1장 generate) | 학습 (3장 train) | 무엇을 제어하나 |
    |---|---|---|---|
    | `model.eval()` | 켬 | 끔 (Trainer가 `train()`으로) | dropout 등 **평가 동작** |
    | `torch.inference_mode()` | 켬 | 끔 | **기울기 그래프 기록** |

    - 둘은 **역할이 다르다**(`eval()` ≠ 기울기 기록 끄기).
  - **생성 설정은 "답을 고르는 방법"이지 학습 파라미터가 아니다**(가중치를 업데이트하지 않음).

    | 인자 | 1장 값 | 하는 일 | 실무에서 볼 점 |
    |---|---|---|---|
    | `do_sample` · `num_beams` | False · 1 | greedy: 가장 큰 후보 | 평가 · 비교는 greedy, 다양한 문장이 필요하면 sampling |
    | `repetition_penalty` | 1.1 | 나온 토큰 점수 깎기 | logit>0 → ÷1.1, <0 → ×1.1. **greedy에도 영향**(순위가 바뀜) → 비교 중 고정 |
    | `max_new_tokens` | 192 | **입력 제외** 새 토큰 상한 | 예상 답 길이의 1.5~2배, **잘림을 로그로** |
    | `eos_token_id` | [151645, 151643] | 나오면 멈춤 | 잘못 바꾸면 안 끝나거나 일찍 멈춤 |
    | `pad_token_id` | 151643 | 길이 맞춤 빈칸 | **종료와 역할이 다르다** |
    | `temperature` · `top_p` · `top_k` | (안 씀) | sampling에서만 의미 | greedy에 넣으면 무시 경고 |

    - JSON처럼 형식이 중요한 출력은 greedy 또는 낮은 temperature. **저장소 기본 생성 설정을 믿지 말고 코드에 명시.**
  - **`generate`는 "입력 + 새 토큰"을 돌려준다** → `generated[0, input_length:]`만 읽는다(입력 289토큰이면 `[:289]`는 버리고 `[289:]`를 읽는다). `decode(skip_special_tokens=True)`는 제어 토큰을 **표시에서만** 빼며 내용 오류는 고치지 않는다.
  - 각 응답에 `input_tokens` · `output_tokens` · `ended_with_eos` · `length_limited`(상한 도달 + EOS 없음)를 같이 기록한다. 슬라이드 19장 표(발췌): simple/boundary 입력 158 · 출력 104 · EOS O, **simple/updated 출력 192 · EOS X → 잘림**, simple/missing 68 · 38 · O, explicit/boundary 291 · 61 · O, explicit/over_limit 289 · 58 · O, explicit/missing 201 · **2** · O(`answered` 한 단어).
  - **실제 응답 8개 — 지시를 바꿔도 형식 · 의미가 다 틀렸다** (슬라이드 20장):

    | 문항 | 정답 행동 | simple | explicit |
    |---|---|---|---|
    | boundary | 승인 불필요 | 애매 · "승인 필요"로 읽힘 | JSON이지만 **"승인이 필요합니다"(오답)** — 코드 펜스로 감쌈 |
    | over · updated | 서면 승인 / 불필요 | "예약할 수 없습니다" 등 | "다음과 같은 방법으로…"(내용 없음) |
    | missing | 보류 + 담당자 | **"50만원 지원"(환각)** | `answered` 한 단어 |

- **QA 체크포인트**:
  - **비교 조건 고정** — 같은 입력 · 같은 가중치 · 같은 생성 설정에서 **system 지시만** 바꾸는 비교. 한 번에 하나만 바꾼다.
  - **잘림(length_limited)을 먼저 분리** — 192토큰에서 끊긴 응답의 의미를 판정하면 안 된다.
  - **입력 토큰 제외** — `generate` 반환값 전체를 응답으로 읽으면 system 지시까지 응답에 섞인다.

### 1-4 : 나눠 읽기 — 실패를 읽고 학습할 행동 정하기
- **핵심 개념**:
  - 흐름: JSON 객체 → 필드와 상태 계약 → 인용 ID → **응답마다 검사하고 기준 옆에 놓기** → 형식 · 의미 · 참조 일치 구분 → `baseline.json` 저장.
  - **`inspect_response`는 세 단계, 앞이 실패하면 뒤는 안 본다** — "거짓 3개를 독립된 오류 3개로 세지 않기 위해".

    | 단계 | 검사 | 코드 |
    |---|---|---|
    | ① `json_object` | 원문을 **고치지 않고** `json.loads` + dict인지 | 코드 펜스 · 앞말을 지워서 성공으로 바꾸지 않음 |
    | ② `schema_ok` | 키가 정확히 `{status, answer, citations}` · status는 answered/abstained · answer는 빈 문자열 아님 · citations는 문자열 리스트 + (answered는 인용 필수 / abstained는 인용 금지) | bool · null을 문자열로 간주하지 않음 |
    | ③ `citation_ids_ok` | 인용 ID ⊆ **이번 문항에 준** 문서 ID | 존재만 확인. 문서가 실제로 답을 뒷받침하는지는 사람이 읽음 |

  - 자기 점검(`check_format_examples`)은 "형식이 올바른 예제는 통과 / 설명이 붙은 원문은 거절 / 잘못된 타입은 거절 / 제공 문서에 없는 인용 ID는 거절" 네 가지를 `assert`로 확인한다. **정답 문장의 의미를 채점하는 테스트가 아니다.**
  - **실제 결과: 8개 모두 ① 단계에서 실패.** 형식과 인용 ID 통과: **simple 0/4 · explicit 0/4**(분모는 관찰용 4문항, 업무 정답률 아님).
  - 형식 통과 수가 늘어도 **업무 의미가 좋아졌다고 결론내리지 않는다.** 확인할 것: 85,000원과 같은 금액에 승인 요구? / 90,000원 질문에서 승인 시점 누락? / 95,000원 규정을 줬는데 옛 한도 사용? / 근거 없는 통신비를 지원 불가로 단정? (단정은 오류, "확인할 수 없다 + 담당자 확인"이 정답)
  - **API 모델은 JSON 모드로 형식을 강제**할 수 있지만, **로컬 모델은 학습으로 형식을 익히고(3장) 의미는 따로 본다.**
  - **`baseline.json`이 답해 주는 질문**:

    | 필드 | 답해 주는 질문 |
    |---|---|
    | `model_id` · `revision` | 같은 가중치 · 템플릿인가 |
    | `runtime` · `weight_dtype` | 환경 · 정밀도 차이인가 |
    | `generation` | 생성 규칙이 같은가 |
    | `cases` · `review_criteria` | 같은 문제로 비교하나 |
    | `records[ ]` | 실제 원문과 판정 근거 |

    → 실험 재현의 네 가지(모델 버전 · 데이터 · 설정 · 원문). 실험 결과 파일은 **노트북과 별도 저장소(Drive · 버킷)** 에 둔다.
- **QA 체크포인트**:
  - **"원문을 고쳐서 통과시키지 않는다"** — 코드 펜스를 벗겨서 파싱하면 형식 실패가 사라져 **학습할 행동(JSON만 출력)** 이 안 보인다. 3장 SFT 전후 비교에서 형식 통과가 오른 것을 "학습 효과"로 읽으려면 이 기준이 그대로 유지돼야 한다.
  - **형식 통과율이 오른 것과 업무 정확도가 오른 것은 다른 주장** — 자동 검사 뒤에 질문 · 규정 · 원문을 같이 읽는 단계를 남긴다 (LLMOps 4-3과 같은 원칙).
  - 인용 ID 검사는 "이번에 준 문서인가"까지만 본다 → **"그 문서가 정말 이 답을 뒷받침하나"는 사람 검토.**
