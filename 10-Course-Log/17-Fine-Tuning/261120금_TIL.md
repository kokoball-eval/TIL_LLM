## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | LoRA | Low-Rank Adaptation (저랭크 적응) | 기반 가중치 W는 **고정**하고, 옆길로 작은 행렬 B·A의 곱(변화량)만 학습해 더하는 방법 |
  | PEFT | Parameter-Efficient Fine-Tuning (파라미터 효율적 미세조정) | 모델 전체보다 **적은 수의 파라미터만** 학습하는 방법들을 묶어 부르는 말. 같은 이름의 Hugging Face 라이브러리도 있다 |
  | QLoRA | Quantized LoRA (양자화 LoRA) | 고정한 기반 가중치를 4비트로 줄여 저장한 채 LoRA 학습 (5장) |
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 모범답안 토큰의 손실로 배우는 **학습 목표**. 3·4·5장이 같은 목표를 쓴다 |
  | DPO | Direct Preference Optimization (직접 선호 최적화) | 두 응답의 선호로 배우는 학습 목표 (6장) |
  | 랭크 r | rank (랭크) | A와 B 사이의 **중간 차원**. ΔW의 랭크는 r 이하. 이번 설정 r = 8 |
  | alpha | lora_alpha (LoRA 배율 값) | 변화량에 곱하는 배율은 **alpha ÷ r**. 이번 16 ÷ 8 = 2 |
  | ΔW | delta W (가중치 변화량) | `(alpha / r) × B @ A`. 학습이 끝난 뒤 W에 합칠 수 있다 |
  | 어댑터 | adapter | 기반 모델과 **함께 써야 하는** 추가 학습 부분(A·B와 적용 설정). 단독으로 완전한 모델이 아님 |
  | q_proj / v_proj | query projection / value projection (쿼리·밸류 투영층) | 어텐션 안의 선형층 두 종류. 이번에 LoRA를 붙인 곳 |
  | all-linear | all-linear (모든 선형층) | `target_modules`에 이 값을 주면 모든 선형층에 LoRA를 붙인다 (보강 실습) |
  | requires_grad | requires grad (기울기 계산 대상 여부) | `False`이면 기울기 · optimizer 상태를 만들지 않아 메모리가 줄어든다 |
  | Kaiming uniform | Kaiming uniform initialization (카이밍 균등 초기화) | PEFT 기본 A 초기화. 원논문은 Gaussian(가우시안) 초기값을 설명 — 둘 다 B = 0으로 시작 |
  | merge_and_unload | merge and unload (병합 후 어댑터 분리) | 변화량을 W에 합친 일반 모델을 반환 |
  | PeftModel | PEFT model (PEFT 모델 래퍼) | 기반 모델에 어댑터를 붙여 둔 모델. `from_pretrained`로 다시 연결 |
  | safetensors | safetensors (안전한 텐서 저장 형식) | 가중치를 담는 파일 형식 (`adapter_model.safetensors`) |
  | atol / rtol | absolute tolerance / relative tolerance (절대 / 상대 허용 오차) | `\|a − b\| ≤ atol + rtol × \|b\|` — 0 근처의 오차 / 값 크기에 비례하는 오차 |
  | logits | logits (로짓) | 다음 토큰 후보별 점수. 저장 전후·병합 전후를 이 값으로 비교 |
  | BF16 / FP32 | Brain Floating Point 16-bit / 32-bit Floating Point | 가중치 숫자 형식. 이번 어댑터 비교는 **같은 정밀도**여야 한다 |
  | GiB | gibibyte (기비바이트) | 바이트 수를 2³⁰으로 나눈 단위 |
  | greedy | greedy decoding (탐욕 디코딩) | 매번 점수가 가장 높은 후보 하나만 고르는 생성 |
  | SHA-256 | Secure Hash Algorithm 256-bit (보안 해시) | 파일 내용의 지문 (`data_sha256`) |

- **핵심 통찰: LoRA는 "적게 학습한다"가 아니라 "무엇을 학습 대상으로 둘지 바꾼다" — 그런데 같은 조건으로 비교해도 공정한 비교가 아닐 수 있다**
  - LoRA는 W를 건드리지 않고 옆길 `h = W·x + (alpha/r)·B·A·x`의 B·A만 학습한다. 그래서 학습 대상은 **540,672개 / 전체 494,573,440개(0.11%)** 이고, 어댑터 파일은 약 **2.1MB**, 최대 메모리는 **1.61GiB**(전체 SFT 4.66GiB)다.
  - 그런데 3장과 **같은 학습률 2e-5**로 돌리면 dev loss는 0.9207 → 0.8717로 조금만 내려가고, 형식 통과 **0/12**, 학습 후 원문은 학습 전과 **글자까지 같다**. 같은 조건이었는데 아무것도 못 배운 것처럼 보인다. 2e-5는 **전체 가중치 SFT 기준** 값이고 LoRA에 맞춘 값이 아니기 때문이다. 슬라이드 문장: "비교 실험은 '한 가지만 다르게'가 원칙이에요. 대신 그 한 가지에 맞지 않는 조건이 섞였는지도 함께 봐요."

    | 교안 | 오늘 한 것 | 남는 산출물 |
    |---|---|---|
    | 4-1 | W 옆에 B·A 경로를 더하는 구조를 작은 행렬로 계산, 두 경로의 합 = 병합 확인, 실제 층의 파라미터 수 계산 | 540,672개 (q_proj · v_proj, r = 8) |
    | 4-2 | B = 0 시작의 첫 기울기, `LoraConfig` · `get_peft_model`, 학습 대상이 `lora_` 뿐인지 검사, 3장과 같은 조건으로 24갱신 | dev loss 0.9207 → 0.8717 · 19초 · 1.61GiB |
    | 4-3 | 어댑터만 저장, 같은 기반 + 어댑터로 복원(오차 0.0), FP32 병합 수치 확인 | 2.1MB · 오차 0.0 · 병합 6.87e-05 |
    | 4-4 | 조건 대조 후 baseline · 전체 SFT · LoRA 원문 비교, 설정 바꿔 보기 | 형식 SFT 12/12 · LoRA 0/12 (lr 2e-5) |

- **두 번째 통찰: 숫자(손실)가 조금 움직인 것과 행동이 바뀐 것은 다르다**
  - 슬라이드 문장: "loss가 줄었다 ≠ 행동이 바뀌었다. 0.92 → 0.87은 정답 토큰 확률이 조금 오른 정도예요." 3장에서 "dev loss 0.0049인데 초과 금액은 틀린다"를 봤다면, 4장은 반대쪽이다 — **손실은 줄었는데 출력은 전혀 안 바뀌었다.** 손실도 원문도 같이 읽어야 한다는 같은 결론이 양쪽에서 나왔다.
  - 보강 실습에서 **한 줄씩** 바꿔 판단이 **0/12 → 6/12 → 10/12**로 올라가는 것을 보여 줬다: ① `learning_rate` 2e-5 → 2e-4(형식만 배움: 짧은 답 · 근거 지어내기) → ② `target_modules` q·v → `"all-linear"`(학습 파라미터 4,399,104개, 전체 SFT와 같은 점수에 메모리는 약 1/3).

- **세 번째 통찰: "같은 입력인지"를 코드가 먼저 확인한 뒤에야 비교한다**
  - 비교 전에 `check_comparison_inputs`가 **학습 조건 · 생성 조건 · 관찰 문항(case_id · messages)** 을 대조하고, 앞에서는 **데이터 해시 · revision · dtype**을 확인한다. 하나라도 다르면 멈춘다. 비교 결과를 읽기 전에 "무엇이 같은지"부터 보증하는 구조다(🧭 1).

- **향후 계획 및 다짐**
  - 올려 둔 `lora.ipynb`는 **셀 출력이 비어 있고** `lora_report.json`도 없는 상태였다. 그래서 이 TIL의 LoRA 숫자(540,672 · 0.8717 · 19초 · 1.61GiB · 2,175,168바이트 · 6.87e-05 · 0.4411 · 0.0184 등)는 **슬라이드에 적힌 실행 결과** 기준이다. 슬라이드의 "SFT 12/12 · 판단 10/12 · 0.0049 · 27초 · 4.66GiB"도 교안 작성 환경 값이고, **내 T4 실행값은 다르다**(🧭 4-①).
  - 5장 전에 할 것(슬라이드 마지막 장): `lora_adapter` · `lora_report.json` 받기 → 5장 QLoRA 비교에 그대로 사용 → 설정 바꿔 보기 실습(lr 2e-4 · `all-linear` · atol 1e-3).
  - 오픈소스 프로젝트(LLM 트리아지 평가)에 가져갈 것: 방법 두 개를 비교할 때 **"조건이 같다"와 "공정하다"를 따로 점검**하기, 병합 · 변환처럼 **수치가 같아야 하는 단계는 허용 오차와 함께 원문 일치도 확인**하기, 비교 보고서에 방법별 학습 파라미터 수 · 시간 · 메모리를 같이 남기기.

### 3. "같은 조건"이 "공정한 조건"은 아니다

| 같게 둔 것 (3장 = 4장) | 방법에 따라 달라야 할 수도 있는 것 |
|---|---|
| 데이터 · 답변 마스크 · 손실 | **학습률** — 전체 SFT 2e-5 · LoRA는 보통 더 큼(1장 표: 흔한 lr 전체 1e-5대 · LoRA 1e-4대) |
| 갱신 횟수 24 · seed 42 · 생성 설정(greedy · 192토큰) | 적용 층 — q·v만이 충분한지 (`all-linear` 보강) |
| 배치 1 × 누적 4 · warmup 2 · linear | 추가 파라미터 크기(r) |

- 같은 학습률 2e-5에서 LoRA가 0/12였다고 해서 **"LoRA는 SFT보다 못하다"** 로 결론내리면 안 된다. 2e-4로 올리자 12/12(형식)가 되고, `all-linear`까지 하면 SFT와 같은 점수(판단 10/12)에 메모리 약 1/3이 됐다.
- 게임 QA로 바꾸면: **저사양 기기와 고사양 기기를 같은 그래픽 옵션으로만 비교하는 것**과 같다. 설정이 같아도 한쪽에 불리하면 "기기 성능 차이"가 아니라 "설정 선택의 차이"를 재는 것이다.

### 4. Claude가 짚어준 확인 포인트

**① 내 `sft_report.json`(T4 · FP32)은 슬라이드의 3장 SFT와 값이 다르다 (Claude가 파일을 열어서 확인)**

|---|---|---|
| 학습 전 dev loss | 0.9207 | 0.9167 |
| 학습 후 dev loss | 0.0049 | **0.0003** (0.000303) |
| 형식 통과 (dev 12) | 12/12 | 12/12 |

- 내 `dev_before` 12개는 모두 형식 실패(0/12)였고, 길이 제한에 걸린 응답은 없었다. missing 두 문항은 2토큰(`answered` 한 단어)이다. 슬라이드의 학습 전 패턴과 같다.

- 차이의 원인은 단정할 수 없다. 정밀도(FP32 vs BF16 — 3장 슬라이드의 "BF16은 작은 변화가 반올림으로 사라질 수 있다"와 이어질 수는 있음) · GPU · 라이브러리 버전이 모두 다르다. 가능한 설명일 뿐 직접 확인한 것은 아니다.
- 4장 노트북은 **내 `sft_report.json`을 읽어서** "전체 SFT" 칸을 채운다. 그래서 내 환경에서 4장을 돌리면 SFT 칸이 슬라이드 21장(12/12 · 10/12 · 0.0049)이 아니라 **내 값**으로 나올 것으로 읽힌다. 주의: 내 "12/12 완전 일치"는 모범답안과 JSON 전체가 같은지 본 **엄격한 기준**이고, 슬라이드의 "판단(보조)"는 간이 규칙이라 두 기준이 다르다.

**② 슬라이드의 파라미터 수 두 개는 계산으로 맞아떨어진다 (Claude의 계산)**

**③ 어댑터 파일 2,175,168바이트는 "54만 개 × 4바이트 + 헤더"와 맞아떨어진다 (Claude의 계산)**

**④ 병합 허용 오차를 1e-4에서 1e-3으로 풀어서 통과시키는 것 — 오차 값을 먼저 읽는다**

- 허용 오차를 올려서 `assert`를 통과시키는 건 **검사를 약하게 만드는 일**이다. 통과 기준을 바꿀 땐 "왜 오차가 커졌나(학습으로 값이 커짐 · FP32 반올림)"를 설명할 수 있어야 하고, 오차만 보지 말고 **병합 전후 다음 토큰 ID가 같은지 · 생성 원문이 같은지**를 같이 확인한다(노트북: 허용 오차는 업무 오답을 허용한다는 뜻이 아님). 원본 실행에서는 다음 토큰 ID가 4913 · 4913으로 같았다.

**⑤ loss가 0.92 → 0.87로 줄었는데 출력이 "글자까지 같은" 이유 (Claude의 설명)**

**⑥ 보강 실습 결과를 읽는 순서 — 판단(보조)는 "간이 규칙"이다**

## 4장. LoRA 어댑터 학습과 모델 복원

### 4-1 : 저랭크 업데이트 — 저랭크 업데이트를 행렬로 이해하기
- **핵심 개념**:
  - 흐름: `h = W·x + (alpha/r)·B·A·x` → W · A · B의 모양 → 작은 숫자 예제로 두 경로의 합과 병합이 같은지 확인 → 실제 층의 파라미터 수.
  - **W는 고정, 옆길 B·A의 변화량만 더한다.** W [출력, 입력](Qwen 첫 층 896 × 896), A [r, 입력], B [출력, r]. 수식: `ΔW = (alpha / r) · B @ A`, **rank(ΔW) ≤ r**. 이번 설정 r = 8 · alpha = 16 → 배율 **2**. 노트북 문구: 이는 W를 작은 A·B로 **대체**하는 구조가 아니라 W 옆에 **더하는** 구조다.
  - **작은 행렬로 확인** (W 2×3, A 1×3, B 2×1, x = [2, 1, 1], rank 1, alpha 2):

    | 항목 | 값 |
    |---|---|
    | W · A · B 모양 | (2, 3) · (1, 3) · (2, 1) |
    | `A @ x` | [1.0] |
    | 기존 출력 `W @ x` | [2.0, 1.0] |
    | 추가할 변화량 `ΔW @ x` | [1.0, −1.0] |
    | LoRA 출력 (두 경로의 합) | [3.0, 0.0] |
    | 병합한 출력 `(W + ΔW) @ x` | [3.0, 0.0] ✔ 같음 |

    - **`(W + ΔW)·x = W·x + ΔW·x`** — 학습할 때는 옆길로 따로 계산하고, 배포할 때는 합쳐서 하나로 만들 수 있다. 같은 결과를 두 방식으로 계산할 수 있다는 것이 **LoRA 저장 · 병합의 근거**다.
  - **파라미터 수: 896 × 896 대신 8 × (896 + 896)**:

    | 층 (한 블록) | W 모양 [출력, 입력] | W 원소 수 (고정) | LoRA r × (입력 + 출력) | LoRA 원소 수 |
    |---|---|---|---|---|
    | q_proj | 896 × 896 | 802,816 | 8 × (896 + 896) | 14,336 |
    | v_proj | 128 × 896 | 114,688 | 8 × (896 + 128) | 8,192 |
    | 블록 하나 합계 | - | 917,504 | - | 22,528 |
    | × 24 블록 | - | - | - | **540,672** |

    - `trainable params: 540,672 || all params: 494,573,440 || trainable%: 0.1093`. 모델 전체 494,573,440 = 기반 494,032,768(3장이 전부 학습한 수) + LoRA 540,672. 기반 쪽은 `requires_grad=False` → 기울기 · optimizer 상태가 없어 메모리가 줄어든다.
  - 노트북 문구: 원논문은 A의 **Gaussian** 초기값을 설명하지만 PEFT 기본은 **Kaiming uniform**이다. 둘 다 B를 0으로 두어 초기 추가 경로를 0으로 만든다 → 논문의 구조와 라이브러리의 구체적인 기본값을 구분해서 읽는다.
- **QA 체크포인트**:
  - **병합 전후가 같다는 것을 숫자로 확인**(작은 행렬 `assert torch.allclose`) — "수식상 같다"를 코드로 한 번 더 증명해 둔다.
  - **실제 모양과 학습할 원소 수를 직접 센다** — q_proj와 v_proj는 출력 차원이 달라서(896 vs 128) 같은 공식에 넣어도 개수가 다르다. 슬라이드 숫자를 믿기 전에 계산으로 검산(🧭 4-②).
  - 배율은 **alpha/r**이라 r만 바꿔도 변화량의 배율이 달라진다(노트북). rank와 alpha를 따로 읽는다.

### 4-2 : PEFT 학습 — PEFT로 LoRA 학습하기
- **핵심 개념**:
  - 흐름: B = 0일 때 첫 기울기 → 3장과 같은 데이터 · 답변 마스크 → `LoraConfig` → `get_peft_model`과 학습 대상 검사 → 같은 `TrainingArguments`로 24번 갱신.
  - **B = 0에서 시작하면 첫 기울기는 B에만 간다** (작은 예제, SGD lr 0.1, 목표 [3, 0]):

    | 단계 | 값 |
    |---|---|
    | 초기 출력 (B = 0 → BA = 0 → h = W·x) | [2.0, 1.0] |
    | 첫 A 기울기 | [[0.0, 0.0, 0.0]] |
    | 첫 B 기울기 | [[−2.0], [2.0]] |
    | 한 번 갱신한 출력 | [2.4, 0.6] |
    | 작은 예제 손실 | 1.0 → 0.36 |

    - 시작 = **원래 모델** / 1번째 갱신에서 **B만** 움직임(A 기울기 0) / 2번째부터 B ≠ 0이라 **A도 함께 학습**. 코드 `assert`: A 기울기 0 · B 기울기 > 0.
  - **`LoraConfig`: 어디에, 얼마나 크게 붙일지 정한다**.

    | 파라미터 | 현재 값 | 의미 |
    |---|---|---|
    | `task_type` | `CAUSAL_LM` | 다음 토큰 생성용 PEFT 구성 |
    | `r` | 8 | A · B 중간 차원 (늘리면 파라미터와 표현 범위가 늘지만 품질 개선은 확인 필요) |
    | `lora_alpha` | 16 | 배율 alpha/r = 2 |
    | `target_modules` | `["q_proj", "v_proj"]` | query · value 투영층에만 적용 (모든 선형층과 다름) |
    | `lora_dropout` | 0.0 | 옆길 입력의 dropout을 끈 비교 |
    | `bias` | `none` | bias는 학습 안 함 |
    | `init_lora_weights` | `True` | PEFT 기본 초기화 (B = 0) |
    | `base_model_name_or_path` · `revision` | 고정한 모델과 커밋 | 어댑터가 어느 기반 가중치에 대응하는지 기록 |

    - 값 8과 16은 이 수업의 **작은 비교 설정**이다. 최적 rank나 모든 모델에 맞는 alpha로 일반화하지 않는다(노트북).
  - **`get_peft_model(base, config)`은 옆길을 "붙이기"만 한다.** 호출만으로 학습이 끝난 게 아니다. 붙인 뒤 `requires_grad`와 이름을 검사한다.

    | 검사 | 언제 | 막는 사고 |
    |---|---|---|
    | 학습 대상 = `lora_` 이름뿐 | 붙인 직후 | 기반 가중치까지 학습 (사실상 전체 SFT) |
    | B = 0 → 학습 뒤 B ≠ 0 · W 그대로 | 학습 전 · 후 | 어댑터가 안 배웠거나 W가 바뀜 |

    - 첫 W/A/B 모양 (896, 896) · (8, 896) · (896, 8), LoRA 배율 2.0, `trainable params: 540,672 || all params: 494,573,440 || trainable%: 0.1093`.
  - **PEFT · LoRA · SFT는 답하는 질문이 다르다** (슬라이드 11장):

    | 이름 | 답하는 질문 | 이 과정 |
    |---|---|---|
    | SFT | 모범답안으로 **무엇을 예측**하도록 배울까? | 3 · 4 · 5장의 학습 목표 |
    | DPO | 두 응답의 선호를 어떻게 배울까? | 6장 |
    | LoRA | **어떤 추가 파라미터만** 학습할까? | 4장 |
    | QLoRA | 고정 기반 가중치의 **저장 비용**을 어떻게 줄일까? | 5장 |
    | PEFT 라이브러리 | 이런 구성을 **어떤 도구**로 적용할까? | `LoraConfig` · `get_peft_model` |

    - 목표: SFT(답변 토큰 손실) / 방법: LoRA(A·B만 갱신) / 도구: PEFT(`LoraConfig`) / 결과: 어댑터(기반 모델과 함께).
  - **학습 조건은 3장과 같고 갱신 대상만 다르다**:

    | `TrainingArguments` | 값 | 3장과 |
    |---|---|---|
    | batch × 누적 | 1 × 4 | 같음 |
    | `max_steps` | 24 (2 epoch) | 같음 |
    | `learning_rate` | 2e-5 | 같음 |
    | warmup · 감소 | 2 · linear | 같음 |
    | bf16 · gradient checkpointing | True · True (지원 시) | 같음 |
    | `eval_steps` · `logging_steps` | 4 · 4 | 같음 |
    | `save_strategy` | `no` | **같음(자동 중간 저장 끔)** — `save_pretrained`로 어댑터를 저장하는 것까지 금지하지는 않음 |
    | optimizer가 갱신하는 것 | **A와 B (540,672개)** | **다름** |

    - 같게 둔 것: 데이터 · 답변 마스크 · 손실, 갱신 횟수 · 학습률 · seed 42, 생성 설정(greedy · 192토큰). 슬라이드 점선 메모: **학습률 2e-5는 3장 전체 SFT 기준이고 LoRA에 맞춘 값이 아니다** → 4-4 끝에서 바꿔 본다.
  - **결과: dev loss 0.9207 → 0.8717, 답은 그대로.** LoRA 학습 후 `policy01-over_limit` 원문은 학습 전 원문과 **글자까지 같다**(코드 펜스 + 규정 문장 복사, 70,000원을 끝내 안 읽음). 학습 시간 19초, 최대 메모리 1.61GiB(SFT 27초 · 4.66GiB). 메모리 차이의 출처: 전체 SFT는 4억 9천만 개의 기울기 + AdamW 상태 2개를 들고 있고 LoRA는 54만 개 분량만. 큰 모델일수록 메모리 차이가 결정적이다(슬라이드).
- **QA 체크포인트**:
  - **붙인 직후 학습 대상을 이름으로 검사** — `lora_`가 아닌 파라미터가 `requires_grad=True`이면 "LoRA인 줄 알았는데 전체 SFT"가 된다. 눈으로 확인하지 않고 `assert`.
  - **"한 가지만 다르게" + "그 한 가지에 맞지 않는 조건이 섞였는지"** — 학습률이 3장과 같다는 것은 비교의 장점이자 함정이다(🧭 3).
  - **손실만 보지 않고 원문을 본다** — 0.92 → 0.87이어도 출력이 안 바뀌었다(🧭 4-⑤).
  - **PEFT와 LoRA를 같은 알고리즘의 두 이름으로 읽지 않는다** — PEFT는 방법들을 묶은 개념이자 라이브러리 이름이다(노트북).

### 4-3 : 저장 · 복원 — 어댑터 저장과 다시 불러오기
- **핵심 개념**:
  - 흐름: `save_pretrained`로 어댑터만 저장 → 모델 해제 → 같은 기반 모델 + `PeftModel.from_pretrained` → logits · 생성 원문 비교 → FP32 `merge_and_unload` 수치 확인.
  - **`save_pretrained`: 어댑터만 약 2.1MB로 저장한다**. 저장 파일 `README.md` · `adapter_config.json` · `adapter_model.safetensors`, 어댑터 가중치 **2,175,168바이트**. 저장 직후 같은 입력의 마지막 위치 logits를 보관하고(`saved_logits`) `del trainer, model, base_model, first_lora` → `gc.collect()` → `torch.cuda.empty_cache()`로 GPU 메모리를 반환한다.

    | 함수 | 하는 일 | 이 수업의 확인 |
    |---|---|---|
    | `model.save_pretrained` | 어댑터 가중치와 설정만 저장 | 기반 모델을 중복 저장하지 않음 |
    | `PeftModel.from_pretrained(base, folder, is_trainable=False)` | 같은 기반 모델에 어댑터를 연결 (**추론용**) | 모델 ID · revision · dtype 맞춤 |
    | `merge_and_unload()` | 변화량을 W에 합친 모델 반환 | 병합 전후 수치 오차 확인 |

    - `is_trainable=False`는 복원한 어댑터를 **추론용**으로 읽는 설정이다(이어 학습하는 설정과 구분).
  - **다시 불러오기: 같은 기반 + 어댑터 = 같은 답**. 코드: `adapter_config.json`의 `base_model_name_or_path` · `revision`이 현재 값과 같은지 `assert` → 기반 모델을 새로 읽고 `PeftModel.from_pretrained` → `allclose(saved_logits, reloaded_logits, atol=1e-4, rtol=1e-4)` + 생성 원문 일치 `assert`. 결과: 재로딩 logits 최대 절대 오차 **0.0**, 재로딩 응답 일치 **True**.
  - **`torch.allclose(a, b, atol, rtol)`** = `|a − b| ≤ atol + rtol × |b|`. atol은 0 근처의 절대 오차, rtol은 b 크기에 비례하는 상대 오차. 노트북 문구: 이 허용 오차는 **업무 답변의 오답을 허용한다는 뜻이 아니다.** 로짓 수치 비교와 생성 문자열의 정확한 일치를 따로 확인한다.

    | 맞춰야 하는 것 | 다르면 |
    |---|---|
    | 기반 모델 ID · revision | 어댑터가 다른 W 위에 더해져 **의미 없는 출력** |
    | dtype (BF16 저장 → native BF16 GPU) | 반올림이 달라 원문이 바뀔 수 있음 → 노트북이 멈춤 |

  - **`merge_and_unload`: 두 경로를 W 하나로 합친다**. 작은 반올림 오차를 보려고 **FP32로 바꾼 모델에서** 비교한다(`model = model.float()`) → 병합 전 logits 보관 → `merge_and_unload(safe_merge=True)` → 병합 후 logits. 결과: FP32 병합 logits 최대 절대 오차 **6.866455078125e-05**(허용 1e-4 이내), 병합 전후 다음 토큰 ID **4913 · 4913**. 병합 모델 전체를 디스크에 저장하지는 않는다. 이 확인은 새로운 학습 결과로 세지 않는다(노트북).

    | 배포 방식 | 장점 | 단점 |
    |---|---|---|
    | 기반 + 어댑터 (`PeftModel`) | 업무별 어댑터 교체 · 저장 2.1MB | 추론 때 옆길 계산이 조금 더 |
    | 병합 (`merge_and_unload`) | 일반 모델과 같은 속도 · 서빙 도구 호환 | 어댑터마다 **전체 모델 크기**로 저장 |

  - 노트북 문구: **QLoRA의 양자화 복원과 이 장의 일반 LoRA 병합을 같은 작업으로 단정하지 않는다**(5장에서 따로).
- **QA 체크포인트**:
  - **저장하고 다시 읽어서 같은 점수 · 같은 원문**이 나오는지 확인 — 파일을 썼다는 것과 복원이 같다는 것은 다른 주장이다(3장 `sft_model` 재로딩 확인과 같은 습관).
  - **어댑터는 "짝이 되는 기반 모델"이 기록돼 있어야 한다** — 모델 ID · revision이 다르면 출력이 의미 없어진다. 어댑터 설정에 기록한 이유가 이것이다. (게임 QA로 바꾸면 **패치 파일이 어느 빌드용인지 버전 표기가 없으면 적용할 수 없는 것**과 같다.)
  - **수치 비교와 문자열 비교를 따로** — logits이 허용 오차 안이어도 생성 원문이 다를 수 있고, 반대도 있다. 둘 다 `assert`.
  - **병합은 "수식상 같다"를 숫자로 확인** — 오차 6.87e-05는 FP32 반올림 수준이다. 오차가 커지면 이유를 설명할 수 있어야 한다(🧭 4-④).

### 4-4 : 같은 조건 비교 — 같은 조건에서 학습 결과 비교하기
- **핵심 개념**:
  - 흐름: `lora_report.json` 저장 → `sft_report.json`과 학습 · 생성 조건 대조 → baseline · 전체 SFT · LoRA 원문 비교 → dev 12개 형식 검사 → 같은 규정 계열의 네 행동 읽기.
  - **비교 전에 조건부터 대조한다** (`check_comparison_inputs`):

    | 대조 대상 | 항목 |
    |---|---|
    | 파일 · 모델 | `data_sha256` · revision · dtype |
    | 학습 조건 | `max_steps` · `learning_rate` · `gradient_accumulation_steps` · `max_length` · `seed` |
    | 생성 조건 | `GENERATION` 전부 |
    | 관찰 문항 | `case_id` · `messages` (질문 + 근거 문서까지 같아야 함) |

    | | baseline | 3장 전체 SFT | 4장 LoRA |
    |---|---|---|---|
    | 출처 | `sft_report.json` · `dev_before` | `sft_report.json` · `dev_after` | 이번 실행 · `dev_after` |
    | 갱신한 파라미터 | 0 | 494,032,768 | 540,672 |

  - **결과: 같은 학습률에서 SFT 12/12, LoRA 0/12** (슬라이드 21장, 교안 작성 환경):

    | | baseline | 전체 SFT | LoRA |
    |---|---|---|---|
    | 학습 파라미터 | 0 | 494,032,768 | 540,672 |
    | dev loss | 0.9207 | 0.0049 | 0.8717 |
    | 형식 통과 | 0/12 | 12/12 | 0/12 |
    | 학습 시간 | - | 27초 | 19초 |
    | 최대 메모리 | - | 4.66GiB | 1.61GiB |

    - 시간은 이 작은 모델 · 24갱신에선 크게 차이 나지 않는다. 측정은 seed 42 · dev 12 · **1회 실행** (1문항 = 8.3%p).
  - **원문 읽기: 형식 통과와 판단은 따로다** (`policy01-over_limit`, 한도 65,000 · 질문 70,000원):

    | | 원문 요약 | 형식 | 판단 |
    |---|---|---|---|
    | baseline | ` ```json ` 펜스 + 규정 문장 복사 (금액 비교 없음) | X | X |

  - **보강 실습 — 설정을 바꿔 보기 (한 줄 바꾸고 다시 돌린다)**:

    | 바꾼 줄 | 셀 | 효과 |
    |---|---|---|
    | ① `learning_rate=2e-5` → `2e-4` (핵심) | `TrainingArguments` (4-2) | 형식 0/12 → 12/12 |
    | ② `target_modules` → `"all-linear"` (선택) | `LoraConfig` (4-2) | 학습 파라미터 540,672 → **4,399,104** |

    - ④를 고치면 `check_comparison_inputs`의 `learning_rate` 대조에서 멈춘다 → **일부러 다르게 한 비교라 그 키만 목록에서 뺀다.** (조건 대조를 우회하는 게 아니라 "이번엔 이 조건이 다르다"를 명시하는 것.)

- **QA 체크포인트**:
  - **비교는 "무엇이 같은가"부터** — 데이터 해시 · 모델 · 정밀도 · 학습 · 생성 · 문항이 같을 때만 숫자를 읽는다(🧭 1). 한 번 맞춰 둔 코드가 **다른 환경에서는 멈춰 주는 것**이 장점이다.
  - **조건 대조를 풀 때는 이유를 남긴다** — ④처럼 일부러 다르게 한 비교는 그 키만 명시적으로 뺀다. 조용히 `assert`를 지우면 비교가 무의미해진다.
  - **결론은 한 번의 실행으로 확정하지 않는다** — 1문항 = 8.3%p, seed 42 · 1회. "LoRA가 SFT보다 못하다 / 같다"가 아니라 "이 설정에서 이 조건으로는"으로 쓴다(🧭 3).
  - **자원 지표를 함께 기록** — 점수가 같아도 메모리 1/3이면 선택이 달라진다. 보고서에 파라미터 수 · 시간 · 메모리를 같이 남긴다.
  - **남는 오답을 유형으로 센다** — 모든 방법에서 초과 금액 2문항이 틀렸다면 방법이 아니라 **데이터/학습량의 한계**일 수 있다(가설, 확인 필요).

## 정리 — 4장 결과물

| 강 | 한 줄 | 남긴 것 |
|---|---|---|
| 4-1 | W 옆에 저랭크 경로 B·A를 더한다 | 두 경로의 합 = 병합 · 540,672개 |
| 4-2 | `LoraConfig`로 붙이고 LoRA만 학습되는지 검사한다 | 0.9207 → 0.8717 · 19초 · 1.61GiB |
| 4-3 | 어댑터만 저장하고 같은 기반 위에 복원 · 병합한다 | 2.1MB · 오차 0.0 · 6.87e-05 |
| 4-4 | 조건을 맞춘 뒤 숫자와 원문을 함께 읽는다 | SFT 12/12 · LoRA 0/12 (lr 2e-5) |

- **5장이 읽는 것**: `lora_adapter/`(2.1MB 어댑터)와 `lora_report.json`(설정 · 자원 · 원문) → 5장 QLoRA는 **4비트 기반 + LoRA**로 같은 조건에서 비교한다.
- 5장 전에 할 것: `lora_adapter` · `lora_report.json` 받기 → 5장 QLoRA 비교에 그대로 사용 → 설정 바꿔 보기 실습(lr 2e-4 · `all-linear` · atol 1e-3).
- 직접 해 본 것: 슬라이드와 노트북 코드를 Claude와 같이 읽고, 숫자별 "보는 것 / 못 보는 것"과 비교 조건 대조 구조를 표로 정리했다. 올려 둔 내 `sft_report.json`을 Claude가 열어 슬라이드 값과 비교했다(🧭 4-①). 4장 노트북 실행은 아직 안 했다(향후 계획).

## ⚠️ 오늘의 함정 모음 (재발 방지용)

| # | 함정 | 왜 틀렸나 | 올바른 방법 | 근거 |
|---|---|---|---|---|
| 1 | LoRA가 W를 작은 A·B로 **대체**한다고 이해 | W는 그대로 두고 **옆에 더하는** 구조 | `h = W·x + (alpha/r)·B·A·x` | 4-1 |
| 2 | 배율을 alpha만으로 읽는다 | 배율은 **alpha ÷ r** (r만 바꿔도 달라짐) | r = 8 · alpha = 16 → 2 | 4-1 |
