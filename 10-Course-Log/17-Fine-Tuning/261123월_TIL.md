## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | QLoRA | Quantized LoRA (양자화 LoRA) | 고정한 기반 모델을 **4비트로 줄여 저장**한 채 그 위에 LoRA 어댑터만 학습하는 구성. 학습 목표는 여전히 SFT |
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 모범답안을 정답으로 따라 쓰게 하는 학습 목표 |
  | LoRA | Low-Rank Adaptation (저랭크 적응) | 기반 W는 고정하고 작은 A·B만 학습 (4장) |
  | 양자화 | quantization | 가중치를 **더 적은 종류의 값(대표값)** 으로 근사해 저장하는 방법 |
  | 대표값 · 코드북 | representative value · codebook | 저장할 때 쓰는 눈금 목록. 값은 가장 가까운 대표값의 **번호**로 저장 |
  | NF4 | 4-bit NormalFloat (4비트 정규분포 플로트) | **0 근처가 촘촘한 16개** 대표값. 균등한 4비트와 다름 |
  | scale | scale (블록 크기값) | 블록마다 곱해 주는 값. 근삿값 = scale × 대표값 |
  | 이중 양자화 | double quantization | **scale까지** 다시 양자화해 부가 저장량을 줄임 (4.5 → 약 4.127비트/가중치, 계산값) |
  | 저장 dtype · 계산 dtype | storage dtype · compute dtype (저장 · 계산 자료형) | 4비트 번호를 담는 상자(`uint8`)와, 풀어서 행렬을 곱할 때의 자료형(BF16·FP32)은 **다른 것** |
  | uint8 | unsigned 8-bit integer (부호 없는 8비트 정수) | 4비트 코드를 담는 바이트 상자. 8비트 양자화라는 뜻이 아님 |
  | prepare_model_for_kbit_training | prepare model for k-bit training (k비트 학습 준비) | 기존 파라미터를 고정하고 재계산을 켜는 학습 준비 함수. **비양자화 FP16/BF16 파라미터를 FP32로 바꿀 수 있음** |
  | paged optimizer | paged optimizer (페이지 단위 최적화기) | 원논문의 메모리 급증 대응 구성. 이번 수업은 쓰지 않고 `adamw_torch`를 유지 |
  | BF16 · FP32 | Brain Floating Point 16-bit · 32-bit Floating Point | 숫자 저장·계산 형식. 5장은 4장과 **같은 정밀도 경로**여야 함 |
  | logits | logits (로짓) | 다음 토큰 후보별 점수. 새 세션 복원 비교에 사용 (어휘 151,936개 전부) |
  | atol · rtol | absolute · relative tolerance (절대 · 상대 허용 오차) | `\|저장 − 복원\| ≤ atol + rtol × \|복원\|` |
  | GiB | gibibyte (기비바이트) | 바이트 수를 2³⁰으로 나눈 단위 |

- **핵심 통찰: QLoRA는 "항상 더 싸고 같은 품질"이 아니다 — 0.5B 모델에서는 이득이 안 보였다**
  - 4장과 같은 q_proj · v_proj, rank 8(학습 파라미터 540,672개)에 **기반 모델만 NF4로 바꿔** 비교했다(교안, RTX 5060 Laptop · BF16 · seed 42 · dev 12 · 1회 실행).

    | 항목 | 4장 LoRA | 5장 QLoRA | 읽을 점 |
    |---|---|---|---|
    | 학습 파라미터 | 540,672 | 540,672 | 같음 |
    | dev loss | 0.9207 → 0.8717 | 1.0459 → 0.9745 | **출발점부터 다름** (4비트 근사 때문) |
    | 형식 · 인용 통과 | 0/12 | 0/12 | 둘 다 실패 → 끝에서 설정을 바꿔 봄 |
    | 학습 최대 메모리 | 1.61 GiB | 1.64 GiB | 0.5B에서는 이득이 안 보임 |
    | 학습 시간 | 18.5초 | 25.3초 | QLoRA가 더 느림 |

  - 이유는 슬라이드가 **구성별 메모리**로 보여 준다. "4비트 모델"인데 가장 큰 덩어리는 **압축되지 않은 임베딩**(272.3MB, 학습 준비 뒤 FP32로 544.5MB)이다. 양자화는 선형층 가중치 저장만 약 1/4로 줄인다.

- **두 번째 통찰: 저장 · 계산 · 압축 안 되는 층을 따로 읽는다**

  | 구분 | 무엇 | 자료형 (셀 14 출력) |
  |---|---|---|
  | ① 저장 | NF4 4비트 번호 + scale | `torch.uint8`에 포장 |
  | ② 계산 | 근삿값으로 풀어서 곱함 | `torch.bfloat16` (T4는 FP32) |
  | ③ 비양자화 · 어댑터 | 임베딩 · Norm · bias · A · B | `torch.float32` (임베딩은 로드 직후 bf16 → 준비 뒤 fp32로 2배) |

  - 그래서 `uint8`만 보고 "8비트 양자화"라고 읽거나, 전체 메모리를 단순히 4비트 비율로 계산하면 안 된다.

- **세 번째 통찰: 같은 0/12도 실패의 이유가 다르고, 복원 검사가 실패하면 지우지 않고 환경부터 본다**
  - 원본 QLoRA dev 12개의 첫 실패 이유: status 필드 없음 5 · abstained인데 인용이 있음 3 · answer가 빈 문자열 2 · 인용 ID가 제공 문서에 없음 1 · JSON 객체를 여러 개 이어 붙임 1. 4장 LoRA(코드 펜스 + 규정 복사)와 실패의 모양이 다르다.
  - 새 세션 복원은 한 문항의 logits와 원문으로만 확인하고, 교안에는 원본이 "이 PC에서 검사 실패"라고 적혀 있다. 노트북 문구: 실패한 검사를 지우지 말고 저장한 환경과 현재 환경부터 확인한다.

- **향후 계획 및 다짐**
  - 올려 둔 `qlora.ipynb`는 **셀 출력이 비어 있는(실행 전) 상태**였다. 그래서 QLoRA의 숫자(1.0459 → 0.9745 · 1.64 GiB · 25.3초 · 451,325,952 / 725,901,056 bytes 등)는 **슬라이드에 적힌 실행 결과**이고, "측정" 환경은 교안 작성 PC(RTX 5060 Laptop · BF16)이다. 슬라이드에도 T4 · L4는 미실측이라고 적혀 있다.
  - 내 환경: 올려 둔 `lora_report.json`은 **NVIDIA L4 · BF16**에서 만든 것이다. 5장 노트북이 `config.dtype`과 현재 GPU의 정밀도가 같은지 확인하므로, **BF16을 지원하는 GPU(L4 등)에서 돌려야** 한다. T4면 시작 전에 `ValueError`로 멈춘다.
  - 6장 전에 할 것(슬라이드 마지막 장): `qlora_result.zip` 받아 두기 → 원본 실행과 변경 실행의 결과를 따로 보관 → 설정 바꿔 보기 실습(lr 2e-4 · all-linear · `atol 1e-4` 그대로, 교안에서는 BF16 실측 통과).
  - 오픈소스 프로젝트(LLM 트리아지 평가)에 가져갈 것: 방법을 비교할 때 **품질 · 메모리 · 시간을 따로 읽고** "항상 더 좋다"로 일반화하지 않기, 실패를 **이유별로 세어서** 기록하기, 양자화처럼 근사가 들어가는 설정은 **값 하나가 아니라 통째로** 보고서에 남기기.

### 3. 이번 비교는 "통제 실험"이 아니다 (노트북 문구)

- 노트북은 "원래 가중치의 비트 수만 바꾼 완전한 통제 실험이 아니다"라고 적는다. QLoRA는 준비 함수가 비양자화 파라미터를 FP32로 바꾸는 차이도 함께 가져오기 때문이다.
- 논문은 NF4 · 이중 양자화 · paged optimizer를 함께 설명하지만, 이번 코드는 **NF4 + 이중 양자화**만 쓰고 optimizer는 4장과 같은 `adamw_torch`다. LoRA도 q · v에만 붙인다. 그래서 논문의 전체 구성이나 성능 수치를 재현한 실험으로 읽지 않는다.
- 게임 QA로 바꾸면: **빌드 A와 B를 비교하는데 두 빌드의 설정이 한 가지가 아니라 여러 가지 다를 때, 그 차이를 "빌드 차이"로만 읽지 않는 것**과 같다.

### 4. Claude가 짚어준 확인 포인트

**① 올려 둔 내 `lora_report.json`은 5장 노트북의 입력 검사를 통과하고, BF16 GPU가 필요하다 (Claude가 파일을 열어서 확인)**
- 필수 항목 11개가 모두 있고, 학습 조건 9개가 5장 기대값과 같다. `data_sha256`은 3일차 ZIP의 지문(`018a6120…`)과 같고, dev 12문항의 ID와 messages도 일치한다.
- `config.dtype`이 `torch.bfloat16`이고 장치는 NVIDIA L4다. 5장은 이 값과 현재 GPU의 정밀도가 같은지 확인하므로 **BF16을 지원하는 GPU에서 돌려야** 하고, BF16 미지원 GPU(T4)면 시작 전에 멈춘다. 11/20 TIL에서 "T4(FP32)로 돌려야 한다"고 적은 것은 그때 올린 `sft_report.json`(T4) 기준이었고, 이번 4장 결과는 L4에서 만든 것이다.

**② 내 L4 LoRA 값은 교안과 거의 같다 — GPU가 달라도 같은 BF16이면 비슷했다 (Claude가 확인)**

| 항목 | 교안 (RTX 5060 Laptop · BF16) | 내 `lora_report.json` (L4 · BF16) |
|---|---|---|
| dev loss | 0.9207 → 0.8717 | 0.9233 → 0.8697 |
| 학습 최대 메모리 | 1.615 GiB | 1.613 GiB |
| 형식 통과 | 0/12 | 0/12 (코드 펜스 10 · 기타 2) |
| 저장 전후 logits 오차 / 병합 오차 | 0.0 / 6.87e-05 | 0.0 / 5.15e-05 |
| 어댑터 파일 | 2,175,168 bytes | 2,175,168 bytes |
| 학습 시간 | 18.5초 | 23.7초 (GPU가 달라 직접 비교 불가) |

- 이 보고서 안의 `comparison.full_sft`(3일차 SFT 결과)는 dev 12문항 중 **10개가 모범답안과 일치**하고, 초과 금액 문항에서 "한도 이하"라고 답한 것도 교안과 같다. 반면 앞서 올렸던 내 T4(FP32) `sft_report.json`은 12/12였다. **같은 코드에서 정밀도(BF16 / FP32)와 GPU가 다르면 판단 점수가 10/12 / 12/12로 달랐다**는 뜻이다. 3일차 TIL에서 "정밀도 차이일 수 있다(확인 못 함)"고 적은 가설이 한 걸음 더 지지되지만, GPU와 라이브러리 버전도 같이 달라서 원인을 단정하지는 못한다.

**③ NF4 복원 예제를 계산해 봤다: 눈금이 많고 촘촘할수록 오차가 줄어든다 (Claude 계산, 교안의 NF4 코드북 사용)**
- 같은 다섯 값(−2.0, −0.9, 0.2, 1.3, 2.0, scale 2.0)을 NF4 16개 대표값으로 저장하면 번호는 [0, 3, 8, 14, 15], 복원값은 [−2.0, −0.7898, 0.1592, 1.446, 2.0]이고 **최대 오차는 약 0.146**이다. 교안의 2비트 예제(대표값 4개)는 최대 오차 0.6333이었다.
- 다만 이건 **작은 예제를 같은 방식으로 계산한 것**이고, 실제 Qwen 가중치의 오차나 모델 품질과 직접 이어 읽으면 안 된다. 눈금 수가 많다고 모델 품질이 같다는 뜻도 아니다(실제로 QLoRA의 dev loss 출발점은 4장보다 높았다).

**④ 슬라이드 13장의 메모리 구성표는 계산으로 맞는다 (Claude 검산)**
- 선형층 4비트 번호 357,826,560개 × 0.5바이트 = 178.9MB, 임베딩 136,134,656개 × 2바이트(BF16) = 272.3MB → ×4바이트(FP32) = 544.5MB, Norm · bias 71,552개는 0.14MB → 0.29MB, LoRA A·B 540,672개 × 4바이트 = 2.16MB. 로드 직후 합 **451.3MB**, 학습 준비 뒤 합 **725.9MB**가 슬라이드와 같다(실제 바이트 수와는 256바이트 차이, 작은 부가 정보로 읽힘). 세 파라미터 묶음의 합도 기반 모델의 494,032,768개와 같다.
- 그래서 임베딩이 "압축되지 않고 오히려 두 배가 되는" 가장 큰 덩어리라는 설명이 숫자로 확인된다.

**⑤ 4.5 → 4.127비트 계산도 맞고, "약 1/4"는 선형층 저장에만 해당한다 (Claude 검산)**
- scale을 FP32로 두면 4 + 32/64 = 4.5비트이고, scale도 양자화하면 4 + 8/64 + 32/(64×256) ≈ 4.127비트다. BF16(16비트) 대비 약 3.9배라서 "약 1/4"이다. 노트북이 말하듯 **설명용 계산이고 실제 파일 크기가 아니며**, 활성값 · 임베딩 · 어댑터는 4비트가 아니다.

**⑥ 슬라이드의 QLoRA 학습 후 인용 ID가 한자 섞인 "政策01-v1"이다 — 인용 ID 검사의 쓸모**
- 원본 QLoRA의 학습 후 응답에서 인용 ID가 제공 문서의 `policy01-v1`이 아니라 `政策01-v1`로 나왔다(슬라이드 14장). 인용 ID가 "제공 문서 ID 집합 안인가"를 확인하는 검사가 이런 오류를 잡는다. 이 검사는 **허용 범위 확인**일 뿐 답변 의미가 맞다는 증거는 아니다(1일차 이후 계속 나오는 이야기).

**⑦ 새 세션 복원은 "같은 조리법"이 필요하다 — 어댑터만으로는 모델이 아니다**
- ZIP에는 `qlora_report.json`(설정 · 원문 · 기준 logits) + 어댑터 설정 + 어댑터 가중치(2.1MiB)만 있고, **기반 모델 가중치 · optimizer · 병합 모델은 없다.** 그래서 복원은 같은 revision을 NF4로 다시 로드 → **같은 학습 준비(FP32 상태 복원)** → 어댑터 부착 → logits 비교 순서로 한다. 준비 단계를 빼면 학습 때와 다른 모델이 된다.

## 5장. QLoRA 학습과 자원 비교

### 5-1 : 양자화와 계산 정밀도 구분하기
- **핵심 개념**:
  - 흐름: 2비트 코드북 예제 → NF4의 16개 대표값 → 이중 양자화 → 저장 · 계산 · 비양자화 층의 자료형 구분.
  - **양자화 = 가까운 대표값의 번호로 저장**한다. 예제(교안): 값 [−2.0, −0.9, 0.2, 1.3, 2.0], scale = 가장 큰 절댓값 2.0, 대표값 4개 [−1, −1/3, 1/3, 1] → 저장 번호 [0, 1, 2, 2, 3], 복원 [−2.0, −0.6667, 0.6667, 0.6667, 2.0], 최대 절대 오차 0.6333. **저장하는 것 = 번호 + scale, 잃는 것 = 대표값 사이의 세밀한 차이.** (실제 NF4 구현이나 Qwen 가중치가 아니라 원리를 보여 주는 예)
  - **NF4**: 0 근처가 촘촘한 16개 대표값이다. 첫 4비트 층의 코드북은 [−1.0, −0.6962, −0.5251, −0.3949, −0.2844, −0.1848, −0.0911, 0.0, 0.0796, 0.1609, 0.2461, 0.3379, 0.4407, 0.5626, 0.723, 1.0]이고, 0 옆 간격은 약 0.08~0.09, 양끝 간격은 약 0.28~0.30이다. 근삿값 = 블록 scale × code[4비트 번호].
  - **scale까지 압축**: 64개 가중치마다 scale 1개, 256개 scale마다 두 번째 scale 1개(설명용 계산). FP32 scale이면 4.5비트/가중치, scale도 양자화하면 4.127비트/가중치. 경계 블록 · 오프셋 같은 작은 부가 정보는 빠져서 실제 파일 크기가 아니다.
  - **BF16 → NF4는 약 1/4**이지만 양자화된 선형층의 가중치 저장만 그렇다. 활성값 · 임베딩 · 어댑터는 4비트가 아니다.
  - **저장 · 계산 · 안 압축된 층은 따로 읽는다** (셀 14의 `dtype_observation`, 교안 실제 출력):

    | 항목 | 값 | 뜻 |
    |---|---|---|
    | `packed_weight` | `torch.uint8` | ① 4비트 번호를 담은 상자 |
    | `linear_compute` | `torch.bfloat16` | ② 행렬 곱 정밀도 |
    | `embedding_before_prepare` | `torch.bfloat16` | ③ 로드 직후 |
    | `embedding_after_prepare` | `torch.float32` | ③ 학습 준비 뒤 2배로 커짐 |
    | `adapter` | `torch.float32` | 학습하는 A · B |

  - **양자화와 LoRA는 줄이는 곳이 다르다** (슬라이드 9장, BF16 기준 계산값):

    | 방법 | 모델 가중치 | 기울기 + AdamW 상태 | 줄인 것 |
    |---|---|---|---|
    | 3장 전체 SFT | 0.92 GiB | 2.76 GiB | - |
    | 4장 LoRA (q·v) | 0.92 GiB | 0.006 GiB | 학습 대상 → 기울기 · 상태 |
    | 5장 QLoRA (q·v) | 0.68 GiB | 0.006 GiB | + 기반 가중치 저장 |

    - **양자화** = 가만히 있는 큰 가중치를 작게 저장, **LoRA** = 움직이는 파라미터를 적게. **QLoRA = 둘을 같이 쓴다.** 이 표는 계산값이고 실제 학습 최대 메모리는 5-3에서 실측으로 본다.
- **QA 체크포인트**:
  - **줄이는 곳을 구분해서 읽기** — "메모리가 줄었다"를 가중치 저장이 줄었다는 것과 학습 중 메모리가 줄었다는 것으로 나눠 본다.
  - **근사 예제는 "원리 예제"라고 표시** — 노트북이 "NF4 구현이나 실제 Qwen 가중치가 아니다"라고 밝히는 것처럼, 단순화한 예제와 실제 값을 섞지 않는다.

### 5-2 : NF4 기반 모델에 LoRA 학습하기
- **핵심 개념**:
  - 흐름: 입력 보고서 확인 → `BitsAndBytesConfig` → `prepare_model_for_kbit_training` → `get_peft_model` → 4장과 같은 24번 갱신.
  - **구조: 압축한 몸통 옆에 학습하는 옆길.** 고정된 Ŵ(NF4로 저장, BF16/FP32로 풀어서 계산) 옆에 A [r, 입력] · B [출력, r](둘 다 FP32)이 있고 × alpha/r = 16/8 = 2다. 양자화한 기반 가중치를 optimizer로 갱신하는 구조가 아니다. 이 수업에는 NF4와 이중 양자화가 있고, **paged optimizer는 논문에만** 있다.
  - **설정: 저장용 줄과 계산용 줄을 구분한다.**

    | 인자 | 정하는 것 |
    |---|---|
    | `load_in_4bit=True` | 지원하는 선형층을 4비트 층으로 로드 |
    | `bnb_4bit_quant_type="nf4"` | 저장: NF4 (FP4와 다른 형식) |
    | `bnb_4bit_use_double_quant=True` | 저장: scale 압축 |
    | `bnb_4bit_compute_dtype` | 계산: BF16/FP32 (4비트 저장과 구분) |
    | `bnb_4bit_quant_storage=torch.uint8` | 저장 상자: uint8 (8비트 양자화라는 뜻이 아님) |
    | `from_pretrained(dtype=…)` | 비양자화 층의 자료형 |
    | `device_map={"": 0}` | GPU 한 개에 배치 (자동 분산 · CPU offload를 섞지 않음) |

    - 값 하나만 바꿔도 근사된 기반 가중치가 달라지므로 **양자화 설정은 통째로 기록**한다.
  - **학습 준비 → LoRA 부착 순서**: 4비트 로드(451,325,952 bytes) → `prepare_model_for_kbit_training`(파라미터 고정 · 비양자화를 FP32로 · 재계산, `use_reentrant=False`) → `get_peft_model`(725,901,056 bytes). 준비 함수는 LayerNorm만 바꾸는 함수가 아니다. `use_gradient_checkpointing`은 활성값을 재계산하는 방식이고 가중치를 디스크에 저장하는 설정이 아니다.
  - **메모리 구성** (`get_memory_footprint`, 슬라이드 13장, MB = 1,000,000바이트):

    | 구성 | 파라미터 수 | 로드 직후 | 학습 준비 뒤 |
    |---|---|---|---|
    | NF4 선형층 번호 (scale 제외) | 357,826,560 | 178.9MB | 178.9MB |
    | 임베딩 (출력층과 공유) | 136,134,656 | 272.3MB | 544.5MB |
    | Norm · bias | 71,552 | 0.14MB | 0.29MB |
    | LoRA A · B | 540,672 | - | 2.16MB |
    | 합계 (실제 출력) | 494,573,440 | 451.3MB | 725.9MB |

    - "4비트 모델"인데 가장 큰 덩어리는 압축되지 않은 임베딩이다.
  - **학습 조건은 4장과 같다**: lr 2e-5 · 24갱신 · 배치 1 × 누적 4 · warmup 2 · `adamw_torch`(paged optimizer는 작은 비교에 추가하지 않음) · 자동 중간 저장 끔. 같은 학습률이라 조건 비교는 깔끔하지만 LoRA가 배우기엔 작은 값이다.
  - **학습 전 dev loss부터 다르다**: 4장(BF16 기반) 0.9207 vs 5장(NF4 기반) 1.0459. 학습 전 같은 질문의 원문도 다르다. 4장은 코드 펜스 + 규정 복사였는데 5장은 펜스 없음 · status 없음 · 인용 ID "政策01-v1"이다.
  - **원본 결과: 1.0459 → 0.9745, 아직 실패.** 학습 후 원문은 `answer`와 `citations`만 있고 status가 없으며, 인용 ID가 틀리고, 질문 금액 70,000원을 비교하지 않는다.
- **QA 체크포인트**:
  - **붙인 직후 세 가지를 코드로 확인한다** — 학습 대상 540,672개 · 학습 대상이 `lora_` 이름뿐 · 첫 기반 층이 `Linear4bit`. 4비트로 로드됐다는 걸 표시된 dtype이 아니라 층 종류로 확인한다.
  - **학습 뒤에는 고정한 4비트 포장 가중치가 그대로인지(`torch.equal`), B가 0이 아닌지** 확인한다(4장과 같은 습관).
  - **근사가 들어간 설정은 통째로 기록** — 양자화 값 하나를 조용히 바꾸면 비교가 무의미해진다.

### 5-3 : 품질, 메모리와 시간을 함께 비교하기
- **핵심 개념**:
  - 흐름: 같은 장치 · 패키지 확인 → 손실 · 메모리 · 시간 → 원문 형식 검사 → 같은 문항 읽기.
  - **측정 도구**: `torch.cuda.synchronize()`로 GPU의 비동기 계산이 끝난 시점을 기준으로 시간을 재고, `reset_peak_memory_stats()`로 최고값의 시작점을 정한 뒤 `max_memory_allocated()`로 텐서 할당의 최고 바이트를 읽는다. 이 값은 **`trainer.train()` 구간의 PyTorch 텐서 최고치**이고 nvidia-smi의 총량이나 예약 메모리와 다르다. 로드 · 최초 dev 평가 · 학습 후 생성 · 저장 · 복원은 제외된다. `same_runtime`이 False면(장치나 패키지가 다르면) 메모리와 시간의 직접 비율을 내지 않는다.
  - **0.5B에서는 메모리 이득이 안 보인다** (교안):

    | | dev loss | 학습 최대 | 학습 시간 |
    |---|---|---|---|
    | 4장 LoRA | 0.8717 | 1.615 GiB | 18.5초 |
    | 5장 QLoRA | 0.9745 | 1.637 GiB | 25.3초 |

    - **QLoRA는 "항상 더 싸고 같은 품질"이 아니다.** 가중치 크기만 계산하면 0.92 → 0.68 GiB로 줄지만, 실제 학습 최대 메모리는 비슷했다(앞의 메모리 구성표가 이유: 임베딩, 학습 준비 뒤 FP32). 시간이 더 걸린 이유는 슬라이드에 없다. 4비트를 풀어서 계산하는 비용 때문일 수 있다는 건 일반적으로 알려진 설명일 뿐 이 자료로 확인한 건 아니다.
  - **형식 0/12, 실패한 이유는 달라요** (원본 QLoRA dev 12개의 첫 실패 이유):

    | 첫 실패 이유 | 개수 | 문항 |
    |---|---|---|
    | status 필드 없음 | 5 | policy01 초과 · policy05 이하/경계/초과/변경 |
    | abstained인데 인용이 있음 | 3 | policy01 이하/경계/변경 |
    | answer가 빈 문자열 | 2 | 두 팀의 근거 없음 문항 |
    | 인용 ID가 제공 문서에 없음 | 1 | policy01 무관 근거 |
    | JSON 객체 여러 개를 이어 붙임 | 1 | policy05 무관 근거 |

    - 통과 조건(1일차와 같은 검사): JSON 객체 · 키 3개 · status 값 · 비어 있지 않은 answer · answered면 인용 필수 / abstained면 인용 없음 · 인용 ID는 제공 문서 안. 코드 펜스를 지워서 통과시키지 않는다.
- **QA 체크포인트**:
  - **개선을 한 가지 숫자로 말하지 않는다** — 손실 · 메모리 · 시간은 각각 따로 읽고, 한 값의 개선이 다른 값의 개선을 뜻하지 않는다.
  - **실패를 이유별로 센다** — 같은 0/12라도 "status를 빠뜨린다" · "비어 있는 답을 낸다" · "인용을 지어낸다"는 서로 다른 결함이다. 게임 QA로 보면 **결함을 유형별로 분류해 원인을 좁히는 것**과 같다.
  - **측정 구간과 범위를 같이 적는다** — "최대 메모리 1.64 GiB"는 학습 호출 구간의 텐서 할당 최고치이지 장비가 쓴 총량이 아니다. 측정 환경(RTX 5060 Laptop · BF16 · seed 42 · dev 12 · 1회)도 함께 적는다.

### 5-4 : 새 세션에서 모델 복원하기
- **핵심 개념**:
  - 흐름: 보고서 · 어댑터를 ZIP으로 보관 → 같은 revision을 NF4로 다시 로드 → 같은 학습 준비 → 어댑터 부착 → logits · 원문 비교.
  - **ZIP에는 어댑터와 "조리법"만 들어간다**: `qlora_report.json`(설정 · 원문 · 기준 logits), `adapter_config.json`(기반 ID · revision · 층), `adapter_model.safetensors`(2.1MiB). 보고서의 `config`에 `compute_dtype · quant_type · double_quant · quant_storage · prepare_nonquantized_fp32`까지 남긴다. **ZIP에 없는 것**: 기반 모델 가중치 · optimizer · scheduler · 병합한 모델. 이 ZIP은 추론 복원 자료이고 학습 재개 체크포인트가 아니며, **양자화 모델 병합은 이 장에서 하지 않는다.**
  - **복원은 학습 때 만든 순서 그대로**: ① 같은 revision을 NF4로 로드(저장 당시의 `quant_type` · `double_quant` · 계산 dtype 적용) ② `prepare_model_for_kbit_training(use_gradient_checkpointing=False)`(추론에는 재계산이 필요 없음, FP32 상태 복원) ③ `PeftModel.from_pretrained(..., is_trainable=False)` ④ 저장한 한 문항의 마지막 위치 logits(어휘 151,936개 전부)와 생성 원문을 비교한다. 기준: `|저장 − 복원| ≤ atol + rtol × |복원|`, `atol = rtol = 1e-4`.
  - 복원은 **저장한 한 문항**으로 확인한다. 모든 입력에서의 동등성이나 업무 품질을 증명하는 검사는 아니다. 다른 장치와 정밀도에서는 작은 수치 차이가 생길 수 있어서 **실패한 검사를 지우지 말고 저장한 환경과 현재 환경부터 확인**한다. BF16으로 만든 결과는 native BF16 GPU에서 복원한다.
  - 교안 기록: 원본 QLoRA는 이 PC에서 **복원 검사에 실패**했고(슬라이드 22장, 구체 원인은 슬라이드에 없음), 설정 바꿔 보기 실습(lr 2e-4 · all-linear · `atol 1e-4` 그대로)은 BF16 실측에서 통과한다고 적혀 있다.
  - `qlora_result.zip`은 노트북을 실행하면 생성되는 결과 파일이고 다시 만들면 덮어쓰므로, 필요한 이전 결과는 PC에 따로 보관한다.
- **QA 체크포인트**:
  - **"같은 조리법"을 보고서에 남긴다** — 어댑터만 있으면 재현이 안 된다. 기반 모델 revision · 양자화 설정 · 계산 dtype · 학습 준비 방식까지 있어야 복원할 수 있다.
  - **실패한 검사를 지우거나 허용 오차를 올리지 않고 원인부터 본다** — 환경(GPU · 패키지 · 정밀도)을 먼저 대조한다. 4장의 "허용 오차를 풀 때는 다음 토큰 ID와 원문 일치도 같이 본다"와 같은 원칙이다.
  - **한 문항의 일치는 범위가 좁은 증거다** — 복원 검증은 "저장과 복원이 어긋나지 않았다"까지만 말한다.

## 정리 — 5장 결과물

| 강 | 한 줄 | 남긴 것 |
|---|---|---|
| 5-1 | 저장 형식과 계산 정밀도는 따로다 | NF4 16개 · 4.127비트 (계산) |
| 5-2 | 준비하고, 붙이고, A·B만 학습한다 | 540,672개 · 1.0459 → 0.9745 |
| 5-3 | 품질 · 메모리 · 시간을 따로 읽는다 | 형식 0/12 · 1.64 GiB · 25.3초 |
| 5-4 | 같은 조리법으로 복원하고 검사한다 | 교안 원본은 이 PC에서 검사 실패 |

- **6장이 읽는 것**: `qlora_result.zip`(어댑터 · 보고서)과 `qlora_report.json`은 7장 비교의 입력이다. 6장 DPO는 답의 선호를 학습한다.
- 6장 전에 할 것: `qlora_result.zip` 받아 두기 → 원본 · 변경 실행을 따로 보관 → 설정 바꿔 보기 실습(lr 2e-4 · all-linear · `atol 1e-4` 그대로).
- 직접 해 본 것: 슬라이드와 노트북 코드를 Claude와 같이 읽고, 올려 둔 `lora_report.json`을 5장 입력 검사와 대조했다. 5장 노트북 실행은 아직 안 했다(향후 계획).
