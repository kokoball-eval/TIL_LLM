## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | reference_answer | reference answer (기준 답안) | 사례 명세(spec)를 받아 **규칙으로** 모범답안을 만드는 함수. 모델이 쓴 답을 복사하지 않는다 |
  | case_type | case type (사례 유형) | 한 규정 그룹에서 만드는 여섯 상황: below · boundary · over_limit · updated · missing · irrelevant |
  | group_id | group identifier (그룹 식별자) | 같은 규정 계열(구판·개정판 포함)의 사례를 묶는 **분리용 메타데이터**. 모델 입력에는 안 넣는다 |
  | messages | messages (대화 메시지 목록) | system · user · assistant 세 역할로 된 대화. 모델이 실제로 읽는 부분 |
  | 토큰 / 토큰 ID | token / token ID | 토크나이저가 문장을 나눈 단위 / 그 단위의 번호. 길이 상한은 **글자가 아니라 토큰** 기준 |
  | prompt_ids / full_ids | prompt token IDs / full token IDs | 정답 **없는** 대화의 토큰 / 정답 **있는** 대화의 토큰. 둘의 차이가 답변 부분(answer_ids) |
  | add_generation_prompt | add generation prompt | assistant가 답변을 시작할 자리 표시를 붙일지. 입력만 만들 땐 True, 정답 포함 대화는 False |
  | EOS | End Of Sequence (시퀀스 종료) | 응답이 끝났다는 토큰 (Qwen은 `<\|im_end|>`). 잘려서 사라지면 안 끝나는 모델을 배운다 |
  | MAX_LENGTH | maximum length (최대 길이) | 입력 + 답변을 합친 **토큰 수** 상한. 이번엔 512 |
  | labels = −100 | labels ignore index (손실 제외 표시) | 그 위치는 **직접 손실에서 뺀다**는 뜻. 입력 문맥에서 지우는 값은 아님 (실제 구현은 3장) |
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 질문 하나에 모범답안 하나를 보여 주고 답변 토큰의 손실을 줄이는 학습 (3장) |
  | DPO | Direct Preference Optimization (직접 선호 최적화) | chosen vs rejected 상대 선호로 학습 (6장). 이 함수는 다음 토큰 정렬을 직접 한다 |
  | RAG | Retrieval-Augmented Generation (검색 증강 생성) | 문서를 검색해 입력 근거로 넣는 구성. 여기선 문서를 **직접 넣어** 생성 단계만 본다 |
  | train / dev / test | training / development / test set (학습 / 개발 / 시험 자료) | 가중치 갱신 / 점검·비교 / 최종 확인. **언제 보느냐**로 구분 |
  | 데이터 누수 | data leakage | 평가할 사례의 정보가 학습이나 후보 선택에 섞여 점수가 부풀어지는 문제 |
  | JSONL | JSON Lines | 한 줄에 JSON 레코드 하나를 저장하는 형식 |
  | seed | random seed (난수 시드) | 섞는 순서를 재현하기 위한 기준값. 이번엔 42 |
  | SHA-256 | Secure Hash Algorithm 256-bit (보안 해시) | 파일 내용의 지문. 한 글자만 달라도 값이 바뀐다 |
  | dataset_info.json | dataset info (데이터 카드) | 데이터의 출처 · 한계 · 모델 버전 · 분할 · 해시를 적어 두는 파일 (HF dataset card와 같은 역할) |
  | HF | Hugging Face | 모델·데이터 공유 플랫폼 |
  | 합성 자료 | synthetic data | 실제 규정이 아니라 **수업을 위해 만든** 자료. 일반화 성능을 보장하지 않는다 |

- **핵심 통찰: 파인튜닝 2장은 "모델을 학습시키는 장"이 아니라 "학습시켜도 되는 자료인지 검사하고 나눠 보관하는 장"이다**
  - 1장이 **학습 전 응답(baseline)** 을 남기는 장이었다면, 2장은 3~8장이 그대로 읽을 `training_data.zip`을 만든다. 슬라이드 정리 문장: "검사를 통과한 72개를 그룹째로 나눈 ZIP". 노트북은 CPU로 실행하고 **모델 가중치를 불러오지도 학습하지도 않는다**(토크나이저만 받는다).

    | 교안 | 오늘 한 것 | 남는 산출물 |
    |---|---|---|
    | 2-1 | 규정 그룹 12 × 사례 6 = 대화 72개. 모범답안을 **규칙 함수**로 생성 | 72개 (answered 48 · abstained 24) |
    | 2-2 | 두 번 토큰화해 **답변 시작 경계** 찾기, 길이 상한 확인 | 경계 299 · 전체 257~380 ≤ 512 |
    | 2-3 | `validate_record` 다섯 단계 검사 + **일부러 틀린 복사본 2개**로 검사 함수 시험 | 72/72 통과 · 오류 2/2 탐지 |
    | 2-4 | **행이 아니라 그룹**으로 8/2/2 분할 → 겹침 검사 → JSONL · ZIP · SHA-256 | 48/12/12 · `training_data.zip` |

- **두 번째 통찰: 학습 데이터도 테스트 대상이다 — 자료와 검사 함수를 **같이** 시험한다**
  - 2-3의 핵심은 "맞는 예는 통과, 틀린 예는 실패하는가"다. 인용 ID를 `없는-문서`로 바꾼 복사본, 같은 금액(85,000원 = 한도)을 "초과"로 바꾼 복사본을 일부러 만들어 검사 함수가 둘 다 거절하는지 확인한다(2/2). 검사 함수가 항상 통과만 시키는 함수가 아닌지 **검사 함수 자체를 테스트**하는 것이다.
  - 다만 이 자동 검사는 **교재가 정한 좁은 규칙(정형 문구 · 금액 · 인용 ID)** 만 본다. 노트북 문구 그대로, 자연어 전반의 정답 판정기가 아니다. 실제 규정으로 넓히면 원문 소유자와 사람이 조건 · 예외 · 단위를 검토해야 한다.

- **세 번째 통찰: 쪼개는 단위가 점수의 의미를 정한다 — 행이 아니라 그룹**
  - 행(row)을 섞어 자르면 test 12행이 모두 train에 **형제 사례**를 갖는다(슬라이드 가상 비교: 12/12행, 그중 5행은 질문까지 같음). 그룹을 섞으면 겹침이 0이다.
  - 그래도 문장 틀을 공유하는 합성 자료라서 비슷함은 남는다. 슬라이드 문장: 이 점수는 "**같은 틀의 새 그룹**"이지 실제 업무 일반화가 아니다.

- **향후 계획 및 다짐**
  - 올려 둔 `data_preparation.ipynb`는 **셀 출력이 비어 있는(아직 실행 전) 상태**였다. 그래서 이 TIL의 숫자(299 · 376 · 77 · 257~380 · 72/72 · 2/2 · 해시 앞자리)는 **수업 슬라이드에 적힌 실행 결과** 기준이다. 노트북을 직접 돌려서 슬라이드 값과 대조해 보기.
  - 3장 전에 할 것(슬라이드 마지막 장): `training_data.zip` 내려받기 → 3~8장 노트북에 그대로 업로드 → `dataset_info.json` 읽어 보기 → 분할 seed · 그룹 · 파일 해시 확인.
  - 오픈소스 프로젝트(LLM 트리아지 평가)에 가져갈 것: 평가 문항을 만들 때 **같은 원인에서 나온 사례를 한 그룹으로 묶고, 그룹 단위로 dev/test를 나누기**, 검사 함수에는 **일부러 틀린 예**를 넣어 시험하기, 데이터에도 **버전 + 해시** 남기기.

## 📊 어제보다 나아진 점

- 어제(1장)는 "학습 전에 무엇이 틀리는지 남기는 장"이라 **응답을 읽는 쪽**이었는데, 오늘은 **학습 자료를 만드는 쪽**으로 시점이 바뀌었다. 같은 `SYSTEM_PROMPT`(1장 explicit 지시와 글자까지 같은 문자열)를 쓰는 것, 입력과 정답 기준을 나누는 것 등 1장 내용이 그대로 이어졌다.
- 슬라이드 21장과 노트북을 Claude와 함께 읽으면서, 검사마다 "**이 검사는 무엇을 보고, 무엇은 못 보나**"를 한 줄씩 적었다(🧭 2). 어제 쓴 방식을 그대로 이어서 했다.
- Claude가 **1장 baseline 4문항(다온팀 85,000원 계열)이 이번 분할에서 train 그룹(policy03)에 들어간다**는 점을 짚어 줬다(🧭 4-①). 3장 학습 전후 비교를 1장 4문항으로 하면 안 되는 이유다. ★
- Claude가 `check_split_overlap`의 입력 중복 검사가 **사실상 실패할 수 없는 구조**라는 점을 코드에서 짚어 줬다(🧭 4-②, Claude의 코드 읽기이며 직접 실행해 확인하지는 않음).
- 아직 코드를 직접 짜지는 못하지만, `reference_answer` · `validate_record` · 그룹 분할 코드를 한 줄씩 읽고 "어디서 만들고, 어디서 걸러지고, 어디서 나뉘는지"는 설명할 수 있게 정리했다.

## 🧭 종합 QA 체크포인트

> 아래 교안별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 교안** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 학습 데이터에 대한 검사 네 가지 (슬라이드 13장 "실무")

| 검사 | 오늘 코드에서의 대응 | 못 보는 것 | 근거 교안 |
|---|---|---|---|
| 스키마 (schema) | 레코드 필드 · 역할 순서 · 응답 3필드 · status 값 · 문자열 타입 | 내용이 맞는지 | 2-3 |
| 중복 | `len({id}) == len(rows) == 72`, train/dev/test 사이 동일 입력 없음 | 표현만 다른 **비슷한** 사례 | 2-3 · 2-4 |
| 누수 | 그룹 단위 분할 + 그룹 겹침 0 검사 | 같은 문장 틀을 공유해서 생기는 유사성 | 2-4 |
| 라벨 규칙 | 초과 · 이하 · 같음 · 근거 부족별 필수/금지 문구 검사 | 교재가 정한 **정형 문구 밖**의 표현 | 2-3 |

- 게임 QA로 바꾸면: **테스트 데이터(계정 · 세이브 · 시나리오)가 맞는지 먼저 검증하고 쓰는 것**과 같다. 데이터가 틀리면 테스트 결과 전체를 믿을 수 없다.

### 2. 검사 하나가 보는 범위를 적는다 (`validate_record` 다섯 단계)

| 단계 | 무엇을 보나 | 못 보는 것 | 근거 교안 |
|---|---|---|---|
| ① 식별 정보 | 필드 4개(id · group_id · case_type · messages), 원래 사례 명세와 일치 | — | 2-3 |
| ② 대화 | 역할 순서 system → user → assistant, `SYSTEM_PROMPT`와 같은지, user 내용이 명세와 같은지 | assistant 내용의 의미 | 2-3 |
| ③ 응답 형식 | status · answer · citations 세 필드, status 값, answer가 빈 문자열 아님 | 값이 맞는지 | 2-3 |
| ④ 인용 | 인용 ID ⊆ 제공 문서 ID, 중복 없음 | **그 문서가 답을 뒷받침하는지** (노트북 주석: 의미가 맞다는 증거가 아님) | 2-3 |
| ⑤ 업무 규칙 | 근거 부족 → abstained + 빈 인용 + "확인할 수 없습니다" + "담당자" / 답변 가능 → 한도와 질문 금액 둘 다 보존 + 초과 · 이하 문구 | 정형 문구와 다른 올바른 문장 | 2-3 |

- 앞 단계가 실패하면 뒤 단계로 가지 않고 `assert`로 멈춘다(1장 `inspect_response`가 앞 실패 시 뒤를 안 보던 것과 같은 구조).
- 점수를 읽을 때는 **검사 이름과 분모를 같이** 본다. `72/72`는 "이 교재 규칙을 모두 통과"이지 "이 데이터가 실제 업무에 좋다"가 아니다.

### 3. 테스트 케이스(사례)는 "틀리기 쉬운 경우"를 일부러 한 세트로 만든다

| case_type | 질문 금액 (policy03 · 한도 85,000) | 넣는 문서 | 모범답안 | 확인하려는 것 |
|---|---|---|---|---|
| below | 80,000원 | v1 | answered · 승인 불필요 | 한도 **바로 아래** |
| boundary | 85,000원 (= 한도) | v1 | answered · 승인 불필요 | **경계값** — 같은 금액 |
| over_limit | 90,000원 | v1 | answered · 예약 전 서면 승인 | 한도 **바로 위** |
| updated | 90,000원 (질문 같음) | v2 (95,000) | answered · 승인 불필요 | **개정** — 질문 같고 문서만 다름 |
| missing | 통신비 질문 | 없음 | abstained · 확인 불가 + 담당자 | **근거 없음** |
| irrelevant | 통신비 질문 (질문 같음) | v1 숙박 규정 | abstained · 숙박 규정으로 판단 금지 | **엉뚱한 문서**가 있어도 지어내지 않기 |

- over_limit과 updated, missing과 irrelevant는 **질문 문장이 같고 문서만 다른 쌍**이다(슬라이드 빨간 테두리). 문서를 읽어야만 맞힐 수 있는 쌍이다.
- 게임 QA의 **경계값 분석 · 동등 분할**과 같다. 한도 아래 · 같음 · 위 + 패치로 규칙이 바뀐 경우 + 데이터가 없는 경우 + 엉뚱한 데이터가 있는 경우까지 그룹마다 똑같이 6종을 만든다.
- 한 그룹의 6종이 **함께 움직이므로** train · dev · test 세 집합 모두 여섯 유형이 같은 비율로 들어간다(슬라이드 17장).

### 4. Claude가 짚어준 확인 포인트

**① 1장 baseline 4문항은 이번 분할에서 train 그룹 — 학습 전후 비교에 쓰면 안 된다**
- 노트북 주석: "1장의 85,000원 규정을 포함한 가상 계열에서 초과와 개정을 나란히 읽습니다"(policy03). 1장 문항(경계 85,000원 · 개정 95,000원 · 근거 없음)과 금액이 같으므로 **1장 4문항 ≈ policy03 계열**이다. 그런데 슬라이드 17장 분할에서 policy03은 **train 8그룹 안**에 들어 있다.
- 그래서 3장에서 SFT 전후를 비교할 때는 1장 4문항이 아니라 **dev 12문항**(공통 dev 문항 `policy01-over_limit`)을 쓴다. 학습에 쓴 문제로 "좋아졌다"고 말하면 안 되기 때문. (1장 4문항과 policy03이 정확히 같은 문장인지는 노트북 실행 후 확인 필요 — 금액 · 팀명 일치와 주석에 근거한 Claude의 연결.)

**② `check_split_overlap`의 "같은 입력 없음" 검사는 이 자료에서는 실패할 수 없다 (Claude의 코드 읽기, 직접 실행 안 함)**
- 겹침 검사는 user 메시지 전체(질문 + 문서)가 집합 사이에서 겹치는지 본다. 그런데 질문과 문서 문장에 **팀 이름**(`가온팀` · `나래팀` …)이 들어가고 팀은 그룹마다 다르다. 그래서 다른 그룹의 입력이 같을 수가 없다.
- 즉 이 자료에서 누수를 실제로 막는 것은 **그룹 겹침 검사(`isdisjoint`)와 그룹 단위로 나눴다는 사실**이고, 입력 중복 검사는 안전망 역할 정도다. 2-3에서 배운 "검사 함수도 시험한다"를 `check_split_overlap`에는 적용하지 않았다는 점이 눈에 띈다. (이 검사가 같은 그룹을 두 집합에 넣었을 때 실제로 실패하는지 직접 확인해 보면 좋다. 확인 필요.)

**③ `labels = −100`은 "입력에서 지우는 것"이 아니라 "직접 손실에서 빼는 것"**
- 노트북 표: 해당 위치의 직접 손실만 제외한다. **프롬프트를 입력 문맥에서 제거하는 값은 아니다.** 프롬프트 토큰도 모델이 읽는 문맥으로는 그대로 쓰인다. 2장은 경계(299)만 확인하고, 실제 마스킹 구현은 3장 `encode_example`.
- 정렬 이야기도 있다: Causal LM의 기본 학습 손실은 다음 토큰 정렬(shift)을 **내부에서** 처리한다. 반면 로짓을 받아 직접 계산하는 DPO 함수는 정렬을 **직접** 해야 한다. 한 곳에서 **두 번 밀면** 정답이 한 칸 어긋난다(노트북: "두 곳에 중복 적용하지 않습니다").

**④ ZIP 파일의 SHA-256은 재실행 때 달라질 수 있다 (Claude 설명, 직접 확인 안 함)**
- 노트북 코드는 `file_hashes`에 **jsonl 세 개만** 해시한다(ZIP은 해시하지 않음). 슬라이드 19장 표에는 ZIP(`018a6120…`)도 있다. `zipfile`은 안에 넣는 파일의 **수정 시각**을 함께 저장하는 것으로 알고 있어서, 내용이 같아도 다시 만들면 ZIP 바이트가 달라질 수 있다. 그래서 재현 확인은 **jsonl 파일별 해시**로 하는 쪽이 안전해 보인다. 확인 필요.

**⑤ 문자 길이로 경계를 잡으면 토큰 경계와 어긋난다**
- 슬라이드 9장 함정 표 4번째 행: 문자 길이로 경계를 자르면 틀린다. 경계는 **토큰 ID 리스트 길이**(`len(prompt_ids)`)로만 계산하고, 그 전에 `full_ids[:len(prompt_ids)] == prompt_ids`를 `assert`로 확인한다. 이 가정이 깨지면(템플릿 차이) 정답 앞에 다른 토큰이 붙은 것이므로 **학습이 엉뚱한 토큰을 배운다**.

## 2장. 학습 데이터 구성과 품질 검증

### 2-1 : 모범답안 — 근거를 모범답안으로 바꾸기
- **핵심 개념**:
  - 흐름: 규정 그룹(팀) 12개 → 그룹마다 여섯 사례 → `reference_answer`로 규칙에 따라 모범답안 생성 → 72개.
  - **72 = 규정 그룹 12 × 사례 6**, 상태는 answered 48 · abstained 24(missing · irrelevant 두 유형이 abstained).
  - 그룹은 팀(가온 · 나래 · 다온 …) + 한도(65,000 ~ 120,000) + 개정 한도(+10,000)로 만든다. 코드: `for group in groups: for kind in 여섯 가지: case_specs.append(...)`.
  - **구판과 개정판은 같은 `group_id`** 를 쓴다(`policy03-v1` · `policy03-v2`, 문서 ID에 버전 포함). 그래야 나중에 서로 다른 집합으로 흩어지지 않는다.
  - **모범답안은 규칙이 만든다.** `reference_answer(spec)`:
    - missing · irrelevant → `status=abstained`, "제공된 근거로는 … 확인할 수 없습니다. 담당자에게 확인하세요.", `citations=[]`
    - 금액 > 한도 → "… 한도를 초과하므로 예약 전 서면 승인을 받아야 합니다."
    - 아니면 → "한도와 같으므로 / 한도 이하이므로 … 사전 승인이 필요하지 않습니다." + 인용 `[문서 ID]`
    - 코드 주석: **모델이 생성한 답을 정답으로 복사하지 않는다.**
  - **같은 질문 + 다른 문서**: policy03-over_limit(v1: 한도 85,000 → 90,000원은 초과 → 서면 승인) vs policy03-updated(v2: 한도 95,000 → 같은 90,000원이 이하 → 승인 불필요). 문서를 읽어야 답이 갈린다.
  - **실무 메모(슬라이드)**: 실제 업무 정답은 규칙 함수로 다 만들 수 없다 → **라벨링 가이드 + 사람 검수**. LLM으로 초안을 만들면 금액 · 조건이 바뀌지 않았는지 **코드로 걸러야** 한다.
  - 표현 문장은 정형 문구(템플릿)라서 사례가 **문장 틀을 공유**한다. 이게 2-4의 "같은 틀의 새 그룹" 한계로 이어진다.
- **QA 체크포인트**:
  - **"틀리기 쉬운 경우"를 데이터를 모으기 전에 설계** — 아래 · 같음 · 위 · 개정 · 없음 · 엉뚱한 문서 (🧭 3).
  - **정답을 만드는 규칙(테스트 오라클)을 코드로 두면** 사람이 72개를 눈으로 맞추지 않아도 된다. 대신 **규칙이 틀리면 72개가 한꺼번에 틀린다** → 2-3에서 규칙과 검사를 따로 시험.
  - **금액 · 조건을 코드로 보존 확인** — LLM 초안은 숫자를 슬쩍 바꿀 수 있다.

### 2-2 : 대화 · 토큰 — 대화 형식과 정답 토큰 구성하기
- **핵심 개념**:
  - 흐름: 레코드 = 메타데이터 + messages → 정답 없는 대화 / 정답 있는 대화를 각각 토큰화 → **접두부 일치 확인** → 답변 경계 → 길이 상한 검사.
  - **레코드 한 줄**: 바깥(`id` · `group_id` · `case_type`)은 **분리 · 분석용 → 모델에 안 넣는다**(정답을 암시하므로). 안쪽 `messages`만 모델이 본다.

    | 역할 | 내용 |
    |---|---|
    | system | `SYSTEM_PROMPT` (1장 explicit과 같은 문자열) |
    | user | `{"question": …, "documents": […]}` JSON 문자열 |
    | assistant | 모범답안 JSON ← **학습 때만** |

  - **언제 어떤 messages를 쓰나**:

    | 언제 | 넣는 messages | 이유 |
    |---|---|---|
    | 학습 (3~6장) | system + user + assistant | assistant(모범답안) 토큰에서 손실 계산 |
    | 생성 · 평가 (1 · 3 · 7장) | system + user | 정답을 넣으면 평가가 무의미 |

  - **두 번 토큰화해서 "답변이 시작되는 위치"를 찾는다** (슬라이드 8장 예시):

    | 인자 | `prompt_ids` (생성 입력) | `full_ids` (학습 대화) |
    |---|---|---|
    | messages | `[:2]` system, user | 전체 3개 (+ assistant) |
    | `add_generation_prompt` | True (assistant 시작 표시) | False (정답이 이미 있음) |
    | `tokenize` · `return_dict` | True · False (ID 리스트) | True · False |

    - 숫자: `prompt_ids` **299** · `full_ids` **376** → `answer_ids` **77개**(답변 + 종료 토큰). `full_ids[:299] == prompt_ids`를 `assert`로 확인한 뒤 `full_ids[299:]`를 답변으로 본다.
  - **템플릿 함정 4가지** (슬라이드 9장):

    | 함정 | 증상 | 막는 법 |
    |---|---|---|
    | system 누락 | 기본 system이 **몰래** 들어가 학습 · 추론 입력이 달라짐 (예: `You are Qwen, created by Alibaba Cloud…`) | system을 항상 명시 |
    | 템플릿 차이 | 정답 앞에 다른 토큰이 붙어 경계가 밀림 | `full_ids[:len(prompt_ids)] == prompt_ids` assert |
    | 문자 길이로 경계 | 토큰 경계와 어긋남 | 토큰 ID 리스트 길이로만 계산 |
    | 모델 교체 | Llama · Gemma는 다른 제어 토큰 | 토크나이저의 템플릿을 그대로 사용 |

  - **`MAX_LENGTH = 512`는 글자가 아니라 토큰 수.** 사례별 대화 길이: 프롬프트 205~302 + 모범답안·종료 52~79 = **합계 257~380**, 상한 512 **초과 0개**. 초과하면 **조용히 자르지 않고 `assert`로 중단**해서 원문을 확인하게 한다.
  - **자르면 생기는 일** (슬라이드 10장): 오른쪽을 자르면 **종료 토큰 소실**(안 끝나는 모델을 배움), 왼쪽을 자르면 **근거 문서 소실**. 긴 문서는 학습 데이터에서 자르지 말고 **RAG 단계에서 필요한 부분만 넣도록** 줄인다.
  - **용어(노트북)**: 채팅 템플릿은 역할을 모델이 배운 제어 토큰과 순서로 바꾸는 규칙. EOS는 응답 종료 토큰. 패딩은 길이가 다른 입력을 한 배치에 넣으려고 덧붙이는 자리(`collate` · `pad_sequence`: 입력은 pad ID, attention은 0, labels는 −100으로 패딩). 이 부분은 3장 구현.
- **QA 체크포인트**:
  - **경계 확인은 `assert`로 자동화** — 템플릿이나 revision이 바뀌어도 접두부가 안 맞으면 즉시 멈춘다. 눈으로 확인하지 않는다.
  - **자르기 전에 먼저 길이를 잰다** — 조용히 자르면 근거 문서나 JSON 끝을 잃었는지 알 수 없다. (게임 QA의 **"에러를 삼키지 않고 로그로 남기는 것"** 과 같은 원칙.)
  - **group_id · case_type을 모델 입력에 넣지 않는다** — 넣으면 정답 힌트가 되어 모델이 문서를 안 읽고도 맞힌다(정답 누수).

### 2-3 : 품질 검사 — 조건과 근거 부족 사례의 품질 확인하기
- **핵심 개념**:
  - 흐름: 식별 정보 → 대화 → 응답 형식 → 인용 → 업무 규칙 → 일부러 틀린 복사본 두 개로 검사 함수 시험. 단계별 내용은 🧭 2 표 참고.
  - **업무 규칙 ⑤ 단계의 "있어야 하는 것 / 있으면 안 되는 것"**:

    | 사례 | 있어야 하는 것 | 있으면 안 되는 것 |
    |---|---|---|
    | 근거 부족 | abstained · 빈 인용 · "확인할 수 없습니다" · "담당자" | — |
    | 답변 가능 | 1박 한도와 질문 금액 **둘 다** | — |
    | 초과 | "초과" · "예약 전 서면 승인을 받아야" | "사전 승인이 필요하지" |
    | 이하 · 같음 | "사전 승인이 필요하지 않습니다" | "예약 전 서면 승인을 받아야" |

  - 형식과 의미는 별개다: 코드 안 주석 — 인용 ID는 인용 **허용 범위**일 뿐 답변 의미가 맞다는 증거가 아니고, 업무 규칙은 이 교재의 **정형 문구만** 확인한다(shortcut). 다른 문장과 실제 규정에는 별도 의미 검토가 필요.
  - **검사 함수도 시험한다 — 일부러 틀린 복사본 두 개** (`copy.deepcopy`로 원본은 건드리지 않음):

    | 복사본 | 일부러 넣은 오류 | 어느 단계에서 거절되나 |
    |---|---|---|
    | `bad_citation` | 인용 ID를 `없는-문서`로 | ④ 인용 |
    | `bad_boundary` | boundary(85,000 = 한도)를 "초과 → 서면 승인"으로 | ⑤ 업무 규칙 |

    - 결과: `rejected == 2` → "의도한 오류 탐지: 2 / 2", 원본 72개 유지.
  - **검사 함수의 테스트 = 맞는 예는 통과하고, 틀린 예는 실패하는가** (슬라이드 14장).
  - **실무(슬라이드 13장): 학습 데이터 검사 네 가지 — 스키마 · 중복 · 누수 · 라벨 규칙** (🧭 1).
- **QA 체크포인트**:
  - **일부러 틀린 예를 넣어 검사를 시험** — 게임 QA의 **결함 주입(fault injection)** 과 같다. "버그를 심어 놓고 테스트가 잡는지" 보는 방식이다. 통과만 하는 검사는 검사가 아니다.
  - **오류가 하나씩 다른 단계에서 걸리는지** 확인(인용 오류는 ④, 경계 오류는 ⑤) — 오류 종류마다 담당 단계가 있어야 원인을 좁힐 수 있다.
  - **경계 사례(boundary)를 "초과"로 바꾼 오류**를 일부러 넣은 것이 포인트: 가장 틀리기 쉬운 **같음(=)** 사례를 검사가 구분하는지 본다.

### 2-4 : 그룹 분할 — 그룹 단위로 학습과 평가 자료 나누기
- **핵심 개념**:
  - 흐름: 행을 섞으면 생기는 누수 → 규정 그룹을 섞어 **8 / 2 / 2** → 겹침 검사 → train · dev · test의 역할 → JSONL · dataset_info · ZIP · SHA-256.
  - **행을 섞어 자르면**: test 12행이 모두 train에 **형제 사례**를 갖는다(슬라이드의 가상 비교, 5행은 질문까지 같음). 그룹을 섞으면 겹침 0.
  - **분할 코드 순서**: 그룹 목록을 **정렬** → `random.Random(SEED).shuffle` → 앞 8 / 다음 2 / 나머지 2.

    | 집합 | 행 | 그룹 (슬라이드 17장) |
    |---|---|---|
    | train | 48 (8그룹) | policy 03 04 06 07 08 09 10 12 |
    | dev | 12 (2그룹) | policy 01 05 |
    | test | 12 (2그룹) | policy 02 11 |

    - **정렬을 먼저 하는 이유**(코드 주석): 섞기 전 그룹 순서를 고정해야 같은 seed에서 같은 분할을 얻는다. 집합(`set`)은 순서가 없으므로 정렬해서 리스트로.
    - 뒤 장 공통 dev 문항: `policy01-over_limit`.
  - **`check_split_overlap`이 확인하는 것**: ① 그룹이 두 집합에 동시에 들어가지 않음(`isdisjoint`) ② 같은 사용자 입력이 두 집합에 중복되지 않음 ③ 그룹의 합집합 = 전체 12그룹 ④ 행 수 48/12/12. (🧭 4-②: ②는 이 자료에서는 사실상 실패할 수 없는 구조라는 Claude의 해석.)
  - **train · dev · test는 "언제 보느냐"로 구분한다** (슬라이드 18장):

    | | 행 · 그룹 | 용도 | 쓰는 곳 | 주의 |
    |---|---|---|---|---|
    | train | 48 · 8 | 가중치 갱신 | 3장 SFT · 4장 LoRA · 5장 QLoRA · 6장 DPO | 여기 점수가 좋은 건 **당연** |
    | dev | 12 · 2 | 점검 · 비교 | 3~6장 dev loss, 7장 후보 비교 | **여러 번 봐서 부풀어짐** |
    | test | 12 · 2 | 최종 확인 | 후보 · 설정을 **고정한 뒤 마지막에 한 번** | **보고 고치면 dev가 됨** |

  - **그룹으로 나눠도 남는 한계**: 문장 틀이 같아 비슷함은 남는다. 이 점수는 "같은 틀의 새 그룹"이지 실제 업무 일반화가 아니다(`dataset_info`의 `limitations`에도 같은 문장).
  - **보관 (JSONL · dataset_info · ZIP · SHA-256)**:

    | 파일 | 내용 | SHA-256 앞자리 (슬라이드) |
    |---|---|---|
    | `train.jsonl` | 48줄 | `d9154d79…` |
    | `dev.jsonl` | 12줄 | `e48906f0…` |
    | `test.jsonl` | 12줄 | `2bca42ac…` |
    | `dataset_info.json` | 데이터 카드 | — |
    | `training_data.zip` | 위 넷 | `018a6120…` |

    | dataset_info 필드 | 왜 남기나 |
    |---|---|
    | `synthetic` · `limitations` | 무엇이고 한계는 |
    | `model_id` · `revision` · `system_prompt` | 같은 템플릿 · 지시 |
    | `split_seed` · `split_groups` | 분할 재현 |
    | `max_length` · `max_observed_tokens` | 512 · 380 |
    | `file_sha256` | 무결성 |

  - **저장 직후 ZIP을 다시 읽어 확인**: `zipfile.ZipFile`로 열어 `train/dev/test.jsonl`을 `json.loads`로 되살린 뒤 `restored == splits[name]`을 `assert` → **인코딩 · 행 수까지** 저장 전과 같은지.
  - **실무(슬라이드)**: 데이터에도 버전이 있다. 실험 기록에 **모델 버전과 데이터 해시를 함께** 남긴다(HF dataset card와 같은 역할).
- **QA 체크포인트**:
  - **쪼개는 단위 = 독립성의 단위** — 같은 원인(규정)에서 나온 사례는 한 덩어리로 움직여야 평가가 독립이다. 게임 QA로 보면 **같은 원인 버그의 재현 케이스를 train/test로 갈라 놓지 않는 것**과 같다.
  - **test는 마지막에 한 번만** — 보고 고치면 dev다. 릴리스 후보를 고정한 뒤 한 번 돌리는 **최종 회귀(블라인드 검증)** 와 같은 규율.
  - **저장하고 다시 읽어서 같은지** 확인 — 파일을 썼다는 것과 읽었을 때 같다는 것은 다른 주장이다.
  - **분할 재현 정보(seed · 그룹 목록) + 해시를 같이 남긴다** — 나중에 점수가 달라졌을 때 "자료가 바뀐 건지"부터 확인하기 위해.

## 정리 — 2장 결과물

| 강 | 한 줄 | 남긴 것 |
|---|---|---|
| 2-1 | 모범답안은 규칙 함수가 만든다 | 72개 = 12그룹 × 6사례 |
| 2-2 | 두 번 토큰화해 답변 경계를 찾고 길이를 확인한다 | 경계 299 · 257~380 ≤ 512 |
| 2-3 | 자료와 검사 함수를 함께 시험한다 | 72/72 통과 · 오류 2/2 탐지 |
| 2-4 | 행이 아니라 그룹으로 나누고 지문을 남긴다 | 48/12/12 · `training_data.zip` |

- **3~8장이 그대로 읽는 것**: `training_data.zip`. 3장에서 `encode_example`(labels −100 마스킹)을 구현하고 SFT로 학습한 뒤 **같은 dev 12문항**으로 학습 전후를 비교한다.
- 3장 전에 할 것: ZIP 내려받기 → 3~8장 노트북에 업로드 → `dataset_info.json` 읽어 보기 → seed · 그룹 · 해시 확인.
- 직접 해 본 것: 슬라이드와 노트북 코드를 Claude와 같이 읽고, 검사별 "보는 것 / 못 보는 것"과 분할의 누수 구조를 표로 정리했다. 노트북 실행은 아직 안 했다(🎯 0, 향후 계획).
