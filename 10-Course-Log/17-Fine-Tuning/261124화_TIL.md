## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | DPO | Direct Preference Optimization (직접 선호 최적화) | 같은 질문의 **두 답을 비교**해서 더 나은 쪽을 선호하도록 배우는 학습 목표 |
  | SFT | Supervised Fine-Tuning (지도 미세조정) | 정답(모범답안) 하나를 따라 쓰게 하는 학습 목표 (3장) |
  | chosen / rejected | chosen (초즌, 고른 답) / rejected (리젝티드, 버린 답) | 선호쌍의 좋은 답 / 나쁜 답. 이번 rejected는 **판단 하나만 일부러 틀리게** 만든 교재용 답 |
  | 선호쌍 | preference pair | 같은 입력 + chosen + rejected + 선호 이유 한 세트 (48쌍) |
  | policy / reference | policy (정책, 학습하는 모델) / reference (기준 모델) | reference는 **학습 전의 SFT를 고정**한 것. 점수를 미리 계산해 숫자로 보관 |
  | logp | log-probability (로그확률) 합 | 응답 토큰(+EOS)의 로그확률을 **더한** 값. 그 응답에 매긴 점수 |
  | reward | (implicit) reward (암묵적 보상) | `beta × (policy logp − reference logp)`. 사람이 준 업무 점수가 아님 |
  | margin | margin (차이 폭) | chosen reward − rejected reward. 클수록 loss가 작아짐 |
  | logsigmoid | log-sigmoid (로그 시그모이드) | `loss = −logsigmoid(margin)`을 수치적으로 안정되게 계산하는 함수 |
  | beta | beta (선호 강도 배율) | 손실 식 안의 **채점 기준 눈금**. 학습률이 아님 (0.1) |
  | 학습률 | learning rate | optimizer 안의 **보폭** (2e-5, 비교용 2e-6) |
  | 과잉 보류 | over-abstention | 근거가 충분한데도 답하지 않고 보류하는 실패 |
  | 근거 없는 단정 | unsupported answer | 근거가 없는데 “지원되지 않는다”처럼 단정하는 실패 |
  | 과최적화 | over-optimization | 점수(loss · margin)는 좋아지는데 좋은 답의 확률까지 떨어지는 현상 |
  | PPO | Proximal Policy Optimization (근위 정책 최적화) | 보상 모델을 따로 두고 생성 · 보상 수집을 반복하는 방식. DPO는 이걸 하지 않음 |
  | W&B | Weights & Biases (실험 기록 도구) | 학습 곡선을 기록하고 실행끼리 겹쳐 보는 도구 (교안 밖 보강) |

- **핵심 통찰: SFT는 "정답을", DPO는 "비교를" 배운다 — 학습 대상은 같고 목표만 바뀐다**

  | | 3장 SFT | 6장 DPO |
  |---|---|---|
  | 데이터 한 건 | 질문 + 모범답안 | 질문 + 좋은 답 + 나쁜 답 |
  | 손실 | 답변 토큰 교차엔트로피(평균) | 두 답의 점수 차이가 기준보다 벌어졌나 |
  | 기준 모델 | 없음 | 학습 전 SFT를 고정 (reference) |
  | 시작점 | 공개 Qwen2.5-0.5B | 3장 SFT 결과 |
  | 학습 대상 | 전체 494,032,768개 | 전체 494,032,768개 (같음) |

  - SFT는 “이렇게 답해”라는 정답지 따라 쓰기이고, DPO는 “이쪽이 저쪽보다 나아”라는 두 답안 중 고르기다. 3~5장이 구조도의 아래 줄(방법)을 바꿨다면, 6장은 위 줄(목표)을 바꾼다.

- **두 번째 통찰: loss는 성공했는데 좋은 답은 무너졌다 — 점수 하나로 판정하지 않는다**
  - 교안 설정(lr 2e-5)에서 24번째 갱신의 loss는 **0.000041**, margin은 **11.54**로 “완벽한 학습”처럼 보인다. 학습한 48쌍 모두 margin이 양수(48/48)다.
  - 그런데 첫 쌍의 chosen 로그확률 합이 **−0.11 → −66.53**으로 떨어졌다. 71토큰 답에서 토큰당 확률로 바꾸면 약 99.8% → 약 39%다. dev 12문항의 형식 통과는 **12/12 → 2/12**, 근거 없는 answered는 **0/4 → 4/4**가 됐고 원문에는 “…받아 보실 수 없습니다.supports#query}”처럼 **말 자체가 무너진** 문장이 나왔다.
  - 학습률을 **2e-6**으로 낮추면 margin 0.59 · chosen reward +0.02 · 형식 12/12로, 좋은 답을 유지한 채 선호만 조금 움직였다(교안 밖 보강 비교).

- **세 번째 통찰: "과잉 보류 0/8"이 좋은 소식이 아닐 수 있다 — 0이 어디서 왔는지 본다**
  - 2e-5 실행의 과잉 보류는 0/8이지만, 형식이 깨져 **status를 읽지 못한 8개**가 만든 0이다. 집계 함수는 읽을 수 있는 status만 세므로, 판정 불가를 따로 세지 않으면 “문제 없음”으로 보인다.
  - 게임 QA로 바꾸면 **“크래시 0건” 리포트가 사실은 테스트가 실행조차 안 돼서 0건인 경우**와 같다.

- **네 번째 통찰: 저장 재현과 학습 재현은 다르다**
  - 저장한 모델을 다시 읽으면 logits 차이 0.0 · 원문 일치 True로 **저장은 정확**하다. 하지만 같은 PC에서 다시 학습하면 형식 통과가 2/12와 0/12로 달랐고(교안 기록은 1/12), 첫 쌍 chosen logp도 −66.53과 −75.78로 달랐다. “같은 파일이면 같은 답”과 “다시 배워도 같은 답”은 다른 주장이다.

- **향후 계획 및 다짐**
  - `dpo.ipynb`와 `dpo_wandb.ipynb`는 **셀 출력이 비어 있는(실행 전) 상태**다. 그래서 이 TIL의 숫자는 **슬라이드의 실행 결과**(RTX 5060 Laptop · BF16 · seed 42 · dev 12 · 1회, T4 · L4는 미실측)다.
  - 내 환경: 올려 둔 `sft_report_a1d2fa.json`은 **L4 · BF16**에서 만든 3장 결과이고 6장 입력 조건을 통과한다(🧭 4-①). 6장은 SFT의 정밀도를 그대로 쓰므로 **BF16을 지원하는 GPU(L4 등)**에서 돌리고, `sft_model.zip`은 **같은 3장 실행에서 만든 것**을 올려야 한다.
  - 7장 전에 할 것(슬라이드 마지막 장): `dpo_report.json`과 SFT 입력 파일 보관 → 7장 비교에 같은 파일 사용 → 설정 바꿔 보기(lr 2e-6, 런타임 재시작 · 빈 폴더 · 처음부터).
  - 오픈소스 프로젝트(LLM 트리아지 평가)에 가져갈 것: 지표 하나(loss · 정확도)가 좋아져도 **원문과 형식**을 같이 읽기, 집계에서 **판정 불가(파싱 실패)**를 별도 칸으로 세기, 실험 곡선을 **실행끼리 겹쳐서** 비교하기.

### 3. 선호쌍 설계 = 테스트 케이스 설계

- **판단 하나만 다르게** 만든다. 형식은 둘 다 맞고 다른 건 판단 하나라서, 모델이 무엇을 배웠는지 좁힐 수 있다. 게임 QA의 **변수 하나만 바꾼 재현 케이스**와 같다.
- **양쪽 실수를 다 넣는다.** 과잉 보류(below)와 근거 없는 단정(missing)을 모두 rejected에 넣었다. 슬라이드 문장: 한쪽만 벌하면 반대쪽으로 치우칠 수 있다. 버그 수정이 반대쪽 회귀를 만들지 않는지 함께 보는 것과 같다.
- **선호 이유를 같이 기록**한다(`reason`). 라벨이 틀리면 그 잘못된 선호도 그대로 학습한다(노트북 문구).

### 4. Claude가 짚어준 확인 포인트

**① 올려 둔 `sft_report_a1d2fa.json`은 6장 입력 조건을 통과하고, 4·5장 비교와 같은 3장 실행이다 (Claude가 파일을 열어서 확인)**
- 필수 항목 6개가 모두 있고 `data_sha256`이 2장 ZIP의 지문(`018a6120…`)과 같다. `weight_dtype`이 `torch.bfloat16`이고 GPU는 NVIDIA L4라서, 6장도 **BF16을 지원하는 GPU**에서 돌려야 한다.
- dev 12문항 원문이 5장 때 올린 `lora_report.json` 안의 `comparison.full_sft`와 **모두 같다.** 즉 4장 비교 · 5장 입력 · 6장 출발점이 같은 3장 실행을 기준으로 이어진다. 6장은 `sft_model.zip`의 해시도 기록하므로, **같은 실행에서 만든 모델 ZIP**을 함께 올려야 한다.

**② 같은 3장 코드, 정밀도에 따라 결과가 갈렸다 (Claude가 보고서 두 개와 교안을 비교)**

| 3장 SFT 결과 | 교안 (RTX 5060 Laptop · BF16) | 내 L4 · BF16 (`sft_report_a1d2fa`) | 내 T4 · FP32 (`sft_report.json`) |
|---|---|---|---|
| 학습 후 dev loss | 0.0049 | 0.0053 | 0.0003 |
| 모범답안과 일치 (dev 12) | 10/12 | 10/12 | 12/12 |
| 초과 금액 문항 | “한도 이하” 오답 | “한도 이하” 오답 | 맞음 |
| 가중치 표본 변경 (256개 중) | 24개 | 27개 | 256개 |

- BF16 두 실행은 GPU가 달라도 거의 같은 모양이고, FP32만 다르다. 3장 슬라이드의 “BF16에서는 작은 변화가 반올림으로 사라질 수 있다”와 맞는 그림이라 **정밀도 차이일 가능성이 더 커졌다.** 다만 라이브러리 버전 등 다른 차이도 있어 원인을 단정하지는 않는다.

**③ 슬라이드의 계산은 모두 맞는다 (Claude 검산)**
- 71토큰 답의 logp 합 −0.11 → 토큰당 exp(−0.11 ÷ 71) ≈ **99.85%**, 합 −66.53 → ≈ **39.2%**(기하평균).
- `loss = −logsigmoid(margin)`: margin 0 → 선호 확률 0.5 · loss 0.6931, 0.2 → 0.55 · 0.5981, 2 → 0.881 · 0.1269, 5 → 0.993 · 0.0067.
- margin 3을 만들려면 logp 차이 변화가 beta 0.1에서 **30**, beta 1에서 **3**이 필요하다. 48쌍 × 2회 ÷ 누적 4 = **24번** 갱신.

**④ loss가 같아도 좋은 답이 떨어지고 있을 수 있다 (손계산 확인)**
- beta 0.1에서 (chosen 변화 0, rejected 변화 −20)과 (chosen 변화 −10, rejected 변화 −30)은 둘 다 margin 2 · **loss 0.1269**로 같다. 앞은 나쁜 답만 내려간 “바라는 모양”, 뒤는 좋은 답도 내려간 **과최적화**다. 그래서 loss · margin과 별도로 **chosen 쪽 값**을 본다.

**⑤ “0/8”의 분모를 읽는다**
- `summarize_behavior`는 **status만** 센다. 형식이 깨진 8개는 status가 `None`이라 과잉 보류에도 근거 없는 answered에도 들어가지 않는다. 그래서 2e-5 실행의 과잉 보류 0/8은 “보류를 안 했다”가 아니라 “**판정할 수 없는 답이 8개**”다. 집계를 읽을 때 “판정 불가” 칸을 따로 둬야 한다(슬라이드도 “status를 못 읽음 8”을 추가로 센다).

**⑥ W&B 보강은 교안 밖이고, 확인된 범위가 정해져 있다**
- 슬라이드 기준으로 **오프라인 모드에서 24갱신 기록**까지 확인됐고, 온라인 업로드 · W&B 화면 · Colab 설치는 아직 미확인이다. lr 2e-5 / 2e-6 / 1e-6 겹치기 그림은 **저장된 `log_history`로 그린 것**이지 W&B 화면 캡처가 아니다.
- API 키는 코드에 쓰지 않고 Colab 보안 비밀(`WANDB_API_KEY`)에서 읽는다. 로그인이 안 되면 오프라인으로 기록하고, 나중에 `wandb sync`로 올릴 수 있다.

## 6장. DPO 선호 학습과 응답 변화 분석

### 6-1 : 응답 쌍 — 선호 이유를 응답 쌍으로 표현하기
- **핵심 개념**:
  - 흐름: 같은 질문 · 같은 규정 → 모범답안은 chosen → 판단 하나만 틀리게 만든 rejected → 선호 이유를 함께 기록.
  - **한 쌍의 예(슬라이드 5장)**: 질문 “다온팀 출장에서 1박 80,000원인 방을 예약하려면 무엇을 해야 하나요?”, 규정 한도 1박 85,000원. chosen은 “한도 이하이므로 사전 승인이 필요하지 않습니다”(answered), rejected는 “제공된 근거로는 확인할 수 없습니다. 담당자에게 확인하세요”(abstained). 선호 이유: 숙박비 규정이 충분한데도 답하지 않는 **과잉 보류를 피한다.** 둘 다 형식은 맞고 다른 건 판단 하나다.
  - **여섯 유형, 잘못은 하나씩** (각 8쌍, 모두 48쌍):

    | 유형 | chosen | rejected에 넣은 잘못 | 피하려는 행동 |
    |---|---|---|---|
    | below | 한도 이하 · 승인 불필요 | 보류 (abstained) | 과잉 보류 |
    | boundary | 한도와 같음 · 불필요 | 초과라고 답함 | 경계값 오판 |
    | over_limit | 초과 · 예약 전 서면 승인 | 한도 이하라고 답함 | 초과 놓침 |
    | updated | 개정 한도로 · 불필요 | 초과라고 답함 | 개정 규정 미반영 |
    | missing | 보류 · 담당자 확인 | 지원되지 않는다고 단정 | 근거 없는 단정 |
    | irrelevant | 보류 · 담당자 확인 | 숙박비 규정을 다른 경비에 적용 | 엉뚱한 근거 사용 |

  - chosen은 2장 모범답안이고, rejected는 **교재용으로 의도해서 만든 답**이다. 실제 사람의 선호를 모은 자료가 아니다(노트북 문구). `make_pair`는 바꿀 문구가 모범답안에 있는지 `assert`하고, chosen과 rejected가 같아지지 않았는지, 둘 다 형식이 맞는지 확인한 뒤 `preference_pairs.jsonl`로 저장한다.
- **QA 체크포인트**:
  - **형식 확인은 의미 확인을 대신하지 않는다**(노트북 주석). 선호 이유와 분기 코드를 같이 읽는다.
  - 라벨(선호 방향)이 틀리면 그 잘못도 학습한다. 선호쌍도 2장 교재처럼 **검수 대상**이다.

### 6-2 : 기준 · 목적함수 — 기준 모델과 선호 목적함수 이해하기
- **핵심 개념**:
  - 흐름: 응답 토큰의 로그확률을 합산 → 고정 기준에서 얼마나 변했나 → beta를 곱한 reward → 두 답의 차이 margin → 손실.
  - **학습 전의 나를 기준으로 고정한다.** 학습하는 policy와 고정한 reference가 각각 두 답의 점수를 만든다. 이 코드는 reference 점수를 **먼저 계산해 숫자로 보관**하므로 두 모델을 계속 GPU에 올려 둘 필요가 없다(DPO 원논문 Figure 1 · 식 7을 다시 그린 그림).

    | 계산 단계 | 코드 | 확인할 의미 |
    |---|---|---|
    | 응답별 로그확률 | `response_logps` | 프롬프트 · 패딩을 빼고 응답과 EOS의 로그확률을 **합산** |
    | 기준 대비 변화 | `policy_logps - reference_logps.detach()` | 기준 점수에는 역전파하지 않음 |
    | 두 응답 비교 | `rewards[0] - rewards[1]` | 이 코드의 margin에는 beta가 포함됨 |
    | 선호 손실 | `-F.logsigmoid(margin)` | margin이 커지는 방향으로 학습 |

  - **점수 = 응답 토큰 로그확률의 합**: `targets = labels[:, 1:]`, `mask = targets.ne(-100)`으로 한 칸 밀린 정답 중 응답 위치만 골라 `-cross_entropy(..., reduction="none")`로 토큰 log-prob을 얻고, `scatter_add`로 응답별로 더한다. 장난감 예: 응답 토큰 [2, 1]개 → 합 [−3.5835, −1.7918], 평균 [−1.7918, −1.7918]. **길이로 나누면 다른 목적함수**가 된다.
  - **margin이 크면 loss가 작다**: margin 0 → loss 0.6931(시작), 2 → 0.1269, 5 → 0.0067. 손계산 함정(같은 loss, 다른 chosen)은 🧭 4-④.
  - **beta와 학습률은 다르다**:

    | | beta = 0.1 | learning rate = 2e-5 |
    |---|---|---|
    | 비유 | 채점 기준 (손실 식 안) | 보폭 (optimizer 안) |
    | 코드 위치 | `rewards = BETA * log_ratios` | `AdamW(lr=LEARNING_RATE)` |
    | 바꾸면 달라지는 것 | reward · margin · loss의 눈금과 기울기 | 갱신 한 번의 가중치 이동량 |
    | margin 3에 필요한 차이 변화 | 0.1이면 30, 1이면 3 | 관계없음 |
    | 오늘 실습 | 0.1 고정 | 2e-5 → 2e-6 비교 |

    - beta가 다른 실행끼리는 reward · margin의 눈금이 달라 숫자를 그대로 비교하지 않는다. beta를 키우면 언제나 변화가 작아진다고 단정할 수도 없다(노트북 문구).
  - **별도 보상 모델이나 PPO 반복이 없다.** 여기의 암묵적 보상을 사람이 준 업무 정답 점수로 해석하지 않는다.
- **QA 체크포인트**:
  - **합의 경계를 검사로 묶는다** — 응답 마지막이 EOS인지, 패딩이 −100인지 `assert`. 3장의 답변 마스크와 같은 원칙이다.
  - **설정 이름이 비슷해도 위치가 다르면 다른 손잡이** — beta(채점 기준)와 lr(보폭)을 따로 기록한다.

### 6-3 : DPO 이어 학습 — SFT 결과에서 DPO 이어 학습하기
- **핵심 개념**:
  - 흐름: `sft_model` 불러오기 → 학습 전 dev 원문 보관 → 기준 점수 48쌍 고정 → 네 쌍마다 한 번 갱신 → 학습 기록 읽기.
  - **학습 전 점수를 재서 얼려 둔다**: `torch.no_grad()`로 48쌍의 (chosen, rejected) 점수를 계산해 `reference_scores`에 보관하고 복사본(`reference_copy`)을 남긴다. 교안 출력: 3장의 저장 원문과 다른 건수 0, 첫 기준 log-prob [−0.1136, −39.3067], 초기 margin / loss 0.0 · 0.6931, 기준 점수 계산 1.806초. `reference_scores.json`으로 저장한다.
  - **셀 19를 지난 model은 더 이상 SFT가 아니다.** 처음으로 돌아가려면 파일에서 다시 불러와야 한다(같은 객체를 직접 갱신).
  - **직접 짠 반복문**(`TrainingArguments`가 아님): EPOCHS 2 · ACCUMULATION 4 · AdamW(weight_decay 0.01, `foreach=False`) · `max_norm` 1.0(`error_if_nonfinite=True`) · **scheduler 없음**(학습률이 일정, 3~5장의 선형 감소와 다름) · gradient checkpointing. 48 × 2 ÷ 4 = **24번** 갱신이고, 4의 배수가 아닌 자료라면 마지막 묶음 처리를 다시 설계해야 한다. 순서는 `random.Random(SEED + epoch)`로 섞는다.
  - **full-weight DPO**: 양자화나 LoRA를 더하지 않고 전체 494,032,768개를 학습한다.
  - **결과 (교안, lr 2e-5)**:

    | 갱신 | loss | margin | chosen reward | rejected reward |
    |---|---|---|---|---|
    | 1 | 0.693147 | 0.00 | 0.00 | 0.00 |
    | 4 | 2.517169 | 5.46 | −6.54 | −12.00 |
    | 24 | 0.000041 | 11.54 | −5.73 | −17.27 |

    - 가중치 표본 변화 36/256 · 최대 0.000225, 학습 시간 16.386초. 값은 **갱신 직전 네 쌍 평균**이다.
  - **lr을 낮춰 겹쳐 보기 (교안 밖 보강, 24번째 갱신)**:

    | lr | loss | margin | chosen reward | rejected reward |
    |---|---|---|---|---|
    | 2e-5 (교안) | 0.000041 | 11.54 | −5.73 | −17.27 |
    | 2e-6 | 0.516517 | 0.59 | +0.02 | −0.57 |
    | 1e-6 | 0.623265 | 0.16 | +0.01 | −0.16 |

    - chosen reward가 0 근처면 좋은 답이 유지된 것이다. loss만 보면 2e-5가 가장 좋아 보이지만 chosen이 −5.73으로 떨어졌다.
- **QA 체크포인트**:
  - **기준은 학습 중에 절대 바뀌면 안 된다** — 학습 뒤 `torch.equal(reference_scores, reference_copy)`로 확인한다. 회귀 테스트의 기준 결과를 테스트 도중 덮어쓰지 않는 것과 같다.
  - **loss가 내려갈수록 의심한다** — 0.000041은 “학습이 끝났다”가 아니라 chosen과 원문을 확인하라는 신호일 수 있다.

### 6-4 : 변화 · 과잉 보류 — 선호 변화와 과잉 보류 분석하기
- **핵심 개념**:
  - 흐름: 학습한 48쌍의 점수 변화 → dev 12개 자유 생성 → 형식 · 보류 · 단정 집계 → 원문 읽기 → 저장 후 재로딩.
  - **48/48 양수인데 좋은 답은 붕괴** (학습 뒤 48쌍):

    | | 학습 전 (SFT) | 2e-5 교안 | 2e-6 |
    |---|---|---|---|
    | margin 양수 | 0/48 (전부 0) | 48/48 | 48/48 |
    | 평균 loss | 0.6931 | 0.00002 | 0.3269 |
    | 첫 쌍 chosen logp | −0.11 | −66.53 | −0.11 |
    | 48쌍 평균 chosen logp | −0.44 | −73.65 | −0.36 |
    | 48쌍 평균 rejected logp | −37.62 | −236.31 | −55.76 |

    - margin 양수 = 기준보다 차이가 나아졌다는 뜻이지 **chosen이 더 높다는 뜻이 아니다.** 2e-6에서도 over_limit 8쌍은 rejected logp가 여전히 더 높다(8/8). 학습 중 chosen reward(네 쌍 평균)와 여기의 chosen logp(응답 합)는 다른 지표다.
  - **dev 12 집계** (`summarize_behavior`, status만 셈):

    | | DPO 전 (SFT) | 2e-5 교안 | 2e-6 |
    |---|---|---|---|
    | 형식 통과 | 12/12 | 2/12 | 12/12 |
    | 과잉 보류 (답할 수 있는 8개) | 0/8 | 0/8 | 0/8 |
    | 근거 없는 answered (근거 부족 4개) | 0/4 | 4/4 | 0/4 |
    | status를 못 읽음 (추가로 셈) | 0 | 8 | 0 |

    - 형식을 통과한 원문도 `{"status": "answered", "answer": "answered", "citations": ["policy01-v1"]}`(policy01-irrelevant)처럼 내용이 비어 있다. 집계는 금액 비교나 이유의 옳고 그름을 채점하지 않는다.
  - **원문: 말 자체가 무너졌다** (2e-5, 줄바꿈만 넣은 원문 발췌). policy01-over_limit은 DPO 전에는 “…한도 이하이므로 사전 승인이 필요하지 않습니다.”(3장의 오답 그대로)였는데 DPO 후 “…예약 전 서면 승인을 받아 보실 수 없습니다.supports#query}”가 됐다. policy05-below에서는 한국어 · 중국어 · 영어가 섞인 문장이 나왔다.
  - **원본은 흔들려도 저장은 정확하다**: 같은 2e-5 설정인데 교안 기록 1/12, 이 PC 먼저 돌린 실행 0/12(첫 쌍 chosen logp −75.78), 이 덱의 실행 2/12(−66.53). 저장 재로딩은 logits 최대 차이 0.0 · 원문 일치 True, 모델 ZIP 0.931GiB, 학습 이후 최대 allocated 4.494GiB. **저장 재현 = 같은 파일, 같은 답 / 학습 재현 = 다시 배워도 같은 답.**
  - 남기는 파일: `dpo_report.json`(설정 · 기록 · 원문) · `dpo_model.zip`(추론용, optimizer 없음) · `preference_pairs.jsonl` · `reference_scores.json` · `dpo_learning.png`. 7장은 이 파일들로 다섯 방법을 비교한다.
- **QA 체크포인트**:
  - **판정 불가를 별도 칸으로** — 파싱이 안 된 답은 “문제 없음”이 아니라 “판정 불가”다(🧭 4-⑤).
  - **원문을 직접 읽는다** — 숫자(형식 · status)가 못 잡는 붕괴(언어 섞임, 깨진 끝맺음)는 원문에서만 보인다.
  - **재현의 종류를 구분해서 적는다** — 저장 재현은 확인됐고 학습 재현은 안 됐다.

## 6장 보강. W&B로 학습 곡선 기록하기 (dpo_wandb.ipynb, 교안 밖)

- **핵심 개념**:
  - 교안 `dpo.ipynb`와 같고 **네 곳만 다르다**(검색창에서 `W&B 추가`로 찾음):

    | 표시 | 위치 | 하는 일 |

## 정리 — 6장 결과물

| 강 | 한 줄 | 꼭 볼 값 |
|---|---|---|
| 6-1 | 같은 입력, 판단 하나만 다른 두 답 | 48쌍 · 유형 6개 · 선호 이유 |
| 6-2 | 기준보다 차이가 벌어졌는지 손실로 | logp → reward → margin → loss |
| 6-3 | SFT에서 24번, 기준은 고정 | loss · margin · chosen reward |
| 6-4 | 점수와 자유 생성을 따로 | 형식 · 보류와 단정 · 원문 |

- **7장이 읽는 것**: `sft_model.zip`(같은 파일 보관), `dpo_report.json`(설정 · 기록 · 원문). 7장은 다섯 방법을 비교 평가한다.
- 7장 전에 할 것: `dpo_report.json` · SFT 입력 보관 → 7장 비교에 같은 파일 사용 → 설정 바꿔 보기(2e-6, 재시작 · 빈 폴더 · 처음부터).
- 직접 해 본 것: 슬라이드와 노트북 두 개를 Claude와 같이 읽고, 올려 둔 `sft_report_a1d2fa.json`을 6장 입력 검사와 대조했다. 6장 노트북 실행은 아직 안 했다(향후 계획).
