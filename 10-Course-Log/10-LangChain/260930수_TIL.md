# 📚 [TIL] LCEL과 Runnable 파이프라인, 순차·병렬 조합과 입력 변환, 구조화 출력 검증과 1회 복구, 그리고 Document 구조

## 💡 오늘의 학습 총평

- **핵심 통찰: LangChain의 모든 부품은 "같은 콘센트 규격"을 따른다**
  - Prompt, Model, Parser, 일반 Python 함수, 심지어 부품을 연결한 체인 전체까지 전부 **Runnable**이다. 그래서 전부 `invoke()` / `batch()` / `stream()`이라는 같은 이름으로 실행된다.
  - 규격이 같으니까 `|`로 끼워 맞출 수 있고, 연결한 결과도 다시 하나의 Runnable이 되어 또 다른 체인의 부품이 된다.
  - 3장에서 4장으로 넘어가며 이게 체감됐다. `RunnableSequence`(직렬), `RunnableParallel`(병렬), `RunnablePassthrough`(통과), `RunnableLambda`(일반 함수 포장)가 전부 같은 규격이라 레고처럼 조립된다.

- **두 번째 통찰: "연결"과 "실행"은 다른 시점이다**
  - `chain = prompt | model | parser`는 **설계도를 그리는 코드**이고, 이 줄에서는 모델 API가 호출되지 않는다.
  - 실제 요청은 `chain.invoke(...)`를 부를 때 발생한다. 모델 객체를 만드는 것도, 체인 생성 함수를 부르는 것도 비용이 0이다.
  - 이 구분 덕분에 **모델을 부르지 않고도 체인의 구조를 확인**할 수 있고, 가짜 모델(`RunnableLambda`)을 끼워서 전체 흐름을 테스트할 수 있다.

- **세 번째 통찰: 구조화 출력은 "형식"을 보장할 뿐 "사실"을 보장하지 않는다**
  - 5장에서 가장 중요한 문장 — *"category='오류'가 스키마를 통과했더라도 실제 질문을 잘못 분류했을 수 있습니다."*
  - Pydantic 스키마를 통과했다는 건 **필드와 타입이 맞다**는 뜻이지 **답이 맞다**는 뜻이 아니다. 형식 검증과 내용 검증은 다른 층이다.
  - 지난 과정의 "JSON 문법 ≠ 스키마 ≠ 비즈니스 사실" 3단 검증이 LangChain에서도 그대로 이어진다.

- **네 번째 통찰: 지난 과정에서 배운 원칙들이 LangChain 부품 이름으로 다시 나온다**

  | 지난 과정 (09-Data-Pipeline-FastAPI) | 오늘 (LangChain) |
  |---|---|
  | 4-2강 `document_id` / `content` / `metadata` | 6-1강 `Document(page_content, metadata)` |
  | 8-2강 재시도는 최대 1회 | 5-3강 출력 복구는 최대 1회 |
  | 8-1강 `gather` 결과는 입력 순서 | 3-2강 `batch` 결과는 입력 순서 |
  | 4-1강 판단 못 하는 값은 억지로 채우지 않는다 | 5-3강 잘못된 category를 임의로 고치지 않는다 |
  | 3-2강 원본은 덮어쓰지 않는다 | 4-2강 `assign`은 원본 `question`을 유지한다 |
  | 6-1강 오류는 `loc` / `type`으로 읽는다 | 5-2강 `error.errors()[0]["loc"]`, `["type"]` |

- **향후 계획 및 다짐**
  - 곧 2차 팀 프로젝트가 시작된다. 오늘 배운 **구조화 출력 + 검증 + 1회 복구** 흐름은 팀 프로젝트에서 LLM 응답을 다룰 때 거의 그대로 쓰일 것 같다.
  - 팀에서 품질·검증 쪽으로 기여한다면, 가장 먼저 챙길 것은 **"스키마를 통과한 결과"와 "정답인 결과"를 따로 보는 것**이다. 형식 준수율만 보고 품질이 좋다고 판단하지 않도록.

## 📊 어제보다 나아진 점

- 어제는 1~2장(Prompt · Model · Parser를 하나씩 실행)까지였고, 오늘은 **3장~6장 1강까지 9개 강의**로 진도 폭이 커졌다.
- 새 부품이 나올 때마다 AI 설명으로 **지난 과정의 어떤 개념과 연결되는지** 먼저 짚고 들어가서, 부품 수가 갑자기 늘었는데도 흐름을 놓치지 않았다.
- 아직 코드는 AI 설명을 들으며 읽는 단계다. 오늘은 특히 **"각 단계가 무엇을 받고 무엇을 내보내는가"라는 자료형 흐름**으로 체인을 읽는 방법을 익히는 데 집중했다. ★

## 🧭 종합 QA 체크포인트

> 아래 강의별 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거 강의** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. 무엇을 모델 없이 테스트할 수 있나 — 결정적 영역과 비결정적 영역

LLM 앱 테스트의 출발점은 **결정적인 부분(같은 입력 → 항상 같은 출력)과 비결정적인 부분을 나누는 것**이다. 오늘 배운 부품 대부분은 결정적이다.

| 대상 | 결정적? | 모델 없이 테스트 | 근거 강의 |
|---|---|---|---|
| Prompt 채우기 (`prompt.invoke`) | ⭕ | 가능 | 3-3 |
| 체인 조립 (`a \| b \| c`) | ⭕ | 가능 — 타입만 확인 | 3-1 |
| 입력 전처리·검증 (`RunnableLambda`) | ⭕ | 가능 | 4-1, 4-2 |
| 필드 추가 (`assign`) | ⭕ | 가능 | 4-2 |
| Pydantic 스키마 검증 | ⭕ | 가능 | 5-1 |
| Parser 검증 (`PydanticOutputParser`) | ⭕ | 가능 — 고정 JSON 주입 | 5-2 |
| 복구 분기 (성공 / 최종 실패 / 생략) | ⭕ | 가능 — 고정 수정 문자열 | 5-3 |
| Document 생성·formatter | ⭕ | 가능 | 6-1 |
| **Model 호출** | ❌ | 가짜 모델로 대체 | 3-1 |

→ **비결정적인 건 Model 한 칸뿐이다.** 나머지를 결정적 테스트로 촘촘히 덮고, Model은 가짜로 바꿔 끼우면 체인 전체 흐름을 비용 0원·매번 같은 결과로 검증할 수 있다.

### 2. 테스트 더블(가짜 부품) 패턴 4종

| 패턴 | 어디서 | 무엇을 대신하나 |
|---|---|---|
| `RunnableLambda(local_model)` | 3-1, 3-3 연습문제 | 실제 ChatModel |
| `AIMessage(content="...")` 직접 생성 | 2-2 (어제) | 모델 응답 |
| 고정 JSON 문자열 | 5-2, 5-3 | 모델이 만든 구조화 출력 |
| 고정 수정 문자열 (`repaired_output`) | 5-3 연습문제 | 복구 요청 결과 |

이 패턴이 가능한 이유는 **체인 생성 함수가 `model`을 인자로 받기 때문**이다(3-3). 외부 의존성을 밖에서 주입받는 구조여야 가짜로 바꿔 끼울 수 있다.

### 3. 판정 기준(oracle) — 무엇으로 합격/불합격을 가르나

| ❌ 쓰면 안 되는 기준 | ⭕ 써야 하는 기준 |
|---|---|
| 답변 문장 글자 단위 일치 | 반환 자료형 (`str`, `dict`, Pydantic 객체) |
| stream 조각 개수·경계 | 조각을 합친 문자열이 비어 있지 않은가 |
| 오류 메시지 문구 | 오류 `loc`(필드 위치)와 `type`(유형) |
| "수정했습니다"라는 모델의 말 | 같은 Parser가 객체를 반환했는가 |
| 스키마 통과 여부 = 품질 | 스키마 통과 **+** 내용 정답 여부 별도 확인 |

마지막 줄이 가장 중요하다. **형식 준수는 평가를 시작할 수 있는 전제 조건이지 품질 지표가 아니다.**

### 4. 호출 수와 비용 — 몇 번 부르는가

| 실행 | 모델 API 호출 수 |
|---|---|
| `chain = a \| b \| c` (연결만) | 0 |
| `invoke()` 1회 | 1 |
| `batch([...N개])` | N |
| `RunnableParallel` (모델 branch K개) 1회 | K |
| 복구 흐름 — 첫 검증 성공 | 0 (추가 호출 없음) |
| 복구 흐름 — 첫 검증 실패 | 1 (최대) |
| 입력 전처리에서 실패 | 0 |

**호출 수 자체가 검증 대상이다.** 정상 입력에서 복구 호출이 발생하면 비용 누수 버그이고, 전처리 실패인데 API가 호출됐다면 검증 순서 버그다. 결과값만 보면 이런 결함은 드러나지 않는다.

### 5. 실패 처리 원칙 3가지

- **Fail fast — 비싼 단계 전에 막는다.** 입력 자료형·필수 키·빈 문자열은 모델 호출 **전에** 전처리에서 거른다 (4-1 `prepare_input`, 4-2 `require_input_dict`). Parallel 구조일수록 효과가 커진다.
- **Fail loud — 조용히 대체하지 않는다.** 파싱 실패를 빈 객체로, 잘못된 category를 임의 값으로 바꾸지 않는다 (5-2, 5-3). 필수 metadata는 `get()` 대체값이 아니라 대괄호로 읽어 누락을 드러낸다 (6-1).
- **Bounded retry — 제한된 횟수, 같은 기준.** 복구는 최대 1회, 재검증은 첫 검증과 **같은 Parser**로 한다 (5-3). 상한이 없으면 비용과 종료 시점을 예측할 수 없다.

### 6. 계약(contract) — 깨지면 조용히 오작동하는 지점

| 계약 | 어긋나면 |
|---|---|
| 입력 딕셔너리 키 = Prompt 변수 이름 | `KeyError` (3-1, 3-3) |
| 앞 단계 출력 자료형 = 뒤 단계 입력 자료형 | 체인 중간에서 실패 (3-1) |
| branch 이름 = 결과를 읽는 키 | `KeyError` (4-1) |
| assign이 만든 키 = 다음 단계가 읽는 키 | `KeyError` (4-2) |
| 스키마 필드·타입·`Literal` 허용값 | `missing`, `literal_error` (5-2) |
| 모든 문서의 metadata 키 집합 | formatter·검색이 문서마다 다르게 동작 (6-1) |
| 체인의 최종 반환 타입 | 호출하는 쪽 코드 전체가 깨짐 (3-1) |

이름 하나를 바꾸면 **그 이름을 읽는 모든 곳**이 영향을 받는다. 이름 변경은 인터페이스 변경으로 다뤄야 한다.

### 7. 순서 의존성 — 리팩토링에 가장 취약한 곳

- `assign` 두 개의 순서 — 뒤가 앞의 키를 읽는다 (4-2)
- Sequence 단계 순서 — 뒤가 앞의 출력을 받는다 (4-1)
- 디버깅 순서 — 왼쪽부터 자료형 확인 (3-3)
- 검증 → 복구 → 재검증 순서 (5-3)

순서를 바꿔도 **문법 오류가 나지 않는 경우**가 가장 위험하다. 이런 지점은 순서를 고정하는 테스트를 둬야 리팩토링 때 조용한 동작 변화를 잡을 수 있다.

### 8. LLM Eval로 확장하면 — 따로 집계해야 할 지표

오늘 배운 구조화 출력·복구 흐름을 평가 파이프라인에 넣으면, 하나의 "성공률"로 뭉치면 안 되는 지표들이 생긴다.

| 지표 | 의미 | 왜 분리하나 |
|---|---|---|
| 1차 형식 준수율 | 복구 없이 스키마를 통과한 비율 | 모델·프롬프트의 진짜 형식 성능 |
| 복구 발생률 | 복구 요청이 필요했던 비율 | 높으면 프롬프트나 스키마 설계 문제 |
| 복구 후 형식 준수율 | 복구까지 포함해 통과한 비율 | 1차 준수율과 섞으면 모델 성능이 과대평가됨 |
| 최종 실패율 | 복구 후에도 실패한 비율 | 사용자에게 도달하는 실패 |
| 내용 정답률 | 형식 통과한 것 중 답이 맞은 비율 | 형식 준수와 별개의 품질 |
| 호출 수 / 건 | 입력 한 건당 평균 API 호출 | 비용 추정, 복구·Parallel 영향 |

## 🎯 오늘 배운 핵심 내용

## 3장. LCEL과 Runnable 기반 파이프라인 설계

### 3-1강 : LCEL pipe 연산자와 Runnable 인터페이스
- **핵심 개념**:
  - **LCEL**(LangChain Expression Language) = LangChain 부품을 조합해 실행 흐름을 표현하는 방법.
  - `prompt | model | parser` → **왼쪽 단계의 출력이 오른쪽 단계의 입력**이 된다. 컨베이어 벨트처럼 왼쪽에서 오른쪽으로 흐른다.
  - Python에서 `|`는 원래 OR 연산이나 딕셔너리 병합에 쓰이지만, Runnable 사이에서는 **연결 연산자**로 동작한다.
- **이번 체인의 자료형 흐름**:
  | 위치 | 구성 요소 | 받는 값 | 내보내는 값 |
  |---|---|---|---|
  | 시작 | 입력 | — | `dict` |
  | 1단계 | `ChatPromptTemplate` | `dict` | 역할별 메시지 묶음 |
  | 2단계 | `ChatOpenAI` | 역할별 메시지 | `AIMessage` |
  | 3단계 | `StrOutputParser` | `AIMessage` | `str` |
  - **`|`가 자료형을 알아서 바꿔주지 않는다.** 왼쪽이 내보낸 값을 오른쪽이 받을 수 있어야 정상 실행된다.
- **Runnable**:
  - 입력을 받아 작업하고 출력을 돌려주는 LangChain 구성 요소의 **공통 실행 방식**. 콘센트 규격과 같다.
  - Prompt · Model · Parser · 연결한 체인 전체가 모두 Runnable이라 전부 `invoke()`를 쓸 수 있다.
  - 연결한 결과의 타입은 `RunnableSequence` — **연결한 전체도 다시 하나의 Runnable**이 된다.
- **연결 ≠ 실행**:
  - `chain = prompt | model | parser` → 구조만 만든다. **API 호출 없음.**
  - `chain.invoke({"question": ...})` → 이때 실제 모델 요청이 발생한다.
  - 입력 딕셔너리의 키는 Prompt의 `{question}`과 **정확히 같아야** 한다.
- **단계별 실행 vs 체인 실행**:
  - 단계별 — 어느 단계에서 문제가 났는지 보기 쉬움 → 처음 구조를 배울 때, 오류를 확인할 때
  - 체인 — 코드가 간결하고 재사용이 쉬움 → 구조를 확인한 뒤 반복 실행할 때
- **QA 체크포인트**:
  - **연결이 비용 0이라는 건 구조 테스트가 공짜라는 뜻.** `type(chain).__name__ == "RunnableSequence"`처럼 체인이 제대로 조립됐는지를 모델 호출 없이 확인할 수 있다.
  - **연습문제 2·3이 `RunnableLambda`로 가짜 모델을 만든다.** `local_model()`이 `AIMessage(content="연습 답변: ...")`을 반환하게 해서, 실제 API 없이 Prompt → 가짜 Model → Parser 전체 흐름을 검증한다. 지난 과정의 `MockTransport`, 1~2장의 가짜 `AIMessage`에 이어 **세 번째 테스트 더블 패턴**이다.
  - **두 호출의 답변을 글자 단위로 비교하지 않는다.** 교안이 *"둘 다 str 결과를 반환하는지 확인하세요"* 라고 명시 — 판정 기준은 문장이 아니라 **자료형과 구조**다.
  - **Parser를 빼면 결과가 `AIMessage`가 된다** (교안 오류 3번). 체인 끝의 부품 하나가 최종 자료형을 결정하므로, 체인을 수정했을 때 **최종 반환 타입이 바뀌지 않았는지**가 회귀 테스트 포인트다.

### 3-2강 : invoke / batch / stream 실행 방식
- **핵심 개념**:
  - **같은 체인을 그대로 두고 실행 메서드만 바꾼다.**
    | | `invoke()` | `batch()` | `stream()` |
    |---|---|---|---|
    | 입력 | 한 건 (`dict`) | 여러 건 (`list[dict]`) | 한 건 (`dict`) |
    | 결과 | 최종 결과 한 개 | 결과 리스트 | 순서대로 도착하는 조각 |
    | 받는 법 | 변수에 바로 저장 | 반복문으로 확인 | 반복문으로 조각 확인 |
    | 사용 예 | 질문 하나에 답하기 | 여러 문장 분류·요약 | 긴 답변을 생성 중부터 보여주기 |
- **batch**:
  - 입력은 딕셔너리 **리스트**, 결과도 **리스트**. 결과의 각 위치는 **입력 목록의 위치에 대응**한다.
  - 입력이 두 개면 모델 요청도 두 번 처리된다 — 필요한 개수만 쓴다.
  - **주의: `Runnable.batch()`는 공급자의 Batch API(파일 올리고 나중에 결과 받는 것)와 다른 기능**이다. 이름만 같다.
- **stream**:
  - 반환값이 "조각을 차례로 꺼낼 수 있는 값"이라 **반복문이 필요**하다. `print(chain.stream(...))`로 바로 출력하면 객체 표시만 보인다.
  - `print(chunk, end="", flush=True)` — 줄바꿈 없이 바로 이어 붙여 출력.
  - 화면에 조각을 보여주면서 전체 답변도 쓰려면 리스트에 모았다가 `"".join()`.
- **선택 순서**:
  - 입력이 한 건인가 여러 건인가? → 여러 독립 입력이면 `batch()`
  - 완성 결과만 필요한가, 생성 중부터 보여줘야 하나? → 완성만 필요하면 `invoke()`, 바로 보여줘야 하면 `stream()`
  - 교안 권장: **먼저 `invoke()`로 정상 동작을 확인한 뒤** 필요에 따라 바꾼다.
- **QA 체크포인트**:
  - **"stream 조각 개수를 정답으로 비교하지 마라"** (교안 오류 5번). 조각의 개수와 경계는 실행마다 달라진다. 테스트는 **조각을 합친 전체 문자열이 비어 있지 않은지**로 판정해야 한다. 비결정적인 값을 assert 대상으로 삼으면 flaky test가 된다.
  - **batch 결과 순서 = 입력 순서.** 지난 과정 8-1강 `asyncio.gather`와 같은 성질이다. 덕분에 입력과 결과를 **위치로 매핑**해서 검증할 수 있다.
  - **`batch` 이름 혼동은 실제 비용 사고로 이어질 수 있다.** 공급자 Batch API는 보통 할인·지연 처리가 되는 별도 기능인데, `Runnable.batch()`는 그냥 요청을 여러 번 보내는 것이다. "batch로 돌렸으니 싸겠지"라는 오해를 경계.
  - **실행 모드를 하나만 골라 돌리게 한 설계** — `EXECUTION_MODE`를 바꿔가며 한 번에 하나만 실행한다. API 호출 수를 의식하게 하는 교안의 일관된 원칙.

### 3-3강 : 중간 출력 디버깅과 chain 재사용
- **핵심 개념**:
  - 체인은 한 줄로 보여도 **실제로는 왼쪽부터 한 단계씩** 실행된다. 오류가 나면 전체를 한꺼번에 고치지 말고 **왼쪽부터 순서대로** 확인한다.
  - 확인 순서: ① 처음 입력의 자료형과 키가 Prompt 요구사항에 맞나 → ② Prompt 결과를 Model이 받을 수 있나 → ③ Model 결과를 Parser가 받을 수 있나
- **str과 dict 불일치 (이번 강의의 단 하나의 오류)**:
  - `topic`, `example` 두 변수를 가진 Prompt에 문자열 `"LCEL"` 하나를 넣으면 → **어느 값을 어느 자리에 넣을지 결정할 수 없어** 오류.
  - 수정: `{"topic": "LCEL", "example": "prompt | model | parser"}`
  - 오류 메시지가 길어도 **먼저 `type(input).__name__`이 `str`인지 `dict`인지** 보면 빨리 찾는다.
  - 변수가 한 개인 일부 Prompt는 문자열을 짧은 입력으로 받아주기도 한다. 이번 Prompt는 변수가 두 개라 딕셔너리가 필요하다.
- **중간 자료형 점검**:
  - 정상 흐름: `입력 dict → Prompt 결과 ChatPromptValue → Model 결과 AIMessage → Parser 결과 str`
  - 교안 조언: *"중간 객체의 긴 내용을 전부 출력하기보다 먼저 자료형 이름을 확인하세요."*
  - `prompt.invoke()`와 `prompt_value.to_messages()`는 **모델 API를 호출하지 않는다** — Prompt가 제대로 채워졌는지만 먼저 확인할 수 있다.
- **체인 생성 함수**:
  - `build_explain_chain(model, audience)` — Prompt · Model · Parser를 조립해서 **체인을 반환**하는 함수.
  - 함수 안에서는 `invoke()`까지 하지 않는다. 질문을 고정하면 재사용이 안 된다.
  - 재사용되는 것: system 메시지의 역할 · human 메시지 구조 · 모델 · Parser · 실행 순서 / 바뀌는 것: 입력 딕셔너리
  - `return`을 빼먹으면 `None`이 반환된다.
- **QA 체크포인트**:
  - **"왼쪽부터 한 단계씩 자료형 확인"은 결함 격리(fault isolation)의 교과서적 절차다.** 게임 QA에서 재현 경로를 단계별로 쪼개 어디서 깨지는지 좁히는 것과 같다. 체인이 길어질수록(4장부터) 이 습관의 가치가 커진다.
  - **체인 생성 함수가 `model`을 인자로 받는 게 핵심 설계.** 모델을 밖에서 넣어주니까(의존성 주입) 테스트할 땐 **가짜 모델을, 실제로는 `ChatOpenAI`를** 넣을 수 있다. 연습문제 3이 정확히 그렇게 `local_model`을 주입한다. **테스트 가능한 코드는 외부 의존성을 밖에서 받는다.**
  - **실습이 잘못된 입력으로 오류를 일부러 재현한다.** 그리고 *"잘못된 문자열 입력은 모델에 전달되기 전에 중단되므로 API가 호출되지 않습니다"* — 입력 오류는 **비용이 발생하기 전에** 걸러진다. 부정 테스트(negative test)를 비용 없이 돌릴 수 있다는 뜻.
  - **Prompt 결과는 API 없이 확인 가능** → 체인이 실패하면 Prompt 단계까지는 무료로 먼저 검증하고, 그다음에 유료인 Model 단계를 본다. **비용이 싼 단계부터 검증하는 순서**.

## 4장. 순차/병렬 실행과 입력 데이터 변환

### 4-1강 : RunnableSequence와 RunnableParallel
- **핵심 개념**:
  - **순차 실행** — 뒤 단계가 앞 단계의 결과를 사용한다. `RunnableSequence`
  - **병렬 실행** — 여러 작업이 **같은 입력**을 각각 사용한다. `RunnableParallel`
  - 판단 질문: 두 번째 단계가 첫 번째 결과를 쓰나? → 순차 / 두 작업이 같은 입력을 각각 쓰나? → 병렬 / 앞에서 입력을 정리한 뒤 둘로 나누나? → **순차 뒤 병렬** (이번 실습)
- **RunnableSequence**:
  - `RunnableSequence(clean_step, label_step)`과 `clean_step | label_step`은 **같은 체인**이다.
  - `|`가 간결하고, 클래스 직접 사용은 단계 목록을 펼쳐 보여주기 좋다.
  - 마지막 단계의 출력이 전체 결과가 된다. **순서가 중요하다.**
- **RunnableParallel**:
  - `RunnableParallel(upper=..., length=...)` → 같은 입력을 두 branch에 각각 전달하고 **branch 이름을 키로 가진 딕셔너리**를 반환.
  - `upper`, `length`는 LangChain이 정한 이름이 아니라 **코드 작성자가 정한 이름**이다. 결과를 `result["upper"]`로 읽는다.
  - 교안의 "병렬"은 우선 **결과를 두 갈래로 나누어 구성한다**는 의미로 이해. 속도 측정이나 실행 방식 조정은 다루지 않는다.
- **완성 실습 구조**:
  ```
  원문 문자열
  → prepare_input: 공백 정리 + {"text": ...}로 변환 (한 번 실행)
  → summary branch  : 요약 Prompt | Model | Parser
  → keywords branch : 키워드 Prompt | Model | Parser
  → {"summary": "...", "keywords": "..."}
  ```
  - `prepare_input`은 문자열이 아니면 `TypeError`, 공백만 있으면 `ValueError` — **모델에 보내기 전에** 막는다.
- **QA 체크포인트**:
  - **`RunnableParallel`을 한 번 `invoke()`해도 API는 두 번 호출된다.** 교안이 강조한 부분 — *"한 모델 객체를 함께 사용한다는 사실이 호출 한 번을 뜻하지는 않습니다."* branch 수가 곧 호출 수이고, 비용과 rate limit 계산의 기준이 된다. branch를 하나 추가할 때마다 비용이 선형으로 늘어난다.
  - **전처리 단계가 API 호출 전에 입력을 검증한다 = fail fast.** 빈 문자열이 들어오면 두 branch에서 각각 비용을 쓰고 실패하는 게 아니라, 전처리에서 한 번에 막는다. 병렬 구조일수록 **앞단 검증의 비용 절감 효과가 커진다.**
  - **branch 이름이 곧 결과 계약.** `keywords`로 만들고 `result["keyword"]`로 읽으면 `KeyError` (교안 오류 5번). branch 이름을 바꾸면 **결과를 읽는 모든 코드가 깨진다** — 인터페이스 변경으로 관리해야 한다.
  - **요약이 "한 문장"인지, 키워드가 "쉼표로 세 개"인지**를 확인하라는 교안 기준 — 이건 Parser가 검증해주지 않는다(`StrOutputParser`는 문자열이면 다 통과). 형식 요구사항을 프롬프트로만 전달하고 검증은 안 하는 상태라는 걸 인식해야 한다. 5장 구조화 출력이 필요한 이유.

### 4-2강 : RunnablePassthrough / RunnableLambda / assign
- **핵심 개념 — 세 도구의 역할**:
  | 도구 | 하는 일 | 내보내는 값 |
  |---|---|---|
  | `RunnablePassthrough()` | 입력을 **바꾸지 않고** 전달 | 받은 입력 그대로 |
  | `RunnableLambda(함수)` | **일반 Python 함수**를 Runnable로 포장 | 함수의 반환값 |
  | `RunnablePassthrough.assign(...)` | **기존 필드를 유지하고 새 필드 추가** | 필드가 늘어난 딕셔너리 |
- **RunnableLambda**:
  - 함수의 계산 내용은 그대로, **체인에 끼울 수 있는 부품**으로 바꿔준다. 감싼 뒤에는 `invoke()`로 실행하고 `|`로 연결할 수 있다.
  - 3장 연습문제에서 가짜 모델을 만들 때 쓰던 게 바로 이것.
- **assign**:
  - `RunnablePassthrough.assign(clean_question=RunnableLambda(extract_clean_question))`
  - `clean_question=` → 새 필드의 이름 / 오른쪽 Runnable의 결과 → 그 필드의 값
  - **입력은 딕셔너리여야 한다.** 문자열 하나만 주면 기존 필드와 합칠 기준이 없어 오류.
- **두 번의 assign 순서**:
  ```
  입력 {question, student_level}
  → 1번째 assign: clean_question 추가
  → 2번째 assign: clean_question을 읽어 question_length 추가
  → {question, student_level, clean_question, question_length}
  ```
  - 두 번째 단계가 첫 번째가 만든 키를 읽는다. **순서를 뒤집으면 `KeyError`.**
- **원본을 덮어쓰지 않는다**:
  - 정리한 질문은 `question`을 수정하는 게 아니라 **`clean_question`이라는 새 필드**에 넣는다. 최종 결과에서 원본과 정리본을 **둘 다** 읽을 수 있다.
- **입력 확인 단계**:
  - `require_input_dict()` — 딕셔너리인가 → `question` 키가 있나 → `question`이 문자열인가를 **assign 전에** 확인.
  - `extract_clean_question()` — 공백 제거 후 **빈 문자열이면** `ValueError`.
- **QA 체크포인트**:
  - **"원본 question을 덮어쓰지 않는다"는 지난 과정 3-2강 원본 보존 원칙과 같다.** 정리 결과가 이상하면 원본과 비교해서 **어느 변환 단계가 문제였는지 추적**할 수 있다. 원본을 덮어쓰면 이 추적이 불가능해진다.
  - **assign 순서 의존성 — 교안에서 네 번째로 만나는 순서 문제.** 지난 과정 4-1강(중복 → 필수값), 6-1강(공백 제거 → 길이 검사), 오늘 3-3강(왼쪽부터 확인), 그리고 여기(clean → length). 순서를 바꾸면 결과가 달라지는 곳은 **리팩토링 시 테스트로 고정해둬야 하는 지점**이다.
  - **이 실습은 모델을 전혀 쓰지 않는다** → API Key 없이, 비용 없이, **매번 같은 결과**(`question_length = 32`). 입력 변환 로직은 완전히 결정적이라 단위 테스트의 이상적인 대상이다. LLM 앱 테스트 전략에서 **비결정적인 모델 부분을 최소화하고 결정적인 변환 부분을 최대한 분리**하는 게 핵심인데, `RunnableLambda`가 그 분리를 가능하게 한다.
  - **`len()` 결과 32를 예상 출력에 박아둔 것** — 한글·영문·공백·물음표가 섞인 문자열의 길이다. 지난 과정 6-1강에서 짚었던 **한글 문자 수 vs 바이트 수** 문제가 여기서도 적용된다. `len()`은 문자 수 기준이다.

## 5장. 구조화 출력과 스키마 검증

### 5-1강 : Pydantic schema와 structured output
- **핵심 개념**:
  - 자연어 답변 `"이 질문은 코드 실행 중 발생한 오류에 관한 질문이며..."` → 프로그램이 "오류"와 `True`를 **문장 안에서 다시 찾아야** 한다.
  - 구조화 출력 → `category="오류"`, `summary="..."`, `needs_code=True`처럼 **필드별로 나뉜 값**.
  | | 자연어 문자열 | 구조화 출력 |
  |---|---|---|
  | 자료형 | `str` | Pydantic 객체 |
  | 값 읽기 | 문장을 다시 해석 | 정해진 필드에 접근 |
  | 필드 누락 확인 | 직접 | 스키마가 검증 |
  | 허용값 제한 | 별도 코드 | `Literal`로 표현 |
  | 적합한 상황 | 설명문을 그대로 보여줄 때 | 분류·저장·조건 분기 |
- **스키마 도구 3종**:
  - `BaseModel` — 필드를 읽고 규칙에 맞는 객체를 만든다
  - `Field` — 필드 설명·기본값을 기록한다
  - `Literal["개념", "코드", "오류"]` — 받을 수 있는 문자열을 목록으로 **제한**한다
- **필드 읽기**:
  - Pydantic 객체는 `result.category`처럼 **점 표기법**으로 읽는다. `result["category"]`가 아니다.
  - 딕셔너리가 필요하면 `result.model_dump()`.
- **`with_structured_output()`**:
  - `structured_model = model.with_structured_output(QuestionClassification)` → 모델이 **스키마에 맞는 객체를 반환**하도록 설정한 실행 객체.
  - 원래 `model`은 그대로 두고 새 실행 객체를 만든다. 별도 API가 아니다.
  - `chain = prompt | structured_model` → **Prompt는 무엇을 분류할지, 스키마는 어떤 필드와 타입으로 받을지**를 각각 담당.
- **로컬 객체 vs 모델 구조화 출력의 차이**:
  - Python 코드에서 직접 객체를 만들 때는 기본값이 있는 `needs_code`를 **생략할 수 있다.**
  - 하지만 `with_structured_output()`이 모델에 전달하는 출력 형식은 **세 필드를 모두 포함하도록** 요청한다.
- **QA 체크포인트**:
  - **"형식이 맞다 ≠ 내용이 맞다" — 이번 장의 가장 중요한 문장.** 교안: *"구조화 출력은 답변을 더 정확한 사실로 만들어 주는 기능이 아닙니다."* 스키마를 100% 통과해도 분류 정확도는 별개다. LLM Eval에서 **형식 준수율과 정답률을 반드시 따로 측정**해야 하는 이유. 형식 준수율 100%는 품질 지표가 아니라 **평가를 시작할 수 있는 전제 조건**일 뿐이다.
  - **`Literal`은 동등 분할(equivalence partitioning)의 유효 클래스를 코드로 박아둔 것.** 테스트 설계 시 유효 클래스 3개(`개념`, `코드`, `오류`) + 무효 클래스(`기타`, 빈 문자열, 대소문자 변형 등)로 나눠서 케이스를 뽑을 수 있다.
  - **API Key 없이도 앞의 두 줄(로컬 객체, 기본값)은 실행된다** — 스키마 자체의 동작은 모델 없이 검증 가능하다. 5-2강에서 이걸 본격적으로 활용한다.
  - **summary 문구를 글자 단위로 비교하지 않는다.** 확인 기준은 반환 클래스 · 세 필드 존재 · `category`가 허용값 중 하나 · `needs_code`가 불리언. 전부 **구조 검증**이고, 비결정적인 문장 자체는 assert 대상이 아니다.

### 5-2강 : Parser 기반 검증과 validation error
- **핵심 개념**:
  - `PydanticOutputParser(pydantic_object=QuestionClassification)` → JSON **문자열**을 읽고 Pydantic 스키마로 검증해 **객체**를 반환.
  - `pydantic_object`에는 클래스 자체를 넘긴다. `QuestionClassification()`처럼 객체를 먼저 만들지 않는다.
  - 검증 3단계: `JSON 문법 읽기 → 스키마로 필드·값 검사 → 검증된 객체 반환`
  - `get_format_instructions()`는 형식 안내 문자열을 만들 뿐 모델을 호출하지 않는다.
- **대표 실패 3종**:
  | 사례 | 입력 | 결과 |
  |---|---|---|
  | JSON 문법 오류 | 쉼표 누락 | JSON을 읽지 못함 |
  | 필수 필드 누락 | `summary` 없음 | `missing` |
  | Literal 허용값 위반 | `category="기타"` | `literal_error` |
  - `needs_code`처럼 기본값이 있는 필드는 JSON에서 **생략 가능**. 기본값이 없는 `summary`는 생략 불가.
- **두 예외의 위치 구분**:
  | 호출한 코드 | 잡는 예외 |
  |---|---|
  | `parser.parse(JSON_문자열)` | `OutputParserException` |
  | `Model.model_validate(딕셔너리)` | `ValidationError` |
  - Parser 내부에서도 Pydantic 검증을 쓰지만, **Parser를 호출한 쪽에는 LangChain의 Parser 예외로 전달**된다.
  - 어느 쪽이 더 좋은 게 아니라 **어떤 함수를 호출했는지에 따라** 알맞은 예외를 처리한다.
- **짧게 읽는 오류 정보**:
  - `error.errors(include_input=False)[0]` → 첫 오류의 `loc`(필드 위치)와 `type`(오류 유형)
  - 먼저 필드 위치를 확인하고, 그다음 유형을 읽는다.
- **JSON과 Python 불리언 혼동**:
  - JSON 안에서는 소문자 `false` / `true`, Python 딕셔너리에서는 `False` / `True`.
  - JSON의 키와 문자열 값은 **큰따옴표**.
- **QA 체크포인트**:
  - **"모델을 호출하지 않고 고정된 JSON 문자열로 검증한다" — 이번 강의 전체가 결정적 결함 주입이다.** 정상 1개 + 비정상 2개(필수 누락, 허용값 위반)를 고정 문자열로 만들어 Parser에 넣는다. 모델이 실제로 이상한 JSON을 뱉을 때까지 기다리지 않는다. 실행할 때마다 결과가 같다.
  - **테스트에서 기대할 예외 타입을 정확히 알아야 한다.** `parser.parse()`를 테스트하면서 `ValidationError`를 기대하면 테스트가 **예외를 못 잡고 실패**한다. 교안 오류 2번 *"모든 실패를 ValidationError로 잡음"* 이 바로 이 실수. **예외는 호출 계층에 따라 바뀐다.**
  - **`loc`/`type`으로 판정 — 지난 과정 6-1강과 같은 원칙.** 오류 메시지 문구가 아니라 `type == "missing"`, `type == "literal_error"`처럼 구조화된 값으로 판정하면 라이브러리 버전이 바뀌어도 테스트가 안 깨진다. 교안도 *"세부 표현이 달라질 수 있다"* 고 명시했다.
  - **`include_input=False`와 "실패한 원문 전체를 출력하지 않는다"** — 오류 로그에 원본 입력이 딸려 나가지 않게 한다. LLM 출력에 사용자 입력이나 민감정보가 섞여 있을 수 있으니, 오류 기록에도 **최소 정보 원칙**을 적용한다.
  - **"실패를 확인하는 것 또한 실습의 정상 결과"** — 교안의 이 문장이 부정 테스트의 본질이다. 필수 필드 누락이 **실패해야 정상**이다. 통과했다면 그게 버그다.

### 5-3강 : 출력 복구와 retry 연결
- **핵심 개념**:
  - 첫 출력 `{"category":"기타","needs_code":false}` → 문제 두 개: `category`가 허용값 아님 + `summary` 없음.
  - **그대로 쓰면** 조건 분기가 예상과 다르게 동작한다. **`category="개념"`을 임의로 넣는 것도** 모델의 의도를 확인하지 않은 추측이다.
- **한 번만 복구하는 흐름**:
  ```
  실패한 출력
  → 첫 Parser 검증
  → 실패하면 수정 Prompt를 한 번 실행
  → 수정 문자열을 같은 Parser로 재검증
  → 성공 객체 또는 최종 실패
  ```
  - `MAX_REPAIR_ATTEMPTS = 1`
- **`try_parse()`**:
  - 성공하면 객체, 실패하면 `None`. 오류 내용을 **고치지 않고** 성공 여부만 알려준다.
  - **첫 검증이 성공하면 수정 요청을 보내지 않는다** — 불필요한 모델 호출 생략.
- **수정 Prompt에 넣는 세 가지**:
  | 변수 | 역할 |
  |---|---|
  | `format_instructions` | Parser가 요구하는 필드와 형식 |
  | `question` | 원래 질문 (의미 유지) |
  | `broken_output` | 첫 검증에 실패한 문자열 |
  - system: *"설명 없이 올바른 JSON 객체로 다시 작성하세요"* — 자유 작문이 아니라 **범위를 좁힌 수정**.
- **두 Parser의 역할 분리**:
  - `StrOutputParser` — `AIMessage` → `str` (본문 꺼내기)
  - `PydanticOutputParser` — JSON `str` → Pydantic 객체 (필드·값 검증)
  - 수정 체인 `repair_prompt | model | StrOutputParser()`의 결과는 **아직 문자열**이다. 반드시 재검증해야 한다.
- **최종 분기**:
  - `final_result is None`이면 실패 문구, 아니면 필드 사용. **`None` 확인 전에 `final_result.category`에 접근하지 않는다.**
  - 최종 실패는 프로그램 중단이 아니라, **검증되지 않은 값을 사용하지 않고 분명한 실패 상태로 종료**한다는 뜻.
- **QA 체크포인트**:
  - **복구 1회 제한 = 지난 과정 8-2강 재시도 1회와 같은 사상.** 교안: *"끝없이 다시 요청하면 실행 시간과 API 사용량이 계속 늘어나고, 언제 끝나는지 예측하기 어려워집니다."* **비용 상한과 종료 보장**이 동시에 걸려 있다.
  - **"수정했습니다"라는 말 ≠ 성공** (교안 오류 7번). 성공 판정은 **같은 Parser가 객체를 반환했는가**로만 한다. 첫 검증과 재검증에 **같은 oracle(판정 기준)** 을 쓰는 것 — 다른 규칙을 쓰면 수정 결과가 원래 스키마를 만족하는지 알 수 없다.
  - **복구가 품질 문제를 가릴 수 있다 — LLM Eval에서 중요한 관점.** 복구 로직이 있으면 최종 형식 준수율은 높게 나오지만, 그건 **1차 출력 품질이 좋아서가 아니라 복구가 메꿔서**일 수 있다. 평가할 때는 **"1차 형식 준수율"과 "복구 후 형식 준수율"을 분리해서 집계**해야 모델·프롬프트의 진짜 성능이 보인다. 복구 발생률 자체도 품질 지표다.
  - **첫 출력이 정상이면 복구를 생략하는 분기도 테스트 대상.** "정상 입력인데 복구 호출이 발생하는가?"는 비용 누수 버그다. 해피 패스에서 **모델 호출 횟수 0회**를 확인해야 한다. 지난 과정 8-2강에서 재시도 로직을 **호출 횟수**로 검증했던 것과 같은 방식.
  - **연습문제 2·3이 모델 없이 고정 문자열로 복구 흐름을 검증한다** — `repaired_output`을 미리 준비해서 "복구 성공"과 "복구 후에도 실패" 두 경로를 둘 다 결정적으로 재현한다. 복구 로직의 **분기 커버리지**를 비용 없이 채우는 방법.

## 6장. Retriever를 활용한 외부 문서 연결

### 6-1강 : Document 구조와 metadata 활용
- **핵심 개념**:
  - LLM 앱이 참고할 정보는 Markdown, 사내 규정, FAQ, DB 행 등 **형태가 제각각**이다. 이걸 그대로 처리하면 본문과 출처 위치를 매번 다시 확인해야 한다.
  - LangChain의 `Document`는 이것들을 **일정한 구조로 묶는다.**
  | 영역 | 저장하는 값 | 자료형 |
  |---|---|---|
  | `page_content` | 문서의 **실제 본문** (검색 뒤 Prompt 참고 문맥) | `str` |
  | `metadata` | 본문을 **설명하는 부가 정보** (ID, 제목, 출처, 키워드) | `dict` |
  - 본문과 metadata는 **함께 이동하지만 역할은 다르다.** 답변 근거는 `page_content`, 구분·표시 정보는 `metadata`.
- **metadata 필드 설계**:
  - 이번 실습: `document_id` · `title` · `source` · `keywords`
  - **같은 의미의 값은 모든 문서에서 같은 키**에 넣는다. 한 문서는 `source`, 다른 문서는 `file`, 또 다른 문서는 `origin`이면 formatter가 문서마다 다른 코드를 실행해야 한다.
  - 키가 반드시 있으면 `metadata["title"]`, 없을 수 있으면 `metadata.get("author", "작성자 없음")`.
  - 교안: *"metadata는 검색 정확도를 자동으로 높이는 마법의 정보가 아닙니다."* 다음 단계가 **실제로 읽고 사용하는 필드**를 일관되게 저장하는 게 핵심.
- **formatter**:
  - `format_document()` — `[doc-001 | LCEL 기초 | langchain_intro.md]` + 본문
  - `format_documents()` — 여러 문서를 **빈 줄로 구분**해 하나의 문자열로
  - **formatter는 원본 Document를 변경하지 않는다.** 표시·Prompt용 문자열을 새로 만들 뿐.
- **범위 명시**:
  - 청킹, 임베딩, Vector DB는 **이번 강의에서 다루지 않는다** — 후속 RAG 과목.
  - `page_content`에 리스트를 넣지 않는다. 여러 문서는 Document 여러 개를 **리스트**에 담는다.
- **QA 체크포인트**:
  - **지난 과정 4-2강과 정확히 같은 설계다.** 그때 손으로 만든 `document_id` / `content` / `metadata` 3분할 문서 계약이 LangChain에서는 `Document(page_content, metadata)`라는 표준 클래스로 나온다. 1장에서 본 "직접 구현 → 표준 부품" 패턴이 Document에서도 반복된다.
  - **metadata 키 일관성 = 데이터 계약.** `source`/`file`/`origin`이 섞이는 건 스키마가 없는 데이터에서 가장 흔한 품질 결함이다. 문서셋을 만들 때 **모든 문서가 같은 키 집합을 갖는지** 검증하는 단계가 있어야 한다. 5장의 Pydantic 스키마처럼 metadata에도 규칙을 먼저 정한다.
  - **`get()` 대체값의 양면성.** 교안 formatter는 `get("document_id", "ID 없음")`으로 키가 없어도 조용히 넘어간다. **화면 표시용**이면 괜찮지만, `document_id`가 **필수 계약**이라면 이 방식은 누락을 **가린다.** 지난 과정 3-2강에서 *"필수 필드는 대괄호로 읽어 KeyError가 계약 위반을 드러내게 한다"* 고 했던 것과 대비된다. **필수 필드는 대괄호(fail loud), 선택 필드만 get(대체값)** 으로 구분하는 게 안전하다.
  - **API 호출 없이 매번 같은 결과** — 문서 개수와 metadata가 코드에 고정돼 있어 formatter 출력이 결정적이다. 다음 강의 Retriever의 검색 결과를 검증할 때 **기대 문서 ID 목록**을 정답으로 쓸 수 있는 기반이 된다.
  - **청킹·임베딩·Vector DB를 명시적으로 범위에서 뺀 것** — 지금 만든 건 검색 대상의 **모양**이지 검색 기능이 아니다. 지난 과정 4-2강 *"JSON 저장하면 바로 RAG 된다는 오해"* 와 같은 경계선이다.
