## 💡 오늘의 학습 총평

- **핵심 통찰: LangChain은 지난주에 손으로 짰던 것을 표준 부품으로 만든 것이다**
  - 지난주 `09. Data Pipeline & FastAPI` 7장에서 직접 구현했던 것들이 LangChain에서 그대로 부품 이름을 달고 나왔다.

    | 지난주 (직접 구현) | LangChain |
    |---|---|
    | 7-1강 `build_prompt()` — `[근거]`/`[질문]` 문자열 조합 | `ChatPromptTemplate` |
    | 7-2강 `call_external_json()`, `call_ollama()` | `ChatModel` (`ChatOpenAI` 등) |
    | 7-2강 `data.get("answer")` + `isinstance` 검사 | `Output Parser` |
    | 7-2강 "어댑터 계층은 모델이 늘어날 때 분리" | `langchain-core`(규격) + `langchain-openai`(어댑터) |

  - 지난주 교안이 *"공급자 인터페이스나 여러 어댑터 계층은 구현하지 않으며, 모델 종류가 실제로 늘어날 때 분리해도 늦지 않습니다"* 라고 미뤄둔 바로 그 계층을, **남이 미리 만들어둔 것**이 LangChain이다.
  - 지난주 코드와 대응시켜 설명을 들으니 새 프레임워크인데도 흐름이 덜 낯설었다. 부품의 **이름**은 새로 배워야 하지만, **왜 나눴는지**는 지난주 내용과 이어졌다.

- **두 번째 통찰: LangChain은 모델을 똑똑하게 만들지 않는다**
  - 1-1강의 가장 중요한 문장 — *"LangChain을 사용한다고 같은 모델의 지식이나 답변 능력이 자동으로 좋아지지는 않습니다."*
  - 바뀌는 건 **모델이 아니라 코드를 짜는 방식**이다. 첫 예제에서는 오히려 코드가 더 길어진다. 장점은 한 번의 호출을 짧게 만드는 게 아니라 **단계가 늘어날 때 바뀌는 지점을 분리**하는 데 있다.
  - LLM Eval 관점에서 중요한 통제 변수다. "LangChain으로 바꿨더니 답변이 좋아졌다"는 착각일 가능성이 높고, 달라졌다면 프롬프트가 미묘하게 바뀌었거나 다른 변수가 섞인 것이다.

- **세 번째 통찰: 결정적인 부분과 비결정적인 부분이 분리된다**
  - `Prompt`(결정적) → `Model`(비결정적) → `Parser`(결정적)
  - 세 부품으로 나누니까 **Prompt와 Parser는 모델 없이, 비용 0원으로, 매번 같은 결과로** 테스트할 수 있게 됐다.
  - 2-2강 연습문제가 전부 `AIMessage(content="...")`를 직접 만들어 Parser에 넣는 방식이었는데, 이게 **LangChain판 MockTransport**다. 지난 과정 1~8장 내내 쓰던 패턴이 그대로 넘어왔다.

- **향후 계획 및 다짐**
  - 10/1 시작하는 2차 프로젝트는 **팀 프로젝트**이고 LangChain을 쓰게 될 것이다. 그 전까지 LangChain 10장을 끝내는 것이 목표.
  - 팀 프로젝트에서 내가 기여할 수 있는 지점은 **품질·검증 쪽**이다. 오늘 배운 것 중 바로 가져갈 것:
    - Prompt와 Parser는 모델 없이 테스트할 수 있다 → 팀 코드에 **비용 0원 단위 테스트**를 붙이는 역할
    - 파싱 실패를 빈 값으로 덮지 않고 **실패율을 따로 집계**하는 것
    - Parser 뒤에서 사라지는 **토큰 사용량·지연 시간**을 설계 단계부터 챙기는 것
    - 팀원마다 로컬 환경변수가 달라 결과가 갈리지 않도록 **`uv.lock` 공유와 실행 전 모델명 확인**

## 📊 어제보다 나아진 점

- 새 프레임워크를 문법부터 외우기보다, AI에게 **지난주 교안 코드와 대응시켜 설명**해 달라고 요청해서 전체 흐름부터 잡았다. 부품 이름이 지난주 어떤 코드에 해당하는지 알고 나니 1~2장이 덜 막막했다.

- 아직은 코드를 직접 짜기보다 **설명을 듣고 개념과 흐름을 이해하는 단계**다. 이해한 것과 손으로 짤 수 있는 것은 다르다는 걸 인정하고, 팀 프로젝트 전까지 진도를 끝까지 따라가는 데 집중한다. ★

## 🎯 오늘 배운 핵심 내용

## 1장. LangChain 애플리케이션 구조와 개발 환경

### 1-1강 : 단순 API 호출과 LangChain 앱 구조 비교
- **핵심 개념**:
  - LangChain은 **모델을 대신하는 또 다른 AI가 아니다.** LLM 앱의 여러 작업을 **역할별 구성 요소로 나누고 연결하는 프레임워크**다.
  - 식당 비유 — 직접 호출은 한 사람이 주문·조리·포장을 다 하는 방식, LangChain은 주문서·조리·포장 담당을 나눈 방식. 작은 식당은 한 사람이 빠르고, 메뉴가 많아지면 나누는 게 관리하기 쉽다.
- **직접 호출의 세 가지 책임**:
  - `입력 준비`(system/user 메시지 직접 작성) → `모델 실행`(`client.chat.completions.create`) → `출력 정리`(`response.choices[0].message.content`)
  - 흐름이 눈에 바로 보이는 장점. 대신 프롬프트나 응답 구조가 바뀌면 **세 줄을 전부 다시 봐야** 한다.
- **LangChain의 세 부품**:
  | 부품 | 받는 값 | 내보내는 값 | 역할 |
  |---|---|---|---|
  | Prompt | 질문이 담긴 입력값 | 역할별 메시지 | 모델에게 보낼 내용을 만든다 |
  | Model | 역할별 메시지 | `AIMessage` | LLM을 호출해 응답을 만든다 |
  | Parser | `AIMessage` | 문자열 등 | 앱에서 쓰기 쉬운 값으로 바꾼다 |
  - **`model.invoke()`의 결과는 문자열이 아니라 `AIMessage` 객체.** 답변 본문과 함께 호출 관련 부가 정보가 들어갈 수 있다.
  - OpenAI SDK의 `user`와 LangChain의 `human`은 **같은 위치**. 이름만 다르다.
- **나중에 붙일 부품 (이번엔 이름과 위치만)**:
  - `Retriever`(6장, 외부 문서 검색) / `Memory`(7장, 이전 대화 반영) / `Callback`(8장, 실행 이벤트 관찰)
  - Retriever·Memory는 **Prompt 앞쪽**에 정보를 더하고, Callback은 **전체 실행을 관찰**하는 위치에 붙는다.
  - 교안 원칙: *"처음부터 모든 구성 요소를 한 프로그램에 넣지 마세요."* 기본 세 단계가 동작하는지 확인한 뒤 필요한 것만 추가.
- **선택 기준**:
  - 직접 호출이 맞는 경우 — 질문 하나에 문자열 하나 / 프롬프트·형식이 거의 안 바뀜 / API 동작 빠른 확인
  - LangChain이 맞는 경우 — 여러 프롬프트를 공통 형식으로 관리 / 모델·출력 형식 교체 가능성 / Retriever·Memory 연결 계획
  - **어떤 방식이 좋은지는 프레임워크 이름이 아니라 프로그램의 변경과 확장 요구로 판단한다.**
- **QA 체크포인트**:
  - **"두 답변이 글자 단위로 같아야 하나?" → 아니다.** 교안의 검증 기준은 ① 질문에 맞는 답변을 반환하는가 ② Prompt/Model/Parser 역할이 분리돼 있는가. **정확 일치(exact match) 대신 구조·형식·의미로 판정**하는 것이 LLM 앱 테스트의 가장 기본적인 전환이고, 앞으로 LangChain 테스트 전부가 이 원칙 위에 선다.
  - **프레임워크 교체 ≠ 품질 향상.** 비교 실험에서 프레임워크 변경과 프롬프트 변경을 반드시 분리해야 한다. 둘이 섞이면 무엇이 결과를 바꿨는지 알 수 없다.
  - **실습이 API를 두 번 호출한다.** 같은 질문을 두 방식으로 비교하니 실행할 때마다 2회 과금. 교안이 *"반복 실행이 필요하지 않다면 결과를 확인한 뒤 바로 종료하세요"* 라고 굳이 적어둔 이유. 이 교안은 끝까지 **API 호출 횟수를 의식하게** 설계돼 있다.
  - **"LangChain 썼더니 코드가 더 길어짐"은 오류가 아니다** (교안 오류 5번). 첫 예제에서 추상화 비용이 이익보다 큰 건 자연스럽다 — 오버엔지니어링을 경계하는 판단 기준이 된다.

### 1-2강 : 패키지 구조와 개발 환경 설정
- **핵심 개념**:
  - LangChain은 하나의 거대한 패키지에 모든 제공자 코드를 넣지 않는다. **공통 기능과 제공자별 연결 코드를 분리**한다.
  - 휴대폰 충전기 비유 — `langchain-core`는 USB-C 같은 **공통 규격**, `langchain-openai`는 그 규격에 맞춘 **OpenAI용 어댑터**.
- **패키지별 역할**:
  | 설치 이름 | 역할 | import |
  |---|---|---|
  | `langchain` | 상위 수준 기능 | 후속 장에서 |
  | `langchain-core` | Prompt·Message·Parser 공통 부품 | `langchain_core` |
  | `langchain-openai` | OpenAI 모델을 ChatModel로 연결 | `langchain_openai` |
  | `openai` | OpenAI 공식 SDK | `openai` |
  | `python-dotenv` | `.env` 읽기 (**LangChain 아님**) | `dotenv` |
  - **설치 이름 ≠ import 이름.** 하이픈이 언더스코어로 바뀌고, `python-dotenv`는 아예 `dotenv`. 모르면 "설치는 됐는데 import가 실패했다"고 오해한다.
- **uv 환경 구성 (3단계)**:
  - `uv python install 3.12` → `uv sync --locked --python 3.12` → `uv run python 실습.py`
  - `Activate.ps1` 실행이나 PowerShell 실행 정책 변경은 **필수가 아니다.** `uv run`이 `.venv`의 Python을 알아서 쓴다.
  - `--locked` = `uv.lock`에 적힌 **정확한 버전**대로만 설치. 간접 의존성까지 고정된다.
  - 수업 기준: Python 3.12 / langchain 1.3.14 / langchain-core 1.5.1 / langchain-openai 1.4.1 / openai 2.48.0 / pydantic 2.13.5
  - 배포 ZIP에 `uv init`을 다시 실행하지 않는다. 새 프로젝트를 만들 때만 `uv init --bare` → `uv add`.
- **VS Code 인터프리터 선택 (가장 흔한 함정)**:
  - `uv run`은 `.venv`를 쓰는데 **VS Code 실행 버튼은 다른 Python을 쓸 수 있다.** 그러면 터미널에선 되고 VS Code에선 `ModuleNotFoundError`.
  - `Ctrl+Shift+P` → `Python: Select Interpreter` → `.venv\Scripts\python.exe`
  - 확인은 `print(sys.executable)` — 경로에 `.venv`가 있어야 한다.
  - `ModuleNotFoundError`가 나면 **패키지 설치보다 인터프리터 선택을 먼저** 확인한다.
- **API Key 관리**:
  - 프로젝트 루트 `.env`에 `OPENAI_API_KEY`, `OPENAI_MODEL` 저장. 따옴표 불필요, 등호 앞뒤 공백 금지.
  - `.gitignore`에 `.env`, `.venv/`, `__pycache__/` 추가.
  - 키는 존재 여부만 `bool(os.getenv(...))`로 확인하고 **값 자체는 절대 출력하지 않는다.**
  - Windows에서 확장자 숨김 때문에 실제 파일명이 `.env.txt`가 되는 경우 주의.
- **첫 ChatModel 호출**:
  - `ChatOpenAI(model=..., reasoning_effort="none", use_responses_api=False, max_completion_tokens=600, timeout=30, max_retries=0)`
  - `response.content`로 본문 확인. 문장은 매번 달라지므로 **인증 오류 없이 문자열이 나오는지**가 성공 기준.
- **QA 체크포인트**:
  - **`max_retries=0`을 명시한 이유가 중요하다.** 라이브러리 기본값은 버전마다 다를 수 있고 조용히 재시도가 켜져 있을 수 있다. 그러면 ① 한 번 호출했는데 여러 번 과금될 수 있고 ② 지연 측정에 재시도 대기가 섞여 수치가 왜곡되고 ③ 실패가 재시도에 가려져 원인을 못 본다. 지난주 8-2강 "재시도는 명시적으로, 대상을 골라서, 최대 1회"와 같은 맥락 — **성능 측정·테스트 시에는 숨은 재시도를 반드시 통제**해야 한다. 의도적인 재시도는 9장 `with_retry`에서.
  - **터미널 환경변수가 `.env`보다 우선한다.** 교안에 조용히 박힌 함정 — `load_dotenv()`의 기본 동작에서 이미 설정된 환경변수가 이긴다. `.env`를 고쳤는데 결과가 안 바뀌는 상황이 여기서 나온다. 지난주 7-2강 `run_all.py`가 `os.environ["LLM_MODE"] = "mock"`을 **강제로 덮어쓴** 이유와 같은 문제. **"실행 전에 선택된 모델명을 확인하라"** 를 체크리스트에 넣는다.
  - **`--offline` 모드 = 비용 0원 환경 검사.** 환경 문제인지 API 문제인지를 **비용 없이 먼저 분리**하는 mock-first 원칙이 그대로 들어와 있다.
  - **버전 고정 = 재현 가능한 실험 환경.** 라이브러리 마이너 버전 하나로 파싱 동작이 달라지면 비교 실험 전체가 무효가 된다. `uv.lock`, `.python-version`, `pyproject.toml` 세 파일을 함께 보관.
  - **키 노출 대응의 두 가지 착각**: 키 일부를 `****`로 가려도 해결되지 않는다(폐기 후 재발급) / `.gitignore` 추가는 **앞으로의 추적만** 막고 이미 올라간 키를 지우지 않는다.

## 2장. Prompt Template / Model / Output Parser 기본 체인

### 2-1강 : PromptTemplate과 ChatPromptTemplate
- **핵심 개념**:
  - Template = **편지 양식.** 문장 구조는 그대로 두고 받는 사람 이름만 바꾼다. `{중괄호}`가 입력 변수.
  - 쓰는 이유 — 공통 지시문을 한 곳에서 관리 / 입력만 바꿔 재사용 / 필요한 입력을 변수 이름으로 확인 / 메시지 순서를 일정하게 유지
- **PromptTemplate — 결과가 문자열 하나**:
  - `PromptTemplate.from_template("주제: {topic}\n독자 수준: {audience}...")` → `format(topic=..., audience=...)` → `str`
  - `from_template()`이 중괄호를 알아서 변수로 인식한다.
  - 필요한 변수가 기억 안 나면 `template.input_variables`로 확인.
  - 입력값 앞에 `독자 수준:` 같은 라벨을 붙이면 값이 바뀌어도 **한국어 조사가 어색해지지 않는다.**
- **ChatPromptTemplate — 결과가 역할별 메시지 목록**:
  - `ChatPromptTemplate.from_messages([("system", "..."), ("human", "{question}")])` → `format_messages(...)` → `[SystemMessage, HumanMessage]`
  - `system` = 모든 질문에 공통으로 따를 역할과 답변 원칙 / `human` = 이번 실행의 질문
  - 답변 원칙을 바꾸려면 **system 한 곳만** 수정하면 된다.
  - `from_messages()`에 넣은 목록 순서가 **실제 전달 순서**.
- **두 Template 비교**:
  | | PromptTemplate | ChatPromptTemplate |
  |---|---|---|
  | 결과 | 문자열 하나 | 역할별 메시지 목록 |
  | 역할 구분 | 문자열 안에서 직접 | system/human으로 보존 |
  | 메서드 | `format()` | `format_messages()` |
  | 적합 | 단순 텍스트 가공 | 채팅 모델 입력 |
  - 어느 쪽이 항상 좋은 게 아니라 **다음 단계가 무엇을 받는지** 보고 고른다.
- **자주 걸리는 오류**:
  - 필수 변수 누락 → `input_variables`와 실제 전달 키 비교
  - 변수 이름 불일치 → `{question}`에 `query=`를 넘기면 안 채워짐. 뜻이 같아도 **이름이 다르면 다른 변수**
  - 중괄호를 문자 그대로 쓰려면 **두 번** 작성: `'{{"answer": "{value}"}}'`
  - Template 만들었는데 답변이 없음 → 정상. Template은 **메시지만 만든다.**
- **QA 체크포인트**:
  - **Prompt는 모델 없이 테스트할 수 있다 — 오늘 가장 중요한 테스트 관점.** 실습.py가 API Key 없이 실행된다는 건, `format_messages()` 결과를 **비용 0원, 매번 같은 결과**로 `assert`할 수 있다는 뜻이다. 역할 순서, 변수 치환 결과, `input_variables`를 검증하면 프롬프트 수정 시 **의도치 않은 변경을 잡는 회귀 테스트**가 된다.
  - **Template은 값을 정확히 치환하지만 자연스러움·사실성은 확인하지 않는다.** 교안이 *"완성된 Prompt를 모델 호출 전에 직접 읽어보라"* 고 한 것 = **Prompt 자체가 테스트 대상**이라는 뜻. 입력값 조합별로 완성된 Prompt를 뽑아 검수하는 작업은 게임 QA의 **로컬라이징 문자열 검수**와 같다 — 변수 치환 후 문장이 자연스러운지, 조사가 맞는지.
  - **Template이 하지 않는 일을 명시한 것이 좋다** — 모델 호출 / 사실성 확인 / **개인정보 제거** / 형식 변환. 특히 세 번째: 사용자가 입력에 전화번호를 넣으면 Template은 그대로 모델에 보낸다. **민감정보가 섞인 입력 케이스**를 테스트 목록에 넣어야 한다.
  - **중괄호 이스케이프는 전형적인 경계 케이스.** JSON 예시를 프롬프트에 넣는 순간 `{`가 변수로 오인된다. 이 버그는 JSON을 넣기 전까지 절대 드러나지 않으므로, **프롬프트에 코드·JSON·템플릿 문법이 섞이는 케이스**를 미리 테스트해야 한다.

### 2-2강 : ChatModel과 Output Parser 연결
- **핵심 개념**:
  - 흐름: `입력 딕셔너리 → [ChatPromptTemplate] → 메시지 목록 → [ChatOpenAI] → AIMessage → [Parser] → str/list/dict`
  - 파이프라인에서 오류가 나면 **앞 단계가 무엇을 내보냈고 다음 단계가 무엇을 기대했는지** 확인한다.
  - `AIMessage`에는 부가 정보가 있으므로, 그게 필요하면 **Parser를 붙이기 전에** 보관한다.
- **Parser 3종**:
  | Parser | 요청할 형식 | 결과 | 적합 |
  |---|---|---|---|
  | `StrOutputParser` | 일반 문장 | `str` | 설명, 요약 |
  | `CommaSeparatedListOutputParser` | `A, B, C` | `list[str]` | 짧은 키워드, 태그 |
  | `JsonOutputParser` | JSON | `dict`/`list` | 분류 결과, 여러 필드 |
- **Parser는 모델을 조종하지 않는다 (가장 중요)**:
  - *"Parser는 모델이 자동으로 형식을 지키게 만드는 장치가 아닙니다."*
  - 두 단계가 따로 필요하다 — ① `get_format_instructions()`로 원하는 형식을 **Prompt에 요청** ② 돌아온 응답을 Parser로 **해석**
  - 모델이 안내를 무시하면 Parser는 실패한다.
- **List Parser의 한계**:
  - 항목 안에 쉼표가 들어가면 깨진다. **구조가 단순한 짧은 키워드 목록**에만 쓴다.
- **JSON Parser는 변환만 한다**:
  - `JsonOutputParser`는 **JSON 문자열 → Python 값**까지만. `category`/`reason` 키의 존재는 보장하지 않는다.
  - 순서: `isinstance(result, dict)` 확인 → 필요한 키 존재 확인 → 그 다음에 값 읽기. 이 순서를 지키면 `KeyError`를 피한다.
  - 필드 타입을 엄격하게 검증하는 건 5장 Pydantic에서.
- **오류는 조용히 삼키지 않는다**:
  - `OutputParserException`을 잡되 **응답 전체가 아니라 오류 종류만** 출력.
  - *"오류를 무시하고 빈 딕셔너리로 바꾸면 데이터 문제를 놓칠 수 있습니다."*
- **Parser 선택 순서**:
  - 필요한 Python 자료형 결정 → 맞는 Parser 선택 → 형식 안내를 Prompt에 포함 → 응답 변환 → **필요한 키와 값 확인**
- **QA 체크포인트**:
  - **`AIMessage`를 직접 만들어 Parser를 테스트 = LangChain판 MockTransport.** 모델을 부르지 않고 원하는 응답을 가짜로 만들어 Parser만 검증한다. 연습문제 3개가 전부 이 방식이다. 이걸로 **이상한 응답을 직접 주입**해 테스트할 수 있다:
    | 가짜 AIMessage | 검증하는 것 |
    |---|---|
    | 정상 JSON | 해피 패스 |
    | JSON 앞에 설명 문장 | 모델이 사족을 붙였을 때 |
    | 키 하나 빠진 JSON | 필수 키 검사 로직 |
    | 깨진 JSON | `OutputParserException` 처리 |
    | 항목에 쉼표가 든 리스트 | List Parser 경계 케이스 |
    모델이 실제로 이상하게 답할 때까지 기다리지 않는다 — **결정적 결함 주입.**
  - **"JSON 변환 ≠ 스키마 검증" — 같은 원칙의 세 번째 만남.** 지난 과정 2-1강 *"JSON 파싱 성공 ≠ API 호출 성공"*, 7장 TIL *"JSON 문법 ≠ Schema 구조 ≠ 비즈니스 사실"*, 그리고 오늘 *"JsonOutputParser 성공 ≠ 필요한 키 존재"*. **형식이 맞다와 내용이 맞다는 다른 계층**이며, 각 계층마다 별도 검증이 필요하다.
  - **Parser 오류를 빈 값으로 대체하지 말 것 = fail loud.** 지난 과정 4-1강 "억지로 채우지 않는다", 7-2강 "오타 모드를 조용히 기본값으로 바꾸지 않는다"와 같은 원칙. LLM 평가 파이프라인에서 파싱 실패를 빈 dict로 처리하면 그 케이스가 "오답"이 아니라 **"누락"으로 사라져 정확도가 부풀려진다.** 파싱 실패율은 **따로 집계해야 하는 품질 지표**다.
  - **Parser가 부가 정보를 지운다** (교안 오류 6번). `AIMessage`의 토큰 사용량·메타데이터가 `StrOutputParser`를 거치면 사라진다. LLM Eval에서 **토큰·지연을 측정하려면 Parser 적용 전 `AIMessage`를 별도 보관**해야 한다. 지난 버그 트리아지 프로젝트의 모델별 토큰 비교를 LangChain으로 옮기면 여기서 데이터가 날아갈 수 있다.
  - **모델 답변 문구를 정답과 글자 단위로 비교하지 않는다.** 교안이 *"최종 자료형과 필요한 값이 들어 있는지 확인합니다"* 라고 명시. 1-1강의 exact match 금지 원칙이 Parser 단계에서도 그대로 적용된다.
  - **`EXAMPLE` 하나씩 실행 = 비용 통제 설계.** text/list/json을 한 번에 돌리면 3회 과금. 실제 API를 부르는 테스트는 **최소한으로, 의도적으로** 돌린다.

| 2-1 | Template을 만들면 답변이 나온다 | 메시지만 만든다. 모델 호출은 별도 |
