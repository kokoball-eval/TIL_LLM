## 💡 오늘의 학습 총평

- **핵심 통찰: 10장 통합 앱은 1~9장 부품의 "조립 설명서"였다**
  - 오늘로 LangChain 과목 10장까지 진도를 마쳤다. 10-1강의 8단계 설계표를 보니, 지금까지 따로 배운 부품이 각자 한 칸씩 자리를 차지하고 있었다.

    | 10-1강 단계 | 하는 일 | 처음 배운 곳 |
    |---|---|---|
    | `input_check` | 빈 질문·세션 값 확인 | 4장 입력 검증 |
    | `history_read` | 현재 세션의 이전 대화 조회 | 7장 Memory |
    | `retrieve` | 질문과 관련된 문서 검색 | 6장 Retriever |
    | `prompt` | 질문 + 대화 + 문서로 메시지 구성 | 2장 Prompt Template |
    | `model_policy` | 모델 호출 + Retry/Fallback | 9장 오류 대응 |
    | `structured_parser` | 응답을 `QAResponse`로 검증 | 5장 구조화 출력 |
    | `local_trace` | 실행 기록 남기기 | 8장 관측 |
    | `history_save` | 검증된 질문·답변만 저장 | 7장 Memory |

  - 10-1강이 *"모든 기능을 한 함수에 넣어도 실행은 되지만, 어느 단계가 무엇을 받아 무엇을 반환하는지 확인하기 어려워진다"* 고 한 것이 이 과목 전체의 결론이다. 부품을 나눠 배운 이유가 **나중에 하나씩 바꾸고, 하나씩 검증하기 위해서**였다.

- **두 번째 통찰: 실패 경로를 "구현하기 전에" 테스트 사례로 정한다**
  - 10-1강은 앱을 만들기 전에 **정상 / 검색 0건 / 일시 오류 뒤 복구 / Primary 지속 실패** 4가지 경로의 기대 `status`와 `route`를 먼저 표로 고정했다.
  - 9-1강(Retry: 복구·소진·제외), 9-2강(Fallback: 정상·기능 저하·정책 밖 오류), 10-3강(normal·temporary·persistent)도 전부 **3~4개 경로를 표로 만들고, 결과값과 실제 호출 횟수를 같이 확인**하는 구조였다.
  - AI가 이 표를 QA의 테스트 케이스 표에 빗대 설명해 줘서 이해가 빨랐다. LLM 앱에서도 **기대 결과(오라클)를 먼저 정하고 구현하는 순서**가 그대로 쓰인다.

- **세 번째 통찰: 관측은 "바라보고", 오류 대응은 "제어한다"**
  - 10-3강의 정리 — *"관측 도구는 실행을 바라보는 역할이고, Retry와 Fallback은 실행을 제어하는 역할입니다."*
  - 8장의 Callback·Langfuse는 답변을 바꾸지 않고, 붙여도 모델 호출 횟수가 늘지 않는다. 반대로 Retry·Fallback은 결과와 호출 횟수를 바꾼다.
  - 그래서 **관측 도구가 실패해도 앱 결과는 바뀌면 안 된다.** 그리고 관측 실패를 막으려고 `chain.invoke()`까지 넓은 `try`로 감싸면, 진짜 모델 오류가 관측 실패처럼 숨어 버린다.

- **네 번째 통찰: 근거는 "대조"하고, 검증된 것만 "저장"한다**
  - 6-3강: 답변에 `[근거: doc-003]`이 붙어 있어도 그 ID가 실제 검색 결과에 있는지 확인해야 한다.
  - 10-2강: 모델이 `sources=["doc-999"]`를 돌려줘도 실제로 검색한 문서가 아닐 수 있다 → `set(result.sources).issubset(allowed_sources)`로 대조한다.
  - 7장·10장: 검증되지 않은 답변을 대화 기록에 저장하면, 그 잘못된 답이 **다음 대화의 입력으로 다시 들어간다.** 그래서 저장은 항상 검증 뒤에 한다.

- **다섯 번째 통찰: 지난 과정에서 배운 원칙이 오늘 또 이름만 바꿔 나왔다**

  | 지난 과정 (09-Data-Pipeline-FastAPI) | 오늘 (LangChain) |
  |---|---|
  | 8-2강 재시도는 명시적으로, 최대 1회 | 9-1강 `stop_after_attempt=2` = 최초 포함 2번, 재시도 최대 1번 |
  | 8-2강 POST(부작용 있는 요청)는 함부로 재시도하지 않음 | 9-1강 Retry는 모델 단계에만 좁게. 저장·전송 단계까지 감싸면 두 번 실행됨 |
  | 7-2강 mock / external / ollama가 같은 `QueryResponse` 반환 | 9-2강 Primary/Fallback이 같은 `UserAnswer`, 10-2강 offline/live가 같은 `QAResponse` 반환 |
  | 4-1강 판단 못 하는 값은 억지로 채우지 않는다 | 8-2·10-3강 토큰 정보가 없으면 0이 아니라 `None` / `not_available` |
  | 8-1강 `gather` 결과는 입력 순서 | 7장 history는 Human → AI 순서, 저장 순서가 곧 대화 순서 |

- **향후 계획 및 다짐**
  - 내일 **10/2(금) 2차 팀 프로젝트가 시작된다.** LangChain 10장을 프로젝트 전에 끝낸다는 목표는 지켰다.
  - 팀에서 품질·검증 쪽으로 기여한다면, 오늘 배운 것 중 바로 꺼낼 수 있는 것:
    - 10-1강처럼 **단계별 입출력 계약표 + 실패 경로 테스트 행렬**을 구현 전에 먼저 제안하기

|---|---|---|

| 근거 ID | 실제 검색 결과의 **부분집합인지** 확인 | 6-3, 10-2 |
| 대화 기억 답변 | 이전 정보("민지")를 참고했는지 **포함 여부**만 | 7-2 |

### 4. API 호출 횟수 — 오늘도 비용이 곧 테스트 설계 대상

| 실습 | 모델 호출 | 비고 | 근거 강의 |
|---|---|---|---|
| 키워드 Retriever | **0회** | 검색은 로컬 Python 코드 | 6-2 |
| retrieval chain | 1회 | 검색은 로컬, 답변 생성만 API | 6-3 |
| session별 history | **0회** | | 7-1 |
| 대화형 체인 | 3회 | student-a 2회 + student-b 1회 | 7-2 |
| Streaming + Callback | 1회 | Handler를 붙여도 1회 그대로 | 8-1 |
| Langfuse tracing | 1회 | `max_retries=0`으로 SDK 내부 재시도 끔 | 8-2 |
| Retry / Fallback | **0회** | 계획된 오류로 재현 | 9-1, 9-2 |
| 설계 계약 / 관측 사례 | **0회** | | 10-1, 10-3 |
| 문서 Q&A 앱 | offline **0회** / live 질문당 1회 | 검색 0건이면 모델 호출 안 함 | 10-2 |

**숨은 호출이 늘어나는 지점**

| 상황 | 실제 최대 요청 수 | 근거 강의 |
|---|---|---|
| `invoke()` 1번 + SDK 내부 Retry 켜짐 | 1번보다 많을 수 있음 | 8-2 |
| 바깥 `stop_after_attempt=2` × 내부 Retry(최초 + 2회) | **2 × 3 = 6회** | 9-1 |
| Retry 전부 소진 후 Fallback 모델 호출 | 위 횟수 + Fallback 호출 | 9-2 |
| Handler마다 체인을 따로 실행 | 모델 요청이 Handler 수만큼 늘어남 | 8-2 오류 6 |

→ 재시도는 **한 계층에서만** 관리하고, 나머지 계층은 끈다(`max_retries=0`). 운영에서 내부 Retry를 켠다면 곱해진 최대 요청 수·지연·비용을 계산해 기록해 둔다.

### 5. 실패 분류표 — 어떤 실패에 어떤 행동을 하나

| 상황 | 분류 | 올바른 행동 | 근거 강의 |
|---|---|---|---|
| 검색 결과 0건 | **실패 아님** | 빈 목록 `[]` 반환, 앱은 `not_found` / `local`로 종료, 모델 호출 안 함 | 6-2, 10-1, 10-2 |
| source filter로 전부 제외됨 | **정상 제외** | 오류로 처리하지 않음 | 6-2 오류 6 |
| 일시적인 모델 연결 실패 | 회복 가능 | 제한된 Retry (`TemporaryModelError`만) | 9-1 |
| 빈 질문, 잘못된 자료형 | 회복 불가 | **즉시 실패** — 반복해도 안 바뀜 | 9-1 |
| Retry 소진 | 회복 실패 | 마지막 원래 예외를 호출자에게 전달, 또는 허용된 Fallback | 9-1, 9-2 |
| Primary를 계속 쓸 수 없음 | 대체 가능 | Fallback → `status="degraded"`로 **표시** | 9-2 |
| 정책 밖 오류 (ValueError 등) | 숨기면 안 됨 | Fallback으로 보내지 않고 전파, `fallback_calls == 0` 확인 | 9-2 |
| 관측 도구(Langfuse) 실패 | 선택 기능 실패 | 로컬 관측으로 진행, **앱 결과는 그대로** | 8-2, 10-3 |

- **fail loud**: 마지막 실패를 빈 문자열로 바꾸면 실패가 성공처럼 보인다 (9-1 오해 6).
- **graceful degradation ≠ 장애 숨기기**: Fallback 결과는 정상처럼 보여 주지 않고 `degraded`와 `route`로 구분한다 (9-2 오해 4).
- **`exceptions_to_handle=(Exception,)` 금지**: 모든 오류를 받으면 입력 오류·코드 오류까지 "기능 저하"로 둔갑한다.

### 6. 부품 사이의 약속(계약)

| 연결 지점 | 약속 | 어기면 | 근거 강의 |
|---|---|---|---|
| Retriever 입출력 | `str` → `list[Document]` (0건이어도 리스트) | 딕셔너리 입력 오류, 단일 객체로 착각 | 6-2 오류 1·2 |
| 검색 결과 → Prompt | `{context}`에는 문서 객체가 아니라 **formatter 문자열** | Document 내부 표현이 그대로 들어감 | 6-3 오류 1 |
| 앞 단계 dict → Prompt | `question`, `context`, `history` 키 이름 = Prompt 변수 이름 | 변수 누락 오류 | 6-3 오류 2, 7-2 오류 2 |
| history → Placeholder | history 객체가 아니라 `list(history.messages)` | 형식 오류 | 7-2 오류 3 |
| Handler 연결 | 실행 config에 **리스트로** `{"callbacks": [handler]}` | 이벤트를 못 받음 | 8-1 오류 4·5 |
| session_id 전달 (기존 래퍼) | 입력 dict가 아니라 `config["configurable"]["session_id"]` | 세션 구분 실패 | 7-2 |
| Primary ↔ Fallback | **같은 Pydantic 출력 타입** (`UserAnswer`) | 화면이 경로마다 분기해야 함 | 9-2 |
| offline ↔ live 체인 | 둘 다 `dict[str, str]` → `QAResponse` | 앱이 체인 종류를 알아야 함 | 10-2 |
| `status` ↔ `sources` | grounded면 sources 필수, not_found면 sources 비어야 함 | `model_validator`에서 오류 | 10-2 |
| 모델 sources ↔ 실제 검색 | `sources ⊆ allowed_sources` | 지어낸 근거가 통과 | 10-2 |

### 7. 상태 격리와 순서 — 섞이면 안 되는 것, 먼저 하면 안 되는 것

**섞이면 안 되는 것 (격리)**
- **세션끼리**: 한 세션에 메시지를 추가해도 다른 세션의 메시지 수는 그대로여야 한다. 전역 history 하나를 공유하면 사용자 대화가 섞인다 (7-1 오류 4).
- **테스트 사례끼리**: 9-1·9-2·10-3은 사례마다 새 `state` dict와 새 체인을 만든다. 호출 횟수가 다음 사례로 누적되지 않게 하기 위해서다. 10-1강 — *"각 테스트는 새로운 앱 상태에서 시작해야 합니다."*
- **실행끼리**: 재사용하는 Callback Handler는 시작 이벤트에서 측정값을 초기화해야 한다 (8-1 연습문제 3).
- **동시 요청끼리**: 서버에서 Handler 하나를 여러 요청이 공유하면 `last_trace_id`가 다른 요청의 값으로 바뀐다 (8-2, 10-3).

**먼저 하면 안 되는 것 (순서)**
- `HumanMessage` → `AIMessage` 순서로 저장한다. 순서가 바뀌면 history와 실제 대화가 달라진다 (7-1 오류 3).
- 현재 질문은 **모델 호출 뒤에** 답변과 한 쌍으로 저장한다. 호출 전에 넣으면 질문이 Prompt에 두 번 들어간다 (7-2 오류 4).
- `retrieve`는 `model_policy`보다 앞, `structured_parser`는 `history_save`보다 앞 (10-1강 순서 검증 코드).
- 검색 0건 확인은 모델 호출보다 앞. 0건인데 모델을 부르면 문서가 아닌 일반 지식으로 답할 수 있다 (10-1, 10-2).

**Claude가 짚어준 확인 포인트**: 10-1강 설계표는 `history_read`가 `retrieve`보다 앞이지만, 10-2강 구현 흐름표는 검색과 0건 확인이 먼저고 대화 조회가 4단계다. 교안이 이 차이를 따로 설명하지 않는다. **설계 문서와 구현 순서가 다를 때 어느 쪽이 기준인지 확인하는 것**도 QA가 할 일이다.

## 6장. Retriever를 활용한 외부 문서 연결

### 6-2강 : Retriever 인터페이스와 검색 질의
- **핵심 개념**:
  - **단순 호출**: 질문 → Prompt → Model → 답변
  - **검색 기반 호출**: 질문 → **Retriever가 관련 문서 검색** → 검색 결과를 Prompt에 전달 → Model → 문서를 참고한 답변
  - Retriever는 **답변을 쓰는 모델이 아니다.** 질문과 관련된 자료를 찾아 다음 단계에 넘기는 **검색 담당**이다.
  - Retriever의 약속: **질의 문자열(`str`)을 받아 Document 목록(`list[Document]`)을 돌려준다.**
    - 결과가 1건이어도 리스트로 돌려준다 → 0건·1건·여러 건을 같은 코드로 다룰 수 있다.
    - 관련 문서가 없으면 오류 대신 **빈 목록 `[]`** — *"빈 목록은 이 Retriever의 유효한 검색 결과입니다."*
- **키워드 점수로 만든 작은 Retriever**:
  - `keyword_score()` — 문서 metadata의 `keywords` 중 질의에 들어 있는 단어 수를 점수로 쓴다. 대소문자 차이는 `casefold()`로 없앤다.
  - `search_documents()` — 점수 0인 문서는 빼고, 점수 높은 순으로 정렬, **같은 점수면 원래 순서 유지**, `max_results`(기본 2)개까지 반환.
  - `RunnableLambda(retrieve)`로 감싸면 `retriever.invoke("질의")`로 실행할 수 있다. RunnableLambda는 실행 방식만 맞춰 줄 뿐, **검색 규칙은 함수가 정한다.**
  - `source_filter` — 특정 출처(`retriever_note.md`)의 문서만 남기고 점수 계산.
  - 교안이 분명히 선을 그음: 이 점수는 **학습용 단순 규칙**이지 의미 이해 점수가 아니다. 비슷한 뜻의 다른 단어는 찾지 못한다.
- **범위**: 임베딩, Vector DB, reranking, `BaseRetriever` 상속 구현은 후속 RAG 과목. Model도 연결하지 않는다.
- **QA 체크포인트**:
  - **동점일 때 원래 순서를 쓰는 정렬 `(-score, index)` = 결정성 확보.** 같은 입력이면 항상 같은 결과라서 `doc-003`, `doc-002`, 0건을 **고정 기대값으로 검증**할 수 있다. 정렬 기준이 불완전하면 동점 문서 순서가 실행마다 바뀌는 숨은 비결정성이 생긴다.
  - **0건을 실패로 판정하지 않는다.** "메모리는 어디에 저장하나요?" → 0건이 정답이다. source filter로 전부 걸러진 것도 정상 제외다(오류 6). 테스트에서 "결과가 비었다 = 실패"로 짜면 정상 동작을 결함으로 보고하게 된다.
  - **빈 결과에서 `results[0]`을 읽지 않는다** (오류 3) — 전형적인 경계값 결함. 0건 케이스는 테스트 목록에 반드시 넣는다.
  - **`casefold()` 정규화 = 입력 변형 테스트 대상.** "Retriever" / "retriever" / "RETRIEVER"가 같은 결과를 내는지 확인한다.
  - **`max_results`를 줄인다고 품질이 좋아지지 않는다** — Prompt에 들어갈 문서 수가 줄 뿐이다.
  - **source filter는 권한 검사가 아니다.** 문자열 비교일 뿐이라 보안 기능으로 오해하면 안 된다.

### 6-3강 : 기본 retrieval chain과 RAG 과목 경계
- **핵심 개념**:
  - 기본 retrieval chain이 하는 일은 두 가지 — ① 질문과 관련된 문서를 **검색** ② 검색된 문서를 **context로 넣어** 모델이 답하게 함.
  - 자료형 흐름: `str → list[Document] → dict → PromptValue → AIMessage → str`
  - 이번 강의의 핵심은 새 검색 알고리즘이 아니라 **Retriever의 출력이 Prompt 입력으로 어떻게 넘어가는지**다.
- **처리 다섯 단계**:
  | 단계 | 입력 | 출력 |
  |---|---|---|
  | 1. 검색 | 질문 문자열 | `list[Document]` |
  | 2. context 구성 | 검색된 문서 목록 | 문서 ID와 본문이 있는 문자열 |
  | 3. Prompt 구성 | 질문과 context | 역할별 메시지 |
  | 4. Model 호출 | 메시지 | `AIMessage` |
  | 5. Parser | `AIMessage` | 답변 문자열 |
- **검색 준비 딕셔너리 — 세 키의 역할이 다르다**:
  - `question` — 원래 질문 그대로
  - `documents` — **근거 문서 ID를 나중에 확인하기 위한** 원본 Document 목록
  - `context` — Prompt가 읽을 문자열. `[문서ID | 제목]\n본문` 형식, 여러 문서는 빈 줄로 구분
  - 검색 결과가 없으면 빈 문자열 대신 **"검색된 문서가 없습니다."** 를 넣어, "결과 없음"과 "본문이 비어 있음"을 구분한다.
- **체인 조립**:
  - `prepare_step = RunnableLambda(retrieve_and_prepare)` → `add_answer_step = RunnablePassthrough.assign(answer=prompt | model | parser)`
  - `assign()`이 준비 딕셔너리를 유지한 채 `answer`만 추가 → 최종 결과에 `question`, `documents`, `context`, `answer`가 **모두 남는다.**
  - system Prompt 규칙: 검색 문서만 사용해 두 문장 이하로 답 / 문서가 없으면 "제공된 문서에서 확인할 수 없습니다." / 답변 끝에 `[근거: 문서 ID]` 표시
- **과목 경계**:
  | 이번 장 | 후속 RAG 과목 |
  |---|---|
  | Document의 page_content와 metadata | 청킹 (긴 문서를 나누는 기준) |
  | 질의 문자열을 받는 작은 Retriever | 임베딩 (텍스트 → 벡터) |
  | 검색 결과를 context 문자열로 변환 | Vector DB 저장·검색 |
  | Retriever → Prompt → Model → Parser 연결 | 검색 방식·파라미터 조정, reranking |
  | 문서 ID를 포함한 기본 문서 Q&A | 검색 품질과 답변 품질 평가 |
  - 한꺼번에 넣지 않는 이유 — 결과가 틀렸을 때 **어느 단계가 원인인지 가리기 어렵기 때문**.
- **QA 체크포인트**:
  - **"근거 표시 ≠ 근거 정확" (오류 7).** 답변에 `[근거: doc-003]`이 있어도 그 ID가 실제 `result["documents"]`에 있는지 대조해야 한다. 교안: *"근거 표시 요청만으로 정확성이 보장되지는 않습니다."* 지난 TIL의 "형식 준수 ≠ 내용 정답"이 **근거 표시**에서 또 나왔다.
  - **결정적 부분에 assert를 건다.** 검색 결과 `doc-003`은 코드가 정하므로 고정값으로 검증하고, 답변 문구는 매번 달라질 수 있으니 비교하지 않는다.
  - **`assign()`으로 중간 산출물을 전부 남기는 설계 = 관찰 가능성.** 답만 남으면 틀렸을 때 검색이 틀렸는지 생성이 틀렸는지 알 수 없다. `documents`·`context`가 남아 있어야 **결함 위치를 단계별로 좁힐 수 있다.**
  - **"단계를 한 번에 늘리지 않는다"는 교안의 학습 순서 = 결함 격리 원칙.** 청킹·임베딩·Vector DB를 동시에 넣으면 원인 분리가 불가능해진다. 비교 실험에서 변수를 하나씩 바꾸는 것과 같은 이유다.
  - **호출 횟수 혼동 주의 (오류 6).** 검색은 로컬, OpenAI 요청은 답변 생성 1회뿐이다.
  - **Key가 없으면 Model을 만들기 전에 종료 (오류 5)**, Key를 코드에 직접 쓰지 않기 (오류 4) — 매 강의 반복되는 보안 기본값.

## 7장. Memory와 대화 맥락 관리

### 7-1강 : 대화 메시지 구조와 session별 history
- **핵심 개념**:
  - 6장까지의 체인은 **입력 하나 → 결과 하나**였다. 다음 호출에 이전 대화가 자동으로 넘어가지 않는다.
    - "제 이름은 민지입니다." → (다음 호출) "제 이름이 뭐였나요?" — 두 번째 질문만 보내면 모델은 첫 문장을 모른다.
  - 그래서 **애플리케이션이** 메시지를 저장했다가 다음 호출에 다시 넘겨줘야 한다.
  - 대화는 **역할이 붙은 메시지 객체**로 저장한다. 그냥 문자열에는 "누가 말했는지"가 없다.
  | 클래스 | 역할 |
  |---|---|
  | `HumanMessage` | 사용자 질문 |
  | `AIMessage` | 모델 답변 |
  | `SystemMessage` | 모델의 역할과 답변 원칙 (개념만) |
  | `BaseMessage` | 공통 부모 (타입 표시용) |
- **history와 session_id**:
  - `InMemoryChatMessageHistory()` — 한 세션의 메시지 목록. `add_messages([HumanMessage(...), AIMessage(...)])`로 추가, `history.messages`로 순서대로 읽기.
  - *"history가 답변을 스스로 만들지 않는다"* — 이미 일어난 대화를 순서대로 **보관만** 한다.
  - `session_id`는 대화를 저장하는 게 아니라 **알맞은 history를 찾는 키**다. `store: dict[str, InMemoryChatMessageHistory]`
  - `get_session_history(store, session_id)` — 처음 보는 ID면 새로 만들고, 있으면 **기존 객체를 돌려준다.**
  - `validate_session_id()` — 공백만 있는 ID는 `ValueError`. 빈 키 하나에 여러 대화가 섞이는 실수를 미리 막는다.
- **"메모리에 저장된다"의 뜻**: Python 프로그램이 켜져 있는 동안만 남는다. 끄면 사라지고, 다른 프로세스와 공유되지 않는다. 영구 저장은 이번 범위 밖.
- **QA 체크포인트**:
  - **값 비교가 아니라 객체 동일성(`is`)으로 검증한다.** 같은 세션을 두 번 조회했을 때 `first is second` → True, 다른 세션은 `is not` → True. 내용이 같은 새 객체가 나와도 "같은 history"가 아니면 앞선 대화가 사라진다(오류 5).
  - **세션 격리는 0건이어야 하는 결함 유형이다.** 한 세션에 추가해도 다른 세션 메시지 수가 그대로인지 확인한다. 실제 서비스라면 다른 사용자의 대화가 섞이는 건 **개인정보 사고**다.
  - **개수 불변식으로 결정적 검증** — 대화 n번 = 메시지 2n개 (student-a 4개, student-b 2개, 새 history 0개).
  - **순서 불변식** — Human → AI, 첫 질문 → 첫 답변 → 두 번째 질문 → 두 번째 답변. 한쪽만 저장하거나 순서가 바뀌는 케이스를 테스트에 넣는다(오류 3).
  - **공백 session_id 거부 = 경계값 입력 검증.** `""`, `"   "` 같은 값을 테스트 목록에 넣는다.
  - **재실행하면 기록이 사라지는 건 버그가 아니다(오류 6).** 결함 보고 전에 **요구사항(영구 저장이 범위인지)** 부터 확인하는 습관.

### 7-2강 : RunnableWithMessageHistory와 Retriever/Memory 비교
- **핵심 개념**:
  - *"기록을 저장했다는 사실만으로 모델이 이전 대화를 알게 되는 것은 아닙니다."* — **저장 ≠ 주입.** 다음 호출 때 history를 Prompt에 넣어야 모델이 읽는다.
  | 동작 | 목적 | 실행 시점 |
  |---|---|---|
  | history 조회 | 현재 세션의 이전 메시지 찾기 | 모델 호출 전 |
  | history 주입 | 이전 메시지를 Prompt에 포함 | 모델 호출 전 |
  | 현재 질문 전달 | 이번에 답할 질문 추가 | 모델 호출 시 |
  | 새 대화 저장 | 다음 호출용 기록 갱신 | **모델 호출 후** |
- **MessagesPlaceholder**:
  - `ChatPromptTemplate.from_messages([("system", ...), MessagesPlaceholder(variable_name="history"), ("human", "{question}")])`
  - 이미 만들어진 메시지 목록을 지정한 자리에 펼쳐 넣는다. 순서는 **system 지시 → 이전 대화 → 현재 질문**으로 고정.
- **`ask_session()` 흐름**:
  - `history = get_session_history(store, session_id)` → `chain.invoke({"history": list(history.messages), "question": question})` → 답변을 받은 **뒤에** `[HumanMessage, AIMessage]` 한 쌍 저장
  - **현재 질문을 호출 전에 저장하면** history와 `{question}`에 질문이 **두 번** 들어간다.
- **RunnableWithMessageHistory (기존 래퍼, 참고만)**:
  - 체인을 감싸 history 조회·갱신을 대신 해 주던 래퍼. session_id는 `config={"configurable": {"session_id": ...}}`로 전달.
  - langchain-core **1.3.3부터 폐기 예정, 2.0.0에서 제거 예정** → 완성 실습에서는 쓰지 않고, 조회·주입·갱신을 직접 한다. 대체 방향은 LangGraph persistence(후속 과정).
- **Retriever vs 대화 history — 서로 대신할 수 없다**:
  | 비교 | Retriever | 대화 history |
  |---|---|---|
  | 가져오는 정보 | 외부 문서 | 현재 세션의 이전 메시지 |
  | 대표 입력 | 검색 질의 | session_id |
  | 대표 결과 | Document 목록 | BaseMessage 목록 |
  | 목적 | 질문 관련 근거 찾기 | 대화 흐름 이어가기 |
  - 교안 정리: **외부 지식은 Retriever, 현재 대화는 history.**
- **QA 체크포인트**:
  - **"질문이 두 번 들어가는가"가 핵심 확인 항목 (오류 4).** 겉보기 답변은 멀쩡해도 Prompt 안에서 질문이 중복되면 토큰 낭비이고, 모델이 같은 질문을 두 번 받은 것처럼 반응할 수 있다. **최종 답변이 아니라 모델에 들어간 메시지 목록**을 확인해야 잡히는 결함이다.
  - **모델 문장과 무관하게 고정되어야 하는 값** — *"세션별 메시지 수는 모델의 문장과 관계없이 각각 4개와 2개여야 합니다."* 답변은 "민지" 포함 여부만 느슨하게 보고, 구조(메시지 수·대화 횟수)는 정확히 본다.
  - **연습문제 2 `ask_offline` = 모델 없이 history 갱신 검증.** 고정 답변 함수로 "호출 전 이전 메시지 0개 → 2개"를 결정적으로 확인한다.
  - **세션 격리의 내용 검증** — student-b의 답변·history에 student-a의 이름(민지)이 **없어야** 한다. 개수뿐 아니라 내용 누출도 본다.
  - **폐기 예정 API 의존 = 버전 리스크.** 지난 TIL의 `uv.lock` 버전 고정과 같은 맥락이다. 라이브러리를 올리는 순간 깨질 코드를 미리 피한다.
  - **키 없으면 네트워크 요청 없이 정상 종료**, 호출 3회로 고정 — 비용 예측이 가능한 실습 설계.

## 8장. Streaming/Callback/Tracing을 활용한 실행 관측

### 8-1강 : Streaming 응답과 Callback Handler
- **핵심 개념**:
  - 흐름이 **두 갈래**다.
  | 구분 | 확인하는 내용 | 출력 |
  |---|---|---|
  | 답변 흐름 | 모델이 만든 실제 문장 | `chain.stream()`이 내보내는 조각 |
  | 실행 흐름 | 모델 호출의 시작·진행·완료·오류 | Callback Handler가 받는 이벤트 |
  - **Callback은 답변을 만들지 않는다.** 실행 중 일어난 사건을 받아 기록하거나 표시할 뿐, Prompt·답변·Parser 결과를 바꾸지 않는다.
  - **Handler를 붙여도 모델 요청은 1번 그대로다.**
- **Streaming**:
  - `for raw_chunk in chain.stream(input_data, config={"callbacks": [handler]}):` → `print(chunk, end="", flush=True)` + `collected_chunks.append(chunk)`
  - 화면 출력과 전체 문자열 저장은 **같은 반복문에서 둘 다** 할 수 있다. 끝나면 `"".join(collected_chunks)`, 비어 있으면 `ValueError`.
  - 조각의 개수와 경계는 **실행마다 다르다.** 한 조각 = 한 글자 / 한 단어라고 가정하지 않는다.
- **Callback Handler (`BaseCallbackHandler` 상속)**:
  | 메서드 | 실행 시점 | 이번 실습에서 하는 일 |
  |---|---|---|
  | `on_chat_model_start` | 모델 호출 시작 | 개수 0으로 초기화, 시작 출력 |
  | `on_llm_new_token` | 새 출력 조각 도착 | 비어 있지 않은 문자열이면 +1 (조각을 출력하지는 않음) |
  | `on_llm_end` | 정상 완료 | 완료와 이벤트 수 N 출력 |
  | `on_llm_error` | 호출 실패 | 예외 **클래스 이름만** 출력 |
  - `on_llm_new_token`의 token은 tokenizer의 토큰 1개와 같다고 보장되지 않는다 → "출력 이벤트 조각"으로 이해.
  - Handler는 체인을 만들 때가 아니라 **실행 config에 리스트로** 넘긴다.
- **QA 체크포인트**:
  - **"stream 조각 수"를 정답으로 비교하지 않는다 (오류 6).** `handler.text_event_count`(모델 쪽 이벤트 수)와 `len(collected_chunks)`(Parser 뒤 조각 수)는 **관찰 지점이 달라서** 같다는 보장이 없다. 성공 기준은 **합친 문자열이 비어 있지 않은지**. 바뀌는 값을 기대값으로 고정하면 flaky test가 된다.
  - **이벤트 수 N이 크다/작다로 품질을 판단하지 않는다.** 측정값과 품질 지표를 혼동하지 않기.
  - **연습문제 2·3 = Handler 메서드를 직접 호출하는 단위 테스트.** API 없이 `on_llm_new_token("안녕")`, `("")`, `("하세요")`를 넣어 빈 문자열 제외 로직(결과 2)을 확인한다.
  - **재사용 Handler의 상태 오염** — 시작 이벤트에서 카운트를 초기화하지 않으면 이전 실행의 값이 섞인다(연습문제 3). 테스트 간 상태 누수와 같은 유형의 결함.
  - **답변이 두 번 출력되는 결함 (오류 3)** — Callback에서도 조각을 출력하면 화면에 같은 답이 두 번 보인다. "출력은 한 곳에서만"이 설계 규칙.
  - **오류 로그는 클래스 이름만** — 예외 메시지 전체에는 요청 내용이나 민감정보가 섞일 수 있다. 오류는 호출자에게도 그대로 전달된다.

### 8-2강 : LangSmith 또는 대체 tracing 도구 활용
- **핵심 개념**:
  - **Tracing** — 한 요청이 거친 단계와 각 단계의 시작·끝을 연결해서 기록하는 방법.
  - 강의 제목은 "LangSmith 또는 대체 도구"지만 **본문은 Langfuse만** 다룬다.
  - 관찰 방법 두 가지:
    - **항상**: `LocalTraceHandler`가 터미널에 실행 시간·토큰 사용량 출력
    - **동의와 인증이 있을 때만**: Langfuse `CallbackHandler`가 같은 실행을 외부로 전송
  - *"Langfuse 업로드는 기본적으로 꺼져 있습니다."* 동의·설정·패키지·인증 중 하나라도 없으면 로컬만 실행된다.
- **LocalTraceHandler**:
  - 시작 시 `time.perf_counter()` 기록 → 완료 시 차이 × 1000 = ms. `perf_counter()`는 시스템 시각이 바뀌어도 영향을 덜 받는 경과 시간용 시계.
  - 토큰은 `on_llm_end()`가 받는 `LLMResult`에서 읽는다 (`usage_metadata`의 `input_tokens` / `output_tokens` / `total_tokens`). **Parser를 지난 최종 문자열에는 토큰 정보가 없다** (오류 10).
  - 토큰 정보가 없으면 **추측하거나 0으로 바꾸지 않고 "제공되지 않음"**. `bool`은 `int`의 하위 타입이라 정수로 취급하지 않는다.
- **`invoke()` 1번 ≠ HTTP 요청 1번**:
  - SDK 자동 Retry가 켜져 있으면 요청이 더 나갈 수 있다 → `ChatOpenAI(timeout=20, max_retries=0, use_responses_api=True)`
  - Retry가 나쁘다는 뜻이 아니라 **"실행 한 번"의 경계를 보기 위한 설정**. 운영 Retry 설계는 9장.
- **Langfuse 연결과 검증 순서**:
  - `has_langfuse_settings()` — `ENABLE_LANGFUSE_UPLOAD=="1"` + PUBLIC_KEY + SECRET_KEY + BASE_URL
  - langfuse import는 **함수 안에서**(없어도 실습이 멈추지 않게) → `get_client()` → **`auth_check()`** → `CallbackHandler()`
  - `auth_check()`는 서버에 묻는 동기 호출 → **시작할 때 한 번만**.
  - 원격 검증: `last_trace_id` 읽기 → **`flush()`**(대기 이벤트 전송) → GENERATION observation **재조회** (2초 간격, 최대 31회, 약 60초)
  - 지역별 `LANGFUSE_BASE_URL`이 다르다 (EU / US / Japan / HIPAA). 키가 맞아도 지역 주소가 틀리면 실패.
- **QA 체크포인트**:
  - **검증 단계를 쪼갠다 — "됐다"의 기준이 세 겹이다.**
    | 단계 | 확인된 것 | 아직 확인 안 된 것 |
    |---|---|---|
    | Client 객체 생성 | 코드가 실행됨 | 인증 (오류 7) |
    | `auth_check()` 통과 | 인증 | 데이터 전송 |
    | `flush()` 완료 | ingestion 전송 | **서버 처리·조회 가능** (오류 9) |
    | observation 재조회 성공 | 조회 가능 상태 | — |
    중간 단계 성공을 최종 성공으로 착각하지 않는 것 — 게임 QA에서 "빌드 업로드 완료"와 "스토어 반영 완료"를 구분하는 것과 같은 감각이다.
  - **재조회에 상한이 있다** (최대 31회, 약 60초). 무한 대기하지 않는 bounded polling.
  - **외부 trace에는 Prompt와 답변이 그대로 남는다.** 개인정보·API Key·회사 비밀을 넣지 않는 것이 **테스트 데이터 선정 기준**이 된다. 업로드는 opt-in.
  - **선택 기능의 모든 실패 경로가 본 실행을 막지 않게** — import 실패, 설정 부족, 인증 실패 모두 `(None, None)` → 로컬 진행. 실패 경로별로 "로컬은 정상 동작하는가"를 테스트한다.
  - **결측값은 0이 아니라 None** — 0으로 채우면 비용 집계가 조용히 과소평가된다. 지난 TIL의 "파싱 실패를 빈 dict로 덮지 않는다"와 같은 원칙.
  - **Handler마다 체인을 따로 실행하면 요청이 2배 (오류 6).** callbacks 목록은 **관찰자만 늘리고** invoke는 한 번.
  - **동시성** — 공유 Handler의 `last_trace_id`는 다른 요청 값으로 바뀔 수 있다. 단일 실행 실습에서는 안 보이고 **부하가 걸려야 드러나는 결함**이다.
  - **Claude가 짚어준 교안 불일치**: 코드의 안내 문구("업로드가 비활성화되었거나 설정이 부족해…")와 예시 출력 문구("업로드가 비활성화되어…")가 다르다. 출력 문자열로 판정하는 테스트라면 이런 차이가 그대로 실패가 된다.

## 9장. Retry/Fallback과 오류 대응 패턴

### 9-1강 : with_retry와 예외 유형별 처리
- **핵심 개념**:
  - Retry는 모든 오류를 없애는 기능이 아니라, **다시 실행하면 회복될 가능성이 있는 오류에 제한된 기회를 더 주는 정책**이다.
  - 판단 기준: **같은 입력·같은 경로를 반복했을 때 결과가 달라질 가능성이 있는가?**
  | 예외 | Retry 여부 | 다음 행동 |
  |---|---|---|
  | `TemporaryModelError` (일시 연결 실패, 순간 과부하) | 예 | 허용 횟수 안에서 다시 실행 |
  | `ValueError` (빈 질문) | 아니요 | 입력을 고친 뒤 새로 실행 |
  | `TypeError` (코드·자료형 오류) | 아니요 | 코드와 자료형 계약 확인 |
- **`with_retry()` 설정**:
  - `RunnableLambda(call_model).with_retry(retry_if_exception_type=(TemporaryModelError,), stop_after_attempt=2, wait_exponential_jitter=False)`
  | 인자 | 값 | 의미 |
  |---|---|---|
  | `retry_if_exception_type` | `(TemporaryModelError,)` | 이 예외만 다시 실행 |
  | `stop_after_attempt` | `2` | **최초 호출 포함** 최대 2번 |
  | `wait_exponential_jitter` | `False` | 수업용 — 실제 대기와 무작위 지연 없앰 |
  - `with_retry()`는 원래 Runnable을 바꾸지 않고 **새 Runnable을 반환**한다 → `retry_step.invoke(...)`로 실행.
- **Retry 적용 범위와 계층**:
  - "입력 확인 → 문서 검색 → 모델 호출 → 결과 저장" 중 **모델 호출 단계에만** 붙인다. 전체에 붙이면 검색·저장이 반복되고, 메시지 전송 같은 부작용이 두 번 실행될 수 있다.
  - **Retry ≠ timeout** — Retry는 실패한 호출을 다시 실행하고, timeout은 한 번의 호출이 기다릴 시간을 제한한다.
  - 바깥 `stop_after_attempt=2` × 클라이언트 내부 Retry(최초 + 2회) → 최악 **2 × 3 = 6회**. 한 계층만 관리하고 내부는 `max_retries=0`.
- **QA 체크포인트**:
  - **3개 사례 매트릭스가 그대로 테스트 케이스 설계 틀이다.**
    | 사례 | 결과 | 실제 호출 수 |
    |---|---|---|
    | 복구 (1번 실패 후 성공) | `success`, 정상 응답 | 2 |
    | 소진 (계속 실패) | `error=TemporaryModelError` | 2 |
    | 제외 (빈 질문) | `error=ValueError` | **1** |
    교안: Retry 정책이 맞는지는 **성공 결과만으로 판단할 수 없고**, 제외 대상 오류가 정말 1번만 호출됐는지까지 봐야 한다. `stop_after_attempt=3`이어도 ValueError는 1번이다(연습문제 2).
  - **`stop_after_attempt=2`는 "두 번 더"가 아니다 (오해 1).** 경계값 해석 실수 — 설정값이 "총 횟수"인지 "추가 횟수"인지는 항상 문서로 확인한다.
  - **마지막 오류를 빈 문자열로 바꾸지 않는다 (오해 6)** = fail loud. 실패가 성공처럼 보이면 상위 코드도, 모니터링도 장애를 모른다.
  - **결정성 확보 3종** — 계획된 오류 주입, `wait_exponential_jitter=False`, 사례마다 새 `state` dict. 네트워크와 무관하게 매번 같은 결과가 나온다.
  - **지난 과정 8-2강과 같은 원칙** — 그때 "재시도는 명시적으로, 대상을 골라서, 최대 1회"를 직접 코드로 봤다면, 오늘은 LangChain 부품 이름(`with_retry`)으로 같은 정책을 적는다.

### 9-2강 : Fallback model/chain과 graceful degradation
- **핵심 개념**:
  - Retry는 **같은 경로를 반복**한다. Primary를 계속 쓸 수 없으면 반복해도 소용없다 → **검증된 대체 경로로 전환**하는 것이 Fallback.
  | 처리 방식 | 판단 질문 | 예시 |
  |---|---|---|
  | Retry | 같은 경로를 다시 실행하면 회복되는가? | 첫 모델 호출의 일시 오류 |
  | Fallback | 허용된 대체 경로가 있는가? | 상세 답변 대신 고정된 제한 안내 |
  | 즉시 실패 | 반복하거나 대체하면 안 되는 오류인가? | 빈 입력, 코드 오류 |
  - Fallback의 목적은 그럴듯한 답을 만드는 게 아니라 **기능이 제한됐다는 사실과 사용자가 다음에 할 행동**을 알리는 것.
  - **Graceful degradation** — 장애를 숨기는 게 아니라, 쓸 수 있는 기능은 유지하면서 **줄어든 기능을 명확히 표시**하는 방식.
- **같은 출력 계약**:
  - `class UserAnswer(BaseModel): status: Literal["ok","degraded"]; answer: str; route: Literal["primary","fallback"]`
  | 필드 | Primary 정상 | Fallback 전환 |
  |---|---|---|
  | status | `"ok"` | `"degraded"` |
  | answer | 정상 처리 문장 | 기능 제한 + 재시도 안내 |
  | route | `"primary"` | `"fallback"` |
  - 두 경로가 같은 타입이면 화면은 **하나의 타입만 처리하고 상태만 구분**하면 된다.
- **연결**:
  - `RunnableLambda(primary).with_fallbacks([RunnableLambda(fallback)], exceptions_to_handle=(PrimaryUnavailable,))`
  - `PrimaryUnavailable`만 전환 허용. Fallback에는 원래 입력이 그대로 전달되고, **Fallback도 빈 질문은 거부**한다.
  - 실제 모델이라면 내부·외부 Retry를 다 쓴 뒤 Fallback으로 가므로 요청 수와 대기 시간이 겹쳐 커진다 → 최대 요청 수를 한곳에서 계산.
- **QA 체크포인트**:
  - **결과 필드 + 경로별 호출 수를 함께 assert한다.**
    | 경로 | status | route | Primary 호출 | Fallback 호출 |
    |---|---|---|---|---|
    | 정상 | ok | primary | 1 | 0 |
    | 기능 저하 | degraded | fallback | 1 | 1 |
    | 정책 밖 오류 | 결과 없음 | 결과 없음 | 1 | **0** |
    정책 밖 오류에서는 "예외 타입이 `ValueError`인가 + `fallback_calls == 0`인가"로 **오류가 숨지 않았는지** 확인한다.
  - **`exceptions_to_handle=(Exception,)` = 결함 은폐 장치 (오해 3).** 앱이 안 멈추는 대신 입력 오류·코드 오류가 전부 "기능 저하"로 집계된다. 장애 대시보드가 거짓말을 하게 된다.
  - **degraded를 정상 성공으로 집계하지 않는다 (오해 4).** 성공률 지표를 낼 때 `ok`와 `degraded`를 섞으면 Primary 장애가 지표에서 사라진다.
  - **Fallback이 상세 답을 추측하지 않는다 (오해 5).** *"모호한 정상 답을 만드는 것보다 한계를 분명히 알리는 편이 안전하다."* LLM 앱에서 환각을 줄이는 설계 원칙이기도 하다.
  - **`Literal`로 status·route 값 제한** = 스키마 수준에서 잘못된 상태값을 차단. 5장 구조화 출력 검증이 오류 대응에도 그대로 쓰인다.

## 10장. 경량 LLM 앱 통합 실습

### 10-1강 : 통합 앱 아키텍처 설계
- **핵심 개념**:
  - 이번 강의는 **모델을 호출하는 앱을 만들지 않는다.** 다음 강의에서 구현할 문서 Q&A 앱의 **책임과 데이터 계약을 먼저 설계**한다.
  - 결과물 세 가지: **요구사항 딕셔너리, 단계 계획 목록, 테스트 사례 목록.** 교안: *"이 결과는 실제 체인을 대신하지 않습니다."*
- **요구사항 — 필수와 선택을 나눈다**:
  - 필수 7개: `question_input`, `retriever`, `prompt_model_parser`, `structured_output`, `session_history`, `retry_fallback`, `local_trace`
  - 선택 2개: `langfuse_trace`, `persistent_storage`
  - *"개수는 기능의 중요도를 나타내지 않습니다."* 그리고 외부로 데이터를 보내는 선택 기능은 **키가 있다는 이유만으로 자동 활성화하지 않는다.**
- **책임 분할 (데이터 계약)**:
  | 책임 | 받는 값 | 내보내는 값 |
  |---|---|---|
  | 입력 확인 | 질문, session_id | 검증된 요청 |
  | 대화 조회 | session_id | 이전 메시지 목록 |
  | 문서 검색 | 질문 | Document 목록 |
  | Prompt 구성 | 질문, 대화, 문서 | 모델 메시지 |
  | 모델 정책 | 모델 메시지 | 모델 응답 |
  | 구조화 검증 | 모델 응답 | QAResponse |
  | 로컬 관측 | 실행 정보 | trace 레코드 |
  | 대화 저장 | 검증된 질문과 답변 | 갱신된 메시지 목록 |
  - 각 단계를 `Stage(TypedDict)`의 `name` / `input` / `output` / `responsibility` 네 필드로 적는다. 앞 단계 출력과 다음 단계 입력을 나란히 검토할 수 있다.
  - `validate_stage_plan()` — **집합 비교로 누락**을, **`index()` 비교로 순서**를 검사 (`retrieve` < `model_policy`, `structured_parser` < `history_save`).
- **테스트 행렬 — 구현 전에 기대값을 고정**:
  | 사례 | 모델 호출 | 기대 상태 | 기대 경로 |
  |---|---|---|---|
  | 정상 검색 | 실행 | grounded | primary |
  | 검색 결과 0건 | **생략** | not_found | local |
  | 일시 오류 뒤 복구 | 다시 실행 | grounded | **primary** |
  | Primary 지속 실패 | Fallback 실행 | degraded | fallback |
- **QA 체크포인트**:
  - **오라클을 먼저 정의하는 설계 = 테스트 설계가 구현보다 앞선다.** 기대 status·route가 코드보다 먼저 있으니, 구현이 끝나면 표와 대조만 하면 된다.
  - **"Retry로 복구됐으면 최종 경로는 primary" (오류 5).** Retry 안에서 성공한 걸 Fallback 성공으로 기록하면 Fallback 사용률이 부풀려진다. **결과 분류 기준을 명확히 정해 두는 것**도 테스트 설계의 일부다.
  - **검색 0건은 모델 실패가 아니다 (오류 4).** `not_found` / `local`이라는 별도 경로. 실패 유형을 뭉뚱그리면 원인별 대응이 불가능하다.
  - **검증 전 저장 금지 (오류 3)** — *"검증되지 않은 답변이 대화 기록에 저장되지 않게 합니다."* 잘못된 답이 다음 대화로 **전파**되는 결함을 순서 규칙으로 막는다.
  - **단계 검사를 존재·순서 두 가지로 나눈 것** — 같은 단계가 다 있어도 순서가 틀리면 다른 앱이다.
  - **선택 기능이 없어도 필수 앱은 동작해야 한다 (오류 6).** 의존성 경계 테스트 — Langfuse를 끈 상태에서도 4개 사례가 같은 결과인지.

### 10-2강 : 미니 챗봇 또는 문서 Q&A 앱 구현
- **핵심 개념**:
  - Retriever 근거 + 세션 대화 기록을 **하나의 Prompt**로 묶고, 출력을 `QAResponse`로 검증하고, 검증된 답만 저장한다.
  - *"history는 현재 세션의 앞선 대화이고, context는 현재 질문으로 검색한 외부 문서입니다. 두 값은 서로 대신할 수 없습니다."*
- **9단계 실행 흐름**:
  | 순서 | 단계 | 핵심 결과 |
  |---|---|---|
  | 1 | 입력 확인 | 비어 있지 않은 질문과 session_id |
  | 2 | 문서 검색 | 관련 Document 목록 |
  | 3 | 검색 0건 확인 | 모델 호출 또는 **not_found 종료** |
  | 4 | 대화 조회 | 현재 세션의 최근 메시지 |
  | 5 | Prompt 구성 | 질문, History, context |
  | 6 | Model·Parser | QAResponse |
  | 7 | 출처 검증 | 검색 결과 안의 문서 ID |
  | 8 | 대화 저장 | 검증된 질문과 답변 |
  | 9 | UI 표시 | 답변 문자열 조각 |
- **QAResponse — 모든 경로를 하나의 타입으로**:
  | 필드 | 자료형 | 역할 |
  |---|---|---|
  | status | `"grounded"` 또는 `"not_found"` | 검색 근거 사용 여부 |
  | answer | `str` | 최종 답변 |
  | sources | `list[str]` | 사용한 문서 ID |
  - `@model_validator(mode="after")` — grounded인데 sources가 비면 오류, not_found인데 sources가 있으면 오류. **필드 모양뿐 아니라 필드 사이의 관계**까지 검증한다.
- **출처 대조**:
  - `allowed_sources = {검색된 문서의 document_id}` → `set(result.sources).issubset(allowed_sources)`가 아니면 `ValueError`.
  - Parser는 sources가 "문자열 목록"인지만 안다. **실제로 검색한 문서인지**는 앱이 따로 확인해야 한다 (오류 3).
- **세부 구현**:
  - `search_documents(top_k=2)` — 6-2강과 같은 키워드 점수 방식
  - `format_history()` — 최근 4개 메시지(`messages[-4:]`)만 "사용자:" / "도우미:" 접두어로. 없으면 "이전 대화 없음"
  - `stream_validated_answer()` — **이미 검증이 끝난 완성 문자열**을 단어 단위로 나눠 보여 줄 뿐, 8장의 모델 토큰 스트리밍이 아니다.
  - not_found 경로에서는 History를 새로 만들지도, 저장하지도 않는다.
- **실행 모드**:
  | 조건 | 선택 체인 | 모델 호출 |
  |---|---|---|
  | `OPENAI_API_KEY` 없음 | `build_offline_chain()` | 없음 |
  | `OPENAI_API_KEY` 있음 | `build_live_chain()` | 실제 호출 시도 |
  - 두 체인 모두 `dict[str, str]` → `QAResponse`. 그래서 `DocumentQAApp`은 어느 체인인지 몰라도 된다.
  - *"API Key 존재는 live 체인을 선택하는 조건일 뿐 성공 판정이 아닙니다."* 성공은 유효한 키·결제·모델 권한·네트워크·구조화 응답·출처 검증이 **모두** 통과해야 한다.
- **QA 체크포인트**:
  - **검증이 두 겹이다** — ① Pydantic: 형식 + status↔sources 관계 ② 앱: sources가 실제 검색 결과 안에 있는가. 지난 TIL의 "JSON 문법 ≠ 스키마 ≠ 비즈니스 사실" 3단 검증이 **근거(출처)** 영역으로 확장됐다.
  - **오프라인 체인으로 답변 품질을 평가하지 않는다 (오류 6).** 오프라인은 **계약과 연결 순서**를 확인하는 도구다. "테스트 더블로 통과했다"를 "기능이 좋다"로 보고하면 안 된다.
  - **과금 없이 확실히 오프라인으로 돌리려면 터미널 환경변수와 `.env` 양쪽에 키가 없어야 한다.** 터미널에서만 지워도 `load_dotenv()`가 `.env`를 다시 읽으면 live 모드가 된다. 1-2강 "환경변수 우선순위" 함정의 실전판 — **실행 전에 어느 모드로 도는지 출력(`mode=offline`)으로 확인**한다.
  - **검색 0건이면 모델 호출 0회** = 비용 절감이자 환각 방지. 테스트에서 "근거 없는 질문"을 넣었을 때 모델이 **불리지 않았는지**까지 확인한다.
  - **질문마다 새 앱을 만들면 History를 잃는다 (오류 7).** 반대로 독립 테스트를 할 때는 새 앱 상태를 만들어야 한다. **"같은 세션 이어가기 테스트"와 "격리 테스트"는 앱 객체 사용 방식이 정반대**다.
  - **ChatGPT 구독과 API 과금은 별도 (오류 9).** 팀 프로젝트에서 "키는 있는데 왜 안 되지?"의 흔한 원인 — 결제·한도·모델 권한을 체크리스트에 넣는다.

### 10-3강 : 관측/오류 대응/LangGraph 연결 한계 정리
- **핵심 개념**:
  | 구성 요소 | 역할 | 앱 결과를 결정하는가 |
  |---|---|---|
  | `with_retry()` | 지정 오류에서 Primary를 제한적으로 재실행 | 예 |
  | `with_fallbacks()` | Retry 소진 시 대체 결과 반환 | 예 |
  | `RunRecord` | 최종 경로와 Primary 시도 횟수를 로컬 기록 | 아니요 |
  | Langfuse Callback | 같은 실행 이벤트를 선택적으로 관찰 | 아니요 |
  | `choose_orchestration()` | 요구사항을 LCEL / LangGraph 경계에 대조 | 실행 전 설계 판단 |
  - **사용자에게 줄 결과(`ObservedAnswer`)와 관측 기록(`RunRecord`)을 분리**한다.
- **RunRecord — 최소 관측 필드**:
  | 필드 | 확인할 질문 | 성격 |
  |---|---|---|
  | case | 어떤 계획된 장애 조건인가 | 고정 |
  | status | 정상인가, 기능 제한인가 | 정책 값 |
  | route | 누가 결과를 만들었나 | 정책 값 |
  | attempts | Primary를 실제로 몇 번 불렀나 | 정책 값 (1 또는 2) |
  | latency_ms | 전체 처리 시간 | **가변 측정값** |
  | token_usage | 토큰 정보를 구할 수 있나 | 로컬은 `not_available` |
  - **기록하지 않는 것**: 질문 원문, 답변 원문, 비밀 키, 상세 오류 메시지.
- **Retry + Fallback 조합 (세 사례)**:
  - `RunnableLambda(primary).with_retry(..., stop_after_attempt=2, ...).with_fallbacks([RunnableLambda(fallback)], exceptions_to_handle=(TemporaryRunError,))`
  | 사례 | Primary 동작 | 최종 경로 | attempts | Fallback 호출 |
  |---|---|---|---|---|
  | normal | 첫 시도 성공 | primary | 1 | 0 |
  | temporary | 첫 실패, 둘째 성공 | primary | 2 | 0 |
  | persistent | 두 시도 모두 실패 | fallback | 2 | 1 |
  - temporary와 persistent는 **같은 오류 타입**이다. 다른 건 오류 발생 횟수 — 비교하려는 건 오류 종류가 아니라 **"허용한 시도 안에서 회복했는가"**.
- **관측 실패에서 앱 결과 지키기**:
  - `flush_langfuse()` — 실패하면 타입 이름만 출력하고 False. **넓은 예외 처리는 선택 도구의 초기화·전송 경계에만** 둔다.
  - *"chain.invoke()까지 같은 try 블록으로 감싸면 Primary의 실제 오류가 관측 실패처럼 숨겨질 수 있으므로 그렇게 구성하지 않습니다."*
  - trace 검증 — 세 사례의 trace ID를 저장 → flush → 재조회. 조회 전에 **세 사례가 정확히 한 번씩, 세 ID가 서로 다른지** 확인한다.
- **LCEL과 LangGraph의 경계**:
  - *"단계가 여러 개라는 사실만으로 별도 오케스트레이션 도구가 필요한 것은 아닙니다."* 열 단계라도 한 방향으로 끝나면 LCEL로 충분하다.
  | 요구 | 현재 경량 앱 (False) | True가 되는 예 |
  |---|---|---|
  | `needs_loop` | 한 번의 Retry 정책 뒤 종료 | 검색 결과를 평가해 질문을 바꾸고 다시 검색 |
  | `needs_resume` | 한 요청 안에서 완료 | 중단했다가 나중에 이어서 처리 |
  | `needs_human_approval` | 자동으로 결과 반환 | 담당자 승인 뒤 다음 단계 |
  | `needs_persistent_state` | 프로세스 안 임시 상태 | 재시작 뒤에도 중간 상태 복원 |
  - 하나라도 True면 LangGraph 검토 (`any(...)`). 이번 앱은 전부 False라 그래프를 추가하지 않는다.
- **QA 체크포인트**:
  - **결정적인 값과 가변 값을 분리해서 검증한다.** `attempts`·`route`는 정확히 비교하고, `latency_ms`는 0 이상인지만 본다. 연습문제 1이 아예 latency를 빼고 status·route·attempts만 출력하는 이유.
  - **관측 실패가 앱 결과를 바꾸지 않는가 = 결과 불변성 테스트.** 연습문제 2의 `BrokenObserver`(flush에서 RuntimeError) → `status=ok route=primary observer_failure_ignored=True`. 부수 기능에 장애를 주입하고 **본 기능 결과가 그대로인지** 보는 방식은 그대로 테스트 케이스가 된다.
  - **넓은 try로 결함을 숨기지 않는다.** 관측 실패 처리와 본 실행 오류 처리를 같은 블록에 넣으면, 진짜 장애가 "관측 도구 문제"로 분류된다.
  - **trace 검증에서 누락·중복 확인** — 3건 중 2건만 조회돼도 "성공"으로 판정하면 안 된다. 일부 성공을 전체 성공으로 오판하지 않기.
  - **토큰 `not_available` ≠ 0** — 0은 "토큰을 전혀 안 썼다"는 다른 뜻이다. 값이 없음을 표현하는 방식도 데이터 품질이다.
  - **`uv run python -O 실습.py`로 최적화 모드에서도 같은 경로가 나오는지 확인** — `assert`문이 꺼진 환경에서도 로직이 같은지 보는 실행 환경 변화 테스트.
  - **도구 선택 기준이 "단계 수"가 아니라 "제어 흐름 요구"** — 반복·재개·사람 승인·영속 상태. 팀 프로젝트에서 "LangGraph 써야 하나?"가 나오면 이 4개 질문으로 판단할 수 있다.
