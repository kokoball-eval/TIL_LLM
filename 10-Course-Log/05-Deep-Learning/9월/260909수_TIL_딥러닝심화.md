## 8장: 모델 적응 전략과 PEFT(LoRA) 기초

### 8-1강. Prompt Engineering과 Prompt-tuning/PEFT 구분
**핵심:**
- 모델 적응 스펙트럼: 가중치 수정 없는 `Prompt-only` -> 파라미터 1% 미만을 학습하는 `PEFT(LoRA)` -> 모델 전체를 갱신하는 `Full Fine-tuning`
- **Why?** -> 비용 낭비를 막고 튜닝 효과를 객관적으로 입증하기 위해, 모든 신규 태스크는 반드시 Prompt-only Baseline부터 시작 필수
- **실무 표준:** 가상 임베딩 벡터만 학습하는 Prompt-tuning과 달리, 선형층에 어댑터를 병렬 결합하는 PEFT(LoRA)를 표준으로 채택

### 8-2강. Prompt-only Baseline 설계
**핵심:**
- 공정한 기준선 마련을 위해 고정 평가셋, 프롬프트 템플릿 함수, 출력 스키마, 평가 지표(Accuracy, Macro-F1) 4요소 고정
- **Why?** -> 생성 모델 특유의 사족이나 서식 이탈을 필터링하기 위해 `parse_label_only` 같은 엄격한 검수 파싱 로직 필수
- **지표 점검:** 정답률과 별개로 약속된 규격대로 답했는지를 검증하는 '형식 준수율(format_success_rate)'을 함께 측정

### 8-3강. Fine-tuning 적용 조건과 비용
**핵심:**
- 단순 지식 부족은 RAG로, 형식 깨짐은 프롬프트 개선으로 해결하며, 정제된 데이터 기반의 판단 행동 교정이 필요할 때만 파인튜닝 적용
- **비용 산정 4계층:** GPU 대여비(컴퓨팅), 라벨링·검수(데이터), 회귀 테스트(평가), 서빙 인프라 및 롤백(운영)
- **주의:** 문제 정의, 데이터 품질, Baseline 유무, 메트릭, 운영 계획 문서화 없는 조기 학습은 심각한 리소스 낭비 유발

### 8-4강. PEFT 개념과 적용 기준
**핵심:**
- 거대 원본 가중치는 Frozen(동결)하고, 1% 미만의 작은 저랭크 행렬 어댑터(Adapter)만 학습
- **주요 파라미터:** `r`(랭크 차원), `lora_alpha`(스케일 가중치), `target_modules`(어텐션 투영층) 설정을 통해 학습 파라미터 99% 이상 절감
- **운영적 이점:** 원본 베이스 모델 1개만 메모리에 상주시키고, 태스크별 수십 MB 크기의 LoRA 어댑터만 동적 교체 서빙 가능

### 8-5강. Prompt-only vs Fine-tuned Model 결과 비교
**핵심:**
- 동일 평가셋, 정답 라벨, 파싱 규칙, 평가 지표라는 철저한 통제 환경에서 전후 비교 수행
- **리그레션(Regression) 추적:** 평균 정확도가 상승했어도 기존 프롬프트가 잘 맞히던 핵심 케이스를 새로 틀리는지 반드시 점검
- **배포 게이트(Release Gate):** 정량 품질, 지연시간(TTFT/TPOT), 메모리 점유율, 롤백 절차 검증을 모두 통과해야 최종 배포 승인

## 9장: LLM 텍스트 생성 제어 및 채팅 템플릿

### 9-1강. generate()와 max_new_tokens
**핵심:**
- Forward pass(단발성 로짓 계산)와 달리, `generate()`는 다음 토큰 선택과 연결을 반복하는 자기회귀(Autoregressive) while 루프
- **Why?** -> 입력+출력 총합을 제한하는 `max_length` 대신, 순수 신규 생성 토큰 수만 통제하는 `max_new_tokens`를 써야 답변 끊김 방지
- **출력 분리:** `generated_ids` 전체 시퀀스에서 프롬프트 입력 길이를 슬라이싱해야 순수 생성 텍스트만 추출 가능

### 9-2강. Greedy Decoding vs Sampling
**핵심:**
- **Greedy (`do_sample=False`):** 매 스텝 확률 1등 토큰만 선택하여 재현성이 높고 결정적이지만, 단조롭고 반복 루프 발생 위험
- **Sampling (`do_sample=True`):** 확률 분포 기반 무작위 추출로 문장이 자연스럽고 창의적이나, 비결정적이라 환각 위험 수반
- **주의:** `do_sample=False` 상태에서는 temperature, top_k, top_p 값을 수정해도 모델이 완전히 무시함

### 9-3강. Temperature, Top-k, Top-p 실험
**핵심:**
- **temperature:** 확률 분포의 첨도(뾰족함) 조절 (낮을수록 결정적·보수적, 높을수록 다양성 증가)
- **후보군 필터링:** `top_k`는 확률 상위 k개 고정 컷, `top_p`는 누적 확률이 p에 도달할 때까지 가변적으로 후보 수집
- **실무 세팅:** 정보 추출 및 분류 태스크는 저온도(0.1~0.2), 일반 대화나 창작은 `temperature=0.7`, `top_p=0.9` 조합 주로 채택

### 9-4강. Chat Message Role과 Chat Template
**핵심:**
- 챗 모델 입력은 단순 텍스트가 아니라 `system`(지침), `user`(질의), `assistant`(답변) 역할 딕셔너리 구조로 전달 필수
- **Why?** -> 모델별 특수 토큰 포맷(Llama-3, ChatML 등) 파편화를 막기 위해 `tokenizer.apply_chat_template()` 표준 API 활용
- **생성 모드:** 어시스턴트 답변 시작 태그를 열어주기 위해 `add_generation_prompt=True` 옵션 반드시 활성화

### 9-5강. apply_chat_template와 입력 디버깅
**핵심:**
- 챗 출력 이상 시 디코딩 옵션보다 먼저 `tokenize=False` 문자열 확인과 특수 토큰 역디코딩으로 입력 템플릿 정합성 점검
- **Left Padding 필수:** Decoder-only 모델 배치 생성 시 문장 뒤(Right)가 아닌 문장 앞(Left)에 패딩 적용
- **Why?** -> 우측 패딩 시 모델의 주의(Attention)가 PAD 토큰에 갇혀 출력이 침묵하므로, 좌측 패딩으로 '진짜 마지막 토큰'을 맨 우측 열에 정렬
