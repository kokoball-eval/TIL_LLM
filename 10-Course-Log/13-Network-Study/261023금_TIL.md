## 💡 오늘의 학습 총평

- **오늘 나온 약어·용어 정리**

  | 약어·용어 | 풀스펠링 | 한 줄 뜻 |
  |---|---|---|
  | LAN | Local Area Network (근거리 네트워크) | 집·사무실·강의실처럼 **가까운 범위**, 우리가 직접 관리하는 네트워크 |
  | WAN | Wide Area Network (광역 네트워크) | 멀리 떨어진 LAN끼리 잇는 넓은 네트워크. 가장 큰 WAN = **인터넷** |
  | ISP | Internet Service Provider (인터넷 서비스 제공자) | WAN을 관리하는 통신사 (KT, SKT, LG U+ 등) |
  | 프로토콜 | Protocol | 데이터를 주고받는 **약속(규칙)**. HTTP, TCP 등 |
  | HTTP | HyperText Transfer Protocol | 웹·API 요청과 응답을 주고받는 프로토콜 |
  | TCP | Transmission Control Protocol | 패킷이 빠짐없이 순서대로 도착하게 챙기는 프로토콜 (스터디 이름의 그 TCP) |
  | 패킷 / 헤더 | Packet / Header | 큰 데이터를 나눈 **작은 조각** / 조각마다 붙는 **주소표** |
  | IP 주소 | Internet Protocol Address | 데이터를 **"어디로"** 보낼지 정하는 주소 (논리 주소, 장소가 바뀌면 바뀜) |
  | IPv4 | Internet Protocol version 4 | 0~255 숫자 4개를 점으로 잇는 형식 (예: `192.168.0.10`) |
  | DHCP | Dynamic Host Configuration Protocol | 새로 붙은 기기에 IP를 **자동으로 빌려주는** 방식 (집에선 보통 공유기) |
  | 사설 IP / 공인 IP | Private IP / Public IP | LAN 안에서만 통하는 주소(아파트 동·호수) / 인터넷 전체에서 하나뿐인 주소(도로명 주소) |
  | localhost | — (`127.0.0.1`) | **"나 자신"**. 내 컴퓨터 안에서만 통하는 특별한 주소 |
  | `0.0.0.0` (서버 설정) | — | "내가 가진 **모든 주소로** 요청을 받겠다"는 뜻 |
  | MAC 주소 | Media Access Control Address | 네트워크 카드에 붙어 나오는 **기기 이름표** (물리 주소), 16진수 12자리 |
  | NIC | Network Interface Card (네트워크 카드) | 기기를 네트워크에 연결하는 부품. MAC 주소가 여기에 붙어 있다 |
  | OUI | Organizationally Unique Identifier | MAC 주소 **앞 6자리** = 제조사 번호 |
  | 스위치 | Switch | 같은 LAN 안에서 **MAC을 보고** 해당 기기에만 넘겨주는 장비 (아파트 경비실) |
  | 라우터 | Router | 서로 다른 네트워크를 잇고 **목적지 IP를 보고** 다음 길을 정하는 장비 (갈림길 안내원) |
  | 게이트웨이 | Gateway | LAN에서 바깥으로 나가는 **출입문** (집에선 공유기, 2회차에서 자세히) |
  | VPN | Virtual Private Network (가상 사설망) | 인터넷(WAN) 위에 만든 **전용 통로**. 밖에서 회사 LAN 안으로 들어갈 때 사용 |
  | NAS | Network Attached Storage | 네트워크에 붙여 쓰는 저장 장치 (LAN 예시로 등장) |
  | GPU | Graphics Processing Unit | LLM을 돌리는 연산 장치. 큰 모델은 여러 GPU를 빠른 LAN으로 묶어 돌린다 |

- **핵심 통찰: 오늘의 한 문장 — "IP는 '어디로', MAC은 '이번 구간 누구에게'"**
  - `client.chat.completions.create(...)` 한 줄을 부르면 몇 초 만에 답이 온다. 그 사이 내 프롬프트는 **집 LAN → 인터넷(WAN) → 데이터센터 LAN**을 건너 GPU 서버까지 간다. 이 스터디는 그 "???" 구간을 10회차에 걸쳐 채우는 구성이고, 오늘은 **출발점과 주소 체계**를 봤다.
  - 택배 비유가 제일 와닿았다. 송장의 받는 주소(**IP**)는 서울에서 부산까지 그대로지만, 구간마다 "다음은 동네 터미널 → 대전 허브 → 친구 집"처럼 바로 다음 목적지(**MAC**)가 새로 붙는다.

    | 구분 | IP 주소 | MAC 주소 |
    |---|---|---|
    | 역할 | 최종 목적지 | 이번 구간에 넘겨줄 바로 옆 장치 |
    | 성격 | 논리 주소 (붙는 네트워크가 바뀌면 바뀜) | 물리 주소 (기기에 붙은 이름표) |
    | 여정 중 변화 | **처음부터 끝까지 그대로** | **장비를 지날 때마다 바뀜** |
    | 보는 장비 | 라우터 | 스위치 |
    | 결과 | — | 멀리 있는 API 서버는 **내 노트북의 MAC을 모른다** |

- **두 번째 통찰: "Private LLM"의 Private이 네트워크 그림으로 보였다**
  - 회사 GPU 서버에 띄운 모델이 집에서 안 열리는 건 그 서버가 **회사 LAN 안에만** 있어서다. 밖(WAN)에서 들어가려면 VPN 같은 전용 통로가 필요하다.
  - 뒤집어 보면 이게 Private LLM을 쓰는 이유 중 하나다. 외부 API는 프롬프트가 **WAN을 건너 남의 데이터센터 LAN까지** 가지만, 사내 서버에 띄운 모델은 데이터가 **회사 LAN 밖으로 나가지 않는다.** 지금까지 "로컬 모델 = 보안"을 막연히 알고 있었는데, 오늘 "어느 LAN 안에 있느냐"라는 그림으로 이해됐다.

    | 지금까지 배운 장면 | 오늘 배운 네트워크 관점 |
    |---|---|
    | LangChain·RAG에서 Ollama 호출 (`localhost:11434`) | 요청이 **내 컴퓨터 밖으로 나가지 않음** (127.0.0.1 = 나 자신) |
    | FastAPI 서버를 띄울 때 보던 `127.0.0.1:8000` | 기본값이 "나만 받기"라 다른 기기에선 안 열림 |
    | OpenAI 등 외부 API 호출 | 집 LAN → 공유기 → WAN → 데이터센터 LAN |
    | LangChain 스트리밍 응답 | 답변도 수많은 **패킷**으로 나뉘어 오고, 도착하면 순서대로 다시 조립됨 |
    | RAG 3일차 `system_error` (서버 연결 실패) | "연결 실패"가 **어느 구간**에서 났는지는 오늘 배운 주소 체계로 좁혀 볼 수 있음 (🧭 7-①) |

- **세 번째 통찰: 주소는 "고정값"이 아니다 — 바뀌는 게 기본이다**
  - IP는 와이파이를 바꾸면 바뀌고(집 ↔ 카페), DHCP로 **빌린** 주소라 다시 접속해도 바뀔 수 있다. 요즘 폰·노트북은 MAC도 와이파이마다 **무작위**로 쓴다(사생활 보호).
  - 그래서 모두가 접속해야 하는 GPU 서버·모델 서버는 **고정 IP나 도메인(이름)** 을 붙여 둔다. 테스트·설정 관점에서도 "어제 됐던 주소가 오늘도 맞다"는 가정을 하면 안 된다 (🧭 2).

- **향후 계획 및 다짐**
  - 이 스터디를 신청한 이유가 두 가지였다 — **로컬 LLM API 작업을 제대로 이해하는 것**, 그리고 **공장 제어 시스템 쪽 진로**에 대비하는 것. 공정 제어 쪽 장비들도 결국 IP 주소를 갖고 네트워크로 묶여 있을 테니, 오늘 배운 LAN/WAN·IP·MAC이 그 출발점이 될 것 같다.
  - 면접 예상 질문 5개(Q1~Q5)는 외우지 말고 **택배·아파트·Ollama 비유로 말로 설명해 보기**.
  - 다음 2회차: **서브넷 · 게이트웨이 · ARP · NAT** — "우리 집 기기는 전부 사설 IP인데 어떻게 공인 IP 하나로 인터넷에 나갈까?" 오늘 나온 "API 서버는 내 노트북의 MAC을 모른다"에 이어, 서버가 보는 IP는 무엇인지도 2회차에서 이어질 것 같다.

## 🧭 종합 QA 체크포인트

> 아래 상세 내용 전체에 공통으로 적용되는 테스트·품질 관점을 먼저 모았다. 표의 **근거** 번호로 🎯 상세 내용을 찾아볼 수 있다.

### 1. "안 열린다"의 위치부터 찾는다 — 구간별 확인 순서

| 순서 | 확인 | 성공하면 | 실패하면 의심할 곳 | 근거 |
|---|---|---|---|---|
| ① | 서버 PC에서 `localhost:11434`로 접속 | 프로그램은 살아 있음 | 서버 프로그램이 안 켜짐 / 포트가 다름 | 3-3, 3-4 |
| ② | 서버 PC에서 **자기 사설 IP**(`192.168.0.10:11434`)로 접속 | "모두에게 받기" 설정이 켜져 있음 | `OLLAMA_HOST=0.0.0.0` 미설정 (기본은 127.0.0.1만 받음) | 3-4 |
| ③ | **같은 LAN의 다른 기기**에서 사설 IP로 접속 | LAN 안 통신 정상 | 다른 LAN(다른 와이파이)에 있음 / 공용 와이파이의 기기 간 차단 / 방화벽 | 2-4, 3-4 |
| ④ | **LAN 밖(집)** 에서 회사 서버 접속 | VPN 정상 | VPN 미연결 — 회사 LAN 안의 서버는 원래 밖에서 안 보임 | 2-4 |

→ RAG 3일차에서 "근거가 빠진 곳이 검색 단계인가, Context 단계인가"를 나눴던 것과 같은 방식. **"접속 안 됨"이라는 하나의 증상**을 구간별로 쪼개야 고칠 곳이 보인다.

### 2. 주소는 바뀐다 — 테스트·설정에 주소를 박아 두지 않는다

| 바뀌는 것 | 언제 바뀌나 | 테스트·운영에서의 위험 | 대응 | 근거 |
|---|---|---|---|---|
| 내 노트북의 IP | 와이파이를 바꿀 때, DHCP 재할당 | 동기 코드에 적어 둔 `192.168.0.10`이 다음 날 다른 기기를 가리키거나 안 열림 | 서버는 **고정 IP 또는 도메인**, 주소는 설정 파일·환경 변수로 분리 | 3-1, 3-2 |
| 사설 IP의 의미 | 다른 LAN으로 가면 | 같은 `192.168.0.10`이 **집마다 다른 기기** | 사설 IP는 "그 LAN 안에서만" 의미 있다는 걸 전제로 | 3-3 |
| MAC 주소 | 와이파이마다 무작위 MAC | MAC으로 기기를 식별하는 집계는 **같은 기기를 여러 대로** 셀 수 있음 | 기기 식별 기준을 MAC에 의존하지 않기 | 4-1 |

### 3. 바뀌는 것과 그대로인 것 — 로그로 알 수 있는 범위

- 여정 내내 **IP는 그대로, MAC은 구간마다 바뀐다.** 그래서 API 서버가 받은 패킷에는 내 노트북의 MAC이 **없다.**
- QA 관점에서는 "서버 로그에 무엇이 남을 수 있는가"의 한계가 된다. 서버 쪽 기록만으로 **어느 기기**에서 왔는지 MAC으로 추적할 수는 없다. (서버가 보는 IP도 사실 공유기를 거친 주소일 텐데, 그건 2회차 NAT에서 확인할 예정.)

### 4. 열면 노출 범위도 같이 넓어진다 — 기능 확인과 보안 확인은 한 세트

- `OLLAMA_HOST=0.0.0.0` → 동기가 접속되는 **기능은 해결**, 동시에 **같은 와이파이의 누구나** 접속할 수 있게 된다.
- 테스트 항목도 둘로 쓴다: ① 허용한 사람이 **접속되는가** ② 허용하지 않은 범위에서 **접속이 막히는가**. 앞쪽만 확인하고 "해결"로 닫으면 공용 와이파이에서 모델 서버가 열린 채로 남는다.
- RAG 3일차의 "필터는 권한이 아니다"와 같은 결 — **열려 있음 ≠ 허가된 사람만 씀.**

### 5. 같은 설정, 다른 결과 — 재현 환경을 기록한다

| 환경 | 같은 LAN인가 | 기기끼리 통신 | 메모 | 근거 |
|---|---|---|---|---|
| 집 공유기 | 같은 공유기면 O | 보통 됨 | 사설 IP를 공유기가 DHCP로 줌 | 2-3, 3-2 |
| 강의실·라운지 와이파이 | 같은 공유기면 O | **막혀 있을 수 있음** | 공용 와이파이는 기기 간 통신을 차단하기도 함 | 2-4 |
| 회사 LAN 밖 (집) | X | — | 회사 서버는 VPN 필요 | 2-4 |

→ "설정은 맞는데 안 된다"는 리포트에는 **어느 네트워크에서 시도했는지**가 반드시 들어가야 한다. 버그 리포트의 재현 환경 항목(기기·OS·빌드)에 **네트워크 환경**도 한 줄 넣는 습관.

### 6. 큰 데이터는 나눠서 온다 — 패킷과 응답 품질

- 긴 RAG 문서도, 스트리밍으로 오는 답변도 **수많은 패킷**으로 오간다. 조각마다 주소표가 붙고 도착하면 **순서대로 다시 조립**된다.
- 나눠 보내기 때문에 여러 사람이 길을 나눠 쓸 수 있고, **문제 난 조각만 다시 보내면** 된다. 스트리밍 응답이 끊기거나 늦게 오는 현상을 볼 때, 모델 문제인지 전달 구간 문제인지 나눠 볼 출발점.

### 7. Claude가 짚어준 확인 포인트

**① RAG 3일차의 `system_error` 안쪽을 오늘 배운 구간으로 쪼갤 수 있다**
- RAG 3일차에서는 Ollama 호출이 실패하면 `httpx.HTTPError` → `system_error`로 기록하고, 근거 부족(`insufficient`)과 섞지 않는다고 배웠다. 오늘은 그 `system_error` **안쪽**을 볼 수 있게 됐다.
- 같은 "연결 실패"라도 원인이 다르다:

  | 상황 | 어디서 막혔나 | 일반적으로 보이는 증상 |
  |---|---|---|
  | Ollama가 안 켜져 있음 | 내 PC 안 (①) | 바로 거절 (연결 거부) |
  | 기본 설정(127.0.0.1)인데 동기가 내 사설 IP로 접속 | 서버 설정 (②) | 바로 거절 |
  | 방화벽·공용 와이파이 차단 | LAN 구간 (③) | 응답 없이 기다리다 **시간 초과** |
  | 집에서 VPN 없이 회사 서버 접속 | LAN 밖 (④) | 주소에 닿지 못함 / 시간 초과 |

- 그래서 러브코드처럼 Ollama를 부르는 앱이라면 `system_error` 하나로 뭉뚱그리기보다 **연결 거부인지 시간 초과인지** 같은 하위 원인을 trace에 남기는 게 디버깅에 훨씬 유리하다. 2차 Review의 "실패도 같은 모양으로 기록하되 error 타입은 남긴다"를 한 단계 더 세분화한 것.

**② 토론 2번의 답 "공용 와이파이는 기기끼리 통신을 막아 두기도 한다"가 슬라이드 17(Ollama)과 연결된다**
- 슬라이드 17은 `OLLAMA_HOST=0.0.0.0`을 켜면 "같은 와이파이의 동기도 접속할 수 있다"고 했다. 그런데 토론 2번 답에는 **공용 와이파이는 기기 간 통신을 막기도 한다**는 단서가 있다.
- 두 슬라이드를 합치면: 스터디를 하는 **라운지 와이파이에서 직접 해 보면, 설정이 맞아도 동기 접속이 실패할 수 있다.** 이건 설정 문제가 아니라 **환경 문제**다.
- 설정이 맞는데도 실패하는 경우를 "설정 오류"로 판단하면 엉뚱한 곳을 고치게 된다. 그래서 🧭 5처럼 재현 환경에 **어느 네트워크에서 시도했는지**를 꼭 적어야 한다. 게임 QA에서도 같은 빌드가 사내망과 외부망에서 다르게 동작하는 경우를 따로 나눠 보던 것과 같은 원리.

**③ `0.0.0.0`은 "서버가 받을 때"의 값이지, "접속할 때" 쓰는 주소가 아니다**
- 슬라이드 17과 핵심 정리 PDF는 `0.0.0.0`을 "내가 가진 **모든 주소로 받기**"라고 설명한다. 즉 **서버 쪽 설정값**이다.
- 접속하는 쪽(클라이언트)은 내 PC라면 `127.0.0.1`(localhost), 동기의 PC라면 **서버의 사설 IP**(`192.168.0.10`)로 접속한다. `0.0.0.0`을 접속 주소로 쓰는 건 의도된 사용법이 아니다.
- 한 값이 "받는 쪽"과 "보내는 쪽"에서 다른 뜻이라 헷갈리기 쉽다. 설정 문서나 테스트 케이스를 쓸 때 **서버 바인딩 주소(받는 범위)** 와 **접속 주소(찾아갈 곳)** 를 다른 항목으로 나눠 적어 두면 혼동이 줄어든다.

## Part 1. 네트워크 기초

### 1-1 : 네트워크 = 데이터가 다니는 길
- **핵심 개념**:
  - 네트워크 = **두 대 이상의 장치가 데이터를 주고받도록 연결된 것.** 필요한 건 세 가지:

    | 요소 | 예 | 택배 비유 |
    |---|---|---|
    | 장치 | 노트북, 휴대폰, 서버, GPU 머신 | 집 |
    | 연결 | 랜선(유선), 와이파이(무선) | 도로 |
    | 약속 (프로토콜) | HTTP, TCP | 운송장 작성 규칙 |

  - 프로토콜은 서로 알아들을 수 있게 정해 둔 **형식**이다.
- **QA 체크포인트**:
  - "약속(프로토콜)"은 LLM 쪽의 **JSON Schema**와 닮았다 — 양쪽이 같은 형식을 지켜야 통한다. 형식이 어긋나면 내용이 맞아도 상대가 못 읽는다.

### 1-2 : 클라이언트와 서버 — 묻는 쪽과 답하는 쪽
- **핵심 개념**:
  - **클라이언트** = 요청하는 쪽 (내 파이썬 코드, 브라우저) / **서버** = 응답하는 쪽 (OpenAI·Anthropic API).
  - `resp = client.chat.completions.create(...)` 이 한 줄이 **클라이언트가 서버에 요청을 보내고 응답을 받는 것**이다.
  - 핵심 정리 PDF: 정해진 기계가 아니라 **역할**이다. 카페의 손님(클라이언트)과 바리스타(서버).
- **QA 체크포인트**:
  - "역할"이라는 점이 중요하다 — 내 노트북도 Ollama를 띄우면 **서버**가 된다. 문제를 볼 때 "지금 이 기기가 어느 역할인가"부터 정해야 클라이언트 문제인지 서버 문제인지 나눌 수 있다.

### 1-3 : 패킷 — 데이터는 잘게 나눠서 보낸다
- **핵심 개념**:
  - 긴 프롬프트·문서·이미지 같은 큰 데이터는 **작은 조각(패킷)** 으로 나눠 보낸다. 이삿짐을 여러 상자에 나눠 담고 상자마다 주소를 붙이는 것과 같다.
  - **패킷 = 주소표(헤더) + 데이터 조각.** 헤더에는 출발지·목적지가 적힌다 → 오늘 배울 **IP·MAC이 여기에 적히는 정보**.
  - 도착하면 **순서대로 다시 조립**한다.
  - 핵심 정리 PDF: 나눠 보내면 여러 사람이 길을 나눠 쓸 수 있고, **문제 난 조각만 다시** 보내면 된다.
  - LLM에서는: 긴 RAG 문서도, 스트리밍으로 오는 답변도 수많은 패킷으로 오간다.
- **QA 체크포인트**:
  - 큰 요청이 느리거나 실패할 때, 전체를 다시 보내는 게 아니라 **조각 단위 재전송**이 일어난다는 걸 알면 "느림"과 "실패"를 구분해서 볼 수 있다.

## Part 2. LAN과 WAN

### 2-1 : LAN — 우리 집 안의 네트워크
- **핵심 개념**:
  - **LAN** = 집·사무실·강의실처럼 **가까운 범위.** 공유기·스위치 하나에 묶인 장치들. **빠르고, 우리가 직접 관리**한다.
  - 예: 집 와이파이에 붙은 노트북·휴대폰·프린터·NAS. 부트캠프 강의실 와이파이에 같이 붙어 있으면 우리도 **같은 LAN.**
  - 핵심 정리 PDF: 아파트 단지 안 길.
- **QA 체크포인트**:
  - "우리가 직접 관리한다" = 문제가 생기면 **우리가 고칠 수 있는 범위**. 장애 분석에서 "우리 쪽(LAN) 문제인가, 바깥(WAN·통신사) 문제인가"를 먼저 가르는 기준이 된다.

### 2-2 : WAN — LAN과 LAN을 잇는 큰 네트워크
- **핵심 개념**:

  |  | LAN | WAN |
  |---|---|---|
  | 범위 | 집, 사무실, 건물 | 도시, 나라, 전 세계 |
  | 관리 | 나, 우리 회사 | 통신사(ISP: KT, SKT, LG U+ 등) |
  | 속도·비용 | 빠르고 저렴 | 상대적으로 느리고 비쌈 |
  | 비유 | 아파트 단지 안 길 | 도시와 도시를 잇는 고속도로 |

  - 가장 큰 WAN = **인터넷.** 집 LAN, 회사 LAN, OpenAI 데이터센터 LAN을 이어 준다.
- **QA 체크포인트**:
  - WAN은 **우리가 통제할 수 없는 구간**이다. 외부 API 응답 시간에는 이 구간이 항상 포함되므로, 성능 측정 시 로컬 모델(LAN 안)과 외부 API(WAN 경유)를 같은 기준으로 단순 비교하면 안 된다.

### 2-3 : 공유기는 무슨 일을 할까?
- **핵심 개념**: 공유기가 하는 일 세 가지
  1. **LAN 만들기** — 와이파이·랜선으로 집 안 기기를 하나로 묶는다.
  2. **주소 나눠 주기** — 새 기기에 **사설 IP를 자동으로** 준다 (DHCP, Part 3).
  3. **바깥으로 나가는 출입문** — 인터넷으로 가는 데이터는 모두 공유기를 거친다 (게이트웨이, 2회차).
  - 핵심 정리 PDF: 공유기 안에는 **스위치와 라우터 기능이 함께** 들어 있다.
- **QA 체크포인트**:
  - 공유기 하나가 세 역할을 하므로, 공유기 문제는 "연결 안 됨 / 주소 못 받음 / 밖으로 못 나감" 세 가지 다른 증상으로 나타날 수 있다. 증상으로 어느 기능이 문제인지 추정할 수 있다.

### 2-4 : 질문 한 번은 LAN → WAN → LAN 여행 + 토론
- **핵심 개념**:
  - `내 노트북 → 공유기 → 인터넷 → LLM API 서버` = **집 LAN → (LAN의 출입문) → WAN → 데이터센터 LAN.**
  - **회사 GPU 서버가 집에선 안 열리는 이유** — 그 서버는 회사 LAN 안에만 있다. 밖(WAN)에서 들어가려면 **VPN** 같은 전용 통로가 필요하다.
  - **데이터센터 안도 결국 LAN** — 큰 모델은 여러 GPU에 나눠 돌리므로 GPU끼리 **아주 빠른 LAN**으로 촘촘히 묶어 둔다.
- **토론 3문항** (교안 발표자 노트 답):

  | 질문 | 답 |
  |---|---|
  | 내 노트북에서 ChatGPT까지 최소 몇 개의 LAN? | **최소 2개** — 우리 집 LAN과 데이터센터 LAN. 실제로는 그 사이 통신사 내부 네트워크도 여러 개 지난다 |
  | 라운지 와이파이에 붙은 우리 노트북들은 같은 LAN? | 같은 공유기에 붙어 있다면 **같은 LAN.** 다만 **공용 와이파이는 기기끼리 통신을 막아 두기도** 한다 |
  | 회사 GPU 서버의 모델을 집에서 쓰려면? | 회사 LAN 안으로 들어가는 전용 통로, **VPN** |

- **QA 체크포인트**:
  - "같은 LAN이다"와 "서로 통신된다"는 **다른 조건**이다 (토론 2번). 연결 테스트 결과를 해석할 때 둘을 구분해야 한다 (🧭 7-②).
  - 사내 서버 접근 테스트는 **사내망 / 외부망+VPN / 외부망(VPN 없음)** 세 조건으로 나눠야 한다. 마지막은 "안 열리는 게 정상"인 케이스다.

## Part 3. IP 주소

### 3-1 : IP 주소 — 네트워크 위의 집 주소
- **핵심 개념**:
  - 데이터를 **"어디로"** 보낼지 정하는 주소. 택배 송장의 **받는 사람 주소.**
  - IPv4 형식: **0~255 숫자 4개를 점(.)으로** 잇는다 (예: `192.168.0.10`).
  - **어느 네트워크에 붙느냐에 따라 바뀐다** (집 와이파이 ↔ 카페 와이파이). 이사하면 집 주소가 바뀌는 것과 같다.
  - 주소 개수가 한정돼 있어서 아껴 쓰는 방법이 있다 → 사설 IP (3-3).
  - (Claude가 계산해 확인) 숫자 하나가 0~255 = 256가지, 네 자리면 256⁴ = 2³² = **약 42.9억 개.** 전 세계 기기 수를 생각하면 모자랄 수밖에 없다.
- **QA 체크포인트**:
  - **경계값** — 각 자리는 0~255. 설정 화면에서 IP를 입력받는 기능이라면 `256`, 음수, 숫자 3개·5개, 빈 칸 같은 입력을 거르는지가 기본 테스트 항목이다.

### 3-2 : IP는 누가 정해 줄까? — DHCP
- **핵심 개념**:
  - 와이파이에 붙으면 공유기가 **자동으로 사설 IP를 빌려준다** (DHCP). 노트북: "주소 하나 주세요!" → 공유기: "`192.168.0.23` 쓰세요."
  - **빌린** 주소라 다시 접속하면 IP가 바뀔 수도 있다.
  - 그래서 모두가 접속해야 하는 **서버는 보통 고정 IP를 쓰거나 이름(도메인)을 붙여 둔다.**
  - LLM 팁: 사내 Ollama·vLLM 서버 주소가 자꾸 바뀌면 곤란하다 → **고정 IP나 도메인으로.**
- **QA 체크포인트**:
  - "어제 되던 주소가 오늘 안 된다"의 흔한 원인. 테스트 코드·설정에 IP를 **하드코딩하지 않고** 환경 변수·설정 파일로 빼 두면 주소가 바뀌어도 한 곳만 고치면 된다 (🧭 2).

### 3-3 : 사설 IP vs 공인 IP, 그리고 localhost
- **핵심 개념**:

  |  | 사설 IP | 공인 IP |
  |---|---|---|
  | 비유 | 아파트 **동·호수** | **도로명 주소** |
  | 통하는 범위 | 우리 LAN 안에서만 | 인터넷 전체에서 딱 하나 |
  | 중복 | 다른 집도 같은 번호를 씀 | 없음 |
  | 누가 주나 | 공유기 (DHCP) | 통신사(ISP). 보통 집 공유기가 하나를 받음 |
  | 예 | `192.168.x.x`, `10.x.x.x`, `172.16.x.x ~ 172.31.x.x` | — |

  - 다른 아파트에도 101동 1001호가 있듯, 다른 집에도 `192.168.0.10`이 있다.
  - **`127.0.0.1` (localhost) = "나 자신".** 내 컴퓨터 안에서만 통하는 특별한 주소.
- **QA 체크포인트**:
  - 사설 IP는 **그 LAN 안에서만 의미가 있는 값**이다. 다른 장소에서 받은 버그 리포트에 `192.168.0.10`이 적혀 있어도, 내 환경의 `192.168.0.10`과 같은 기기라는 보장이 없다.

### 3-4 : LLM 연결고리 — Ollama, 옆자리 동기는 왜 접속이 안 될까?
- **핵심 개념**:
  1. 내 노트북에서 Ollama 실행 → `localhost:11434` **잘 된다.**
  2. 동기가 `192.168.0.10:11434`(내 사설 IP)로 접속 → **실패!**
  3. 이유: 기본 설정은 **`127.0.0.1`(나 자신)의 요청만** 받는다.
  - 해결: "나만 받기" → "모두에게 받기"로 바꾸는 설정 **`OLLAMA_HOST=0.0.0.0`** 을 켜면 같은 와이파이의 동기도 접속할 수 있다. `0.0.0.0` = "내가 가진 **모든 주소로** 받기."
  - **주의**: 모두에게 받기로 열면 **같은 와이파이의 누구나** 접속할 수 있다. 공용 와이파이에서는 조심.
- **QA 체크포인트**:
  - **"나에게선 되는데 남에게선 안 된다"** 의 전형. 개발자 PC에서 `localhost`로만 확인하고 "정상"으로 닫으면 이 버그를 놓친다 → 접속 테스트는 **다른 기기에서도** 해야 한다.
  - 해결책이 곧 **노출 범위 확대**다. "접속된다"와 "허용 범위 밖은 막힌다"를 함께 확인 (🧭 4).
  - `0.0.0.0`은 서버가 **받을 범위**를 정하는 값, 접속할 땐 `127.0.0.1`이나 사설 IP를 쓴다 (🧭 7-③).

## Part 4. MAC 주소

### 4-1 : MAC 주소 — 기기에 새겨진 이름표
- **핵심 개념**:
  - 네트워크 카드(NIC)마다 **공장에서 붙여 나오는 번호.** 숫자와 영문자(A~F)로 된 **12자리** (예: `3C:22:FB:7A:1E:09`).
  - **앞 6자리: 제조사 번호**(OUI) / **뒤 6자리: 기기마다 다른 번호.**
  - **같은 LAN 안에서 "바로 옆 장치"를 찾을 때** 쓴다. IP처럼 장소에 따라 바뀌는 주소가 아니라 **기기 자체에 붙은 번호.**
  - 요즘 폰·노트북은 **와이파이마다 무작위 MAC**을 쓰기도 한다 (사생활 보호).
  - (Claude가 계산해 확인) 16진수 한 자리 = 16가지, 12자리면 16¹² = 2⁴⁸ ≈ **281조 개.** 뒤 6자리만 해도 2²⁴ ≈ 1,677만 개라 한 제조사가 이만큼을 구분해 붙일 수 있다.
- **QA 체크포인트**:
  - "기기에 고정된 번호"라고 배웠는데 **무작위 MAC**이 있다 — 규칙에는 예외가 있다는 사례. MAC으로 기기를 식별·집계하는 기능이라면 **같은 기기가 다른 기기로 잡히는 경우**를 테스트해야 한다 (🧭 2).

### 4-2 : IP와 MAC, 왜 둘 다 필요할까?
- **핵심 개념**:
  - 택배: `서울 우리 집 → 동네 터미널 → 대전 허브 → 부산 친구 집`
    - **IP 주소** = "부산 ○○로 12" (최종 목적지) → **처음부터 끝까지 그대로**
    - **MAC 주소** = 구간마다 **"바로 다음에 받을 곳"으로 새로 붙는 이름표** (→ 동네 터미널 → 대전 허브 → 부산 친구 집)
  - 그래서 **멀리 있는 OpenAI 서버는 내 노트북의 MAC을 모른다.**
  - 핵심 정리 PDF: **스위치**는 같은 LAN 안에서 MAC을 보고 그 기기에만 넘겨주고(아파트 경비실), **라우터**는 서로 다른 네트워크를 잇고 목적지 IP를 보고 다음 길을 정한다(갈림길 안내원).
- **QA 체크포인트**:
  - **어떤 정보가 어디까지 전달되는가**를 아는 게 로그 분석의 전제다. 서버 측 기록만으로는 출발 기기의 MAC을 알 수 없다 (🧭 3).

### 4-3 : 내 프롬프트의 여정 따라가 보기 (1/5 ~ 5/5)
- **핵심 개념**:

  | 단계 | 위치 | 봉투의 IP (최종 목적지) | 봉투의 MAC (바로 다음) |
  |---|---|---|---|
  | 1/5 | 내 노트북 (출발) | API 서버 | → 공유기 |
  | 2/5 | 공유기 도착 | API 서버 (그대로) | → 통신사 라우터 (새로 붙음) |
  | 3/5 | 통신사 라우터 도착 | API 서버 (그대로) | → 인터넷 라우터 (또 바뀜) |
  | 4/5 | 인터넷 라우터 도착 | API 서버 (그대로) | → API 서버 (마지막 구간) |
  | 5/5 | API 서버 도착 | API 서버 | 도착 완료! |

  - **IP는 한 번도 안 바뀌고, MAC은 장비를 지날 때마다 바뀐다.** 4-2의 택배 비유와 똑같다.
- **QA 체크포인트**:
  - 표로 보면 **"변하지 않는 값(불변식)"과 "구간마다 바뀌는 값"** 이 분명하다. 테스트에서도 단계마다 "그대로여야 하는 값"과 "바뀌어야 하는 값"을 나눠 확인하면 이상한 지점을 빨리 찾는다 — RAG 3일차에서 단계별 state를 출력해 어디서 생겼는지 찾던 것과 같은 방식.

## 5. 면접 예상 질문 · 정리

- **면접 예상 질문** (핵심 정리 PDF 모범 답안 요약):

  | 질문 | 답 | 설명할 때 쓸 비유 |
  |---|---|---|
  | Q1. LAN과 WAN의 차이는? | LAN은 가까운 범위를 **우리가 직접 관리**하는 네트워크, WAN은 LAN끼리 잇는 넓은 네트워크로 **주로 통신사가 관리**. 제일 큰 WAN이 인터넷 | 단지 안 길 vs 고속도로 |
  | Q2. IP 주소와 MAC 주소의 차이는? | IP는 위치에 따라 바뀌는 **논리 주소**로 최종 목적지를 가리킴. MAC은 기기에 붙은 **물리 주소**로 같은 LAN 안에서 바로 다음 장치에 넘길 때 씀. 그래서 목적지 IP는 끝까지 그대로, MAC은 장비를 지날 때마다 바뀜 | 택배 주소와 구간별 이름표 |
  | Q3. 사설 IP를 쓰는 이유는? | ① IPv4 주소가 모자라서 LAN 안에서만 쓰는 주소를 따로 두고 아껴 씀 ② 인터넷에서 쓰지 않기로 약속된 주소라 내부에서 써도 공인 IP와 **겹치지 않음** | 아파트 동·호수 vs 도로명 주소 |
  | Q4. localhost(127.0.0.1)는? | **"나 자신"** 을 가리키는 주소. 내 컴퓨터 안에서만 통함 | Ollama가 옆자리에서 안 열리던 이유 |
  | Q5. DHCP는? | 새 기기에 IP를 **자동으로 빌려주는** 방식. 주소가 겹치지 않게 나눠 주고, 집에서는 보통 공유기가 해 줌 | "주소 하나 주세요!" |

- **오늘의 한 잔 요약**:
  1. **LAN과 WAN** — LAN은 가까운 우리끼리, 인터넷(WAN)은 LAN을 잇는 큰 길
  2. **IP 주소** — "어디로" 보낼지 정하는 주소 · 사설 · 공인 · localhost
  3. **MAC 주소** — "이번 구간 누구에게" 넘길지 정하는 기기 이름표
- **다음 메뉴 (2회차 · 네트워크 주소와 통신)**: 서브넷 · 게이트웨이 · ARP · NAT — 공유기는 어떻게 우리 모두를 **공인 IP 하나로** 내보낼까?
- **QA 체크포인트**:
  - 면접 답을 외우는 대신 **비유로 설명**하라는 안내가 좋았다. QA 면접에서도 "결함을 비개발자에게 설명하기"가 중요한 역량이라, 같은 연습이 된다.
